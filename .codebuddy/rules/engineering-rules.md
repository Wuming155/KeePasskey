# 工程规则

## 结构与依赖

- 围绕领域职责组织代码，跨模块走公开接口，依赖方向见 [架构](../../docs/architecture/ARCHITECTURE.md)。
- 优先组合与构造注入，Android 依赖沿用 Hilt；避免全局可变状态、职责混杂的工具类和不必要的转发层。
- 文件和函数按可理解的职责拆分，不设机械行数阈值，不为达标拆出无意义的小文件。命名表达领域与动作，不维护后缀白名单。
- 格式签名、协议字段和有业务含义的边界使用命名常量；状态用 enum 或 sealed 类型。

## 错误、并发与持久化

- 跨模块失败沿用 core 的结果类型，给出可处理的错误语义；不将外部异常 message 直接显示给用户。
- 协程取消必须传播，作用域与生命周期对应；不使用 GlobalScope 承担业务。仓库对自身 suspend API 的线程安全和调度负责。
- KDF、加解密、XML 和网络/文件 IO 离开主线程。提交边界须能在取消和失败时保持一致，不留下“内存已更新、文件未写”的半步状态。
- 现有私有库先写临时件、同步落盘，再原子替换；新建库排他创建，不覆盖既有文件。流使用 use 关闭。SAF 的非原子边界见 [工程边界](../../docs/architecture/已知工程限界.md)。

## 敏感数据与平台

- 密码、密钥及派生材料优先使用 CharArray/ByteArray，按 [所有权契约](../../docs/architecture/敏感缓冲所有权契约.md) 清理，禁止擦除借用或仍存活的共享实例。
- Rust 秘密缓冲用 Zeroizing 或等价确定性清理；不引入 C/C++ 秘密管理。日志、异常和 toString 不输出敏感内容，测试只用虚构凭据。
- Screen 消费 ViewModel 状态、上报事件；状态保持不可变。确认 Compose 内容槽布局，用预览检查重要状态和系统大字号。
- 系统凭据服务不能依赖主界面存活；交付前复核会话、调用方和请求身份。窗口与剪贴板保护遵守 [设计约定](../../docs/architecture/产品裁决登记.md)。
- R8 规则按实际反射或 JNI 需求最小保留，改动后用真实 release 构建验证，不以源码字面检查代替打包。

## 测试

- 测试按行为与风险准入，不要求每次改动都新增用例。新增前先查已有覆盖；仅对尚未覆盖的重要行为、边界或可复现缺陷补充测试，优先扩展已有用例或表驱动数据，不按任务编号另建测试文件。
- 优先测试输入输出、状态迁移、协议向量和文件结果；失败、取消、并发与恢复路径按风险覆盖。在能够证明目标行为的最低成本层验证；只有平台、跨模块或独立实现才可证明的风险再增加对应层级测试，跨层重复须说明各自验证的不同契约。
- 不新增只锁定源码文本、注释、私有结构或非契约调用次数的测试；静态约束优先使用现有编译器、Lint 或扫描入口，不为每次整改增加专用扫描脚本。新增长期检查须说明现有工具无法覆盖的风险及维护成本。
- 修改行为时同步更新、合并或删除失效和重复用例；临时排查探针放已忽略的 build/，需要长期回归时提炼为最小行为测试。密码算法向量、数据完整性、失败恢复和互操作覆盖退役须说明风险为何消失或由何处替代，不得为消除失败而删除测试、弱化断言或长期跳过。
- 测试变更在提交或 PR 说明中交代新增覆盖、已有覆盖复用及合并删除的理由，评审核对实际风险收益、执行稳定性和维护成本；不另建测试台账，不以用例数或覆盖率数字单独作为验收目标。
- app JVM 的 ViewModel 用既有 MainDispatcherGuard 跟踪与收尾，避免后台任务污染后续用例。Rust 单测沿用独立 src/tests 文件布局。
- 运行受影响的标准测试；设备用例和原生改动按 [设备测试规则](../../AGENTS.md#工作规则) 实跑，优先复用已有专用测试 AVD，按需清理环境。跳过与零用例不得当作通过。

## 文档维护流程

### 归属与新增条件

文档职责以 [文档体系与入口](../../docs/README.md) 为准。先定位已有维护位置，优先替换或补充对应段落；其它文件只链接，不复制同一套规则、参数、问题状态或验证数字。

新增永久文档须同时满足以下条件，并在变更说明中交代，无需为此另写申请文档：

1. 有明确读者和会反复发生的使用场景，内容在本次任务结束后仍需维护。
2. 现有文件没有合适归属；把内容放进去会混淆职责，而不只是使文件变长。
3. 内容不能由代码、配置、测试、工具帮助或运行报告直接提供，并能明确由哪些后续变更触发更新。

满足条件时按主题命名，放入现有职责目录，并更新 docs/README.md 的入口、职责与更新时机。新增顶层分类、独立指南或拆分现有文件，也按同一条件判断。用户明确要求的报告可按指定形式交付；只有满足上述条件才纳入长期维护目录。

禁止默认创建按日期、问题编号或批次命名的审计报告、整改方案、完成总结与交接记录；不恢复 records、resolved 等流水归档目录，也不把多个文件简单拼成一个长期增长的汇总。工具使用说明和测试样本说明就近维护，不在 docs 中复制一份。

### 每次变更的步骤

1. **定位**：按文档入口判断本次是否改变用户行为、开发流程、模块边界、设计取舍、安全契约或数据政策；未改变这些事实时可以不改文档。
2. **就地更新**：改写受影响段落，同时删除旧说法、重复说明与失效链接。保留当前结论、必要理由和适用前提，不追加“本轮”“后续补记”或逐次更正流水。
3. **处理问题状态**：新缺陷只登记在 ACTIVE_ISSUES.md，包含影响、核实时间与方式及关闭条件；未验证完成的仍保留。关闭后移除条目，将仍有维护价值的约束归入对应主题，实际修改与验证结果写入提交或 PR 说明。接受风险须有已明确的产品取舍及理由，不能仅靠迁入工程边界文档就视为解决。
4. **放置证据**：日志、测试报告、截图和临时计划放本地已忽略的 build/ 或 CI artifact。长期复现所需的最小公开样本和生成方法随测试保存；证据描述注明版本、环境和实际位置，不能把会清理或过期的产物称为永久存档。不得保存真实凭据或用户库。
5. **检查并交付**：运行 `python tools/doc/check_md_links.py`，复核命令、路径和结论与实际交付一致；目录变化时同步入口。代码与受影响文档在同次变更交付，提交和推送仍按用户授权执行。

### 收敛与退役

- 每次触及一篇文档，顺带清除相关章节的过期信息与重复内容；不要求为此定期产出新的审计或盘点报告。
- 主题失效时直接删除；合并或迁移时同批改引用并删除旧副本，不保留空壳、旧编号指针或归档索引来维持历史结构。
- 设计发生变化时替换旧决策，确有必要时保留一句变更理由；完整演进由 Git 历史承接。只有已提交内容才能从 Git 恢复，未提交材料需要保留时先提炼结论或明确交付位置。
- 不追求文件数或行数指标。增长时先检查是否混入历史流水、实现复述或第二份事实源，再决定是否按独立读者与职责拆分；不得把增长机械转移到一个更大的文件或新的登记表。
- 文档变更评审核对四件事：是否有明确用途、是否归属唯一、是否替换旧信息、是否有可执行的更新与退役时机。无需另建检查台账。
