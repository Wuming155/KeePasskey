## 一、密钥隔离：AndroidKeyStore 与 StrongBox

### ✅ 符合规范的实现

| 项目 | 实现 | 官方依据 |
|---|---|---|
| Keystore Provider | `KeyStore.getInstance("AndroidKeyStore")`，密钥材料不可导出 | 《Android Keystore system》 |
| 算法 | AES-256-GCM（`KEY_ALGORITHM_AES` + `BLOCK_MODE_GCM` + `NoPadding` + 256 位） | 《security-tips#Cryptography》："Use 256-bit AES"、"GCM mode 提供完整性" |
| 用途限定 | 仅 `PURPOSE_ENCRYPT or PURPOSE_DECRYPT`，未开放 WRAP/SIGN | 《KeyGenParameterSpec》用途授权最小化 |
| StrongBox | 先检测 `FEATURE_STRONGBOX_KEYSTORE`，`setIsStrongBoxBacked(true)` 优先落 StrongBox，捕获 `StrongBoxUnavailableException` 后回退 TEE | 《privacy-and-security/keystore》StrongBox 章节逐条对齐（含回退要求） |
| 认证绑定 | `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG \| AUTH_DEVICE_CREDENTIAL)` per-operation 授权；旧规格密钥经 `KeyInfo.getUserAuthenticationType` 探测后自动重建迁移 | 《KeyGenParameterSpec.Builder#setUserAuthenticationRequired》 |
| 生物特征失效策略 | 纯生物识别密钥 `setInvalidatedByBiometricEnrollment(true)`；含锁屏凭据的密钥不设该标志（与官方"AUTH_DEVICE_CREDENTIAL 下忽略"语义一致） | 同上 |
| Provider 选择 | 未显式指定 provider（未传 `"BC"` 等） | 《privacy-and-security/cryptography》："requesting a specific provider is discouraged" |
| Jetpack security-crypto | 未使用（该库 1.1.0 已废弃，官方不再维护） | 《privacy-and-security/cryptography#Deprecated》 |

### ⚠️ 发现与建议（P2 加固，非漏洞）

1. **缺少密钥认证（Key Attestation）**。官方文档明确 StrongBox 支持 key attestation，可用 `setAttestationChallenge()` 验证密钥确实落在硬件（TEE/SE）而非软件模拟 Keystore。对密码管理器而言，建议在首次生成密钥时做一次 attestation 校验并记录结果，防御被 root 设备上的软件 Keystore 伪装。
2. **建议补充 `setUnlockedDeviceRequired(true)`**。官方文档说明该标志要求设备处于解锁态才可使用密钥（与认证要求互补）。注意：Android 12–14 存在官方文档列出的已知缺陷（无锁屏时密钥不可用、移除锁屏自动删钥等），**Android 15+ 已修复**——本项目 minSdk 36，可安全启用。
3. `KeystoreManager` 的 `context: Context?` 可空设计导致单测路径下 `isStrongBoxSupported` 恒为 false。生产 DI 路径无影响，但建议把"能力探测"抽为接口注入，避免测试与生产行为分支差异。

**结论：密钥隔离实现与官方规范高度一致，无发现漏洞。**

## 二、加密参数与 IV 随机性

### ✅ 符合规范的实现

1. **快速解锁封印（AES-256-GCM）**
   - 认证标签 128 位（`GCM_TAG_LENGTH_BITS = 128`）✓
   - 未调用 `setRandomizedEncryptionRequired(false)`，即保持 Keystore 默认的"加密必须随机化"——每次 `cipher.init(ENCRYPT_MODE, key)` 由安全硬件生成新鲜随机 IV，硬件侧维护 IV 计数器防重用 ✓
   - IV 经 `cipher.iv` 取出后与密文一并 Base64 存入 SharedPreferences（`saveEncryptedCredential`）。**IV 本身不是机密，此存储方式正确**；配合硬件密钥，XML 明文泄露无法解密 ✓
   - GCM IV 唯一性由 Keystore 硬件保证，无重用风险。历史遗留的 Android 9–11 重启后 IV 计数器重置缺陷已在 API 31+ 修复，本项目 minSdk 36 不受影响 ✓
2. **KDBX 库文件加密**
   - AES-256-CBC 属 KDBX 标准强制；完整性由外层 HMAC-SHA-256 流承担（`KdbxFile` 中 `hmacKey64` 派生链完整），等价官方推荐的 "CBC/CTR + HMAC-SHA-256/512" 组合 ✓
   - 每次 `save()` 时 `masterSeed / encryptionIv / salt` 均由 `SecureRandom` 重新生成（`freshEncryptionIv` 等），保存即换 IV，无跨版本重用 ✓
   - ChaCha20 引擎 nonce 12 字节、AES/Twofish IV 16 字节，与 KDBX4 规范及 KeePass 2.61.1 硬校验一致 ✓
3. **随机源**：所有密钥/种子/IV 均由 `java.security.SecureRandom` 生成，未出现 `Random(...)` 用于安全用途（仅测试代码中存在固定种子，合规）✓

### ⚠️ 唯一需要评审的取舍：`InMemoryCipher` 的确定性 IV

`core/security/InMemoryCipher.kt` 使用 `AES/CTR/NoPadding`，IV = `SHA-256(进程密钥 ‖ 明文)` 前 16 字节，**同一明文恒产生同一（IV, 密文）**，以维持 `ProtectedString.equals` 的相等性语义。

- **不是官方定义的"IV 重用漏洞"**：官方警告的重用指"不同明文使用相同 IV 导致密钥流复用"；本实现不同明文 → 不同 IV → 不同密钥流，密钥流不复用。
- **真实代价是等值泄露（equality leakage）**：攻击者拿到多个时刻的堆 dump，可判断"两个受保护字段的明文是否相同"（如检测不同条目复用了同一密码、频繁出现相同 TOTP 前缀等），且 CTR 无认证标签（可篡改性在内存防御层场景可接受）。
- **建议的严格更优方案（消除确定性加密）**：把"相等性比较"与"加密"解耦——
  1. 另存一个 `HMAC-SHA256(进程密钥, 明文)` 比较标签用于 equals/hashCode/合并检测；
  2. 实际加密改用每次 `SecureRandom` 生成的新 IV。
  这样比较语义不变，但堆中不再存在可关联的确定性密文，完全消除等值泄露面。
- 现状与 KeePassDX `protectInMemory` 同级取舍，且文档中已如实声明边界，可作为 P3 演进项。

## 三、内存明文安全（Zeroization）

### ✅ 已建成的防线（超出一般开源项目水准）

- **主密码全链路 CharArray 化**：`SecurePasswordField` → `UnlockViewModel` → `VaultRepository` → `DatabaseSession`，输入组件在 `onDispose`/内容变更时 `fill('0')`；ViewModel 持有私有 CharArray 副本并自行擦除，不进 UiState/StateFlow。
- **`DatabaseSession` 凭据缓存**：密码/密钥文件以 CharArray/ByteArray 缓存，换库、改密、会话结束均显式 `Arrays.fill` 清零；`useCredentials {}` 提供克隆副本 + 使用后清零契约。
- **`ProtectedString` 堆内密文驻留**：受保护字段（密码/TOTP 种子/Passkey 私钥）经 `InMemoryCipher` 加密驻留，读取瞬间才物化明文并清零；提供 `useChars {}` 安全闭包。
- **KDBX 派生链擦除**：`KdbxFile` 中 compositeKey、transformedKey、cipherKey、HMAC 密钥等中间产物全部 `Arrays.fill` 清零。
- **外围卫生**：WebDAV 同步在请求构建后立即清零 `passwordChars`；Autofill 服务在任何返回路径清零密码 CharArray；日志中无明文。

### ⚠️ 残留的 String 泄漏点（真实发现）

String 不可变且无法擦除，以下位置仍会因 `String`/`toCharArray()` 在堆上留下无法回收擦除的明文副本：

| # | 位置 | 问题 | 严重度 | 建议 |
|---|---|---|---|---|
| M1 | `EntryEditViewModel.kt`：`passwordChars = state.password.toCharArray()` | `UiState.password` 以 String 持有条目密码，`toCharArray()` 的副本可擦除，但源 String 不可擦除，编辑期间驻留堆 | 中 | 编辑表单字段改用 CharArray 桥接（复用 `SecurePasswordField` 模式），或仅在保存瞬间物化 |
| M2 | `EntryDetailViewModel.kt`：`revisionPassword?.toCharArray()` | 同上，历史版本密码以 String 承载 | 中 | 同 M1 |
| M3 | `SettingsScreen.kt`：`newPassword.toCharArray()`（修改主密码对话框） | 新主密码先入 String 状态再转 CharArray | 中 | 对话框内部改走 CharArray 直通（对齐 `DatabasePickerScreen` 的 H2 整改模式） |
| M4 | `PasswordSaveActivity.kt`：`password.toCharArray()`（来自 Intent） | 密码经 Intent extra（String）跨进程/跨组件传递，在系统 Parcel 与接收方堆各留副本 | 中高 | 改为把明文写入进程内单例/内存封印存储，Intent 只传引用键；或接收后引导用户重建凭据 |
| M5 | `SecurePasswordField`：内部显示用 String | 组件内部 String 仅存活于输入过程（已文档化的取舍）。Compose `TextField` 只接受 String，无法完全消除 | 低 | 已是当前生态最优解；可在 `onDispose` 外再增加"失焦即清显示态"缩短寿命 |
| M6 | `SettingsScreen`/`UnlockScreen` 的普通文本框残留（如数据库备注、非密码字段） | 非敏感，无需处理 | 信息 | — |

**官方规范对照**：Android 官方《security-tips》要求"尽量减少敏感数据存活时间、避免以 String 长期持有"；官方未提供 JCA 级 zeroization API，业界共识（与 OWASP MASVS 一致）即本项目已采用的 CharArray + 显式 `fill` 方案。M1–M4 是最后一段未闭合的链路。

## 四、结论与优先级

| 优先级 | 事项 |
|---|---|
| ✅ 通过 | AndroidKeyStore 用法、StrongBox 优先+回退、GCM 参数（256 位密钥 / 128 位标签 / 硬件随机 IV）、KDBX IV 每次保存刷新、SecureRandom 全覆盖、Derived-key 擦除链、CharArray 主密码链路 |
| P2（加固） | ① 密钥生成后硬件落位校验；② minSdk 36 下启用 `setUnlockedDeviceRequired(true)`；③ `InMemoryCipher` 改为 HMAC 等值标签 + 随机 IV 加密，消除确定性密文 |
| P3（收敛） | M1–M4 四处 String 密码残留改为 CharArray 直通；M4（Intent 传密码）优先级最高 |

未发现可直接利用的高危漏洞；核心风险面为 UI 层 String 明文残留（M1–M4）与确定性内存加密的等值泄露（低危、已声明取舍）。

## 五、整改实施记录（2026-09-06 同日完成）

> 完整性说明：原报告 P2-① 建议对 AES 密钥启用 Key Attestation（`setAttestationChallenge`）。
> 实施时核实官方规范：**attestation 仅适用于非对称密钥（KeyPairGenerator），AES 对称密钥不支持**。
> 故改为等效落位校验方案：`KeyInfo.getSecurityLevel()`（API 31+，minSdk 36 恒可用）直接探测
> 密钥实际落位（StrongBox / TEE / 软件），生成即告警软件级落位——这正是 attestation 想要回答的问题，
> 且无证书链验证与 Google 根证书固定负担。

### P2 加固（全部完成）

| 项 | 实施 |
|---|---|
| ① 密钥硬件落位校验 | `KeystoreManager` 新增 `KeySecurityLevel` 枚举与 `getKeySecurityLevel(alias)`（基于 `KeyInfo.getSecurityLevel()`）；`generateKeyInternal` 生成后自动校验，SOFTWARE 级记录告警（不硬失败，兼容模拟器/CI） |
| ② `setUnlockedDeviceRequired` | `generateKeyInternal` 增加 `unlockedDeviceRequired`（默认随 `requireUserAuth`）：认证绑定密钥启用（官方文档确认 Android 15+ 无已知缺陷，minSdk 36 安全）；非认证密钥（WebDAV 同步封印）保持 false，锁屏后台同步不受影响 |
| ③ InMemoryCipher 确定性加密 | 重构为「HMAC-SHA256 等值标签 + 随机 IV 加密」：主密钥经域分离派生 encKey/eqKey（主密钥派生后清零）；seal 每次以 SecureRandom 生成新 IV（密钥流永不复用）；`ProtectedString.equals/hashCode` 改比较 HMAC 标签（`MessageDigest.isEqual` 常时时间比较）；clear 连同 iv/tag 一并擦除。等值语义不变（同明文同标签），堆中不再存在可跨实例关联的确定性密文 |

### P3 收敛（全部完成）

| 项 | 实施 |
