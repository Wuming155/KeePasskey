### 83.1 为什么必须「分别断言」而不是「注入 DTD 就抛异常」

防护由**三层中任意一层存活即可拦住**构成（`startDTD` 兜底、`resolveEntity` 兜底、
工厂特性开关）。笼统断言「注入 `<!DOCTYPE>` 会抛 `KdbxCorruptFileException`」的问题在于：
**三层里只要还剩一层，断言就仍然是绿的**——它无法回答「我们依赖的那一层是否真的在设备上生效」。
三条前置依赖各自可能在本平台静默失效：

| 编号 | 前置依赖 | 失效后的表现 |
|---|---|---|
| **D-1** | `parse(InputStream, DefaultHandler)` 走 `ParserAdapter` 时，handler **实现 `EntityResolver`** 才会被注册为实体解析器 | `resolveEntity` 永不回调，第二道兜底形同不存在 |
| **D-2** | 平台 SAX 层**不**自行短路外部实体 | 若平台自行拒绝则我们的兜底「看起来生效」其实是平台功劳；反之若平台放行而我们误以为它兜住，就是缺口 |
| **D-3** | `setProperty(lexical-handler)` 在平台可用 | **仅记 WARNING** 地静默降级——`startDTD` 兜底整体失效，而这正是内部实体炸弹的总闸 |

### 83.2 用例清单与各自能 / 不能证明什么（如实声明）

新增 `database/src/androidTest/java/com/keepasskey/database/xml/KdbxXmlDtdRejectionDeviceTest.kt`（5 例）：

| 用例 | 断言 | 能证明 | **不能**证明 |
|---|---|---|---|
| `D1 解析 handler 必须是 EntityResolver` | `DefaultHandler2` 确为 `EntityResolver` | D-1 的**结构性前置**成立（ParserAdapter 据此注册实体解析器） | 不构成端到端证据——是类型层前置 |
| `D3 DOCTYPE 必须由 startDTD 兜底拒绝而非特性开关` | 异常文案为 DTD 兜底那句 | **D-3 成立**：`setProperty(lexical-handler)` 在本平台可用，`startDTD` 真的被调用 | 对 D-1/D-2 无话可说 |
| `D2 外部实体载荷必须被拒绝` | 外部实体载荷被拒绝，且拒绝点在 DTD 声明处 | 端到端被拒绝；且**外部实体根本没有机会被解析** | **无法把实体层单独隔离**——本平台 `startDTD` 先触发。要隔离须移除 DTD 兜底，而那正是我们不做的 |
| `内部实体展开炸弹在展开前中止` | 10 层嵌套 `&aN;` 载荷被拒 | 炸弹在**展开之前**即中止（不会先撑爆内存） | —— |
| `无 DTD 文档不得被 DTD 兜底误伤` | 无 DTD 文档不落 DTD 文案异常 | **反向对照**：兜底只认 DTD 声明，不误伤合法库 | —— |

**关于 AC 的原始措辞**：原 AC 要求「注入 DTD 的**合法口令 KDBX** 必抛异常」。本批按第四轮定版建议
改为直接喂 XML——外层 KDBX 需要**重新加密**才能构造，而外层字节解析与 DTD 无关，
只会把断言推离被保护的那一层。

### 83.4 为什么这些用例必须留在设备侧

`KdbxXmlParser` 的加固是**探测式**的：`buildHardenedParser` 逐特性试建 parser，建不起来的项跳过并
告警（ISSUE-P1-12 的设备侧实测缺陷：Android 的 `setFeature` 不校验、延迟到 `newSAXParser()` 才抛）。
宿主 JVM 的 Xerces 与 Android 的 Expat 对同一批特性的接受度**不同**，因此「哪几层在设备上真的
生效」只能在设备上回答——这正是本项当初被登记为「测试有效性缺口」的原因。

### 83.5 附带产出：`ISSUE-P2-47` 的代码取证复核（该条**未**闭环）

本批对表内 P2 首条做了一次实施前复核，结论已逐条写回该条目，要点：

1. **AC② 按原文不可实施**：`KdbxFile.kt:337` 保存时 `p.copy(salt = freshSalt)`、`:342`
   `masterSeed = freshMasterSeed` ⇒ **KDF 盐与主种子每次保存都重新生成** ⇒ 任何「库 header 摘要」
   都会每次保存都变；照原文绑定将使**每次保存后快速解锁立即失效**（核心功能回归）。
   且封印载荷持有的是主密码：「回滚到旧主密码版本」的旧口令本就解不开当前库；
   「库与封印被一致回滚」是同步防回滚链（AC①）的职责。
   ⇒ 须改设计或登记为已接受边界，**属架构决策，不得由实施者自行择一**。
2. **AC① 实质已具备**：已见内容摘要链即**本地记录**（不依赖服务端版本号）；`ReplayDetected`
   在三处裁决点均**不应用**远端，落为 `SyncOutcome.Error(sync_error_rollback_rejected)`——
   不存在静默覆盖。
3. **`sequence` 刻意不改格式**：让它「看起来有用」需变更 MAC 载荷 ⇒ 全部存量状态文件 MAC 失效
   ⇒ 按既有 fail-open 口径给所有存量用户打开一次重放窗口，代价大于收益。
4. **AC③ 尚缺**：引擎级「远端回退 → 拒绝且不覆盖本地」用例待补。

**本批未把 `ISSUE-P2-47` 读作已闭环**——它卡在上述设计取舍；本批的价值是**阻止一次会造成
功能回归的照做实施**，并把决策点显式登记出来。
