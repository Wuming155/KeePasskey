## 3. 判定与探针（平台查询单点化）

| 环节 | 实现 | 说明 |
|---|---|---|
| 纯判定 | `passkey/CredentialProviderRegistration.of(systemState)`（新增） | 三态：`ENABLED` ⇒ `REGISTERED`、`DISABLED` ⇒ `NOT_REGISTERED`、`UNREADABLE` ⇒ `UNKNOWN` |
| 读取结果类型 | `passkey/CredentialProviderEnabledState`（同文件，enum） | `ENABLED` / `DISABLED` / `UNREADABLE`：不用 `Boolean?` 表达——`null` 既可能是「系统服务不可得」也可能是「组件名推导失败」，而调用方极易顺手写成 `?: true`（＝谎报正常），故以枚举显式表达 |
| 平台查询单点 | `passkey/CredentialProviderHealthProbe.probe()`（新增，`@Singleton`） | 唯一调用 `android.credentials.CredentialManager.isEnabledCredentialProviderService(ComponentName)`（API 34+ **公开** API）的生产点；系统服务不可得 / 调用抛异常一律收敛为 `UNREADABLE` 并落 `AppLog.w`（只记失败事实与异常类型）；组件名经 `ComponentName(context, KeePasskeyCredentialProviderService::class.java)` 推导（`applicationId` 与源码命名空间不一致，硬编码即判错） |
| 初版方案与其被推翻（如实留痕） | 曾读 `Settings.Secure.credential_service`（§240 证明的路由权威） | 真机抛 `SecurityException`（该键对普通应用**不可读**）⇒ 判定永远停在「未知」；改公开 API 后两态均可判定。守卫 `不得回到读取内部键 credential_service` 防其被「凭记忆」改回（见 §5） |
| 报告映射 | `autofill/AutofillHealthPolicy`：新增 `credentialProviderRegistration`（**无默认值**）+ 两个异常项 | `NOT_REGISTERED` ⇒ `CREDENTIAL_PROVIDER_NOT_REGISTERED`；`UNKNOWN` ⇒ `CREDENTIAL_PROVIDER_STATE_UNKNOWN`；`REGISTERED` ⇒ 无项 |
| 边界（不得外推） | `isLegacyAutofillOperational` **不含** CM 登记态 | CM 未登记只影响保存 / 通行密钥通道，传统 `AutofillService` 照常工作——计入即会给用户**错误的修复指引**（与 `ISSUE-P3-113` 字段屏蔽项同口径） |
| 界面 | `AutofillHealthCard`：两项各配文案；`HealthIssueRow` 的入口由 `if (issue == SYSTEM_NOT_ENABLED)` 改为 `when(issue)`，两项共用 `SystemSettingsNavigation.credentialProviderIntent(context)` | 入口不可解析时返回 `null` ⇒ 只留纯文案（既有三条 action 的同一条硬约束）；**真机实测本机 ROM 无该 activity 命中**，故实际呈现为纯文案，见 §4.4 与限界 §27 |

**文案定稿**（zh / en 各两条）：

| 资源键 | 取值（zh） | 取值（en，节录） |
|---|---|---|
| `autofill_health_issue_cp_not_registered` | 系统未把本应用登记为凭据提供者，保存密码 / 通行密钥的请求不会被发到本应用（点「保存」会没有反应）；请在系统设置的「凭据提供程序」中把 KeePasskey 设为当前服务 | The system has not registered this app as a credential provider, so password / passkey save requests are never routed here (tapping "Save" does nothing); open system settings, go to credential providers and select KeePasskey as the current service |
| `autofill_health_issue_cp_state_unknown` | 无法读取系统的凭据提供者登记状态，当前状态未知；若保存密码 / 通行密钥时没有反应，请在系统设置的「凭据提供程序」中确认 KeePasskey 已被选中 | The system credential provider registration could not be read, so the current state is unknown; … |

「未登记」文案刻意写明**用户可感知的后果**（点「保存」没有反应）——否则用户无法把「状态」与「现象」对上。

## 4. 真机验证（2026-09-21，Redmi 4X / santoni，Android 17 · API 37）

**工具口径**：界面取证走 `android layout`（Android CLI 的 uiautomator 等价物）；输入注入（点击 / 文本）
Android CLI 无对应命令，按 CLI 官方 `references/interact.md` 以 `adb shell input` 为**退路**（同 §243）。
系统侧路由取证复用 §240/§241 入库的**独立包名 CM 探针** `com.keepasskey.test/…CredentialSaveClientActivity`
（未改一行），以 `logcat` 观察。

**环境前提**：设备现有库 `passwords.kdbx`（§244 建的虚构口令测试库）**未改动**；本批另建
`e2e-p2-239.kdbx`（虚构主密码，不入文档）用于登入设置页，用毕即按 §4.3 清理。

### 4.1 两态实测（判决性读数）

| 状态 | 系统侧 `credential_service` | 健康卡（`android layout` 逐字读数） | 系统路由实测（CM 探针 `logcat`） |
|:--:|---|---|---|
| **A 已登记** | `com.keepasskey/com.keepasskey.app.passkey.KeePasskeyCredentialProviderService` | 仅 `• 系统未选择本应用为自动填充服务，请前往系统设置启用`（**无** CM 异常项） | `Provider session created …` → `Provider status changed: SAVE_ENTRIES_RECEIVED`（**请求被路由到本应用**） |
| **B 未登记**（`settings delete secure credential_service`） | `null` | `• 系统未把本应用登记为凭据提供者，保存密码 / 通行密钥的请求不会被发到本应用（点「保存」会没有反应）；请在系统设置的「凭据提供程序」中把 KeePasskey 设为当前服务` | `starting executeCreateCredential …` → `CM-SAVE-STATUS:onError type=…TYPE_NO_CREATE_OPTIONS`（**框架层丢弃，与 §240 E3 同症状**） |
| A 复原 | 同 A | CM 异常项**消失**（与 A 逐字一致） | — |

⇒ 健康卡的判定与**真实路由行为**在两态下逐一对应（「未登记」正是「点保存没反应」的成因），
且状态恢复后判定同步复原（非一次性快照）。

### 4.2 一次被现场推翻的初版设计（如实留痕）

初版探针读的是 `Settings.Secure.credential_service`（§240 已证明它是路由权威）。真机上该读**抛
`java.lang.SecurityException`**，卡面如实出现 `• 无法读取系统的凭据提供者登记状态，当前状态未知；…`
——**AC② 的行为是对的**（读取失败 ⇒ 未知，未谎报正常），但判定在该 ROM 上**永远无法给出结论**。
随后改用公开 API `android.credentials.CredentialManager.isEnabledCredentialProviderService(
ComponentName)`（API 34+，`Context.CREDENTIAL_SERVICE` 为公开常量、无需任何权限），
并按下述三条取得其与路由权威的一致性证据：

1. 系统侧日志逐字：`I/CredentialManager: isEnabledCredentialProviderService with componentName:
   com.keepasskey/com.keepasskey.app.passkey.KeePasskeyCredentialProviderService`（该调用确实抵达框架）；
2. 状态 B 下该调用同时给出 `W/CredentialManager: isEnabledCredentialProviderService component name
   does not match requested component`（＝false），而同轮创建请求以 `TYPE_NO_CREATE_OPTIONS` 被丢弃
   ⇒ 该 API 的 false 与「系统不路由」同态；
3. 状态 A 下卡面无 CM 异常项且创建请求被正常路由 ⇒ 该 API 的 true 与「系统会路由」同态。
   （`CM-SAVE-STATUS:enabledProbeThrew=IllegalArgumentException` 是**测试探针自身**在 release 环境下的
   反射类名问题，属 §244 已登记的既有边界，与产品代码无关。）

### 4.3 收尾

测试库 `e2e-p2-239.kdbx` 已按界面动作移除（确认弹窗与 §246 §6 同形，正文指名该文件），
设备活动库回到 `passwords.kdbx`、`files/` 与 `shared_prefs/keepasskey_vault_meta.xml` 与操作前逐项一致；
`credential_service` 已复原为原值；应用以 `force-stop` 收尾。取证用的构建即为本批的正式 release 包
（`flags=[ HAS_CODE ALLOW_CLEAR_USER_DATA ]`，**非** debuggable），故设备未留调试构建。

### 4.4 一键直达入口在本机 ROM 上如实降级（AC① 的负向分支）

`android.settings.CREDENTIAL_PROVIDER` 在**本机不可解析**：`cmd package resolve-activity` 在
**shell 视角**（无包可见性过滤）下同样返回 `No activity found`（对照组 `android.settings.ACCESSIBILITY_SETTINGS`
有命中）⇒ 健康卡该项**不渲染**「打开系统设置」按钮，只保留纯文案「请在系统设置的『凭据提供程序』中…」
——即 AC① 要求的「如实降级说明，不得伪造『已开启』」。该可用性差异已登记
[`../../architecture/已知工程限界.md`](../../architecture/已知工程限界.md) §27。

## 7. 如实声明（边界与未验证项）

1. **「公开 API 与路由权威等价」只在本机 ROM 上取得三条证据**（§4.2）：API 调用抵达框架、
   状态 B 下 API=false 且创建请求被 `TYPE_NO_CREATE_OPTIONS` 丢弃、状态 A 下 API=true 且请求被正常路由。
   **不得**据此断言「所有 ROM 上二者恒等价」——该 API 的实现由各 ROM 自持，本批未在第二台设备上复测。
   若将来出现二者背离（API 报「已启用」而保存仍无反应），本判定会给出**偏乐观**的结论；届时应按
   §4.2 的三条证据重新对齐，必要时改回「读权威 + 不可读即未知」的保守口径。
2. **初版方案（读 `Settings.Secure.credential_service`）已被推翻并留痕**：该键对普通应用**不可读**
   （真机 `SecurityException`），说明「读内部键」这条路在 API 37 上不可行；守卫用例
   `不得回到读取内部键 credential_service` 防止后人「凭记忆」改回。
3. **未覆盖**：① 真机上 `CredentialProviderRegistration.UNKNOWN` 这一态的**端到端**呈现——
   本批用初版方案（读内部键必抛）实证过该态卡面，但最终方案下未再构造出「系统服务不可得 /
   调用抛异常」的真实场景（该态由 4 例用例锁定其映射）；② 中英文两套文案**在真机上只验了中文**
   （设备为中文环境，英文取值由 `CredentialProviderHealthWiringTest` 的解析断言锁定）；
   ③ 设置页其它既有异常项（自动填充未选中 / 权限等）未逐项复测，仅观察到与改动前一致。
4. **未改动任何判定 / 放行语义**：`KeePasskeyCredentialProviderService` 的两条入口、
   `RuntimeIntegrityGate` 门控、黑名单与 DAL 校验**一行未改**；本批只新增「读系统状态 → 呈现」这一条
