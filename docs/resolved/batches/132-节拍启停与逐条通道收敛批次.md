## 2. 本批实现

### 2.1 详情页节拍随订阅期启停（对应 AC ①）

原状：`init` 里 `viewModelScope.launch(Dispatchers.Default) { totpTicker.run(...) }` ——
只要 ViewModel 活着（含页面退到后台栈、Activity stopped）就每秒唤醒一次并做一次仓库调用。

现改为把节拍启动挂到 `uiState` 链的**订阅期**上：

```kotlin
    val uiState = stateAssembler.assemble(...)
        .onStart {
            totpTickJob?.cancel()
            totpTickJob = viewModelScope.launch(Dispatchers.Default) { totpTicker.run(...) }
        }
        .onCompletion { totpTickJob?.cancel() }
        .stateIn(scope = viewModelScope, started = SharingStarted.WhileSubscribed(5000), …)
```

`stateIn(WhileSubscribed(5000))` 在最后一个订阅者离开（宽限 5 s）后取消上游收集 ⇒
`onCompletion` 停表；重新订阅时 `onStart` 再启表。`totpTicker.run(...)` 的**循环体逐字未改**
（含 `previous` 状态机与 HOTP 跳过），只改**谁来启动它**。

**两处如实留痕**：

1. **`StateFlow` 没有 `subscriptionCount`**：首版按「`uiState.subscriptionCount` + `collectLatest`」写，
   编译期实测报 `Unresolved reference 'subscriptionCount'`（该属性在 `MutableSharedFlow` 上，
   `StateFlow` 不暴露）⇒ 改用上面的 `onStart`/`onCompletion` 形态。该事实留痕以免后人重试同一路径。
2. **`liveTotpCodeFlow` 仍为可写 `MutableStateFlow`**：`ISSUE-P2-65` 的会话锁定观察者要把它置 null
   以擦除实时码 ⇒ **不能**改成派生只读 `StateFlow`（这正是本批没有采用「冷流 + `stateIn`」重构的原因之一）。

### 2.2 验证器页接入批量通道（对应 AC ② 的**前半**）

`AuthenticatorViewModel` 的 `combine` 变换体内，把「逐条 `vaultRepository.calculateEntryTotp(entry.id)`」
改为先取一次批量快照 `vaultRepository.calculateEntryTotps(filtered.map { it.id })`，
再在 `filtered.map { … }` 内查表取用。格式化 / `isHotp` / 周期取值逐字未变（同一实现内部共用）。

⇒ 每拍的挂起调用由 **T 次降为 1 次**（一次会话读取 + 一次条目索引，O(N+T)）。

**未做（**转登**，见 §5）**：AC ② 要求同时把「列表内容」与「剩余秒数」解耦——即列表只在
`period` 边界重建、倒计时由卡片读共享刻度现算。该半项需要改 `TotpCardItem`（去掉
`remainingSeconds`）、`AuthenticatorScreen`（卡片内按 `period` 现算，用于 `isUrgent`、进度环、
倒计时文本三处）并让「码」的刷新走独立通道，属**状态形状 + UI 三处联动**的改动，
**转登为 `ISSUE-P3-182`**（本批不做，理由见该条目）。

### 2.3 列表页周期集合随快照缓存（对应 AC ③）

`VaultListTotpTracker.entryPeriods()` 原每拍（1 Hz）都重建 `filter` + `map` + `Set` 三个中间集合；
现按 `currentEntries()` 的**实例身份**缓存（`entries !== periodsSnapshot` 才重算）。
`currentEntries` 生产传入的是 `{ uiState.value.entries }`，状态对象不可变 ⇒ 该实例在同一列表状态
下稳定，缓存命中率高。仅在节拍链（`flowOn(dispatcher)` 上的 `onEach`）内访问，无需额外同步。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：「节拍随订阅启停」「每拍挂起调用 T → 1」「周期集合不再每拍重建」均为
   **源码结构**结论，**不得**宣称百分比收益，也不得推断真机耗电 / 帧率。
2. **AC 的部分验收判据未按原文落地**：「1 Hz 刻度不触发整页状态新建」与「同拍内批量取码只调用一次」
   两条**运行期断言未做**——本批以**源码文本守卫**替代（理由同 §129：宿主侧无计数通道，
   而 `calculateEntryTotps` 是接口方法，计数需要引入测试替身与订阅编排）。**不得**读作
   「已用运行期计数证明」。
3. **详情页节拍的「离屏停止」是结构性结论**：`onStart`/`onCompletion` 的触发依赖
   `stateIn(WhileSubscribed(5000))` 的取消语义，**未在设备侧观测**（例：后台栈页面是否确实不再唤醒）。
4. **验证器页仍每秒重建整页状态**（`timerSecondsFlow` 仍在 `combine` 内）⇒ 「整页重建」这一半
   **未消除**，只是把每条的挂起调用换成了一次批量调用；**不得**读作「验证器页已与秒级节拍解耦」。
5. **周期集合缓存以「实例身份」为键**：若未来 `currentEntries()` 改为每次返回新建列表，
   缓存将永不命中（不会更差，只是白留两个字段）。
6. **未跑设备侧 / `assembleRelease` / `lint`**；`§120` 的 `period` 口径用例在宿主侧全绿，
   但**设备侧渲染未复测**（本批不改周期判据，只改驱动与缓存）。

## 6. 过程缺陷与留痕

1. **首版实现编译失败**：误用 `StateFlow.subscriptionCount`（该属性只在 `MutableSharedFlow` 上）⇒
   改为 `onStart`/`onCompletion` 形态；**该次失败在 `compileDebugKotlin` 阶段即终止**，
   未进入任何模块的测试执行。
2. **第二版编译失败（1 例）**：`currentEntryOrNull(): UiVaultEntry?` 引入了未导入的类型名 ⇒
   改为**返回类型推断**（`private fun currentEntryOrNull() = uiState.value.entry`），避免新增导入。
3. **导入清理失误并当场修正**：为新增 `Job` / `onStart` / `onCompletion` 编辑导入块时，
   一次编辑**重复引入了 `Dispatchers` 与 `launch`**（各出现两次）⇒ 立即读取导入块并合并去重。
   **如实留痕**：该重复导入若未清理只会是编译告警，但仍属我制造的多余改动。
4. **全量单测两次撞上已知偶发红（本会话第 4 / 5 次观测）**：
   两次均为 `SyncCacheEvictorTest`（先是 `关闭密码库后同步缓存目录为空`，后是 `锁库后同步缓存目录为空`），
   断言值为**大写键名**的 `<hash>.META.tmp`。**判据本身已是「磁盘实体」口径**
   （`syncDir.walkTopDown().filter { it.isFile }`）⇒ 本次**不属于** `§7` 的「枚举鬼影」面，
   而落在其**第二项已接受残余**：`isFile` 非百分百可靠，口径更正后仍有约 **3% 假阳性**，
   更强判别式（同路径短时有界重枚举 15 ms × 4，实测 380 例假阳性 0 命中）**刻意未采纳**以避免时序依赖断言。
   **处置**：`§107` 同法——**定向复跑 6/6 绿**（`--rerun-tasks`，每条 4 秒），随后**全量复跑绿**（1m44s）；
   **未改任何断言**（真残留仍必红，不构成放宽）。**与本次改动无因果关系**（本批三处改动均不触碰 SyncCache）。
   **另记一条环境事实**：该残余在**隔离运行**下命中率明显低于**全量运行**（全量首跑 2/2 红、
   隔离 6/6 绿），与 `§7` 的「与删后的目录索引有关 ⇒ 文件系统 churn 放大」解释一致。
