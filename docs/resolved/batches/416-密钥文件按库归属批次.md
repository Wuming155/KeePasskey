### ISSUE-P2-460：密钥文件记忆无库维度——建库成功即丢第二因子，切库套用旧库因子

> **本轮状态（2026-10-03）**：**只登记，未实施**。用户 2026-10-03 已就整改口径裁决「按库归属」（见
> [`architecture/产品裁决登记.md`](../../architecture/产品裁决登记.md) PD-67），验收标准按该口径写定；
> **实施尚未开工**，本条留在在册状态跟踪。

- **核实时间点**：2026-10-03；**核实方式**：① 真机取证（Redmi M332BF / `a7eb933d`，`com.keepasskey.debug`，
  建库窗口 09:28，进程 pid 26050 全程存活、**无 FATAL / ANR**——用户口述的「一闪而退」是**弹窗宿主随会话锁定被拆**，
  不是 App 崩溃）；② 代码直读（记忆层 / 副本层 / 交付层四处落点）；③ 三家竞品源码直读
  （[竞品对比报告 §4.4](../../references/UI与操作体验的竞品对比报告.md)）。
- **用户回执原话（两条现象，2026-10-03）**：①「生成密钥文件后保存一闪而退」；②「密钥文件选定后哪怕切换密码文件也不会变」。
- **根因（两条现象同源）**：密钥文件记忆是**无库维度的全局单槽**，且**只在解锁成功时才写**。
  - `RealSettingsRepository.setRememberedKeyFile`（L267-270）只往 `last_key_file_uri` / `last_key_file_name`
    **两个全局键**写，**无任何库维度**；
  - 唯一写入者是 `KeyFileSessionCoordinator.rememberKeyFileOnSuccess`（L282）——**仅「解锁成功」触发**；
  - 建库链路 `VaultLifecycleCoordinator.createDatabaseWithKeyFile`（L139-183）**既不写记忆、也不收编副本**，
    反在 `finally` 里 `generatedKeyFile?.fill(0)` 把字节擦掉；
  - 恢复侧 `restoreRememberedKeyFile`：副本分支按 `dbId` 取（**有**库维度），但**副本缺失时裸落到全局
    `remembered.uri` 通道**——`SafKeyFileAccess.loadRemembered` 直接读 `settings.lastKeyFileUri`，
    **不做任何归属校验**。
  > 注：副本层 `KeyFileVaultCopyStore` **本来就是按 `dbId` 存的**（§411 已实施），缺陷只在更上面一层的记忆层。
- **真机落点取证（2026-10-03 09:28 窗口后 `run-as com.keepasskey.debug`）**：
  `files/passwords.kdbx`（1020 B，09:28，**库已建成且带第二因子**）、`files/passwords.kdbx.bak`（1024 B）、
  `files/keyfiles/` **空**（副本没写）、`/sdcard/Download/` **无 .keyx**（SAF 也没落）、
  `last_key_file_uri` 仍指向**旧库**的 `Download/QQ/usr.dat`。
  ⇒ **生成出来的密钥文件永久丢失，而该库带着第二因子已建好，现在解不开。**
  成因：`DatabasePickerKeyFileDeliveryController.saveTo` 是**到写盘那一刻才向会话现取字节**
  （`vaultRepository.exportKeyFileBytes()`），会话一旦被锁字节已清零 ⇒ 拿不到 ⇒ 只发一条「保存失败」然后静默。
- **竞品对照（结论：全局记忆槽在整个生态里是孤例，详见竞品报告 §4.4）**：
  KeePassDX 存 Room `file_database_history.keyfile_uri`（表主键 `database_uri`）；keepass2android 存
  SQLite `FileTable.keyFile` 列（且 `null`＝保留 / `""`＝**故意清除**的三态语义）；Monica 存
  `local_keepass_databases` 四元组（`key_file_uri` + `key_file_internal_path` + `key_file_name` + `key_file_fingerprint`）。
  **三家都没有全局「记住上次的密钥文件」这层**；另有两家「取不到就不许建库」的硬门
  （keepass2android `CreateDatabaseActivity`：取不到密钥文件 ⇒ 报错并 `return`，库根本不创建；
  Monica `AddEditPasswordScreen:1151`：`keyFileInternalPath` 非空**或** `generatorVerification` 已 `Verified` 才放行）。
- **等级说明（可上调）**：本条按 **P2 中危**登记（缺陷面可用「删库重建」绕开，非致命安全漏洞），
  但因含**不可逆数据丢失面**（第二因子一丢即不可恢复）与**跨库因子套用**（安全/可用性双重面），
  **等级可由用户裁定上调至 P1**；认领时先复核上述行号是否漂移。
- **验收标准（按用户裁决「按库归属」，三处落点）**：  
  ① **存储层**：把 `last_key_file_uri` 那一对全局键降级为 **`dbId → keyFileUri` 按库存**（实现把 `databaseId`
  摘要进键名，天然 namespace 隔离，**结构上不可能读到另一个库的记录**，无需运行期归属校验）；全局槽仅作
  「未登记时的一句话提示」来源，**不参与任何解锁裁决**；  
  ② **建库链路**：`createDatabaseWithKeyFile` 成功即 `vaultCopyStore.save(dbId, bytes)` + 登记，
  **不再等下次解锁才登记**（对齐 keepass2android / Monica 的「取不到就不许往下走」硬门）；  
  ③ **交付与恢复**：`saveTo` 写盘前若发现会话已锁、取不到字节，显式提示「密钥文件已丢失，请重新生成」，
  **不得静默「保存失败」**；`restoreRememberedKeyFile` 的 SAF 分支加库归属校验——**宁可显示「未记住」，
  也绝不能跨库套用**；  
  ④ 全量 test 绿 + 门禁九条全 PASS；真机回归同口径走查（建库→生成→保存→解锁 + 切库不串因子）。
- **关联**：与 `ISSUE-P3-448`（导入密钥文件语义）**同触记忆层但不同因**——P3-448 是「导入语义」，本条是
  「归属维度」；整改时两条须**同批收口**，否则会留下「按库登记 + 全局兜底」的混合态（比现状更坏）。
- **旁证（方法论，勿再踩）**：本次「一闪而退」**logcat 几乎无痕**（诊断闸门默认关、`KpLog` 全场仅 1 条：
  `SyncCacheEvictor 同步缓存已随会话终止销毁`）⇒ **该类问题不得指望 logcat 定位，靠文件落点取证**
  （`run-as … ls -l files/`、`files/keyfiles/`、`/sdcard/Download/` 有无 .keyx）。

## 3. 整改（三处落点 + 交付兜底）

### 3.1 AC① 存储层：全局单槽降级，按库记忆登场

- **`SettingsRepository`**（接口 + `RealSettingsRepository` + 测试 `FakeSettingsRepository`）新增按库 API：
  `rememberedKeyFileFor(dbId)` / `setRememberedKeyFileFor(dbId, uri, name)` / `clearRememberedKeyFileFor(dbId)`，
  载荷 `RememberedKeyFileMeta(uri, displayName)`（仍只有非密钥元数据）。
  **键名 = `"keyfile_remember_uri_" + SHA-256(dbId)`（name 同前缀）**——与 `KeyFileVaultCopyStore` 的副本
  文件名同一摘要口径（§411：SAF 库 id 含 `/` 斜杠本就不能直接进键名/文件名），同库恒同键、
  **结构上不可能读到另一个库的记录**，AC① 要求的「无需运行期归属校验」由此成立。
- **旧全局槽降级为只读提示来源**：`UserSettings.lastKeyFileUri/lastKeyFileName` 保留（历史升级用户的
  DataStore 里已有这两键，无法安全迁移——旧记录**不知道属于哪个库**），但 `setRememberedKeyFile` 全局写入
  **退役删除**（生产不再有任何写入方）；`clearRememberedKeyFile` 保留为「清陈旧全局槽」的卫生出口。
  升级用户体验：本库未登记记忆时，解锁页给**一句话提示**（新资源 `keyfile_legacy_memory_hint`，
  zh/en 成对）——「检测到旧版本记住的密钥文件（xxx），为避免套用到其它密码库已不再自动载入」，
  **绝不自动套用**（宁「未记住」不串因子）。

### 3.2 `KeyFileAccess` 契约 dbId 化（编译期逼出全部消费点）

`loadRemembered()` → `loadRemembered(dbId)`；`remember(uri, name)` → `remember(dbId, uri, name)`；
`forget()` → `forget(dbId?)`（dbId 非空清本库按库记录，**任何清除裁决都顺带清旧全局槽**——陈旧元数据
不残留）；新增 `loadLegacyGlobalHint()`（只读提示通道，KDoc 明示**不参与任何解锁裁决**）。
唯一生产实现 `SafKeyFileAccess` 改走按库 API；测试假实现（3 处）随契约编译期暴露、逐处更新。

消费面同口径收敛：

- **`KeyFileSessionCoordinator`**：`rememberKeyFileOnSuccess` 按**本库**登记（活动库 id 缺失时**放弃登记并
  留痕，绝不退回全局槽**——AC① 的「无归属宁可不记」）；`restoreRememberedKeyFile` 重构为**两级裁决链**
  （拆出 `restoreFromCopy` / `restoreFromMemory` / `showLegacyHintIfAny` 三个私有协作者，本函数回到
  行数闸门内）：副本优先 → 本库按库 SAF 记忆（授权校验沿用 `KeyFileRememberPolicy.canRestore`，失败
  `forget(dbId)` 静默降级）→ 都未登记才走全局槽**一句话提示**。
- **`SettingsMasterKeyChangeController`**：改绑 / 解绑的 `syncRememberedKeyFile` 与设置页
  `importRememberedCopy` 全部 dbId 化（`importRememberedCopy` 现读的是**本库名下**的记忆）。

### 3.3 AC② 建库链路：成功即收编 + 登记，不再等下次解锁

`DatabasePickerViewModel.createDatabase` 成功路径新增 `adoptKeyFileOnCreate(dbId, vaultName, resolution)`：

- **副本**：经既有导出通道 `exportKeyFileBytes()` 现取**会话绑定**的字节（生成型与既有因子同路，
  不新造第二条生成/读取路径），`keyFileVaultCopyStore.save(dbId, bytes, displayName)` 后 `fill(0)`；
  生成型显示名取建议名（`<库名>.keyx`），既有因子取来源文档名。收编失败只留痕不阻断（库已建成，
  一次性交付提示仍在；副本缺失只降级恢复体验，不得谎报建库失败）；
- **登记**：既有因子在「记住密钥文件位置」偏好开启**且**取得持久化读授权时，把来源 Uri 记到**本库名下**
  （与解锁页同口径，偏好关闭不写 Uri 记忆；生成型因子无 SAF 来源，副本即其登记形态）；
- dbId 取 `targetUri ?: fileName`，与 `DatabaseSelected` 事件、`importExternalDatabase` 的登记 id
  完全同一口径。

至此 P2-460 的数据丢失主链（建库成功 → 字节被擦 → 会话被锁 → 交付拿不到）在**上游**被切断：副本在建库
成功那一刻就已落私有目录，密钥文件再也不会「永久丢失」。

### 3.4 AC③ 交付与恢复

- **交付两级字节源**：`DatabasePickerKeyFileDeliveryController.saveTo` 的字节解析拆出 internal 分型内核
  `resolveDeliveryBytes()`——第一级既有导出通道（会话快照），第二级**回落本库私有目录副本**（AC② 收编的
  兜底消费）。两级都取不到 ⇒ 新资源 `db_picker_keyfile_lost`（zh/en 成对）显式告知
  「密钥文件已丢失……请删除该库后重新创建并妥善保存密钥文件」，**不得**再与普通写盘失败混同报
  「保存失败」。`requestSave` 增带 `dbId`（与建库成功路径同源）。
- **恢复侧归属校验**：AC③ 的「SAF 分支加库归属校验——宁可显示未记住也绝不跨库套用」由 AC① 的
  摘要键**结构性**达成（本库记录只可能写在本库键名下），另以回归用例锁定（§3.5）。

## 5. 真机回归走查判据（AC④，待用户装机回执）

1. **建库→生成→保存**：新建库勾选生成密钥文件 → 建成后 `run-as com.keepasskey.debug ls -l files/keyfiles/`
   **应立即有 `<sha256>.kfc`**（不等解锁）；弹「立即保存」走 SAF 落盘成功；
2. **交付兜底**：建库后不立即保存、等弹窗宿主被拆（或手动锁会话）后重新触发导出 ⇒ 从副本交付成功或
   显式「密钥文件已丢失」提示，**不再**只有一句「保存失败」；
3. **解锁**：杀进程冷启动 → 该库解锁页自动载入副本第二因子、解锁成功；
4. **切库不串因子**：再建一个无第二因子的库并切换 → 解锁页**不得**出现前库的密钥文件自动载入；
   升级用户且有旧全局记录时，应看到「旧版本记住的密钥文件」一句话提示而非自动载入；
5. **双语**：切 English 复查两条新文案（`db_picker_keyfile_lost` / `keyfile_legacy_memory_hint`）无中文残留。
