## 2. 实施与验收

- **前提复核（认领时，2026-10-14；直读 + 逐入口核对）**：前提成立——`PasskeyEntryCoordinator` 的
  `saveNewPasskeyEntry` / `saveOrReplacePasskeyEntry` / `replacePasskeyOnEntry` / `clearPasskeyOnEntry` /
  `applySignCountPatch` **五处**均为「`databaseSession.saveEntry*/updateEntryById` 导致内存树已改 →
  `persistSession()` 失败只写 `debugLog.warn` → 仍返回条目 / 计数器」同型；行号随历次重排漂移
  （现为 `:148-156` / `:203-210` …），对象与事实全部在案。

- **改动一（`core`：新增分型错误码）**：`KdbxError` 新增 `PASSKEY_ENTRY_NOT_FOUND`，使「未命中条目」
  与「落盘失败」可**按 `code` 分型**（不再靠文案比对）；`app` 层 `KdbxErrorTexts` 同批登记映射，
  `values/strings.xml` + `values-en/strings.xml` 成对新增 `err_passkey_entry_not_found`。

- **改动二（`PasskeyEntryCoordinator`：五处写入口统一返回 `KdbxResult`）**：
  - `saveNewPasskeyEntry` / `saveOrReplacePasskeyEntry` / `replacePasskeyOnEntry` / `clearPasskeyOnEntry`
    返回 `KdbxResult<KdbxEntry>`；`incrementPasskeySignCount` 返回 `KdbxResult<Int>`、`patchPasskeySignCount`
    返回 `KdbxResult<Unit>`；
  - **落盘交付边界**：`databaseSession` 变更后**只有** `persistSession()` 成功才交付 `Success`，失败
    **原样上浮**保存失败码（漂移中止 / 只读 / 磁盘满），且失败时条目 **保留在内存树（DIRTY）供重试**——
    绝不把「内存已改」当成「已持久化」交付；
  - **分型失败**：未命中 / id 非法 ⇒ `PASSKEY_ENTRY_NOT_FOUND`；只读 ⇒ `SAVE_READ_ONLY`（新增
    `databaseSession.isReadOnly` 前置判据，避免把「只读」误报成「未命中」），两者均**无任何写入**；
  - 落盘交付边界与两个失败构造拆入新文件 `PasskeyWriteCommit.kt`（见下「行数分档」），
    `PasskeyEntryCoordinator.kt` 仅保留薄委托 —— 语义不变，为维持其规模档。

- **改动三（`VaultPasskeyRepository` / `RealVaultRepository`：接口契约与委托对齐）**：接口五个写入口
  （含 `patchPasskeySignCount`）改签名为 `KdbxResult`，KDoc 补「只有落盘成功才交付 `Success`」契约；
  `RealVaultRepository` 委托逐条对齐返回类型。

- **改动四（消费方按结果分型，四处）**：
  - `PasskeyCreateActivity.createAndReturn`：落盘 `Failure` ⇒ `rejectAndFinish(PASSKEY_PERSISTENCE_FAILED)`
    **拒绝向 Credential Manager 回传成功**；并**把 `bindCallerForRegistration` 从「验证通过即写」移到
    「落盘确认之后」**（方案步骤 6：不向未持久化请求写入调用方信任绑定）；
  - `PasskeyAssertionActivity.signAndReturn`：`incrementPasskeySignCount` 为 `Failure` 时**拒签**——
    未命中走静默 `failAndFinish`（与既有口径一致），落盘失败经 `rejectAndFinish(PASSKEY_PERSISTENCE_FAILED,
    titleRes = cred_reject_get_title)` 给出可恢复提示；
  - `VaultListActionController.confirmPasskeyImport`：只有 `Success` 才提示成功并交出导航；`Failure`
    经 `op_failed` + `textArg(code)` 如实上浮（**不再按「已建条目」谎报成功**）；
  - `EntryEditPasskeyUnbind.confirmUnbind` / `EntryEditPasskeyImport.confirm`：按错误码分型——未命中
    用既有文案（`edit_passkey_unbind_failed` / `passkey_import_entry_missing`），落盘失败用新增
    `passkey_write_failed`。

- **改动五（`FakeVaultRepository`：替身对齐新契约）**：四个写入口返回 `KdbxResult`，未命中一律

## 4. 限制与后续边界

- **Activity 结果级自动化用例未新增**：本批把「保存失败 ⇒ 不向 CM 回传成功」的**判定收口在协调器**
  （`KdbxResult` 契约），并以失败注入单测锁定；两条 Activity（`PasskeyCreateActivity` /
  `PasskeyAssertionActivity`）的分支为**薄判定**（读 `Failure` → `rejectAndFinish`），本仓无 Robolectric /
  Activity 宿主级单测设施，**未新增** Activity 结果级用例，仅经编译门禁与逻辑复核。方案 §4 的
  「补 Activity 结果测试」**部分未完成**，如实留痕。
- **设备侧新分支未做故障注入**：真机仅实跑了既有 `PasskeyCreationDeviceTest`（覆盖率适配后的签名），
  **未**在设备上注入磁盘满 / SAF 写失败来驱动注册 Activity 走 `PASSKEY_PERSISTENCE_FAILED` 分支
  （UTP 无既有故障注入设施）。方案 §5 的「系统回传在独立 AVD 真跑」以「修改用例实跑通过」达成，
