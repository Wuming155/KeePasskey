### 1.5 装机即回归：收编通道 ANR（同批热修复，commit 2）

- **现象**：用户装机走查「正在派生密钥的过程中卡住了，进不去」；MIUI ANR 报告实锤——`MainActivity` Input dispatching timed out 5 s 后被系统杀（`bg anr`）。
- **取证**：`Slow Binder: com.keepasskey.debug → /system/bin/keystore2 → /odm/bin/hw/...keymint-service.strongbox-nxp`，主线程（tid 32349）keystore2 binder 阻塞 13.012 s、主线程消息总时长 41.789 s（`kotlinx.coroutines.internal.DispatchedContinuation`）；传感器 `dumpsys biometric` 证实该机 KeyMint 为 **strongbox-nxp**。
- **根因（本批 §1.2 引入）**：`onUnlockSuccess`（主线程协程）同步调用 `KeyFileVaultCopyStore.save()`——①Keystore `getOrCreateKey` 优先落 StrongBox；②700 KB 密钥文件**整载荷**经 KeyMint binder 做 GCM doFinal——正是 §408 教训「芯片只加密小数据段」的反例；③全部发生在主线程。UI 恒显 `DERIVING_KEYS` 阶段文案，用户观感即「派生密钥卡住」。
- **整改（信封加密 + 全程 IO 线程）**：①每次 save 生成随机 32 B DEK，Keystore 只封 32 B（小载荷，秒内）；700 KB 级载荷由 DEK 走**软件层** AES-256-GCM（`javax.crypto` 本地运算，不进 KeyMint）；②文件布局改 `[12B sealIv][2B sealCtLen][sealCt][12B dataIv][dataCt]`；③`save` / `load` 改 `suspend` + `withContext(Dispatchers.IO)`，Keystore 与文件 IO 绝不上主线程；④测试钩子改 `sealHook` / `unsealHook`（载荷层走 JVM 真实 JCE）。
- **过程留痕**：首版 DEK 清零时机错误（内层 `finally` 先于软件层 doFinal 清零 → 用全 0 密钥加密 → 回读 tag 必败），测试红灯立即暴露，清零收口移至最外层 `finally`（dek + payload 同口）。
