## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：`app/.../autofill/AutofillCandidateRanker.kt:136-147` 的评分循环对**全库条目**逐条访问
  `KdbxEntry` 属性 getter（`core/.../model/KdbxEntry.kt:28-41`），而每个 getter 每次都要走
  `fields[...]?.readString()`——未密封字段至少 `data.clone()` + 一次 `String` 构造，
  若该字段被写为 `Protected="True"`（KeePassXC 会写）则是**一次完整解密**；
  并对每条调 `PasskeyData.fromCustomFields`（`core/.../model/PasskeyData.kt:210`，内部 `associateBy` 建 map
  + 最多 9 次 `readString`），而绝大多数条目根本不是 passkey 条目。
  N = 5000 时约 5 万次 String 构造 + 5000 个临时 Map，全部落在引擎回调线程。
- **整改方向**：① `fromCustomFields` 前置廉价短路（先探 `Passkey.` 前缀键，无则直接返回 `null`）；
  ② 为 `KdbxEntry` 提供**不解密、不物化明文**的判定入口（复用既有 `ProtectedString.length`），
  把 `url.isNotBlank()` 一类判定改走它；③ 确需字符串投影时在投影层一次算好并随 UI 模型缓存。
- **验收标准**：非 passkey 条目的评分不产生 Map 与字符串（分配 / 调用计数断言）；
  候选排序结果与现状逐条一致（既有排序用例全绿）；不得引入新的明文 `String` 长期持有。
- **核实时间点与方式**：2026-09-17 读 `AutofillCandidateRanker.kt:85-150`、`KdbxEntry.kt:20-60`、
  `PasskeyData.kt:200-230` 核实。
- **风险提示**：自动填充候选匹配涉及**调用方归属与签名绑定判定**，只做「先算 / 后算」的等价搬移，不得改变判定顺序与放行面。

## 2. 本批实现

### 2.1 `PasskeyData.fromCustomFields`：不解密、不建 Map 的形状短路（对应 AC ①）

在 `associateBy` 之前插入**只扫 key 名**的前置判定：三个必需字段（`FIELD_RP_ID` /
`FIELD_CREDENTIAL_ID` / `FIELD_PRIVATE_KEY`）缺任一即 `return null`。

- **省掉什么**：绝大多数条目没有 passkey 字段，原先却一律先 `associateBy` 建一次 Map，
  再按字段逐个 `readString()`（**每次都是一次驻留密文解密 + `String` 物化**——该构造器对
  所有字段一律密封，`isProtected` 只影响 XML 写出，故「未受保护字段无需解密」是**错误印象**）。
- **为何不用「`Passkey.` 前缀探测」**：AC 原文写的是「先探 `Passkey.` 前缀键」，
  但那会漏掉 `FIELD_PREFIX` 之外的兼容/历史命名，且「前缀存在」比「三个必需键齐备」弱得多
  （前缀命中仍要建 Map 与解密才发现解析失败）。本批改为**判定必需键齐备**——既是最强判据，
  又与既有 null 语义**逐字等价**。
- **等价性**：三个必需键的存在性判定与后续 `map[...] ?: return null` 是同一条件的两种写法；
  短路只是把「必然失败」的路径提前到解密与建 Map 之前。原 null 处理**保留未动**
  （后续仍写 `?: return null`，不使用 `!!`）。

### 2.2 `AutofillCandidateRanker`：`url` 每条目只读一次（对应 AC ②）

- `scoreEntry` 中 `entry.url` 原被访问 **2~4 次**（包名维度 1 次、域名维度 1 次、
  `isExactDomain` 1 次；`entry.url.isNotBlank() && …` 处又是 2 次）；现改为函数开头
  `val entryUrl = entry.url` 一次读出并下传，`isExactDomain(entry, …)` 改签名接收
  `entryUrl: String`（其 `else` 分支原本就只读 `entry.url`，故语义逐字等价）。
- **为何不做 AC ② 原文的「为 `KdbxEntry` 加不解密判定入口」**：评分路径上**必须要 URL 的文本**
  （`DomainMatcher.isDomainMatch(entryUrl, webDomain)` 与 `DomainMatcher.extractDomain` 都要字符串），
  故「不解密判定」只能省掉**不匹配**条目的读；而把读次数从 2~4 收敛到 1 已经吃掉了同一条收益，
  且**不新增 API 面**。⇒ 该子项**判定不采用**（属对 AC 的实质修正，理由如上）。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：「每条目由 2~4 次 URL 读取收敛为 1 次」「非 passkey 条目不再建 Map/解密」
   均为**源码级调用点与分支结构**的结论，**不得**宣称百分比收益，也不得推断真机填充时延。
2. **仍存在的每次播放成本（本批未消除）**：
   - 评分仍对**每个候选条目**读一次 URL（一次解密 + 一个 `String`）——这是域名匹配的输入，无法省；
   - `fromCustomFields` 对**真的带 passkey 字段**的条目仍会建 Map 并逐字段 `readString()`（属必要读取）；
   - `N = 5000` 时仍是 O(N) 次评审 + O(N) 次 URL 读取，**不得**读作「已与库规模解耦」。
3. **未做分配 / 调用计数断言**：宿主侧无法在不改实现的前提下统计解密次数，
   等价性靠**行为用例**与**源码文本守卫**承担；守卫对「把读取点搬进辅助函数」的实现无鉴别力。
4. **AC ② 的原文路线未采用**（理由见 2.2），AC ③（投影层一次算好并随 UI 模型缓存）
   属 UI 投影层的另一件事，**不在本批范围**（该层的 `UiVaultEntry` 已在 §114/§117 处理过执行线程与频率）。
5. **`ISSUE-P3-170`（同一请求内的证书摘要 ×2 / Keystore IPC ×3 段 / hex 格式化）仍未做**，
   即自动填充请求路径上**还有**若干可收敛的重复工作。
