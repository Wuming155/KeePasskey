### ISSUE-P3-611：归档分册容量规则与现行索引不一致

- **来源 / 严重度**：归档维护规则复核，Low，可信度高。
- **核实时间点 + 核实方式**：2026-10-14；只读计数 `docs/resolved/BATCH_158_PLUS.md` 中的 `| §N |` 数据行，共 346 行；对照 `docs/resolved/README.md` 的「各册 ≤100 数据行」及超过 100 行时另立分册说明，并阅读 `tools/doc/check_resolved_index_sync.py` 判据。该机检不检查分册容量。未发现历史批次正文丢失。
- **背景 / 位置**：`BATCH_158_PLUS.md` 当前已有 346 条索引行，但归档维护说明仍要求各册不超过 100 行且触顶另立分册；现有索引机检只核对批次正文、分册索引、全量索引与最大编号，不校验容量规则。
- **触发 / 后果**：新增批次时，书面容量规则与现行滚动索引的存放方式不一致，维护者无法从现有规则确定下一条索引的归属；本次未发现正文不可达或历史丢失。
- **涉及文件**：`docs/resolved/README.md`、`docs/resolved/BATCH_158_PLUS.md`、`tools/doc/check_resolved_index_sync.py`。
- **责任席位 / 当前状态**：`mech_611`；暂停，等待用户恢复。不得据此自行搬移整册或新建分册。
- **建议 / 验收**：未来先裁定滚动容量规则或分册方法；保持原索引、正文和锚点可达，并通过归档索引、单调性及 Markdown 链接检查。本条不预设解决方案。

## 4. 限制与后续边界

- **容量本身不设 fail-closed 门槛**：分册 05 是既成超额册，若把「≤100 行」设为硬判据会立刻判红，
  而重分册会破坏锚点——故容量只出**读数**，硬约束落在「区间有序且不重叠」（新批次只能进最新册）。
  这是针对「维护者无法确定下一条索引归属」的直接解法，不是对容量的追溯性纠偏。
- **判据 6 不校验「册内是否跳号」**：分册 05 的 §158~§504 区间内若有个别缺号，判据 6 不报
  （缺号由判据 1「批次正文 → 分册」反查：正文存在则必被某册登记）。如实登记该边界。
