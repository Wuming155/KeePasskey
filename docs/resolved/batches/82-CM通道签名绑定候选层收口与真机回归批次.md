### 82.2 实施口径修正：为什么**不做**「首现显式授权面」

§81 曾预判「无绑定调用方须有受保护窗口内的首现显式授权面」才不致功能回归。本批复核后**否决该口径**，
理由是它**会把安全性做反**：

- 若对**从未绑定**的调用方照常产出候选、由用户在窗口内授权并把**本次调用方**记为绑定，那么
  记下的是**第一个**到来的调用方。若第一个是**侧载顶替应用**，则真正的应用此后永远落入
  「已绑定但签名不匹配」⇒ **被永久拒绝**；且用户没有任何路径纠正（绑定不可撤销地指错了对象）。
  即：**在首次填充时绑定，比不绑定更糟**。
- 可信参照只能来自**可信的创建时机**——用户主动发起的**保存**与**注册**流程
  （二者都由平台下发 `CallingAppInfo`，且都是「用户把凭据交给这个应用」的显式行为）。
  §81 已把绑定写在这两处，故**凡经本应用流程创建的条目都必然已绑定**。

据此，本批采用**三值**门控而非二元判据：

| 判定 | 条件 | 处置 |
|---|---|---|
| `AUTHORIZED` | 已绑定该包名且本次摘要命中 | 包名维度放行 |
| `REJECTED` | 包名为空，**或**已绑定该包名但本次摘要不匹配 | 包名维度**不命中**（AC② 两条判据） |
| `UNBOUND` | 该包名从未绑定过 | 退回包名维度**既有行为** |

**`UNBOUND` 是明示边界，不得读作「已加固」**：对从未绑定过的包名，`ISSUE-P2-83` 的越权面依然存在。
之所以不在此处 fail-closed——CM 通道**没有自动填充那样的选择器中立面**（候选为空则用户在系统 UI 上
既看不到任何东西、也无处授权），而「首次填充即绑定」已被上述论证否决。该边界连同理由写在
`CredentialManagerPackageBindingGate` 的 KDoc 中，并由 `UNBOUND` 专项用例锁定其行为。

### 82.3 落实

| 产物 | 内容 |
|---|---|
| `CredentialManagerPackageBindingGate`（新，纯函数） | 三值判定；两个外部事实（`isTrusted` / `hasAnyBinding`）以函数参数注入，JVM 可穷举 |
| `CredentialManagerCallerTrustStore.hasAnyBindingFor`（新） | 区分「已绑定不匹配」与「从未绑定」的支点；只看键**存在性**，不读值、不泄露摘要 |
| `CredentialCandidateMatcher`（自组装器抽取，纯函数） | 把候选入选判据从依赖 `VaultRepository`/`Context` 的组装器里抽出，使「不命中」可在**候选层**直接断言（含真机） |
| 接线（4 处） | `CredentialResponseAssembler` 通行密钥候选 / 密码候选；`PasswordFillActivity` 回传前；`PasskeyAssertionActivity` 签发前 |
| `KeePasskeyCredentialProviderService.findMatchingEntries` | 新增 `packageDimensionAuthorized` 入参，**刻意无默认值**——包名维度是越权面，默认值等于留一个「忘记传参 = 放行」的 fail-open 口子 |

**顺带查明**：`findMatchingEntries` 在**生产路径已无调用方**（仅单测可达），故它原先不构成活跃越权面；
本批仍给它加门控入参，理由是「留着一条不带门控的包名维度匹配器」迟早被误用。
