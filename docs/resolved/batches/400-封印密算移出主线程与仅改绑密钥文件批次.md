# 批次 400：封印密算移出主线程与仅改绑密钥文件批次（ISSUE-P1-429 / ISSUE-P3-430 整条闭环）

> 日期：2026-10-02。两条同会话登记同会话闭环（P1 0→1→**0**；P3 2→3→**1**）。
> 起因：用户真机走查 §399 批次装机反馈两条——①「使用密码和密钥文件解锁会直接卡死（这个问题之前是没有的）」；②「如果想要绑定密钥文件，必须重新设置密码，不能单独设置」。

## 1. ISSUE-P1-429：Keystore 密算跑主线程 → ANR

### 1.1 取证与根因

真机（a7eb933d）`dumpsys dropbox data_app_anr` 两条 ANR（2026-10-02 07:02:35 / 07:03:21，`com.keepasskey.debug`）堆栈对读：主线程 tid=1 阻塞在 `IKeystoreOperation$Stub$Proxy.update`（binder 到 `keymint-service.strongbox-nxp`，elapsed 5.28s），app 帧分别为：

- `BiometricResealCoordinator.authorizeAndSeal`（改密后重封印，BiometricResealCoordinator.kt:182）
- `BiometricEnrollmentCoordinator.authorizeAndSeal`（主密码解锁成功后自动登记，BiometricEnrollmentCoordinator.kt:239）

根因链：封印载荷 v1 复合帧 = 主密码 + **整个密钥文件字节**（ISSUE-P2-23）⇒ 密钥文件可达 `KEY_FILE_MAX_BYTES` = 1 MiB ⇒ StrongBox 分块加密 1 MiB ≈ 数百次 binder update ≈ 5s+；而该 `doFinal` 与封印密钥供给（`prepareEncryptCipher` / `getKeySecurityLevelForDatabase`，同为 keystore binder）都跑在 `viewModelScope`（Main）上 ⇒ 输入超时 ANR。「之前没有」是因为此前载荷只含主密码（几十字节）。

### 1.2 整改

五处 keystore 调用移 `Dispatchers.IO`（行为语义零变化，失败路径与清零链原样）：

1. `BiometricEnrollmentCoordinator.authorizeAndSeal` 的 `authedCipher.doFinal(payload)`；
2. `BiometricResealCoordinator.authorizeAndSeal` 的同型 `doFinal`；
3. `BiometricUnlockCoordinator.startBiometricUnlock` 的解封 `doFinal`（解密侧同病，载荷同源）；
4. `BiometricEnrollmentCoordinator.requestBiometricEnrollment` 的 `defaultSealKeyProvision` 调用（测试替身 `sealKeyProvisionOverride` 一并在 IO 求值，替身语义不受影响）；
5. `BiometricResealCoordinator.resealAfterMasterKeyChange` 的同型供给调用。

## 2. ISSUE-P3-430：不改主密码、单独改绑密钥文件

### 2.1 database 层

- `SessionPersistence.changeKeyFileOnly(newKeyFileData)`：以 `SessionCredentialCache.passwordSnapshot()` 克隆出的当前主密码 + 新密钥文件字节走既有双参 `changeCredentials`——**密码分量原样保留**；快照在 `finally` 清零；「无主密码分量 + 解绑」＝不剩任何因子，fail-closed 显式拒绝。
- `DatabaseSession` 门面：`changeKeyFileOnly` 转发 + `passwordSnapshot()` 暴露（克隆副本契约：调用方用毕清零，绝不落 String）。

### 2.2 app 层

- `VaultRepository` 新增 `changeKeyFileOnly(keyFileIntent)`（`Keep` = 无任何改动，fail-closed Failure 不静默成功）；`RealVaultRepository` / `VaultLifecycleCoordinator` 落地（`Use`→`changeKeyFileOnly(bytes)`、`Remove`→`changeKeyFileOnly(null)`，仅成功时刷新库列表）。
- `SettingsMasterKeyChangeController.submit`：`newPasswordChars` 为**空数组** = 密码分量不变，分派到 `changeKeyFileOnly`；空数组 + `Keep` = 无任何改动，同步拒绝不进任务（对话框闸门本应拦住，双闸不互替）；重封印入参对应传 `null`。
- `MasterKeyChangeDialog`：两个密码框整体留空 = 保持当前主密码（仅改绑密钥文件），弱口令确认闸只在真实改密时介入；留空 + `Keep` = 无改动，提交钮禁用；新增提示文案 `set_master_key_keep_hint`（zh/en 成对）。
- 重封印联动（陈旧封印不得残留）：`BiometricResealCoordinator.resealAfterMasterKeyChange` 入参放宽为 `CharArray?`——null = 密码分量未变，从新增的 `sessionPasswordChars` 提供者（`SettingsBiometricGate` ← `SettingsViewModel` ← `DatabaseSession.passwordSnapshot()`）取会话当前主密码快照封印，快照归协调器所有、`finally` 清零；取不到（仅密钥文件会话等）留痕跳过，交由下次主密码解锁的登记路径自然重封印。

## 4. 如实声明

- `KeystoreManager.kt` 与 `SyncCredentialSealer.kt` 的 keystore `doFinal` 未移 IO：载荷均为小尺寸偏好项（非封印载荷），实测未构成 ANR 主体；如后续真机实测超时另行立条。
- 封印载荷含完整密钥文件字节（上限 1 MiB）的形态本批未改：移 IO 后不再 ANR，但 StrongBox 加密大载荷仍需数秒（用户表现为指纹授权后短暂等待）——属 ISSUE-P2-23 帧格式的既有设计，收窄需改封印协议，另行裁决。
