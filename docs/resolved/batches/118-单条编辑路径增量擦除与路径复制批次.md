## 1. 缺陷与整改

### 1.1 缺陷面（开工复核后的准确表述）

`ISSUE-P3-156` 正文点名的两处成本面，经开工复核**逐条成立**，并补一处正文未写明的细节：

1. **整树重建**：`SessionTreeEditor.updateOrAddEntry` / `updateOrAddGroup` 的递归以
   `group.subgroups.map { 递归(sub) }` 收尾，**每一个分组**都会被 `copy()` 成新对象
   （仅 `entries` 列表按引用复用）⇒ 单条条目编辑付 O(分组数) 次对象分配；
   目标父组根本不在树内时**同样重建整棵树**（纯浪费）。
2. **全库身份集合**：`SessionContentMutations` 在替换前调 `KdbxGroup.clearSupersededSensitiveData(surviving)`，
   该实现先 `surviving.collectSensitiveIdentities(live)` 把**整棵新树（含全部 history）**的
   `ProtectedString` / `KdbxAttachment` 收进 `IdentityHashMap` 集合，再遍历旧树逐实例查表
   ⇒ 每次编辑 O(条目数 × 字段数) 次哈希插入 + 同量级查表。
   （正文「O(元素数 × 字段数)」口径成立；此处补明：**插入与查表各一遍**。）
3. **正文未写明、本批必须处理的前提**：`updateOrAddEntry` 还会对 **`parentGroupId == null`** 的条目
   做落树规范化（ISSUE-P3-63），该规范化**不得**在路径复制改写中丢失（既有 5 例规范化用例锁定）。

### 1.2 整改设计

**A. 路径复制（`SessionTreeEditor`）**

递归改为「命中即返回、未命中按**同一实例**原样返回」：`updateOrAddEntryIn` / `updateOrAddGroupIn`
返回 `null` 表示目标不在本子树，调用方据此复用原实例（不再无差别 `copy`）。
`removeEntry` / `removeGroup` 同样加「未命中即复用」判定（`entries` / `subgroups` 列表亦按引用复用）。
`normalizeParentRefs` 增加「无需修正即返回同一实例」。
目标父组不在树内时返回**同一根实例**（原实现整树重建）。

> **语义变化（如实留痕，1 处）**：原实现对**所有** id 相同的分组都落树（`map` 全扫）；
> 现改为**命中首个即返回**。KDBX 分组 UUID 在树内唯一（`findGroup` / `allGroups().firstOrNull{}` /
> `subtreeContainsGroup` 等既有 API 均已按唯一性假设工作），故正常库上逐条等价；
> 仅在**损坏库（重复分组 UUID）**下行为由「重复落树」变为「首个命中」。该变化同时是 O(分组数) 遍历的消除来源。

**B. 替换关系回报（新增 `EntryEditResult` / `GroupEditResult`）**

树变换**本来就走到了被替换位置**，故让它把「被替换下线的旧节点 + 同位置上线的节点」一并回报，
调用方无需再反推。`saveGroup` 的根分支抽为 `replaceRootGroup`（返回同一形态的结果）。

**C. 增量定点擦除（`KdbxGroup.eraseSupersededSensitiveData`，新增）**

```
新树.eraseSupersededSensitiveData(被替换旧节点, 同位置新节点)
  ├ 1 快速通道：新节点与旧节点共享全部承载容器（copy 只改元数据）⇒ 零候选返回
  ├ 2 候选 = 旧节点可达敏感实例（collectSensitiveIdentities，**只对该节点调用一次**）
  ├ 3 候选减去「新节点仍可达者」（dropSensitiveIdentitiesFrom）
  ├ 4 候选减去「**新树任意位置**仍可达者」（同上，对整棵新树做引用比较、**不插入集合**）
  └ 5 余下者即真正下线 ⇒ 逐个清零（clearSensitiveIdentitiesIn）
```

**等价性依据（路径复制契约）**：新树除被替换位置外与旧树按同一对象引用共享全部子树，
故「旧树中下线、新树中存活」的实例**只可能来自被替换节点** ⇒ 候选集合规模 = 被替换节点规模，
**不随全库规模增长**。步骤 4 不可省：存活实例可能挂在**树内其它位置**（克隆体、
`HistoryManager.recordHistorySnapshot` 的历史快照、回收站 moved 副本），跳过即**误擦存活密文**。

**D. 调用面接线（`SessionContentMutations`）**

| 写路径 | 擦除方式 | 说明 |
|---|---|---|
| `saveEntry` | 增量（旧条目 → 新条目） | 新增条目无替换关系 ⇒ 零成本 |
| `saveGroup` | 增量（旧子树 → 上线子树）/ 根分支 | `preserveChildrenIfMissing` 产物即「新节点」 |
| `batchMoveEntries` | 增量（逐条：源位置被移除的旧条目 + 目标位置被替换者 → moved 副本） | 擦除在**最终树**上执行；`copy` 共享全部实例 ⇒ 候选通常为空 |
| `deleteEntry` / `deleteGroup` / `batchDeleteEntries` | **不变**（无擦除） | ISSUE-P2-06 既定修正，见 `SessionContentMutations` 注释 |
| `updateDatabaseMeta` | **通用实现不变** | 任意整库变换无法定位替换位置（同步合并 / 远端接管需要它）；仅改元数据时 `this === surviving` 零成本返回 |

`KdbxGroup.clearSupersededSensitiveData`（通用）与新增增量实现共用同一批原语，
避免安全逻辑出现两份漂移实现；两条路径的结论一致性由**差分用例**逐实例对拍（见 §2.1 第 7 例）。

## 3. 边界与如实声明（**不得**把这些读作已验证）

1. **无真机 / 性能实测**：本批判据为**行为等价 + 结构性修复 + 变异验证**。
   消除的是「O(分组数) 次对象分配」与「O(条目数 × 字段数) 次哈希插入」这两类**结构性工作**，
   **不得**据此宣称任何百分比收益（「本机墙钟对比」未做）。
2. **候选收敛是构造性结论 + 结构性守护，而非运行期计数证据**：
   「集合规模不随全库规模增长」由代码路径保证（候选只由被替换节点收集一次），
   并由 `SessionTreeEditorPathCopyTest` 的 `assertSame` 锁定其前提；
   **没有**任何用例在运行期观测集合大小（无性能插桩，亦未新增生产代码测试钩子）。
3. **擦除结论在行为层由「与通用实现对拍」守护**：差分用例（8 例文件中的第 7 例）对
   5 个同型场景逐实例比较两条实现的「已清零 / 未清零」结论；该对拍**只覆盖 5 个构造场景**，
   **不构成**「两条实现全域等价」的证明。
4. **步骤 4 仍是一次全树引用扫描**：候选非空且未被步骤 2 / 3 清空时（例如 passkey 计数器补丁、
   `updateEntryOtpConfig` 换掉旧 OTP 实例）会走一次 O(全库) 的**引用比较**扫描。
   本批消除的是**分配与哈希**，**不得**读作「编辑路径已完全无全库遍历」。
5. **调用前提（API 契约收窄）**：增量入口要求调用方**列全**本次全部被替换节点；
   **不负责**发现未声明的下线实例（`KdbxIncrementalSensitiveErasureTest` 末例显式锁定该前提）。
   路径复制契约下「替换关系之外不存在下线实例」，但**若未来有调用方绕过树变换直接构造新树**，
   其未声明的下线实例将**不再被擦除**——新的整库变换请继续使用 `clearSupersededSensitiveData`。
6. **`updateDatabaseMeta` 路径本批未优化**：单条条目更新仍有一条不经编辑器的路径
   （`PasskeyEntryCoordinator` 的计数器补丁：整树 `replaceEntry` + 通用 O(全库) 身份集合），
   已转登 `ISSUE-P3-157`；故**不得**读作「单条编辑路径已全部 O(被替换节点)」。
7. **根分组整根替换分支仍可能 O(全库) 收集候选**：`saveGroup` 命中「传入分组自身即根分组且携带子项」
   时，被替换节点是**旧根**（其可达实例即全库）。快速通道只在「新旧根共享承载容器」时命中（`copy` 改名场景）。
   该分支在现有调用面不可达（UI 的 `saveGroup` 均以具体分组 id 调用），**未加额外防护**。
8. **未跑**：`assembleRelease`、设备侧 instrumented 用例、`tools/audit/check_recheck_consistency.sh`
   的触发条件（本批**未改**任何审计 / 复核报告；仍如实执行了闸门，见 §4.3）。

### ISSUE-P3-156 单条编辑路径的整树遍历与全库敏感身份集合重建

- **背景**：单条条目编辑（含回收站移动、批量操作等写路径）在 `SessionTreeEditor.updateOrAddEntry` 中
  **遍历并复制全部分组节点**（非路径复制），随后 `SessionContentMutations` 调用
  `clearSupersededSensitiveData`，由 `KdbxGroup.collectSensitiveIdentities` 把**全库（含历史）**的
  `ProtectedString` / `KdbxAttachment` 收进一个 `IdentityHashMap` 集合——每次编辑都是 O(元素数 × 字段数)。
- **量级**：O(分组数) 对象复制 + O(条目数 × 字段数) 集合元素 /每次编辑。
- **核实时间点与方式**：2026-09-17 由 §115 的开工复核确认（`ISSUE-P3-150` 原正文 ③④ 转登至此）。
- **整改方向**：编辑器**已持有**「被替换掉的旧节点」信息，据此可做**增量**擦除（只擦本次真正被丢弃的实例），
  无需每次从新树反推存活集合；路径复制（只重建从根到目标的分组链）可同时消除 O(分组数) 复制。
- **验收标准**：擦除语义**不得削弱**——既有「被替换节点的敏感数据必被清零」用例全绿，
  且须补一条**负向对照**（故意漏擦某类节点时用例必红）；编辑路径的集合规模不再随全库规模增长。
- **风险提示**：擦除保证是安全属性，**宁可保留 O(N) 也不得漏擦**；无增量方案的可核对性证据前不得动手。
