> ### ISSUE-P3-336 相册导入恒报「图片读取失败」——`inJustDecodeBounds` 返回值被误判空（用户真机直报）
>
> - **优先级**：P3（§340 新增特性**完全不可用**；相机扫码主通路不受影响，无数据与安全影响）
> - **背景**：`ISSUE-P3-334` 的相册导入通路装机后用户真机实测**每次选图都失败**（同一张二维码
>   用相机扫码可以解出）。根因：`TotpGalleryImport.loadGalleryPixels` 读尺寸步写成
>   `openInputStream(uri)?.use { BitmapFactory.decodeStream(stream, null, bounds) } != null`——
>   而官方契约是 **`inJustDecodeBounds = true` 时 `decodeStream` 恒返回 `null`**（不分配位图），
>   该判断恒 false ⇒ 函数无条件 `return null` ⇒ UI 恒显「图片读取失败」，**有界解码与 zxing
>   解码根本不会执行**。属 §340 批次的实现缺陷：JVM 单测无法覆盖 Android 框架 API 语义，
>   且该批如实声明「真机手动冒烟未做」即装机，缺陷未经设备侧拦截。
> - **核实时间点**：2026-09-26
> - **核实方式**：①用户真机直报「不行，失败了，同样的二维码，扫码可以」（装机后复测）；
>   ②`google-developer-knowledge` 查证官方文档 `BitmapFactory.Options.inJustDecodeBounds`
>   「decoder will return null (no bitmap)」；③代码走查 `TotpGalleryImport.kt` 定位
>   `boundsReadable` 判空恒 false，两条失败路径合流于 `return null`。
> - **涉及文件**：
>   - `app/src/main/java/com/keepasskey/app/ui/screens/edit/TotpGalleryImport.kt`（读尺寸判空修复 +
>     透明底像素合成白底加固）
>   - `app/src/test/java/com/keepasskey/app/ui/screens/edit/TotpGalleryImportDecodeTest.kt`
>     （透明底 QR 回归单测 + `decodeStream` 返回值判空静态守卫）
> - **验收标准（AC）**：
>   1. 读尺寸步按官方两步加载口径：**不判 `decodeStream` 返回值**，仅验 `outWidth / outHeight > 0`；
>   2. 同批加固：ARGB→灰度时**非全不透明像素合成到白底**（`out = rgb·a/255 + 255·(255−a)/255`）——
>      相册常见透明底 QR PNG 经 `getPixels` 还原的 a=0 像素 RGB 为 0，不合成会把整图读成全黑；
>      配 JVM 回归单测（白底改全透明的 QR 帧可解出原文）；
>   3. 静态守卫（同 `SensitiveWindowHardeningTest` 源码扫描先例）：源码出现
>      `decodeStream` 返回值 `!= null` 判空即红，失败消息指向本条；
>   4. 全量 `.\gradlew.bat test` 全绿且 `python tools/doc/gate_readings.py` 7/7 PASS；
>   5. `assembleRelease` 覆盖安装后**用户真机复验通过**（同一二维码：相机可扫、相册可导入）；
>      归档（`RESOLVED_LOG` 索引 + 批次正文）与代码同批提交。

## 1. 判证与根因（判定链）

1. **用户现象**：装机后相册导入**每次**失败；同一张二维码相机扫码可以解出 ⇒ 问题隔离在相册通路、
   与图像内容无关（若为图像内容问题，不应是「必失败」形态）。
2. **官方契约查证**（`google-developer-knowledge` → `BitmapFactory.Options` 官方文档）：
   `inJustDecodeBounds = true` 时解码器「will return **null** (no bitmap)」，仅回填
   `outWidth / outHeight` 等字段——即「读尺寸」这步的返回值**恒为 `null`、与图片是否可读无关**。
3. **代码走查定位**：`TotpGalleryImport.loadGalleryPixels` 首行判断
   `val boundsReadable = openInputStream(uri)?.use { decodeStream(stream, null, bounds) } != null`
   ——`use` 返回内层 `decodeStream` 的结果（恒 `null`）⇒ `boundsReadable` **恒 false** ⇒
   `if (!boundsReadable || ...) return null` 无条件提前返回 ⇒ UI 恒显「图片读取失败」，
   后续 `gallerySampleSize` / 像素提取 / `decodeQrFromPixels` **一行都不会执行**。
4. **为何机检全绿仍漏出**：JVM 单测只测了 `decodeQrFromPixels` 纯函数（合成像素可解），
   `loadGalleryPixels` 依赖 `BitmapFactory`/`ContentResolver`，宿主侧不可构造；§340 批次
   又如实声明未做真机冒烟即装机——缺陷无任何闸门覆盖，首触即由用户发现。

## 2. 整改内容

1. **判空修复（AC①）**：读尺寸步改为官方两步加载口径——`decodeStream` 调用结果**故意不接**
   （内联注释写明「返回值恒 `null`、故意不接」），只验 `bounds.outWidth <= 0 ||
   bounds.outHeight <= 0` 作可解性判定；函数 KDoc 写明契约出处与本条事故（`ISSUE-P3-336`）。
2. **透明底加固（AC②）**：`decodeQrFromPixels` 灰度化循环内对 `alpha != 255` 的像素按
   `out = rgb·a/255 + 255·(255−a)/255` **合成到白底**——相册常见透明底 QR PNG 经
   `Bitmap.getPixels`（premultiplied 还原）对 a=0 像素给出 RGB=0，不合成会把整图灰度成全黑、
   必解不出。与修复同属「让相册图真正可解」的完整闭环。
3. **回归单测（AC② 后半）**：`透明底二维码像素帧可解出原文（alpha 合成到白底）`——白底像素
   替换为 `0x00000000`（a=0、RGB=0，真实还原形态）后断言仍解出原文；该例对修复前实现**必红**
   （全黑帧 → `NotFoundException` → null）。
4. **静态守卫（AC③）**：`读尺寸不得以 decodeStream 返回值判空`——读源码（`stripCommentsOnly`
   剔注释后）以 `decodeStream[\s\S]{0,200}?!=\s*null` 正则扫描，命中即红（失败消息含
   `ISSUE-P3-336`），并正向断言 `bounds.outWidth <= 0` 可解性判定存在。
   **反向反校**：判据对缺陷版源码（`e7338680`）全文命中 1 处（会红）、对修复版剥注释后 0 命中（绿）；
   新增测试与生产代码同批入库（测试资产纪律）。
5. **`TotpGalleryImportDecodeTest` 用例 4 → 6**：原 4 例不动，新增透明底回归与静态守卫各 1 例。

**未采用的替代方案（留痕）**：①用 `inJustDecodeBounds=false` 的返回值判可读后再量尺寸——多解一次
全图像素、违背官方两步加载口径；②只修判空不做透明底加固——透明底 PNG 是相册导入的常见输入，
留作已知必失败形态等于把下一次用户直报推迟到以后，且已有零成本 JVM 测试面可覆盖。
