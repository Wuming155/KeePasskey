## 2. 两条用例各把住什么（三层证据，逐层加强）

**`EntryEditViewModel`**（擦除动作 = `clearAllSecrets()`）：
1. 锁定后 `loadedPassword`（一次性预填通道）置空；
2. **锁定前拿到的数组本体被填零**——只丢引用而不 `fill('0')` 的话，明文仍随数组副本留在堆上，
   这一层能区分两种做法（注意擦除字符是 `'0'` 而非 `'\u0000'`，断言按实现写）；
3. **私有副本 `passwordChars` 确实擦除**——它不进 UiState（只有 `passwordLength` 进），
   唯一可断言的观测点是**保存落库的内容**：锁定后再 `saveEntry()`，
   若私有副本没被擦，`vaultRepository.saveEntry` 就会把明文再写回去 ⇒ 断言取回的空 `CharArray`。
   这一层是**行为级**的，不依赖反射、也不依赖内部字段名。

**`SettingsViewModel`**（擦除动作 = `syncController` 的三个 `clear…Prefill()`）：
断言 WebDAV 口令 / S3 AccessKey / S3 SecretKey **三条通道同时置空且本体填零**。
**先断言前提**（三条通道锁定前的内容逐字等于预置的虚构凭据）——否则本用例就是三个空断言。

**刻意不写进去的断言**（各有一条不成立的口径，钉上去等于替它背书）：
- 详情页那类 `isPasswordVisible`：`clearAllSecrets()` 不回写 UiState；
- `passwordLength` / `isDirty`：锁定后长度读数残留属既有呈现口径，且**长度非机密**；
- `restoreSyncCredentials()` 的 fail-closed 分支（解封失败 ⇒ 整条配置返回 null）：
  那是 `SyncCredentialsStoreTest` 的范围，本批只补 VM 侧的擦除回调，两者不互相顶替。

## 3. 为什么必须新写一个可写的 prefs 替身（这一步曾差点写成空断言）

三条预填通道的**唯一填充点**是 `SettingsViewModel.init → restoreSyncCredentials()`，
而它要求「凭据已封印落盘且可解封」：

- `SyncCredentialsStore(context, keystoreManager = null)` 在无 AndroidKeyStore 的宿主 JVM 上，
  `sealer.encrypt(...)` 直接返回 `null` ⇒ `saveWebDavConfig` **整体不落盘**（fail-fast）；
- 该类的 `customEncryptor` / `customDecryptor` 是 `@VisibleForTesting internal var`
  （TASK-14 收窄：生产不可写），注入一对 XOR 可逆闭包即可在 JVM 上跑通往返；
- 而 `android.jar` 的 `Context.getSharedPreferences` 桩返回 `null`，
  既有测试里的**只读**代理（`edit()` 返回 `null`）在写入时当场 NPE ⇒ **预置凭据这条路需要可写替身**。

`InMemorySharedPreferences` 就是补这一格：`putString/getString/remove/clear/getAll` 全走内存 map，
`context()` 顺带给一个临时 `getCacheDir`。
**未去改写 `SyncCredentialsStoreTest` 里那份私有代理**（测试资产只增不改，且改它属无关风险面）
⇒ 同一形态现存两处，后续可让该类改用共享件（登记在下批候选，属整理不属缺陷）。

**判据性质（不作突变测试，如实说明机制）**：本批**没有**用「临时改坏生产代码看用例是否报红」来验证断言强度
——那会往生产文件里注入未擦除明文的窗口期。三条断言的**分工**是按实现读出来的
（`EntryEditViewModel.kt:365` 无条件提交 `passwordChars.copyOf()`；`:419-433` 的 `clearAllSecrets()`
逐通道 `fill('0')` 后置空），故三种退化各有其命中者：

| 退化形态 | 命中它的断言 | 为何其它两条仍绿（ ⇒ 必须三条并存） |
|---|---|---|
| 锁定观察者根本没注册（`register()` 被摘） | 三条全红 | 前提仍绿，故红一定来自擦除动作缺失而非夹具 |
| 只把通道引用置空、不 `fill('0')` | 「数组本体填零」红 | 置空与落库两条按其本身口径仍成立（明文却仍随副本留在堆上） |
| 只清预填通道、不动私有副本 `passwordChars` | 「锁定后保存不带明文」红 | 通道两条只看通道，管不到私有副本 |

`SettingsSessionLockEraseTest` 同理：三条通道各有「锁定前逐字等于预置值」的前提断言，
故「通道压根没填」会先以**前提失败**报红，不会伪装成「擦除成功」。

**残留风险（如实登记）**：两条用例都是**白盒接线级**证据，不含设备侧的锁定链路
（`DatabaseSession.lock()` 由谁在何时触发属 `SessionLockGuard` 与解锁页的范围）；
