# §157 源码文本清洗口径统一批次（`ISSUE-P3-194` 第一段：双口径工具 + 3 份守卫收口）

> **起因**：`ISSUE-P3-194`（§156 登记）——静态源码守卫的「剥注释」不认识字符串字面量，
> 实测 97 份 main 文件的块注释视图被误配对（最坏单文件 10 KB 级真实代码从守卫视野消失），
> 12 份守卫受影响、其中 4 份做全目录扫描。用户命题「修复存量问题」。
> **本批未改任何生产代码**（改动全部落在 `app/src/test`）。

---

## 1. 关键设计：清洗必须分**两种口径**，不能一把梭

首版只有一种口径（`stripStringsAndComments`：抹掉字面量 + 去注释），把它套到
`DatabaseConfigHeaderMappingTest` 上**当场变红**：

```
标签「ChaCha20 (256-bit)」只应定义于 CipherLabels.kt：[] expected:<[CipherLabels.kt]> but was:<[]>
```

**裁定（这正是 `ISSUE-P3-194` 整改纪律 ② 所要求的「逐条裁定」第一例）**：
不是代码有旁路，而是**该守卫的判据对象就是字面量本身**（要比对标签字符串出现在哪些文件里）——
抹掉字面量等于把被查找的东西删了。故工具补第二种口径：

| 口径 | 适用守卫 | 本批使用者 |
|---|---|---|
| `stripCommentsOnly`（**tokenizer 逐字符扫描**：只去注释，保留字符串内容） | 判据含字面量本身者（标签词汇表、MIME、文案一致性） | `UiMd3AlignmentWiringTest`、`DatabaseConfigHeaderMappingTest` |
| `stripStringsAndComments`（抹字面量 + 去注释，只留代码骨架） | 判据只涉及**代码形状**者（签名、调用点、计数） | `ExportTicketSinkGuardTest`（§156 已用，本批保留） |

`stripCommentsOnly` 用状态扫描记录「在串内 / 在注释内」，因此**字符串里的注释符不再造成误配对**
（原假阴性根因），同时不破坏注释的正常剔除。

## 2. 自检用例（整改纪律 ③）

新增 `app/src/test/java/com/keepasskey/app/testutil/SourceTextSanitizerTest.kt`（3 例）：

1. **串内注释符不吞后续代码**：样例含 `arrayOf(<闭><开>)` 形态 + 真块注释 + 行尾注释 + KDoc，
   要求「其后的声明仍在视野内」「真注释仍被抹掉」「字面量在两种口径下的去留正确」；
2. **三引号与转义引号不破坏扫描**（三处声明计数 = 3）；
3. **未闭合字符串不得越吃越多**。

> 该文件**自身刻意不写出那两个符号序列**（用 `OPEN` / `CLOSE` 常量拼接）——
> 否则自检用例本身就成为「注释符落在串内」的受害者，误导其它仍在用 naive 剥离的守卫。
> 这个坑是本批踩过一次后写进 KDoc 的（见 §4 留痕 ①）。

## 4. 过程留痕（真实发生，不隐去）

1. **一次批量改写失败并回退**：首版用脚本一次性改 18 份守卫的 stripper，语句边界识别不全
   （`= source` 后接换行续体的形态被截断、参数名回退猜错）⇒ `compileDebugUnitTestKotlin` 报 6 处语法错。
   **处置**：`git checkout --` 逐文件回退到 §156 提交态（回退范围经 `git status --porcelain` 核对，
   仅这 18 份测试文件，未触碰已提交工作与文档），改为**逐份手改 + 单跑该守卫**。
   教训：**跨多份「安全接线守卫」的批量文本改写不适用**——它们各自的判据性质不同（见 §1），必须逐份裁定。
2. 自检用例首版把 `/*`、`*/` 直接写进测试源文件的字符串里 ⇒ 既让本文件成为其它守卫的误导源，
   又因 Kotlin 原始字符串起始引号的写法触发编译错（`Unresolved reference 'marker'`、
   `Literals must be surrounded by whitespace`）；改为常量拼接 + 手工拼接样例串后通过。
3. `stripStringsAndComments` 套用到「以字面量为判据」的守卫后失败一例（见 §1）——
   本批据此**新增**口径而非放宽该守卫的断言（未删任何判据）。
