### 行尾归一（主控复核发现的真实回归，已修正）

- **回归**：首版清单按**原始字节**计算哈希（误设 `.gitattributes` 能保证工作区字节为 LF——它只保证
  **入库 / 检出**为 LF）。主控独立复核发现 3 个被覆盖脚本——`tools/doc/count_line_tiers.py` /
  `tools/audit/check_launch_language_seed.py` / `tools/passkey-interop/verify_interop.py`——**工作区为
  CRLF、索引为 LF**（`git ls-files --eol` 实测 `w/crlf i/lf`）。首版清单因此存这三条脚本的 **CRLF 哈希**；
  而 CI 以 **LF** 检出，`hygiene-gate` 首步会算出 LF 哈希 ⇒ **CI 假红**（本机因工作区同为 CRLF 而假绿，
  该缺陷在本地任何门禁读数中都不显形）。
- **修正**：`sha256_file` 改为按**行尾归一后**（CRLF / CR → LF）的字节计算；重生成清单（**4 条哈希变更**：
  上述 3 脚本 + 本校验脚本自身），模块 / 函数 docstring 同步说明归一必要性；`--selftest` 新增
  「CRLF 与 LF 同内容必须同哈希」正样本把归一口径锁死。
- **CI 等价复核**：以各脚本内容的 **LF 形态**重算 19 条哈希与清单逐条比对 ⇒ **零失配**（等价于 CI 的 LF 检出）。

  修改脚本与清单的 PR，除「两处敏感面 diff 在评审中可见」这一结构性信号外，仓内**无**独立信任根可
  发现——真正能阻断的只有分支保护 / 必需评审（`PD-04` 裁决不启用）。本批把「单行削弱判据」从

  自身**未**被钉哈希——可经「在机检命令后追加 `|| true`」「删 `run` 块内 `set -euo pipefail`」
