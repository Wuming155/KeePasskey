### ISSUE-P3-212 通行密钥签名私钥材料擦除收敛至加密引擎单点（对齐 KeePassDX 单点清零契约）

- **优先级**：P3 低危
- **核实时间点**：2026-09-20 经 grep 全仓 `signAssertion` 与 `PasskeyAssertionPayload.kt:89-117` 核实
- **核实方式**：当前 `PasskeyCryptoEngine.signAssertion` 仅对内部克隆的 `workingKey` 执行 `Arrays.fill`，而入参 `privateKeyBytes` 依赖各调用方（`PasskeyAssertionPayload`、测试类等）各自在 `finally` 中清零。KeePassDX（`crypto/Signature.kt`）的契约是在签名执行完毕后由底层单点清零调用方传入的私钥缓冲。若调用方遗漏 finally 擦除，可能造成敏感私钥在内存中残留。
- **整改依据**：`AGENTS.md` §3 硬约束第 2 条（敏感数据铁律，擦除收敛）；对齐 KeePassDX `Signature.sign` 签名后清零输入缓冲口径。
- **涉及文件**：
  - `crypto/src/main/java/com/keepasskey/crypto/passkey/PasskeyCryptoEngine.kt`
  - `app/src/main/java/com/keepasskey/app/passkey/PasskeyAssertionPayload.kt`
  - `crypto/src/test/java/com/keepasskey/crypto/PasskeyCryptoEngineTest.kt`
- **验收标准 (AC)**：
  1. `PasskeyCryptoEngine` 增加消费式签名入口 `signAssertionConsumingKey(algorithmId, privateKeyBytes, dataToSign)`（或由 `signAssertion` 直接执行传入数组的清零），在签名完毕（无论成功或异常）的 `finally` 中统一将传入的 `privateKeyBytes` 显式擦除（`fill(0)`）；
  2. `PasskeyAssertionPayload` 消费签名材料改走消费式签名，消除活动层散落清理的遗漏风险；
  3. 宿主单测验证：调用该接口后，传入的入参字节数组已被清零。

### ISSUE-P3-213 通行密钥协调器在写路径上对 v1 历史条目就地自动迁移至 KPEX schema

- **优先级**：P3 低危
- **核实时间点**：2026-09-20 经 `PasskeyEntryCoordinator.kt:154-220` 与 `PasskeyData.kt:134-153` 核实
- **核实方式**：当前 `PasskeyEntryCoordinator.applySignCountPatch` 在原子修补签名计数器时，若既有条目是 v1 旧 schema（`Passkey.*` 旧键名），仅替换/追加了 `Passkey.SignCount`，条目整体仍保持 v1 旧格式；用户即便常态使用该凭据，也永远无法迁移到 KeePassXC / KeePassDX 兼容的 KPEX schema，导致老库无法随使用自然演进（限界 §4.3 第 4 条声明）。
- **整改依据**：渐进式架构演进原则；在已有条目受控变换临界区内，把读出的有效 `PasskeyData` 在需要保存/修补时，通过 `toCustomFields()` 将旧键清洗并换新为标准 KPEX 字段；对 v1 历史私钥（hex/Base64）经编码器转换为 PKCS#8 PEM 文本，实现写路径上的平滑无缝自动收敛。
- **涉及文件**：
  - `app/src/main/java/com/keepasskey/app/data/repository/PasskeyEntryCoordinator.kt`
  - `crypto/src/main/java/com/keepasskey/crypto/passkey/PasskeyCryptoEngine.kt`（提供旧格式私钥转 PEM 工具，或由协调器调用）
  - `app/src/test/java/com/keepasskey/app/data/repository/PasskeyEntryCoordinatorSignCountTest.kt`
- **验收标准 (AC)**：
  1. 当 `PasskeyEntryCoordinator` 对条目进行计数器修补（`patchPasskeySignCount` / `incrementPasskeySignCount`）时，若条目持有 v1 旧 schema 字段且缺少 `KPEX_PASSKEY_*` 核心字段，则在同一受控变换内，将其平滑迁移为标准 KPEX 字段（清洗全部 `LEGACY_FIELD_*`，写入 `toCustomFields()` 规范字段）；
  2. 迁移过程中私钥若为旧 hex 标量或 Base64 种子/DER，自动重包为 PKCS#8 PEM 并以受保护属性写入 `KPEX_PASSKEY_PRIVATE_KEY_PEM`；
  3. 单元测试验证：包含 v1 字段的条目在递增计数器后，KDBX 条目自定义字段中的 `Passkey.RelyingParty` 等旧键被移除，`KPEX_PASSKEY_RELYING_PARTY` 等 KPEX 键被完整建立，且私钥符合 PEM 格式规范。

### ISSUE-P3-214 通行密钥算法识别热路径增强与旧格式精确嗅探

- **优先级**：P3 低危
- **核实时间点**：2026-09-20 经 `PasskeyKeyText.kt:140-165` 与 `PasskeyData.kt:410-412` 核实
- **核实方式**：`PasskeyKeyText.sniffAlgorithmId` 目前仅能嗅探包含 ASN.1 OID 的 PKCS#8 DER / PEM。对于外部历史库中存量的 hex 格式私钥（v1 ES256，定长 32 字节 / 64 字符 hex）或 32 字节 Base64（v1 Ed25519 种子），`sniffAlgorithmId` 返回 null。此时 `PasskeyData.fromCustomFields` 盲目回退为 `ALGORITHM_ES256`，若历史条目为 Ed25519 则断言时将因算法错配而失败。
- **整改依据**：提高旧条目及外部条目算法嗅探的精确度，使热路径候选判定及断言签名无需依赖静默盲回退。
- **涉及文件**：
  - `core/src/main/java/com/keepasskey/core/model/PasskeyKeyText.kt`
  - `core/src/main/java/com/keepasskey/core/model/PasskeyData.kt`
  - `core/src/test/java/com/keepasskey/core/model/PasskeyDataFromCustomFieldsTest.kt`
- **验收标准 (AC)**：
  1. `PasskeyKeyText.sniffAlgorithmId` 扩展支持识别纯 hex（64 字符 hex 标量）为 `ALGORITHM_ES256`，识别 32 字节原始私钥种子为 `ALGORITHM_ED25519`；
  2. `PasskeyData.fromCustomFields` 当私钥无法识别算法且未显式指定 `Passkey.Algorithm` 扩展键时，通过嗅探精准识别，只有在确实全非已知模式时才 fail-safe 回退；
  3. 宿主测试覆盖：v1 hex 文本与 Ed25519 种子私钥经 `fromCustomFields` 还原时，算法标识分别准确为 ES256 与 Ed25519，不再靠盲回退。

## 2. 整改明细

### 2.1 `ISSUE-P3-212`：消费式签名入口 + 活动层清理面收敛

1. **crypto：新增消费式入口**
   - `PasskeyCryptoEngine.signAssertionConsumingKey(algorithmId, privateKeyBytes, dataToSign)`：签名语义 = 内部一行委托
     `signAssertion`，差异只在 `finally` 中 `Arrays.fill(privateKeyBytes, 0)`——**成功与异常两条路径都擦除**（AC①，
     采用条目给出的「新增入口」方案而非改 `signAssertion` 语义：全仓 `signAssertion(` 共 36 处引用
     （定义 1 + 调用 35，其中 **33 处在测试 / 对拍探针**）都按「入参归调用方所有」使用，
     就地改语义会造成静默破坏——例如同一数组被连续两次签名时第二次将拿到全零私钥）。
   - `signAssertion` 的 KDoc 同步写明「不改动调用方缓冲」并指向消费式入口，避免两档语义再被混淆。
2. **app：断言路径改走消费式入口**（AC②）
   - `PasskeyAssertionPayload.build` 的签名调用由 `signAssertion` 改为 `signAssertionConsumingKey`；
     随之**删除**活动层的 `signingKeyBytes` 变量与其 `finally { fill(0) }`——私钥副本的生命周期整体交给引擎单点，
     活动层只剩 `authData` / `clientDataBytes` / `dataToSign` 三个派生中间量（KDoc 逐条更新）。
3. **单测**（AC③，`PasskeyCryptoEngineTest` 新增 3 例）
   - 成功路径：调用后入参缓冲**全零**，且**同时**断言 `signAssertion` 对调用方缓冲零改动（两档语义并列锁定）；
   - 异常路径：非法标量（`d=0`）抛 `CryptoException.InvalidKeyException` 后入参缓冲**同样全零**；
   - 覆盖 Ed25519 种子与 RS256 PKCS#8 DER 两种材料形态（非仅 ES256）。

### 2.2 `ISSUE-P3-213`：v1 → KPEX 写路径就地迁移

1. **core：迁移判据下沉到 schema 属主**（`PasskeyData.needsKpexMigration`）
   - 判据 = **持有任一 v1 旧键 且 KPEX 核心三键（RP ID / Credential ID / 私钥）不齐备**；只扫键名，
     不解密、不建 Map、不物化明文（与 `fromCustomFields` 的 `ISSUE-P3-171` 形状短路同口径），
     故可在写路径每次计数器修补时安全地先判后迁。
2. **crypto：历史文本 → PKCS#8 PEM 的迁移入口**
   - 新增协作单元 `PasskeyLegacyKeyText`（`internal object`，与 `PasskeyKeyCodec` / `PasskeyAssertionSigner` 同级同风格）：
     - `legacyTextToKeyBytes`：hex 标量（2~64 字符，奇数长度左对齐补零半字节）/ Base64 种子 / Base64 PKCS#8 DER → 原始字节；
     - `legacyTextToPemChars`：按算法重包 PEM——ES256 走命名曲线 `secp256r1` 的 PKCS#8（标量有效域复用签名侧
       **同一权威检查点** `PasskeyKeyCodec.parseEcPrivateKey`）、Ed25519 走 RFC 8410 `version = 0`、RS256 结构校验后重包；
       一切失败（形态非法 / 算法不匹配 / 标量越界 / 算法不受支持）**归一为 null**（fail-safe）。
   - `PasskeyCryptoEngine` 暴露一行委托 `legacyPrivateKeyTextToPemChars`（供 app 层调用）与
     `decodeLegacyPrivateKeyBytes`（断言回退路径共用同一解码实现）。
   - **解码口径单点化**：原 `PasskeyAssertionPayload` 内的私有 `decodeLegacyPrivateKeyBytes` / `hexNibble` **逐字搬入**
     `PasskeyLegacyKeyText`，app 层改为调用 crypto 的公开入口（消除两处各持一份 hex/Base64 解析的漂移风险）。
3. **app：在计数器修补的同一受控变换内迁移**（AC①②）
   - `PasskeyEntryCoordinator.entryWithSignCount` 先调 `migrateLegacySchemaIfNeeded(entry)`，再写计数器：
     「迁移动 + 计数器写」同属 `DatabaseSession.updateEntryById` 的**一次**原子替换，不存在中间态。
   - 迁移实现：保留全部非 passkey 字段（按引用复用）→ 丢弃全部 schema 键（`isPasskeyFieldKey`）→
     写入 `data.copy(privateKey = <PEM ProtectedString>).toCustomFields()`（旧键清除 + KPEX 规范字段建立，
     PEM 以受保护属性承载）。私钥重包失败时原样返回条目并留痕日志（**不阻断计数器写入**）。
   - 副产物（既有机制，非本批新增）：被替换下线的 v1 私钥实例随 `eraseSupersededSensitiveData` 定点擦除清零。
4. **单测**（AC③，`PasskeyEntryCoordinatorSignCountTest` 新增 3 例 + `PasskeyLegacyKeyTextTest` 新增 6 例 +
   `PasskeyDataSchemaInteropTest` 新增 2 例）
   - 端到端：v1 条目递增计数器后，7 个旧键**全部**消失、KPEX 核心键与扩展键建立（含保护位与 BE/BS 文本口径）、
     私钥为 PKCS#8 PEM 且经**生产解析链路**还原出的标量逐字节等于原 hex 标量、并可**真实签发**；旧私钥实例已清零；
   - 算法保持：v1 Ed25519 种子条目（无 `Passkey.Algorithm`）迁移后仍按 Ed25519 解析且种子逐字节不变；
   - fail-safe：私钥文本不可解析时保持旧 schema 且计数器照常写入（不产生半套 KPEX 字段）；
   - 迁移工具直测：ES256/Ed25519/RS256 三形态各自「文本 → PEM → 生产解析链路 → 同密钥」往返。

### 2.3 `ISSUE-P3-214`：旧格式精确嗅探

1. **判定顺序重排 + 两类新判据**（`PasskeyKeyText.sniffAlgorithmId`）：
   PEM → 解包 PKCS#8 按 OID 判定（原口径不变）⇒ **恰 64 个 hex 字符 → ES256** ⇒ Base64 / 裸 DER 按 OID 判定
   ⇒ 仍无 OID 但候选恰 32 字节 → **Ed25519**（AC①）。
   - hex 分支**必须先于** Base64 解码：hex 字符集是 Base64 字母表的真子集，64 字符 hex 文本会被 Base64 解码器
     「成功」解出 48 字节无 OID 垃圾——不先判 hex 就永远丢掉了 v1 ES256 的唯一判据。
2. **调用侧语义不变**（AC②）：`PasskeyData.fromCustomFields` 仍是「扩展键优先 → 嗅探 → 回落 ES256」，
   本批只让嗅探在 v1 形态上给出确定答案；真正全非已知模式时才 fail-safe 回落（新用例锁定该边界）。
3. **单测**（AC③，`PasskeyDataFromCustomFieldsTest` 新增 4 例）：v1 hex → ES256、32 字节种子 → Ed25519、
   全非已知形态仍回落 ES256、显式扩展键优先于嗅探结果。

## 4. 过程缺陷与如实声明

1. **hex 分支不吃两侧空白（既有语义，非本批引入，已用测试钉死）**：`PasskeyLegacyKeyText.legacyTextToKeyBytes`
   的 hex 判定发生在去空白**之前**（与该实现的原 app 层版本逐字一致），故 `" 0102 "` 这类带空白的「看似 hex」
   文本走 Base64 分支而非 hex 分支。本批新增用例起初按「先去空白再判 hex」书写而**当场变红**，据此确认为
   **测试假设错误**而非实现缺陷——已把该口径以显式用例 + KDoc 钉死（v1 写入形态本就无空白，实际不受影响）。
   **未**为「看起来更整齐」而改写这份逐字搬移的既有语义。
2. **未改 `signAssertion` 的入参所有权语义**：条目 AC① 允许「或由 `signAssertion` 直接执行传入数组的清零」，
   本批选择新增消费式入口。理由已入 §2.1——35 处既有点中 33 处在测试与设备侧 / 对拍探针（`PasskeyInteropProbeTest`、
   `PasskeyInteropExternalFixtureTest`、`PasskeyNativeSignTest` 等）按「入参借用」使用，
   就地改语义属静默破坏面，代价远高于多一个入口。
3. **迁移是「用到才迁」而非「升级即迁」**：本批不扫描全库、不在解锁时批量改写条目；未被任何断言触及的
   v1 条目仍保持旧形态。限界 §4.3 第 4 条已据此**收窄**（原「v1 旧条目仍不自动迁移」→「只在被断言触及时迁移」），
   互操作对拍记录以**补注**方式留痕（不改写历史结论）。
4. **批次主题边界**：`PasskeyLegacyKeyText` 与 `PasskeyPkcs8Codec` 分工为「历史 v1 文本形态」与
   「PKCS#8 / PEM 编解码」；前者独立成文件是为避免把已 353 行的后者推入 400 档（工程规则「单文件超约 400 行须拆」）。
