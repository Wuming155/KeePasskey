# §223 生物识别解锁默认关闭与「开启前当场验证」批次（`ISSUE-P2-212`）

> **起因**：用户命题「软件的生物识别解锁，默认虽然开了，但是不起作用呀。正常应该由自己手动打开，
> 并且打开那一瞬间验证生物识别呀。」——同时点出**两个**缺陷：① 出厂默认 `true` 与「无封印凭据
> 即无任何生物入口」的实现事实相矛盾，形成静默失效；② 开关切换**不经任何身份确认**，
> 直写偏好即启用。
> **核实时间点**：2026-09-20（开工前复核正文前提——`UserSettings.biometricEnabled` 确为 `true`、
> `SettingsPreferencesController.setBiometricEnabled` 确为裸 `scope.launch { 写偏好 }`、
> 封印登记确只在主密码解锁成功后发生；行号以开工时真实内容为准）。
> **主题**：生物识别解锁开关的**默认态修正**与**开启动作的即时强认证**——默认关闭、由用户手动开启，
> 且开启的**那一瞬间**当场发起一次强生物识别验证，验证通过才写偏好。

### ISSUE-P2-212 生物识别解锁开关默认开启却静默失效，且开启动作不经任何身份确认

- **优先级**：P2 中危（用户可见功能静默失效 + 安全开关状态失真）
- **核实时间点**：2026-09-20 经全仓 `grep biometricEnabled` / `grep setBiometricEnabled` 与
  `BiometricEnrollmentCoordinator.kt` 通读核实
- **核实方式**：`UserSettings.biometricEnabled` 出厂默认 `true`，`RealSettingsRepository`
  读回时亦 `?: true`；而**封印凭据只在主密码解锁成功后**登记
  （`BiometricEnrollmentCoordinator.registerIfNeeded`：`if (!settings.biometricEnabled) return` ⇒
  登记以开关为前置条件）。于是新装设备上出现「设置里开关显示已开、解锁页却没有任何生物识别入口」
  的静默失效——`UnlockModePolicy.resolve` 要求「开关开启 **且** 封印凭据存在」才呈现快速解锁模式，
  凭据不存在时永远回落主密码。
  另一侧，`SettingsPreferencesController.setBiometricEnabled(enabled)` 只做
  `scope.launch { settingsRepository.setBiometricEnabled(enabled) }`——开关可在**未做任何身份确认**
  的情况下被打开，与「生物识别解锁」这一安全开关应有的语义不符。
- **整改依据**：`AGENTS.md` §3 硬约束第 2 条（敏感数据铁律）与「声明 ⇄ 生效一致」原则；
  参照 `docs/references/KeePassDX-架构分析.md` 第 6.4 节「生物识别解锁流程」的
  「用户显式启用 + 启用时即验证」口径。
- **涉及文件**：
  - `app/src/main/java/com/keepasskey/app/data/repository/SettingsRepository.kt`
  - `app/src/main/java/com/keepasskey/app/data/repository/RealSettingsRepository.kt`
  - `app/src/main/java/com/keepasskey/app/ui/screens/settings/SettingsPreferencesController.kt`
  - `app/src/main/java/com/keepasskey/app/ui/screens/settings/SettingsViewModel.kt`
  - `app/src/main/java/com/keepasskey/app/ui/screens/settings/subscreens/SecuritySettingsScreen.kt`
- **验收标准 (AC)**：
  1. 生物识别解锁开关出厂**默认关闭**（`UserSettings` 默认值、`RealSettingsRepository` 未持久化
     读回值、`SettingsUiState` 默认值三处一致），由用户在设置页手动开启；
  2. 用户**打开**开关时**当场发起一次强生物识别验证**（`BiometricPrompt`），
     **验证通过才写入偏好**；取消 / 失败 / 设备无可用强生物识别一律**不写偏好**；
  3. 设备无可用 Class 3 强生物识别（含未录入）时**拒绝开启**并如实提示，
     **绝不**降级到设备锁屏凭据；
  4. 验证进行中开关禁用（防并发发起多个 `BiometricPrompt`），并呈现进度与结果反馈。

## 2. 整改明细

### 2.1 默认态修正（AC①）

1. **`UserSettings` 出厂默认 `true` → `false`**（`SettingsRepository.kt:28`）：KDoc 写明
   「默认关闭 + 开启须当场验证」，并记录原实现「默认 true 却因无封印凭据而完全不生效」的静默失效史。
2. **`RealSettingsRepository` 读回缺省 `?: true` → `?: false`**（`RealSettingsRepository.kt:94`）：
   未持久化过即视为关闭，与出厂默认口径一致（两处若不一致会出现「首启显示开、重启后变关」的抖动）。
3. **`SettingsUiState.biometricEnabled` 默认 `true` → `false`**：仅作预览/默认构造口径，
   运行时该字段恒由持久化值投影（`settingsUiStateFlow` → `userSettings.biometricEnabled`）。

### 2.2 新增 `BiometricEnableCoordinator`：开启动作的当场验证（AC②③④）

**新增** `app/.../ui/screens/settings/BiometricEnableCoordinator.kt`（241 行，含状态类型）：

1. **状态与持久化解耦**（`BiometricToggleUiState`）：`verifying`（验证中）+ `notice`（一次性反馈）。
   拆出独立类型的理由写在 KDoc 里——**开关的选中态只看持久化值**，本状态只表达即时过程，
   两者经投影层合流（`SettingsUiState.biometricVerifying` / `biometricToggleNotice`）。
2. **`setEnabled(enabled, activity)` 分档**：
   - **关闭**：直接落偏好（无需验证），并清除残留提示；
   - **开启**：先做能力闸门，再发起验证，**通过才落偏好**。
   - 验证进行中的重复触发为**幂等空操作**（AC④：不并发发起第二个 `BiometricPrompt`）。
3. **能力闸门 fail-closed**（AC③）：`isStrongBiometricAvailable` 要求
   `BiometricStatus.AVAILABLE` 且认证器集合为 `BiometricAuthManager.UNLOCK_AUTHENTICATORS`
   （Class 3 强生物识别）；未注入管理器 / 无宿主 Activity **一律按不可用处理**，
   以 `R.string.sec_biometric_enable_unavailable` 如实提示并**不写偏好**，绝不降级锁屏凭据。
4. **可选 CryptoObject 绑定**：若活动库已有封印凭据，则以该凭据的**解密 Cipher** 发起验证
   （既证明用户身份，也顺带证明凭据仍可解封）。Cipher 准备失败（生物录入变更致密钥吊销、
   Keystore 不可达）⇒ **清除陈旧凭据**并退化为纯身份验证，登记交由下次主密码解锁完成
   （与解锁侧同一处置口径，避免「开关开着、凭据却注定解不开」的死循环态）。
5. **`Failed` 不是终态**：单次比对未通过时系统弹窗仍驻留等待重试，故 `awaitVerification`
   忽略 `BiometricResult.Failed` 继续挂起，避免「用户最终验证成功、开关却没开」的错位；
   `VERIFY_TIMEOUT_MS = 60_000` 为兜底（宿主 Activity 销毁等极端情形下系统不回调），
   超时按 `ERROR_AUTH_TIMEOUT` 处理，杜绝协程永久悬挂。
6. **可测性**：两处 Android 触点（能力探测 / `BiometricPrompt` 发起）以
   `strongBiometricAvailableOverride` / `promptOverride` 开放替身（与
   `BiometricEnrollmentCoordinator.sealKeyProvisionOverride` 同一约定），生产恒 `null` → 走真实实现。

### 2.3 接线与 UI（AC②④）

1. **`SettingsPreferencesController.setBiometricEnabled` 删除**：原实现只做「裸写偏好」，
   保留即等于留一条**绕过验证**的旁路；原地留注释指向 `BiometricEnableCoordinator`。
2. **`SettingsViewModel`**：
   - 注入 `BiometricAuthManager?` / `BiometricCredentialStorage?`（允许为 null 仅为既有单测注入，
     缺失时开启动作 fail-closed）；
   - 构造 `BiometricEnableCoordinator`，持有 `biometricToggleState` 并作为**第六路流**
     传入 `settingsUiStateFlow`（`SettingsUiStateProjection` 由「五路」改「六路」，原
     `combine(autofillState, databaseConfigState){ Pair }` 扩为 `Triple`，避开 combine 重载上限）；
   - 新增 `activeDatabaseId` 跟踪（`vaultRepository.getDatabases()` 取 `isActive` 首个，
     否则首个），供协调器判定封印凭据是否就绪；
   - `setBiometricEnabled(enabled, activity)` 委托协调器（原 `preferences.setBiometricEnabled` 直写移除）。
3. **`SecuritySettingsScreen`**：
   - 宿主 Activity 经 `androidx.activity.compose.LocalActivity` 获取（**非**
     `LocalContext.current as? Activity`——后者触发 AndroidLint `ContextCastToActivity`，见 §4.1），
     经回调第二参数透传（`onBiometricToggle: (Boolean, FragmentActivity?) -> Unit`）；
   - 开关 `enabled = !uiState.biometricVerifying`（AC④）；验证中呈现 `CircularProgressIndicator`；
     `biometricToggleNotice` 非空时以 `bodySmall` 呈现结果文案。
4. **`SecuritySwitchRow` 新增 `enabled: Boolean = true`**：默认值保证其余十余处既有调用点行为不变。
5. **文案**（中英各 +4 条，`values/strings.xml` 与 `values-en/strings.xml`）：
   `sec_biometric_verify_title` / `_subtitle`（验证弹窗）、`sec_biometric_enable_unavailable`（无可用强生物识别）、
   `sec_biometric_enable_pending_seal`（已启用但凭据待下次主密码解锁登记）。

## 4. 过程缺陷与如实声明

1. **lint `ContextCastToActivity`（本批自身引入并当场闭环）**：设置页最初按
   `LocalContext.current as? FragmentActivity` 取宿主，AndroidLint 报 Error
   `ContextCastToActivity`（该检查禁止把 `Context` 直接强转 `Activity`——Compose 的 `Context`
   可能是 `ContextWrapper` 链中的非 Activity 节点），致 `:app:lintDebug` **BUILD FAILED**、
   issue 计数 214 → 215。改用 `androidx.activity.compose.LocalActivity`
   （`activityCompose = 1.10.0` 已提供，宿主 Activity 精确提供该 CompositionLocal）后回到 **214**。
   `LocalActivity.current as? FragmentActivity` 仍是**窄化**转换（`Activity` → `FragmentActivity`），
   不再命中该检查、也不会因转换为 null 而误启用。
2. **设备侧未跑（如实声明）**：本批**未改动** `*/src/androidTest/**` 下任何用例，
   亦未改原生内核 / JNI 绑定，故未执行 `connectedDebugAndroidTest`；
   仅以 instrumented **源码编译**确认无编译面破坏。`BiometricPrompt` **实际弹窗**与
   `CryptoObject` 绑定按限界 §4.1 仍属「只能靠手工冒烟承担」的既有边界，
   本批未扩自动化（新增的 8 例为**逻辑面**用例，以 `*Override` 替身驱动）。
3. **对既有测试资产的处置（只增不删）**：出厂默认由 `true` 改 `false` 使两个既有用例类的
   前提失效——均按「保留并显式标注」处置，**未删除任何用例**：
   - `QuickUnlockSealDowngradeTest` 的 fixture 显式 `setBiometricEnabled(true)`
     以保留「封印流程降级闸门」原有语义（该类测的是封印降级，不是出厂默认）；
   - `UnlockViewModelBiometricAutoPromptTest` 的两处注释更正为「出厂默认已为 false」，
     用例语义（显式开启 / 显式关闭）不变。
4. **「已启用但凭据待登记」是刻意的中间态而非缺陷**：无活动库或库从未主密码解锁过时，
   验证通过即写偏好并按 `sec_biometric_enable_pending_seal` 如实告知——原生实现下**不存在**
   「未持有主密码即可生成封印凭据」的路径（封印载荷的生成只发生在主密码解锁后的
   `BiometricEnrollmentCoordinator`），本批不发明绕过该约束的机制，改为把该约束**显式传达给用户**。
