## 141.0 原文收录（`ACTIVE_ISSUES.md` 条目正文，原样剪切）

> ### ISSUE-P3-184 详情页 TOTP「复制」按钮未写入剪贴板，仅弹「已复制」提示（谎报成功）
>
> - **背景**：2026-09-17 应用户要求核查「列表行验证码徽标无可点复制入口」的交互成本评估时**顺带发现**：
>   详情页 `TotpCard` 的复制按钮 `onClick` 只 `onShowMessage(UiMessage(R.string.detail_totp_copied))`
>   （`EntryDetailCards.kt:241`），既不经 `clipboardSecurityManager.copySensitiveText`，也不从仓库取码；
>   消费侧 `userMessage` 仅渲染 snackbar（`EntryDetailScreen.kt:100-106`），无任何隐式复制副作用。
>   ⇒ 点击后剪贴板保持**原内容**（可能是上一条目的密码），用户按提示粘贴会**贴出错误凭据**（把 A 条目的
>   密码贴进 B 场景的误贴风险）。
> - **影响**：功能缺陷 + 敏感路径上的误导性成功反馈；验证码本体仍显示在卡片上，无数据丢失 / 泄露（什么都没复制）。
> - **核实时间点与方式**：2026-09-17 全仓检索 `copySensitiveText` / `copyTotp` / `detail_totp_copied`
>   （真实复制仅命中 HOTP 取码 `EntryDetailViewModel.kt:474`、密码复制、受保护字段复制三路径，均非 TOTP 复制）；
>   走读 `TotpCard → EntryDetailScreen:302 → viewModel.showMessage` 全链确认无剪贴板写入。
> - **整改方向**：补真实复制通道——详情页投影已有 `liveTotpCode ?: entry.totpCode`（与卡片显示同源），
>   点击时经 `clipboardSecurityManager.copySensitiveText(title, code)` 复制（对齐 HOTP 路径的通道语义；
>   HOTP 有意不提供复制当前码以免重复消费计数器，TOTP 无此约束），仅复制、不推进任何状态。
>   该通道修好后，列表行验证码徽标挂 `clickable` 直接复制才成为可落地的低成本交互（徽标本无复制入口，
>   进详情页复制此前也实际不可用）。
> - **验收标准**：点击后剪贴板内容为**当前有效码**；走受保护剪贴板（自动清空计时与密码复制一致）；
>   文案与实际行为一致；单测覆盖「复制后剪贴板含码」与只读会话 no-op。
> - **风险提示**：低——纯补齐缺失写入，不触碰既有敏感通道与 FFI 面。

## 141.1 事先声明（口径与边界）

交互必须成本一致——本批 5 项中有 3 项（甲b / 乙 / 丁）正是「同类交互在本应用内存在两套成本」的实例。

## 141.3 关键约束的落地方式（逐条对应用户提出的红线）

| 红线 | 落地 |
|---|---|
| 甲b 徽标点击会吞掉该区域的行点击 / 长按 | 已知且**有意**：徽标处点击语义即「复制」，故长按进批量模式在小块徽标区域失效（用户已确认可接受）；徽标外围不受影响 |
| 甲b 不得破坏 ISSUE-P2-89 / P3-158 的「每秒 tick 只重组徽标」性能契约 | 点击层加在**徽标内部**且不引入新的状态读取；`EntryTotpBadge` 仍是唯一读取 `liveCodes` / `nowSeconds` 的组合作用域 |
| 乙 选项数过多时 `SegmentedButtonRow` 会溢出 | 改用 `FlowRow` 流式换行承载 5~7 档；回调接口（`onAutoLockTimeoutChange` 等）**未动** |
| 丙 仅开启时触发、关闭绝不发起网络调用 | `enableBreachCheckAndScan()` 不含 false 分支；关闭走原 `setBreachCheckEnabled`；`runBreachCheck` 的 `if (!breachCheckEnabled()) return DISABLED` 门控**未动** |
| 丙 并发互斥不得只靠按钮 `enabled` | 复用 `SettingsHealthController.rescanHealth` 首行的 `isHealthScanning` 早退（**第二道门**），自动触发路径因此天然防并发 |
| 丙 失败如实上浮、不新增外发面 | `runBreachCheck` 的 `FAILED` + `breachCheckMessage` 链路**未动**；查询仍走既有 k-匿名范围通道 |
| 丁 同步必须走**已保存**配置，不得用表单内存态 | 编排入口 `verifyConnectionThenSync()` **不接收任何表单实参**；触发点唯一：`if (persistConfig()) onSyncAfterSave()`；成功保存时凭据 `CharArray` 已交出并清空 |
| 丁 保留「未验证不同步」守卫，但由「解锁条件」改为「前置步骤」 | 守卫语义原样保留（`isConnectionVerified` 判据 + `SyncStatusCard` 的 `enabled` 未动）；合并按钮把测试连接变成**串行前一步**，未通过则发「已跳过同步」并停止 |
| 戊 必须 `try-catch` 降级，排障入口不得成为新崩溃点 | `launchSafely` 包 `runCatching`；`resolveActivity` 为空时**不渲染入口**（宁可退回纯文案也不给死链） |
| 戊 `minSdk 36` 下 action 可用性 | `ACTION_REQUEST_SET_AUTOFILL_SERVICE` / `ACTION_ACCESSIBILITY_SETTINGS` 均为 API 26 前已存在的公开 action，无版本门槛 |

**一处按规范纠正的实现（留痕以免后人重蹈）**：戊的实现初版按臆测给 `ACTION_REQUEST_SET_AUTOFILL_SERVICE`
挂了 `Settings.EXTRA_AUTOFILL_SERVICE_COMPONENT` 以预选本应用，**编译期即报 `Unresolved reference`**；
经 `google-developer-knowledge` 检索确认该常量**不在** `Settings` 的公开常量表中（官方仅文档化了
`ACTION_REQUEST_SET_AUTOFILL_SERVICE` 本身）⇒ 改为**只发 action**，并在 `SystemSettingsNavigation` 的 KDoc
写明「**不得**用未公开 extra 冒充『已预选』」。
