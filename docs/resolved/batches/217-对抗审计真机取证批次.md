## 3. 新立条目

- **`ISSUE-P3-209`**：`CleartextPolicyDeviceTest` 的 SSRF 用例**恒真**——断言只有 `error != null`，
  不区分 `UnknownHostException`（守卫拦截）与 `SSLHandshakeException`（自签 TLS 失败），
  故**对守卫是否接线零判别力**；而 `docs/architecture/已知工程限界.md:245` 与 §203 批次据此登记
  「工厂客户端 SSRF 回环防线生效」⇒ **证据链引用错误**（结论本身经本批用例独立证实）。

## 4. 过程留痕（如实登记，不美化）

1. **自方指控被证伪（本批最重要的一课）**：主代理曾据「MockWebServer 用 IP 字面量」提出
   「`CleartextPolicyDeviceTest` 假阳性归因」指控。四轮对抗审查中，该指控先被质疑（第 1 轮证据链缺 host 取值），
   再由上游源码（`mockwebserver3/MockWebServer.kt`）与**真机用例**双双证伪：
   `start()` 以 `InetAddress.getByName("localhost")` 绑定、`url()` 取 `address.hostName`（记忆主机名、不反向解析）
   ⇒ host 是**主机名**，请求**确实**经 `Dns.lookup` 并被 `SsrfGuardDns` 拦截。
   **结论改写为「用例有效但判别力偏弱」**，另立 `ISSUE-P3-209`。**证伪发生在自方主张上，按纪律留痕。**
2. **权限探针断言写错**：首版按「应用私有目录 = 0700」预设断言 `cacheDir`，真机实测 **0771**（`rwxrwx--x`）即红。
   该失败本身即是取证——把断言改为真正的安全不变量（others 不得读写）+ 自建目录的 umask 证据；
   **未放宽被测量的事实，只修正了错误前提**。
3. **PendingIntent 用例形态返工**：首版用动态 receiver + 显式广播读回 extras，真机**未送达**（拿到 `null`）。
   因该投递语义易受实现细节影响、会把用例判别力污染成「投递机制是否可用」，改为**直接验证 `Intent.filterEquals`**
   （匹配键本身，可静态判定且与真实落地 Activity 同源）；旧用例已删除。
4. **诊断用例一次性使用并清除**：为取得 `maxHeap` 与解压结果（结果 XML 不捕获 stdout、Android CLI 无 logcat 能力），
   临时加入一条以断言消息携带实测值的诊断用例，取值后即刻删除；**未留在用例集中**。

## 5. 未闭环项（转出）

- **P2-199 的 A1/A2**：CM 是否在多次响应间保留/复用同一 `PendingIntentRecord`——需两路并发 CM 响应，
  单进程无法自动化；仓库内仍为设备侧待验证项 **C-3**。
- **P2-200 落点① 的「OOM 是否总能被归一」**：本轮证明 OOM **确实发生**；其被 `catch (Throwable)` 捕获的
  可靠性（捕获后 handler 内再分配是否再抛）仍需专项实测，故相关条目措辞保持「best-effort / 不得断言绝无崩溃」。
