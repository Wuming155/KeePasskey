# §372 锁库后冷启动同步误报本地修改批次（`ISSUE-P2-404` 整条闭环）

- **触发**：2026-09-30 用户真机反馈：「每次打开后，都会显示"云端服务器校验版本"，
  然后提示本地修改已经同步了，但我明明没有修改呀。」
- **开放项变动**：P2 区 0 → **1**（登记）→ **0**（本批闭环，P2 区再度归零）。

## 0. 原文收录（登记即闭环，同会话完成）

> **ISSUE-P2-404**（核实时间点 / 核实方式＝2026-09-30，用户真机症状报告——每次打开应用
> （解锁进入列表页）先显示「正在与云端服务器校验最新版本...」，随后提示「本地修改已上传至云端」，
> 而用户**未做任何编辑**；同期根因由**全链路静态逐行推演**定位（各环节均给出代码落点，逐行核实）。
> **如实声明**：该根因链尚未经真机日志取证确证（`AppLog` verbose 的
> 「同步周期开始: cached=..., dirty=...」一行即可确证 `cached=false`），认领时须先复现取证再动手）：
> **锁库清缓存后每次冷启动自动同步都误判「本地修改」并整库重传**。
>
> **症状**：每次「锁库 → 再打开」必现一次无意义整库上传；进程被杀未走锁库回调时缓存残留，
> 不必然复现（默认开启的前台闲置自动锁定约 5 分钟即触发一次，故用户感知为「每次打开」）。
>
> **根因链（五环相扣，缺一不现）**：
> 1. **锁库全量清缓存**（安全设计，`ISSUE-P1-07`）：`SyncCacheEvictor.onSessionLocked()` →
>    `evictAll()` 把 `cacheDir/sync` 的 `.cache` / `.version` / `.baseversion` / `.basecache` /
>    `.meta` 全部销毁（`SyncCacheEvictor.kt:46`）；
> 2. **冷启动自动同步**（`VaultListViewModel.kt:198` init 内 `triggerPullRefresh`）时缓存缺失：
>    `SyncCycleSetup.buildCycleContext` 走 `!isCached` 分支 ⇒ `localBytes` = 当前库**重新序列化**
>    的新字节（KDBX4 每次保存重生成 masterSeed / IV / KDF salt，字节必然漂移），且不写缓存
>    （`SyncCycleSetup.kt:164`）；
> 3. **「有本地修改」是保守占位而非证据**：`SyncContentChangeDetector.resolveLocalContentChanged`
>    在内存基线（冷启动为 null）与缓存快照（已清）双缺失时 `return true`（`SyncContentChangeDetector.kt:51`）；
> 4. **字节级短路永不命中**：远端存在 ⇒ 走步骤 4 `openRemote` 未缓存分支下载远端，
>    `handleRemoteSynced` 首分支 `openResult.remoteBytes.contentEquals(ctx.localBytes)` 是**字节级**比较——
>    内容相同的两次独立序列化在随机 IV 下恒 false ⇒ 落入 `isDirty || hasLocalContentChanged`
>    （此刻为第 3 环的保守 true）分支转三方合并（`SyncCycleRemoteOutcomes.kt:38`、`:45`）；
> 5. **合并上传无内容相同短路**：`.basecache` 同被清空 ⇒ `resolveTrustedBase(null)` 退化空底版并集；
>    本地与远端内容一致 ⇒ 无条目级冲突 ⇒ `autoMergeAndUpload` **无条件**序列化上传并返回
>    `MergedAndUploaded`（`SyncConflictAutoMerge.kt:114`、`:160`），UI 映射为 `vault_sync_uploaded`
>    「本地修改已上传至云端」（`VaultListSyncController.kt:109`）。
>
> **危害**：① 每次打开全库上传（带宽 / 电量 / 大库下秒级卡顿面）；② 远端 ETag 与修改时间频繁
> 无意义前移，多设备协同噪音源；③ **加剧坚果云限流**——`ISSUE-P2-402` 已认定 429/503 限流为
> 真实诱因，本缺陷是同链条上的请求放大器。
>
> **参考项目对照（2026-09-30，经 `docs/references/keepass2android-架构分析.md` §5.4/§9.2 定位后
> 对源码定点核实）**：
> - kp2a **不存在本缺陷的结构性前提**：`App.Lock()`（`src/keepass2android-app/app/App.cs:128`）
>   只清内存态，**离线缓存（`.cache`/`.version`/`.baseversion`）跨锁永久保留**，仅设置页
>   「清除离线缓存」入口可手动清（`AppSettingsActivity.cs:626`）。且 kp2a 是**单副本架构**——
>   同步缓存工作副本就是「本地数据库文件」本身，不存在「本地文件 vs 缓存」二元结构，故其
>   「本地无修改」判定是纯哈希等式（`CachingFileStorage.cs:184` `localVersion == baseVersion`），
>   **决策树里根本没有「基线缺失保守占位」这个分支**。
> - kp2a 显式同步任务（`SynchronizeCachedDatabase.cs:127-150`）远端未变时：有本地修改才上传；
>   **两端一致 ⇒ `FilesInSync` 零上传零下载**——这正是本缺陷误报分支本应呈现的行为。
> - KeePassDX 无云同步引擎（仅手动并入第二文件的三方合并），本缺陷无对应裁决可借鉴。
> - 结论：KeePasskey 相对 kp2a 的两处分叉（P1-07 锁库清缓存 + 「用户可见库文件 / 同步缓存」
>   双副本，后者服务于云端打开与无同步本地使用）制造了 kp2a 没有的「本地树在手、基线已销毁」
>   窗口；本条整改即给 kp2a 的 `FilesInSync` 分支补上「基线丢失后仍可命中」的通路（内容级比较），
>   **不是**推翻既有架构分叉。
>
> **验收标准**：AC① 行为级单测：锁库清缓存后冷启动同步周期，本地与远端**内容一致** ⇒
> 结果为 `UpToDate` 且 mock Provider 零 `uploadAtomic` 调用、远端字节经 adoption 交付缓存重建基线；
> AC② 回归：本地与远端**内容确有差异**（缓存缺失场景）⇒ 仍按既有合并 / 上传路径收敛；
> AC③ 真机：锁库 → 解锁 → 自动同步显示「云端数据库同步校验完成，当前为最新版本」，
> 坚果云远端文件修改时间 / ETag 不变；连开两次第二次不触发上传。

## 1. 排查过程（证据链）

1. **文案反查**：`vault_sync_uploaded`（「本地修改已上传至云端」）仅 `VaultListSyncController`
   一处消费，触发条件为 `SyncOutcome.UploadedLocal / MergedAndUploaded`；
   「正在与云端服务器校验最新版本...」（`vault_sync_verifying`）是列表页同步指示态——
   与用户描述的两段式症状完全吻合，且解锁进入列表页的自动同步触发点在
   `VaultListViewModel` init（`ISSUE-P3-272` 接线）。
2. **上传出口穷举**：`UploadedLocal` 三个产出点（首传基线 / 快速提交 / `LocalWinAutoUploaded`
   与 `RemoteLostRestored`）+ `MergedAndUploaded`（自动合并上传）。逐条排除后收敛：
   冷启动场景（无编辑 ⇒ `isDirty=false`）唯一可达的整库上传出口是步骤 4 的合并路径。
3. **五环根因链**（见 §0 原文）：锁库清缓存 → 重序列化字节漂移 → 保守占位 `true` →
   字节级 `contentEquals` 恒不命中 → 合并上传无内容相同短路。每环均有代码落点逐行核实。
4. **参考项目定点调研**（用户指示）：kp2a 锁库不清缓存 + 单副本架构，故无此缺陷形态；
   其显式同步的 `FilesInSync` 分支（远端未变 + 本地未变 ⇒ 零上传）是本缺陷误报分支的应然行为。
   KeePassDX 无云同步，无可借鉴裁决。

## 2. 整改

- **`SyncContentChangeDetector` 三态化**：新增 `internal enum class LocalContentChangeState`
  （`UNCHANGED` 内容级确证一致 / `CHANGED` 内容级确证有变化（含缓存损坏保守归类）/
  `BASELINE_MISSING` 基线与缓存双缺失的保守占位），`resolveLocalContentChanged` 返回三态
  （收 `internal` 可见性）；KDoc 写明三态语义与「占位不得当证据消费」的边界。
- **贯穿**：`SyncCycleContext` 与 `RemoteSyncContext` 各增 `localChangeState` 字段
  （`hasLocalContentChanged` 保留为其 Boolean 投影，既有判定口径不变）；
  `SyncCycleRunner.handleOpenRemote` 透传；装配段 verbose 日志增列 `localChange=`（真机取证面）。
- **`handleRemoteSynced` 内容级兜底**：字节级短路不命中后、进入合并分支前，当
  `!isDirty && localChangeState == BASELINE_MISSING` 时解析远端字节并复用 `KdbxContentComparator`
  与本地树做内容级比较——一致 ⇒ 走「两端一致」同款收尾（`adoption.accept()` 交付远端字节重建
  缓存与基线三步 + `lastSyncedDb` 前移 + 返回 `UpToDate`，会话树不替换）；确有差异 ⇒ 原样落入
  既有合并路径。解析产物仅用于比较，比较后 `clearSensitiveData()` 显式擦除（`ISSUE-P3-119`
  同款纪律）。
- **边界红线（未触碰）**：锁库清缓存（`ISSUE-P1-07`）安全设计原样保留；真实本地修改
  （内容级确证）的快速提交 / 合并上传语义（F1「已落盘未同步」覆盖面）原样保留；
  远端更新 + 本地未变的远端接管路径不受影响（该场景 `BASELINE_MISSING` 下仍走合并收敛，
  与整改前一致，无回归）。

## 4. 过程留痕

- 首轮编译红一次：`SyncCycleSetup` verbose 日志引用了声明于其后的 `localChangeState`
  （Unresolved reference）——日志块移到三态声明之后回绿，非逻辑缺陷；
- 首轮编译红一次：`SyncContentChangeDetector` 为 public 类，公开函数暴露 internal 返回类型
  （EXPOSED_FUNCTION_RETURN_TYPE）——`resolveLocalContentChanged` 收 `internal` 回绿
  （消费方仅同模块周期内部件，与 `SyncCycleContext` 等既有 internal 口径一致）；
- 已否决替代方案（防复提，详见 §0）：① 取消锁库清缓存——击穿 `ISSUE-P1-07` 失窃爆破
  威胁模型；② `filesDir` 持久化「上次同步内容哈希」——KDBX4 序列化字节非确定，字节哈希
  无从命中，等价内容哈希需规范化序列化层，改动面远大于本方案；
- 可选后手（未纳入本批）：仿 kp2a 精神在 `filesDir` 持久化「上次同步后库文件字节哈希」
  （仅摘要非密文，不触 P1-07），冷启动免 KDF 直接判定「库文件自上次同步未动过」；
  `VaultFileBaselineHolder`（`ISSUE-P2-378`）已具备同型载体，是否合入由后续批次按复杂度裁决。
