## §1 条目与整改

### ISSUE-P3-530：常驻通知「自动锁定倒计时」越过零点后显示负数

**条目原文（登记入 `ACTIVE_ISSUES.md` 后本批整条剪切归档，文字逐字）**：

> - **核实时间点**：2026-10-07；**核实方式**：① 用户真机反馈「密码库锁定倒计时会出现负数」，
>   追问确认**出现在通知栏常驻通知**（非解锁页节流倒计时）；② 全库逐处核对每个「时长 → 数字」显示点
>   （时长换算 / 下限钳制 / 取模），确认**唯一**可能为负者即本处——解锁页节流倒计时由构造保证
>   `remainingMs > 0` 且 ticker 与 UI 双重钳制，TOTP / 剪贴板 / 列表徽标倒计时均有 `coerceAtLeast(0)`；
>   ③ 框架行为取证：本机 SDK 源码 `sources/android-36.1/android/widget/Chronometer.java` 对越过零点的
>   倒计时走 `R.string.negative_duration`（即 `-%s`），**不会停在 0**；④ 平台机制取证：
>   `NotificationManagerService.java`（`aosp-mirror` master，2026-10-07 现取；行号为核实时刻快照）。
> - **背景**：`UnlockedNotificationController.post()` 在有自动锁定截止点时用
>   `setWhen(deadline) + setUsesChronometer(true) + setChronometerCountDown(true)` 交系统秒表渲染，
>   而撤销 / 刷新只能在**进程存活**时由本应用完成（到点 `_lockDeadline` 落 `null` 后重投空闲文案；
>   锁库则整体 `cancel()`）。通知归系统所有、**不随进程消亡**（本类 KDoc 已声明同一事实）：
>   进程被系统回收后 `AutoLockManager` 的 `delay()` 定时任务随之消失 ⇒ 通知留在通知栏、`when` 已成
>   过去时刻 ⇒ 系统秒表越过零点继续走，显示 `-0:01`、`-0:02`…，并一直累积到下次冷启动
>   `start()` 无条件 `cancel()` 才撤销。同状态下通知还持续声称「密码库已解锁」，而内存会话早已不存在。
> - **涉及文件**：`app/src/main/java/com/keepasskey/app/notification/UnlockedNotificationController.kt`
>   （`post()` / `cancel()`）、`app/src/main/java/com/keepasskey/app/notification/NotificationGate.kt`（纯决策层）。
> - **验收标准**：① 倒计时态的「到期撤销」改交**系统侧**（`Notification.setTimeoutAfter`，由
>   `NotificationManagerService` 直接排定 `ELAPSED_REALTIME_WAKEUP` 闹钟），**进程被回收也成立**；
>   ② 重投常驻通知时不得留下上一版已排定的系统 timeout 闹钟——该闹钟按**通知 key** 命中当前这条并撤销它，
>   而 NMS 只在通知被**撤销**时取消闹钟；③ 非倒计时态**必须不设** timeout（`setTimeoutAfter(0)` 等于立刻撤销，
>   会瞬间吞掉常驻通知，同 `NotificationGate.totpRemainingSeconds` 已立的教训）；④ 全量 `test` 全绿 **且**
>   `python tools/doc/gate_readings.py` 全 PASS，读数块原样入批次档。

**机制核实（开工前，2026-10-07，四条独立证据）**：

1. **症状位置（用户回执）**：**先问后动**——用户确认负数出现在**通知栏常驻通知**，而非解锁页
   「密码库已临时锁定，请在 N 秒后重试」的失败节流倒计时。该处正是全库唯一的**系统渲染**倒计时（证据 2）。
2. **全库排查：唯一可能为负者**（逐处核对每个「时长 → 数字」显示点）：
   - 解锁页失败节流倒计时（`unlock_error_locked_out_seconds` / `_minutes`）：
     `ThrottleGate.Locked.remainingMs` 由 `UnlockThrottleManager.gate()`（`remaining > 0` 才判 `Locked`）
     与 `registerFailure()`（`backoff > 0` 才判 `Locked`）保证**恒 > 0**；ticker 每拍减 1 s 且
     非正即归零并跳出；UI 又只在该值 `> 0` 时渲染该行 ⇒ **结构上不可能为负**；
   - TOTP（列表徽标 / 详情 / 验证器环）、剪贴板清空倒计时、`EntryDetailTotpTicker`：均有
     `coerceAtLeast(0)` 或取模恒正；
   - **常驻通知**：`setWhen(deadline) + setUsesChronometer(true) + setChronometerCountDown(true)`
     ——数字由**系统**渲染，本应用无法钳制，越过零点也无处回落。
3. **框架行为（本机 SDK 源码 `sources/android-36.1`）**：`android/widget/Chronometer.java:356-367`
   ```java
   long seconds = Math.round((mCountDown ? mBase - now - 499 : now - mBase) / 1000f);
   boolean negative = false;
   if (seconds < 0) {
       seconds = -seconds;
       negative = true;
   }
   String text = DateUtils.formatElapsedTime(mRecycle, seconds);
   if (negative) {
       text = getResources().getString(R.string.negative_duration, text);
   }
   ```
   AOSP `core/res/res/values/strings.xml:5708-5709`：
   ```xml
   <!-- The representation of a time duration when negative. An example is -1:14. ... -->
   <string name="negative_duration">\u2212<xliff:g id="time" example="1:14">%1$s</xliff:g></string>
   ```
   ⇒ 越过零点**不停在 0**，而是继续显示 `−0:01`、`−0:02`…（`\u2212` 为 U+2212 减号）。
4. **平台机制（AOSP `NotificationManagerService.java`，`aosp-mirror` master 2026-10-07 现取；行号为核实时刻快照）**：
   - **排定**：`scheduleTimeoutLocked()`（`:9885-9892`）——仅当 `timeoutAfter > 0` 时
     `mAlarmManager.setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP, SystemClock.elapsedRealtime() + timeoutAfter, pi)`；
     PendingIntent 以**通知 key** 为 data（`getNotificationTimeoutPendingIntent()`，`:9869-9883`）。
     **闹钟由 system_server 自行排定 ⇒ 应用无需 `SCHEDULE_EXACT_ALARM`**（已查：该文件无同名权限判定）。
   - **撤销**：`cancelScheduledTimeoutLocked()`（`:9896-9902`）的**唯一调用点**在
     `cancelNotificationLocked()`（`:10487-10491`）⇒ **重投同键通知不会撤销旧闹钟**（这正是 AC② 的由来）。
   - **触发**：`mNotificationTimeoutReceiver`（`:1975-2010`）按 key `findNotificationByKeyLocked` 后
     `cancelNotification(..., REASON_TIMEOUT ...)`，撤销排除位仅
     `FLAG_FOREGROUND_SERVICE | FLAG_USER_INITIATED_JOB` ⇒ 本通知（`FLAG_ONGOING_EVENT` / `ONLY_ALERT_ONCE` 等）
     **在时限内**。
   - **缺陷链**：进程被系统回收 ⇒ `AutoLockManager.scheduleBackgroundLock()` 的 `delay()` 随进程消失
     （到点重投空闲文案 / 锁库整体撤销**都无人执行**）⇒ 通知留在通知栏、`when` 已成过去时刻 ⇒
     系统秒表越过零点显示负数，并一直累积到下次冷启动 `start()` 的 `cancel()` 才撤销。

## §3 如实声明

1. **设备侧对照走查未做**（已另立 `ISSUE-P3-531`）：`adb devices -l` 现查**无任何设备在位**，故本批证据
   全在宿主侧（纯函数用例 + 接线守卫 + 全量 `test` + 门禁）。而本例的**建成效果依赖 OEM 通知面**——
   §428→§432 三项（通道重要度 / 展开态样式 / 动作落点）**都只有装机回执才能判定**，KeePassDX 那句
   「Won't work with Xiaomi」在本机也不成立。故按 §463 → `ISSUE-P3-526` 的先例**另立 P3 条目**
   `ISSUE-P3-531` 承载，并在条目内写明可执行判据（截止时刻通知**自行消失**而非显示负数、
   `dumpsys alarm` 见平台包排定的 timeout 闹钟、`am kill` 不得用 `force-stop`、补「截止前回前台」一态）。
2. **未跑**：`connectedDebugAndroidTest`（本批零设备侧代码面）、`lint`、`assembleRelease`、截图包装编译门禁、
   KPEX 对拍（未触碰 KPEX 字段 / 编解码）。
3. **闹钟排定方与权限**：`setTimeoutAfter` 的闹钟由 system_server 以 `ELAPSED_REALTIME_WAKEUP` 排定
   （AOSP `:9889-9890`），按该类型语义**含整机休眠时间并会唤醒设备**，与秒表口径一致；应用侧不需
   `SCHEDULE_EXACT_ALARM`。反过来说，**若某厂商定制未排定该闹钟，负数会复现**——这正是 §3.1 的走查判据。
4. **`setWhen(now + countdownTimeoutMs)` 的写法说明**：`countingDown` 由纯决策函数给出，Kotlin 无法据此对
   `deadline: Long?` 做智能转换；而 `deadline - now + now == deadline` 为同一取值口径（Long 精确算术），
   故以「剩余时长」回推截止点，避免 `!!` 或把判空条件再写第二遍（重复判据易漂移）。
