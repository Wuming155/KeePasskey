## 1. 条目正文（原样收录）

### `ISSUE-P3-292`：合并历史取三方并集且不截断（未编辑过的条目永久留存对端快照，并放大 `ISSUE-P1-276` 的引用计数）

- **核实时间点**：2026-09-23 经截断挂载点核对（本条由首轮 P2 **降级**为 P3：原「撞 128 MiB 致全端停摆」的定性被否证——历史附件只是 `<Value Ref="x"/>` 短节点，膨胀驱动量是文本，冲破外层 128 MiB 载荷界需量级离谱的快照数）。
- **核实方式**：`sync/.../merge/KdbxEntryMerger.kt:168` 为 `local.history + remote.history + base.history` 三方并集，仅按 `times.lastModificationTime` 去重；条数 / 体积修剪函数 `pruneHistory` 只挂在 `database/.../history/HistoryManager.kt:48`（`recordHistorySnapshot`）与 `:83`（`rollbackToSnapshot`），保存路径的整树修剪只有 `pruneGroupHistoryByAge`（`:130`，按天数不按条数）⇒ **用户未再编辑过的条目，合并来的历史永久留存**；合并落库与写出（`SyncConflictController.kt:357/380`）不经任何截断。
- **后果**：① 每个历史快照是完整 `KdbxEntry`（含各自 `ProtectedString`），内存逐快照单调增长；② 回滚界面会出现对端旧版本；③ **与 P1-276 的耦合（`ISSUE-P1-276` 已于 §273 闭环）**——每多一条历史就给同一池条目多写一个 `<Ref>`，即 `N` 每轮 +1。P1-276 整改后该耦合的表现已由「**整库打不开**」降级为「**放大上限被推高**」：新判据「单条目引用次数 ≤ 1024」「单条目物化字节 ≤ 64 MiB」正是按『合并历史未截断』这一现状取的宽值，**故本条不落地，`MAX_REFERENCES_PER_POOL_ITEM` 就不能收紧**（见 [`architecture/已知工程限界.md`](../../architecture/已知工程限界.md) **§29** 的解除条件）。
- **对照**：KXC `Merger.cpp:452/598`（合并内 `truncateHistory`）、官方 `PwDatabase.cs:939` → `PwEntry.cs:646-685`（按条数 + 体积修剪）均在合并后截断。
- **涉及文件**：`sync/src/main/java/com/keepasskey/sync/merge/KdbxEntryMerger.kt`、`app/src/main/java/com/keepasskey/app/sync/SyncConflictController.kt`、`database/src/main/java/com/keepasskey/database/history/HistoryManager.kt`。
- **验收标准**：AC① 合并产物在落库前按库 Meta 的 `HistoryMaxItems` / `HistoryMaxSize` 截断（与 `pruneHistory` 复用同一函数，禁两份口径）；AC② 用例：双侧各 6 条历史合并后 ≤ 上限，且被截掉的快照仍按既有约定处理；AC③ 与 `ISSUE-P1-276` 的耦合**已单向闭环**（该条 §273 闭环，指针与耦合说明见 [`273-附件池引用计费重定口径批次.md`](273-附件池引用计费重定口径批次.md) 与限界表 **§29**）——**本条落地后必须复评** `KdbxAttachmentBudget.MAX_REFERENCES_PER_POOL_ITEM` 的取值依据（该上限当前正是按「合并历史不截断」取的宽值），复评结论须回填限界表 §29 与本节；禁「只修一个就算闭环」；AC④ 用例只可新增，不得删除既有合并历史用例（测试资产纪律 ①）。

**开工前前提复核（2026-09-24）**：成立，四处缺陷全部复现。① `KdbxEntryMerger` 确为三方并集 + 升序 `sortedBy`；② 两条合并路径（`SyncConflictController.resolveConflicts` 的用户裁决路径与 `SyncConflictAutoMerge.autoMergeAndUpload` 的自动合并路径）确在 `localDb.copy(rootGroup = …)` 后**直接**序列化 / 采纳，无任何截断；③ `HistoryManager.pruneHistory` 为 `private`，外部无法复用（故须新增公开入口，禁在下游另写一份）；④ `sys` 模块只依赖 `core`（`sync/build.gradle.kts`），**不能**调用 `database` 的 `HistoryManager` ⇒ 截断点只能落在 app 侧（依赖 direction 见 `AGENTS.md` §3.1）。**另发现**（见 §4）：合并历史的排序方向与本仓 `HistoryManager` 的位置口径相反。

## 2. 整改

### 2.1 截断入口（AC①，单一口径）

- `database/.../HistoryManager.kt` 新增公开入口
  `pruneGroupHistoryByLimit(group, maxItems, maxSize)`：对整棵分组树递归按库级上限修剪，
  与 `recordHistorySnapshot` / `rollbackToSnapshot` **复用同一 `private pruneHistory`**
  （禁两份数字）；沿用 `pruneGroupHistoryByAge` 的**惰性分配 + 无变化返回同一实例**范式。
- `app/.../sync/SyncConflictMergeAdjudication.kt` 新增内部助手
  `truncateMergedHistory(db)`：取 `db.historyMaxItems` / `db.historyMaxSize`（即库级 Meta 的两个上限）
  调用上述入口，无变化时返回**同一 `KdbxDatabase` 实例**。
- 两条合并路径各在**构建 `mergedDb` 的那一步**套用该助手：
  - `SyncConflictController.resolveConflicts`（用户裁决路径）；
  - `SyncConflictAutoMerge.autoMergeAndUpload`（自动合并路径）。
  位置刻意选在 `codec.serializeLocalDatabase(mergedDb)` **之前** ⇒ **上传给云端的字节与本地落库的树
  取自同一个已截断产物**，不存在「本地截了、远端没截」的裂口。

### 2.2 连带修正：合并历史的排序方向（整改中发现的耦合缺陷）

**发现**：`KdbxEntryMerger` 把合并历史按 `sortedBy { lastModificationTime }` **升序**输出（头部最旧），
而本仓 `HistoryManager` 的约定是**头部最新**（`recordHistorySnapshot` 头插、`pruneHistory` 以
`take(maxItems)` 保留头部，二者由 `HistoryManagerTest` 锁定）。两侧相反 ⇒ 直接套用 `pruneHistory`
会在合并产物上**裁掉最新快照**（数据损失方向），且合并来的历史在详情页**倒序**显示。

**处置**：`KdbxEntryMerger` 改 `sortedByDescending`（对齐本仓约定）。
`KdbxMergerTest` / `KdbxMergerV2Test` 中两处「按升序」断言随之更正，
**并逐处注明这是口径更正、被覆盖的集合与去重判据未变**（非删用例、非放宽断言）。

> 方向判据来自官方实现（格式裁决者）：`参考项目/KeePass-2.61.1-Source/KeePassLib/PwEntry.cs`
> 的 `CreateBackup` 明注 `m_lHistory.Add(peCopy); // Must be added at end`，
> `RemoveOldestBackup` 按**时间戳**找最旧（而非按位置）。**读取侧尚未归一文件顺序**
> 这一残余已即时补登 `ISSUE-P3-306`（`ISSUE-P3-306` 不在本批范围，**未修复**）。

### 2.3 AC③ 复评：`MAX_REFERENCES_PER_POOL_ITEM` 维持 1024

按 AC③ 要求复评并回填两处（限界表 **§29** 与 `KdbxAttachmentBudget` 常量 KDoc）：

- **截断已生效**：单附件的历史快照数**不再随合并轮次单调增长**（§29 边界 ③ 的既有表述已更新）。
- **但上限不可据此收紧**：
  ① 上界实际是「共享该池条目的**条目数** × (1 + `historyMaxItems`)」，条目数维度本不受历史截断约束；
  ② `historyMaxItems` 的官方语义含 **-1 = 不限制**（合法配置），此时上界回到「无界」；
  ③ 默认 Meta 下单条目贡献 ≤ 11 次引用，1024 仅约等于 93 个共享条目的额度，进一步收紧会对
  「多条目共享同一附件（去重）」的合法大库造成 `ISSUE-P1-276` 同型的**自伤型误拒**。
- **「恢复整库维度可拦截口径」亦不采纳**：去重口径使「整库字节」维度恒真，恢复它等于恢复 §273 明确否证的误拒面。
- ⇒ 结论：**维持 1024**；放宽仍被 §29 边界 ① 禁止。

## 3. 验证

### 3.1 新增用例（AC②④）：`app/src/test/java/com/keepasskey/app/sync/MergedHistoryTruncationTest.kt`（4 例）

1. `双侧各 6 条历史合并后按库级上限截断且保留最新`——**前置断言**合并产物确为未截断的 12 条并集
   （防「截断断言恒真」的假绿）+ 方向为降序；截断后恰为 10 条，且**保留集恰为最新 10 条**
   （被裁的是最旧的 1100 / 1200）；
2. `未超上限时返回同一实例不做无谓重建`（`assertSame`）；
3. `合并路径与记录路径产出的历史方向一致`——记录路径（`recordHistorySnapshot`）产出后逐项断言时间戳
   序列，证明两条路径同为「头部最新」；
4. `体积上限同样自最旧端（列表尾部）移除`——三条快照尺寸量级分离（约 10k / 20k / 30k），上限 45k
   ⇒ 精确保留最新一条（断言不依赖 `estimateHistoryItemSize` 的固定开销细节）。

**既有用例未删**（AC④）：`KdbxMergerTest` / `KdbxMergerV2Test` 的方向断言为**口径更正**（升序 → 降序），
集合与去重判据断言原样保留；`HistoryManagerTest`（记录 / 修剪 / 保留期）**零改动且全绿**。

> **踩坑留痕（重要）**：首版把「裁最旧」实现为**纯时间戳口径**（对齐官方 `RemoveOldestBackup`），
> 结果把 `HistoryManagerTest` 的两条既有用例改红——该实现依赖时间戳严格单调，而该用例的多个快照
> **时间戳并列**（同一毫秒内构造），稳定排序退回索引序 ⇒ 在「头部最新」的列表上反而裁掉**最新**。
> 说明本仓的位置口径（`take` 保留头部）在**方向已被保证**时才是正确且稳定的选择；
> 真正该修的是**方向来源**（合并器 + 读取侧），故改为修正合并器而非重写修剪算法。
> 这条踩坑正是把方向问题从「合并器小瑕疵」升级为独立条目 `ISSUE-P3-306` 的直接原因。
