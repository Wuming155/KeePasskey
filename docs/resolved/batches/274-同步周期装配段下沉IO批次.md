## 2. 整改

### 2.1 AC①：装配段整体下沉 `Dispatchers.IO`（单点包裹）

`SyncCycleRunner.runSyncCycle` 的装配调用点（整改后 `:218`）：

```kotlin
val setup = withContext(Dispatchers.IO) { setupCycleContext(activeFile, currentDb) }
```

**为什么选「调用处整体包裹」而不逐个函数改造**（条目 AC① 括号内给的是两条并列手段，本批取前者）：

1. **四类缺陷一次收口**——`setupCycleContext`（整改后 `:114-170`）是**一条直线代码块**，凭据解密（`:97`/`:102`）、整库缓存读（`:128`/`:138`）、全库比较（`:139`）、tmp 写 + `fd.sync()` + rename（`:146`）全部在内，整体包裹即全部下沉；逐函数改 suspend 只覆盖 `SyncCache` 三处，剩下两类仍要靠第二套手段补。
2. **抗回归**——日后在装配段内新增任何同步 IO 调用，自动获得同一保障；逐函数改造则每加一处都要人去改。
3. **不扩散 API 变更面**——`SyncCache` 被 `SyncEngine` 大量调用（`SyncEngine.kt:92/97/103/105/156/220/236/237/336/337/359/408/451`、`SyncEngineSupport.kt:49/82/83`），改其公开签名会把影响面推到整个 `sync` 模块。
4. **互斥语义不变**——`withContext` 嵌在 `session.mutex.withLock` 内部，`Mutex` 与线程无亲和性，锁的覆盖范围与拆分前逐字一致；`withContext` 返回后步骤 2/3/4 仍在调用方线程，其内部经 `SyncEngine` 的 IO 兜底不变。

装配段内不存在主线程专有 API（SharedPreferences / Keystore / 文件 IO 均线程安全），Keystore 操作在 IO 线程上执行无副作用。

### 2.2 AC②：KDoc 与实况对齐

`SyncCycleRunner` 类 KDoc 的「调度边界」段（整改后 `:36-42`）由「与拆分前一致：加密与合并在 Default、网络与写盘在 IO，**本类不额外切线程**」改写为三条并列，并点明反直觉处：**「引擎内的 `Dispatchers.IO` 兜底覆盖不到装配段」**——因为装配段是绕开 `SyncEngine` 直调 `SyncCache` 的，原 KDoc 把该段误划入「sync 模块内」的 IO 范围。

### 2.3 AC③：守卫用例（五类探针 + 栈归因 + 非空性断言）

新增 `app/src/test/java/com/keepasskey/app/sync/SyncAssemblyOffMainThreadTest.kt`（373 行 / 1 例）。

**四类探针的落点选择**（每类一个可观测点，缺一即断言①红）：

| 原子写 | `SyncCache.writeCache`（本批 `open` 化） | 同记录型子类 |

**两个必要的生产侧测试接缝**：

- `SyncCycleRunner.syncCacheFactory`（新增，`:86` 声明 / `:129` 使用）——`@VisibleForTesting internal var`，生产恒为 null ⇒ 就地构造真实 `SyncCache`，行为零变化。之所以必须新增：本类在装配段内**自行**构造 `SyncCache`，记录型子类没有别的入口。口径与 `SyncSessionState.testSyncProvider` 一致（本仓既有注入模式）。

**用例的两条断言 + 一套归因**：

- **栈归因**：栈上存在 `SyncCycleRunner.setupCycleContext` 即判定「来自装配段」。引擎侧经 `handleOpenRemote` 发起的同名 `SyncCache` 调用栈上**没有** `setupCycleContext`，故不会被误认。
- **断言①（非空性）**：五类探针都必须**归因于装配段**——否则「装配段根本没跑到那一步」时断言②会空转通过。该断言在本批实测中立刻抓到一次真实失效（见 §4.2）。
- **断言②（零主线程 IO）**：所有记录（含引擎侧同名调用）的执行线程都不得等于本用例的主线程基准。

**主线程基准的取法**：`Dispatchers.setMain(StandardTestDispatcher)` 后取 `withContext(Dispatchers.Main) { Thread.currentThread() }` 的**真实线程**——不依赖「测试主体恰好就是主线程」这一假设。收尾走 `MainDispatcherGuard.tearDown()`（`ISSUE-P3-189` 路线①：不调 `resetMain`）。

**驱动方式**：第一轮经假 Provider（进程内内存实现）建立远端基线与本地缓存；第二轮**撤掉** `testSyncProvider` / `testRemotePath` 使**真实凭据链真正执行**（这是「凭据读取」探针成立的前提），同时置 `isOfflineMode` ⇒ 装配段之后的引擎判定走 `SyncEngine.openRemote:91-95` 的离线早退分支，**全程不触网**。第二轮另制造两处内容变更（新增条目 + 注入墓碑），驱动内容比较与 `writeCache` 分支。

**AC③ 原话「沿用 `OffMainComputation.kt` 口径」的落地说明**：该助手是「推进虚拟时间 + 真实睡眠」的**等待**助手，用途是让真实线程上的工作在中间态断言前完成。本用例**只做周期结束后的线程身份断言**，`runTest` 会在挂起点自然等待真实线程上的 `withContext` 返回，无需其轮询——故按其实质（真实线程工作不随虚拟时间推进）以更直接的手法落地，未引入该助手。该判断已写入开工前前提复核第 6 条。

## 4. 过程留痕（真实发生的两处踩坑，均未美化）

### 4.1 `WebDavSyncProvider` 构造期的 SSRF 防护拒绝「用内网地址做不触网的假端点」

首版用例把 WebDAV 端点写成 `https://127.0.0.1:1/dav`（意图：即便意外触网也是瞬间连接被拒）。实测第二轮直接返回
`SyncOutcome.Error(同步端点主机 "127.0.0.1" 为内网/保留网段地址，已拒绝（SSRF 防护：禁止直连内网段与云元数据端点）)`
——`resolveProvider()` 在**构造 Provider 时**即抛 `InvalidEndpointError`，装配段在 `:99` 早退，凭据探针虽已记录但缓存三类探针全不触发。

处置：改用公网域名 `https://dav.example.com/dav`（构造期只做校验；离线模式保证构造后不触碰网络）。**教训**：本仓的「假端点」不能落在内网 / 保留网段，该约束由 Provider 自身的 SSRF 防护强制。

### 4.2 `MutableStateFlow` 按 `equals` 合并 ⇒ 「行为等价但类型不同」的替身赋值被静默吞掉

「内容比较」探针首版注入的是**空**替身列表（`RecordingDeletedObjects(emptyList())`，内容与原 `emptyList()` 完全等价，只换了容器类型）。实测注入后断言恒红，诊断输出 `deletedObjects=EmptyList`。

根因：`DatabaseSession.databaseFlow` 背后的 `MutableStateFlow` **按 `equals` 合并取值**，而 `KdbxDatabase` 是 data class ⇒ `oldDb.equals(newDb)` 逐字段比较时 `EmptyList.equals(空替身)` 为 `true`，整个赋值被判为「值未变化」而**丢弃**，替身从未进库。（`setDatabaseForTesting` 本身工作正常，是 StateFlow 的合并语义吞掉了写入。）

处置：注入**一条真实墓碑**（`DeletedObject(id = KdbxUuid.random())`）——内容确实不同 ⇒ 赋值落地；比较器首条判据随之必然命中（正是探针要测的那一行）。并把「注入是否生效」写成用例内的显式断言（`databaseFlow.value.deletedObjects === injected`），使该坑有现形器。**教训**：用替身替换 StateFlow 持有时，替身必须与旧值**按 `equals` 不等**，否则赋值静默消失——这属本仓可复用的诊断经验。
