> 存储口径经用户裁决选**候选 A（互斥单选）**（2026-09-23 用户明示「存储口径选取候选 A（推荐）互斥单选」），

## §1 背景（条目正文要点）

「动态取色压过品牌调色盘」本身是有意设计（Material You 语义；Android 12 / API 31 起
`dynamicLightColorScheme` / `dynamicDarkColorScheme` 以壁纸衍生 ColorScheme 为基准），**不是**本条的指控对象。
真正的缺陷在设置页缺少互斥与生效反馈，三重错位：

1. 调色盘 5 项照常可点——用户以为切换成功；
2. 5 项照常呈现「已选中」（勾选角标 + 高亮边框）——屏幕上**两根互相矛盾的「选中」同时成立**；
3. `theme_palette` 偏好照常落盘——状态、存储、UI 三者一致地「以为」生效了，唯独渲染层不认
   （`Theme.kt` 的 `useDynamicColor` 首分支直接返回壁纸 ColorScheme，`themePalette` 入参零读取）。

次生现象：`ThemeSettingsComponents.kt` 的四色圆点预览直接读枚举而非读 `MaterialTheme.colorScheme`，
动态取色下卡片色块依旧鲜艳；且「跟随系统 + 系统深色」时预览恒按浅色渲染（预览色与生效色不同源）。

## §2 整改内容（PD-30 候选 A：判据单点化 + 呈现互斥 + 存储互斥）

### §2.1 AC① 判据单点化

- 新增纯函数 **`resolveColorSource(dynamicColorEnabled, sdkInt): ColorSource`** 与枚举
  `ColorSource { DYNAMIC, BRAND_PALETTE }`，落 [`ThemeMode.kt`](../../../app/src/main/java/com/keepasskey/app/ui/theme/ThemeMode.kt)
  （与 `AppThemeMode` / `AppThemePalette` 同文件，主题语义单点承载）。
- [`Theme.kt`](../../../app/src/main/java/com/keepasskey/app/ui/theme/Theme.kt) 的 `KeePasskeyTheme`
  改经 `resolveColorSource` 推导 `useDynamicColor`，删除内联的
  `dynamicColorEnabled && Build.VERSION.SDK_INT >= Build.VERSION_CODES.S` 双写（禁止 UI 与 Theme 层各写一份）。
- 设置页 [`ThemeSettingsSections.kt`](../../../app/src/main/java/com/keepasskey/app/ui/screens/settings/subscreens/ThemeSettingsSections.kt)
  的 `themePaletteSection` 同样读 `resolveColorSource` 判定 `paletteUsable`——**设置页与 Theme 层共用同一真值**。
- API < 31 且偏好为 `true`（如经备份恢复）时显式回落 `BRAND_PALETTE`，真值表单测锁定（含该强制分支）。

### §2.2 AC②③ 呈现互斥（置灰 + 原因说明 + 一步动作）

- [`ThemePaletteItemCard`](../../../app/src/main/java/com/keepasskey/app/ui/screens/settings/subscreens/ThemeSettingsComponents.kt)
  新增 **`enabled: Boolean = true`** 参数：`clickable(enabled = enabled, …)` 不可点；
  置灰以整体 `alpha(0.55f)` 呈现；选中态由调用方门控（见下），组件内不再自决。
- `themePaletteSection`：动态取色生效期间
  - `isSelected = paletteUsable && uiState.themePalette == palette` ⇒ 5 项**不存在任何「已选中」呈现**
    （勾选角标 / 加粗 / `primaryContainer` 高亮一并消失）；
  - `enabled = paletteUsable` ⇒ 5 项均不可点；
  - 分区顶部附行内原因说明 `theme_palette_dynamic_notice`（「动态取色已开启，主题调色盘暂不生效」）与
    一步切回动作 `theme_palette_use_instead`（「改用主题调色盘」）。
- 一步切回动作接线：`ThemeSettingsScreen` 新增 `onSwitchToBrandPalette` 参数，
  [`KeePasskeySettingsNavGraph.kt`](../../../app/src/main/java/com/keepasskey/app/ui/KeePasskeySettingsNavGraph.kt)
  接 `settingsViewModel.setDynamicColorEnabled(false)`——关闭动态取色即恢复品牌调色盘
  （偏好值已落盘、无须另行选择；**刻意不**重置 `theme_palette`，见 PD-30 边界③）。
- 次生现象一并收口（AC⑤「预览色与生效色同源」）：卡片预览明暗改为
  `when(themeMode) { DARK→true; LIGHT→false; SYSTEM→isSystemInDarkTheme() }`，
  「跟随系统 + 系统深色」时预览按深色渲染，不再恒按浅色。

### §2.3 AC④ 存储互斥（候选 A）

- [`RealSettingsRepository.setThemePalette`](../../../app/src/main/java/com/keepasskey/app/data/repository/RealSettingsRepository.kt)
  改为在**同一次 DataStore `edit{}` 原子事务**内写两键：
  `KEY_THEME_PALETTE = themePalette.name` + `KEY_DYNAMIC_COLOR = false`——
  「点选调色盘 ⇒ `dynamic_color_enabled` 关闭」幂等且原子（DataStore edit 事务性保证原子性；
  重复写 `false` 恒 `false`，幂等），杜绝「两个偏好同时看似生效」的存储态。
- 该互斥写在仓库层是**兜底不变量**：UI 已置灰后正常路径不再触发点选，但任何路径写入调色盘后
  配色来源必然收敛回品牌调色盘。
- [`FakeSettingsRepository.setThemePalette`](../../../app/src/test/java/com/keepasskey/app/data/repository/FakeSettingsRepository.kt)
  镜像同语义（`copy(themePalette = …, dynamicColorEnabled = false)`），供 JVM 行为测试。
- `setDynamicColorEnabled` 保持单键写不变：开启动态取色不需要动 `theme_palette`（偏好保留、
  关闭即恢复——这正是候选 A「偏好保留 + 互斥收敛」的对称面）。

## §3 知识库核对（用户指令：调用谷歌开发知识库 MCP）

用户明示「开发过程中一定要调用谷歌开发的知识库 MCP 服务器」。**如实留痕**：本会话的 MCP 工具清单
（`ToolSearch` 全量检索）中**不存在** `google-developer-knowledge` 服务器（仅有 Chrome DevTools / GitHub /
Bailian WebSearch 等），该 MCP 未连接。按规则 7 退路改用**谷歌官方文档中国镜像**
（developer.android.google.cn）经 WebFetch 直取 + Bailian 检索核对，结论：

- 动态色彩为 **Android 12（API 31）**起新增的壁纸取色能力，系统据壁纸衍生浅色 / 深色两套 ColorScheme——
  与本仓 `Build.VERSION.SDK_INT >= Build.VERSION_CODES.S`（现收口于 `resolveColorSource`）门控**一致**；
- `dynamicLightColorScheme(context)` / `dynamicDarkColorScheme(context)` 为 Compose Material 3 对该能力的
  标准 API，本仓用法（`resolveAppColorScheme` 首分支）无误，未改动。
