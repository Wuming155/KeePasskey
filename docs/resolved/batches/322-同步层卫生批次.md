## 2. 三项整改

### 2.1 项 1（核心）：解析失败会话的附件残留不回滚 → 失败路径补回滚

新增 `BinaryStore.delete(key)`（core 接口，默认空实现仅为既有测试 fake 兼容；生产
`FileBinaryStore` 经 `SyncCache.clear(key)` 按键真实删除），并新增
`SpillRecordingBinaryStore`（记录器，`database/session/SessionExternalParser.kt` 内，
`store` / `storeFromStream` 记录本次解析新落盘的键）：`parseExternalKdbxBytes` 解析失败
（含取消）路径调 `purge()` 逐一删除本次新落盘条目——失败解析的附件明文不再滞留 `cacheDir`。
成功路径记录自然作废（键归解析产物所有，由 ISSUE-P3-258 池所有权机制管理）；键为随机
UUID，并发解析互不干扰，删除自身键不影响既有会话附件。
测试 3 例（`SpillRecordingBinaryStoreTest`）：登记 + purge 逐一删除、purge 幂等 + 读路径透传、
成功路径不越权清理。**如实声明**：AC 的另一分支「登记量级与窗口」不再需要——回滚已使
失败解析的残留归零。

### 2.2 项 2（部分成立）：崩溃窗内 `.version` / `.cache` 失配 → baseversion 取所写字节真值自愈

`recoverFromMetaFailure`（远端 404 自愈分支）的 `advanceBaseAndPersist` 此前以磁盘
`.version` 内容（`state.localVersion`）充当 baseversion——崩溃窗内两者可能失配，取后者会把
陈旧版本固化进基线。现改传 `null`（`advanceBaseAndPersist` 内按**本次所写字节**现算 SHA-256）：
baseversion 恒为真值。其余调用点（结算句柄 / commitLocal 系）本就传本次摘要，无需改动。
**自愈口径**：崩溃窗失配时 `.version` 由 `hasLocalChanges` 判为「有本地修改」⇒ 下轮按冲突/
重传收敛，基线不再被陈旧值固化。测试：404 自愈用例补 baseversion == SHA-256(所写内容) 断言。

### 2.3 项 3（部分成立）：同步失败文案透传服务器可控串 → 出显面收口

生成侧透传站点全部改固定通用文案 / 仅异常类型名（type 保留）：
- `SyncCycleRunner` 三处周期边界 catch（`sync_error_unknown` / `sync_error_vault_takeover_failed`）；
- `SyncCycleSetup` 端点非法 catch（`sync_error_invalid_endpoint`，此前 `e.message` 可能内嵌服务器可控端点内容）；
- `SyncConflictResolution` / `SyncConflictAutoMerge` 四处上传失败文案（`sync_error_upload_resolved_failed` /
  `sync_error_upload_merged_failed` 的参数改 `javaClass.simpleName`）；
- `SettingsSyncController` 测试连接失败（`sync_test_connection_failed`，此前透传异常 message）。

保留不动（如实声明）：`saveResult.message` 类参数（本地磁盘 IO 异常，非服务器可控）；
消费侧 `ConflictResolutionViewModel:245` / `SettingsSyncController:313` 展示的 `outcome.message`
在本批生成侧收口后仅余本仓固定文案与本地 IO 异常文本，无服务器可控串来源——不再改消费侧，
避免把本仓既有可读的错误细节一并抹掉。
