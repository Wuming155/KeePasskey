## 1. 整改对象

  契约靠 KDoc「调用方用毕必须显式清零」维系；两个生产调用点只擦**内层再克隆**，外层借出副本全程滞留堆内存至 GC。
- `ISSUE-P3-312`：① CSV 公式注入零中和（导出仅 RFC 4180 引号化、导入零告警）；
  ② `产品裁决登记.md` PD-21 括注「本周期无本地内容变更」缺代码支撑（该分支在判定之前即返回），
  且曾被上一轮审计当免检理由引用。
- `ISSUE-P2-309`：`SyncCycleSetup.buildCycleContext` 以 `readBaseContent(...) ?: cachedSnapshotBytes`
  用**工作副本**给三方合并的 base 兜底，与紧邻注释的明令禁止直接矛盾，并与
  `SyncConflictController` / `SyncConflictResolution` 两处无兜底口径不一致。

## 2. 整改内容

### 2.1 `ISSUE-P2-312`：清零责任上收到借出方

- `SessionCredentialCache.useCredentials` 改为 `try { block(...) } finally { 借出克隆 Arrays.fill }`
  （AC①）——主密码填 `'0'`、密钥文件填 `0.toByte()`，正常返回与抛异常两条路径同覆。
  契约与 `ChildDatabaseCredentialStore.useCredentials`（本仓已有的**更强**保证）对齐，不再依赖调用方自觉。
- KDoc 同步更正两处：`SessionCredentialCache` 与 `DatabaseSession.useCredentials` 原「调用方必须显式清零」
  已不成立，改为「本方法返回前由借出方清零；调用方**不得**依赖借出副本在返回后仍可读」。
- **未改动**：两个生产调用点（`SyncDatabaseCodec.serializeLocalDatabase`、`parseExternalKdbxBytes`）的
  内层再克隆与其 `finally` 保留——它们把内层副本交给 `KdbxFile.save/load` 作入参，而
  `KdbxFile` 的 `finally` 只擦**派生**的 `cipherKey/hmacKey64`（不擦入参），故内层副本仍需调用点自擦。
  本次只补齐「借出方」这一层，不重排既有所有权。
- 新增用例 2 例（`DatabaseSessionCredentialsTest`）：正常路径断言借出的 `pwd`/`keyFile` 克隆在
  `useCredentials` **返回后**逐元素为 `'0'` / `0x00`（并先断言块内确实读到凭据，防「空数组假绿」）；
  异常路径同样清零。附带断言会话内部缓存不受借出副本清零影响（第二次借出仍读到原口令）。

### 2.2 `ISSUE-P3-312` 项 1：CSV 公式注入——导入侧告警 + 导出侧提示

- **导入侧（AC①）**：`ImportWarningReason` 新增稳定编码 `FORMULA_INJECTION_RISK`；
  `BrowserCsvImporter` 在条目产出前探测「将随明文 CSV 再导出」的六个字段
  （title / username / url / notes / 分组路径各段 / password）是否以 `=` `+` `-` `@` TAB CR 开头，
  命中记**行级**警告且**每行最多一条**（多字段命中不刷屏）。
  口令走 `CharArray` 首字符判定，不经 `String`。
- **只告警不改写**（AC① 括注的口径）：撇号前缀式中和会把口令 / 用户名本身改坏，代价高于收益，处置权交给用户。
- **UI 接线**：`ImportReportDialog.warningReasonRes` 穷尽 `when` 补该编码分支；
  `values/` 与 `values-en/` 同步新增 `import_warn_formula_injection` 一案。
- **导出侧提示（AC①）**：`dbset_export_csv_plain_warn_message`（中英两份）追加第四条要点，
  明示「以 `=` `+` `-` `@` 或制表符开头的字段，用表格软件打开该文件时单元格可能被当作公式执行」。
- 新增用例 4 例（`BrowserCsvImporterTest`）：等号开头标题 → 行级 `row:2` 警告**且源值逐字符不变**；
  口令以 `@` 开头 → 告警且 `CharArray` 内容原样；同一行多字段命中 → 恰好一条警告；
  普通字段 → 不记该警告（负向对照）。

### 2.3 `ISSUE-P3-312` 项 2：PD-21 括注更正（文档诚信）

- 已直读 `SyncEngine.kt` 反校前提：`openRemote` 在 `:110` 的 `metaResult.isFailure` 即
  `return recoverFromMetaFailure(...)`，**早于** `:128` 的 `hasLocalChanges` 判定 ⇒
  原括注「本周期无本地内容变更」作为行为背书**不成立**（该分支上传的是**上一周期**的工作副本，与本轮有无变更无关）。
- 按 AC 采「改述」方案：PD-21 括注更正为「该分支在 `hasLocalChanges` 判定之前即返回」，
  并就地留「更正留痕」一段（结论「只写一份」不变，只撤掉错误背书）。
- **本批不动生产代码**：该分支缺省 `remoteExists` 的 TOCTOU 属 `ISSUE-P3-300` AC⑤ 的真实服务器实验面，维持开放。

### 2.4 `ISSUE-P2-309`：合并基准不再取工作副本兜底

- `SyncCycleSetup.kt` 删去 `?: cachedSnapshotBytes`（AC①）：`.basecache` 缺失即以 `null` 交
  `resolveTrustedBase`，退化为**空库并集 + 同字段分叉进冲突清单交用户决策**（宁多冲突不丢数据）。
  `readBaseContent` 无兜底由此与 `SyncConflictController.kt:333` / `SyncConflictResolution.kt:209`
  三处一致（AC②，该两处本批零改动）。
- **为何既有污染判据救不了这条**：`resolveTrustedBase` 只以**字节级** `contentEquals(localBytes)` 判「base 被本地顶替」，
  而 KDBX4 每次保存重生成 masterSeed / IV / KDF salt ⇒ 同一内容的两次序列化字节必然不同，该判据**永不命中**；
  兜底进来的工作副本其**内容**恰等于本地内容 ⇒ 本地编辑被判「local == base，本地未改」⇒ 同字段分叉远端全胜。
- 新增端到端用例 1 例（`SyncBaseSnapshotFallbackTest`，`runSyncCycle` 全链路 + 进程内 Provider）：
  建基线 → 本地改同一字段并保持 DIRTY → 工作副本被本地内容覆盖 → 对端独立推进同字段 → **删除 `.basecache`**
  → 再跑一轮。断言三条：结论必须是 `ConflictNeedsUser`（不得是 `MergedAndUploaded`）、
  会话树仍含「本地修改」、远端字节未被本轮静默改写。
- **判别力实验（红-绿留证）**：修复前实跑该用例 ⇒ `java.lang.AssertionError: base 缺失必须退化为…: MergedAndUploaded`
  （缺陷现形，本地编辑被远端版本顶替）；按上文删兜底后复跑 ⇒ 通过。
