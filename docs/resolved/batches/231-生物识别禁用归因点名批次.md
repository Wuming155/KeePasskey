## 1. 背景与原貌（原样收录自待办条目）

### ISSUE-P2-227：生物识别被完整性闸门禁用时提示未点名命中信号（归因笼统）

- **核实时间点**：2026-09-20 经用户真机反馈 + 代码走查核实。
- **核实方式**：文案 `sec_biometric_integrity_blocked`（`strings.xml:615`「设备存在安全风险，已禁用生物识别快速解锁，请改用主密码解锁」）**由本应用产生**，非 `BiometricPrompt` / Keystore 返回；触发点 `BiometricAuthManager.kt:116` 读 `currentEnforcement().disableBiometricQuickUnlock`，`RuntimeIntegrityPolicy.kt:183-216` 中 ELEVATED / COMPROMISED / UNDETERMINED 三档皆置 true。
- **背景与根因**：用户看到「设备存在安全风险」无法分辨究竟是「**本机跑的是可调试构建**」（`appDebuggable`，`RuntimeIntegrityDetector.kt:173` 读 `FLAG_DEBUGGABLE`）、「**安装来源不在受信任清单**」（`:286-293`）、还是「**真被 root / 注入框架攻破**」（`:174-176`）「**快照陈旧/扫描未完成**」（`RuntimeIntegrityPolicy.kt:270-274`）。**开发者自测环境（debug 包）必然命中 ELEVATED**，故该提示在正常开发路径上恒定出现，用户据此怀疑整机安全。**另有一处注释前提为假**：`RuntimeIntegrityDetector.kt:276` 称「adb 直装 installer 为 `null` 故不升级」，实测 adb / `pm install` 记录的 `installingPackageName` 为 **`com.android.shell`（非 null）**，不在 `TRUSTED_INSTALLERS`（`:463-468`）⇒ 侧载的 release 包同样被判 ELEVATED。
- **裁决范围（用户 2026-09-20 明示）**：**仅整改归因呈现 + 更正错误注释**；`com.android.shell` **不**加入受信任清单、debug 构建**不**放宽降级——判据与 fail-closed 分级保持不动（避免降低安全性）。
- **验收标准**：AC① 生物识别被拦时的文案点名**具体命中信号**（可调试构建 / 安装来源包名 / root 痕迹 / Magisk 痕迹 / 注入框架 / 调试器附加 / 正被 trace / 尚未完成扫描），多信号并中时按危害度排序呈现，全部资源化中英双语；AC② 设置页风险卡同源（不得第二数据源）；AC③ 错误注释就地更正；AC④ 新增纯函数级用例穷举「信号集合 → 文案资源 id」映射。

## 2. 整改方案与架构落地

判据（风险分级、`disableBiometricQuickUnlock` / `disableAutofill` 的后果）**一字未改**；
本批只把「闸门为何拦下」这一信息从判定处带到呈现处。

### 2.1 归因清单与判定同源产出

- 新增 `security/IntegrityBlockReason.kt`（80 行）：8 个命中信号枚举，每项携带 `@StringRes`，
  **声明顺序即危害度降序**（动态攻击特征 → 静态可疑 → 未判定），并附纯函数
  `from(signals, undetermined)`（沿 `passkey/CredentialRejectionReason` 的既有范式）；
- `IntegrityEnforcement` 增字段 `biometricBlockReasons`（默认 `emptyList()`），由
  `RuntimeIntegrityPolicy.evaluate` 在 COMPROMISED / ELEVATED 两档内联产出、
  `IntegrityEnforcement.UNDETERMINED` 常量携 `SCAN_UNDETERMINED`——
  **不存在第二数据源**（AC②），`escalateForLiveSignals` 走 `evaluate` 重算，故冷启动后才出现的
  调试器 / `ptrace` 同样进入清单；
- `BiometricResult.Error` 增字段 `blockReasons`（默认空，既有构造点零改动）。与 `errString` 的分工写明：
  `errString` 是系统透传诊断串、禁止外显（ISSUE-P3-14 契约不变）；`blockReasons` 是工程自产的**枚举**，
  经资源映射后可安全展示；
- `BiometricAuthManager.authenticate` 把 `enforcement.biometricBlockReasons` 随失败结果下行。

### 2.2 呈现：解锁处点名首项、设置页逐条列出

AC①「多信号并中时按危害度排序呈现」落为**两个界面分工**（避免把三条长句塞进一条 Snackbar）：

- **解锁 / 设置页开关当场验证**：`BiometricFailureMessagePolicy.of(error)` 在 `ERROR_INTEGRITY_BLOCKED`
  分支取清单**首项**（即危害度最高者）的专属文案；清单为空时回落既有通用文案
  `sec_biometric_integrity_blocked`（**绝不凭空造原因**）。该映射仍是纯函数、`errString` 依旧不参与决策；
- **设置页「安全防护」风险卡**：`IntegrityRiskCard(level, reasons)` 在清单非空时改为
  「当前命中项：」+ 逐条点名，**取代**原来那句「可调试构建**或**非受信任安装来源」的笼统枚举
  （清单为空仍回落档级文案）。数据取自同一份 `integrityReport`，未新增订阅源。

### 2.3 文案（+9 zh / +9 en）

8 条专属信号文案（`sec_biometric_block_debugger` / `_traced` / `_hook` / `_root` / `_magisk` /
`_debuggable` / `_installer` / `_undetermined`）+ 1 条风险卡前缀（`sec_integrity_risk_reasons_prefix`）。
每条自带处置指引（「请改用主密码解锁」；debug 版一条额外给出「正式使用请安装 release 版」）。
**一律无插值**：installer 包名在声明层面可被任意应用自称，写进文案反而误导，故不插值
（`CredentialRejectionReason` 同规）。

### 2.4 AC③ 错误注释就地更正

`RuntimeIntegrityDetector.detectUntrustedInstallSource` 的 KDoc 原以「adb 直装」为 `installer == null`
的例子——前提为错。现更正为：adb / `pm install` 走 shell 身份，`installingPackageName` 为
`com.android.shell`（**非 null**）⇒ 不在受信任清单，**adb 安装的 release 包同样被判 ELEVATED**；
并注明判据按用户裁决不放宽，但后果自此对用户点名可见（映射到 `sec_biometric_block_installer`）。

## 4. 残余与未执行声明

- **真机核对未执行**：本环境无可用设备 / AVD，故「debug 包解锁时是否确实显示『当前安装的是可调试构建…』」
  这一效果**未实测**（限界 §4.1 手工冒烟边界）。用户在本机 debug 包上重试生物识别解锁即可直接看到新文案；
- **判据未动带来的必然结果**：debug 构建与 adb 安装的包仍会被禁用生物快速解锁——本批只让**原因可见**，
  放宽与否属产品裁决（用户 2026-09-20 明示不放宽）。若日后要改，落点在
  `RuntimeIntegrityPolicy.evaluate` 的 `elevated` 判定与 `TRUSTED_INSTALLERS` 清单；
- **自动填充侧的同类笼统文案未纳入本批**：`autofill_save_integrity_blocked`（`strings.xml:616`）
  「设备存在安全风险，已禁用凭据保存」同样未点名信号。它经 `callback.onFailure()` 交给**系统保存对话框**
  渲染（非本应用界面，措辞与长度均不受本应用控制），故归因价值与呈现载体都不匹配——
  如需点名须连带设计呈现位置，**未排期**；
