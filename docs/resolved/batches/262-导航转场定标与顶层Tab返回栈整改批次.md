## 1. 背景与原貌（原样收录自 `ACTIVE_ISSUES.md`）

### `ISSUE-P2-260`：底栏顶层 Tab 切换实际为「压栈」——`popUpTo` 目标不在返回栈上被忽略，`saveState` / `restoreState` 从未生效

- **核实时间点**：2026-09-22（切换动效对照评审）。
- **核实方式**：
  - `app/src/main/java/com/keepasskey/app/ui/KeePasskeyApp.kt:229-239` 经源码核实：`navigateToTopLevel` 用 `popUpTo(graph.findStartDestination().id) { saveState = true }`，而同一 `NavHost` 的 `startDestination` 是 `Screen.Unlock.route`（同文件 `:349`）；
  - `app/src/main/java/com/keepasskey/app/ui/KeePasskeyNavGraph.kt:54-59`、`:97-103`、`:210-216` 经源码核实：解锁成功与手动锁库均执行 `popUpTo(Screen.Unlock.route) { inclusive = true }` / `popUpTo(0) { inclusive = true }`，解锁态下返回栈根为 `VaultList`，**`Unlock` 已不在栈上**；
  - `navigation-runtime-android:2.10.0`（`gradle/libs.versions.toml:44` 声明的实际依赖版本）的 `NavControllerImpl.class` 常量池经反查核实：含 `Ignoring popBackStack to destination … as it was not found on the current back stack`（3 处，分别对应 destination / route / popUpTo 三条路径），命中即 `return`，**不执行任何 pop**。
  - **本条结论为静态推断，尚未真机复现**——复现方式见 AC①。
- **背景与影响**：`popUpTo` 恒被忽略 ⇒ 每次点底栏都是 `navigate` **新压一个 entry**：① `saveState` / `restoreState` 成对失效，Tab 的滚动位置、搜索词、子目录不被保存；② 返回栈无界增长（Vault → 认证器 → Vault 会得到两个 `VaultList` entry），返回键在 Tab 历史里回退，而非被顶层熔断；③ 新 entry 即新 `ViewModelStore`，每次切 Tab 重建该 Tab 的 ViewModel 并重读数据库——转场（220ms）跑完时内容可能尚未回填，这是「动画很快但什么都没交代」观感的来源之一；④ 同级 Tab 切换走的是前进（`navigate`）语义，故 `VaultList` / `Authenticator` / `Generator` 只能用 `topLevelEnterTransition` 掩盖方向感，而返回时命中 `popEnterTransition = defaultPopEnterTransition`（从左滑入）——**同级切换被渲染成下钻返回**。
- **验收标准**：
  - AC① 先复现留痕：`android-cli` 拉起应用后连点底栏三次再按返回键，抓 `logcat` 是否出现 `Ignoring popBackStack to destination`，并记录返回键落点与返回栈快照；
  - AC② 修正 `navigateToTopLevel` 的 `popUpTo` 目标，使 Tab 切换真正为同级替换（候选：把 `Unlock` 一并纳入返回栈根，或改用能命中栈上目标的等价写法），并确认 `saveState` / `restoreState` 生效（切回 Tab 后滚动位置与搜索词保留、ViewModel 不重建）；
  - AC③ 补一条不变式用例锁定「连续切 Tab 不增长返回栈」（宿主纯逻辑或真机 instrumented 均可）；
  - AC④ 修复后收口 `ISSUE-P3-261` 偏差表第 6 / 第 8 项的转场语义（同级切换不再走 pop 语义后，`popEnterTransition` 的例外配置应一并复核）。
- **依据**：`app/src/main/java/com/keepasskey/app/ui/KeePasskeyApp.kt:229-239`；`app/src/main/java/com/keepasskey/app/ui/KeePasskeyNavGraph.kt:54-59/97-103/210-216`；`navigation-runtime-android:2.10.0` `androidx/navigation/internal/NavControllerImpl.class`。

### `ISSUE-P3-261`：全局转场动效偏离官方规范（「Fade Through」实为交叉淡化 / 缩放起点与插值器无出处 / 视差自造 / 预测性返回槽位未用 / 覆盖不全 / 内容层零动效）

- **核实时间点**：2026-09-22（切换动效对照评审）。
- **核实方式**：
  - 源码核实本应用现状：`app/src/main/java/com/keepasskey/app/ui/navigation/AppNavigationMotion.kt:24-82`（6 条转场全部 `tween` + `FastOutSlowInEasing`，常量 `:25-29`）、`.../ui/KeePasskeyApp.kt:347-363`（`NavHost` 四向接线）、`.../ui/KeePasskeyNavGraph.kt:44-137` 与 `:199-219`（顶层 Tab 覆盖范围）、`.../ui/theme/Theme.kt:111-117`（已启用 `MotionScheme.expressive()`）；
  - 全仓度量核实：`grep -rn "spring(" app/src/main` = **0 处**；`grep -rn "animateItem\|animateContentSize" app/src/main` = **0 处**；`grep -rn "tween(" app/src/main` = 14 处；
  - AndroidX 官方参考实现经源码核实：`material-components-android` `MaterialSharedAxis.java:86,89`（默认时长 `motionDurationLong1`、缓动 `motionEasingEmphasizedInterpolator`）、`MaterialFadeThrough.java:33,35,38`（`DEFAULT_START_SCALE = 0.92f`、同默认时长与缓动）、`FadeThroughProvider.java:38,55-77`（`FADE_THROUGH_THRESHOLD = 0.35F`，类注释「fades out and in views **sequentially**」）、`SlideDistanceProvider.java:117-123`（两侧等距 `mtrl_transition_shared_axis_slide_distance`）；
  - `androidx.compose.material3` token 源码核实：`tokens/MotionTokens.kt`（`DurationLong1 = 450.0`、`DurationMedium1/2 = 250/300`、`EasingLegacyCubicBezier = CubicBezierEasing(0.4f, 0.0f, 0.2f, 1.0f)`、`EasingEmphasizedCubicBezier = CubicBezierEasing(0.2f, 0.0f, 0.0f, 1.0f)`）、`tokens/ExpressiveMotionTokens.kt`（spatial 默认 damping 0.8 / stiffness 380）；
  - 官方文档经 Google 开发者知识库 MCP（`google-developer-knowledge`，2026-09-22 会话内直查 `search_documents` / `get_documents` / `answer_query`）核实：
    - **Compose 动效自定义页**：「spring can handle interruptions more smoothly than duration-based `AnimationSpec` types because it guarantees the continuity of velocity」；
    - **Compose 内建动效页**（`animation/composables-modifiers`）：「By default, the initial content fades out **and then** the target content fades in (this behavior is called fade through)」——fade through 的官方定义即**顺序**淡化；
    - **移动端 predictive back 设计指引**（`design/ui/mobile/guides/patterns/predictive-back`）给出**全屏表面**动效规格表：Exit Scale `100% → 90%`、Enter Scale `110% → 100%`、Exit/Enter Fade 以 **35% 进度阈值**为界（原文「At the 35% mark, neither screen is showing」）、插值器 `(.1, .1, 0, 1)`（"to match the interpolator used for the SystemUI animations"）；并声明共享元素过渡「does not work with FragmentManager, the Navigation Component, or Navigation Compose. In these cases, **avoid scaling the screen by 90%**」；
    - **shared axis 的时长与缓动**（经 `answer_query` 汇总，源 `MaterialSharedAxis` 参考页）：滑动总时长 **300ms**、滑动缓动 `cubic-bezier(0.4, 0, 0.2, 1)`；出向淡出 **90ms**（`cubic-bezier(0.4, 0, 1, 1)`）、入向淡入 **210ms 且延迟 90ms**（`cubic-bezier(0, 0, 0.2, 1)`）；
    - **同级 / 层级的选型口径**（源 Android Auto 设计系统 Motion 页）：同级 peer views（如 app bar 标签）用**横向**「side-to-side movement reflects the state of staying at the same level」；层级下钻用 **Z-depth**「scales up the lower layer and fades it in while the higher layer fades out」；
  - 依赖 API 面核实：`navigation-compose-android:2.10.0` 的 `NavHostKt.class` / `DefaultNavTransitions.class` 常量池经反查核实——`predictivePopEnterTransition` / `predictivePopExitTransition` 两槽位**在本项目实际版本中已存在**，且 `DefaultNavTransitions` 已提供 `popEnterTransition(enter)` / `popExitTransition(exit)` 派生助手。
  > **初版更正留痕**：本条初版曾断言「缓动用错（`FastOutSlowInEasing`）」「时长比官方短 1.5 倍（450ms）」。经上列文档核实，`cubic-bezier(0.4, 0, 0.2, 1)` 与 300ms **正是设计规范给 shared axis 的取值**，450ms 与 emphasized 曲线是 AndroidX **实现**的取舍——初版把实现值当成了规范值，**该两条论断已作废**，偏差表第 1 / 2 项已按核实结果重写。
- **背景与影响**：`§228` 以「Material 3 Motion System + Predictive Back 最佳实践」结案，但参数与官方规范 / 参考实现在多处不符（详见下表 16 项），且同一屏内并存两套动效语言（主题 Expressive 弹簧 vs 自研 tween）——用户主观观感即「傻快傻快」。
  - **同类项目横向对照（定标依据，2026-09-22 经 `docs/references/` 全量检索核实）**：五个参考项目中**只有 Monica** 有成文的动效设计（单 Activity + Navigation Compose，`SharedTransitionCompat` 共享元素 + 精确 Enter/Exit，见 `Monica-架构分析.md:184-186`）；🥇 KeePassDX 与 🥈 keepass2android 均为 Compose 之前的多 Activity 架构，`docs/references/` 全文对二者**零动效记载**（KeePassDX `:31/:329` 自陈「无 Compose、无单 Activity、无 Navigation 组件」）；桌面两项（KeePassXC / KeePass-2.61.1）无转场概念，官方分析已声明「不参考其 UI」。⇒ KeePasskey 的转场**已领先参考项目**，差距不在「有没有」，而在「参数对不对、顺不顺」——真正的对标物是 Material 3 官方规范、AndroidX 参考实现与 Monica 的共享元素。
  - **逐项偏差：**

| # | 本应用现状 | Material 3 / AndroidX 参考实现 | 后果 |
|:--:|---|---|---|
| 1 | 缓动恒为 `FastOutSlowInEasing`（6 条转场全部） | **设计规范本身给的就是这条曲线**：Material Design 给 shared axis 滑动的缓动是 `cubic-bezier(0.4, 0, 0.2, 1)`（＝ Compose `FastOutSlowInEasing`）；但 M3 token 把它命名为 `EasingLegacyCubicBezier`，AndroidX 实现已改用 `motionEasingEmphasizedInterpolator`（＝ `EasingEmphasizedCubicBezier`） | **此曲线本身不算错**（与 Material Design 文档一致，`ISSUE-P3-261` 初版曾误判为「用错」）；真正的问题在于它是 M3 标记的 legacy 曲线、参考实现已迁移——属「要不要跟 M3」的取舍，须裁决登记 |
| 2 | 时长 300（导航入）/ 250（导航出）/ 220 + 150（Tab） | 设计规范：shared axis 滑动总时长 **300ms**；其中**出向淡出 90ms**、**入向淡入 210ms 且延迟 90ms**（fade through 以 35% 为界）。AndroidX 实现用 `motionDurationLong1` = 450ms | **滑动 300ms 与规范一致**（初版「短 1.5 倍」的说法系误用实现值当规范值）；错的是**淡出段**：规范 90ms，本应用 250ms（导航）/ 150ms（Tab）——出向淡出慢约 2.8 倍，且与入向重叠 |
| 3 | 全部 `tween`（全仓 `spring(` 0 处） | 主题已启 `MotionScheme.expressive()`（spatial 默认 damping 0.8 / stiffness 380）；官方明确 spring 在被打断时保证速度连续 | 连点 Tab 或手势中断时 tween 从零重启（「顿一下再冲出去」）；底栏指示器在弹、页面在匀速滑，同屏两套语言 |
| 4 | `topLevel*` 进出**同时从 0 开始**（入 220ms / 出 150ms 并发） | 官方两处一致：Compose 文档「By default, the initial content fades out **and then** the target content fades in (this behavior is called fade through)」；移动端 predictive back 设计指引「Enter fade starts at the 35% progress threshold … At the 35% mark, **neither screen is showing**」 | 并发淡入淡出 ⇒ 两页同时半透明叠底，中段出现整体亮度凹陷（「闪一下」）；代码注释称 Fade Through，实为 cross-fade |
| 5 | 入向缩放起点 `0.96f` | 官方给出的两个值都不是 0.96：fade through 用 `DEFAULT_START_SCALE = 0.92f`（由小涨上来）；全屏表面 predictive back 用 **Enter Scale 110% → 100%**（由大收进来） | 0.96 是第三种、无出处的取值；且若按「全屏表面」口径，入向本该从 **110%** 收进来而不是从 96% 涨上来 |
| 6 | 视差只在返回方向存在：下钻出向用 `topLevelExitTransition`（只 `fadeOut`、**不动**），入向滑满屏；返回时出向滑满屏 + 缩放 0.9 + 淡出，入向从 −25% 恢复 | AndroidX `MaterialSharedAxis` 两侧**等距**滑动（`SlideDistanceProvider`，默认 `mtrl_transition_shared_axis_slide_distance`）；corpus 内 Google 文档未给出 shared axis 的偏移比例 | 同一层级关系进出两副面孔，前进方向根本没有共享轴，只是「内容盖在静止底板上」 |
| 7 | 视差比例 `PARALLAX_FACTOR = 4`（出向 25% 屏宽、入向 100% 屏宽） | 文档未给比例；参考实现为两侧等距（30dp 量级） | 4:1 无出处：出向几乎不动，两层读不出「共享同一根轴」 |
| 8 | `Screen.Settings` 是底栏 Tab（`AppBottomBar.kt:66-71`）却无 `topLevel*` 覆盖（`KeePasskeyNavGraph.kt:199`） | 同级切换应同族 | 切设置＝旧页 150ms 淡出 + 新页 300ms 滑入，与其余三个 Tab 不同族 |
| 9 | 预测性返回：出向 `slideOutOfContainer` + `scaleOut(0.9)` + `fadeOut(250)` 三效并发，入向仍从 −25% 滑入 | 官方**全屏表面**规范：Exit Scale **100% → 90%**、Enter Scale **110% → 100%**、Exit/Enter Fade 以 **35% 阈值**为界、插值器 **(.1, .1, 0, 1)**（"to match the interpolator used for the SystemUI animations"）；并明确「与 Navigation Compose 同用时，**避免把屏幕缩到 90%**」 | 只有 `0.9` 这一个数字对得上；滑动、并发、插值器（本应用 (0.4, 0, 0.2, 1)）、35% 阈值全部不符 |
| 10 | `NavHost` 只设 `enter/exit/popEnter/popExit` 四向，**未设** `predictivePopEnterTransition(swipeEdge)` / `predictivePopExitTransition(swipeEdge)` | 该两槽位在 `navigation-compose-android:2.10.0`（本项目实际版本）的 `NavHostKt` 中**已存在**（class 常量池核实）；`DefaultNavTransitions` 另提供 `popEnterTransition(enter)` / `popExitTransition(exit)` 派生助手 | 手势驱动那一段没有专属实现，只能复用 pop 的四向参数；官方推荐的「由 enter/exit 派生 pop」写法亦未采用 |
| 11 | 全仓 `Modifier.animateItem` / `animateContentSize` = 0 处 | 列表增删/重排应可动 | 搜索 / 过滤 / 删除后条目瞬移，转场再顺也接不住 |

- **验收标准**：
  - AC① **先定标再动手**：基准分两栏——**设计规范**（滑动 300ms、滑动缓动 `cubic-bezier(0.4,0,0.2,1)`、出向淡出 90ms、入向淡入 210ms 延迟 90ms、fade through 35% 阈值、全屏表面 Exit Scale 90% / Enter Scale 110% / 插值器 (.1,.1,0,1)）与 **AndroidX 实现**（`motionDurationLong1` 450ms、emphasized 缓动、`0.92f`）。逐项裁决「对齐规范」或「对齐实现」或「有意偏离」；凡裁决为有意偏离的项**必须**登记 `architecture/产品裁决登记.md`，不得静默保留；
  - AC② **最高优先**：`topLevel*` 改为真正的 sequential fade through——出向 `fadeOut(tween(90))`、入向 `fadeIn(tween(210, delayMillis = 90))`（35% 阈值口径），消除两页同时半透明的亮度凹陷；`Screen.Settings` 补齐 `topLevel*`（现与其余三 Tab 不同族）；
  - AC③ 缩放起点定标：`0.96f` 无出处，须在 fade through 的 `0.92f`（由小涨上来）与全屏表面的 **110% → 100%**（由大收进来）之间二选一，并登记理由；
  - AC④ 预测性返回段收口：按官方全屏表面规格核对 `scaleOut(0.9f)`（已对上）、补 35% 阈值与插值器 `(.1,.1,0,1)`，去掉与缩放并发的满屏滑动；同时评估启用 `predictivePopEnterTransition(swipeEdge)` / `predictivePopExitTransition(swipeEdge)` 两个专属槽位（`navigation-compose:2.10.0` 已具备），并复核官方「与 Navigation Compose 同用时应避免缩到 90%」的告诫；
  - AC⑤ 导航转场由 `tween` 迁到 `MaterialTheme.motionScheme`（`defaultSpatialSpec` / `fastSpatialSpec`）或等效 spring；4 处 `AnimatedContent` / `AnimatedVisibility` 改读 `effectsSpec` / `fastEffectsSpec`，消除同屏两套动效语言；
  - AC⑥ 视差与方向语义收口：前进与返回两方向采用同一套比例，`PARALLAX_FACTOR` 魔数落为具名 token 或改按官方等距方案；
  - AC⑦ **选型口径裁决**（偏差表第 14 / 15 项）：同级 Tab 与层级下钻分别用哪种转场，须按官方口径统一并登记产品裁决——现为「同级用淡、层级用横滑」，而 corpus 内 Google 文档口径相反；
  - AC⑧ 内容层补齐：`LazyColumn` 加 `Modifier.animateItem`；评估「列表项 → 详情页共享元素」可行性（须注意官方声明共享元素过渡与 Navigation Compose 不兼容，应改为「返回时跑共享元素」的方案）并给出结论（做或不做均须留痕）；

## 2. 整改落地

### 2.1 `ISSUE-P2-260`：顶层 Tab 切换改为**真正替换返回栈**

- **先定因后整改**：根因由「源码直读 `NavControllerImpl` + 真机 `logcat` 判据行」双证（见 §3.1 ⑥），
  再动代码；AC① 要求的「先复现留痕」由 §3.1 ⑥ 的**旧形态用例 + 逐字 logcat** 承接（本仓既有体例：
  §249 / §252 / §254 的反向反校均以「重建旧形态并取读数」承担，未留旧实现分支）。
- **根因（源码级定案）**：`NavController` 对**不在当前返回栈上**的 `popUpTo` 目标**静默忽略**——
  `androidx.navigation` 2.10.0 的 `NavControllerImpl.popBackStackInternal`（`commonMain/.../NavControllerImpl.kt`）
  在反向扫描返回栈找不到目标时打印
  `Ignoring popBackStack to destination … as it was not found on the current back stack` 并 `return false`，
  **不执行任何 pop**。原实现在 `navigateToTopLevel` 里取 `graph.findStartDestination().id`
  （＝ `NavHost.startDestination` 的 `Screen.Unlock`），而解锁成功（`popUpTo(Unlock) { inclusive = true }`）
  与手动锁库（`popUpTo(0) { inclusive = true }`）都把 `Unlock` 弹出栈外 ⇒ 解锁态下该目标不在栈上
  ⇒ `popUpTo` 恒被忽略 ⇒ 每次点底栏都是纯 `navigate` 压栈。
- **整改**：`popUpTo` 目标改取**当前顶层路由**（底栏 / 侧栏只在 `BottomNavItem.isTopLevelRoute`
  为真的路由呈现 ⇒ 当前路由必为栈上的顶层 entry），并保留 `inclusive = true` + `saveState = true` +
  `launchSingleTop = true` + `restoreState = true`。`currentRoute` 为空时**不做任何 pop**（fail-safe，
  宁可不省这一层栈也不猜目标）。
- **为什么 `inclusive = true` 恰好对上 `restoreState`**：`executePopOperations` 在 `saveState = true` 时，
  `inclusive` 分支把被弹 entry 的状态以**被弹目的地自身的 id** 为键写入 `backStackMap`
  （非 `inclusive` 才改写成「popUpTo 目标及其父图」的键）；而 `navigate` 侧的恢复判据正是
  `backStackMap.containsKey(node.id)`。故「以自身为 popUpTo 目标 + inclusive」是**唯一**能让
  「切走再切回」命中同一份保存状态的组合；`popEntryFromBackStack` 亦因 `saveState = true` 而
  **不清**该 entry 的 `ViewModelStore`（`if (!saveState && !transitioning) viewModelStoreProvider?.clear(entry.id)`）。
- **顺带收口的三处语义**（均在 AC② 的影响清单内，真机与用例逐条对上）：
  1. 返回栈不再无界增长：连续切 Tab 后非图目的地数恒为 1；
  2. 返回键在顶层被熔断：`NavController.onBackPressedCallback.isEnabled` 以
     `destinationCountOnBackStack > 1` 为条件（`NavController.android.kt:1115-1118`，计的是
     `backQueue.count { it.destination !is NavGraph }`），改前会累积到 > 1 从而让返回键在 Tab 历史里回退，
     改后保持为 1 ⇒ 交由外壳层 `BackHandler`（返回键锁定）或系统 Back-to-home；
  3. 同级切换不再走 pop 语义：`navigate` 内部先 pop（`ComposeNavigator.isPop = true`）再 push
     （`isPop = false`），收尾值是 false ⇒ 本次切换读的是 `enterTransition` / `exitTransition`
     （即 `topLevel*`），不会被渲染成「下钻返回」。
- **AC④ 的复核结论（`ISSUE-P3-261` 偏差表第 6 / 8 项收口）**：
  - 顶层路由的 `popEnterTransition = defaultPopEnterTransition` **保留**——修复后该 slot 的唯一命中路径是
    「下钻页（详情 / 编辑）返回本页」，此时共享轴视差还原才是正确语义；
  - 顶层路由原先的 `popExitTransition = topLevelExitTransition` **删除**——它在修复后**不可达**
    （顶层路由的退出只发生在 `navigateToTopLevel` 内部的同一次 `navigate` 里，`isPop` 收尾为 false），
    且若将来被命中，用「同级淡出」渲染一次层级弹出反而是错的 ⇒ 继承 `NavHost` 层的层级默认值。
- **新增守卫**：
  - 宿主静态守卫（`AppNavigationMotionTest`）：`navigateToTopLevel` 函数体必须 `popUpTo(stackRoute)` +
    `inclusive` / `saveState` / `restoreState`，且**不得**再出现 `findStartDestination`；
  - 设备侧不变式用例（`TopLevelTabBackStackDeviceTest`，2 例）：
    ① 「连续切两轮 Tab ⇒ 顶层 entry 数恒为 1 + 切回后 `NavBackStackEntry.id` 不变」；
    ② 「以栈外目标 popUpTo ⇒ 返回栈只增不减（旧缺陷形态）／以栈上当前路由 popUpTo ⇒ 回到 1」
    —— 第 ② 例把原缺陷的**成因**也钉成断言，防将来有人把 `popUpTo` 目标换回栈外。
