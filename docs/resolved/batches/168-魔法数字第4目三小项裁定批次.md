## 1. 改动（三处，全部只命名、不改任何取值）

| 对象 | 改动 |
|---|---|
| `core/.../model/PasskeyKeyText.kt` | 同一 `object` 内原有两组**同值异名**常量：`ASCII_NEWLINE`(0x0A) / `ASCII_SPACE`(0x20) 与 `CHAR_LF` / `CHAR_CR` / `CHAR_SPACE` / `CHAR_TAB`。合并为**唯一一组** `ASCII_LF` / `ASCII_CR` / `ASCII_SPACE` / `ASCII_TAB`，两处使用点（`indexOfLineBreak` 与 `stripWhitespace`）改引；被删的四枚名在 KDoc 里留了来路说明 |
| `app/.../passkey/SimpleJson.kt` 等 3 份 | 新增包内 `internal const val ASCII_SPACE = 0x20`，替换三处内联 `0x20`：`SimpleJson` 的「未转义控制字符」判定、`CallingOriginResolver.escapeJson` 的 `\uXXXX` 转义分支、`PasskeyAssertionActivity` 的 Base64 两侧空白修剪。**两种语义由比较符区分**（`<` 为控制字符、`<=` 为可修剪空白），已写进常量 KDoc，避免后人误「统一」成同一写法 |
| `crypto/.../passkey/PasskeyCryptoEngine.kt` | 新增 `const val CREDENTIAL_ID_MAX_BYTES: Int = 0xFFFF`，替换 `require(credentialId.size <= 0xFFFF)` 的内联上限（它是 WebAuthn §6.1 里 `credentialIdLength` 这个 2 字节大端字段的天然上界） |

## 3. 为什么第 3 类不在本批动

这些值集中在 `crypto` / `database` 的**格式与协议编解码面**（CBOR / COSE / PKCS#8 / `.kdbx` XML 与内部流）。
判定「是内联魔法数字还是格式固定字节」须逐处对照规范，而任何**改定义位置**的动作都要求重跑
`.kdbx` 语料对拍与 passkey 一致性套件（§38 互操作证据纪律）——那是一段独立的工作量，
和本批「纯命名收敛、无格式风险」不同性质，**混做会让本批的验证证据被稀释**。
