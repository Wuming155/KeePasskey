### 90.2 新增两例（及其负向鉴别力）

| 用例 | 覆盖 |
|---|---|
| `重放被拒后本地缓存与基线不被覆盖` | 接受 v1 → 接受 v2 → 端点重放 v1 ⇒ 断言裁决为 `RollbackRejected`，**且** `readCache == v2`、`readBaseContent == v2` |
| `上传路径遇远端重放拒绝合并并保留本地` | 本地修改后上传，远端被换成曾接受过的 v1 ⇒ ETag 预检冲突 → 下载到 v1 ⇒ 断言 `SyncCommitResult.RollbackRejected(keptLocal = true)`，**且** `readCache == 本次本地内容` |

**第一例的负向鉴别力**：无守卫时 `openRemote` 对「远端 ≠ base」一律下载应用（`RemoteSynced`），
会把重放的 v1 写进缓存与基线——此时任务本身**看起来是成功的**，用户下一次打开的是复活了已删条目 /
回退了已更新字段的旧库。故「断言缓存仍是 v2」正是本项防回滚的**唯一可观测判据**。

**第二例填补的空白**：`SyncCommitResult.RollbackRejected` 分支（`SyncEngine.kt:276-278`）
此前**完全没有用例**。它的语义是：上传因 ETag 预检失败进入冲突分支、下载到的远端内容**恰是设备侧
曾接受过的历史版本** ⇒ **不得**进入三方合并（`ConflictNeedsMerge`）。若判成合并，那份被命中的旧库
会作为「远端一侧」参与合并，把已删条目复活、把已更新字段回退——正是本项要防的形态。
