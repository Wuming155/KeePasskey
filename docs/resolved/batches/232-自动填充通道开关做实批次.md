> 闭环日期：2026-09-20
> 涉及模块：`app`（设置页 / 扩展偏好持久化 / 两条凭据通道服务）

## 1. 背景与原貌（原样收录自待办条目）

### ISSUE-P2-228：自动填充卡三开关为无持久化无消费方的假开关，且「无障碍」措辞与事实不符

- **核实时间点**：2026-09-20 经全仓 grep + Manifest 核对核实。
- **核实方式**：① `AndroidManifest.xml` 仅注册 `CredentialProviderService`（`:137`）与 `AutofillService`（`:157`），全仓 `AccessibilityService` 子类**只出现在 `RuntimeIntegrityDetector` 的第三方服务枚举里**（`:194-211`），本应用**没有**任何无障碍服务；② 字符串 `autofill_legacy_title`「旧版自动填充服务」/ `autofill_legacy_sub`「兼容低版本 Android 的无障碍填充方式」（`strings.xml:813-814`，EN `values-en/strings.xml:807-808`「Accessibility-based filling compatible with older Android versions」）；③ 该开关绑定 `uiState.autofillServiceEnabled`（`AutofillSettingsComponents.kt:97`），默认 `true`（`SettingsUiState.kt:132`、`SettingsPreferencesController.kt:51`），`setAutofillServiceEnabled`（`:228`）只更新内存 `StateFlow`——`ExtendedSettingsStore` **无对应持久化 key**、`KeePasskeyAutofillService` **零消费**，唯一去处是健康卡入参（`AutofillSettingsScreen.kt:75`）；④ 同卡 `credentialProviderEnabled` / `passkeySupportEnabled` 全仓 grep **唯一消费点即 UI 自身**（`:81` / `:89`）。
- **背景与根因**：用户按文案理解「这是需要无障碍权限的旧版通道」，与「安全防护」页「已启用无障碍服务」（`strings.xml:612`，判据为**非本应用**的第三方无障碍服务）撞成语义冲突；实际是**关掉啥也不影响、重启即回 true 的假开关**，且「旧版」在 minSdk 36（`AutofillService` 自 API 26 起）下无对应实体。项目已有先例反对假开关：`AutofillSettingsComponents.kt:101-108`（ISSUE-P0-02「避免设置页出现『看似可关』的假开关」）、ISSUE-P3-44 把假保存开关接线为真实消费方。
- **验收标准**：AC① 中英文案去除「无障碍」「旧版」虚假描述，如实表述其控制对象；AC② 三开关持久化到 `ExtendedSettingsStore`（重启不回弹）；AC③ 开关有**真实生产消费方**（关闭即对应通道不下发/不注册/不响应），消费点 fail-closed 默认值明确；AC④ 与系统真实状态（`AutofillHealthProbe` 的 `systemEnabled` / CM 可用性）联动呈现，并提供既有 `SystemSettingsNavigation` 跳转入口；AC⑤ 新增接线守卫用例，禁「UI 有开关、生产无消费方」复现。

> **开工前对用户的更正（2026-09-20）**：用户原始诉求为「该开关应默认关闭，打开时跳转系统无障碍设置、授予后才可开启」。
> 排查证实**本应用没有任何 AccessibilityService**，该开关与无障碍权限毫无关系 ⇒ 「跳无障碍设置后才有资格开启」这一修法**无对象可落地**。
> 经 AskUserQuestion 重新对齐，选定方案为「**文案改对 + 开关做成真的**」，默认值维持 `true`
> （与假开关时期的**实际可观察行为**一致：该通道一直是开着的；改成默认关闭等于顺带改变出厂行为，属另一项裁决）。

## 2. 整改方案与架构落地

### 2.1 消除第二数据源：三开关整体迁入扩展偏好

- `ExtendedSettings` 增 `credentialProviderEnabled` / `passkeySupportEnabled` / `autofillServiceEnabled`
  （默认 `true`）；`ExtendedSettingsStore` 补齐 `K_CREDENTIAL_PROVIDER_ENABLED` /
  `K_PASSKEY_SUPPORT_ENABLED` / `K_AUTOFILL_SERVICE_ENABLED` 的读侧、写侧与三个单键访问器；
- **ISSUE-P2-43 踩坑防线**：单键访问器不读数据类默认值，故新增 `CHANNEL_SWITCH_DEFAULT` 常量作为
  单键缺省，并由 `数据类默认值与单键读取缺省同值` 用例锁定两侧一致；
- **删除** `SettingsPreferencesController` 的 `autofillStateFlow` / `autofillState` / 三个 setter
  与 `SettingsUiStateProjection` 的 `AutofillUiState` 载体（连同 `combine` 里那一路输入流）——
  UI 侧三字段改由持久化快照 `extState` 投影（AC②「重启不回弹」的实现即此：**只有一份真相源**）；
  `SettingsViewModel` 的三个门面方法名不变、改委托到 `extendedPreferences`，故导航图零改动。
- 处置口径与既有先例一致：`SettingsPreferencesController` 内本就留着
  「ISSUE-P3-65：两个假开关 setter 已移除」的同型记录。

### 2.2 三条通道的真实消费点（AC③）

| 开关 | 消费点 | 关闭后的行为 |
|---|---|---|
| `autofillServiceEnabled` | `KeePasskeyAutofillService.onFillRequest`（与 §230 自我排除合并为同一前置守卫）+ `onSaveRequest` 前置守卫 | 不下发解锁引导 / 数据集 / `SaveInfo`；不接收框架保存（`onSuccess`＝「本次无需保存」，不报错） |
| `credentialProviderEnabled` | `KeePasskeyCredentialProviderService.buildBeginGetResponse` + `buildBeginCreateResponse` | 两条入口一律返回**空响应**（无候选、无解锁 Action、无保存入口） |
| `passkeySupportEnabled` | `CredentialResponseAssembler.buildPasskeyEntries`（候选出口）+ CM 创建侧 `BeginCreatePublicKeyCredentialRequest` 分支 | 不产出任何 `PublicKeyCredentialEntry`、不产出公钥注册条目；**密码候选与密码保存不受影响** |

- 前置守卫一律放在 `awaitEnforcement()` **之前**：用户显式关闭本通道时无需先跑一轮完整性重扫；
- CM 创建侧关闭通行密钥时走 `else -> null` 的既有收敛语义（系统侧等价于「本提供方不处理该请求」）。

### 2.3 文案与真实系统状态（AC①④）

- 键改名 `autofill_legacy_title|sub` → `autofill_service_title|sub`（中英各 2 条），
  新值如实表述为「浏览器与应用表单的账号密码填充通道」并写明关闭后果；
  `autofill_health_issue_app_disabled` 同步改指新名；
  `autofill_cm_sub` / `autofill_passkey_sub` 补写各通道关闭后的**确切**边界；
- 「安全防护」页那行「已启用无障碍服务」**保持不动**：它的判据是 `getEnabledAccessibilityServiceList()`
  里**非本应用**的服务（ISSUE-P2-44 / P3-215），与本批三条开关本就无关——冲突源自文案措辞，非逻辑冲突；
- AC④ 的「与系统真实状态联动」由既有 `AutofillHealthCard` 承担（`AutofillHealthProbe` 探
  `serviceDeclared` / `systemEnabled`（`AutofillManager.hasEnabledAutofillServices()`）/ CM 可用性，
  并带 `SystemSettingsNavigation.autofillServiceIntent` 一键直达系统设置，受
  `OneTapInteractionWiringTest` 守卫）；`appEnabled` 一路现读持久化值，健康卡与开关从此同源。

### 2.4 已登记限界（不谎称能力）

关闭 CM / 自动填充开关**不会**把本应用从系统的「自动填充服务 / 凭据提供方」列表中摘除，
只是不再交付任何凭据。动态禁用已绑定的扩展组件会把系统留在「选中但无响应」的异常态，故刻意不做；
文案已写明「系统设置仍会列出本应用，可在其中改选」。登记为
[`已知工程限界.md` §23](../../architecture/已知工程限界.md)。

1. **新增用例**：`AutofillChannelSwitchWiringTest`（新类，9 例）——
   三开关的消费点存在性（含「填充与保存两条路径各求值一次」「CM 两条入口各求值一次」的**计数**断言，

## 4. 残余与未执行声明

- **设备侧未执行**（本环境无可用设备 / AVD）：以下四条须真机冒烟——
  ① 关闭「系统自动填充服务」后第三方表单不再出现本应用候选、且本应用内也不出现保存气泡；
  ② 关闭「凭据管理器」后系统凭据弹窗对本应用返回空；
  ③ 关闭「通行密钥支持」后浏览器发起注册时本应用不出条目、而密码填充仍在；
  ④ **杀进程重启后三个开关保持用户所选**（持久化的直接验收）。
  新增/修改的均是**生产代码**而非 `androidTest` 用例，故不触发 AGENTS.md §5 ②「设备用例必跑」条款，
  但按 §4.1 手工冒烟边界如实登记为**未核对**；
- **默认值仍为开启**：本批只让开关**真实生效**，未改变任何通道的出厂默认（假开关时期通道实际上恒开）。
  若产品要把「通行密钥支持」等改为默认关闭，属独立的默认值裁决（沿 `ISSUE-P2-43` / `P2-71` 的
  「敏感通道默认关闭」口径另行处理），本批不夹带；
- **同卡另两个开关的命名**：`autofill_cm_*` / `autofill_passkey_*` 键名与其中文化表述已核对为准确
  （Credential Manager 与 Passkey 支持确实是上表所列的语义），故未改名以免无谓 churn。
