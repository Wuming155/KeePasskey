## 2. 整改明细

### 2.1 `ISSUE-P1-216`：回传值的**读回点移入临界区**（机制性根因）

**根因（机制性，非「偶发」）**：`PasskeyEntryCoordinator.applySignCountPatch` 整改前的写法是

```kotlin
val patched = databaseSession.updateEntryById(targetUuid) { entry -> …entryWithSignCount(entry, value) } ?: return null
val applied = PasskeyData.readSignCount(patched.customFields)   // ← 会话 Mutex 已释放
```

而计数器补丁走的是**增量定点擦除**（`SessionContentMutations.updateEntryById` →
`KdbxGroup.eraseSupersededSensitiveData`），且 `withSignCount` 每次落树都**新建**一个计数器
`ProtectedString`。于是：

1. 第 N 次提交上线的落树实例，**恰好**是第 N+1 次提交的擦除候选（其计数器实例不在替代实例的可达集内）；
2. 后者的擦除在会话 Mutex 内完成；前者那条 `readSignCount` 却落在 Mutex **之外**——
   并发后继提交抢先完成时，先提交方读回的就是**已清零**的实例 ⇒
   `ProtectedString.checkNotCleared()` 抛 `IllegalStateException("ProtectedString 已经清零，禁止继续访问")`
   （即 CI 日志的 `ProtectedString.kt:173`）。

**为何「本机绿 / CI 红」（本批首次给出机制性解释）**：该窗口宽度只有百纳秒级，命中与否取决于
**被抢占**。`runTest` + `Dispatchers.Default` 下未获锁的调用方处于**挂起态、不占 CPU**，解锁方
几乎总能先跑完那条读回；而 CI runner 上（低核数 + 32 路真并发）调用方是**真线程争抢 CPU**，
解锁方极易在窗口内被抢占。**实测对照**（临时探针，未入库）：

| 复现形态 | 轮数 × 并发 | 命中次数 |
|---|---|---:|
| `runTest` + `Dispatchers.Default`（既有用例形态） | 1200 × 32 | **0** |
| 真实线程 + `CyclicBarrier` 同时起跑 + GC 搅动 | 800 × 32 | **3402** |

异常类型与消息与 CI 日志**逐字同形**（`java.lang.IllegalStateException: ProtectedString 已经清零，禁止继续访问`）。

**修复**：读回点移入 `transform`（**临界区内**），临界区外只搬运一个 `Int`
（`app/.../data/repository/PasskeyEntryCoordinator.kt`）。语义**不损失**——读的正是本次落树的
同一实例，「回传值严格等于已提交状态」的原契约保持不变；KDoc 就地写明「读回不得挪出临界区」及机制。

**新增回归用例（3 例，`PasskeyEntryCoordinatorSignCountTest`）**：

| 用例 | 作用 |
|---|---|
| `后继提交会定点擦除先前落树实例的计数器_故临界区外读回必失效` | **确定性**复现机制面：两次提交后断言先前落树实例的计数器已被清零，并按整改前写法**复演**出与 CI 逐字同形的异常（不依赖调度运气） |
| `并发递增在真实线程屏障同步下仍取回各自唯一计数器` | **竞态复现**（AC③）：真实线程 + 屏障，32 路 × 150 轮。整改前**实测第 11 轮即红**（12 轮版），修复后 150 轮全绿 |
| `多轮并发递增不丢失更新` | 廉价伴随守卫：`Dispatchers.Default` 32 路 × 60 轮，覆盖「受控变换单调下界」的多次交错 |

### 2.2 `ISSUE-P2-217`：fast-gate 的 Lint 步骤**显式排除**与静态分析无关的原生构建

**污染链实测**（2026-09-20 本机 `./gradlew lint --dry-run`，任务清单逐行核对）：

```
:crypto:lint → :crypto:lintAnalyzeDebug → :crypto:generateDebugLintModel
  → :crypto:writeDebugLintModelMetadata → :crypto:bundleDebugLocalLintAar
  → :crypto:mergeDebugNativeLibs → :crypto:cargoNdkBuild
```

即 AGP 的 **lint 模型链**要取库模块的**本地 lint AAR**，而该 AAR 的打包会合并原生库
⇒ 触达 `cargoNdkBuild`。fast-gate 按设计不装 NDK / Rust，故该步骤此前恒在
`error: no such command: ndk` 处失败，**从未产出真实 Lint 判定**。

**修法（AC 选项 ②）**：`./gradlew lint -x :crypto:cargoNdkBuild --console=plain`——**显式**排除
这一项，被排除的只有「为打包而做的原生交叉编译」，它与静态分析无因果关系；步骤内**没有**
任何吞掉失败的写法（`lint` 任务自身的成功/失败判定完整保留）。若将来任务名漂移导致排除失效，
该步骤会以「cargo-ndk 缺失」**响亮报红**（fail-closed，绝不静默转绿）。

**为何不选 AC 选项 ①（补装 NDK + cargo-ndk）**：fast-gate 的既有设计契约是「不装 NDK/Rust、
3~5 分钟内给出快速反馈」（见 `build.yml` 头注释）；补装会把该 job 拉长数倍（NDK 约 1.2 GB +
Rust 工具链 + `cargo install cargo-ndk` 源码编译），且与 native-gate 的职责重复。
选项 ② 在**不牺牲**判定力的前提下保住该契约——两者都能满足 AC①，本批取成本更低且不破坏设计的那个。

**本机验证（等价证据）**：

| 检查 | 结果 |
|---|---|
| `./gradlew lint -x :crypto:cargoNdkBuild --dry-run` | 任务清单中 `cargoNdkBuild` 出现 **0** 次（排除生效） |
| `./gradlew lint -x :crypto:cargoNdkBuild` | **BUILD SUCCESSFUL in 3m11s**；日志 `cargoNdkBuild` **0** 次、`FAILED` **0** 次 |
| `grep -cE "^ *<issue$" app/build/reports/lint-results-debug.xml` | **214**（与既有基线**持平** ⇒ 排除未改变任何 Lint 结论） |
| 各模块 lint 报告 | app 214 / crypto 1 / core 0 / database 0 / sync 0（crypto 的 1 条为既有条目，非本批引入） |

### 2.3 `ISSUE-P2-218`：`Set up Android SDK` 显式传 `packages:`（不含已下架的 `tools`）

**根因**：`android-actions/setup-android@v4.0.1`（钉死 SHA 的 `action.yml` 原文）默认
`packages: 'tools platform-tools'`，而**裸 `tools` 包在远端 SDK 仓库已不存在**——
2026-09-20 直取 `https://dl.google.com/android/repository/repository2-1.xml`（373,254 B）与
`repository2-3.xml`（415,919 B）实测：`path="tools"` 出现次数**均为 0**（`path` 含 `tools` 子串的
条目全部是 `build-tools;*` / `cmdline-tools;*` / `platform-tools`）。故该步骤恒失败：
`Warning: Failed to find package 'tools'` → `sdkmanager` 退出码 1。

**修法（AC 选项 ②）**：`native-gate` 与 `device-gate` 两处均改为显式 `packages: "platform-tools"`。
理由（三选一说明）：① 钉回 v3 的已核实 SHA **不成立**——v3 的默认 `packages` **同样含 `tools`**
（见 `docs/records/ci-静态校准记录.md` §2 补充栏原文），钉回去等于保留同一缺陷，且会回退 PR #5 的
整体升级；③ 去掉该 Action 改手工安装需自行实现 cmdline-tools 的下载与解包（增面且无额外收益）。
选项 ② 一行改动**精确移除唯一失效项**，Action 仍负责供应 cmdline-tools（裸 `sdkmanager` 在 `PATH`
上的前提）与许可证接受，NDK / 编译平台 / build-tools 仍由下一步 `sdkmanager --install` 按固定版本安装。

**文档同步更正**：`docs/records/ci-静态校准记录.md` 新增 **§12**（远端仓库实测 + Action 契约原文 +
三选一取舍表 + 未做的事），并在 §2 的 Action 版本表为 v3 那一行**就地加注「基线已过期」**并指向 §12，
避免后续维护者据陈旧基线判断。**未钉 `cmdline-tools-version`（如实声明）**：该值本次只核实到
Action 的默认字面量，未核实 `14742923` 对应产物仍可取；在无法验证的情形下显式钉一个未验证的值
反而更差，故沿用 Action 自身默认（§12.4 已写明）。

**机检守卫（`ISSUE-P3-205` / §218 的「散文承诺 ≠ 机检」立规）**：新增

     （Code Scanning open 告警计数下降）：同因未达成，`ISSUE-P2-219` 的闸门转绿以**本机同参数**
     扫描 + 硬断言退出码 0 为等价判据（与 §11.5 的既有处置口径一致）。
