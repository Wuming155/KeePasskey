## 2. 分段边界按特性切，且**渲染顺序一字未动**

| 段 | 覆盖对话框 | 在原宿主中的位置 |
|---|---|---|
| `VaultListCreationDialogs` | 新建分类选择、模板选择（ISSUE-P3-51） | 第 2、3 块（原样相邻） |
| （宿主内保留） | 排序选择、批量移动、清空回收站 | 第 1、4、9 块 |
| `VaultListGroupDialogs` | 新建群组、重命名、换图标、删除群组 | 第 5~8 块（原样相邻） |

两段的调用点**就写在原块所在的位置** ⇒ 九个对话框的**组合顺序完全不变**。
这条不是可有可无：`AlertDialog` 系各自开独立窗口，若同时可见，渲染先后决定谁压在上层；
因此分段只做「换容器」，不做「重排」。

`VaultListDialogController` 是 `@Stable` 的普通状态持有者（`var showX by mutableStateOf(...)`），
把它作为参数传进段组件不构成「段落读页面 `UiState`」——段的入参仍是控制器 + 标量 + 回调，
`uiState` 的取值（`templateEntries` / `breadcrumbs.lastOrNull()?.name`）留在宿主里算好再传。

`python tools/doc/check_verbatim_move.py /tmp/old_vh.kt <新文件>`（同文件即可，只传两份参数）报
**`orig_content_kinds=140 / MISSING_KINDS=0 / NEW_ONLY_KINDS=27`**——
原文件每一行内容都仍存在于新文件（只是位置换到段组件里），新增 27 行全是段签名 / KDoc / 调用点 / 一条 import。
⇒ 本批**不需要**「缺失行逐条解释」那一节，也说明前几批（§191~§194）报出的缺失确实来自
「判定合并 / 表达式改具名实参」这类主动改写，而不是工具误报——同一把尺子在纯搬时给 0。

唯一**新增**的类型依赖是段签名里的 `List<UiVaultEntry>`（原本只以 `uiState.templateEntries` 出现，
不点名类型）⇒ 补一条 import。
