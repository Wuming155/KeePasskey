### 74.1 缺陷（可观测证据 → 根因）

失败上下文原文（`SyncCacheEvictorTest` 第 140 行断言）：

```
残留计数必须排除防回滚状态（它不是密文快照）；
清理后目录内容=[490a5659…c77a1.rollback]；
销毁器日志=[[INFO] [SyncCacheEvictor] 同步缓存已随会话终止销毁,
            [WARN] [SyncCacheEvictor] 同步缓存残留 0 项，锁定后密文可能仍可恢复]
```

**两条互相矛盾的日志**（先 INFO「已销毁」，再 WARN「残留 0 项，密文可能仍可恢复」）指向：
`evictAll()` 的 `cleared` 为 **false**，而 `remaining` 为 0。追到 `SyncCache.clearAll()`：

```kotlin
allDeleted = allDeleted && removed   // removed = child.delete()
```

`File.delete()` 对**已不存在**的目标返回 `false`。于是「先列目录、再逐个删除」的清理在
**并发或连续两次**执行时必然出现：后一次 `delete()` 的目标已被先者删除 → `removed = false`
→ **误判为删除失败**。触发路径（`session.lock()` 的观察者回调与用例内显式 `evictAll()` 竞态）
正是该用例偶发红的根因；`session.lock()` 的观察者通知是异步的，故时序不稳定、表现为「偶发」。

**影响面（不止于测试）**：
1. 锁库路径产出**自相矛盾告警**「残留 0 项，密文可能仍可恢复」——运维/排障被误导；
2. `SyncCacheEvictor.evictAll()` 返回 `false`，经
   `MainApplication.purgeVolatileCachesBeforeExit()`（ISSUE-P3-116 / §68）把「两个清理面是否都成功」
   误报为失败——**用户显式退出应用时的清理结果被误判**；
3. 连续两次清理（锁定 → 退出清理）中第二次必然报失败。

### 74.2 整改

`SyncCache` 抽出可测的删除原语并确立**幂等契约**（`sync/src/main/java/.../engine/SyncCache.kt`）：

```kotlin
internal fun deleteCacheChild(child: File): Boolean {
    if (!child.exists()) return true
    val removed = if (child.isDirectory) child.deleteRecursively() else child.delete()
    return removed || !child.exists()   // 已不存在即成功
}
```

`clearAll()` 改为逐项调用该原语；**判据从「删除动作的返回值」改为「删除后目标是否仍存在」**——
后者才是调用方真正关心的语义。防回滚状态（`.rollback`）的保留语义**未变**。

### 74.4 过程缺陷（如实留痕）

1. **「偶发红」被容忍了太久**：该用例自 §58 起就记录了偶发（用例注释含「观测 3 次全量 / 1 次失败」），
   但当时（`ISSUE-P3-108`）只把它当作 Windows 文件句柄时序问题登记，**未追到
   `File.delete()` 对不存在目标返回 false 这一根因**。
   ⇒ 纪律：**偶发失败必须补齐「失败上下文采集」并等下一次复现**——本次正是靠前次补的上下文
   （销毁器日志 + 清理后目录内容）一次性定位；仅登记为「时序问题」会长期掩盖真实缺陷。
2. **同一份日志里的矛盾是强信号**：`INFO 已销毁` 与 `WARN 残留 0 项` 不可能同时为真。
   ⇒ 纪律：清理类代码的**返回值语义**应与**日志判据**一致；出现自相矛盾日志时，
   优先怀疑「成功判据取错了对象」（此处取的是 `delete()` 返回值，而非文件是否仍在）。
