# §320 合并主路径采纳结算批次（`ISSUE-P2-313` 闭环，P2 区清零）

> **批次性质**：数据完整性整改。把 §317 的「采纳结算句柄」机制延伸到合并主路径
> `markResolvedAndUpload`——合并产物上传成功时基线不再即时前移，而是随采纳结论结算，
> 消除「采纳失败 → 下轮陈旧树本地赢覆盖云端 merged 内容」的同型损失链（§317 补登的残余项）。

---

## 1. 整改对象

| 条目 | 判据来源 | 本批处置 |
|---|---|---|
| `ISSUE-P2-313` 合并主路径（markResolvedAndUpload）基线前移仍先于本地采纳——采纳失败后同型「陈旧树本地赢覆盖」损失链 | §317 整改中逐行反校发现并补登 | **闭环**（AC① / AC② / AC③ 全部达成，见 §2 / §3）；**P2 区随之清零** |

## 2. 整改方案

### 2.1 AC①：`markResolvedAndUpload` 类型化终态 + 采纳结算

1. `SyncEngineResults.kt` 新增 `SyncResolveUploadResult`（sealed interface）：
   `Uploaded(newEtag, settlement)`（基线前移**尚未落地**）/ `Failed(error)`（含 412
   `ConflictError`，调用方按原口径取 `error` 分派重入）。
2. `SyncEngine.markResolvedAndUpload` 返回类型 `Result<String>` → 该终态：上传成功 ⇒
   `writeCache`（工作副本）+ 返回结算句柄；基线前移与高水位记录**不再即时落地**。
   上传失败 ⇒ `Failed`（缓存与基线保持原状，写序约定不变）。
3. 两处调用方随采纳结论结算：
   - 用户裁决路径 `resolveConflicts`（`SyncConflictResolution.kt`）：`Uploaded` ⇒
     `adoptMergedDatabase(mergedDb, settlement)`（§317 已有该结算参数——校验-采用失败 /
     落盘失败 `reject`、全部成功 `accept`）；`Failed(ConflictError)` ⇒ 412 重入
     `handleResolveUploadSuperseded`（其内部 `commitLocal` 分支 §317 已带结算）；其他
     `Failed` ⇒ 类型化 Error（口径不变）。
   - 自动合并路径 `autoMergeAndUpload`（`SyncConflictAutoMerge.kt`）：`Uploaded` ⇒
     `adoptMergedIfSessionUnchanged` 失败 / 落盘失败 `reject`（`abortDiverged` / 如实报错）、
     全部成功 `accept`；`Failed` 分支按原 412 重入与错误口径分派（重入侧 `commitLocal`
     结算 §317 已接）。

### 2.2 AC②：用例锁定「采纳失败 ⇒ 基线保持旧值、下轮按冲突收敛」

- **引擎级**（`SyncEngineTest` 新增 1 例）：`markResolvedAndUpload` 成功后 `reject` ⇒
  云端已含 merged、缓存工作副本含 merged，但 `baseversion` / meta ETag / basecache 全部保持旧值、
  `hasLocalChanges` 为真（下轮按冲突收敛而非误判已同步）；随后重试上传结算 ⇒ 收敛。
  既有 4 例 `markResolvedAndUpload` 用例随新终态类型适配（成功路径结算后断言基线前移）。
- **端到端**（`SyncMidCycleEditGuardTest` 新增 1 例，AC② 判别力场景）：合并上传窗口内注入
  「用户编辑并保存」⇒ 校验-采用如实中止（`abortDiverged`）；第三轮 `runSyncCycle` 断言
  provider 侧字节仍含「远端新增」（云端 merged 内容不被陈旧树覆盖）且「本地新增」「窗口内编辑」
  均保留。fake Provider 增 `onNextUpload` 钩子（上传落库后注入窗口编辑，模拟真实事件序列）。
  整改前该场景第三轮以「旧树 + 窗口编辑」本地赢整库上传、对端条目被静默抹掉——判别力由
  引擎级 reject 用例与本端到端用例共同锁定。

## 4. 收敛性声明（如实登记）

- **采纳失败 reject 后的状态**：云端 = merged、缓存工作副本 = merged、基线 = 旧值 ⇒
  下轮 `hasLocalChanges` 为真且 baseEtag ≠ remoteEtag ⇒ 冲突三方合并收敛
  （merged 已含双侧内容，重合并无信息损失），**不会**误判「已同步」也不会触发本地赢覆盖。
- **accept 前进程死亡**：与 §317 各分支同口径——会话已采纳（内存+正式文件）而基线未动 ⇒
  下轮按冲突重合并收敛；基线前移丢失只造成一次冗余上传，不造成数据丢失。
- **`Failed` 语义与 `Result` 时期一致**：上传失败时缓存与基线保持原状；412 仍按
  ISSUE-P1-275 AC③ 重入冲突流程（深度界限不变）。
