## §68 退出前清理易失缓存批次（2026-09-15）：ISSUE-P3-116

> **本批次缘起**：用户显式「彻底退出应用」入口（`showKillAppOption` 开启时呈现）此前只做
> `finishAffinity + exitProcess`，用户以为「退出即不留痕」，而磁盘上仍留着两类可被离线读取的内容。
> 本批把终止动作固定为「退栈 → **清理易失缓存** → 退出进程」，清理**必须早于**进程终止。
>
> **补录说明（ISSUE-P3-129 ①）**：本批次在 `AGENTS.md` §1 / §6 与 `ACTIVE_ISSUES.md` 三处被引为
> 「§68 批次」，但其正文**从未落入归档库**（当时归档库仅 §1 ~ §67），致该闭环条目证据链悬空。
> 本文件为 2026-09-15 按 `ISSUE-P3-129` AC① **补录**，事实取自整改提交 `7a6789a`（其第 7 项）
> 与 2026-09-15 在同一 HEAD 上的**复跑实测**；补录本身不改写任何原始结论。

### 68.1 缺陷（ISSUE-P3-116）

| 面 | 落盘内容 | 原清理时机 |
|---|---|---|
| `cacheDir/attachments` | 附件**解密明文**（超过落盘阈值的附件，`FileBinaryStore`） | 仅 ① 应用冷启动（`MainApplication.onCreate`）② 会话锁定 / 关闭 |
| `cacheDir/sync` | 远端 KDBX **密文快照**（`SyncCacheEvictor`） | 同上 |

两个面的共同缺口：用户走「彻底退出应用」时，`finishAffinity + exitProcess(0)` **先终止了进程**，
此后没有任何代码有机会执行清理；下一次清理要等到下次冷启动 —— 即用户显式要求「退出」之后，
明文附件与可离线爆破的密文快照**仍然留在磁盘上**。属「入口语义与实现不符」，非新引入的落盘面。

### 68.2 整改

| 关键改动 | 位置 | 要点 |
|---|---|---|
| 终止动作收敛为固定顺序 | `app/src/main/.../ui/screens/vault/AppTerminationPolicy.kt` | `terminate(detachTask, purgeCaches, exitProcess)`：**退栈 → 清理 → `exitProcess(0)`**。顺序不可颠倒：清理一旦晚于退出即**永不执行**；`purgeCaches` 约定为同步且不自抛 |
| 退出前统一清理 | `MainApplication.purgeVolatileCachesBeforeExit()` | 覆盖两个面：`fileBinaryStore.clear()`（附件明文）+ `syncCacheEvictor.evictAll()`（KDBX 密文快照）。两段均以 `runCatching` 包裹，任一失败只落**脱敏**日志（`AppLog.w`）并返回 `false`，**不阻断退出**；返回值仅用于日志与单测观察 |
| 真实消费点接线 | `app/src/main/.../ui/KeePasskeyApp.kt` | `killAppAction` 仅在 `AppTerminationPolicy.showsEntry(showKillAppOption, hostActivity != null)` 为真时下发；`purgeCaches` 取 `(context.applicationContext as? MainApplication)?.purgeVolatileCachesBeforeExit()` |
| 顺序回归锁 | `app/src/test/.../AppTerminationPolicyTest.kt` | 断言 `calls.indexOf("purge") < calls.indexOf("exit")`（**清理必须早于 exitProcess**），并校验调用点确实引用 `purgeVolatileCachesBeforeExit()` |

### 68.3 语义边界（如实声明，与 `AGENTS.md` §6 同口径）

1. **只清缓存目录**。`<库文件名>.kdbx.bak`（滚动备份，属**用户数据**而非缓存）与
   `filesDir/rollback`（防回滚安全状态，**不得**随退出销毁，否则云侧可重放旧库）**不在**清理面内。
2. **清理为同步 best-effort**：任一实现失败只落脱敏日志、**不阻断退出**。
3. **与反取证无关**：落盘清理仍是 unlink-only（`ISSUE-P2-66` 已接受边界），
   **不得**据此断言「退出即不可恢复」。
4. **仍不覆盖的终止路径**：`force-stop` / OOM / 进程被 kill 等**不经该入口**的终止，
   仍依赖下一次冷启动清理（`ISSUE-P1-19` / F-13 的如实口径，未因本批变化）。
