## 2. 取证（**先补未取证的两点，再决定是否改码**）

### 2.1 未取证点 ①：base 树来源＝**解析自 basecache 字节**（决定性）

读链：`app/.../sync/SyncConflictController.kt` 的 `handleConflictMerge`：

```kotlin
val localDb = localDbOverride ?: codec.parseKdbxBytes(localBytes)   // 非 override 时也解析
val remoteDb = codec.parseKdbxBytes(remoteBytes)                     // 恒解析
val base = resolveTrustedBase(codec, baseSnapshotBytes, localBytes)  // 见下
```

而 `app/.../sync/SyncConflictMergeAdjudication.kt` 的 `resolveTrustedBase`：

```kotlin
val parsedBase = baseSnapshotBytes?.let { codec.parseKdbxBytes(it) }
val trustedBase = parsedBase?.takeIf { !baseSnapshotBytes.contentEquals(localBytes) }
```

⇒ **base 侧恒为「解析实例」**；`baseSnapshotBytes` 取自 `syncCache.readBaseContent(remotePath)`（`<hash>.basecache`
＝「最后确认与云端一致时的完整字节」，`SyncCache.kt` 类 KDoc），该字节既可来自**本端上传序列化**，
也可来自**远端字节采纳**（`SyncEngineAdoptionSettlement.accept()` → `advanceBaseAndPersist(…, bytes)`）。

⇒ **local 侧在 `localDbOverride != null` 时为内存会话树**（`ISSUE-P3-168` 起本地侧优先取内存树，
省一次 KDF + 整树构建）。故合并侧的比较形态与 `ISSUE-P3-542` 的「解析实例 vs 内存构造实例」**同型**。

### 2.2 未取证点 ②：两侧 base 快照语义**不共用**（如实）

「是否需要重新上传」侧（`KdbxContentComparator`）的 `reference` 取 `SyncSessionState.lastSyncedDb`（**内存基线**）、
缺失时回落解析缓存快照；合并侧（`KdbxEntryMerger.isModified`）的 base **恒为解析树**。
两处**问题不同**（`PD-20` 已成文），故本批**不**统一 base 语义，只统一 `fields` 的**比较方式**。

### 2.3 决定性读数（临时探针，已删）

## 3. 整改内容

### 3.1 `core`：新增**单一入口** `KdbxEntry.fieldsContentEquals`

`core/.../model/KdbxEntry.kt` 新增：

```kotlin
fun fieldsContentEquals(other: KdbxEntry): Boolean {
    if (fields.size != other.fields.size) return false
    for ((key, av) in fields) {
        val bv = other.fields[key] ?: return false
        val same = if (isStandardField(key)) av.contentEquals(bv) else av == bv
        if (!same) return false
    }
    return true
}
```

标准五字段判定（`isStandardField`）作为**私有**伴随函数就地承载；比较走 `ProtectedString.contentEquals`
（HMAC 等值标签），**不解密、不物化明文**。KDoc 显式声明「两侧判据的单一入口」与「不得据此改 `ProtectedString.equals`」。

### 3.2 `sync`：`KdbxEntryMerger.isModified` 改走该入口

`if (base.fields != current.fields) return true` → `if (!base.fieldsContentEquals(current)) return true`；
KDoc 增「`fields` 比较口径与 `KdbxContentComparator` 同源（`ISSUE-P3-543`，与 `PD-80` 同口径）」。

### 3.3 `app`：`KdbxContentComparator` 委托同一入口（**删掉本地副本**）

删除私有的 `fieldsChanged(a, b)` 与 `isStandardField(key)`（§477 引入的两份判据之一），
`entryChanged` 首项改 `!a.fieldsContentEquals(b)`；类 KDoc 的「标准五字段按内容比较」一节改为
「判据实现已上收 `core` 的 `KdbxEntry.fieldsContentEquals`，两侧同引」。同步删除失效的
`import com.keepasskey.core.model.KdbxConstants`。

> **行为等价性**：原 `fieldsChanged` 的判据（size 不符 ⇒ 变更；逐键比值；标准五字段忽略标志、其余 per-value）
> 与本入口**逐条相同**，故 §477 的 5 例 `KdbxContentComparatorTest` 断言**未改一字**即保持绿（见 §5）。

### 3.4 未改面（**有意不动，如实声明**）

- **`ProtectedString.equals`**：其等值语义另有 2026-09 加解密审查的裁决依据与既有消费面（`PD-80` 边界 1）；
- **`EntryMergeHelpers.isFieldDifferent`**：`mergeStandardFields` 内两侧同口径比较，探针 E 显示该支自愈；
  改它属「以合并产物换判据一致」的另一面，**无读数支撑**，本批不动；
- **`KdbxXmlEntrySerializer.isStandardField`**（`database`，写侧）：与 `MemoryProtectionConfig.isProtectEnabledFor`
  同源的第三个副本，属写侧标志判定而非变更判据，**不在本条 AC 面内**，本批不动（如需收口应另立条目）。
