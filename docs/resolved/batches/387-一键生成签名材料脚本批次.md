**口令喂入通道的实测裁决**（本批核心工程结论）：keytool 的多行口令提示喂入，
① PS 原生管道编码不可靠（GBK 误区）；② `.NET Process.StandardInput` 经 JVM 透明回声
（`Cat.java` 单文件启动器）证实**字节逐字正确**，但 keytool 多行提示仍读错行——同机
bash 管道同命令一次成功，判定为 keytool 每提示新建 reader 的行为与 .NET 管道组合的
不兼容，不再深究；③ **最终通道＝Git Bash 中转管道**（`printf '%s\n' … | keytool`）：
口令仅存在于 bash 命令串（进程内存参数区，不落盘、不进 Windows 进程命令行枚举的
keytool 参数），字符池排除引号/反引号/`$`/反斜杠，bash 单引号安全；④ 无 bash 时退回
`keytool -storepass`（口令进进程命令行约数秒）——**有告警的显式降级**，不静默。
