## 1. 背景与原貌（走查所得缺口 `G1`）

`KDF` 派生与受保护字段之外，KDBX4 还有**第二把明文密钥**：内层随机流密钥
（`InnerRandomStreamKey`，官方恒 64 字节），它解密全部 `Protected="True"` 字段。其全仓使用点只有两处：

| 路径 | 原貌 | 问题 |
|---|---|---|
| **读** | `KdbxFile.loadPayload` 用**文件自述**的密钥构造 `InnerRandomStreamCipher` → `KdbxXmlParser(...).parse(...)`；此后 `buildDatabase` 只把 `innerHeader.binaries` 交给数据库 | 密钥数组**无任何清零点**：`InnerHeader` 实例随局部变量出栈、密钥明文留存至 GC |
| **写** | `KdbxFile.save` 生成 `freshInnerKey` 并置于 `InnerHeader`，供内层流密码加密受保护字段 | 同型无清零点 |

**为什么不能由 `InnerRandomStreamCipher` 擦**：该类的构造参数 `streamKey` 是**调用方数组**
（B 类借用，见契约 §2.2 判定树 Q3）——`InnerRandomStreamCipher` 只擦**自己派生出的中间量**
（`sha512` / `key` / `nonce`，`InnerRandomStreamCipher.kt:56-79`），对调用方数组**无所有权**，
越权擦除即为契约 R1 的违例。故擦除责任归属 `InnerHeader`（该数组的 O 类所有者）。

**为什么不是「顺手在 `KdbxFile` 里 `fill(0)`」**：本条的落点选择正是 `RC-02` 的收口命题——
把擦除挂在**命名所有者**（`InnerHeader.clearSensitive()`）与**确定性钩子**（`finally`，契约 R3）上，
而不是在调用点散落裸 `fill`（那正是 §57 / §58 / §59 三批「各修一处、下次再漏」的形态）。

## 2. 整改方案与代码落点

### 2.1 命名所有者：`InnerHeader.clearSensitive()`

`database/.../file/InnerHeader.kt` 新增 `fun clearSensitive()`（就地 `innerRandomStreamKey.fill(0)`），
KDoc 明写：① O 类所有权在本类；② 调用时机为本实例生命周期终点；③ **不触碰** `innerRandomStreamId`
与 `binaries`（前者是算法标识、后者属二进制池，见 [`../../architecture/已知工程限界.md`](../../architecture/已知工程限界.md) §1.6）；
④ 派生自本密钥的引擎内部态（BC `StreamCipher` 密钥调度）**无法**经公开 API 擦除，属已声明残余（§4）。

### 2.2 读路径：抽出 `decodeInnerPayload` 并把擦除放进 `finally`

原 `loadPayload` 内的「构造内层流密码 → 解析 XML → 校验 HMAC 终止块」22 行原样下沉为私有函数
`decodeInnerPayload(xmlInputStream, hmacBlockIn, innerHeader)`，**行为逐字不变**（含 D7 的异常包装、
`verifyEndOfStream` 的位置），仅新增 `finally { innerHeader.clearSensitive() }`。

- 擦除**晚于**解析与终止块校验（早于解析会以全零密钥解出乱码，库直接打不开）；
- 覆盖三条异常出口：解析失败 / HMAC 终止块校验失败 / 内层算法不受支持（`KdbxCorruptFileException`）；
- 副作用（正向）：`loadPayload` 因此回到约定行数以内，巨型函数压力未增。

### 2.3 写路径：在 `savePayload` 的级联收尾之后擦除

`savePayload` 的收尾 `finally` 中，把原有的一句 `gzipOut?.close() ?: cipherOut.close()`
包进 `try { … } finally { innerHeader.clearSensitive() }`——**收尾抛异常同样擦除**。

落点理由（就地 KDoc 已声明）：`savePayload` 是该密钥**实际保护过载荷**的唯一路径。若更早的步骤
（KDF 派生 / 外层头部写出）失败，密钥尚未加密任何载荷，其残留不构成新的秘密暴露——故不为此把
`save()` 的 85 行函数体整体再包一层（那属「为纸面完整而改写控制流」，风险非零、收益为零）。

### 2.4 契约用例：`InnerStreamKeyWipeTest`（8 例）

| 层 | 用例 | 钉住的语义 |
|---|---|---|
| 行为 | 内层随机流密钥必须可被确定性擦除 | `clearSensitive()` 逐位清零（非空跑：入参按键序填充） |
| 行为 | 擦除是幂等的且不触碰算法标识与二进制池 | 二次调用无害；`innerRandomStreamId` / `binaries` 及其内容不变 |
| 行为 | 默认构造的实例互不共享密钥数组 | 默认参数是**每次求值**的新数组——若被提为共享常量，擦一个实例会污染其余实例 |
| 行为（非空跑） | 受保护字段经保存与重载往返仍可原样解密 | 方向性闸门：写侧擦除若早于序列化，产物必解不开 |
| 静态 | `InnerHeader` 必须提供擦除入口 | `InnerHeader.kt` 含 `clearSensitive()` 且体内清的是 `innerRandomStreamKey` |
| 静态 | 读路径必须在解析之后且于 `finally` 内擦除 | 存在性 + **顺序**（晚于 `KdbxXmlParser(`）+ 位于最后一个 `finally` 之后 |
| 静态 | 写路径必须在序列化之后擦除 | 存在性 + **顺序**（晚于 `KdbxXmlSerializer(`） |
| 静态 | 写路径的擦除必须落在 `finally` 内 | 级联收尾抛异常时不得残留 |

**为何需要静态层**：`KdbxDatabase` 不保留 `InnerHeader`，擦除效果**无法由外部用例观测**——这是本仓
既有的同型处置（对齐 `CredentialIntermediateWipeTest` / `ChangeCredentialsKeyFileWipeTest`）。
顺序断言的存在还有一条**前瞻**理由：当前 `InnerRandomStreamCipher` 在 `init` 中一次性派生状态，
故「擦早一点」暂时不会改变密码学结果；一旦日后改为**惰性读取**（§147 在 CBC 流上真实发生过：
调用方按 JCE 假设提前擦密钥 ⇒ 全零密钥解密、宿主全绿仅真机失败），顺序即成为正确性条件。

## 4. 已知边界与残余（如实声明）

1. **引擎内部态不擦**：`InnerRandomStreamCipher` 持有的 BC `ChaCha7539Engine` / `Salsa20Engine`
   实例内部含密钥调度（由本密钥派生）。BC 公开 API 无「擦除内部态」入口（`reset()` 只复位计数、
   不归零密钥），故属**已声明残余**——缓解方向是内核下沉（若日后该路径改为原生实现，可由
   `Zeroizing` 承担，与 `crypto/src/main/rust/` 既有口径一致）。
2. **写路径「更早失败」窗口不覆盖，且不构成暴露**：`save()` 在 KDF 派生 / 外层头部写出阶段失败时，
   `freshInnerKey` 尚未加密任何载荷（载荷由 `savePayload` 统一写出），其残留不属「已保护过数据的密钥」；
   本批**刻意不**为覆盖该窗口把 `save()` 函数体整体再包一层 try/finally（理由见 §2.3）。
3. **未做设备侧**：本批只动 `database` 模块的 JVM 可测路径（无原生分派、无会话锁路径、无
   `androidTest` 新增或修改），故按测试资产纪律②**无**设备侧必跑项；「真机解锁真实库」的效果
   由既有 `RealKdbxCorpusUnlockTest` 的宿主/设备双口径继续承担，本批未另行实测。
4. **`G2` 未一并处理，且其原前提经本批「实施前复核」两处不成立（已就地更正）**：
   原登记为「`SyncSessionState.lastSyncedDb` 与 `SyncConflictController.clearPendingConflictSession()`
   只置 null、不擦树」——复核后前者（全仓 5 处赋值**全部**是 `databaseSession.databaseFlow.value`，
   即**会话活动树本身**）与 `pendingLocalDb`（生产两处调用都传 `localDbOverride = localDbSnapshot`）
   均为会话树的引用，**只置 null 是正确形态**；真实残余只余 `pendingRemoteDb` 与 `pendingMergedRoot`
   的合并器新建节点。**并且** `clearPendingConflictSession()` 同时服务「会话锁定」与「合并树已采用为
   会话库并落盘成功」两条路径 ⇒ 在该处就地擦除会**连带擦掉刚被采用的活动库中共享的节点**（P0 级）。
   故本批**不实施**该处擦除（不是「未及实施」，是「原方案会写坏库」）；准入条件与责任人（会话终止路径
   + 身份集合判定 + `KdbxMerger` 复用边界 + 真机同步冲突链路）已登记于
   [`../../ACTIVE_ISSUES.md`](../../ACTIVE_ISSUES.md) 与设计附 A 的 `G2` 更正行。
5. **`G4`（清零点无统一符号，散落 100+ 处）与 `G5`（部分收口点缺契约用例）仍开放**：`G4` 属纯机械
   替换、按模块分批；本批**未**顺手做（避免把「一处收口点整改」扩成跨模块大改，违反 AC②）。
