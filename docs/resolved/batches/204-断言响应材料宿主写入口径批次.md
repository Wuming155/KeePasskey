# §204 批次：断言响应材料宿主写入口径批次（ISSUE-P3-188 剩余清单第 4 项结案）

> 日期：2026-09-19　|　条目：`ISSUE-P3-188` 剩余清单第 4 项（**结案移出**，剩余清单回到 1~3 项）
> 背景：§173 把断言侧响应组装下沉为 `PasskeyAssertionPayload.build(...)` 后，四条安全判据本可离线
> 断言，但 `org.json.JSONObject` 在宿主 JVM 是 Android 桩（§174 实测）——本批执行 §174 明示的**路线②**。

## 1. 本批做了什么

1. **新增宿主可用的极简 JSON 写入器** `app/src/main/java/com/keepasskey/app/passkey/WebAuthnJsonWriter.kt`
   （`internal object`，零依赖、可 JVM 单测）：
   - 键序 = 插入序、紧凑输出、字符串转义按 **AOSP `JSONStringer`** 语义（含 `/` → `\/`；
     `\t` `\b` `\n` `\r` `\f` 短转义；其余 `≤ 0x1F` 写小写四位 `\u00xx`；`≥ 0x20` 原样 UTF-8）；
   - **不实现数字与 null**：WebAuthn 响应材料无数字 / null 值，可缺席的键由调用方显式省略
     （ISSUE-P2-72「取不到即省略」语义，同时避免 null 值序列化漂移）。
2. **注册 / 断言两处 payload 全部改走写入器**（§174「勿只改一半」）：`PasskeyAssertionPayload.build`
   与 `PasskeyRegistrationPayload.build` 的 clientDataJSON、最终响应 JSON、`clientExtensionResults`
   组装全部换口径，`org.json` import 双双移除（仅 KDoc 注释保留对齐对象说明）；
   `buildPrfClientExtensionResults` 返回类型由 `JSONObject` 改为 `WebAuthnJsonWriter.Obj`
   （核实过无外部消费方，安全收敛为 private）。
3. **四条宿主离线断言** `PasskeyAssertionPayloadBuildTest`（宿主 JCE 现场生成 secp256r1 密钥对，
   私钥按仓内 PKCS#8 PEM 契约（64 列折行）包入 `PasskeyData`，解析 / 签名仍走**生产链路**
   `decodePemPrivateKeyText` → `signAssertion`；JSON 解析一律走本仓 `SimpleJson`）：
   ① `clientDataPackage=null` ⇒ `clientDataJSON` 无 `androidPackageName` 字段、整份响应不含本应用
   包名（含「有调用方包名时原样写入」正对照）；② `prfEval=null` ⇒ `clientExtensionResults` 为空对象；
   ③ `authenticatorData` 37 字节 / 前 32 字节 = `SHA-256(rpId)` / 第 33 字节 = flags / 第 34~37 字节 =
   大端 `signCount`——即 **WebAuthn 标准布局**（条目原文「前 16 字节 / 第 5~8 字节」系笔误，
   按标准口径执行）；④ 签名可由该凭据公钥对 `authData || SHA-256(clientDataJSON)` 验过
   （JCE `SHA256withECDSA`）。
4. **转义语义宿主回归** `WebAuthnJsonWriterTest`（8 例）：键序 / 紧凑 / 布尔 / 嵌套 / 数组 /
   `/` 转义 / 短转义族 / 低段控制字符小写四位补零 / 非 ASCII 与 U+2028·U+2029 原样。
5. **设备侧逐字节对拍** `WebAuthnJsonWriterParityDeviceTest`（3 例，**双设备实跑全绿**）：
   在真实 Android 平台 `org.json` 上锁定「写入器输出 == 平台输出」（字符串值关键输入集、
   键序插入序、布尔 / 嵌套 / 数组形态）。宿主 JVM 无法执行平台 `org.json`（Android 桩），
   该契约**只能在设备侧锁定**——写入器序列化语义若有漂移，此用例先红。

## 4. 过程中发现并同批修复的设备用例缺陷（ISSUE-P3-197 的根因）

§204 验证期间 `AutofillAuthChainDeviceTest` 从「真机两轮绿」翻转为双设备同点失败
（完整性留痕断言）。二分定位（`git stash` 回滚工作区改动后失败依旧 ⇒ 与本批 payload 改动无关；
真机 device logcat 中留痕行**存在**却未匹配）后确认**用例自身两处解析/采窗缺陷**：

1. **`linePid()` 解析缺陷（主因）**：threadtime 的 pid/tid 为**右对齐 5 位宽**——4 位 pid 前有
   2 个空格，`split(" ")` 把连续空格解析成空元素（`getOrNull(2) = ""`），「本进程」过滤恒假；
   只有 5 位 pid 才凑巧正确。实测轨迹完全吻合：真机 pid 5 位时两轮绿（§203 提交前后）、
   pid 回落 4 位后恒败；模拟器 pid 恒 4 位故**从未绿过**（§203 批次登记的「模拟器专有差异」
   的真根因，当时登记为「成因未定位」并在同批以 §204 二分定位推翻）。修复：按连续空白切分。
2. **采窗缺陷（次因）**：阶段 0 的 `logcat -c` 已把进程启动时那拍留痕清掉，等待只能依赖
   30s 周期重扫的**下一拍**，而 `INTEGRITY_WAIT_MS = 15s < 30s`——相位错过即恒等不到。
   修复：15s → 35s（> 一个完整周期，断言强度不变）。

修复后：真机恢复**全绿（64 例）**；模拟器推进到完整性断言**之后**的新失败点（「系统填充 UI 未出现
认证引导数据集」）——属强系统 UI 依赖的环境敏感面（该用例设计验证环境为真机），CI `device-gate`
以 `notClass` 显式排除该类（workflow 注明理由）、真机承担，残余面登记 `ISSUE-P3-197` 继续。
