# §239 运行环境完整性检测开关批次

> **条目**：`ISSUE-P3-236`（同轮新登并**整条结案**）；产品口径登记 [`PD-15`](../../architecture/产品裁决登记.md)。
> **时间**：2026-09-21。
> **命题（用户 2026-09-21 原话）**：「将当前默认启用且会在 root 环境等异常情况下阻止指纹识别使用的机制（如 root 检测等）
> 改为可由用户自行配置的开关。要求能够灵活开启或关闭该检测，默认状态为关闭，以便在 root 环境下指纹识别仍可正常使用；
> 同时需考虑相关安全风险提示或可选说明，确保开关配置清晰、易于操作。」

---

## 1. 背景与缺陷定位

运行环境完整性检测（`ISSUE-P2-08` / ZT-13 起建）此前是**恒开且零配置入口**的硬编码行为：

| 环节 | 整改前形态 |
|---|---|
| 采集 | `RuntimeIntegrityDetector.detectSignals()`：root 落点 / Magisk 痕迹 / 调试器 / `ptrace` / 注入框架 / debug 构建 / 无障碍 |
| 裁决 | `RuntimeIntegrityPolicy.evaluate()`：命中 ⇒ `COMPROMISED`（禁生物快速解锁 + 禁自动填充 + 风险提示） |
| 门控 | `BiometricAuthManager.authenticate()`、`KeePasskeyAutofillService`、`KeePasskeyCredentialProviderService` 经 `RuntimeIntegrityGate` 读策略 |
| 配置面 | **无**——无偏好键、无 `BuildConfig` 字段、无 UI 入口；`LIVE_RESCAN_INTERVAL_MS` / `SNAPSHOT_STALE_AFTER_MS` 为常量 |

后果：对**自有且已 Root（含 Magisk）**的设备，指纹快速解锁被永久锁死且用户既看不到「为什么」也无法选择——
而这类设备恰恰是密码管理器的常见用户群（自建同步 / 定制 ROM）。§236 已就 `ISSUE-P2-232`（完整性风险升级是否主动熔断）
落过一处关键补正：`COMPROMISED` 的五项构成中**三项是纯文件存在性检查**（root 落点 / Magisk 痕迹 / frida 落点），
字面熔断会让这类设备在解锁后 ≤30 s 反复被锁而实质不可用——本批是该结论在「生物快速解锁」面上的同源处置。

**定位：这是产品取舍（用户明示裁决），不是缺陷。** 故登记为 `PD-15` 而非挂在 `ACTIVE_ISSUES.md`；
本批交付的是「把既有取舍做成**用户可配置**」，而非「判断该检测该不该有」。

## 2. 整改

### 2.1 偏好层（出厂默认**关闭**）

- `UserSettings.integrityCheckEnabled: Boolean = false`（新增，含口径 KDoc）。
- `SettingsRepository.setIntegrityCheckEnabled(enabled)` + `RealSettingsRepository` 实现
  （键 `integrity_check_enabled`，读回缺省 `?: false`）+ `FakeSettingsRepository` 同语义内存实现。

### 2.2 裁决层（关闭只解除**降级**，不改变**判定**）

`RuntimeIntegrityPolicy.evaluate()` 增参 `enforcementEnabled: Boolean = true`，并拆出两个私有纯函数
`riskLevelOf()`（信号 → 等级）与 `enforcingEnforcement()`（等级 → 阻断策略），**两者逐字承接原 `when` 块**，判定口径零变更。

关闭态（`enforcementEnabled = false`）产出：

- `level` / `signals` —— **仍是真值**（Root 命中照样报 `COMPROMISED`）；
- `enforcement` —— `disableBiometricQuickUnlock = false`、`disableAutofill = false`、`requireRiskNotice = false`、
  `biometricBlockReasons` 空清单（通道既已放行，就不给「为什么被禁」的消费侧提供一份本就未生效的归因）；
- `requireAccessibilityNotice` —— 原样保留（无障碍提示与总开关正交：只提示、不降级）。

`escalateForLiveSignals()` 同步增参，实时（调试器 / 钩子 / `TracerPid`）升级不改变关闭态的执行口径。

**关键的诚实性取舍**：关闭的是「降级」而不是「判定」。若连等级一起关掉，设置页会在真有 Root / 注入框架时
显示「无风险」——**谎报安全比不检测更坏**，故 `report` 恒为真值。

### 2.3 门控层（两个入口都必须短路）

`RuntimeIntegrityDetector` 新增 `@Volatile private var enforcementEnabled = false`（初值 = 出厂默认，避免冷启动瞬间反转口径），
由 `start()` 内 `observeEnforcementPreference()` 订阅设置流维持一致；开关变更即 `refresh()` 一次，
快照不会出现「用关闭态的策略代表开启态」。

- `currentEnforcement()`（**指纹**入口）与 `awaitEnforcement()`（**自动填充 / CM** 入口）
  首行各自 `if (!enforcementEnabled) return IntegrityEnforcement.ALLOWED`——
  **刻意连「未判定 / 快照已陈旧」的 fail-closed 保守分支一并绕过**：那条保守策略同样是「检测」语义的一部分，
  用户既已显式关闭，就不该再以「扫描还没跑完」为由把指纹挡在门外。
- **关闭只解除阻断，不停探测**：30 s 周期重扫照常运行（成本为每 30 s 一次文件探测），
  用户重新开启时 `report` 已是真值、无需等待下一轮。

### 2.4 设置页与文案

- `SecuritySettingsScreen` 生物识别卡片内新增开关行（`sec_integrity_check_title` / `_sub`），
  **关闭态常驻**代价说明 `sec_integrity_check_off_notice`（`colorScheme.error`，语义与「关闭自动擦除剪贴板」的常驻提示一致）；
  归入生物识别卡片而非「隐私泄露防护」分区，是因为它存在的唯一目的就是决定「指纹在 Root / 调试 / 注入环境下是否还能用」。
- 接线：`SettingsViewModel.setIntegrityCheckEnabled` → `SettingsPreferencesController`（仓库直写，**无需当场身份验证**
  ——该开关不涉及身份确认，且两个方向都即时可回改）→ `KeePasskeySettingsNavGraph` 的 `onIntegrityCheckToggle`。
- 文案 zh/en 各 +3 键；`SettingsUiState.integrityCheckEnabled` + 投影映射。

    root 命中仍报 `COMPROMISED`（不谎报无风险）；放行态不携带阻断归因；无障碍提示正交；
    **开启态 fail-closed 后果逐项不变**（root → 三通道阻断 + `[ROOT_ARTIFACTS]`）；

    （`UserSettings` / `SettingsUiState` / 持久化读回缺省）；设置页暴露开关并常驻关闭代价说明；
    ViewModel 与导航图接线；中英三键齐备。

  `python tools/doc/count_test_results.py` 现跑 **`xml=344 tests=2415 failures=0 errors=0 skipped=13`**
  （§238 基线 343/2402 ⇒ **+1 类 / +13 例**，与本批新增用例逐例可对）。
- 文档自检：`check_md_links.py` / `check_resolved_index_sync.py` / `count_line_tiers.py` / `long_functions.py` 现跑结论见 §239 索引行。

### 过程缺陷（如实留痕）

1. `evaluate()` 改造首轮把 `riskLevelOf(signals)` 在同一函数内调用了两次（`level = riskLevelOf(...)` 与
   `enforcingEnforcement(riskLevelOf(...), ...)`），虽行为等价但属重复求值，当场提为局部量后修正。
2. 新用例文件首稿在「关闭检测时实时信号升级不再降级」一例中误写为 `RuntimeIntegrityLevel.SUMMARY`
   （无此类型 / 无此属性），**在提交前自查发现**并改为 `assertEquals(RuntimeRiskLevel.COMPROMISED, escalated.level)`；
   该错误未进入任何一次编译，故未产生「红—绿」记录。
3. **一次与本批无关的已知平台偶发红**：最终全量跑曾有**一轮**失败于
   `SyncCacheEvictorTest > 关闭密码库后同步缓存目录为空`（`expected:<[]> but was:<[…\cache\sync\490A5659…C77A1.BASEVERSION.tmp]>`）。
   该现象属**已登记限界 §7「目录枚举噪声与其派生残余」**（本机 Windows/NTFS `File.listFiles()` 偶发返回
   无实体的**大写拼写**条目，其 `isFile` 在约 3% 情形下仍为 true）。
   **逐字段对拍即定性**：鬼影签名 = hex 大写 + 后缀段全大写 + 无 UUID，与全仓唯一写入者
   `SyncCache.tmpFileFor`（`<64 位小写 hex>.<后缀>.<UUID>.tmp`）**不可能混淆**；且「`.tmp` 未被清除」
   这类结构缺口会每次复现，而本处隔离复跑 1/1 绿、随后全量复跑亦绿 ⇒ **非本批引入、非真空残留**。
   处置遵循该限界既定口径：**不改测试、不改产品代码**，只在限界 §7 补登「第四处观测点」，使下一次同形红不再被读作新缺陷。

## 4. 如实声明（**不得读作已验证**）

- **无设备可用 ⇒ 开关的最终效果未真机核对**：本环境（Windows / 无连接设备）未执行任何 `connectedAndroidTest`。
  具体地，下列三条**均未实证**，只由代码路径与纯函数用例支撑：
  ① 在已 Root（含 Magisk）真机上「关闭开关后 `BiometricPrompt` 真的弹出并可解封」；
  ② 「开启开关后同一台设备立即恢复拦截」；
  ③ 自动填充 / CM 两条通道在两种开关态下的实际下发行为。
- 本批**未触碰** `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 与任一原生绑定 / 引擎，
  亦未新增或修改 `*/src/androidTest/**` 用例 ⇒ 按 `AGENTS.md` 规则「测试资产纪律」②，本批**无设备侧必跑项**；
  但该结论**不**豁免上面 ①②③ 的手工冒烟——它们属发布前应做而本环境做不了的事。
- **默认口径已被反转**：出厂默认由「恒开」变为「关闭」。这是用户明示裁决（`PD-15`），
  **不是**「本仓认为该检测不必要」；`ISSUE-P2-08` / `P3-83` / `P3-120` 的全部探测能力与判据**一行未删**，
  开启开关即完整恢复（`RuntimeIntegrityPolicyTest` 等既有用例对开启态行为原样锁定）。
- 限界 §3.5 的「`LIVE_RESCAN_INTERVAL_MS` / `SNAPSHOT_STALE_AFTER_MS` 不得为省电放宽」**口径不变**
  （已就地补注本开关的位置）；`docs/architecture/已知工程限界.md` 的既定残余风险登记不因本批解除。
