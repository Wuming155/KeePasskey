## 2. 生成侧脱敏纪律随迁且未放宽

1. 全程**零 String 中间量**：ES256 私钥标量以 BigInteger 二进制 → hex `CharArray`，
   Ed25519 / RS256 的 Base64 编码走 `CharArray` 通道；
2. 每个中间字节 / 字符副本用毕即 `fill(0)` 擦除（ISSUE-P1-02）；
3. 私钥文本经 `sealedFromPrivateChars` 封装为 `ProtectedString`（`InMemoryCipher` 密文驻留）后
   才作为 `PasskeyData` 字段返回，字符副本在 `finally` 清零；
4. `crypto` 模块的**原生面未被触碰**：未改 `crypto/src/main/rust/**`、`jni_bridge_ext.rs`，
   也未改任何 `Native*` 绑定的分派 / 探活 ⇒ `AGENTS.md` §5 的原生面设备验证义务**未触发**。

## 3. 搬家事故留痕（一次「块边界」错误，编译期即暴露）

下沉脚本用「从签名行往上回退到注释块」定位块首、以「下一个函数 KDoc 之前」定位块尾，
结果把夹在两个函数之间的 **`val SUPPORTED_ALGORITHMS` 声明**一并扫进了新文件（它在原文件里
位于 `generateRs256KeyPair` 与 `isAlgorithmSupported` 之间）。`compileDebugKotlin` 立即报
`Unresolved reference 'SUPPORTED_ALGORITHMS'`，遂按 11 行块原样搬回原位。
**教训**：以「函数签名」为锚做区间搬动时，块尾必须是**上一个函数体的收尾**，不能是
「下一个声明的 KDoc 之前」——中间夹的属性声明会被吞。补一条纪律：**搬动后先编译，再谈验证**。
