## 491.1 原始条目（原样收录）

### `ISSUE-P3-576`：自定义图标上传通道对 SAF 流无大小闸门，与同文件附件通道防护不对等

**背景与影响**：`EntryEditPickers.kt:236` `rememberCustomIconPicker` 直接
`openInputStream(uri)?.use { it.readBytes() }` **无上限物化**（峰值约流大小 2 倍，`Error` 不被 `:245`
`catch(e: Exception)` 捕获 → 进程崩溃、未保存编辑丢失）；同文件 `rememberAttachmentPicker` 已有
「申报长度拦截（`:173-179`）+ 读后兜底并 fill(0)（`:188-192`）」双闸门，`AttachmentSizeLimits.kt:13-14`
KDoc 明言「读取字节之前即拒」的设计意图未落到图标通道。攻击者 App 经 MediaStore 贡献超大「图片」
（普通 App 贡献媒体无需权限）诱导用户在 Photo Picker 选中即可触发，影响为进程 DoS。

**验收标准**：图标通道接入与附件通道同等的双闸门（申报长度拦截 + 读后兜底），超限按既有上限拒绝；单测锁定。

**核实时间点 + 核实方式**：2026-10-11，数据流安全审查工作流（同 P2-573 口径），基准提交 `cd223701`；六要素详情见
[`security/数据流安全审查_2026-10-11.md`](../../security/数据流安全审查_2026-10-11.md) 发现 4（verdict=confirmed）。
来源攻击面：其他攻击面兜底。

## 491.2 前提复核（2026-10-11 直读）

- **条目成立（快照一致，零漂移）**：直读 `EntryEditPickers.kt` 原状——`:236` 即
  `val rawBytes = context.contentResolver.openInputStream(uri)?.use { it.readBytes() }`（图标通道**无任何**尺寸判定）；
  `:245` 即 `catch (e: Exception)`（不捕 `Error`）；对照通道 `rememberAttachmentPicker` 的申报长度拦截在
  `:173-179`、读后兜底 `bytes.size` 判 + `bytes.fill(0)` 在 `:188-192`；`AttachmentSizeLimits.kt:13-14`
  KDoc 即「超限在读取字节**之前**即拒」。条目所引行号与语义逐条吻合。
- **「报告补充」两点独立复核**：`decodeAndScaleToPng`（`EntryEditIconCodec.kt:17-46`）先
  `inJustDecodeBounds` 读尺寸、再以 2 的幂 `inSampleSize` 粗降采样，位图物化**有界**；真正无界物化点在
  原 `:236` 的 `readBytes`（峰值约流大小 2 倍）——与发现 4 复核 notes 逐字吻合。
- **「既有图标上限」不可直接复用为原始字节闸门**：`CustomIconCoordinator.MAX_ICON_BYTES = 256 KB`
  （`:156`）作用于 `decodeAndScaleToPng` 的**产物**（入库体积），文案 `icon_too_large`
  （「请选择小于 256 KB 的图片」）与该上限绑定；而 Photo Picker 返回**原图**（12–48 MP JPEG / HEIC
  约 3–15 MB），以 256 KB 拦原始流会把正常选图整体拒绝 ⇒ 原始字节闸门必须另立上界（见 §491.3 ①）。
- **测试基建口径**：`grep -rl robolectric app/src/test` 零命中 ⇒ 宿主侧无 Robolectric，SAF /
  `ContentResolver` 流不可在 JVM 复现 ⇒ 判定抽纯函数直测、接线走源码静态守卫
  （先例：`TotpGalleryImportDecodeTest` 对 `TotpGalleryImport.kt` 的 `decodeStream` 判空扫描）。

## 491.3 整改

### ① 上界常量：`AttachmentSizeLimits` 新增图标上传上限（`MAX_ATTACHMENT_BYTES` 同源派生）

`database/.../AttachmentSizeLimits.kt:52` 新增 `MAX_CUSTOM_ICON_UPLOAD_BYTES = MAX_ATTACHMENT_BYTES / 4`
（= 16,777,215 B ≈ 16 MiB − 1，远小于附件上限 64 MiB − 1）。KDoc 依据：① 图标产物被
`decodeAndScaleToPng` 固定降采样为 ≤128px PNG（入库另受 256 KB 约束），原始字节只是**有界位图解码**的输入；
② 覆盖 Photo Picker 合法原图（12–48 MP JPEG / HEIC 约 3–15 MB）；③ `readBytes()` 峰值约 2 倍流大小，
本上限封顶使原始物化峰值 ≤ ~32 MiB，与附件上限同口径地远低于低端机 192 MiB 堆界
（真机实测见 `KdbxAttachmentBudget` 类 KDoc）。对象级 KDoc 补段说明本项**不共用**附件取值但**同源派生**，
「文件大小上界只认本对象一处」的口径不破。

### ② 判定纯函数与提示工厂（`EntryEditPickers.kt`）

- `:94-99` 新增 `internal fun exceedsCustomIconUploadLimit`：`Long?` 重载吃「申报长度」
  （`null` 与 `-1` = `UNKNOWN_LENGTH` 都视为未知 ⇒ 放行给读后兜底），`Int` 重载吃「实读大小」
  （`ByteArray.size` 恒非负），判定唯一一条 `sizeBytes != null && sizeBytes > MAX_CUSTOM_ICON_UPLOAD_BYTES`
  ——纯函数、无 Android 依赖，供纯 JVM 单测直测。
- `:78-82` 新增 `iconTooLargeMessage()`：与附件通道 `attachmentTooLargeMessage()` 同型，上限数值经
  `%1$d` **参数注入**（按 1 MiB 向上取整显示为 16），不在文案里再写一份数字。
- `:64-65` 私有镜像 `MAX_CUSTOM_ICON_UPLOAD_BYTES`（与既有 `MAX_ATTACHMENT_BYTES` 私有镜像并列，
  同取数据库侧常量）。

### ③ 图标选择器双闸门（读前申报长度拦截 + 读后实读兜底）

`rememberCustomIconPicker`（`:262-306`）按附件通道同型两段闸门重排：

- **闸门①（读前，`:271-280`）**：`openAssetFileDescriptor(uri, "r")?.length` 申报长度超限即拒绝并提示，
  **不读流**；`runCatching` 保护段沿用附件通道同款 `cancel-n/a:` 标注（保护段无挂起点）。
- **闸门②（读后，`:282-288`）**：申报长度不可得（`null` / `UNKNOWN_LENGTH`）或流实际更长时按
  `readBytes()` 的 `rawBytes.size` 二次判定，超限先 `rawBytes.fill(0)` 清零再拒绝。
- 两闸门均未触发时才进入既有 `decodeAndScaleToPng` → `onCustomIconUploaded` 路径（`:289-296`）；
  解码失败与异常分支（含 `CancellationException` 重抛）逐字保留。

### ④ 捕获面判定（不把 `catch (Throwable)` 当修复）

`catch (e: Exception)` 确实捕不到 `OutOfMemoryError`，但本批**不**改为 `catch (Throwable)`：那会把
协程取消与致命错误一并归一为「图片无效」业务失败，违背取消语义纪律（`ISSUE-P3-569` / `P3-570`，§484/§486）。
闸门是主防线：申报长度拦截生效后，Photo Picker / MediaStore 系统 provider 形态（正常路径）**不再**触发
无界物化；申报长度失真的自定义 provider 形态残余与 Error 面残余一并如实声明（§491.5）。

### ⑤ 文案（中英成对）

新增 `edit_icon_too_large`（`values/`「图片超过 %1$d MB，未上传为图标」与 `values-en/` 英文逐键成对），
与 `edit_attachment_too_large` 相邻同型（数值参数注入）。既有 `icon_too_large`（256 KB 产物上限文案）
保持原义未动。

### ⑥ 测试资产

**新增** `app/src/test/java/com/keepasskey/app/ui/screens/edit/EntryEditIconUploadGateTest.kt`（6 例，纯 JVM）：

1. 申报长度超过图标上限 ⇒ 拒绝（含「附件上限量级必然超图标上限」防回退判据）；
2. 申报长度未超限与边界值恰好等于上限 ⇒ 放行；
3. 申报长度未知（`null` 与 `UNKNOWN_LENGTH` = -1）⇒ 放行、交读后兜底；
4. 读后实读大小超限 ⇒ 拒绝（`Int` 重载口径，边界与申报侧一致）；
5. 图标上限与附件上限**同源派生**（`MAX_ATTACHMENT_BYTES / 4`）且远小于；
6. 源码静态守卫：`rememberCustomIconPicker` 内**申报长度判定先于读流**（顺序反转即「先读爆内存再判超限」），
   且读后兜底带 `rawBytes.fill(0)` 与 `iconTooLargeMessage()` 接线——「超限不读流 / 读后清零」由此锁定。

未删除任何既有用例（测试资产纪律 ①）。

## 491.5 如实声明

- **上界取 1/4 派生（≈ 16 MiB − 1）而非复刻附件上限**：条目「报告补充」明言图标上限应**远小于**
  `MAX_ATTACHMENT_BYTES`；本批以 `MAX_ATTACHMENT_BYTES / 4` **同源派生**（16,777,215 B），
  既不另立字面量，又保证与附件上限不同量级。未取 256 KB（`MAX_ICON_BYTES`）：那是 `decodeAndScaleToPng`
  的**产物**上限，Photo Picker 原图普遍大于它，直接复用会把正常选图整体拒绝（§491.2 已核实）。
  **残余**：合法来源中体积 > 16 MiB 的原图（如 108–200 MP 超大图 / 大尺寸全景）会被拒并提示
  「图片超过 16 MB，未上传为图标」——有意收敛（图标产物固定 ≤128px，用户换图即可），非缺陷。
- **提示键未直接复用既有键（有意取舍）**：`icon_too_large` 文案硬编码「小于 256 KB」（产物上限，
  与原始字节上限不同量级），复用会让用户看到**错误数值**；`edit_attachment_too_large` 主语是「附件」。
  故按附件通道**同型**新增 `edit_icon_too_large`（中英成对、数值参数注入）——「两通道口径一致」落实于
  ①同一双闸门形态、②上界常量同处同源、③提示的数值不写死机制，而非共用同一文案键。
- **未采纳「有界流式读取」替代 `readBytes()`**：条目最小修复建议即「附件通道同款两段闸门」，
  本批逐字照做以保持两通道口径一致。**残余**：申报长度**失真**的 provider 形态（申报 ≤ 上限但流实际
  更大且 readBytes 期间越堆）仍可能物化——Photo Picker 返回 MediaStore **系统 provider**，申报长度
  来自真实文件大小，该形态在 Photo Picker 面不可达；申报长度**不可得**的形态已由读后闸门兜底；
  读后兜底的物化上限即「provider 实际可流出量」，此残余与附件通道**同型同等**，如实登记于此。
- **未采纳 `catch (Throwable)`**：理由见 §491.3 ④；Error（如 OOM）仍不被 `catch (e: Exception)` 捕获，
  闸门使**正常路径**不再触发无界物化，Error 面残余与附件通道同型。
- **未改面**：`rememberAttachmentPicker`（申报拦截守护段与判定 `:205-212`、读后兜底 `:220-225`、
  `cancel-n/a` 标注、`attachmentTooLargeMessage()`）、`decodeAndScaleToPng`、`CustomIconCoordinator`
  的 256 KB 入库上限与 `icon_too_large` 文案、`icon_invalid_not_png` 失败分支——全部逐字未动。
- **设备侧缺口**：SAF 真机形态（Photo Picker 选超大盘外文件被读前拒绝）**未获真机证据**（按任务禁令未跑
  设备侧）；判定与接线由纯函数 + 源码静态守卫锁定，真机可视回归如需补做，应在 AVD（非用户真机）上执行。
