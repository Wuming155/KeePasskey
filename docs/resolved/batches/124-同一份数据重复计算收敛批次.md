## 1. 逐条整改内容与证据

### 1.1 `ISSUE-P3-166` 健康检查对同一条目 3 次解密 + 2 次 SHA-256

**原条目**（自 `ACTIVE_ISSUES.md` 原样收录）：

- **背景**：`database/.../audit/HealthCheckEngine.kt:52`（第一趟建重用索引）与 `:98`（第二趟判定）——
  第一趟 `readUtf8()` + `sha256`，第二趟又 `readChars()` + `readUtf8()` + `sha256` 去查第一趟刚建的表。
  `ProtectedString.readUtf8()/readChars()` 每次都是一次真实 JCE 解密（每次新建 `Cipher`）。
  ⇒ 每条目 3 次解密 + 2 次哈希，可合并为 1 次解密 + 1 次哈希。
- **整改方向**：第一趟把 `hashHex` 存入 `Map<entryId, String>` 供第二趟复用（或合并为单趟：先计数再产出 REUSED 条目）；
  顺带把 `entry.title` / `entry.userName` 在每条目的多个分支里重复读取改为每条目读一次存局部变量。
- **验收标准**：新增用例断言同一条目在一次扫描内解密次数（读 `readUtf8`/`readChars` 次数）不高于 2；
  各类风险等级（EXPIRED / WEAK / REUSED 等）判定结果与现状逐项一致。
- **核实时间点与方式**：2026-09-17 主控直读 `HealthCheckEngine.kt:46-124` 核实。
- **风险提示**：口令明文中间量必须继续在 `finally` 中清零（`passChars` / `passBytes`），合并趟次不得引入新的长期持有。

**本批实现**：

1. **第一趟按条目 id 留档哈希**：新增 `passwordHashByEntryId: MutableMap<String, String>`
   （键为 `entry.id.toHexString()`，值即本趟已算出的 `hashHex`），第二趟直接取用
   `passwordHashByEntryId[id].orEmpty()`，**删除**第二趟的 `HashUtil.sha256(passBytes)` 调用。
   ⇒ 同一条口令在一次扫描内的哈希次数由 **2 → 1**、解密次数由 **3 → 2**。
   两趟「取哈希」的前置条件（`length > 0` 且 `passBytes.isNotEmpty()`）逐字相同，故复用必然命中。
2. **明文中间量的清零语义保持不变**：第二趟仍在 `finally` 中 `Arrays.fill(passChars, '0')` 与
   `Arrays.fill(passBytes, 0)`；第一趟仍在 `finally` 中清零 `passBytes`。未引入任何跨条目持有。

**刻意不做（两处，各有理由）**：

- **不把 `passLength` 改为 `ProtectedString.length`**：`readChars()` 仍留在第二趟。理由：
  `length` 返回的是**密文 = 明文长度（字节）**（`ProtectedString.kt:79-84`，CTR 无填充），
  而现有实现用的是 `passChars.size`（**字符**数）并写进用户可见的文案
  「密码过弱（长度: N…）」。改用 `length` 会让非 ASCII 口令显示**字节数**（如 6 个汉字显示 18），
  属**用户可见的语义变更**，本批不做（要省这一次解密须先定文案口径）。
- **不做 `entry.title` / `entry.userName` 的「每条目读一次」**：这两个 getter 每次访问都是一次
  `readString()`（解密 + `String` 物化），但**只出现在「已判定有问题」的分支内**——对绝大多数
  「无问题」条目，把它们提到循环开头会**凭空新增 2 次解密**（把优化做成回归）。
  等价且无额外分配的做法要求把「先判定、后统一构造 issue」重构一遍（涉及 `continue` 分支与
  issue 顺序），对一条 P3 项的回归面而言不划算；如日后要做，须以「判定与构造分离」为形，
  并保证 issue 产出顺序（EXPIRED → WEAK → REUSED）不变。

**行为面依据**：`database/src/test/java/com/keepasskey/database/HealthCheckEngineTest.kt`（5 例），
其中 `测试弱密码与重复密码识别` **直接覆盖 REUSED 路径**（即本批改动的取哈希方式），
另有 EXPIRED / 常见弱口令 / 模式化弱口令 / 强口令不误判四例为对照。

### 1.2 `ISSUE-P3-169` 内存驻留加密每次访问新建 `Cipher` / `Mac`

**原条目**（原样收录）：

- **背景**：`core/.../security/InMemoryCipher.kt:103`（`seal`）与 `:119`（`unseal`）每次调用都
  `Cipher.getInstance` + `init`，`hmacSha256` 另各来一次 `Mac.getInstance`；触发面为
  `ProtectedString.kt:42`（构造即 seal）与 `:177-183`（每次读取即 unseal）。
  装载 1000 条目库 ⇒ 至少 1000 次两套 provider 查找 + 1000 次 HMAC，其中等值标签多数**从未被比较过**。
- **整改方向**：① 按线程持有 `Cipher` / `Mac`（`init` 仍按 IV/方向重做），消除每次的 provider 查找；
  ② `seal` 的等值标签改**惰性计算**（首次 `equals` / `hashCode` 时才算）。
- **验收标准**：同实例内 `Cipher.getInstance` / `Mac.getInstance` 调用次数与「字段数」解耦（调用计数断言）；
  等值语义与常时比较（`tagsEqual` 走 `MessageDigest.isEqual`）不变；既有 `ProtectedString` 全集用例绿。
- **核实时间点与方式**：2026-09-17 主控直读 `InMemoryCipher.kt:86-131` 核实。
- **风险提示**：`ISSUE-P3-153` 已指出「真正的浪费是每次新建 `Mac`/`MessageDigest`」，本条是其**具体点位与频率**；
  改动不得把 `Cipher` 跨线程共享（`Cipher` 非线程安全），也不得改变「密钥流绝不复用」的 IV 语义。

**本批实现（①）**：新增 `private val sealCiphers = ThreadLocal.withInitial { Cipher.getInstance(TRANSFORMATION) }`
与 `private val eqMacs = ThreadLocal.withInitial { Mac.getInstance(MAC_ALGORITHM) }`；
`seal` / `unseal` 改用 `sealCiphers.get()`、`hmacSha256` 改用 `eqMacs.get()`。
**取 `ThreadLocal` 而非共享单例**：`Cipher` 与 `Mac` 均非线程安全（本条风险提示已写明不得跨线程共享）。
`init` 仍按 IV / 方向 / 密钥逐次重做（必要开销）；每次 `seal` 仍生成**全新随机 IV**，密钥流复用语义未变。
两者均声明在 `init { }` **之前**（Kotlin object 的属性初始化按声明顺序执行，`init` 块会经
`hmacSha256` 触达 `eqMacs`）——顺序错误会在对象初始化期 NPE。

**不扩大秘密驻留面的论证（须与 §121 的相反结论区分）**：复用实例会持有 `SecretKeySpec`
（`encKey` / `eqKey` 的副本），而这两把子密钥**本就在本对象字段里随进程存活**
（类 KDoc 的 `ISSUE-P2-06` 评估结论：不轮换、不擦除——否则未被会话树覆盖的存活实例的旧密文
将永久不可解密）⇒ 本处缓存**不引入新的驻留面**。这与 `OtpEngine` 的 `Mac` 复用被判定**不实施**
（`已知工程限界.md` §9）是不同情形：那里缓存的密钥是**每个条目的种子**，复用会让调用方
`fill(0)`「自己那份即唯一副本」的前提失效。

**② 判定不可实施（对条目 AC 的实质修正）**：AC 原文要求「等值标签改惰性计算」。
读实现后确认**不可能在不扩大明文驻留面的前提下实现**——惰性算标签意味着必须在首次
`equals` / `hashCode` 之前**保留明文**（或明文副本）以供后来计算 HMAC，而本类的全部设计目的
正是「堆中不驻留明文」。若改为「先算密文、标签按需从密文反推」则等于放弃等值语义的正确性。
⇒ 该项**不实施**（属「条目 AC 与实现原理冲突」，非「未完成」）。

**行为面依据**：`core/src/test/java/com/keepasskey/core/security/ProtectedStringMemoryEncryptionTest.kt`（12 例），
覆盖密封产物 ≠ 明文且长度保持 / 密封解封往返一致 / 相同明文等值标签一致且密文随机化 /
不同明文不同标签与随机 IV / 读取路径往返 / 相等性经标签保持 / 不同内容不相等 / 保护标志不同不相等 /
`clear` 后读取被硬拒绝 / 清零后互不相等 / 空值与非保护值行为不变 / `useUtf8` 自动清零。

## 3. 边界如实声明（不得外推）

1. **无任何性能实测**：判据是「不再产生某类工作」的**结构性**断言与行为等价用例；
   「哈希 2 → 1、解密 3 → 2」是**源码级计数**（同一函数体内的调用点），非运行期计数。
2. **本批未把解密次数降到 1**：第二趟仍有一次 `readChars()` + 一次 `readUtf8()`（两次解密）。
   原 AC 写「可合并为 1 次解密 + 1 次哈希」**不准确**——只降到 2 次，且剩下的一次
   `readChars()` 是保持「长度为字符数」文案口径的代价（见 1.1 的刻意不做第 1 条）。
3. **`ThreadLocal` 的代价已声明**：长生命周期线程池下每线程各持有一份 `Cipher` / `Mac` 实例
   （不随线程回收自然释放），两份都是同一进程级密钥的副本 ⇒ 无新增秘密面，但有常量内存占用。
   **不得**读作「进程级只创建一次」。
4. **守卫是源码文本断言**：它锁的是「接线未被改回」，**不是**运行期调用计数；
   且 `assertEquals(1, …)` 这类断言对「把调用点搬进另一个辅助函数」的实现无鉴别力。
5. **`ISSUE-P3-166` 的 title/userName 重复读取未处理**（理由见 1.1），
   即「每条目最多 6 次 title/userName 解密」在有问题的条目上**仍然存在**。
6. **`ISSUE-P3-169` ② 未实施**（原理冲突，见 1.2）⇒ 装载 1000 条目库仍有 1000 次
   等值标签 HMAC 计算本身（省掉的只是 1000 次 `Mac.getInstance`）。

## 4. 过程缺陷与留痕

1. **对条目 AC 的第三处实质修正**：本批开工读实现后发现 `ISSUE-P3-169` ②「惰性计算等值标签」
   与「堆中不驻留明文」这一设计目的**直接冲突**（§121 的 `Mac` 复用、§122 的「整比 `times`」为前两处）。
   三处均为「AC 写在读实现之前」，**处置一致**：读实现 → 就地判定 → 在批次文档与 KDoc 写明依据。
2. **一处自查**：`ThreadLocal` 字段的**声明位置**必须早于 `init { }`（后者经 `hmacSha256` 触达 `eqMacs`）。
   写成「函数体引用后来的属性」在 Kotlin 里合法、运行时才会 NPE，故显式放在 `eqKey` 之后、
   `init` 之前，并就地留痕。
3. **原 AC 的一处不准确已更正**（不改原 AC 事实、只补口径）：见 3.2——「合并为 1 次解密」不成立。
