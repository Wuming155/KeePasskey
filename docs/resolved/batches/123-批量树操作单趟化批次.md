## 1. 逐条整改内容与证据

### 1.1 `ISSUE-P3-160` 批量条目变更按 id 逐次重走整棵树（`O(K × 节点数)`）

**原条目**（自 `ACTIVE_ISSUES.md` 原样收录）：

- **背景**：`database/.../session/SessionContentMutations.kt:137`（`batchMoveEntries`）与 `:162`（`batchDeleteEntries`）
  对**每个 id** 调一次 `SessionTreeEditor.removeEntry` / `updateOrAddEntry`，而 `SessionTreeEditor.kt:108` 的
  `removeEntry` 无条件 `group.subgroups.map { … }` 递归整棵树（命中也不提前退出）并每次新建列表。
  调用面：`app/.../data/repository/RecycleBinCoordinator.kt:172` 交接回收站全部条目、
  `VaultListActionController.kt:114/128` 传多选集合 ⇒ 回收站 100 条 + 200 组时约 100 次全树遍历 + 约 2 万次临时 List 分配，
  且全程持会话 Mutex（锁持有时间被放大 K 倍）。
- **整改方向**：新增按 id 集合**单趟剪枝**的 `removeEntries(Set<KdbxUuid>)`；`batchMoveEntries` 改为
  「一次批量移除 → 逐条路径复制插入」。
- **验收标准**：批量删除 / 移动的树变换结果与逐条实现等价（含未命中分支的实例身份复用）；回收站清空路径回归绿。
- **核实时间点与方式**：2026-09-17 读 `SessionContentMutations.kt:120-173` 与 `SessionTreeEditor.kt:98-122` 实际内容核实。
- **风险提示**：须保全 `ISSUE-P2-06` 的「删除路径不擦除」修正与 `ISSUE-P3-118` 的路径复制契约。

**本批实现**：

1. `SessionTreeEditor` 新增 `fun removeEntries(group: KdbxGroup, entryIds: Set<KdbxUuid>): KdbxGroup`——
   按 id 集合**单趟**剪枝整棵树（每个节点恰好访问一次），列表**惰性分配**（仅在确需替换时
   `toMutableList()`），未命中子树按**同一实例**返回；空集合直接返回同一实例。
2. `SessionTreeEditor.removeEntry`（单条）同步去掉「无条件 `subgroups.map { … }`」——
   改为「仅当子树确实变化时才新建列表」。**刻意不引入**「命中即停止下降」的提前退出：
   那属另一处语义变化（`ISSUE-P3-118` 已就分组首命中留痕过同类假设），在 UUID 唯一性前提下收益有限，
   故本批只消除分配、不变更扫描范围。
3. `SessionContentMutations.batchDeleteEntries`：**单趟** `removeEntries(currentDb.rootGroup, entryIds)`
   取代 `for (id in entryIds) removeEntry(...)`；仍无条件写回新库实例并置 `DIRTY`
   （与逐条实现逐字一致，**含「id 不存在」的情形**）。
4. `SessionContentMutations.batchMoveEntries`：一次 `removeEntries(currentDb.rootGroup, entryIds)`
   取代对 `entriesToMove` 逐个 `removeEntry`（被移除集合与逐条实现相同：`entriesToMove` 的 id ⊆ `entryIds`）；
   插入阶段保持「逐条路径复制插入」（§118 后已是 O(深度)/条），**未动**。

**依据（沿用既有契约）**：删除路径的擦除口径不变（`ISSUE-P2-06`：无替换树 ⇒ 禁止身份擦除）；
路径复制契约不变（`ISSUE-P3-118`：未命中即复用同一实例）。

### 1.2 `ISSUE-P3-161` 冲突决策逐条重建整棵分组树（`O(冲突数 × 分组数)`）

**原条目**（原样收录）：

- **背景**：`app/.../sync/SyncConflictController.kt:107` 对每条冲突调 `applyResolvedEntryToGroup`，
  而 `:332` 的实现对**每一层**都执行 `group.subgroups.map { … }` + `group.copy(subgroups = …)`——
  目标条目不在该子树时也照旧复制 ⇒ 每条冲突一次全树重建。5000 组 + 100 条冲突约 50 万次 `copy`，
  在 `Dispatchers.Default` 且持锁执行。
- **整改方向**：先按 `parentGroupId` `groupBy` 一次，单趟递归中按当前组 id 取对应条目列表替换，降为 `O(G + k)`。
- **验收标准**：冲突解决结果与逐条实现等价；新增用例断言「仅目标分组链上的节点被复制」。
- **核实时间点与方式**：2026-09-17 读 `SyncConflictController.kt:95-124` 与 `:332-349` 实际内容核实。

**本批实现**：

1. `resolveConflicts` 的决策循环改为**先收集后落树**：逐条冲突求出 `resolvedEntries`（字段级优先逻辑未动），
   按目标父组 id 归入 `resolvedByParent: MutableMap<KdbxUuid, MutableList<KdbxEntry>>`（`getOrPut` 保持**冲突原顺序**），
   收集完成后**单趟**调用新函数。
   - 父组缺失（`parentGroupId == null`）落**根组**：与原实现的 `entry.parentGroupId ?: group.id`
     在顶层调用时即根组同语义。
2. 新增 `applyResolvedEntriesToGroup(group, byParent)` 取代逐条的 `applyResolvedEntryToGroup(...)`：
   单趟递归到底，**仅复制确实含目标的分组**（未命中子树复用同一实例）；
   同组内条目按收集顺序「找到即替换、找不到即追加」，与逐条实现一致。
3. 冗余的全限定名 `com.keepasskey.core.model.KdbxGroup` 收敛为已导入的短名（同批顺带清理）。

**等价性依据**：
- 行为面由既有端到端冲突用例 `app/src/test/java/com/keepasskey/app/sync/SyncCoordinatorTest.kt`
  与 `sync/src/test/java/com/keepasskey/sync/KdbxMergerTest.kt` 承担（本批全绿）；
- 结构面由接线守卫锁定（`AlgoHotPathGuardsTest` 新增 1 例：必须存在 `applyResolvedEntriesToGroup(`
  且**不得**残留 `applyResolvedEntryToGroup(`）。

## 3. 边界如实声明（不得外推）

1. **无任何性能实测**：判据是「不再为每个 id 各走一次整棵树、不再为沿途每个分组分配列表」的**结构性**结论
   与契约用例，**不得**宣称百分比收益，也不得据此推断真机表现。O(K × 节点数) → O(节点数) 的结论
   来自源码结构（每个节点访问一次），非运行期计数。
2. **`ISSUE-P3-161` 无新增行为用例**：新函数是 `SyncConflictController` 的 private 成员，该类依赖
   引擎 / 缓存 / 会话 / 字符串等多重注入，宿主侧难以单独构造 ⇒ 等价性主要依赖**既有**冲突端到端用例
   与新加的**结构守卫**；**不得**读作「已用专门用例逐分支验证」。
3. **`removeEntry` 的扫描范围未变**：本批只消除「无条件分配列表」，**没有**加「命中即停止下降」的提前退出
   （避免在批量化之上再叠一处语义变化）。
4. **`batchDeleteEntries` 仍无条件置 `DIRTY` 并写回新库实例**（即使 id 全不存在）——与逐条实现逐字一致，
   本批**刻意不**顺手改成「零变化则不置 DIRTY」（那会变更状态机语义）。
5. **批量移动的插入阶段未改**：`updateOrAddEntry` 仍是逐条路径复制（§118 后为 O(深度)/条），
   本批只收敛「移除阶段」的 O(K × 节点数)。
6. **`ISSUE-P3-161` 的落位面未变**：`parentGroupId` 指向的分组在树中不存在时，条目同样**不落位**（与逐条实现一致，
   属既有行为而非本批引入）。

## 4. 过程缺陷与留痕

1. **编辑期一次 `old_string` 与源码不符而失败**：我把 `SyncConflictController` 决策循环里的
   「用户钦点**的**字段」漏抄一个「的」，`Edit` 直接报 `old_string not found`；
   重新读取该区域后逐字修正并成功。**未进入构建**（编译/测试从未见到该中间态），据实留痕——
   这是「改前必读、不凭记忆抄」的又一实例。
2. **用例设计自查**：`render()` 递归渲染树结构以做等价比较（而非逐字段断言），
   刻意同时覆盖「分组层级」与「各分组条目顺序」两个维度；`sampleTree()` 的三层结构
   （根 / 二层 / 叶子）用于覆盖深层删除与兄弟保留。
3. **P3-161 的首版方案曾考虑「让 `applyResolvedEntryToGroup` 接受整批」**：即改签名而不改调用点结构；
   最终选择「调用点先收集成表 + 新函数单趟落树」，因为前者仍会保留「每条各走一次」的外层循环，
   不能把复杂度降到 O(G + k)。
