## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：① `app/.../autofill/AutofillOriginResolver.kt:41` 与 `AutofillDatasetBuilders.kt:160`
  对**同一包名**各算一次调用方证书摘要（每次含 `getPackageInfo` + 逐签名者 `MessageDigest.getInstance` +
  32~96 次 `"%02X".format`）；② `app/.../autofill/KeystoreHmacFieldSignatureSource.kt:53` 每次字段屏蔽检查
  走 **3 段 Keystore IPC**（`containsAlias` + `getEntry` + `Mac.init`，均为 TEE/daemon 往返），
  而一次请求至多 2 个角色 ⇒ 2 次三段式 IPC；③ `AutofillFieldSignature.kt:75` 与 `UnlockThrottleIntegrity.kt:39`
  以 `"%02x".format` 逐字节生成 hex（后者还经 `ByteArray.take(16)` 产生 **16 个装箱 `Byte`**）。
  同仓 `PasskeyKeyCodec.scalarToHexChars` 已有查表范式。
- **整改方向**：① 摘要算一次作参数下传（或按包名做请求级 / 短 TTL 记忆化）；② 缓存 Keystore `SecretKey` 句柄，
  同请求内 `Mac` 复用（`doFinal` 后自动复位）；③ hex 改查表（预置 `CharArray`），去掉 `take` 装箱。
- **验收标准**：一次填充请求内证书摘要计算次数为 1、Keystore IPC 段数下降（调用计数断言）；
  屏蔽判定的**签名原文与结果逐字节不变**；锁定态 fail-safe 语义不变。
- **核实时间点与方式**：2026-09-17 读 `AutofillOriginResolver.kt:30-105`、`AutofillDatasetBuilders.kt:145-165`、
  `KeystoreHmacFieldSignatureSource.kt:45-70`、`AutofillFieldSignature.kt:70-95`、`UnlockThrottleIntegrity.kt:35-45` 核实。
- **风险提示**：`UnlockThrottleIntegrity` 的别名派生若改算法会使**存量存在性标记失配**（等于节流复位），
  故只做「去装箱 + 查表 + 复用 digest」三项纯等价替换；Keystore 句柄缓存必须在失效时重取（`§80` 的
  `Mac.getInstance(..., "AndroidKeyStore")` 真机失效教训）。

## 2. 本批实现

### 2.1 证书摘要只算一次（对应 AC ①）

- `AutofillOriginResolver.resolveUsableWebDomain` 增加**可选参数**
  `certDigests: CallerCertDigests = callingAppCertDigests(callingPackage)`；默认值使既有调用点
  （确认页 / 选择器等）**零改动**，并在函数内直接使用该参数（删掉内部那次读取）。
- `AutofillDatasetBuilders.appendUnlockedDatasets` 改为**先读一次** `callerCertDigests`，
  再把它同时传给归属解析与 `AndroidPackageBindingPolicy.isPackageDimensionAuthorized`
  （原来后者自己再读一次）。
- **顺带的一致性收益**：同一请求内两处判定现在恒用**同一份摘要快照**。原实现两次读取之间若发生
  调用方身份变化（重装等不可观测的极端情形），两处会用不同摘要——新实现消除了这一分歧。
- **时序变化（如实留痕）**：摘要读取由「DAL 校验之后」提前到「之前」，即网络校验前多一次读取；
  单次请求内语义无变化。

### 2.2 Keystore 密钥句柄缓存（对应 AC ②）

- `KeystoreHmacFieldSignatureSource` 新增 `@Volatile private var cachedKeyEntry: KeyStore.SecretKeyEntry?`；
  `obtainMac()` 改为「缓存命中即用，缺失才走 `loadOrCreateKeyEntry()`（`containsAlias` → 必要时
  `generateKey` → `getEntry`）」，即 **2 段 Keystore IPC 从每次调用降为每进程首次一次**。
- `Mac` **仍每次新建**（`javax.crypto.Mac` 非线程安全，且 `Mac.getInstance` 是纯 JVM 侧开销、不走 IPC）
  ⇒ **「同请求内 Mac 复用」这一半判定不做**：它省不到 IPC，却要引入「谁持有 Mac」的并发约束。
- **失效面复核（安全前提）**：该别名 `com.keepasskey.autofill_field_signature` 全仓
  **无任何删除点**（2026-09-17 检索全仓 `deleteEntry` 确认：命中项全是库内条目 / 分组删除，与 Keystore 无关），
  故不存在「外部删键后仍用旧句柄」的失效面；`Mac.init` 失败时**清空缓存并返回 null**（fail-closed），
  下次调用按原路径重建一次，覆盖密钥被系统侧失效的极端情形。
- **秘密面论证**：`SecretKeyEntry` 是 TEE 侧**不可导出**密钥的**引用**，缓存它不落任何密钥材料，
  也不改变「密钥永不导出」的边界（属「引用驻留」而非明文驻留）。
- **沿用 `§80` 教训**：仍以默认 provider 取 `Mac`、把 `AndroidKeyStore` 的 `SecretKey` 交给 `init`
  （`Mac.getInstance(..., "AndroidKeyStore")` 在真机必抛，`§80` 已实测）。

### 2.3 hex 改查表（对应 AC ③）

- `AutofillFieldSignature.toHexString` 与 `AutofillOriginResolver.callingAppCertDigests` 的
  `"%02x"` / `"%02X"`.format 逐字节调用改为**查表**（`CharArray` + 位运算）；后者同时把
  `MessageDigest` 提到循环外**复用一次**（`digest()` 自带复位），取代「每个签名者各 `getInstance` 一次」。
- 大小写口径逐字保持：字段签名**小写**、证书摘要**大写**（后者有既有对外口径依赖）。
- **`UnlockThrottleIntegrity` 的同族项本批不做**（条目风险提示已写明）：其别名派生若改算法会使
  **存量存在性标记失配**（等于节流复位），要做得先定「保值替换」方案，属独立条目范畴。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：「摘要 2 次 → 1 次」「2 段 IPC 从每次调用 → 每进程一次」「每字节 format → 查表」
   均为**源码级调用点与结构**结论，**不得**宣称百分比收益，也不得推断真机填充时延。
2. **未做调用计数断言**：`callingAppCertDigests` / Keystore IPC 的调用次数在宿主侧不可观测
   （需真机 Keystore），等价性靠**行为用例**与**源码文本守卫**承担；守卫对「把调用点搬进辅助函数」无鉴别力。
3. **Keystore 句柄缓存的 IPC 收益是「每进程一次」而非「永久一次」**：进程重启后缓存为空，
   仍需一次 `containsAlias` + `getEntry`；`obtainMac` 仍是 `@Synchronized`（并发调用会串行）。
4. **`Mac` 仍每次新建**（见 2.2），故「同请求内 Mac 复用」这一半**未做**。
5. **AC ① 未做「按包名短 TTL 记忆化」**：本批只在**同一次请求内**去重（跨请求的记忆化需要
   缓存失效口径与跨进程一致性论证，属另行裁决）。
6. **`UnlockThrottleIntegrity` 的同族 hex 与装箱未做**（理由见 2.3）⇒ 该路径仍保留
   `ByteArray.take(16)` 的 16 个 `Byte` 装箱与逐字节 `format`。
7. **锁定态 fail-safe 语义未变**：`hmacSha256` 任何失败仍返回 null、调用方按密钥不可用处理；
   本批未改任何 fail-closed 分支。

## 5. 过程缺陷与留痕

1. **本批无编译 / 断言失败**（首次全量即绿；前两批各有一次 `old_string` 不匹配，本批四文件编辑一次成功）。
2. **一处前置检索充当安全前提**（见 2.2 的失效面复核）：若不做该检索就缓存句柄，等于把一个
   「外部删键后旧句柄仍有效」的假设写进产品；故该检索结论（全仓无删除点）与日期一并写进就地 KDoc，
   供后人复核。
