## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：`database/.../fieldref/FieldReferenceEngine.kt:151` 在 `REF_REGEX.replace` 的回调体内执行
  `root.allEntries().firstOrNull { … }`，而 `allEntries()` 每次现场递归展平整棵树并分配新 List，
  且该表达式位于**递归展开链**上（每层深度各展平一次）⇒ `O(引用数 × 深度 × 条目数)` 次列表物化。
  附带成本：检索字段为 `P` 时逐条目 `readString()`（`:186`，每次一次 JCE 解密），为 `UUID` 时逐条目 `toHexString()`。
- **整改方向**：`resolveWith` 入口按需构建一次索引（`Map<RefField, Map<String, KdbxEntry>>` 或
  `associateBy { it.id }`）随递归下传，把每次查找降为 O(1)，并让按口令检索不再需要逐条解密。
- **验收标准**：同一文本的解析结果不变（含未命中保留原文、掩码占位、深度上限、环状引用）；
  新增用例断言「一次解析内 `allEntries()` 至多调用一次」；按 `P` 检索不再对未命中条目解密。
- **核实时间点与方式**：2026-09-17 读 `FieldReferenceEngine.kt:125-191` 实际内容核实。
- **风险提示**：该引擎位于 `P0-08` 消费点白名单语义之上，**不得**在索引化过程中改变「受保护值不物化」的判定路径。

## 2. 本批实现

新增私有嵌套类 `RefIndex(root, valueOf)`，在 `resolveWith` 入口建**一次**并沿递归全程共享；
`resolveInternal` 的 `root: KdbxGroup` 形参改为 `index: RefIndex`：

- **条目树只展平一次**，且**惰性**（`by lazy { root.allEntries() }`）——文本不含引用时
  `resolveWith` 已短路，根本不触发；只在真的遇到引用时展平一次。
- **按检索字段分桶的索引同样惰性**（`byField.getOrPut(field) { … }`）。
  **这一点是对 AC 的一处刻意收窄**：AC 建议「`Map<RefField, Map<String, KdbxEntry>>`」，
  若照此**一次性建全部字段的索引**，就会把**全库口令**都 `readString()` 解密一遍
  （无论文本里有没有 `P@` 引用）——那是**反向优化**，也违背 AC 自己的「按 `P` 检索不再对未命中条目解密」。
  现实现只在**实际被引用到的字段**上建索引 ⇒ 无人引用口令时**零口令解密**。
- **查找语义逐字等价**：键用 `TreeMap(String.CASE_INSENSITIVE_ORDER)`。
  **为何不用 `lowercase()` 归一化做键**：`HashMap` + `lowercase` 的等价类与 `equalsIgnoreCase`
  **不同**——例如希腊语词尾 sigma（`'ς'` vs `'Σ'`，`equalsIgnoreCase` 判等而 `lowercase` 不等），
  会造成「原本命中的引用变为未命中」的静默漂移；`CASE_INSENSITIVE_ORDER` 与 `equalsIgnoreCase`
  同用逐字符大写→小写折叠，等价类一致。该权衡由用例显式锁定（见 §3 第 3 例）。
- **同值取文档序首个**：`if (!index.containsKey(value)) index[value] = entry`——
  `TreeMap` 的 `containsKey` 走同一比较器，故同值只保留先插入者，与原 `firstOrNull` 的文档序语义一致。
- 复杂度：由 `O(引用数 × 深度 × 条目数)` 次**展平**（每次一遍递归遍历 + 一个 `List` 分配）
  降为 `O(条目数 · log 条目数)` 的**一次**索引构建（仅对被引用到的字段各一次）+ 每次查找 `O(log 条目数)`。
- **保护值判定路径未动**：`isProtected` / 掩码占位 / `ResolveMode` 分支逐字保留（条目「风险提示」的硬约束），
  索引只替换「如何找到目标条目」，不参与任何放行或物化判定。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：复杂度由「`O(引用数 × 深度 × 条目数)` 次展平」降为「一次索引构建 + 每次查找
   `O(log n)`」是**源码结构**结论，**不得**宣称百分比收益。
2. **AC 的「一次解析内 `allEntries()` 至多调用一次」未做运行期计数**：`KdbxGroup` 是 `data class`（final），
   宿主侧无法在不改生产代码的前提下为 `allEntries()` 计数 ⇒ 以**源码文本守卫**（全文件仅一处、且在 `by lazy` 内）
   替代，**不得**读作「已用运行期计数证明」。
3. **索引只覆盖「按字段值检索目标」这一步**：`valueOf` 的取值本身（含受保护字段的 `readString()`）
   与递归展开的深度控制**未变**；`UUID` 检索仍会为每条目 `toHexString()`（构建该字段索引时各一次）。
4. **索引是「每次解析调用」而不是「跨调用缓存」**：同一条目文本在详情页与列表中分别解析时
   仍各自建一次索引（跨调用缓存需要失效口径，属另行裁决）。
5. **`TreeMap` 的代价已如实计入**：构建为 `O(n log n)`（含逐字符大小写折叠的比较），
   查找为 `O(log n)` 而非 `O(1)`；换取的是与 `equalsIgnoreCase` **完全一致**的等价类
   （见 §2 的 sigma 取舍）。若日后确认检索文本恒为 ASCII，可改回 `HashMap` + `lowercase` 并删除该用例。
6. **未做设备侧验证**（`FieldReferenceEngineDeviceTest` 未运行）；本批未改正则、未改掩码语义
   ⇒ 与 ICU 兼容性（`ISSUE-P0-04`）无交集，但**不得**据此声称「设备侧已确认」。
