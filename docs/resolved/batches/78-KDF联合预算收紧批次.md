## §78 KDF 联合预算收紧批次（2026-09-15）：ISSUE-P2-49（AC② 收口）

> **本批次缘起**：`ISSUE-P2-49`（复核**升格 P1**）的 AC①/AC③ 已于 §48 完成，**AC② 长期未闭环**——
> 复核定版确认「协程 `withTimeout` 对**阻塞式原生派生**无效」（只在返回后的挂起点生效），
> 故属「无效纸面加固」；而 AC② 真正要解决的可用性 DoS 量级此前无从判断。
> §76 已在真机分路径实测出**实测速率**，本批据此把联合预算由 `2^40` 收紧为 **`2^33`** 并收口 AC②。

### 78.1 交付清单

| 子项 | 内容 |
|---|---|
| 预算收紧 | `KdbxKdfParameterCodec.ARGON2_MAX_TOTAL_WORK`：`2^40` → **`2^33`**（`2^33` 由 §76 真机实测速率锚定；`KdbxHeader.validateArgon2Bounds` 委托同一实现，自动同步） |
| 可见性调整 | 该常量由 `private` 改为 **`internal`**——设备侧实测用例需读它构造边界样本，避免在测试里复制字面量造成两处漂移 |
| 边界双向锁 | `KdfParametersBoundsTest`：预算内合法配置改为「`64 MiB × 128 = 2^33` 恰好通过」，越界档改为「`64 MiB × 129` 拒绝」，并**新增**「原 `2^40` 档（`64 MiB × 16384`）在收紧后必须被拒」——政策变更双向锁定 |
| 镜像测试同步 | `Argon2KdfBoundsMirrorTest`：原「迭代取 `2^24` 仍界内」不再是界内配置（`2^24 × 8192 = 2^37 > 2^33`），改用恰好落在新预算边界上的 `I = 2^20` |
| 设备侧实测 | `KdfWallClockDeviceTest` 改为**读取常量**（不再硬编码 `2^40`），并**新增 AES-KDF 封顶轮数的墙钟实测**（此前完全缺失） |

### 78.2 实测证据（arm64 真机 Redmi 4X / LineageOS / Android 17 / API 37 / `maxHeap` 192 MiB）

| 观测项 | 实测 |
|---|---|
| 联合预算（新） | `8 589 934 592` 字节·轮 = `2^33` |
| **最坏合法配置的墙钟（按实测吞吐换算）** | **≈40 s**（`0.011 h`）——原 `2^40` 为 **≈1.39–1.44 小时** |
| 最坏合法配置是否仍被接受 | **是**（`worstCaseWithinBudget_acceptedByCodec=true`，即收紧的是**上界数值**而非拒绝该档） |
| `M = 堆/2` 时的最大迭代数 | `85`（原为 `10 922`） |
| 默认配置（`64 MiB × I=2 × P=2`） | 0.619 s |
| 重载（`96 MiB × I=8`） | 2.471 s |
| 实测吞吐 | `2.169×10⁸` 字节·轮/秒 |
| **AES-KDF `R = 2^20`** | **0.137 s** ⇒ 速率 `7.638×10⁶` 轮/秒 |
| **AES-KDF 封顶 `R = 2^28`（按实测速率换算）** | **≈35 s** |
| AES-KDF 本仓默认 `R = 6×10⁶` | ≈0.79 s |

⇒ **两个 KDF 族的最坏墙钟已收敛到同一量级**（Argon2 ≈40 s / AES-KDF ≈35 s），
故 **AES-KDF 的 `R ≤ 2^28` 封顶无需调整**（其量级已与收紧后的 Argon2 预算相当）。

### 78.3 覆盖性核对（AC④「不误拒合法库」）

1. 本仓默认 `64 MiB × 2 = 2^27` ✓（余量 64 倍）；
2. 真机**有效内存上界** `M ≤ maxHeap/2`（§76 实测 96 MiB）叠加本仓 `KdfBenchmark` 自荐的 `I ≤ 20`
   ⇒ 本机可达的最大配置 ≈`2^32.3 < 2^33` ✓；
3. 官方**桌面**偏执配置（如 `1 GiB × 10 = 2^33.3`）会超出本预算，但其 `M = 1 GiB`
   **在本仓任何设备上都先被 `M ≤ maxHeap/2` 拒绝**（Android 非 `largeHeap` 应用的堆上限远小于 2 GiB）
   ⇒ 本预算**不新增**任何「本可解锁却被拒」的情形。
   **如实声明的例外**：若某设备的应用堆上限 ≥2 GiB（未观测到），该档将由联合预算拒绝而非堆门槛拒绝——
   错误信息为明确的「工作量越界」而非「损坏文件」，属可诊断的 fail-closed。

### 78.4 残余与边界（如实登记，同步写入 `AGENTS.md` §6）

1. **无中途取消**：本次以「工作量上界 + 实测速率锚定」把最坏耗时压到 ≈40 s（本机实测速率下），
   但**仍不支持派生中途取消**（RustCrypto 的 `hash_password_into_with_memory` 不暴露逐 pass 回调，
   实现可取消派生需自写填充循环）。**解除条件**：如需把最坏耗时进一步压到秒级或支持取消，
   须在原生内核引入**可取消派生**（pass 之间检查取消标志）。
2. **换算而非实跑**：`≈40 s` 由**实测吞吐换算**得出（用例日志标注 `extrapolated_`），
   未实跑该最坏配置（会让设备满载 40 s 无关紧要，但为保持用例时长可控而未跑）。

### 78.5 过程缺陷（如实留痕）

   而本仓 `settings.gradle.kts` 显式设置 `RepositoriesMode.FAIL_ON_PROJECT_REPOS`，两者直接冲突。
   **处置**：本批所有验证均在「临时移开该 init 脚本 → 跑验证 → **finally 中恢复**」下完成，
   并在每步输出中打印恢复结果（`init.gradle 恢复=True`）——**未修改仓库任何配置文件**。
   ⇒ **给环境所有者的建议**：init 脚本应改用 `beforeSettings` / `settingsEvaluated` 向
   **settings 级**仓库注入（或删除 `FAIL_ON_PROJECT_REPOS`），否则任何声明该模式的工程都会构建失败。
2. **同一工作树上的并发操作已第二次造成影响**（前一次见 §75.5 的外部提交 `5371a0d`）：
   ⇒ 纪律：**在同一工作树上做长时间验证前，先确认没有并发构建 / 提交**；本次以
