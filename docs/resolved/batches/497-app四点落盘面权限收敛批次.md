## 497.3 整改

### ① 原语下沉 core（AC① 前置：口径单一真相源）

**裁决：② 下沉 `core` 共享**（未选 ① app 侧本地等价实现）。理由：本条缺陷的**根因即「口径漂移」**——
`sync` 自 `ISSUE-P1-07`/`P3-202` 起自声明 0600/0700，而 `app` 四点各自裸写。若在 `app` 再复制一份
`FILE_OWNER_ONLY` / `DIRECTORY_OWNER_ONLY` 常量与唯一临时名 / 原子移动逻辑，等于**再造第二份可漂移的拷贝**，
与工程规则「同一数值多处出现必须收敛到单一常量」及本条整改意图相悖；而 `core` 被 `app`/`sync`/`database`
全员依赖，下沉**不破坏** `app → sync → core` 单向依赖（`sync → core` 本就存在）。

- **新增** `core/src/main/java/com/keepasskey/core/security/SecureFileWrite.kt`（`object`，纯 JVM 原语）：
  - `SUFFIX_TMP = ".tmp"`（通用后缀单一常量）；
  - `uniqueTmpFor(targetFile, suffix)`：`<目标名>.<UUID><后缀>`，与目标**同目录**（保证 rename 同文件系统）；
  - `openOwnerOnlyOutput(tmpFile)`：打开流即在**写入第一字节前**收敛 0600；
  - `writeSynced(tmpFile, bytes)`：写入 + `flush` + `fd.sync` + 收敛 0600；
  - `moveAtomically(tmpFile, targetFile): Boolean`：`renameTo` →（失败）`Files.move`（`ATOMIC_MOVE` →
    降级 `REPLACE_EXISTING`），成功后收敛目标 0600；`renameTo` 与两条 `Files.move` 均失败时按原语义抛
    `IOException`（不吞，保持与 sync 一致的上抛口径）；
  - `restrictToOwnerOnly(file, isDirectory)`：POSIX 精确置位（文件 0600 / 目录 0700）；非 POSIX 文件系统
    降级 `java.io` 尽力而为。
- **`SyncCacheFiles` 退化为薄委托**：`tmpFileFor` / `writeTmpSynced` / `moveAtomically` / `restrictToOwnerOnly`
  四项逐字委托 `SecureFileWrite`（`SUFFIX_TMP` 取值收敛到 `SecureFileWrite.SUFFIX_TMP`）；缓存域专有逻辑
  （`fileFor` 规范键定位、`deleteOrphanTmpFiles` 通配清理、`deleteChild` 有界重试删除）**留在 sync**。
  **行为与权限口径零变更**——`SyncCache` / `SyncCacheMaintenance` / `SyncRollbackGuard` 三个消费者逐字未改，
  `SyncCacheTest` 全绿可证。

### ② 四落盘点接入「唯一临时名 + 仅属主权限 + 原子交付」（AC①）

四点统一改用 `SecureFileWrite` 原语，固定名 → 唯一名，并对落地文件显式收敛 0600：

| 落盘点 | 临时名（整改前 → 后） | 权限收敛 | 失败清理 |
| --- | --- | --- | --- |
| `CloudVaultImporter.import` | `<name>.kdbx.importing` → `<目标名>.<UUID>.importing` | 打开流即 0600；目标经 `moveAtomically` 0600 | 只删自己的唯一名 tmp |
| `SyncRemoteVaultCopy.backupRemoteVaultCopy` | `<目标名>.backup` → `<目标名>.<UUID>.backup` | 同上 | 同上 |
| `VaultFileCopy.copyBeside` | `<目标名>.tmp` → `<目标名>.<UUID>.tmp` | 打开流即 0600；目标经 `moveAtomically` 0600 | 同上 |
| `KeyFileVaultCopyStore.save` | `<目标名>.tmp` → `<目标名>.<UUID>.tmp`；另 `dir` 收敛 0700 | 同上；**目录 0700**（本批唯一由 app 自建的落盘目录） | 同上 |

- 两点下载链（`CloudVaultImporter` / `SyncRemoteVaultCopy`）在下载完成后补 `flush()` + `fd.sync()`——原实现
  无 fsync，rename 交付前未强制落盘，属「原子写盘」纪律的既有缺口，本批一并补齐。
- 落地用原子 rename/move（`moveAtomically`，`renameTo` → `Files.move` 回退，绝不非原子 `copyTo`）；失败清理
  只 `delete()` **自己的**唯一名 tmp（唯一名使精确删除成立），彻底消除「失败路径删掉并发者正写的 tmp」。

### ③ 提交互斥（AC③）

  `§391` 行数分档闸门）：`busy: StateFlow<Boolean>` + `submit(submission)`。守卫在**协程之外同步置位**

## 497.5 如实声明

- **AC② 设备侧 stat 未取证（未执行）**：`SyncCacheAndroidRuntimeTest` 形态的「app 四点落盘文件 / 目录
  `stat` 实测 0600 / 0700」**未执行**。原因：本环境**禁跑设备侧 / 连接测试**（设备存有真实用户库，UTP 卸载
  应用即致数据永久丢失），且新增 `*/src/androidTest/**` 用例按测试资产纪律**必须真机实跑**方可入库——二者
  互斥。故本批**不新增** `androidTest`（含等价 stat 断言），该取证缺口登记
  [`docs/architecture/已知工程限界.md`](../../architecture/已知工程限界.md) **§43**，并在此**明确声明为「未执行」
  而非「已证」**：宿主全部断言只锁「唯一临时名 / 原子交付 / `restrictToOwnerOnly` 调用不抛」的结构性契约，
  **不构成**权限位真值证据（宿主 JVM 无法代表 Android `umask` 语境）。
- **方案取舍（复用 vs 本地实现）**：`SyncCacheFiles` 为 `internal` ⇒ 直接复用不通；最终选 **② 下沉 core**，
  使 0600 / 0700 权限位与唯一临时名**全仓单一真相源**（未选 ①「app 侧本地等价实现」——那会再造一份可漂移
  拷贝，与本条缺陷根因相悖）。代价：`sync` 的 `SyncCacheFiles` 改为薄委托、新增一个 core 公共类型；收益：
  不变量口径自洽，后续新增落盘点直接复用同一原语。
- **未采纳项**：① `CloudVaultImporter` / `SyncRemoteVaultCopy` 的**下载链上游**（`provider.download` 内部的
  `SyncDownloadLimits.copyBounded`）逐字未动；② 未对 `filesDir`（平台创建、平台保证 0700）另行收敛——
  本批只收敛**应用自建**的落盘目录（`KeyFileVaultCopyStore` 的 `keyfiles/`）；③ 未把 `file://` 等其他
  app 落盘点纳入本批（超出本条四点范围）。
- **真实缺陷（过程留痕）**：首版把 busy 守卫**直接内联**进 `DatabasePickerViewModel`，使该文件由 395 行增至
  410 行、越过 `tier2(400~500)` 阈值触发 `count_line_tiers` 红（预算 35 只紧不松、不得为新增大文件上调）。
  按仓内既有「薄控制器」范式拆出 `DatabasePickerImportController` 后 VM 回落至 394 行、门禁复绿——非缺陷，
  是「行数分档闸门按设计生效」的实证。
- **行号漂移（不成立面）**：条目所引四点行号（`CloudVaultImporter.kt:148-163` 等）为**整改前快照**，逐字吻合
  （见 §497.2）；整改后行号已随代码变化，本批不再回填旧行号。
