## 2. 实施与验收

- **前提复核（认领时）**：直读 `BiometricUnlockCoordinator.completeBiometricUnlock` 确认前提成立——
  `decode(decryptedBytes)` 与密钥文件现读（挂起）均在 `try/finally` **之前**；`startBiometricUnlock` 的
  `withContext { doFinal(...) }` 结果若在交付前取消则无引用，只能等 GC。

- **改动一（解封收尾所有权前移，`BiometricUnlockCoordinator.completeBiometricUnlock`）**：清理范围自
  **解码开始**建立——`decode` 与密钥文件现读全部移入 `try`，`finally` 统一 `payload?.wipe()` 与
  `decryptedBytes.fill(0)`。decode 抛异常或现读在挂起点抛异常 / 被取消时，已解密字节与已解码载荷都被擦除。

- **改动二（跨交付边界所有权，`BiometricUnlockCoordinator.startBiometricUnlock`）**：在工作线程块内
  一产出解密结果即 `decryptedHolder.set(it)`（`AtomicReference<ByteArray?>`）；交付成功时 `set(null)`
  解除登记并移交 `completeBiometricUnlock`，外层 `finally` 兜底 `getAndSet(null)?.fill(0)`——
  覆盖「工作线程已完成 `doFinal`、调用方在结果交付前被取消」的窗口（原实现该结果对上层不可达）。

- **改动三（codec 半解码清理，`BiometricSealedPayloadCodec.decode`）**：帧头自洽后若密码段已解码成功、
  而密钥文件段长度前缀越界（`readLength` 抛异常）等半解码失败，已分配但**不会交付**的 `passwordChars`
  / `keyFileData` 由 codec 自身在 `catch` 内擦除（调用方拿不到对象，无从清理）。

- **测试（`BiometricUnlockBufferCleanupTest`，新增 3 例，均以引用观察字节内容）**：
  | 注入路径 | 断言 |
  |---|---|
  | 载荷 `decode` 抛异常（未知版本帧） | 传入的解密字节归零 |
  | 密钥文件现读在挂起点抛异常 | 传入的解密字节归零 |
  | 工作线程 `doFinal` 已完成、交付前取消（受控线程调度器 + 阻塞式假 `Cipher`/`CipherSpi` 制造确定性窗口） | 工作线程产出的结果数组归零 |

  这三条各以「归零」为唯一通过路径（无其它代码路径会写入该数组），故对「擦除缺失」具备判别力。

## 4. 限制与后续边界

- **未做代码变异反校**：「临时禁用擦除」属对生产代码注入安全回退，被权限分类器拦下且违反仓库既有纪律
  （不在生产代码注入不安全构造做变异测试）。本批改以「归零是三条用例的唯一通过路径」保证判别力，
  此缺口如实留痕。
- 借用会话密钥文件（`KeyFileSessionCoordinator`）**未**被本协调器擦除（其清零由既有路径承担），
  符合所有权约定。
- 未做内存提取 / 硬件认证实测；`decode` 半解码擦除属内部不可观测对象，按代码路径核对而非运行观测。
- 未触达 Passkey schema / KPEX / 原生绑定，不触发互操作对拍与四层设备测试；生物识别授权的
  AVD 实跑属既有冒烟范畴，本批未新增设备用例。
