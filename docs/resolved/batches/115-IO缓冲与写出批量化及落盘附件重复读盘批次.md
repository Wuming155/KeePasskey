## 1. 缺陷与前提更正

本批两条条目的**开工复核**各撞出一处前提问题（条目维护规则 2：「前提已不成立的，就地修正或显式标注后再动手」）。

### 1.1 `ISSUE-P3-151` ②：XML 写出逐字符 —— 并修掉**非 BMP 字符被截断损坏**（真缺陷，非纯优化）

`KdbxXmlStreamWriter.escape` 原以 `writer.write(codePoint)` 逐**码点**写出，而
`java.io.Writer.write(int)` 的语义是「**只写低 16 位**」⇒ 非 BMP 字符（emoji，如 U+1F600）
被写成 `0xF600`（私用区字符），**写出即已损坏**。实测证据（把实现回退到逐码点写法后跑新增用例）：

```
expected:<[😀开头表情 …尾部🔐🔒]> but was:<[开头表情 …尾部🔒🔒]>
```

即标题 / 备注中的 emoji 在**保存后不可逆丢失**——属数据完整性缺陷，先前无任何用例覆盖（既有
`testCrlfTextPreservedRoundtrip` 只覆盖 CR/CRLF，全仓无代理对用例）。

### 1.2 `ISSUE-P3-151` ①：GZip 默认 512 B 缓冲 —— **前提更正**：cipher 流没有缓冲参数

原稿称「`GZIPInputStream/OutputStream` 与同链的 `CipherInputStream/OutputStream` 都未传缓冲，
三处一行改动即可」。复核结论：**后者并不存在缓冲尺寸构造参数**（其内部固定 512 B 常量），
「一行改动」只适用于 GZip 三处；AES 侧的块粒度须以**自研分块流**解决（同仓
`CbcDecryptingInputStream` 已有先例），且它与既有 `transform(key, iv, block)` 契约不兼容（JCE 自带链值状态），
**属独立一档改动 ⇒ 转登 `ISSUE-P3-155`**。

### 1.3 `ISSUE-P3-151` ③：每个 `<Times>` 固定 5 次正则嗅探

`KdbxXmlTimeHelper.parseDate` 的 ISO-8601 嗅探原为正则 `^\d{4}-\d{2}-\d{2}`，而每个 `<Times>` 调 5 次
（条目 / 分组 / 历史各一份），万级条目库上构成可观的引擎进入开销。

### 1.4 `ISSUE-P3-150`：**前提整体更正** —— 整树 `copy` 是有意契约，真实成本面在别处

原条目以「整树 `copy` + 附件字节 `copyOf()` 是纯浪费」为由要求整改。开工复核（阅读
`KdbxBinaryDeduplicator` / `KdbxAttachment` / `InnerHeader.BinaryItem` + 既有用例）**推翻该前提**：

- 「提交独立副本 / 池为唯一权威源」是**有意设计的别名隔离契约**，由 P1-9 回归用例
  `KdbxBinaryDeduplicatorTest.testAttachmentClearDoesNotZeroBinaryPool` 明确锁定
  （外部按 `Closeable` 契约清零附件**不得**波及二进制池）；省下的只是若干对象分配，
  代价是放宽一条被用例守护的所有权保证 ⇒ **刻意不改**，结论登记
  [`architecture/已知工程限界.md`](../../architecture/已知工程限界.md) §1.7；
- **复核后确认的真实成本面**：`candidateItem` 对落盘附件恒以 `source.withFlags(flag)` **新建实例**，
  而 `BinaryItem.contentHash` 是**按实例** `lazy` 缓存的、落盘条目首次计算必须**流式读回整份附件**
  ⇒ **每一次保存都把全部落盘附件重新读盘一遍**（与附件总量成正比，百 MB 级附件库即每次保存秒级 I/O）。

## 2. 整改内容

| 落点 | 变更 |
|---|---|
| `KdbxFile.guardPayloadSize` / `savePayload` | `GZIPInputStream` / `GZIPOutputStream` 传 `COMPRESSION_BUFFER_BYTES = 64 KiB`（原默认 512 B） |
| `KdbxXmlBinaryNode.gunzip` | `GZIPInputStream` 传 `GZIP_INFLATER_BUFFER_BYTES = 64 KiB`（拷贝缓冲维持既有 8 KiB） |
| `KdbxXmlStreamWriter.escape` | 改为**按「无需转义的连续区间」批量 `write(String, off, len)`**，并抽出 `needsEscape(codePoint, escapeNewLines)` 与 `escape` 分支一一对应；代理对按 UTF-16 区间原样搬运 ⇒ **修复非 BMP 截断** |
| `KdbxXmlTimeHelper` | 正则嗅探 → **结构化前缀判定** `looksLikeIso8601Date(value)`（4 位数字 + `-` + 2 位 + `-` + 2 位），语义与 `^\d{4}-\d{2}-\d{2}` 逐一等价（`\d` 未开 `UNICODE_CHARACTER_CLASS` 时只匹配 ASCII 数字） |
| `KdbxBinaryDeduplicator.candidateItem` | `flags` 未变时**直接复用来源实例**（落盘来源与旧池回退两条分支各一处），使 `contentHash` 缓存跨保存保留 |

## 4. 边界与如实声明（**不得**把这些读作已验证）

1. **本批无真机 / 性能实测**：三处改动的量化收益（GZip 调用次数、写出粒度、跨保存的读盘量）都需要设备侧 profile，
   条目原文要求的「同一真机、同一语料的前后墙钟对比」**未做**。判据取「行为等价 + 结构性修复 + 变异验证」，
   **不得**据此宣称任何百分比收益。
2. **落盘附件读盘次数为宿主侧计数证据**：以假 store 计数断言（1 次 vs 每次保存 1 次），
   **未**在设备侧以真实文件系统观测 I/O 次数。
3. **XML 写出的输出字节仅在「非 BMP 字符」一类上发生变化**（代理对不再被截断）；BMP 字符、转义规则、
   `&#xD;` 处理、非法码点剔除、属性与文本两路径的差异全部逐字未变——由既有往返 / CRLF / 元数据用例覆盖。
4. **`.kdbx` 产物字节是否与修复前一致**：对**不含非 BMP 字符**的库应完全一致（转义结果逐字符相同）；
   含 emoji 的库**本就不一致**——旧产物是损坏的（这正是本条修复的缺陷）。**未做**「同一库新旧产物二进制对拍」，
   故不宣称「产物字节级不变」。
5. `ISSUE-P3-151` ① 的 cipher 侧、`ISSUE-P3-150` 的编辑路径 ⇒ **转登** `ISSUE-P3-155` / `ISSUE-P3-156`，本批**未做**。

### ISSUE-P3-151 IO 缓冲与解析常数项（GZip 512 B / XML 逐字符写出 / 时间戳正则）

- **背景（含一处前提更正）**：三处与库规模线性相关的常数项：
  ① `GZIPInputStream(raw)` / `GZIPOutputStream(cipherOut)` / `KdbxXmlBinaryNode.gunzip` 未传缓冲尺寸，
     `java.util.zip` 默认内部缓冲为 **512 字节**，多 MB 载荷以极小粒度反复进出 inflate/deflate；
     **前提更正（2026-09-17 开工复核）**：原稿称「同链上的 `CipherInputStream` / `CipherOutputStream` 同样可传缓冲」
     ——**该两个类没有缓冲尺寸构造参数**（内部固定 512 B），故「一行改动」只适用于 GZip；
     cipher 侧的块粒度需自研分块流才能改，**已转登 `ISSUE-P3-155`**。
  ② `KdbxXmlStreamWriter.escape` 对文本逐**字符**调 `writer.write(int)`（保存侧随 XML 字符数线性），
     且 `Writer.write(int)` 只写低 16 位 ⇒ **非 BMP 字符（emoji）被截断损坏**（见验收标准第 2 条）；
  ③ `KdbxXmlTimeHelper.parseDate` 每次先跑一次正则嗅探再 Base64 解码，而每个 `<Times>` 固定调用 **5 次**。
- **量级**：①O(载荷字节 / 512)；②O(XML 字符数)；③O(条目数 × 5) 次正则 + Base64。
- **核实时间点与方式**：2026-09-17 逐处阅读下列源码核实（①②为 Kotlin 侧形参缺省，非平台行为推断；
  ②的截断后果经变异验证实测确认）。
- **依据**：`database/.../file/KdbxFile.kt:85,390-394`、`database/.../xml/KdbxXmlBinaryNode.kt:157`、
  `database/.../xml/KdbxXmlStreamWriter.kt:23,84-102`、`database/.../xml/KdbxXmlTimesNode.kt:53-59`、
  `database/.../xml/KdbxXmlTimeHelper.kt:143,152`（正则本身已是顶层 `val`，**不是**每条目重建，此处只优化调用次数与前缀判断）。

  （顺带修掉非 BMP 截断）；③ 以廉价结构化前缀判断替代正则（语义逐一等价）。
- **验收标准**：`.kdbx` 往返字节级一致（现有互操作与 golden 用例全绿）；
  **非 BMP 字符（emoji）往返无损**（新增用例，变异验证须能变红）；
