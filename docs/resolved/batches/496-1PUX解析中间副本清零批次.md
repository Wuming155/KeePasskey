**背景与影响**：`OnePasswordPuxImporter.parseOrThrow`（`OnePasswordPuxImporter.kt:81-84`）从
`PuxArchiveReader.readEntry`（`PuxArchiveReader.kt:49-78`，经 `:98-106` `readBounded` 返回全新独立数组）取得
`export.data`——**整份含全部明文口令的 JSON 字节**——解码解析后失去引用但全程无 `fill(0)`（成功路径 `:98-106`

## 496.3 整改（AC②：**选「改造接口使可擦除」路线 (a)**，未选「登记限界」）

### ① `parseOrThrow`：`exportData` 成功 / 失败路径均清零（AC①）

`OnePasswordPuxImporter.parseOrThrow`（现 `:84-117`）以 `try/finally` 包裹解析主体，`finally` 中
`exportData.fill(0)`（`:115`）——成功 `return` 与解析失败（`ImportFormatException` / 其它 `Throwable`）两条路径
**一致经过该 `finally`**，与同函数 `accumulator.clearEntries()` 的失败路径擦除纪律对齐。

### ② `readBounded` / `readEntry`：消除「调用方不可达」的明文副本（AC②）

新增 `app/src/main/java/com/keepasskey/app/data/importer/ErasableByteSink.kt`（`internal class`，61 行）：

- **为何必须新增可擦载体**：`java.io.ByteArrayOutputStream` 的内部缓冲是私有字段、**对调用方不可达**，
  `toByteArray()` 只把内容复制出去；解压明文在缓冲里驻留到 GC，调用方无从擦除。故 AC② 无法靠「调用方多清一处」解决。
- `ErasableByteSink` 自持 `ByteArray` 增长，**两个清零点缺一不可**：① 容量增长时新缓冲分配后旧缓冲先
  `fill(0)` 再切引用（旧缓冲曾承载已写入明文）；② `wipe()` 就地清零内部缓冲。
- `readBounded`（现 `:100-119`）改由 `ErasableByteSink` 承载，`finally { sink.wipe() }`（`:117`）覆盖
  **成功返回**（`return sink.copyOut()` 已取出独立副本）与**超限抛异常**（`ImportLimitExceededException`）两路径；
  `copyOut()` 返回与内部缓冲**无别名**的独立副本，其清零责任转移给调用方（即 ① 的 `parseOrThrow`）。
- `readEntry`（现 `:48-82`）把分片起始读缓冲 `buffer` 移出 `use{}` 并加 `try/finally`，`finally { buffer.fill(0) }`
  （`:80`）——该 8 KiB 缓冲逐段承载解压明文，属**同型未引副本**，一并在收尾擦除。
- 删除 `import java.io.ByteArrayOutputStream`。

**故本批未新增 `已知工程限界.md` 条目**（若走 (b) 才应加 §43）：原「调用方不可达的副本」已由接口改造
**整体消除**，不存在需要登记的残余不可达明文副本。复核实测：`grep` 确认 `PuxArchiveReader.kt` 内
`ByteArrayOutputStream` 已零残留（机检见 496.4）。

### ③ KDoc 同步

`OnePasswordPuxImporter` 类 KDoc「敏感数据残余面」段补记：可擦的**字节副本**一处不留（`export.data`
在 `parseOrThrow` 的 `finally` 清零；`PuxArchiveReader` 侧条目缓冲与分片读缓冲各在其 `finally` 擦除）。
`PuxArchiveReader.readBounded` / `ErasableByteSink` 各自 KDoc 写明清零点与所有权转移。

## 496.5 如实声明

- **②的路线取舍**：采纳 AC② 的 **(a)「改造接口使可擦除」**，**未采纳 (b)「登记限界」**。理由：
  ① (a) 的成本可控——新增一个 61 行的 `internal` 可擦载体、`readBounded` 改动约 20 行，`PuxArchiveReader.kt`
  由 378 行增至 **390 行**（仍 < 400，未顶入 tier2 棘轮档，见门禁 `[2/16]` 读数 tier2=35/budget=35 持平）；
  ② (b) 只是「承认漏擦」——把**可确定性擦除**的明文副本降级为永久残余面，与敏感数据铁律相悖，(a) 能真正消除；
  ③ `readEntry` 的返回契约（独立副本）逐字未变，既有 23 例 `OnePasswordPuxImporterTest` 全绿，无调用方受影响。
- **同型未引副本一并收口**：`readEntry` 的 8 KiB 分片读缓冲 `buffer`（`READ_BUFFER_BYTES`）逐段承载解压明文，
  条目未点但同型，本批一并在 `finally` 擦除——**未新增**残余面，属「顺手补齐同型点」，已在上文 496.3 ② 注明。

  `PuxIntermediateWipeTest` 断言「增长 / 擦除后全零」提供引用（生产路径只经 `copyOut()` 取值、绝不读该引用）；
