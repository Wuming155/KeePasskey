# §237 已有 SAF 库授权失败不再静默批次

- **批次编号**：§237（`docs/resolved/README.md` 此前最大 §236）
- **日期**：2026-09-20
- **条目范围**：`ISSUE-P3-230`（整条结案）
- **主题**：把「打开已有 SAF 库时持久化授权失败被静默吞掉」这一**会持续误导用户**的静默缺陷，
  改为「容错取向不变 + 三处可观测归因」：日志留痕、解锁页一次性提示、列表状态与**重新授权**入口。

---

## 1. 缺陷与整改

### 1.1 缺陷（原条目）

`VaultLifecycleCoordinator.importExternalDatabase` 对 `takePersistableUriPermission(uri, READ or WRITE)`
一直是 `try { } catch (_: Throwable) { }`（理由「部分外部 Provider 不支持持久化授权，容错继续」）。
临时授权在**本次会话内**有效 ⇒ 打开与保存都能成功；但进程重启后未拿到持久化授权的 uri 失去读权限
⇒ 该库**从列表里可见却永远打不开**，且应用不给任何归因（用户只看到「解锁失败」）。
同日的新建路径（§233）已改为「授权失败即在建库前显式失败」，本条是**已有库侧**的同一残留面。

### 1.2 整改（三项，AC③ 的容错取向不变）

| AC | 交付物 |
|---|---|
| **AC①** | ① 失败落 `AppLog.w`（`VaultLifecycleCoordinator`，携带异常、脱敏）；② 解锁页一次性提示 `unlock_msg_no_persisted_permission`（`UnlockViewModel.importExternalDatabase` 的**成功分支**，优先于弱因子提示——它直接决定「下次能否打开」） |
| **AC②** | ① `VaultDatabaseInfo.lacksPersistedPermission`（`VaultDatabaseCatalog.buildDatabaseList` 投影填充）；② 卡片状态行 `VaultDatabasePermissionNotice`（警示图标 + 说明 + 「重新授权」，**整行可点**）；③ `DatabasePickerScreen` 的 `OpenDocument` launcher：重选**同一个**文件重取长期授权，随后**复用既有导入路径** `onImportFromSource(LOCAL, name, uri)` 登记（同一 path 幂等覆盖，不新开登记分支） |
| **AC③** | 授权失败**仍容错继续**——判据只驱动提示与状态，**不参与放行 / 拒绝决策**；未改为硬失败（云盘类 provider 不受影响） |

### 1.3 判据单点化（防两处口径漂移）

新增 `app/.../data/repository/VaultUriPermission.kt`：

- `lacksPersistedReadPermission(path, grantedUriStrings)`——**纯函数**（JVM 可测）：
  非 `content://` 恒 false，`content://` 仅在不在已授权集合时为 true；
- `persistedReadUriStrings(context)`——**唯一的平台查询**；查询失败返回 **`null`（未知）** 而非空集，
  调用方遇 `null` 必须**不提示**。这把「查询失败」与「确实没授权」分开，杜绝**谎报风险**
  （空集会被判为缺授权并触发虚假告警）。

两处消费方（列表投影 / 解锁页提示）**共用**该判据，避免出现两种口径（本仓在 `ISSUE-P2-43`
的默认值问题上已踩过同型坑）。

## 3. 如实声明

1. **SAF 真机行为未核对**（本环境无设备）：系统文件面板的呈现、各 provider 对持久化授权的实际支持
   差异、以及「重选同一文件后重启仍可打开」这一整链，均属限界 §4.2「手工冒烟承担」的边界。
   本批的判据与接线已由宿主用例 + 源码守卫锁定，但**设备侧观感与真实 provider 行为未验**。
2. **重授的「同一文件」由用户保证**：SAF 无「原地续期」原语，重新授权必须经用户重选文件；
   若用户选了**另一个**文件，将按既有导入语义**新增 / 覆盖**该 path 的条目（既有行为，本批未改）。
3. **未改动**：`takePersistableUriPermission` 的容错取向（AC③）、新建路径（§233 的前置硬失败）、
   写盘通道与非原子降级口径（限界 §24）均**零改动**。
4. 未改 `*/src/androidTest/**` 与原生内核 ⇒ 按测试资产纪律②**无设备侧必跑项**。

## 4. 条目原文（原样收录，便于回溯）

### `ISSUE-P3-230`：打开已有 SAF 库时持久化授权失败被静默吞掉（重启后库打不开且无告警）

- **核实时间点**：2026-09-20 随 `ISSUE-P2-229` 整改过程中同处代码走查发现。
- **核实方式**：`VaultLifecycleCoordinator.importExternalDatabase`（现 `:213` 附近）对
  `takePersistableUriPermission(uri, READ or WRITE)` 包 `try { } catch (_: Throwable) { }`，
  注释理由为「部分外部 Provider 不支持持久化授权，容错继续」；调用链
  `OpenExistingVaultDialog.kt:43`（`OpenDocument`）→ 本方法 → 解锁走 `openStream`。
- **背景与影响**：临时授权在**本次会话内**有效，故打开与保存都能成功；一旦进程重启，
  未拿到持久化授权的 uri 会失去读权限 ⇒ 该库**从列表里可见却永远打不开**，
  且应用不给任何归因提示（用户只会看到「解锁失败」）。新建路径已在 §233 改为
  「授权失败即在建库前显式失败」，本条是同一缺陷在**已有库**侧的残留面。
- **验收标准**：AC① 授权失败不得静默：至少落 `AppLog.w` 并在打开成功后给出一次性可见提示
  （文案含「重启后可能需要重新选择该文件」）；AC② 列表项对「无持久化授权」的库给出可辨识状态，
  点击可直接重新拉起 `OpenDocument` 重授；AC③ 不改变既有「provider 不支持持久化仍允许本次打开」
  的容错取向（不得改为硬失败，否则云盘类 provider 会整体不可用）。
