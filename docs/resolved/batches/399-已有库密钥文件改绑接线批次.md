## 1. 背景与整改内容

### 1.1 缺口（核实方式见条目登记）

密钥文件能力四处已实现（解锁页 SAF 选择 / 建库既有因子 / 建库生成 / 设置页导出），但**已存在**的库没有任何入口添加 / 更换 / 解绑第二因子：设置页「修改主密码」只调 app 层单参 `changeCredentials(newPassword)`。database 层双参 `DatabaseSession.changeCredentials(newPasswordChars, newKeyFileData)`（`null` = 不使用密钥文件）早已实现且带所有权契约 KDoc——纯 app 层接线缺口。

### 1.2 整改（全部 app 层，database / crypto / sync 零改动）

1. **意图类型**：`VaultRepositoryTypes.kt` 新增 sealed `ChangeKeyFileIntent`（`Keep` / `Remove` / `Use(bytes)`），三态分别映射 database 层两个重载——`Keep` 走单参（沿用会话当前绑定快照），`Remove` 显式双参 `null`（解绑），`Use` 传用户选定字节（绑定或更换）。刻意 `data object`/普通 class 而非 `Boolean`，杜绝「虚假开关」复潮；`Use` 刻意不做 `data class`（与 `CreateKeyFileFactor.Existing` 同口径：密钥字节不是值对象）。
2. **仓库面**：`VaultRepository.changeMasterPassword` 增 `keyFileIntent` 参数（默认 `Keep`，既有调用点零改动）；`RealVaultRepository` / `VaultLifecycleCoordinator` 透传并在协调器内 `when` 三态映射（仅成功时刷新库列表语义原样）。
3. **控制器**：`SettingsMasterKeyChangeController.submit` 增 `keyFileIntent` 形参；`Use` 字节借用语义——仓库侧只读不擦除，清零责任在控制器 `finally`（与密码数组同一收尾窗口，忙路径同步拒绝分支同批擦除），私有扩展 `eraseBorrowedBytes()` 单点收口。
4. **UI**：`MasterKeyChangeDialog` 增密钥文件三态选择段（`KeyFileChoice` 本地枚举 + RadioButton 三行）：保持现状 / 绑定或更换（SAF `OpenDocument` 选文件，行文案随所选文件名变「已选择：%1$s」）/ 解绑。读取强制走全仓唯一 SAF 通道 `KeyFileAccess`（经 `SettingsFeatureControllers.keyFileReader` 暴露，通道缺失按 `Unreadable` fail-closed）；「绑定或更换」未成功读到文件时提交按钮禁用（fail-closed）；读不到（空 / 超限 / 流异常）就地 error 文案反馈，绝不静默。字节擦除链：换选离开 `USE` 就地擦 → 关闭路径 `wipeDialogState()` 擦 → 提交时所有权随 `Use` 移交控制器（对话框丢引用不补刀）。
5. **行数门禁代价（结构性搬移，行为零改动）**：`SettingsViewModel.kt` 原已 499 行贴 tier1 红线 ⇒ 不再加 funnel 方法，改按仓内既有「下沉」范式：`keyFileReader` 落 `SettingsFeatureControllers`（其本就持有 `keyFileAccess`），提交动作改经 `internal val masterKeyChangeController` 直用控制器（原 `changeMasterPassword` 单参转发器退役）。`SettingsViewModel.kt` 终态 500 行（tier2 顶格）。
6. **文案**：zh/en 成对新增 5 条（`set_master_keyfile_section` / `_keep` / `_use` / `_selected` / `_remove`），读失败复用既有 `unlock_keyfile_read_failed`。
