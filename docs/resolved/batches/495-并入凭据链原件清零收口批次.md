## 495.3 整改（AC①：选「改契约——调用方负责清零」路线）

### ① 分层契约（改后，与实现逐行一致）

| 层 | 角色 | 清零行为 |
| --- | --- | --- |
| `SettingsImportPresenter.submitMergeCredentials`（链首，`Uri` 入口与字节入口） | **原件清零收口点（O）** | `try/finally`：提交返回前对 `passwordChars.fill('0')` + `keyFileData?.fill(0)`（正常 / 异常 / 控制器缺失三路径一致）。`Uri` 入口改为**委派**字节重载，读出的 `keyBytes` 与 `passwordChars` 走同一 `finally` |
| `VaultImportController.submitMergeCredentials` | **只读借用（B）** | 纯透传，**不清零**（KDoc 更正为「原件清零责任归调用方」） |
| `KdbxMergeController.submitCredentials` | **只读借用（B）** | **任何路径不清零原件**；只清自身 `copyOf` 副本（`runMerge` 的 `finally`）。**移除两个早退分支的顺手代擦**（原 `:112-113` / `:119-120`）——对借用数组就地清零正是契约 §3 R2 的违例形态，且是条目所指「语义自相矛盾」的另一半 |
| `ImportMergeCredentialSheet` | 交出方（转移） | 自身状态两路径自清（原行为）；交出的数组归宿主链收口点，本组件不再清零（KDoc 校正） |

### ② 路线取舍（为何不「在控制器里也清原件」）

采纳条目 AC① 的「改契约」分支（而非「控制器正常路径也清原件」），四条理由：

1. **与所有权契约一致**：控制器对两入参是**借用**（`敏感缓冲所有权契约.md` R2：借用方「只读且不驻留，**不得擦除**」），
   在控制器里清调用方原件属 R2 违例形态；按契约修正方向应为「调用方负责清零」。
2. **收口点唯一**（R5 取向）：清零收敛到链首 `finally` 一处，避免「补一处、漏一处」——本条目本身的成因正是
   「三处零散判断（两早退分支清、正常路径不清）」。
3. **覆盖最全**：控制器缺失（`SettingsImportPresenter` 设计中 `controller` 可为 null 的回落路径）、
   无 Context / 密钥文件读取失败、提交抛异常——三条路径都过同一 `finally`；若清零放在控制器，
   控制器缺失与异常路径均漏。
4. **可测**：链首为纯 JVM 可构造 / 可驱动层（见 495.5）；控制器层构造需伪 `VaultRepository`、
   `VaultImportController` 在本仓测试中「持 `Uri` / `Context`，纯 JVM 不可构造」（`VaultImportProgressCancelTest` KDoc 既有结论），
   清零放控制器则无法直测。

### ③ 顺序安全性（清零不波及后台消费）

副本 `copyOf` 与消费协程 `launch` 均发生在 `submitCredentials` **同步返回之前**，收口点在返回后才清零 ⇒
清零只触及原件，后台消费用的副本与之无别名面（同 `CredentialIntermediateWipeTest` 锁定的「先 `copyOf` 再擦原数组」形态）。

### ④ KDoc 同步（条目 AC① 后半句：三层 + 一张表）

- `KdbxMergeController.submitCredentials`：改为「B 类借用 / 任何路径不清零原件 / 副本 `finally` 清 / 原件归调用方」；
- `VaultImportController.submitMergeCredentials`：更正为「纯透传的借用引用（不清零）」；
- `SettingsImportPresenter.submitMergeCredentials`（两重载）：写明「原件清零收口点唯一」与委派链；
- `ImportMergeCredentialSheet`：校正「借用语义 / 取消时由调用方清零」两句失实表述。
- `DatabaseSettingsSections.VaultImportSection` 的「宿主负责读字节与清零」表述**改后为真**（收口点在宿主链首），未改。

## 495.6 如实声明

- **覆盖边界（宿主 JVM 不可驱动的形态）**：`android.net.Uri` 无 JVM 实现（本仓惯例，见 `VaultImportProgressCancelTest`
  KDoc），`pendingUri` 只能经 `beginWithUri` 注入 ⇒ 用例驱动的是「控制器在场 + 无待并入 Uri」链路形态；
  `ContentResolver` 读取 `keyBytes`（Uri 非空）与控制器 `copyOf` 正常消费分支无法在宿主构造。
  该两形态的清零由**同一 `finally`** 覆盖（结构保证），**非**本用例实测——如实声明，不以推理冒充实测。
- **填充字符沿用 `fill('0')`（未统一为 `'\u0000'`）**：本链既有清零点（`.kdbx` 并入面）与仓内主体口径一致
  （`app/src/main` 全量 `grep` 计数：`fill('0')` 170 处 vs `fill('\u0000')` 2 处），且条目给出的最小修复建议即「与
  `ImportMergeCredentialSheet` 既有做法一致」。两者对「原件不可再恢复」等价（覆写为任一固定值即销毁原值）；
  统一填充字符属契约 §7 Step 3「命名工具替换」的**按需**面（其解除条件明写「因擦除写法不统一而导致实际漏擦」时重启），
  本批不为此单独开面。用例常量注释已标明「与仓内既有口径一致」。
- **未在 `VaultImportController` / `ImportMergeCredentialSheet` 重复 `fill`**：收口点唯一（R5 取向）；
  两层 KDoc 已如实声明「借用 / 交出」角色。若未来新增绕过链首的直接调用方，须自行清零（契约已写明）。
