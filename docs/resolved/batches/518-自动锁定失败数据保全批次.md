### ISSUE-P1-592：自动锁库在 DIRTY 补存失败后销毁唯一的新数据

- **整改方案**：[ISSUE-P1-592 独立方案](../../architecture/问题整改方案/P1/ISSUE-P1-592/自动锁定失败数据恢复方案.md)；方案已编制，尚未实施。

- **来源 / 严重度**：全面软件审计 `AUD-04`，High，可信度高。
- **核实时间点 + 核实方式**：2026-10-13；直读 `AutoLockSessionGuard.triggerLock` 与 `DatabaseSession.lock`，核对现有正常补存测试。
- **背景 / 位置**：`app/.../security/AutoLockSessionGuard.kt:126-132` 补存失败只记录日志，仍锁定并清空树；无已加密恢复副本。
- **触发 / 后果**：已有修改因磁盘满 / 提供方错误保存失败，随即熄屏或自动锁；该版本永久丢失。此处是已进入会话的 DIRTY 数据，与用户主动放弃编辑草稿不同。
- **建议 / 验收**：制定兼顾锁定与恢复的失败策略（如独立加密恢复快照及持久化告警），禁止以一直保持解锁作为唯一补救；注入写盘失败验证锁定后仍可恢复或明确告知无法保全。
- **详细证据**：[全面软件审计](../../security/全面软件审计_2026-10-13.md)。

## 2. 实施与验收

- **前提复核（认领时，2026-10-14；直读 `triggerLock` / `DatabaseSession.save` / `SessionPersistence`）**：前提成立——
  DIRTY 分支补存失败仅 `debugLog.error` 一行，随后无条件 `databaseSession.lock()` 清空内存树与凭据缓存；
  方案声明的前置依赖 `ISSUE-P1-593` / `P1-601` / `P2-600` 已分别于 §505 / §513 / §510 闭环。

- **改动一（锁定路径明确结果，方案步骤 1）**：新增 `SessionRecoveryPolicy.kt`（含 `sealed interface LockOutcome`：
  `NoPendingChanges` / `Saved` / `RecoveryCommitted` / `PreservationFailed(alertPersisted)` / `Deferred`）。
  `AutoLockSessionGuard.triggerLock` 改为返回 `LockOutcome`，并把 DIRTY 分支收敛到
  `preserveDirtySessionBeforeLock()`；新增 `lockOutcomes: SharedFlow<LockOutcome>` 供 UI 观察。

- **改动二（独立加密恢复副本，方案步骤 2/3）**：新增 `VaultRecoveryStore.kt`——应用私有**非缓存**目录
  `filesDir/recovery`（目录 0700 / 文件 0600，不依赖 umask）：
  - 载荷 `<sha256(库身份)>.<代次>.kre` 即会话导出的**标准 KDBX 密文**（复用 `DatabaseSession.exportToBytes`，
    同一复合凭据加密；**主密码与密钥文件绝不随副本落盘**）；
  - 索引 `<sha256(库身份)>.krem` 为**非敏感旁路索引**（UTF-8 Properties：库身份 / 显示名 / 代次名 / 长度 / SHA-256），
    **只用于发现**，恢复语义一律从成功解密的载荷读取；
  - **提交顺序**＝新代次载荷（唯一临时名 → 写满 → `flush`+`fd.sync` → 0600 → 原子改名）→ 索引原子改名（提交点）
    → 清理更早代次 ⇒ **保留上一份有效副本直到新副本确认**；中断于①②时索引仍指旧代次、旧载荷未删；
  - 读取按**长度 + SHA-256** 校验，不符即判损坏并 **不自动采纳**。

- **改动三（保全编排，方案步骤 2/4）**：新增 `SessionRecoveryCoordinator.kt`（`internal`，实现 `SessionRecoveryPolicy`）：
  补存失败 → `exportToBytes`（Default 序列化）→ `VaultRecoveryStore.write`（IO 落盘）→ 成功回报
  `RecoveryCommitted`；序列化失败或落盘失败 → 经 `RecoveryAlertStore` **尽力持久化**「无法保全」告警并回报
  `PreservationFailed(alertPersisted)`。整体包 `NonCancellable`（锁定常发生在进程即将退后台的时刻，恢复必须跑完）。

- **改动四（告警持久化 + 冷启动查看，方案步骤 1/4）**：新增 `RecoveryAlertStore.kt`（SharedPreferences，**非敏感**：
  库身份 / 时刻 / 是否写出过副本），写入用 `commit()` 取得真实成败信号；冷启动一次性消费呈现。

- **改动五（冷启动处置 UI，方案步骤 5）**：新增 `VaultRecoveryCoordinator.kt`（发现 → 以对应凭据解锁 → 预览差异 →
  恢复 / 另存 / 保留 / 删除）+ `ui/screens/recovery/RecoveryViewModel.kt` + `VaultRecoveryDialog.kt` +
  外壳挂点 `ui/RecoveryShellHost.kt`（自 `KeePasskeyApp` 拆出，控母文件行数与函数长度）。口径：
  - **覆盖保护**：正式库存在且未获显式确认时 `restore` 返回 `kdbx.recovery.overwrite_blocked`，UI 展示差异并请用户确认；
  - 差异预览用**按库 id 取回的密钥文件收编副本**（`ISSUE-P3-448`）补齐复合凭据；差异指纹只用非敏感字段；
  - 仅本地文件库支持原地恢复（SAF `content://` 库返回 `kdbx.recovery.local_only`，引导另存）；
  - **成功恢复 / 另存并确认后才删除副本**（方案步骤 6 前半）。

- **改动六（凭据轮换清理旧密文副本，方案步骤 6）**：`RealVaultRepository.changeMasterPassword` /
  `changeKeyFileOnly` 成功后按活动库身份调 `VaultRecoveryStore.deleteByVaultId`——旧口令可解的恢复副本不得留驻
  （与 `.bak` 换密清理同口径）。

- **改动七（错误码与文案）**：`KdbxError` 新增 5 码（`kdbx.recovery.*`）并在 `KdbxErrorTexts` 映射；
  `values/strings.xml` + `values-en/strings.xml` 成对新增 `err_recovery_*` 与 `recovery_*` 文案。

- **测试（宿主）**：
  - `AutoLockSessionGuardTest` 扩 4 例（`NoPendingChanges` / `Saved` 不触发恢复 / 补存失败触发恢复并回传结果 /
    保全失败携带告警标志），注入记录型 `SessionRecoveryPolicy`；
  - 新增 `VaultRecoveryStoreTest`（6 例）：写入发现 / 代次滚动只留最新 / 篡改判损坏不采纳 / 索引不含载荷明文 /
    根目录不可写返回 false / 按库身份删除幂等；
  - 新增 `SessionRecoveryCoordinatorTest`（2 例）：补存失败写出**可用会话凭据解开**的恢复副本（含未落盘条目）/
    两通道皆失败登记无法保全告警；
  - 新增 `VaultRecoveryCoordinatorTest`（6 例）：预览差异并识别外改 / 未确认覆盖被拒且不动正式库 / 确认后恢复并删副本 /
    另存为并删副本 / 损坏副本预览失败 / 删除后不再待处置。

- **验收矩阵对照（方案 §4）**：①「正式写失败、恢复目录可写 ⇒ 如期锁定；重启后恢复新条目」→

  ③「写恢复临时文件中断 / 损坏 ⇒ 上一有效副本保留、损坏副本不自动采纳」→ `VaultRecoveryStoreTest`（代次滚动 / 完整性校验）

  `VaultRecoveryCoordinatorTest` 预览差异 + 未确认覆盖被拒例；⑤「换凭据后发现旧恢复副本 ⇒ 旧密文清理」→

## 4. 限制与后续边界

- **设备侧「熄屏 / 后台锁 / 进程重启」实跑未覆盖**：方案 §4 要求「设备测试确认熄屏、后台锁和进程重启后的真实行为」。
  本批**未**新增 `*/src/androidTest/**` 用例（Android 侧行为经由既有 `AutoLockSessionGuard` 注册管道驱动，
  其内核已由宿主用例全链路覆盖），故本批**不触发**四层设备测试义务；方案该行**如实登记为未执行**。
  真实故障注入（让设备写盘失败）与真实进程重启后的恢复走查仍待补。
- **「另存」落点口径**：本批另存落在应用私有目录（`filesDir`，名称去重），新库在**库列表刷新后**可见；
  未接 SAF「另存到用户所选位置」（避免在本批引入 ActivityResult 通道）。属方案内的实现选择，非缺陷。
- **SAF 库不支持原地恢复**：`content://` 库的 `restore` 返回 `kdbx.recovery.local_only`，引导另存——
  会话锁定后无法再取得其 `saveWriter`，原地写回需重新获取 URI 权限，超出本批范围。
- **恢复副本保留数量**：按方案「推荐保留一份最新有效版本」，每次写入清理更早代次；**未**做保留期限 / 数量策略
  （方案称属实施批次需明确的产品口径）。当前口径：直到用户恢复 / 另存 / 主动删除，或换密清理。
- **未做官方实现对拍**：恢复载荷即生产 `KdbxFile.save` 产物（与正式库同一管线），字节布局零变化，
  故未新增 `verify_interop.py` 对拍。
