## 1. 为什么单独跑一轮

§240 闭环时密码方向已端到端打通，但用户报告的是「通行密钥**和**账号密码均无法保存」——而
通行密钥方向**未做过同口径真机复算**（§240 已如实声明该边界）。本轮专门补这一条。

工具：把 §240 新增的设备侧真实客户端 `CredentialSaveClientActivity` 扩展到公钥创建请求
（新增 `passkey` / `passkey-malformed` 两种模式），其余口径不变。

## 2. 方法学发现（可复用判据，本轮最大收获）

**「provider 日志里看到 `BeginCreateCustomCredentialRequest`」≠「应用不支持通行密钥」。**

`androidx.credentials.provider.BeginCreateCredentialRequest$Companion.createFrom`
（2026-09-21 经 `javap -c` 核对已发布的 `credentials:1.6.0` AAR）的结构是：

```java
try {
    if (type == "android.credentials.TYPE_PASSWORD_CREDENTIAL")     → BeginCreatePasswordCredentialRequest
    if (type == "androidx.credentials.TYPE_PUBLIC_KEY_CREDENTIAL")  → BeginCreatePublicKeyCredentialRequest
    return new BeginCreateCustomCredentialRequest(type, data, callingAppInfo);
} catch (FrameworkClassParsingException e) {          // ← 异常表：from 12 to 79 target 82
    return new BeginCreateCustomCredentialRequest(type, data, callingAppInfo);
}
```

而 `BeginCreatePublicKeyCredentialRequest$Companion.createFrom$credentials` 对
`BUNDLE_KEY_REQUEST_JSON` 有 `checkNotNull`（缺失即 NPE → 被上层兜底成
`FrameworkClassParsingException`）。⇒ **类型字符串正确、但载荷残缺时，请求会以
「类型=公钥 + 类=Custom」的矛盾形态送到 provider**，然后落进 provider 的 `else` 分支 ⇒ 空响应。

**本探针首版即踩中该形态**（只把载荷写进 `credentialData`，`candidateQueryData` 留空），
一度把现象误读为「应用不支持公钥创建请求」；经反编译核对后改正探针（两份 Bundle 内容一致，
与 androidx 的 `toCredentialDataBundle$` / `toCandidateDataBundle$` 逐键对齐），
类型随即被正确识别。**该次误判如实留痕**，以免后人重蹈。

## 3. 真机结论

### 3.1 冷启动轮（force-stop 后首轮）

| 时刻 | 事件 |
|:--|:--|
| 06:51:35.407 | `Provider session created and being added` |
| 06:51:37.864 | `KeePasskeyCredProvider: onBeginCreateCredentialRequest … BeginCreatePublicKeyCredentialRequest`（**2.46 s**） |
| 06:51:38.409 | `Provider status changed: CANCELED`（**2.99 s** = 系统预算） |
| 06:51:38.412 | 客户端 `onError: TYPE_NO_CREATE_OPTIONS` |

⇒ **与密码方向同源**：不是通行密钥专属缺陷，而是 `ISSUE-P1-238` 的冷启动预算问题
（我们的代码进入得太晚，系统已取消会话）。

### 3.2 热态轮（进程存活）

| 时刻 | 事件 |
|:--|:--|
| 06:52:07.457 | `Provider session created` |
| 06:52:07.478 | 我们的回调（**21 ms**） |
| 06:52:07.493 | `Provider status changed: SAVE_ENTRIES_RECEIVED` + `ui invocation is needed` |

⇒ **provider 侧通行密钥创建入口工作正常**。

### 3.3 面板与落地页

系统面板如实呈现（各字段均来自 `CredentialCreateEntries.passkeyEntry`）：

```
KeePasskey
要创建通行密钥以便登录"com.keepasskey.test"吗？
将通行密钥或密码保存至活动密码库
CM Probe User
cm-probe-user • 通行密钥
继续
```

点击「继续」→ `ActivityTaskManager` 拉起
`com.keepasskey/.app.passkey.PasskeyCreateActivity`，即
**`FLAG_MUTABLE` 填充式 PendingIntent 握手在通行密钥方向同样成立**——
若握手失败，该 Activity 会立刻呈现 `MISSING_REQUEST` 拒绝页而非进入解锁引导。

落地页最终停在**解锁/建库引导**（「欢迎使用 KeePasskey / 尚未选择或创建密码库」）：
本机从未创建或打开过密码库，故注册流程无法继续——**属环境前提，不是缺陷**。

## 4. 应用侧整改（本轮唯一代码改动）

`KeePasskeyCredentialProviderService.buildBeginCreateResponse` 的 `else -> null` 分支原为
**完全静默**。真机排查时正是因为它零日志，才把「载荷残缺被 androidx 降级」误判为
「应用不支持该请求」。

改为留痕：

```kotlin
else -> {
    AppLog.i(TAG, "未识别的创建请求类型，不产出创建入口: ${request.javaClass.simpleName}")
    null
}
```

**只记请求类名**（androidx 三种固定类型之一），**不记类型字符串**——后者由调用方提供、
可携带任意内容（ISSUE-P1-10 口径）。响应语义**不变**（仍是空响应 = fail-closed）。

## 6. 如实声明（边界与未验证项）

1. **未完成通行密钥注册闭环**：需先有**已解锁的密码库**（本机无），故「用户验证 → 生成密钥 →
   落库 → 回传 `CreatePublicKeyCredentialResponse`」这一段**未在真机跑通**；
   `PasskeyCreateActivity` 之后的行为只有既有设备侧用例
   （`PasskeyCreationDeviceTest` / `CredentialProviderRequestContractDeviceTest`）覆盖。
2. **`PasskeyRegistrationGate` 的 DAL 门控未实测**：非浏览器调用方（如本探针）在解锁后
   还需通过 `DigitalAssetLinksVerifier` 远程声明校验，属**既有设计**（限界/裁决表已登记），
   本轮未改动、也未构造通过/拒绝两侧的真机证据。
3. **未点击面板的其它分支**（更换提供方、取消）。
4. **冷启动轮次仍为点测**：本轮 1 次冷启动命中预算（未超时），§240 的 3.05 s 超时轮与
   本轮通行密钥方向的 2.46 s → 2.99 s CANCELED 共同支持 `ISSUE-P1-238` 的结论，
   但**不构成统计意义上的测量**。
5. 本批未触 `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 与任一原生绑定。
