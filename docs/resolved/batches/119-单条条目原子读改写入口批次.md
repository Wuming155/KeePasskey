## 1. 缺陷与整改

### 1.1 缺陷面（开工复核后的准确表述）

条目正文点名的两处成本面经开工复核**逐条成立**（前提无需更正）：

1. **擦除退化为通用实现**：`PasskeyEntryCoordinator.applySignCountPatch` 经
   `DatabaseSession.updateDatabaseMeta` 做原子读-改-写，而该入口的变换是**任意整库变换**
   （同步合并 / 远端库接管会整体替换分组树），无法定位被替换节点 ⇒ 替换前只能走
   `KdbxGroup.clearSupersededSensitiveData`：为**整棵新树**（含全部 history）建 `IdentityHashMap`
   身份集合，再遍历旧树逐实例查表 ⇒ O(条目数 × 字段数) 次哈希插入 + 同量级查表 /每次 passkey 断言。
2. **该路径自带整树重建**：`PasskeyEntryCoordinator.replaceEntry` 对**每一个分组**做
   `group.copy(entries = …, subgroups = …)`（未命中分支也重建）⇒ O(分组数) 次对象分配 /每次断言。

**核实时间点与方式**：2026-09-17 逐处阅读 `PasskeyEntryCoordinator.kt:123-164`（原子读-改-写主体与
`replaceEntry`）与 `SessionContentMutations.updateDatabaseMeta` 确认（§118 开工复核时首次确认并转登，
本批开工复核复查仍成立、行号无漂移）。

### 1.2 整改设计

**A. 新增「单条条目原子读-改-写」入口（`DatabaseSession.updateEntryById`）**

`DatabaseSession.updateEntryById(entryId, transform)` → `SessionContentMutations.updateEntryById`：
在会话 Mutex 内的**单次**受控变换中完成「按 id 定位 → transform → 落树 → 增量定点擦除」，
擦除复用 §118 的增量原语（`eraseSupersededSensitiveData`，候选**只取自被替换的那一条旧条目**）。

- **返回值**＝**落树上线的条目实例**（`transform` 的产物）；调用方需要回传的值应写入该实例后再从它读回，
  与已提交状态同源。
- **未命中条目**（或只读态 / 无活动库）返回 `null`，且**零写入、不置 DIRTY**——旧实现即使命不中也会把
  同一实例写回并置 DIRTY（顺带修正的边界行为）。
- 入口是**更新专用**：按 id 定位，绝不新增条目；upsert 仍走 `saveEntry`。

**B. 路径复制定位（`SessionTreeEditor.updateEntryById`，新增）**

按**条目 id** 递归定位（不依赖 `parentGroupId`；既有的 `updateOrAddEntryIn` 是按父组 id 定位），
命中即插入变换产物并回报替换关系，未命中分支按**同一实例**原样返回——与 §118 的路径复制契约同源。

**C. 接线（`PasskeyEntryCoordinator`）**

`applySignCountPatch` 改走 `updateEntryById`，删除 `replaceEntry`（整树重建消失）；
回传值**从已提交条目读回**（`PasskeyData.readSignCount(patched.customFields)`），
使「返回给断言路径的计数器」严格等于库内已提交状态（`incrementPasskeySignCount` 的既有契约不变）。

**D. 不放宽 `updateDatabaseMeta`**

同步合并 / 远端接管 / 回收站墓碑 / 自定义图标引用清理等**任意整库变换**仍走通用实现；
其 KDoc 已补指「需要 O(被替换节点) 的单条写入请走 `saveEntry` 或 `updateEntryById`」。

**原子性（风险提示项，不得削弱）**：现值读取、目标值计算与落树同处一个临界区；
既有并发用例（32 路递增、单调性契约）在本批全绿即为该约束的回归守护。

## 3. 边界与如实声明（**不得**把这些读作已验证）

1. **无真机 / 性能实测**：本批判据为**行为等价 + 结构性修复 + 变异验证**。消除的是「O(分组数) 次对象分配」
   与「O(条目数 × 字段数) 次哈希插入」两类**结构性工作**，**不得**据此宣称任何百分比收益。
2. **候选收敛是构造性结论 + 结构性守护，而非运行期计数证据**：「集合规模不随全库规模增长」由代码路径保证
   （候选只由被替换的旧条目收集一次），并由路径复制用例的 `assertSame` 锁定前提；
   **没有**任何用例在运行期观测集合大小（无性能插桩，亦未新增生产代码测试钩子）。
   且 §118 的 **M5 结论继续适用**——破坏路径复制后擦除用例**仍全绿**，故擦除正确性的唯一守护面仍是 `assertSame` 系列，
   **不得**放宽为 `assertEquals`（本批 M2 再次实测复现：app 侧擦除断言对路径复制破坏完全不敏感）。
3. **增量擦除的步骤 4 仍是一次 O(全库) 引用比较扫描**：候选非空且未被前序步骤清空时（passkey 计数器补丁正是
   这种情形：被替换旧条目的其它计数器实例与存活字段共存）会走一次整树引用扫描。
   本批消除的是**分配与哈希**，**不得**读作「该路径已完全无全库遍历」。
4. **入口语义收窄**：`updateEntryById` 只做**单条、已存在条目**的变换，未命中即零写入；
   「条目不存在」与「落树实例」用同一返回值表达 ⇒ **不适用于**「变换产物本身可能为 null」的场景；
   批量 / 整库变换仍走既有入口。
5. **其余 `updateDatabaseMeta` 调用面本批未动**：同步合并、远端接管、回收站墓碑、自定义图标引用清理、
   变体字典写入都仍是任意整库变换，通用擦除**必须**保留（本批未改其语义）。
6. **未跑**：`assembleRelease`、设备侧 instrumented 用例（本批不触碰 Android 平台 API 差异面）。

### ISSUE-P3-157 `updateDatabaseMeta` 单条条目更新路径的整树重建与全库身份集合重建（passkey 计数器补丁）

- **背景**：`ISSUE-P3-156`（§118）已把 `SessionTreeEditor` 驱动的三条写路径（`saveEntry` / `saveGroup` /
  `batchMoveEntries`）改为增量定点擦除，但**单条条目更新还有一条不经编辑器的路径**：
  `PasskeyEntryCoordinator.applySignCountPatch` 经 `DatabaseSession.updateDatabaseMeta` 做原子读-改-写，
  而 `updateDatabaseMeta` 的变换是**任意整库变换**（同步合并 / 远端库接管会整体替换分组树），
  无法定位被替换节点 ⇒ 擦除只能退回通用实现（为整棵新树建身份集合，O(全库)）。
  该路径同时自带一处整树重建：`PasskeyEntryCoordinator.replaceEntry` 对**每个分组**做
  `group.copy(entries = …, subgroups = …)`（未命中分支也重建）。
- **量级**：O(分组数) 对象复制 + O(条目数 × 字段数) 身份集合元素 /每次 passkey 断言。
- **核实时间点与方式**：2026-09-17 逐处阅读 `PasskeyEntryCoordinator.kt:123-164`（原子读-改-写主体与
  `replaceEntry`）与 `SessionContentMutations.updateDatabaseMeta` 确认；该路径**不在** `ISSUE-P3-156`
  正文点名范围内（点名者为 `SessionTreeEditor.updateOrAddEntry` + `SessionContentMutations.
  clearSupersededSensitiveData`），故 §118 未纳入、转登本条。
- **整改方向**：新增「单条条目原子读-改-写」入口（会话 Mutex 内单次变换：按 id 定位 → 变换 → 落树 →
  增量定点擦除），并把 `replaceEntry` 改为路径复制；**不得**放宽 `updateDatabaseMeta` 的通用擦除
  （同步合并 / 远端库接管仍需它）。
- **验收标准**：passkey 计数器并发用例（32 路递增）与单调性契约全绿；该路径的擦除候选集合规模不再随全库增长；
  负向对照（故意漏擦计数器旧实例）用例必红。
- **风险提示**：计数器是 RP 侧防克隆校验的依据，读-改-写的原子性不可削弱（不得把变换拆到锁外）。
