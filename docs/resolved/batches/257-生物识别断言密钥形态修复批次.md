## 1. 条目正文（原样收录）

### `ISSUE-P1-242`：生物识别快速解锁恒被断言门控拒绝（断言读路径每次重建私钥 ⇒ 公钥与登记记录脱钩）

- **优先级**：P1（核心功能阻断——快速解锁完全不可用；每次失败还会清除封印凭据与通行密钥登记，用户被迫走主密码重新登记）。
- **核实时间点与核实方式**：2026-09-22，四条独立证据——
  ① **用户真机报告**（弹窗可唤起 → 认证成功 → 提示「快速解锁凭据校验未通过」；主密码重登记 / 冷启动重进均复现；同机应用内通行密钥验证正常）；
  ② **本机 SDK 源 `D:\Android\SDK\sources\android-36.1`**（`KeyGenParameterSpec` 的 `setUserAuthenticationParameters` 实现与 javadoc、
  `KeyStore2ParameterUtils.addUserAuthArgs` / `addSids`）；
  ③ **官方指南**（Android CLI 离线知识库 `kb://android/identity/sign-in/biometric-auth`，本机直读）；
  ④ **设备侧实测**（Pixel_10 AVD / API 36 与 Redmi 4X / API 37 双设备：四种密钥形态读数 + 新增设备用例在原始实现上判红、在整改后判绿）。
- **背景**：`ISSUE-P1-09`（§2.5，提交 `89c2f9a`）为快速解锁断言加了防克隆门控：生物识别授权解封成功后，要求 Keystore 内不可导出的
  ES256 私钥对 `AuthenticatorData || SHA-256(clientDataJSON)` 签名，验证侧复核 challenge / clientDataJSON / rpIdHash / `signCount` 严格单调。
  该批同时改了两件事：① 把断言私钥的生成规格从「不要求用户认证」改为**意在**「绑定强生物识别 + 30 秒认证时间窗」；
  ② 在断言**读路径**新增「规格探测：不是认证绑定形态就删钥重建」的轮换。该批验证只有宿主 JVM 单测（软件 EC 密钥对），**无设备侧证据**。
- **根因（两处同源缺陷，均出自同一批改动）**：
  1. **规格的认证绑定从未生效（`setUserAuthenticationParameters` 单独调用不生效）**：该 API 只**配置**认证参数，认证要求本身
     仅由 `setUserAuthenticationRequired(true)` 开启（SDK 源 javadoc 原文：*This has effect if the key requires user authentication for
     its use (see `setUserAuthenticationRequired(boolean)`)*；Builder 只写 `mUserAuthenticationValidityDurationSeconds` /
     `mUserAuthenticationType`，而 `KeyStore2ParameterUtils.addUserAuthArgs` 在 `!isUserAuthenticationRequired()` 时直接下发
     `KM_TAG_NO_AUTH_REQUIRED`，认证参数被**静默忽略**）。`ISSUE-P1-09` 的规格漏写 `setUserAuthenticationRequired(true)`。
     **设备侧实测（双设备一致）**：该形态生成出的私钥 `authRequired=false validity=0 authType=0`，且**无任何授权即可签名**。
  2. **读路径的轮换前提恒不成立 ⇒ 每次断言都重建私钥**：读路径按 `KeyInfo` 探测「是否绑定认证」
     （`isUserAuthenticationRequired && userAuthenticationValidityDurationSeconds > 0`），不匹配即 `deleteEntry` 重建。
     由缺陷 1，该判据对本仓生成的私钥**恒为假** ⇒ 每次 `assertUnlock` 都删除并重建私钥 ⇒ 新公钥与**已登记记录**里的公钥脱钩 ⇒
     签名验证必然失败 ⇒ 断言门控 fail-closed ⇒ 用户看到「快速解锁凭据校验未通过」，且**每一次**都如此。因为失败发生在
     验证侧而非签名侧，用户「主密码解锁后重新登记」也只是重置了登记记录，下一次断言又重建私钥 —— 与「重登记 / 杀进程重进仍复现」
     的现象完全一致。
- **为何应用内通行密钥（WebAuthn）不受影响**：该通道的私钥是条目内的软件 PEM（`PasskeyPkcs8Codec`），生物识别只作**门控**、
  不与 Keystore 密钥操作绑定；全仓唯一「Keystore 内签名密钥」就是本条的断言私钥。
- **为何宿主 JVM 全绿**：断言验证逻辑是纯函数、可用软件 EC 密钥对完整覆盖；失效面是**真实 AndroidKeyStore 上「读路径是否重建了私钥」**，
  宿主无 AndroidKeyStore，不可能覆盖（`AGENTS.md` §5「涉及平台 API 的逻辑不可只靠宿主单测」）。
- **验收标准**：① 断言读路径不再重建私钥，轮换只发生在登记序列内（有宿主守卫钉死）；② 断言私钥规格由单点声明、显式声明
  「不要求用户认证」，并写明**不得**补 `setUserAuthenticationRequired(true)`（否则撞平台约束，见限界 §3.6）；
  ③ 设备侧实证 `enroll → assertUnlock → verifyAndCommit` 全链可用（**不依赖**生物识别交互即可判别），且该用例在原始实现上判红；
  ④ 平台约束、API 陷阱与安全后果落文档（限界 §3.6）。

## 4. 相邻面复核（**已核实为非缺陷，刻意不改**）

- **「封印凭据在案但断言登记记录不可用」不触发补登记**：`BiometricEnrollmentCoordinator.requestBiometricEnrollment` 在
  `hasEncryptedCredential(dbId)` 为真时直接返回，故记录缺失 / MAC 校验未过 / 公钥与私钥脱钩时不补登记，用户须先撞一次断言门控
  fail-closed（提示与引导文案正确），再以主密码解锁恢复。
  **裁定：保持现状**——「记录被删」正是断言层的**显式可见信号**（`UnlockPasskeyManager` 类 KDoc 明写该设计价值），
  在主密码路径静默补登记会抹掉这一信号（攻击者文件级删除记录后不再有任何可观测迹象）。**不得**以「体验优化」为由改成静默补登记。
- **fail-closed 清除封印凭据**：断言失败即清除封印凭据与登记记录，即使失败源于瞬时 Keystore 异常也如此。**裁定：保持现状**
  （`ISSUE-P1-09` 有意设计；静默放行正是该条要堵的洞）。
