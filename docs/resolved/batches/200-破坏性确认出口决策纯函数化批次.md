## 1. 改动

| 对象 | 行数 | 说明 |

新增三个 JVM 可测单元（全部 `internal`、同文件）：

1. `EntryDetailConfirmIntent`（`CONFIRM` / `DISMISS`）——两份确认段组件只上报意图，不复位、不上行；
2. `EntryDetailConfirmExit`（`propagateAction` / `resetTriggerState`）+ 唯一裁定入口
   `entryDetailConfirmExit(intent)`——「取消 → 只复位、绝不上行；确认 → 复位并上行」的**唯一**策略点；
3. `entryDetailConfirmExitHandler(reset, propagate)`——按仓库口径「**先复位、再上行**」执行决策
   （§169 导出确认、§198 删除确认同款顺序），返回 `(Intent) -> Unit` 供 `onExit` 直挂。

接线：两个段组件签名从「两个出口闭包」改为单个 `onExit: (EntryDetailConfirmIntent) -> Unit`，
宿主以 `entryDetailConfirmExitHandler(reset = …, propagate = …)` 供闭包——**状态所有权仍只有一处**
（复位闭包留在调用点，未把 `mutableStateOf` 抬进段组件，§198 §2 的口径不破）。

## 2. 顺序口径统一留痕（唯一行为相邻差异）

回滚确认的历史顺序是「**先上行、再复位**」（`onRollbackRevision(rev)` 先、`revisionToRollback = null` 后），
git 考古（`198cd36` / `097ab7e` 起）确认**自始如此**；§198 文档「两个出口的先后顺序（先复位再上行）逐字未改」
对回滚这一份**记述失真**（下沉时逐字保留了孤例）。本批把它并入「先复位、再上行」口径：
唯一行为差异是 `onRollbackRevision` 同步抛错时对话框先关闭（差异仅在异常路径，正常路径不可分辨）；
`rev` 经 `let` 捕获，复位不影响上行动作。批次留痕即本节。

## 3. 断言面（两类样板，不互相顶替）

- `EntryDetailConfirmExitTest`（4 例，纯函数面）：取消决策**绝不上行**且必复位；确认决策上行且复位；
  取消经执行器只复位；确认经执行器**先复位、再上行且恰好一次**（顺序以记录列表逐元素断言）。
- `EntryDetailDestructiveConfirmWiringTest`（4 例，静态接线守卫，idiom 沿用 `SettingsSubscreenScaffoldWiringTest`）：
  ① 执行器调用点 == 2（带「= 」前缀排除同文件定义行，段组件在位作反向哨兵）；
  ② `onDeleteEntry()` 裸调用 == 0（只能以引用传入 `propagate`）；③ `onRollbackRevision(` 调用 == 2 处
  （确认闸门的 `propagate` 闭包 + 差异对话框本体——后者无确认步骤、不属本项两份闸门，不在整改范围），
  且确认闸门那处必须形如 `propagate = { onRollbackRevision(rev) }`；
  ④ 两个触发态复位各只允许 1 份、写在执行器 `reset` 实参里。
