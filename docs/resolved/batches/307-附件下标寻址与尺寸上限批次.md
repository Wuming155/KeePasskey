## 1. 条目正文（原样收录）

### `ISSUE-P3-295`：附件面两处——按文件名（而非 `refIndex`）取字节致同名导出错内容；添加时无尺寸上限

- **核实时间点**：2026-09-23 经同名可否产生的前提核实（本仓**不可**产生同名不同内容，只能来自外部库；首轮所提「改按 UI 的 id 取字节」的修法前提被否证）。
- **核实方式**：① `app/.../data/repository/VaultEntrySecretReader.kt:279` 以 `attachments.firstOrNull { it.name == fileName }` 取字节，调用方 `EntryDetailAttachmentExporter.kt:39` 传 `attachment.fileName`，Toast 亦只报文件名 ⇒ 外部库（KeePass XML / Bitwarden / 桌面版）含同名附件时导出 A 得 B 的字节且提示为 A。解析侧逐 `<Binary>` 节点 emit、去重器原样保留 `name`（`KdbxXmlBinaryNode.kt:208-238`、`KdbxBinaryDeduplicator.kt:84-92`）；本仓编辑页按 fileName 视为替换（`EntryEditViewModel.kt:330-341`）故不自产同名。**修法前提**：`VaultEntryMapper.kt:60` 的 UI `id` 就是 `"${entry.id}_${att.name}"`（名字派生），改按 id 无法消歧，**须按 `refIndex` / 列表下标**。② `ui/screens/edit/EntryEditPickers.kt:64` 对 `*/*` 选择结果整份 `readBytes()` 交 `EntryEditViewModel.kt:330-341`；全仓无 `MAX_ATTACHMENT` 类约束（`BinaryStore.kt:47-57` 的 1 MiB 是落盘阈值非上限；`KdbxXmlBinaryNode.kt:58` 的 `AttachmentBudget` 默认 `unlimited()` 且只封解析不可信库）；无路径穿越面（`FileBinaryStore.kt:38` 只用固定目录名）。
- **涉及文件**：`app/src/main/java/com/keepasskey/app/data/repository/VaultEntrySecretReader.kt`、`app/src/main/java/com/keepasskey/app/ui/screens/detail/EntryDetailAttachmentExporter.kt`、`app/src/main/java/com/keepasskey/app/ui/screens/edit/EntryEditPickers.kt`、`app/src/main/java/com/keepasskey/app/ui/screens/edit/EntryEditViewModel.kt`。
- **验收标准**：AC① 附件寻址改按 `refIndex`（或树内下标），UI 的 `id` 生成同步去名字依赖；同名场景用例：导入含两个同名附件的第三方库 → 分别导出各自字节；AC② 对「添加无上限」给结论：设尺寸上限并如实提示，或维持现状并登记 `PD-*`（现状属用户自选大文件自伤 OOM，无攻击者面，故 P3）；AC③ 若设上限，须与解析侧预算的口径统一（`ISSUE-P1-276` 已 §273 闭环，现行三面判据与常量见 `database/src/main/java/com/keepasskey/database/xml/KdbxAttachmentBudget.kt`：单条目物化 ≤ 64 MiB / 引用次数 ≤ 1024 / 内联累计 ≤ 64 MiB），禁两套数字。

**开工前前提复核（2026-09-24）**：成立。① 取字节确按 `it.name == fileName` 匹配、调用方确传 `attachment.fileName`；UI `id` 确为 `"${entry.id.toHexString()}_${att.name}"`（名字派生）；② 添加入口确无任何尺寸约束（`readBytes()` 整份读入）；③ 解析侧预算常量确为 `internal class AttachmentBudget` 的伴生常量（app 侧不可见 ⇒ 须先建立公开的单一数字来源，见 §2.2）。

## 2. 整改

### 2.1 寻址键改「附件下标」（AC①）

| 位置 | 改前 | 改后 |
|---|---|---|
| `VaultRepository.getAttachmentData` | `(entryId, fileName: String)` | `(entryId, refIndex: Int)` |
| `VaultEntrySecretReader.getAttachmentData` | `attachments.firstOrNull { it.name == fileName }` | `attachments.getOrNull(refIndex)` |
| `UiAttachment` | — | 新增 `refIndex: Int = -1`（`-1` = 无库内下标，仅编辑会话新添加项） |
| `VaultEntryMapper` 投影 | `id = "${entryId}_${att.name}"`、`map {}` | `id = "${entryId}_$index"`、`mapIndexed {}`、`refIndex = index` |
| `EntryDetailAttachmentExporter` | 传 `attachment.fileName` | 传 `attachment.refIndex` |

- **下标越界 / 负下标返回 null**（不回落到同名项）——这是本条的要点：**同名不得再被当作寻址键**。
- Toast 仍报**文件名**（那是给用户看的显示名），但字节按下标取 ⇒ 「提示与字节一致」。

### 2.2 添加上界（AC②）：设上限，且与解析侧**同一数字**（AC③）

- AC② 取「设尺寸上限并如实提示」分支（未走 `PD-*` 维持现状分支）。
- 新增公开单一数字来源 `database/.../xml/AttachmentSizeLimits.kt`：
  `MAX_ATTACHMENT_BYTES = 64 MiB`；解析侧的 `AttachmentBudget.MAX_INLINE_MATERIALIZED_BYTES`
  改为**由它派生**（原为同值字面量）⇒ 全仓该量级只剩**一个字面量**，AC③ 的「禁两套数字」得到结构保证。
- 拦截时机在 `EntryEditPickers` 附件选择回调内，且**先用 `openAssetFileDescriptor(...).length`
  按申报长度拦一次**（provider 能给长度时，超大盘外文件根本不会被读进内存），
  再在读入后做**兜底二次判定**（长度不可得 / 流实际更长），兜底分支命中时先 `fill(0)` 再提示。
- 提示文案 `edit_attachment_too_large`（中英成对），上限数值经**参数注入**（`%1$d MB`），
  文案里不另写一份数字。

## 4. 如实声明

1. **同名附件只能来自外部库**：本仓编辑页按 `fileName` 视为替换故不自产同名，本条的缺陷形态需外部库
   （KeePass XML / Bitwarden / 桌面版）含同名附件才显现——用例以**手工构造**的同名两条覆盖，符合该前提。
2. **未做真实第三方库端到端对拍**：本条是**寻址语义**修复（下标 vs 名字），不涉 KDBX 格式读写；
   解析侧的 `<Binary>` 名称保留行为未改动。故未跑 `.kdbx` 语料校验与 KPEX 对拍。
3. **上界与解析侧预算同源自 64 MiB，但语义不同**：解析侧是「不可信库的物化预算」，本条是「用户自选文件的上界」；
   两者共用取值是因为**同一堆界论证**（低端机 192 MiB 堆），不是同一判据——已在 `AttachmentSizeLimits` KDoc 写明。
4. **`hygiene-gate` 两条仍为红**（`tier1=4` / `functions_ge_100=2`），属 `ISSUE-P3-305` 范围，本批未触碰。
5. **无设备侧必跑项**：未触 `*/src/androidTest/**`、未改原生内核；超限提示的真机交互面（SAF 选择器）
   属既有 instrumented 覆盖之外，本批以静态 + 单元用例承接。
