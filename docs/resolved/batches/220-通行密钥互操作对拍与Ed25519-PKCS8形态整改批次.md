## 1. 条目原文（原样收录，剪切自 `docs/ACTIVE_ISSUES.md`）

### ISSUE-P2-210：通行密钥 `KPEX_PASSKEY_*` 互操作**仅格式面证据**，缺官方实现端到端对拍（限界 §4.3 解除条件，用户强制验收门槛）

- **背景与证据**（2026-09-19 核实）：写入形态自 §149 起已是 KeePassXC / KeePassDX 口径
  （`core/src/main/java/com/keepasskey/core/model/PasskeyData.kt:134-153` 写 `KPEX_PASSKEY_*` + PKCS#8 PEM），
  但既有对拍全部是「自家 writer → 自家 reader」与格式常数断言（`PasskeyDataSchemaInteropTest` 8 例 /
  `PasskeyPkcs8CodecTest` 9 例）——**核实方式**：2026-09-19 全仓 `grep -rn "keepassxc-cli\|pykeepass"`
  作用于 `*.kt` 命中仅 `database/.../OwnProductInteropProbeTest.kt` 的 KDoc 字符串，且其被验对象是
  KDBX **时间编码（D1）**，与通行密钥无关 ⇒ 通行密钥面**零**外部官方实现参与。
  [`已知工程限界.md`](../../architecture/已知工程限界.md) §4.3 已自陈「只有格式面证据 / 未用
  `keepassxc-cli` / `pykeepass` / 真实 KeePassDX 对拍」，其**解除条件**即「以官方实现打开本仓产出的库
  并成功读取 / 使用该通行密钥」。
- **本机工具链已实测可用**（2026-09-19 核实方式 = 实跑）：`pykeepass 4.2.0`（`create_database` /
  `set_custom_property(protect=)` / `get_custom_property` / `is_custom_property_protected` 均可用）、
  `keepassxc-cli 2.7.12`（`show --all -s` 可读出含受保护值的全部自定义属性）、
  `python cryptography 50.0.0`（可独立产出 PKCS#8 PEM EC / Ed25519 私钥）。
- **涉及文件**：`database/src/test/.../PasskeyInteropProbeTest.kt`（新增）、
  `database/src/test/resources/fixtures/`（外部实现产出的只读 fixture）、`tools/passkey-interop/`（新增脚本）、
  [`docs/architecture/已知工程限界.md`](../../architecture/已知工程限界.md) §4.3。
- **验收标准**：① 探针经**生产写入路径**（`PasskeyCryptoEngine` 生成 + `PasskeyData.toCustomFields` +
  `KdbxFile.save`）产出含 `KPEX_PASSKEY_*` 通行密钥条目的 `.kdbx`，并生成 `PASSKEY_PROBE.md`
  （SHA-256 / 口令 / 外用复现命令）；② `keepassxc-cli` 与 `pykeepass` **各自独立**读出全部 KPEX 键、
  保护位与 PKCS#8 PEM 完整性（`PrivateKeyInfo` 可解析、OID 与算法一致），命令与原文输出留痕；
  ③ **反方向**：由 `pykeepass` + `cryptography` 独立产出、**不含**任何 `Passkey.*` 扩展键的 KPEX 库，
  经生产 `KdbxFile.load` + `PasskeyData.fromCustomFields` 解析成功，算法由 PKCS#8 OID **字节嗅探**得出，
  且该私钥经生产通道还原后**能真实签名并通过公钥验签**；④ `.\gradlew.bat test` 全绿；⑤ 结论回填限界 §4.3 与批次文档。

### ISSUE-P2-211：Ed25519 通行密钥的 PKCS#8 PEM 写成 `version=1` + `publicKey [1]`，OpenSSL 系实现（KeePassXC）拒收 ⇒ 互操作失败

- **背景与证据**（2026-09-19 由 `ISSUE-P2-210` 的外部对拍首次暴露）：
  `crypto/src/main/java/com/keepasskey/crypto/passkey/PasskeyPkcs8Codec.kt:112-123` 的
  `encodeEd25519ToPem` 直接取 BC `PrivateKeyInfoFactory.createPrivateKeyInfo(...)` 的 DER，
  其形态为 `30 51 02 01 01 …`——**version = 1** 且带 `publicKey [1] IMPLICIT BIT STRING`
  （RFC 5958 `OneAsymmetricKey`）。
  **取证方式**：`PasskeyInteropProbeTest` 产出的 Ed25519 条目经 `pykeepass` 读出 PEM 后交
  `cryptography`（OpenSSL 后端）解析 → `ASN.1 parsing error: extra data`；随后以三份手写 DER
  逐个送 `load_der_private_key` 做**隔离实验**，结论为「只要 version=1 即被拒」，
  而 `version=0` + 内层双包 `04 22 04 20` 通过。
  本仓自身解码器接受该形态（`PasskeyPkcs8Codec.kt:69` 的 `PKCS8_VERSIONS = setOf(0, 1)`），
  故「自家 writer → 自家 reader」长期全绿，缺陷得以藏身。
  RFC 8410 §10.3 已就此警示：「部分私钥导入函数尚不支持 RFC 5958 的 `OneAsymmetricKey`
  结构，会拒绝含 `publicKey` 的私钥结构」，并给出 version=0 的编码示例。
- **后果**：Ed25519 通行密钥落库的 `KPEX_PASSKEY_PRIVATE_KEY_PEM` 在 KeePassXC / KeePassDX 侧
  **无法导入**（ES256 与 RS256 的 DER 形态经同一脚本核对正确，不受影响）。
- **涉及文件**：`crypto/.../passkey/PasskeyPkcs8Codec.kt`、`crypto/src/test/.../PasskeyPkcs8CodecTest.kt`。
- **验收标准**：① 编码侧 Ed25519 改为输出 **version = 0 的 `PrivateKeyInfo`**（无 `publicKey`、
  无 `attributes`），内层仍为 `CurvePrivateKey` 双包 OCTET STRING；② 解码侧**继续接受 v0/v1**
  （存量库不回归）；③ 新增形状守卫用例锁定 DER 结构（顶层恰 3 成员、version=0、总长 46 字节），
  既有往返用例保留；④ `crypto` 单测 + `tools/passkey-interop/verify_interop.py` 全绿；⑤ 结论回填限界 §4.3。

## 2. 整改

### 2.1 补齐互操作对拍（`ISSUE-P2-210`）

新增工具目录 [`tools/passkey-interop/`](../../../tools/passkey-interop/README.md)：

| 组件 | 职责 |
|---|---|
| `PasskeyInteropProbeTest.kt`（新，`database/src/test/.../file/`） | 经**生产写入路径**（`PasskeyCryptoEngine` 生成 → `PasskeyData.toCustomFields` → `KdbxFile.save`）产出含 ES256 / Ed25519 / RS256 三条 KPEX 条目的 `.kdbx` + 机器可读清单 + `PASSKEY_PROBE.md` |
| `verify_interop.py`（新） | **权威判据**：`pykeepass` 逐字段 + `cryptography` 独立解析 PEM 并重导出公钥 + `keepassxc-cli` 交叉核对；退出码 1 即失败 |
| `make_external_fixture.py`（新） | 用 `pykeepass` + `cryptography`（**均非本仓实现**）产出读取半边 fixture，内建「不得含 `Passkey.*` 扩展键」自检 |
| `PasskeyInteropExternalFixtureTest.kt`（新，`database/src/test/.../file/`） | 读取半边：外部产出的 KPEX 库经生产读路径还原，算法由 OID 嗅探，且**能真实签名并被外部公钥验签** |

**判据构成**（每条目 38 条 × 3 条 = 114 条）：必需 KPEX 键齐备 / 公开材料逐字段相等 /
保护位与 KeePassXC 口径一致 / `FLAG_*` 为 `1`·`0` 文本 / 扩展键算法一致 /
PEM 内层 DER 摘要一致 / `cryptography` 独立解析 PEM 并由私钥重导出公钥**与产物公开公钥逐字节相等** /
PRF 存在性与 32 字节 / 双实现对 6 个键的读数交叉相等。

### 2.2 修复 Ed25519 PKCS#8 形态（`ISSUE-P2-211`）

`PasskeyPkcs8Codec.encodeEd25519ToPem` 不再使用 BC `PrivateKeyInfoFactory`（其产出 RFC 5958
`OneAsymmetricKey`），改为新增私有 `ed25519PrivateKeyInfoDer(seed)` **手工构造最小形态**：

```
SEQUENCE {
  INTEGER 0                                 -- RFC 8410：无 publicKey ⇒ version 必须为 0
  SEQUENCE { OID 1.3.101.112 }              -- AlgorithmIdentifier，parameters 必须缺省
  OCTET STRING { OCTET STRING (32) seed }   -- privateKey 内承载 CurvePrivateKey（双包为规范要求）
}
```

解码侧**不动**（继续接受 v0/v1），并在 `PKCS8_VERSIONS` KDoc 就地写明「编码侧只写 v0、解码侧接受 v1
是为存量库」的理由。

## 4. 过程缺陷与如实声明

0. **条目原文的一处笔误更正（保留原文，另加本节更正）**：`ISSUE-P2-211` 验收标准 ③ 原写
   「总长 46 字节」——**46 是外层 SEQUENCE 的「内容长度」（`0x2e`），DER 总长为 48 字节**
   （外层头 2 + 内容 46）。实现侧的契约常量取 **48**（`PasskeyPkcs8CodecTest.DER_TOTAL_BYTES`），
   并已由 OpenSSL 产出的同形 DER（`302e020100300506032b6570…`）交叉核对。原文按「只搬迁不改写」
   保留，以此更正为准。
1. **对拍脚本自身的口径缺陷（本批首次运行时暴露）**：清单按「PEM 文本字节」取 SHA-256、
   脚本按「剥装甲后的 DER」取 SHA-256，两侧口径不一致 ⇒ 首轮 3 条判据不通过中**有 2 条属脚本口径问题**，
   仅 1 条（Ed25519 解析失败）是被验对象的真实缺陷。两侧统一按 DER 取摘要后消失。
   **不得**把首轮的「3 条不通过」读作 3 个产品缺陷。
2. **本批**未执行**「端到端真机贯通（github.com）」**：该链路需真实浏览器 + 真实 RP 交互 +
   用户在系统 CM 选择器上点选 + 生物识别，`ISSUE-P2-83` AC③ 的 `cmd credential` 入口在设备上
   返回 `No shell command implementation`，无自动化入口（限界 §4.1 已登记）。已给出可执行的手工冒烟清单
   （记录文档 §6），**本轮以「未执行」如实登记，不以任何形式声称该链路已验证**。
3. **互操作结论的边界**：本批证据是**文件级 / 离库**的（字段键名、保护位、PEM 可解析、公钥一致、
   签名可用）；**不含** CM 通道交互、**不含**「用外部管理器完成一次真实 RP 登录」、
   **不含** PRF 与真实 RP 的对拍。限界 §4.3 的边界条款已按此更新。
4. **v1 旧条目不自动迁移**的口径不变。
5. 本批**未**修改任何 `crypto/src/main/rust/**` 或 JNI 导出签名，故符号契约数不变。
