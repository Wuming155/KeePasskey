## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：`crypto/.../cipher/CbcStreams.kt:216-233` 每读满一个 64 KiB 块产生
  `ByteArray(chunkSize)` + `concat`（合并 pending 与整块）+ `pending = all.copyOfRange` + `transformBlocks` 的
  `slice = source.copyOfRange`（又一份整块），随后 `Arrays.fill(all, 0)` 与下轮 `wipeBuffers()` 再清一次
  ⇒ 约 **4 次 64 KiB 分配 + 3 遍整块内存搬运**；加密侧 `emitAlignedBlocks`（`:103-117`）每块再多一次
  `buffer.copyOf(aligned)`。该路径服务原生 Twofish（整库数据流）。
- **整改方向**：`chunk` / `slice` / `out` 改**实例级复用缓冲**（构造时分配一次，`Arrays.fill` 清零语义保留）；
  `concat` 改「pending 固定 16 B 缓冲 + 双缓冲轮换」；`transformBlocks` 让变换以 `(offset, len)` 工作，
  去掉 `copyOfRange`；`emitAlignedBlocks` 同理用预分配 scratch。
- **验收标准**：往返字节级一致；填充非法 / 长度非整数倍 / 提前 `close` 三类流式语义逐例对齐 JCE 基线
  （既有 `CbcStreamFramingTest` 为基线）；用毕清零语义逐条保留（含抛异常路径）。
- **核实时间点与方式**：2026-09-17 读 `CbcStreams.kt:95-300` 核实。
- **风险提示**：属**主加密数据面**（与 `ISSUE-P3-155` 同族），高回归面，须排在零风险项之后；
  「复用缓冲」**不得**成为「不清零」的借口——清零责任须逐路径重述。

## 2. 开工复核结论（决定了本批能做到哪一步）

读实现后发现一条**既有代码已经依赖、但 KDoc 未声明**的事实，它决定了复用的边界：

- `CbcBlockTransform` 的 `typealias` KDoc 只说「`data`（长度须为 16 的整数倍）→ 变换结果」，
  并在加密侧注释里写「原地加密与否由变换实现决定」——**契约上是实现自定**；
- 但 `transformBlocks` 的 `finally { Arrays.fill(slice, 0) }` **已经依赖「变换返回独立结果数组」**：
  若某实现原地返回入参，该 `finally` 会把刚产出的明文自己抹掉（且 `NativeTwofish` 流式用例会立刻变红）。
  ⇒ **事实上契约 = 「返回独立数组」**，本次复用输入缓冲与该事实同源、不新增假设。

据此本批把它由**隐式前提**升级为**显式校验**（见 §3 的 `requireDistinctResult`），
并以用例锁定（见 §4）。

## 3. 本批实现（解密侧：3 处 64 KiB 分配 → 0）

| 原实现（每 64 KiB 块） | 现实现 |
|---|---|
| `val chunk = ByteArray(chunkSize)`（64 KiB） | **删除**：改为实例级 `buffer = ByteArray(chunkSize + Pkcs7.BLOCK_SIZE)`，其头部 `[0, pendingLength)` 承载扣留的末分组、其后为本轮载荷 |
| `concat(pending, chunk, read)`（≈64 KiB+16 新数组 + 两段拷贝） | **删除**：`pending` 改「**偏移 + 长度**」（`pendingLength`），下一轮直接读进 `buffer[pendingLength..]`，末分组用 `arraycopy` 原地前移（同数组重叠拷贝由 `arraycopy` 保证语义） |
| `transformBlocks(all, 0, keep)` 内 `source.copyOfRange(...)`（≈64 KiB） | **稳态路径删除**：新增实例级 `bodyScratch`（长度恒为 `chunkSize`），把载荷 `arraycopy` 进去后交给变换（零分配）。**首块与尾部路径**（载荷长度 ≠ `chunkSize`）沿用原 `transformBlocks`，每流各至多一次 |
| `Arrays.fill(all, 0)`（整块清零） | 保留但**收窄到载荷区**：`Arrays.fill(buffer, Pkcs7.BLOCK_SIZE, filled, 0)`（不得覆盖已前移的末分组） |
| `wipeBuffers()` 清上一轮明文 | **逐字保留**；`close()` 追加清 `buffer` / `bodyScratch` / `chain` / `pendingLength` |

⇒ 稳态（除首块与末块外）**零新增大数组分配**、零整块拷贝（只剩一次 64 KiB `arraycopy` 到复用 scratch）。
**首块 / 末块**各保留一次分配（载荷长度非 `chunkSize`，无法套用定长 scratch —— 见 §5 第 1 条）。

**新增契约校验**：`requireDistinctResult(transform(...))` —— 变换结果不得与 `bodyScratch` 别名，
否则抛 `IllegalStateException`（把「下一块会覆盖尚未交付的明文」这一**静默错误**变成**响亮失败**）。

## 5. 边界如实声明（不得外推）

1. **未改变换契约 ⇒ 仍有两处分配/拷贝未消除**（AC 的 `(offset, len)` 部分）：
   `transformBlocks` 的 `copyOfRange` 与加密侧 `emitAlignedBlocks` 的 `buffer.copyOf(aligned)`
   都是「变换只接受**整数组**」这一签名导致的——去掉它们必须把 `CbcBlockTransform` 改成
   `(key, chain, data, from, to)` 形式。而该变换的唯一生产实现是
   `NativeTwofish.decryptBlocks(key, iv, data)`（`TwofishCipherEngine.kt:78`），
   改动会触及 **JNI 定长布局契约**（`AGENTS.md` §3.2：跨 FFI 只传基本类型与数组）
   ⇒ 属**跨 FFI 契约变更**，**本批不做**（收益是每块 1 次分配，代价是主加密数据面的 FFI 面改动）。
   同理由此**加密侧未做**（其 `copyOf` 同因签名受限）。
2. **无任何性能实测**：本批是**分配/拷贝次数**的结构性削减（稳态 3 → 0 次大数组分配），
   **未**做吞吐或耗时对比，**不得**宣称百分比收益。
3. **块的量级是估算**：`10 MiB / 64 KiB ≈ 160 块` 用于说明量级，非实测采样。
4. **实例内存形态变化（如实声明）**：原实现每块临时分配、由 GC 回收；现改为**连接期常驻**
   `buffer`（64 KiB + 16）+ `bodyScratch`（64 KiB）≈ **128 KiB/流**。该流在外层 Twofish 路径上
   同时至多一个实例，量级可忽略，但**不得**读作「内存占用下降」。
5. **清零语义逐条保留、但位置有调整**：载荷区改为「按 `[Pkcs7.BLOCK_SIZE, filled)` 区间清零」
   （原为整块 `Arrays.fill(all, 0)`），因为末分组已前移到缓冲头部、不得被覆盖；
   明文侧（`out` / `wipeBuffers` / `close`）与 `chain` 的清零路径**未变**。
6. **JCE 基线对齐是既有用例承担的**：本批**未**新增流式语义用例（三类错误语义与分段对齐仍由
   `CbcStreamFramingTest` 的 10 例覆盖）；**未跑 `keepassxc-cli` 官方 CLI 对拍**（`§120` 的那套
   跨实现对拍未复跑），故**不得**声称「互操作已复核」。
7. **未跑设备侧 / `assembleRelease`**；本条只触及 Twofish（原生）流式路径的框架层，
   AES / ChaCha20 走 JCE，不受影响。

## 6. 过程缺陷与留痕

1. **一次实现缺陷并由既有用例当场抓住（3 例红）**：首版把「稳态载荷恒为 `chunkSize`」当作
   无条件前提，**忽略了首块尚未扣留末分组**（此时载荷为 `chunkSize - 16`）⇒
   首块多解密一个分组、结果错位；`CbcStreamFramingTest` 的
   `解密侧与 JCE CipherInputStream 多长度一致` / `小分块解密与默认分块结果一致` 与
   `TwofishNativeParityTest` **同时变红**（**这正是既有基线用例的价值**）。
   修法：`keep == chunkSize` 才走复用快路径，否则沿用一次分配路径。
2. **一次断言设计错误**：新增的契约用例首版直接 `stream.read(64 KiB)`，而单次 `read` 只消费
   首个 refill 的产物 ⇒ 走不到稳态快路径、校验不触发（用例假红）。改为 `stream.copyTo(...)`
   读到稳态，并就地注明「必须读到稳态那一轮」。
