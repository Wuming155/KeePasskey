## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

### ISSUE-P3-168 冲突同步周期最多 6 次全量 KDBX 加解密（每次各跑一遍 KDF）

- **背景**：`app/.../sync/SyncCycleRunner.kt:127` 在内存基线缺失时解析缓存快照，
  `:131` 序列化本地库，冲突时 `SyncConflictController.kt:227` 又把**刚序列化出的字节解析回树**，
  再解析远端字节（`:229`）与 base 快照（`:244`），合并后再序列化一次（`:288`）⇒ 常态冲突周期
  = 4 次全量 load + 2 次全量 save = **6 次 KDF 派生**（KDBX4 默认 Argon2id，单次数百毫秒量级），
  且全程持 `SyncSessionState.mutex`。其中 `parse(localBytes)` 的产物与内存会话树等价，属可省的一次解密。
- **整改方向**：① 合并直接用会话内存树构造待合并模型，仅在字节与内存树可能不一致时回落解析；
  ② 为 `SyncDatabaseCodec` 加会话级「内容摘要 → 已解析树」缓存（锁内使用，锁库 / 超限即 `clearSensitiveData` 淘汰）。
- **验收标准**：同一冲突周期内 KDF 派生次数下降（调用计数/日志断言）；合并结果与现状逐字段一致；
  `§90` 的防回滚不变量与 `§114` 的 TOTP 缓存失效点全绿；缓存淘汰路径有显式擦除断言。
- **核实时间点与方式**：2026-09-17 读 `SyncCycleRunner.kt:127-139`、`SyncConflictController.kt:220-292` 核实。
- **风险提示**：树级缓存**扩大解密明文的驻留面**，必须按 `§52`（同步解析落盘与内存池擦除边界）同口径登记
  所有权与擦除责任，否则不得实施；本条属高回归面，排在零风险项之后。

## 2. 开工复核：条目自身有两处前提需更正（**先读实现再动手**）

1. **行号漂移**：`SyncConflictController` 的四处引用整体 **+10 行**（`:227/:229/:244/:288` →
   `:237/:239/:254/:298`），根因是 `03e6052`（§123 批次，ISSUE-P3-161）改动；本文档一律按当前行号。
2. **KDF 次数口径偏低**：真实常态冲突周期是 **4 次 load + 4 次 save = 8 次 KDF**，而非条目所记 6 次——
   条目只数了 `SyncDatabaseCodec` 的两处 save，漏掉 `SyncCycleRunner.kt:264`（快速提交冲突分支 R3 落盘）
   与 `:363`（`ConflictDetected` 分支 R3 落盘）以及 `SyncConflictController.kt:311`（合并上传后落盘）
   三处 `databaseSession.save()`（每处同样各跑一遍 KDF）。**本批不改变这些写盘点**（改了会影响
   `databaseFlow` 发射次数 ⇒ 触及 §114 的 TOTP 缓存失效点与 §90 的「拒绝即不覆盖」判据），
   故「8 → 7」是本批的实际收益边界。
3. **可复用性前提（逐点核实成立）**：`KdbxMerger.mergeDatabases(base, local, remote)` 接收的是**三棵树**，
   不是字节 ⇒ 把本地侧换成内存树**在合并器一侧零签名改动**。
4. **等价性的两条来源**（AC ① 的「仅在可能不一致时回落」正是把这两条写成前置条件）：
   - 快速提交路径（`tryFastCommitPath`）：本周期 `localBytes` **刚由 `currentDb` 序列化而来**（`:130-136`）；
   - `openRemote` → `ConflictDetected` 路径：`openResult.localBytes` 实为**引擎读出的缓存字节**（`SyncEngine.kt:140`），
     而 `localBytes` 与缓存快照的等价由 `SyncContentChangeDetector.resolveLocalContentChanged` 保证
     （判定「本地内容无变化」⇒ 会话树内容 ≡ 缓存快照字节；判据是 `KdbxContentComparator` 的全字段内容比较）。
   两条之外没有第三处合并入口（`applyForcedConflictStrategy` 不做三方合并）⇒ 回落路径保留但不生效，
   仅作未来调用方的安全阀。
5. **不得在合并内重读 `databaseFlow`**：同步周期持 `SyncSessionState.mutex`，但 **UI 写路径不取该锁**
   （只取 `DatabaseSession.mutex`）⇒ 合并内重读可能拿到与 `localBytes` 不对应的树，与随后上传的字节产生分歧。
   故一律使用**本周期起点**的快照 `currentDb`（`:76`）。

## 5. 边界如实声明（不得外推）

1. **AC 的「调用计数 / 日志断言」未按原文落地**：宿主侧**没有可注入的计数缝**——`SyncDatabaseCodec` /
   `SyncConflictController` / `DatabaseSession` 全是无接口的 `final class`，注入替身需先把它们抽接口或改 `open`
   （属**安全面 / 架构面**的独立改动，本批不做）。故「少一次解析回树」以**接线守卫（源码级调用点断言）**承担，
   与 §125 的既有口径一致；**不得**读作「已用运行期计数证明 KDF 次数下降」，**更不得**换算成耗时百分比（无实测）。
2. **8 → 7 是源码结构结论**：本批只消除 `parse(localBytes)` 一处；其余 3 次 load（缓存快照 / 远端 / base）
   与 4 次 save 的写盘点**一律未动**（动它们会改变 `databaseFlow` 发射次数，触及 §114 TOTP 缓存失效点与
   §90 「拒绝即不覆盖」判据）。
3. **等价性差分证据的覆盖面**：2 例差分覆盖「并集自动合并」与「条目级字段冲突 + KEEP_LOCAL」两条分支，
   输入含双方各新增条目 / 分组；**未**覆盖附件（`binaries` 池形态与内联 / 落盘阈值差异不在快照内）、
   墓碑（场景不产生 `deletedObjects`）、历史快照（`history` 只比条数）、`times`（刻意排除）。
4. **等价性的前提是「可证」而非「恒真」**：`ConflictDetected` 路径依赖 `SyncContentChangeDetector` 的
   「本地内容无变化」判定（`KdbxContentComparator` 全字段比较，**刻意不比 `times`**）⇒ 若本地仅改 `times`
   而字段未变，改后的本地侧会取**会话树**的 `times` 而非缓存快照的 `times`（改动前取后者）。
   §10 已登记「生产可达面上不存在只改 `times` 的写入者」，故本批**未**为该差异设防；若日后出现该类写入者，
   必须重新评估此处。
5. **`save()` 期间可能替换会话树实例**：`DatabaseSession.save()` 在「确有历史修剪」时会
   `db.copy(rootGroup = prunedRoot)` 并写回 `core.database.value`。本批传入的是**周期起点快照**，
   故合并产物可能把刚被修剪掉的历史短暂带回内存树——**与改动前同构**（改动前解析的 `localBytes` 也是
   修剪前序列化的字节），且紧随其后的 `save()` 会再次修剪；**不是**本批引入的行为差异。
6. **AC ② 判定不实施**（会话级「内容摘要 → 已解析树」缓存）：理由与解除条件登记
   [`../architecture/已知工程限界.md`](../../architecture/已知工程限界.md) **§14**（驻留面 + 无擦除钩子 +
   无淘汰口径 + 风险不对称；且 ① 已吃掉其唯一「本轮可省」的那次解析）。
7. **未跑设备侧**：未跑 `connectedDebugAndroidTest` / `-DliveSyncTest`（真实联调）/ `assembleRelease` / `lint`；
   `§90` 与 `§114` 的回归依据是**全量单测**（`SyncRollbackGuardTest` 9 例、`SyncEngineTest` 27 例、
   `TotpCodeCacheTest` 5 例、`SyncCoordinatorTest` 5 例全部绿）。
8. **KDoc / 注释级引用无编译器保障**：更名与口径更新涉及多处 KDoc，已全仓 `grep` 复核；`docs/` 下历史归档
   正文按约定**只搬迁不改写**。
9. **P0 级擦除边界的真实风险已实测复现**：见 5.10 的变异验证——去掉判据后活动库**当场被清空**。
10. **变异验证 1 项**：把远端解析失败分支的 `if (localDbOwned) wipeDiscarded(localDb)` 改回无条件
    `wipeDiscarded(localDb)` ⇒ `SyncConflictMergeLocalTreeEquivalenceTest > 远端解析失败时不得擦除会话内存树`

## 6. 过程缺陷与留痕

1. **一次用例设计错误（与实现无关，当场发现）**：差分用例首版用 `KdbxUuid.random()` 造场景 ⇒ 两次对照运行
   的条目 / 分组 UUID 天然不同，快照比较退化为「比 UUID」，两条差分用例双双 FAILED（报错形态是
   `ComparisonFailure` 且两侧内容结构相同、仅 id 不同）。修法：改用**固定 UUID**（`uuidOf(hex)`，16 字节构造），
   并在测试 KDoc 写明「两次对照必须使用同一批标识」。**这是断言写错、不是实现错**（同一教训在 §137 也出现过）。
2. **一次编辑工具报错**：`if (localDbOwned) wipeDiscarded(localDb)` 在文件内有两处（远端解析失败 / 序列化失败），
   首次 `Edit` 因 `old_string` 不唯一被拒；补上下文（上一行注释）后成功。留痕以免后人误判为「改动未生效」。
3. **本批无编译失败**；但全量单测**两次撞上宿主侧既知偶发红**（均与本批改动**无因果关系**——本批只改
   冲突合并的树所有权，不触碰 `SyncCache` / 原子写盘）：
   - 第 1 次：`SyncEngineTest > 测试远端404丢失自愈恢复`，异常 `java.nio.file.AccessDeniedException:
     …<hash>.baseversion.<uuid>.tmp -> …<hash>.baseversion`（**`已知工程限界.md` §12 家族**：Windows 对
     「覆盖已存在目标」的 rename 在目标句柄未完全释放时拒绝）⇒ **定向复跑 4/4 绿**、随后全量复跑；
   - 第 2 次：`SyncCacheTest > clear 与 clearAll 均不删除防回滚状态文件`，断言值里出现**大写键名**的
     `<HASH>.VERSION.tmp`（**§7 家族**：目录枚举鬼影 / `isFile` 假阳性，约 3% 命中）⇒ **定向复跑 6/6 绿**、

   处置与 §107 / §132 一致：**不改产品代码、不改断言**（真残留仍必红，不构成放宽），并按 §12 的约定留痕。
4. **先读实现再动手再次奏效**：条目给的「6 次 KDF」与四处行号都需更正（见 §2），若照条目字面实施，
