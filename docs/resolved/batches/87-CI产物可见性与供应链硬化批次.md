### 87.1 ④ `mapping.txt`：公开仓库不得上传去混淆映射（**已整改**）

**缺陷形态**：GitHub Actions 的 artifact 对公开仓库而言**等同公开文件**。整改前
`build.yml` 的归档步骤带 `if: always()`、无任何可见性限制，`path:` 里一并列出
`app/build/outputs/mapping/release/{mapping,seeds,usage,configuration}.txt`。
对本应用（密码管理器）而言，这等于公开 **类 / 方法 / 字段命名全貌**——
任何人可据此把崩溃栈与反编译结果还原成可读符号，正好抵消 R8 的收益。
更糟的是仓内 `NOT-FOR-RELEASE.txt` 还把这当作既定事实写出来（「属公开去混淆信息」），
说明当时是**已知并接受**的状态，而非疏漏。

**整改**：

| 改动 | 说明 |
|---|---|
| 移出产物集 | `path:` 只保留 `*.apk` / `*.idsig` / `NOT-FOR-RELEASE.txt` |
| **保留审计能力** | 新增步骤把四份映射的**体积 / 行数 / SHA-256** 写入 `$GITHUB_STEP_SUMMARY`——原归档目的是「保留面审计」，摘要足够且可安全公开 |
| 说明同步更正 | `NOT-FOR-RELEASE.txt` 改为写明「映射不随产物归档」+ 完整映射的获取路径（本地 / 私有制品库），并提示不要粘贴进公开 issue / PR |
| **防回加守卫** | 新增 `CiArtifactVisibilityGuardTest`（4 例）：逐个 `upload-artifact` 步骤扫描窗口内不得出现 `outputs/mapping`；摘要步骤必须存在且覆盖四份文件；说明文案必须写明不归档；**三份工作流全部**扫描 |

**为什么不「改为私有 artifact」**：GitHub 没有「仅维护者可下载」的 artifact 可见性开关
（private repo 才天然如此，本仓为公开仓）；因此「可见性收窄」在平台能力上不可达，
可行解就是**不上传**＋**摘要留痕**。

### 87.2 ① 依赖校验 / 版本锁定：登记为已知限界

`gradle/verification-metadata.xml` 不存在（`gradle/` 仅 4 项，`dependencyLocking` /
`lockAllConfigurations` 全仓零命中）。**本批不引入**，理由：

1. 生成完整元数据需在**干净环境**以 `--write-verification-metadata sha256` 重写全量依赖图哈希，
   属独立工程（且会与依赖升级流程强耦合）；
2. 它防的是「依赖坐标被替换 / 投毒」，与既有
   `.github/workflows/dependency-scan.yml`（CVSS ≥ 7.0 **硬断言**）＋ Dependabot 覆盖的
   **advisory 面是不同威胁**，**不可互相替代**——故不把「已有扫描」当作本项的闭环理由，
   而是明确登记为**已知限界**（AC 允许的分支）。
