## 2. 为什么这次不是「逐字搬」而是「并三为一」

§178 / §179 / §183 / §186 / §187 都是窄参数段落组件的**原样下沉**，逐字性用
`check_verbatim_move.py` 复核。本批若照搬，只能把三段各自包一层，页面照样留着六条
`stringResource` 与三份重复分支——**收敛收益接近零**。故把两条同形判定并为一个组件，
代价是逐字性判据只能部分成立：

`python tools/doc/check_verbatim_move.py /tmp/old_hc.kt <新 HealthCheckScreen.kt> <HealthCheckComponents.kt>`
（`/tmp/old_hc.kt` = `git show HEAD:…HealthCheckScreen.kt`）报
**`orig_content_kinds=185 / MISSING_KINDS=29 / NEW_ONLY_KINDS=155`**。
29 条缺失项**逐条看过**，全部属下列三类机械改写，无一条是语义变更：

1. **`Triple` 容器本身**（`val weakStatus = if (…)`、`} else if (uiState.reusedPasswordCount > 0) {`、
   `icon = weakStatus.first`、`Triple(` ×6、`} else {` ×2 等）——由 `HealthAuditTone` + `when (tone)` 承担；
2. **`uiState.` 前缀消失**（`isWarning = uiState.hasHealthScanned && uiState.weakPasswordCount > 0` →
   `isWarning = tone == WARNING`；`R.string.health_leak_sub_breached, uiState.compromisedPasswordCount ?: 0` →
   `compromisedCount`）——值改由调用方以标量参数传入，**取法逐字照抄**（含 `?: 0`）；
3. **图标/配色/文案的三种字面量各少一份**（`Icons.Default.Security` need 2 have 0 等）——
   合并成一份后本就该少（这正是本批收益来源）。

⇒ **口径如实登记**：本批**不**声称「逐字搬移」，声称的是「判定等价 + 缺失行逐条可解释」。
等价性的关键一条：原 `isWarning = hasHealthScanned && count > 0` 与新
`tone == WARNING`（即 `hasScanned && count > 0`）**同值**，且「未扫描优先」的判序原样保留。

## 3. 判定为什么值得单独有宿主用例

`healthAuditTone` 的**代价是安全语义**：扫描前 `weakPasswordCount` / `reusedPasswordCount` 天然是 0，
判序若颠倒，未扫描时页面会亮「安全」徽标——ISSUE-P3-61 立这条就是为了禁止「以 0 冒充安全」。
此前这条判序只活在 Compose 内联链里，**无人可直调**。现收敛为纯函数并补 4 例：

| 用例 | 钉住什么 |
|---|---|
| 未扫描 + 计数 0 ⇒ `NOT_SCANNED` | 不以 0 冒充「通过」 |
| 未扫描 + 计数 2 ⇒ `NOT_SCANNED` | **判序**：未扫描优先于计数 |
| 已扫描 + 0 ⇒ `PASS` | 只有真扫描结果才给「通过」 |
| 已扫描 + 1 ⇒ `WARNING` | 「需注意」用 warning 不用 error 红的前提态 |

**刻意不测**的三条面：图标 / 配色 / 文案资源的映射（属呈现面，`UiMd3AlignmentWiringTest` 与截图包装覆盖）、
`HealthBreachAuditRow` 的五分支（`BreachCheckStatus` 是枚举且各分支只做资源选择，无判序风险，
且其「绝不以已防护掩盖未检测」的行为级证据在 `BreachCheckHealthTest` 的 VM 侧）；
`SessionLockGuardTest` 一类的样板测试不互相顶替的规矩同样适用。
