## 2. 本批实现

### 2.1 `TracerPid`：字节级解析 + 按线程缓冲（对应 AC ①）

- `ProcTracerPid` 新增**字节级重载** `parse(statusBytes: ByteArray, length: Int): Int?`：
  按 `\n` 分行、行首逐字节匹配 `TracerPid:`、只把**命中的那一行**的字段值物化成 `String`
  （原先物化整份 `status`）。两个入口**共用同一个** `parseValue(raw) = raw.trim().toIntOrNull()`
  ⇒ 二者不可能漂移。
- `ProcStatusTracedProcessProbe` 的读取缓冲改 `ThreadLocal` 复用（原每次调用新分配 8 KiB），
  `readStatusBounded()` 改为 `readStatusInto(buffer): Int`；`read <= 0` 的「不可判定」语义与
  原空串分支同义。
- **等价性**：`lineSequence()` 与我的按 `\n` 分行在**孤立 `\r` 分行**上有可分辨差异——
  已在 KDoc 写明；`/proc` 伪文件不产生该形态，且即便出现也只让一行读得更长、经 `trim()` 后同义。

### 2.2 maps：流式字节匹配（对应 AC ②）

- `detectHookFramework` 的 maps 分支改调 `containsHookMarker(input, chunkSize)`：
  **逐块读取 + 块间重叠**（保留 `maxMarkerLen - 1 = 8` 字节，保证跨块特征串不漏），
  块内做「首字节快速筛选 + 不区分大小写字节比对」，**全程零 `String` 分配**
  （原实现逐行解码 + 每行 6 次 `contains(ignoreCase = true)`）。
- **新增有界上限** `MAPS_SCAN_MAX_BYTES = 16 MiB`：超限即停止并落脱敏告警（fail-open，
  与「读取失败不视为攻击特征」同口径）。该上限同时**封住「hook `read` 后喂无限流」的挂死面**
  ——原 `useLines` 在无限流下会一直读到 OOM。16 MiB 远超真实 maps 规模，不构成检测面收窄。
- `containsHookMarker` 放入**伴生对象**（它不依赖任何实例状态，判据只由 `HOOK_MARKERS`
  与本节常量决定），并以 `internal` + 可选 `chunkSize` 暴露给用例——**这是本批最重要的可测性改动**：
  重叠窗口算错会静默漏掉恰好跨块的特征串，而那正是「改名 + 已注入」场景的检测依据。
- 特征串清单 `HOOK_MARKERS` / 落点清单 `HOOK_TRACE_PATHS` **逐项未改**（`§92` 的判据契约）。

### 2.3 刻意不做（AC ③）

`Debug.isDebuggerConnected() || Debug.waitingForDebugger()` 在 `detectSignals`（`:171`）与
`escalateForLiveSignals`（经 `liveDebuggerAttached()`，`:146`）各探测一次。**本批不做**，
理由是收益与回归面不成比例：两个布尔探针为**进程内静态查询**（无 IO、无分配），
而收敛它需要把「本次调用已探测到的信号」在两条路径间传递——`escalateForLiveSignals`
的语义与「实时信号 ⇒ COMPROMISED」的判定顺序由既有用例锁定（`§85` 的 TracerPid 门控批次），
为省两次布尔查询去动该契约不划算。**该子项保持未做并如实声明。**

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：「不再逐行物化 `String`」「不再每次分配 8 KiB」是**源码级分配与调用点**
   结论，**不得**宣称百分比收益，也不得推断真机填充 / 解锁时延。
2. **`/proc/self/maps` 的真实读取路径未被任何用例覆盖**：宿主 JVM 无该文件、
   `File(PROC_SELF_MAPS).exists()` 为 false；本批以「把**流式匹配**抽成可注入 `InputStream`
   的 `internal` 函数 + 以小块驱动边界场景」替代，**未做的**是「真实 maps 内容 + 真实 File 读取」
   的端到端断言 ⇒ **不得**读作「maps 层检测已按真实文件验证」。
3. **`MAPS_SCAN_MAX_BYTES` 是新增的行为边界**：真实 maps 超过 16 MiB 时本函数返回 false
   （未命中，且落脱敏告警）。该上限封住「hook `read` 喂无限流」的挂死面，但**意味着**
   「超限时漏报」——属**有意的 fail-open 取舍**，与既有「读取失败不视为攻击特征」同口径；
   **不得**读作「检测面未变」（超大 maps 场景下确有收窄，只是不现实）。
4. **ASCII 折叠与 `String.contains(ignoreCase)` 的等价性有前提**：清单全为 ASCII
   （已由用例锁定）。对非 ASCII 特征串，Java 的 `ignoreCase` 用 Unicode 大小写折叠，
   与本实现的 ASCII 折叠不同 ⇒ 若日后要加非 ASCII 特征串，**必须**同步改匹配实现。
5. **AC ③（`Debug` 探针去重）未做**（理由见 §2.3）⇒ 同一次调用内仍会各探测一次。
6. **未跑设备侧与 `assembleRelease`**；`§92` 的判据面用例（含真机基线文档断言）在宿主侧全绿，
   但**真机 maps 行为未复测**（本批未改清单、未改判定门槛，故未安排真机复测）。

## 5. 过程缺陷与留痕

1. **本批首次全量编译失败**（1 例）：`RuntimeIntegrityMarkerScanTest` 以伴生风格调用
   `RuntimeIntegrityDetector.containsHookMarker(...)`，而该函数当时是**实例方法** ⇒
   `Unresolved reference`。修法不是改测试的调用形态，而是把该函数（连同两个匹配助手）
   **移入伴生对象**——它本就不依赖任何实例状态。**该次失败未进入任何模块的测试执行**
   （`compileDebugUnitTestKotlin` 阶段即失败）。
2. **本批第二次全量 4 例断言失败**：`containsHookMarker` 的 `require(chunkSize > overlap)`
   被测试的 `chunkSize = 8` 触发（最长特征串 9 字符 ⇒ 重叠窗口 8，`8 > 8` 不成立）。
   **这是测试选参错误，不是实现错误**：`require` 恰好防住了「分块小于重叠窗口」这一会静默漏报的
   危险配置。修法为测试改用 `chunkSize = 16` 并相应对齐边界偏移，同时把这个约束写进测试 KDoc。
   ⇒ 该 `require` 是**有价值的护栏**，本批保留。
3. 上述两次失败均**如实留痕**，以便后人对齐基线时不会误用中间态。
