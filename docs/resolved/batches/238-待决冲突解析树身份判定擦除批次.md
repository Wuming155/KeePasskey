# §238 待决冲突解析树身份判定擦除批次

- **批次编号**：§238（`docs/resolved/README.md` 此前最大 §237）
- **日期**：2026-09-20
- **条目范围**：`ISSUE-P3-235`（`RC-02` 敏感缓冲所有权收口，**整条结案**——本批即其 AC② 的 `G2` 步）
- **主题**：把 `SyncConflictController` 独占持有的**解密解析树**（冲突待决期的 `pendingLocalDb` /
  `pendingRemoteDb` / `pendingMergedRoot`，以及一次合并判定的 `localDb` / `remoteDb` / `trustedBase` /
  未被采用的合并产物）由「只丢引用、等 GC」改为**按身份集合判定定点擦除后再丢引用**。
  这是 `RC-02`「缺失的不是意识而是收口点」在同步合并面的最后一处结构性缺口。

---

## 1. 缺陷与整改

### 1.1 缺口（`G2`，原条目残余）

`SyncConflictController` 是上述整树的**唯一持有者**，但 `clearPendingConflictSession()` 只把字段置 null。
在「冲突待决 → 用户直接锁定会话」这条路径上，`DatabaseSession.lock()` 只擦除**活动会话树**，
而 `pendingRemoteDb`（`codec.parseKdbxBytes(remoteBytes)` 的独立解析树，含远端独有条目的全部
`ProtectedString` 与 ≤ 落盘阈值的附件内联明文）**不在活动树内** ⇒ 其明文只随引用丢弃、等待 GC，
违反契约 R3（「**禁止**以等 GC 作为擦除手段」）。

### 1.2 为什么不能「顺手补一处 `clearSensitiveData()`」（P0 级风险）

`KdbxDatabase` 是 data class，且 `KdbxMerger` 对「单侧独有对象」**按原实例复用**：

- `localDb.copy(rootGroup = mergedRoot, …)` 会让合并树与来源树**共享同一批 `ProtectedString` /
  `KdbxAttachment` 实例**，且 `header` 实例亦被共享（data class 浅拷贝）；
- `resolveConflicts` 成功分支在 `updateDatabaseMeta { mergedDb }` **之后**才调
  `clearPendingConflictSession()` ⇒ 此刻活动会话树**就是**合并树。

⇒ 无判定的裸擦会**静默清空刚被采用的活动库内容**（`SECURITY_RECHECK_2026-09.md` §9.6 #3 / #19 同型）。
这正是 §52 / `ISSUE-P3-119` 当年把 `pending*` 明确判为「**不可擦而非漏擦**」的原因；
`ISSUE-P3-235` 的 `G2` 就是把该处变成**可擦**。

### 1.3 整改（两处收口点 + 一个判定原语）

| 交付物 | 内容 |
|---|---|
| 判定原语 | `SyncConflictMergeAdjudication.kt` 新增 `eraseDiscardedDatabase(db, live)` / `eraseDiscardedGroup(discarded, liveRoot)`：以 `live`（当前活动会话树）收集敏感实例**身份**（引用相等），只擦 `db` 中不被存活侧引用到的实例；**头部 KDF secret 另设一道护栏**——仅当 `db.header !== live?.header` 时才擦（共享头部误擦会写出错密钥的库）。`live == null`（会话终止：活动树已被先行擦除并置空）⇒ 全量擦除；`db === live` ⇒ 不动作 |
| 收口点 ①（`G2` 本体） | `clearPendingConflictSession()`：擦 `pendingLocalDb` / `pendingRemoteDb` / `pendingMergedRoot` 后再丢引用。它同时服务**决策路径**（活动树即刚采用 / 未改写的会话库 ⇒ 判定生效，合法）与**会话终止路径**（`SyncCoordinator.onSessionLocked`，存活侧为空 ⇒ 全量擦除） |
| 收口点 ②（同族补齐） | `autoMergeAndUpload`：① **上传失败** ⇒ 合并产物与三棵解析树**全部**失去持有者，逐棵判定擦除；② **成功** ⇒ 以 `updateDatabaseMeta` 后的活动树为存活侧，擦三棵来源树（合并树已上线，不列入）。此前这两条路径分别「什么都不做」与「只擦序列化失败分支」，属同一缺口的旁支，本批一并收口 |

**与池面无关**：`InnerHeader.binaries`（≤ 落盘阈值的附件明文）仍属 `已知工程限界.md` §1.6 的既定边界，
本批**未**触碰（准入①② 未变；契约 §6.2 新增第 5 条说明「`G2` 收口**不构成**池内擦除的准入」）。

### 1.4 结论更正留痕（如实）

契约 §7 Step 2 原记「`clearPendingConflictSession()` **结构上不是合法擦除点**」。该结论的**前提是
无判定的裸擦**；改为身份集合判定后它即为合法擦除点——契约 §7.1 本就限定「S 类只准许丢引用
**或身份集合判定**」。本批已在该文件就地更正，并将「`lastSyncedDb` 赋值点」现查计数
（**8 处**，非原记 5 处）与新增结论登记进 §4 / §7 / §8 / 附 A。

## 3. 如实声明

1. **自动合并成功路径的擦除效果不可外部观测**：该路径不进入 `pending*` 通道，解析树实例不外泄，
   故其用例只锁定「不误擦已采用实例」一侧（远端独有条目被原实例复用进活动库，逐字段可读）；
   「确实擦到了」由原语层用例与「会话终止」链路用例承担（二者均观测到 `ProtectedString` 转为清零态）。
2. **设备侧无新增必跑项**：本批**未**改动 `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 或任一
   `Native*` 绑定，**未**触及 `*/src/androidTest/**` ⇒ 按测试资产纪律②无设备侧义务。
   契约 §7 Step 2 原记「该链路改动须真机跑设备侧层」经复核**前提不成立**（该链路的既有覆盖
   `SyncConflictMergeLocalTreeEquivalenceTest` / `SyncCoordinatorTest` / 本批新用例**全在宿主层**，
   设备侧目录内不存在覆盖 `SyncConflictController` / `handleConflictMerge` / `clearPendingConflictSession` /
   `SyncCoordinator.onSessionLocked` 的用例），故按「测试资产纪律」只需宿主全绿；该更正已写入契约。
3. **`lastSyncedDb` 保持「只丢引用」**：其赋值点现查 8 处、右侧**全部**为
   `databaseSession.databaseFlow.value`（会话活动树的引用），擦除由 `DatabaseSession` 对活动树的那一次
   `clearSensitiveData()` 承担；本批只补充字段与方法的注释说明，**未**改其行为
   （逐树递归擦除会误伤新树共享的未修改子树，见 `KdbxGroup.clearSupersededSensitiveData` 红线）。
4. **池内二进制未变**（限界 §1.6）：`InnerHeader.binaries` 的擦除准入①② 仍未满足，本批零改动。
5. `SyncSessionState` / `SyncCoordinator` 的改动**仅为 KDoc 与注释**，无行为变更。
6. **过程留痕（分档越档已整改）**：首轮实现的 KDoc 与编排把 `SyncConflictController.kt` 推到 **405 行**，
   **越过 tier2（400~500）档沿**（`count_line_tiers.py` 由 `tier2=29` 变 `30`）。随即把
   `eraseDiscardedParseResults` 与其 KDoc 外移到同包 `SyncConflictMergeAdjudication.kt`
   （该文件本就是「无实例状态的合并判据 / 擦除原语」的落位处），文件回落到 **390 行**，分档恢复持平；
   外移为**纯移动**（调用点显式传入 `databaseSession.databaseFlow.value`），并已重跑反校复检（§2.1 末段）。
   本项登记缘由：分档持平是本仓长期度量，越档即使不触发门禁也必须如实留痕且整改。
7. **一次偶发红如实留痕（未以改用例 / 改实现掩盖）**：最终验证期间的一次全量 `test` 出现
   `AutofillPickerViewModelCredentialLookupTest`（缓存命中即免一次仓库单条查询 `expected:<0> but was:<1>`）
   与 `AutofillPickerViewModelSessionLockTest`（选择器缓存前提 `expected:<1> but was:<0>`）共 **3 例**失败；
   单独重跑这两类**全绿**、随后再次全量 `test` 亦**全绿**（`343/2402 failures=0`）⇒ 判为**跨用例状态污染类偶发**
   （与 §18 已处置过的「测试调度器跨用例污染」同族）。本批改动**只落在 `app/sync/`**（同步冲突会话与
   会话终止观察者路径），与自动填充选择器的缓存判据无调用关系，故不记为本次改动的回归；
   **未**为此修改任何用例或删改断言。
