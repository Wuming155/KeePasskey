## 2. 整改

### 2.1 AC①：复用既有宽松解码器 + 全仓 `Base64.getDecoder()` 清点

**生产改动（一处）**：`KdbxXmlMetaReader.kt` 的 `IconNode.end()` 由严格解码改为
`KdbxXmlValueUtil.decodeBase64LenientWhitespace(encodedData)`，异常类型由宽泛 `Exception` 收窄为
`IllegalArgumentException`（与 `KdbxXmlStringNode` / `KdbxXmlBinaryNode` 同口径），失败仍抛
`KdbxCorruptFileException`（**禁**降级为原始字节）。`import java.util.Base64` 一并移除。

**全仓清点（生产 `src/main`，2026-09-23）**——其余 `Base64.getDecoder()` 调用点**均非**同类「外部 KDBX XML 大段折行误拒面」：

| 位置 | 输入来源 | 是否同类误拒面 | 结论 |
|---|---|---|---|
| `KdbxXmlValueUtil.kt:33` | 宽松解码器内部（已剥空白后再交严格解码） | 否（即 D19 修复本体） | 保留 |
| `KdbxXmlValueUtil.kt:69/83` | UUID（16 字节 / 24 字符 Base64） | **理论同类、实践不可达**：定长短串不会被 76 列折行；已有 `trim()` 去首尾空白 | 本批不改（变更最小化） |
| `KdbxXmlTimeHelper.kt:175` | 时间（8 字节 / 12 字符） | 同上 | 本批不改 |
| `KdbxKeyFile.kt:106` | 密钥文件 v1.0 `<Data>` | **已自行剥空白**（`:74` `stripWhitespace` 后再解码） | 无需改 |
| `PasskeyKeyText` / `PasskeyLegacyKeyText` / `PasskeyPrf` / `PasskeyRegistrationPayload` / `WebAuthnRequestOptions` | 本仓 KPEX / WebAuthn 文本契约（非 KDBX XML） | 否 | 不改 |
| `BiometricCredentialStorage` / `SyncCredentialSealer` / `UnlockPasskeyManager` / `UnlockThrottle` / `SyncRollbackGuard` | 本仓自产本地密文/偏好串 | 否（写侧无折行） | 不改 |

### 2.2 AC②：用例（打开成功 → 图标可渲染 → 往返一致）

新增 `database/src/test/java/com/keepasskey/database/xml/KdbxCustomIconBase64LenientTest.kt`（**5 例**）：

1. **76 列折行打开**：`chunked(76)` + 缩进换行样本 → 解析成功，`customIcons.single().data` 与源字节 `contentEquals`（「可渲染」在 XML 层的可测形态 = 交付渲染器的字节一致）。
2. **往返一致**：生产 `KdbxDatabase` + `KdbxXmlSerializer` 写出 → 将 `<Data>` 正文按 76 列折行 → `KdbxXmlParser` 读回字节一致。
3. **混合空白**：空格 + `\r\n` + 缩进混排样本 → 同样按官方语义解码。
4. **非法输入仍拒**：`!!!NOT_VALID_BASE64@@@` → `KdbxCorruptFileException` 且消息含 `CustomIcon`（**不**静默丢弃图标）。
5. **接线守卫**：读生产源码，断言 `decodeBase64LenientWhitespace` 在位、去注释后 `Base64.getDecoder()` 生产调用计数为 0（防回退到严格解码）。
