## 2. 发现①：`PasskeyCreationDeviceTest` 真机首跑即红（用例契约误用，非生产缺陷）

**失败形态**（`:app:` 首跑，44 例中 1 红）：

```
PasskeyCreationDeviceTest > 真机端到端创建通行密钥并验证其签名能力[Redmi 4X - 17] FAILED
  CryptoException$InvalidKeyException: 无法从字节流解析 EC 私钥（所有形态均失败）
    at PasskeyKeyCodec.parseEcPrivateKey(PasskeyKeyCodec.kt:112)
    at PasskeyAssertionSigner.bcSignEs256(PasskeyAssertionSigner.kt:38)
    at PasskeyCryptoEngine.signAssertion(PasskeyCryptoEngine.kt:315)
  Caused by: java.lang.NumberFormatException: Illegal embedded sign character
    at java.math.BigInteger.<init>(BigInteger.java:495)
    at PasskeyKeyCodec.parseEcPrivateKey(PasskeyKeyCodec.kt:108)
```

**该用例从未被执行过**：`git log --diff-filter=A` 显示 `PasskeyCreationDeviceTest.kt` 由 **§149**
（提交 `d2735ae`）新增；§149 批次正文 §4.1 **自陈**「**未跑设备侧 / 真机**（`connectedDebugAndroidTest` 与
`assembleRelease` 未跑）」，仅以三模块 `compileDebugAndroidTestKotlin` 通过作为设备侧证据。本批是它的**首次真实执行**。

**根因（用例侧契约误用）**：私钥在库内以 **PKCS#8 PEM 文本**驻留（§149 起对齐 KeePassXC / KeePassDX 的
`KPEX_PASSKEY_PRIVATE_KEY_PEM` 口径），而 `PasskeyCryptoEngine.signAssertion` 的入参契约是**签名材料**
——KDoc 原文：「承载私钥材料的字节流（原始私钥标量、种子或 PKCS#8 DER 编码）」。用例第 4 步把
`usePrivateKeyBytes` 读出的 **PEM 文本字节流直接**喂给 `signAssertion`，绕过生产断言路径的还原步骤
（`PasskeyAssertionActivity.decodePrivateKeyMaterial` → `PasskeyCryptoEngine.decodePemPrivateKeyText`）。
于是解析依次落空：长度既非 32 也非 64 ⇒ `PrivateKeyFactory.createKey`（非 DER）失败 ⇒ 回退
`BigInteger(String(bytes), 16)` 把 PEM 正文当 hex 解析，Base64 字母表里的 `+` 被 `BigInteger` 判为
**内嵌正负号** ⇒ `NumberFormatException: Illegal embedded sign character`。

**修复（`app/src/androidTest/.../PasskeyCreationDeviceTest.kt`，仅测试源集）**：改为与生产断言路径
**同一通道**——先 `decodePemPrivateKeyText(raw)` 还原签名材料，再以还原出的 `algorithmId` / `keyBytes` 送签。
判据不降反增，新增三条断言：① PEM 通道必须可还原（`checkNotNull`）；② 还原出的算法必须与条目字段一致；
③ ES256 还原结果必须是定长 32 字节标量（新增命名常量 `ES256_SCALAR_BYTES`，不引数字硬编码）；
并在 `finally` 中 `Arrays.fill(keyBytes, 0)` 清零取出的材料（与生产侧同一敏感缓冲纪律）。
**生产代码零改动**——生产路径本来就是对的。

**为什么不是 §188（上一批）拆分引入**：该调用链上 §188 只碰过两个文件，且**均逐值等价**——
`PasskeyKeyText.kt` 只是把 `0x0A / 0x0D / 0x20 / 0x09` 收进 `CHAR_LF / CHAR_CR / CHAR_SPACE / CHAR_TAB`；
`PasskeyKeyCodec.kt` 只收敛了 `extractEcPoint` 的 65 / 64 / 32 / `0x04` 常量，**`parseEcPrivateKey` 一行未动**；
`PasskeyCryptoEngine.kt` 与 `PasskeyAssertionSigner.kt` **不在 §188 改动清单内**。
决定性证据是用例本身：它由 §149 引入且 §149 明确记录了「未跑设备侧」。

**随批立规（防再犯）**：`AGENTS.md` §5 + `.codebuddy/rules/engineering-rules.md` §「测试资产纪律」新增
——**`*/src/androidTest/**` 新增或修改的用例必须在设备上实际执行该用例后方准入库；
`compileDebugAndroidTestKotlin` 通过不构成任何验证证据**（编译只保证类型自洽，不保证契约用对）。

## 3. 发现②：宿主单测 1 例偶发红，属 §18 归档批次「测试调度器跨用例污染」的未覆盖余量

**形态**：全量首跑时 `:app:testDebugUnitTest` 报
`BreachCheckHealthTest > 查询失败时状态为 FAILED 且原因如实上浮，绝不回落为未泄露 FAILED` FAILED
（`IllegalStateException at TestMainDispatcherJvm.kt:45` → `MainDispatchers.kt:111` → `Looper.java`）。

**定性证据链**：
1. 同命令**第二轮 114 task 全绿**；单独 `--tests` 重跑该类亦绿 ⇒ 套件内时序 / 顺序相关，非确定性；
2. 从 `kotlinx-coroutines-test-jvm-1.11.0-sources.jar` 取抛点原文（`TestMainDispatcherJvm.kt:45`
   `reportMissingMainCoroutineDispatcher`）：「`Dispatchers.Main` 在平台调度器缺失且测试调度器未设置时被访问，
   请确保 `setMain()` 先于任何 `Dispatchers.Main` 访问，且 `resetMain()` 之后不再访问」；
3. 归类：与归档批次 **§18**（`18-偶发红根因修复-测试调度器跨用例污染.md`）**同一根因**——
   `runTest` 结束不取消 `viewModelScope`，ViewModel 内在真实线程上执行的在途工作于 `resetMain()` **之后**
   回跳已失效的 Main；§115 亦曾把本用例同一条报错如实判为「§18 类偶发红、与本批无因果」。

**本批处置**：给 `ui/screens/settings` 下三个直接构造 `SettingsViewModel` 的用例
（`BreachCheckHealthTest` / `HealthCheckViewModelTest` / `ChildDatabaseSettingsWiringTest`）补齐 §18 口径——
`@After` 中**先 `viewModelScope.cancel()`、再 `resetMain()`**。`SettingsViewModel` **无调度器注入点**，
故采用 §18 对 `AuthenticatorViewModelTest` 的那一种修法（有注入点时应首选注入测试调度器）。
**未删除、未跳过任何用例**（§147「测试资产不删除」）。

**修复后复跑证据**：`.\gradlew.bat test --rerun-tasks --max-workers=1 --continue` **连续三轮全绿**
（末轮 `*/build/test-results/testDebugUnitTest/*.xml` 的 mtime 区间 `14:24:48 ~ 14:25:34`，
`tests=2182 failures=0 errors=0 skipped=13`）。
如实标注：修复前的命中率是 **1/2**，故三轮全绿只是**弱证据**，不构成「该类别已消除」的结论——
`ISSUE-P3-189` 的验收标准仍要求余量 18 类全部具备防护 + CI 不再出现同类异常。

**余量已登记 `ISSUE-P3-189`**：同类风险仍有 **18 个测试类**未具备该防护（其中风险最高的是
`DatabasePickerViewModelTest` / `DatabasePickerKeyFileCreateTest`——生产侧用 `Dispatchers.IO` 且无注入点）。

1. **发现①是「用例写错」而非「生产有 bug」**，但反过来说：**§149 声称的「创建链路真机端到端签名可用」

   诚实的，本批只是把它欠的账补上。
2. **本批设备侧结果不覆盖系统级 Passkey 交互**：44 例 `:app:` instrumented 用例走的是应用内引擎与
   内存会话，**不含**真实 RP / 浏览器经 `CredentialManager` 的下发与回传链路；
   `已知工程限界.md` §4.1「Passkey 系统级交互未覆盖」的边界**不因本批改变**。
   KPEX 落库形态仍只有**格式面证据**（未用 `keepassxc-cli` / `pykeepass` / 真实 KeePassDX 端到端对拍）。
3. **单台机型**：结论仅代表 Redmi 4X（A53 / API 37）一台，**不得**外推至其它机型或 Android 版本。
4. **用例总数口径差**：本批聚合 `tests=2182`，§149 记录为 `tests=2184`（同为 debug 变体）。
   本批**未增删任何宿主用例**（改动为 3 个类的 `@After` + 1 个设备用例的第 4 步），
   该 2 例差额**未逐例溯源**；§149 自身已声明其差额「未逐例溯源（口径差异未核实）」，本批同样不下结论。
5. **发现②的修复只是防护，不是「复现-修复-复验」闭环**：偶发红在本批只命中过 1 次，

   `UncaughtExceptionsBeforeTest`」，本批只覆盖其中一部分。
