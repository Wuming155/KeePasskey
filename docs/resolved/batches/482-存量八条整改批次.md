> ### ISSUE-P2-548：同步失败通知「先发后撤」——鉴权 / 协议失败被伪装成离线且无告警残留
>
> - **现象**：WebDAV 密码填错（401/403）或服务端 5xx 时，UI 显示「离线，已保留本地副本」，
>   且**通知栏不留任何失败痕迹**——库可长期未同步成功而用户无感知。
> - **核实时间点 / 方式**：2026-10-09，静态逐行取证（**未跑构建 / 未跑测试 / 未真机**）：
>   ① `sync/.../webdav/WebDavSyncProvider.kt:163-164` 401/403 → `throw SyncException.AuthenticationError`；
>   ② `:150-151` `getMetadata` 走 `runCatching` ⇒ 以 `Result.failure` **返回**而非抛出，故 `SyncCycleRunner.kt:365`
>   的 `NetworkError -> Offline` catch **不覆盖此路径**；
>   ③ `sync/.../engine/SyncEngine.kt:220-224` `recoverFromMetaFailure` 的 `else` 分支把**所有非 `FileNotFound`**
>   失败（含 `AuthenticationError` / `ProtocolError`）归一为 `RemoteUnreachableUsingCache`，
>   同时 emit `CouldntOpenFromRemote`；
>   ④ `app/.../sync/SyncCycleRunner.kt:354` → `SyncOutcome.Offline`；
>   ⑤ `app/.../sync/SyncFailureNotifier.kt:33-42` `isEngineFailure(CouldntOpenFromRemote)=true` ⇒ `post()`；
>   ⑥ `:89-103` `lastOutcome.collect` 对**非 `Error`** 一律 `cancel()`。
> - **根因（与初版审查结论的差异，勿误修）**：**不是**「`Offline` 不发通知」——事件通道**确实**会 `post()`。
>   **真缺陷是「同周期内竞态」**（**2026-10-09 真伪核实更正：原写「定序」不准确**）：
>   `SyncCoordinator.syncNow():254-255` 确实**先** `publishSyncEvents()`（内含 `_syncEvents.tryEmit`）**后**
>   写 `_lastOutcome.value` ⇒ 发射顺序为「先事件后结论」；但两个订阅者是 `SyncFailureNotifier.start():87-104`
>   在同一 scope 下的**兄弟协程**，该 scope 为 `guardedScope(Dispatchers.Default, …)`（`:76`）
>   ⇒ 两次唤醒分派到**不同线程并行**，**发射顺序不构成执行顺序保证**；且 `posted`（`:81`）是
>   **非 `@Volatile` 普通 `var`**（写于 `post()`、读于 `cancel()`）⇒ 跨线程**无 happens-before**。
>   **三种交错都会出现**：① `post()` 先且 `posted` 可见 → 通知被撤（原述结果）；② `cancel()` 先 →
>   `if (!posted) return`（`:135`）空转后由 `post()` 留下通知；③ `cancel()` 读到陈旧 `false` → 通知留下。
>   ⇒ 「通知被撤掉」**真实可能但非确定发生**；**确定成立**的是「同周期内既 `post()` 又 `cancel()`
>   ＋ `posted` 状态机数据竞态」——**两者都须一并整改**。
>   **照「`Offline` 也纳入通知」去改会误修**（真实断网时通知刷屏）。
> - **前提边界（2026-10-09 真伪核实补正）**：上述「通知被撤」路径只在**库已有缓存基线**（非首次同步）

## 1. 整改

### 1.1 `ISSUE-P2-548`：远端失败按起因分型 + 失败通知裁决单点化

**根因（批次内更正后口径）**：不是「`Offline` 不发通知」——事件通道**确实**会 `post()`。
真缺陷有两层：① **起因混同**——`SyncEngine.recoverFromMetaFailure` 的 `else` 分支把
「真连不上（`NetworkError`）」与「鉴权 / 协议 / 5xx」归一为同一降级结果，app 层一律产出
`SyncOutcome.Offline` ⇒ UI 显示「离线，已保留本地副本」，密码填错也像没事；② **同周期竞态**——
两个订阅者是 `guardedScope(Dispatchers.Default, …)` 下的**兄弟协程**，「先 `publishSyncEvents()`
后写 `_lastOutcome`」只是**发射**顺序、不构成**执行**顺序，且 `posted` 是**非 `@Volatile`** 的裸 `var`。

**改动清单**（按模块）：

| 面 | 文件 | 改动 |
|---|---|---|
| sync 结果模型 | `engine/SyncEngineResults.kt` | 新增 `SyncOpenResult.RemoteRejectedUsingCache(localBytes, cause)` 与 `SyncCommitResult.RemoteRejected(keptLocal, cause)`；两个「不可达」结果的 KDoc 写明语义边界 |
| sync 分型 | `engine/SyncDegradeResults.kt`（**新文件**） | `degradeUsingCache` / `degradeCommitUsingCache` 单点分型（只认 `SyncException.NetworkError`）；同进同出，防「打开阶段报鉴权失败、上传阶段仍报离线」的裂口 |
| sync 调用点 | `engine/SyncEngine.kt` | open 三处（元数据失败降级 / 强制上传失败 / 本地赢上传失败）与 commit 三处（冲突下载失败 / 普通上传失败 / 强制提交失败）改走分型 |
| app 归类 | `sync/SyncRemoteFailureOutcome.kt`（**新文件**） | `classifyRemoteFailure`（纯函数）+ `StringsProvider.remoteFailureOutcome` + `remoteFailureDescriptor`：**NetworkError→Offline / AuthenticationError→`sync_error_auth_failed` / 其余→`sync_error_remote_rejected(状态码或类型名)`** |
| app 调用点 | `sync/SyncCycleRunner.kt`、`SyncCycleCommitPaths.kt`（2 处）、`SyncConflictController.kt`、`SyncConflictAutoMerge.kt`、`SyncConflictResolution.kt` | 六处 `RemoteRejected` 消费点补映射；首传探测原有的三分法（`ISSUE-P2-402`）**收敛进同一点**，口径逐字不变 |
| 通知判据 | `sync/SyncFailureNotifier.kt` | `isEngineFailure` 排除 `NetworkError` 起因（真断网不亮通知，AC②）；两条流 `merge` 为**单个收集器**（结构性消除「发射顺序 ≠ 执行顺序」）；发/撤与 `posted` 收进新纯类 `SyncFailureNotificationState`（`@Synchronized` + `@Volatile`），权限被回收走 `markPostFailed()` 回退 |

**为何上传侧一并处置（超出条目原文范围，如实留痕）**：条目只写了 `openRemote`/`getMetadata` 路径，
但 `commitLocal*` 的上传失败（含 401）此前同样落到 `RemoteUnreachable` → `Offline` ⇒ 同一条欺骗面
（且同周期通知同样被撤）。只修 open 侧等于半修，故六处一并收敛。

**未采纳的方案（如实）**：曾计划用 `Dispatchers.Default.limitedParallelism(1)` 收束两个收集器；
该 API 在 `app` 模块解析不到（编译实测 `UNRESOLVED_REFERENCE`），改用 `merge` 合并两条流——
**更彻底**（不是「同一线程上两个协程」，而是「一个协程」）。
