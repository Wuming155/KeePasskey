## 1. 条目正文（原样收录）

### `ISSUE-P2-253`：关闭生物识别开关不删除已存封印数据，全应用无主动撤销入口

- **优先级**：P2（中危缺陷——用户明确关闭生物识别后期望其数据被删除，而含主密码密文的封印凭据、断言登记记录与 Keystore 密钥全部继续驻留；违背数据最小化与用户撤销意图。**非可解密性漏洞**：封印密文在无强生物授权下不可解开）。
- **核实时间点与核实方式**：2026-09-22，四路定点核实——
  ① **生产源码直读**：`BiometricEnableCoordinator.setEnabled(false)` 原实现只写 `settingsRepository.setBiometricEnabled(false)`（协调器 KDoc 原文明写「关闭开关：直接落偏好」）；
  ② **全仓 grep** `clearCredential|clearAll\(|deleteKey`：`BiometricCredentialStorage.clearCredential` 的调用点仅在解锁失败路径（`BiometricUnlockCoordinator` 4 处）与 Cipher 准备失败路径（`BiometricEnableCoordinator:181`），**设置页关闭路径零命中**；`clearAll()` 生产调用点为零；
  ③ **参考项目定点取证**（只读已知文件，无目录扫描）：KeePassDX `DeviceUnlockFragment.kt` 菜单提供「删除加密密钥」入口、keepass2android `PasswordActivity.cs` 提供 `ClearFingerprintUnlockData` 清绑定——两者均有用户可见的生物识别数据撤销出口，本项目无；
  ④ **文档检索**：`docs/ACTIVE_ISSUES.md`（当时三区均 0 项）与 `docs/architecture/产品裁决登记.md` 检索「删除封印 / 撤销生物识别」零命中——属**未登记缺口**，非已裁决取舍。
- **背景**：生物识别快速解锁把主密码（+ 可选密钥文件字节）以 Keystore AES-256-GCM 封印进 SharedPreferences `com.keepasskey.biometric_credentials`（每库 `iv`/`cipher`），并随登记写入解锁通行密钥断言记录（公钥 / credId / signCount + MAC）与 per-database Keystore 密钥（封印密钥 `BIOMETRIC_KEY_ALIAS_<dbId>`、断言密钥对 `BIOMETRIC_KEY_ALIAS_passkey_<dbId>`）。关闭开关后 `UnlockModePolicy` 不再放出快速解锁入口（密文不可用），但**数据本身一直驻留**；全应用也没有任何用户可见的「删除生物识别数据」操作。参考项目均有撤销出口（见核实 ③）。
- **验收标准**：
  ① 设置页关闭开关：先落偏好关闸，再撤销**全部**生物识别数据——各库封印 `iv`/`cipher`、断言登记记录（含 MAC）、各库封印 Keystore 密钥与断言密钥对；
  ② 「拒绝软件级降级 → 关闭开关」路径（`BiometricEnrollmentCoordinator.acquireDowngradeConsent` 拒绝分支）同样撤销；
  ③ 封印 BiometricPrompt 挂起期间开关被关闭的竞态：封印落库前**复核** `biometricEnabled`，为 false 即放弃写回；
  ④ 次序固定「**先落偏好、再删数据**」（偏好先 false 使登记入口 `if (!settings.biometricEnabled) return` 与落库复核同时拦截并发写回）；
  ⑤ 刻意保留 `AUTOFILL_AUTH_KEY_ALIAS`（自动填充放行绑定与本开关无关）与 `UNLOCK_PASSKEY_INTEGRITY_KEY_ALIAS`（完整性 HMAC，无认证门控、不承载秘密，供重新登记复用）；
  ⑥ 封印 / 断言两类别名构造**单点化**（`KeystoreManager.sealAliasFor` / `unlockPasskeyAliasFor`），撤销与生产取同一来源；
  ⑦ 宿主单测覆盖「关闭 = 撤销」行为与登记路径接线守卫，全量 `test` 全绿。

### 3.3 判别力说明

- 行为判据（关闭 → 数据消失）由前两例直接承载：若把协调器关闭分支的 `revokeAllBiometricData()` 去掉，`关闭开关撤销全部封印凭据与断言登记记录` 即红；若 `revokeAllBiometricData` 只清封印不清断言记录，存储层第 1 例与协调器例的 `getUnlockPasskey` 断言即红。
- 登记路径两处接线（拒绝撤销、落库复核）JVM 无法端到端驱动（需 `FragmentActivity` + 系统 BiometricPrompt），以源码守卫承载次序与存在性。

## 4. 相邻面复核（**已核实为非缺陷 / 不在本批范围，刻意不改**）

- **封印密文 at-rest 安全性本就成立**：无强生物授权解不开；本条解决的是「用户撤销意图未被执行 + 数据最小化」，批次不改变任何密码学语义。
- **自动填充 / CM 生物放行不随本开关撤销**：其绑定密钥 `AUTOFILL_AUTH_KEY_ALIAS` 不承载数据、放行语义独立于「快速解锁开关」（全仓 `biometricEnabled` 消费点仅解锁 / 登记 / 设置投影）。
- **完整性 HMAC 密钥保留**：`UNLOCK_PASSKEY_INTEGRITY_KEY_ALIAS` 无认证门控、不承载秘密，供重新登记复用。
- **已知限界不在本批**：登记弹窗挂起期主密码明文滞留 ≤60s、断言私钥不绑认证（限界 §3.6）、`BiometricPrompt` 真实交互无自动化（`ISSUE-P2-192` 余量，多批次如实声明）、完整性闸门默认关（PD-15）——均维持现状。
- **节流**：关闭动作无用户确认弹窗（关闸即删、可重新开启并经主密码重新登记，删除的是可再生数据），不引入额外确认。
