## 1. 条目正文（原样收录）

### `ISSUE-P2-291`：同步配置 / 凭据 / 缓存只按 `remotePath` 键控，无库身份绑定 ⇒ 换库后仍可整库覆盖另一库的云端副本

- **核实时间点**：2026-09-23 经远端路径与凭据解析链核对。**注**：本条在对抗轮未列为独立攻击对象（首轮报告原列 P2），开工前须按规则 6.1② 自行复核「多库 + 多同步配置」的真实装配路径。
- **核实方式**：`app/.../sync/SyncProviderResolver.kt:113-138` 按库文件名 / 偏好推导 `remotePath`，`SyncCredentialsStore.kt:137` 的缺省远端路径为 `/keepasskey.kdbx`（**不含库身份**），`sync/.../SyncCache.kt:434` 的缓存键同为 `remotePath` ⇒ 两个库若指向同一远端对象（或用户改选库后未重配同步），本库整库字节会被上传覆盖对方云端副本，且基线 / 防回滚记录同样按 `remotePath` 记账，无法辨识「换库」。
- **背景与根因**：与 `ISSUE-P2-229`（SAF 库不参与同步）不同面——本条是**同步库身份与远端目标缺少绑定校验**。对照 keepass2android 按 `iocInfo`（含库上下文）解析存储对象（`GetFileStorage(iocInfo)`），非以路径字符串为唯一键。后果是跨库整库数据丢失，非字段级。
- **涉及文件**：`app/src/main/java/com/keepasskey/app/sync/SyncProviderResolver.kt`、`app/src/main/java/com/keepasskey/app/sync/SyncCredentialsStore.kt`、`sync/src/main/java/com/keepasskey/sync/engine/SyncCache.kt`、`sync/src/main/java/com/keepasskey/sync/engine/SyncEngine.kt`。
- **验收标准**：AC① 同步配置须绑定**库身份**（库头摘要或库 UUID）并参与凭据 / 缓存 / 基线 / 防回滚的键，换库即视为新配置；AC② 首次将「非本配置创建时绑定的库」推向远端时须显式二次确认（说明将整库覆盖），禁静默 PUT；AC③ 用例：两库共用同一 `remotePath` ⇒ 第二个库上传前被拦或需确认，缓存与基线互不串用；AC④ 与 `ISSUE-P1-275`（乐观锁，已闭环，见 `RESOLVED_LOG.md` §272）同批考虑：ETag 基线亦须在库身份变更后失效，不得沿用旧基线。

**开工前前提复核（2026-09-23）**：成立，且装配链比条目括注更收敛——全仓同步周期唯一入口为 `SyncCycleRunner.runSyncCycle`（`remotePath` 解析 `:127`），缓存 / 基线（`SyncCache`，键 `SHA-256(remotePath)`）与防回滚高水位（`SyncRollbackGuard`，键同）都经 `setupCycleContext` 一次装配；`SyncCredentialsStore` 全部配置（含缺省 `/keepasskey.kdbx`）确无库身份参与。库身份可用载体选定**根分组 UUID**（`KdbxGroup.id`，建库 `KdbxUuid.random()` 随机生成、保存 / 合并全程随 copy 保留、迁移 / 导入不换值），比「库头摘要」稳定（后者随任意保存漂移）。手测装配回退路径（`SyncCoordinator` 手工 `SyncCycleRunner`，既有单测 4/5 参构造）一并纳入：登记表缺省关闭绑定闸，行为与整改前一致。

## 2. 整改

### 2.1 AC①：库身份参与缓存 / 基线 / 防回滚键控

- `SyncCache` / `SyncRollbackGuard` 新增**库身份命名空间**构造参数 `vaultScope`（默认空串）：非空时规范键 = `SHA-256("vaultScope\nremotePath")`，缓存 / 版本 / 基线 / ETag 元数据 / 防回滚高水位全部落库身份键下——同一 `remotePath` 被不同库共用时物理隔离；空串保持旧键（附件二进制池 `FileBinaryStore` 与既有直构造调用方零影响）。
- 新增 **`SyncVaultBindingStore`**（app 层 `@Singleton`）：`remotePath` → 归属库身份（根组 UUID hex）登记表。落盘刻意与 `SyncCredentialsStore` **共用同一 prefs 文件**——同步凭据 `clear()`（换服务器 / 退出同步）连带销毁绑定，杜绝残留绑定错误拦截新配置。
- **一次性迁移**：`SyncCache.adoptLegacyKeysIfPresent` / `SyncRollbackGuard.adoptLegacyKeyIfPresent` 把旧无命名空间键改名迁入库身份键（仅当库身份键尚无对应文件）——单库老用户的缓存 / 基线 / ETag / 防回滚状态零感知延续，不因升级重建基线。

### 2.2 AC②：绑定闸 + 显式二次确认

- `SyncCycleRunner.setupCycleContext` 装配段在**任何网络写（含 `getMetadata`）之前**裁决：未登记 ⇒ 当前库即创建绑定者（登记 + 迁移旧键）；一致 ⇒ 放行；登记为**另一库** ⇒ 中止返回新 `SyncOutcome.VaultBindingMismatch`，零字节出网。
- `SyncCycleRunner.takeoverVaultBinding`（确认路径）：用户显式确认后**改绑** + `commitLocalForce`（无预条件）整库上传，云端原属另一库的副本被整体替换——正是对话框告知并确认的内容。
- UI 通道：`SyncCoordinator.confirmVaultBindingTakeover` 公开入口（与 `syncNow` 共享会话互斥）；`VaultListSyncController` 置确认位 → `VaultListScreen` 渲染 `VaultBindingTakeoverDialog`（error 色确认钮 + 「不可恢复 / 先确认另一库已备份」明示）；`SettingsSyncController` 只提示不提供第二处覆盖闸门；后台 `PeriodicSyncWorker` 走 `syncNow` 的 mismatch 分支被静默拦截（绝不在后台代做取舍，同 `ConflictNeedsUser` 口径）。

### 2.3 AC④：库身份变更后旧基线天然失效

绑定不符被拦时不迁移、不沿用旧库任何状态；确认接管走库身份新键（其下无 state）+ 无预条件上传——旧 ETag 基线物理上不参与新库身份键下的任何决策。

## 4. 如实声明

- 库身份载体取**根分组 UUID** 而非条目括注的「库头摘要或库 UUID」二选一中的库头摘要：KDBX 格式无库级 UUID，根组 UUID 是建库即稳定的最接近载体（合并 / 导入保留；`KdbxMerger` 语义下三方合并以 base 根组 id 为准，换库必换 id）。
- 被拦截库的旧键缓存残留（归「最后同步者」）不主动清除：占几百字节、不含明文、`SyncCacheEvictor` 锁库时随 `clearAll` 收口；主动清除反而会误删真正归属者的活跃缓存。
- UI 确认入口单点化：仅库列表页（下拉刷新触发链）提供整库覆盖确认，设置页与后台 Worker 只拦不放——与「后台绝不做破坏性取舍」的既有口径一致。
- 未跑 `lint` / `assembleRelease` / 截图门禁（无 `@Preview` 改动）/ KPEX 对拍（未触 passkey 面）；全量首轮红为并行竞争偶发，已登记成因。
