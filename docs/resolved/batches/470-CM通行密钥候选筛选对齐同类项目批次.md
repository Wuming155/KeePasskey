## 1. 原条目（`ISSUE-P2-530`，本轮登记）

### CM 通道「候选筛选」与「归属校验」合一——未取证浏览器上通行密钥零候选

- **背景（用户报告 2026-10-07）**：「相同场景下 KeePassDX 能呼出通行密钥，本应用却不行」。用户随后明确要求
  **对齐同类项目（如 KeePassDX）**。
- **根因（2026-10-07 逐行直读本仓 + 四个同类实现）**：
  1. `CredentialResponseAssembler.resolvePasskeyTargetRpId` 在非 https origin 时返回 `""`（`CredentialResponseAssembler.kt`，
     `if (!browserFlow) return ""`），随后 `CredentialCandidateMatcher.matchesPasskey` 的非浏览器分支**只认**
     「条目 url 恰好是 `android://<调用方包名>`」⇒ 浏览器上创建的 `https://<rpId>` 条目**恒不入选**；
  2. `browserFlow = origin.startsWith("https://")`（`CallingOriginResolver.kt`），而 origin 只在浏览器**命中特权指纹白名单**时才是
     https，否则降级 `android:apk-key-hash:`；本仓内置表只有 Chrome ×2 + Firefox ×2（`BrowserSigningFingerprints.kt`），
     而 §36（`architecture/已知工程限界.md`）已登记本机**无 Chrome**、用户在用浏览器为 via / 夸克 ⇒ 本仓候选恒为 0；
  3. 零候选时**没有任何出口**：拒绝页（含 `PD-12` 的就地授权）只在**选中条目后**的落地页触发。
- **同类项目读数（逐行直读，本批对照依据）**：

  | 项目 | 通行密钥候选检索键 | 是否把「调用方归属」当候选门槛 | 出处 |
  |---|---|---|---|
  | KeePassDX | 请求 `rp.id` + `allowCredentials` | **否**（`populatePasskeyData` 形参里无 `CallingAppInfo`） | `.../credentialprovider/passkey/PasskeyProviderService.kt:421-431`；锁库/无匹配各给一条条目 `:472-530` |
  | Monica | 请求 `rpId`（`allowCredentials` 严格不中则放宽回落 discoverable） | **否**（该文件 `callingAppInfo`/`origin`/`signingInfo` 零命中） | `.../passkey/MonicaCredentialProviderService.kt:255-312` |
  | Authnkey | **不筛**，恒返回一条中立条目（`displayName` 带 rpId） | **否**（同上零命中） | `.../pl/lebihan/authnkey/AuthnkeyCredentialService.kt:136-170` |
  | fenris | **`rpId` 优先**，调用方 origin 仅兜底；并明文声明「不校验 rpId ⇄ origin，交给 Credential Manager」 | 只用于取 origin，**不作门槛** | `.../credentialprovider/Util.kt:63`、`.../webauthn/Validation.kt:38` |

  **净结论**：本仓整改前是**唯一**把通行密钥候选绑在调用方归属上的实现；其代价不是「少一道校验」而是**零候选**。
- **登记裁决（代理裁决，可逆）**：见 `PD-77`——**筛选按请求 `rp.id`，归属一律留在签发前**。

## 2. 整改

1. **候选筛选**（`CredentialCandidateMatcher.matchesPasskey`）：域维度改为
   `targetRpId.isNotBlank() && DomainMatcher.isDomainMatch(passkey.relyingPartyId, targetRpId)`，
   与 `android://` 包名维度**并存**（任一命中即入选）；`browserFlow = true`（可信浏览器）**维持放宽前口径**——
   只认域匹配。`allowCredentials` 严格收敛、过期 / 回收站排除、`ISSUE-P3-339` 的「passkey 不经 `entry.url` 域兜底」**均未改**。
2. **检索键解析**（`CredentialResponseAssembler.resolvePasskeyTargetRpId`）：非浏览器调用方不再返回空串，
   改为返回请求自报的 `rp.id`（去空白）；`rp.id` 缺失 / 空白时仍退回空串 ⇒ 交由包名维度把关（不得因缺 rpId 而整体不出候选）。
   可信浏览器分支的「`rp.id` 必须等于 origin 域或其可注册后缀」校验**一字未改**。
3. **断言侧拒绝收尾**（`PasskeyAssertionActivity`）：归属复校（`passesOriginBinding`）失败原为**静默** `failAndFinish()`；
   改为调用 `rejectUntrustedCaller` —— 调用方确属「已安装、未加入特权名单的浏览器」时呈现拒绝原因页
   （新原因 `CALLER_BROWSER_NOT_TRUSTED`）并附 `PD-12` 那条就地授权（复用 `BrowserRemedyBuilder` 的资格守卫）；
   其余情形维持静默收尾。**签发侧门控零放宽**。
4. **拒绝页标题**：`BaseCredentialActivity.rejectAndFinish` 增加 `@StringRes titleRes`（默认创建链路标题），
   断言链路传新增的 `cred_reject_get_title`（zh「无法使用通行密钥」/ en「Cannot use passkey」）。
5. **文案**：`passkey_reject_caller_browser_not_trusted`（zh / en 成对，**无插值**，`ISSUE-P1-10` 口径）。
