## 2. 状态所有权仍在外层（与 §165 同口径）

`showPlaintextExportConfirm` / `pendingExportAttachment` / `pendingPlaintextExportUri` 三态与
「取消 → 删除 SAF 已建空文档（ISSUE-P2-20）→ 复位三态」「确认 → 复位三态 → `confirmed = true` 放行导出」
的**先后顺序**逐字保持在 `EntryDetailScreen` 内；新组件只呈现两条出口。

## 3. 观测登记（本批刻意**不做**的合并）

详情页的明文导出确认与设置页的 `ExportConfirmationDialog`（§156 收敛产物）**同形而不等价**：

- 设置页三处在确认时经 `ExportConfirmationPolicy.confirm` **签发 `ExportTicket`**，导出控制器入口以该令牌为
  必填参数（UI 无法绕过确认直接调用）；
- 详情页这一处**无令牌机制**：由 `EntryDetailViewModel.exportAttachment` 内的
  `ExportConfirmationPolicy.allows(risk = ATTACHMENT, confirmed)` 判定并 fail-closed；
  确认按钮文案亦不同（`detail_attachment_export_warn_confirm` vs `dbset_export_plain_warn_confirm`）。

强行合并会改动那个安全共享组件的 API 与用户可见文案，属**行为变更**而非结构收敛 ⇒ 不在本条整改范围内做。
若日后要统一，须单独立项并同时把 `ExportTicketSinkGuardTest` 的签发点判据扩到详情页。

**另一处顺带发现（登记备查，本批不动）**：预览夹具的 `previewStateOf` 辅助在本包与 `edit` 包里
**各存一份 `private` 实现**（`EntryDetailCards` / `EntryDetailSections` / `EntryDetailTopBar` /
`EntryDetailScreenPreviews` / `EntryEditComponents` 共 5 份）。收敛为包内一份 `internal` 实现是可做的小项，
但它不影响任何档位计数，且会让 5 份文件的预览接线同时变动 ⇒ 留给后续单独一小批处理。

## 4. 过程留痕（编辑事故，已修复且未入库）

用 Edit 在 `EntryDetailDialogHost.kt` 中部插入新组件时，`old_string` 取的是**类 KDoc 的开头三行**——
结果整块被插在 KDoc 中间，把该文档注释劈成两半（残留 ` *` 起始的孤儿片段）。
编译器不会报这种错（注释语法不敏感），靠**肉眼复读 diff** 才发现。
处置：改用 python 做行手术（定位孤儿边界 → 还原原 KDoc 头 → 把组件移到文件末尾），
再 `:app:compileDebugKotlin` 与 `wc -l` 双验（175 → 211，与「原 175 + 组件 36」吻合）。
**教训**：往文件里插整块内容时，anchor 必须覆盖**被替换文本的完整边界**，或直接改为「追加到文件末尾」。
