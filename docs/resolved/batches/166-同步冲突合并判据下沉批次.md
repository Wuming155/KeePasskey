## 2. 为什么恰好是这四件

`SyncConflictController` 的两件事本可分离，此前被写在一起：

- **待决冲突会话的上下文持有**（`pending*` 七个字段、`conflictFlow`、`beginPendingConflict` /
  `clearPendingConflictSession`、`resolveConflicts` 的 `If-Match` 与落库）——**依赖实例状态与互斥前提**，
  留在门面；
- **冲突裁决的规则本身**（base 可信性、决策清单口径、擦除前提、单趟落树）——**纯判定**，
  与「谁持有会话」无关，搬走后调用点仍逐字等价。

刻意**没有**搬 `autoMergeAndUpload`：它承载 `localDbOwned` 判据下的一处 `wipeDiscarded(localDb)` 调用，
而 `AlgoHotPathGuardsTest` 的擦除边界判据（见 §3）正锚在门面的两棵树上；搬走它需要同时把该判据的
定位串扩到第三份文件，收益（省 40 行）与代价（P0 判据的覆盖面变薄）不成比例。

## 3. 接线守卫核查（判据未放宽，并按需扩了扫描并集）

`AlgoHotPathGuardsTest` 有两处锚在本文件，本批**只放宽定位串、未降低断言强度**：

1. `批量树操作必须走单趟剪枝而不得回退为逐条重走整树`：原按 `SyncConflictController.kt` 单文件扫描
   `applyResolvedEntriesToGroup(` 存在 / `applyResolvedEntryToGroup(` 不存在。搬出**定义**后，单文件扫描
   只剩调用点，「逐条实现在分支文件里复活」这一情形将看不见 ⇒ 改按「门面 + 分支文件」**并集**扫描，
   **两条判据逐字保留**；
2. `同步冲突合并的本地侧必须直取内存树`：`localDbOverride ?: codec.parseKdbxBytes(localBytes)`、
   `val localDbOwned = …`、`if (localDbOwned) wipeDiscarded(localDb)` 三处 contains 判据仍锚门面
   （`handleConflictMerge` / `autoMergeAndUpload` 未搬，故无需改）；但 `wipeDiscarded` 的**定义**已下沉，
   故把「裸调用计数 = 带判据计数」这条等式判据的扫描范围同样改为并集（**两侧计数都不变**，
   仍是 2 : 2）。否则「把一个裸调用搬进分支文件」即可绕过本判据。

`readSource` 对不存在的路径**先断言失败**，故并集里少一份文件不会静默通过（不需要额外的「非空」断言）。
**未做**的验证：把一处裸 `wipeDiscarded(localDb)` 临时写进分支文件以观测守卫转红——那会向生产代码插入
一处未受判据保护的秘密擦除调用（正是该判据防御的 P0 形态），即便随即回退也不入库，故改以**机制论证**
（并集覆盖 + 路径存在性断言 + 正则只看 `wipeDiscarded(localDb)` 这一具体形态）支撑，登记为本批的
已知证据缺口。

行为级证据 `SyncConflictMergeLocalTreeEquivalenceTest`（3 例，覆盖内存树直取 / 不可信 base /
远端解析失败擦除路径）本批**原样通过**，未改判据。
