## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：① `RealVaultRepository.getEntries()` / `getGroups()` 是冷流，而
  `VaultListViewModel.kt:249` 与 `VaultListDecorationsProvider.kt:38` 各自订阅一次
  ⇒ 一次数据变更做 2 份整库条目投影 + 2 份分组投影；详情页更密（`EntryDetailStateAssembler.kt` 中
  `getEntry(id)` 出现于 `:138` / `:104` / `:92` 三处，`getGroups()` 于 `:108` / `:203` 两处）。
  ② `app/.../ui/KeePasskeyApp.kt:61` 根组合读取**整个** `SettingsUiState`（100+ 字段）
  并在 `:243` 传给 `keepasskeyNavGraph(appSettings = …)`，而 `NavHost` 以
  `remember(route, startDestination, builder)` 建图 ⇒ 任一无关偏好变化都会整图 `createGraph`。
- **整改方向**：① 在 ViewModel / 仓库层对这两条流 `shareIn(scope, WhileSubscribed(5000))` 后复用
  （详情页把 `entry` 收敛为一条再 `combine` 派生路径与装饰）；② 根只读真正需要的窄字段，
  `keepasskeyNavGraph` 改接收窄参数或用 `remember` 包一层。
- **验收标准**：新增用例断言「同一次数据变更内整库投影只执行一次」（投影计数）；
  导航图不因无关设置字段变化而重建（结构断言或计数）；页面行为用例全绿。
- **核实时间点与方式**：2026-09-17 读 `VaultListViewModel.kt:248-267`、
  `VaultListDecorationsProvider.kt:30-50`、`EntryDetailStateAssembler.kt:85-210`、`KeePasskeyApp.kt:55-70/235-250` 核实。
- **风险提示**：`shareIn` 会改变流的**订阅语义与重放行为**（新收集者不再触发重算），
  须逐一核对「谁依赖冷流的重算」与 `§117` 的调度器注入口径；导航图改动须复核全仓预览与截图基线。

## 2. 本批实现（① 冷流重复订阅）

### 2.1 列表页：两条整库投影流共享

`VaultListViewModel` 新增两条**共享**投影流（`replay = 1` 让 `combine` 立即拿到最近值；
`WhileSubscribed(5000)` 与 `uiState` 自身启停口径一致）：

```kotlin
    private val entriesFlow = vaultRepository.getEntries()
        .shareIn(viewModelScope, SharingStarted.WhileSubscribed(5000), replay = 1)
    private val groupsFlow = vaultRepository.getGroups()
        .shareIn(viewModelScope, SharingStarted.WhileSubscribed(5000), replay = 1)
```

- `uiState` 的 `combine` 改用 `entriesFlow` / `groupsFlow`（**`getDatabases()` 本就只订阅一次，未动**）；
- `VaultListDecorationsProvider` 改为**消费传入的共享流**（构造参数 `entries` / `groups`），
  不再自行 `getEntries()` / `getGroups()`。
⇒ 一次数据变更的整库条目投影与分组投影由 **2 份降为 1 份**。

**风险提示的核对结论**（谁依赖「每个收集者各跑一遍」）：这两个流的消费者只有
`uiState` 的 combine 与装饰装配，后者按 `entries`/`groups` 计算图标与引用文案——**均无副作用、
不依赖「被订阅即重算」**；且二者都在 `displayDispatcher`/`flowOn` 上执行，与 `§117` 的调度口径不冲突。

### 2.2 详情页：当前条目与分组各共享一份

`EntryDetailStateAssembler` 的 `assemble(inputs)` 内新增两条共享流：

```kotlin
        val currentEntry = inputs.entryId
            .flatMapLatest { id -> if (id != null) vaultRepository.getEntry(id) else flowOf(null) }
            .shareIn(scope, SharingStarted.WhileSubscribed(5000), replay = 1)
        val allGroups = vaultRepository.getGroups()
            .shareIn(scope, SharingStarted.WhileSubscribed(5000), replay = 1)
```

- 三处 `getEntry(id)`（核心 combine / `decorationsFlow` / `groupPathFlow`）收敛为**一处**；
  `decorationsFlow` / `groupPathFlow` / `displayPrefsFlow` 改为**接收**该共享流（不再是 `entryIdFlow`）；
- 两处 `getGroups()`（`groupPathFlow` / 末尾 `allGroups` 叠加）收敛为**一处**；
- 装配器新增构造参数 `scope`（由 VM 传 `viewModelScope`）——`shareIn` 必须有作用域，
  而装配器此前**无作用域**（这是本批唯一的结构性 API 变更，全仓仅一处构造点）。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测、也无投影计数**：AC 要求的「同一次数据变更内整库投影只执行一次」是**运行期计数**，
   本批以**源码文本守卫**（订阅点数量）替代——理由与前几批一致：`getEntries()` 是接口方法，
   计数需引入记录型仓库替身并编排订阅（`§117` 的 `DispatchRecordingDispatcher` 只能计派发、
   不能计「投影被执行几次」）。⇒ **不得**读作「已用运行期计数证明」。
2. **`shareIn` 改变了订阅语义**（风险提示已预警）：共享后新收集者拿到 `replay = 1` 的最近值而
   **不触发上游重算**；本批已核对两个消费者均无该依赖（见 2.1），但**未穷举**未来调用方。
3. **仍存在一处未共享的整库读取**：`EntryReferenceDisplayResolver` 的
   `loadEntries = { vaultRepository.getKdbxEntries() }` 是**一次性 suspend 读取**（非流），
   当且仅当某个条目含 `{REF:}` 时触发（该解析器有无引用即零开销直返的快径）⇒ 本批**未消除**它，
   **不得**读作「列表页整库读取已收敛为一次」。
4. **`uiState` 的 `getDatabases()` 未共享**（本就只订阅一次）；`RealVaultRepository.getEntry(id)`
   单条投影仍未补 `flowOn`（`§117` 的记录已声明该边界）。
5. **详情页装配器新增 `scope` 形参是一次 API 变更**：全仓仅 `EntryDetailViewModel` 一处构造
   （已核实），但 `internal` 类若被其它分支/工具引用需同步——本批未加编译期之外的守卫。
6. **② 导航图重建未做，转登 `ISSUE-P3-183`**（见 §5）。
7. **未跑设备侧 / 预览 / 截图基线**：本批改动影响 `uiState` 的发射时序（共享 + replay），
   但**未在设备侧核对界面**（含 `§120` 记的预览基线）。

## 6. 过程缺陷与留痕

1. **本批一次编译失败（1 例）**：`assemble` 头部改完后**漏改两处调用点**
   （`decorationsFlow(inputs.entryId)` 仍传 `Flow<String?>`、末尾 `.combine(vaultRepository.getGroups())` 未换共享流），
   编译器直接报 `Argument type mismatch` ⇒ 补齐后通过。**该次失败在 `compileDebugKotlin` 阶段终止**，
   未进入测试执行。
2. **本批一次工序纪律偏离并如实留痕**：在 `EntryDetailStateAssembler.kt` 上**同一响应内连发 3 次 Edit**
   （违反「同一文件不得连发 Edit」的作业纪律）。三处 `old_string` 互不重叠且文本唯一，故实际未产生
   失效匹配；但该做法在遇到**相邻或有交集**的区域时会静默改错位置——**后续须改为逐次读取后编辑**。
