### 1.1 `ISSUE-P3-162` 分组索引缺失导致的平方级投影（面包屑 / 回收站子树 / 路径批量解析）

**原条目**（自 `ACTIVE_ISSUES.md` 原样收录）：

- **背景**：三处同族问题——① `app/.../ui/screens/vault/VaultListProjection.kt:92` 面包屑
  `while` 循环内 `allGroups.find { it.id == curId }`（每层一次全表扫描）并用 `breadcrumbs.add(0, grp)` 头插；
  ② 同文件 `:100` 回收站集合用递归 `allGroups.filter { it.parentId == parentId }`（每个节点重扫全表）；
  ③ `app/.../ui/screens/vault/GroupPathPresenter.kt:41` 的 `pathsOf` 对每个分组各调一次 `fullPathOf`，
  而后者首行即 `groups.associateBy { it.id }` ⇒ G 次 Map 构建。三处均在**每次状态投影**执行。
- **整改方向**：投影入口建一次 `associateBy { it.id }` + `groupBy { it.parentId }` 并下传；
  面包屑改查表（`ArrayDeque.addFirst` 或尾部追加后 `reversed()`）；回收站改按 `childrenByParent` 一次 BFS。
- **验收标准**：`pathsOf` 内部不再有循环内 `associateBy`；面包屑不再线性查找；回收站集合构建为单趟；
  行为等价用例（深层树 + 环状父链 + 回收站多层后代）全绿。
- **核实时间点与方式**：2026-09-17 读 `VaultListProjection.kt:78-147`、`GroupPathPresenter.kt:20-42` 实际内容核实。

**本批实现**：

- `GroupPathPresenter`：新增私有 `pathOfIndexed(byId, groupId)`，`pathsOf` **只建一次**索引后对全部分组复用；
  公开的 `fullPathOf(groups, groupId)` 保留原签名（详情页调用点不变），改为转调同一私有实现。
  索引语义不变（`associateBy` 对重复 id 取后者，与原实现同一表达式）。
- `VaultListProjection`：入口一次建 `groupsById` + `childrenByParent`；面包屑改
  `groupsById[id]` 查表 + `ArrayDeque.addFirst`（末尾 `toList()` 交付不可变快照）；回收站集合改
  `childrenByParent` 驱动的**单趟 BFS**（以 `buildSet` 的 `add` 返回值去重，兼作环防御）。
- 名称排序两处：`sortedBy { it.title.lowercase() }` / `sortedByDescending { … }` 改
  `sortedWith(compareBy(String.CASE_INSENSITIVE_ORDER) { it.title })` / `compareByDescending(...)`。

**语义变化 1 处（如实留痕）**：面包屑父链**新增「已访问集合截断」**。原实现遇环状父链
（异常库文件：A 的父为 B、B 的父为 A）会**无限循环**（既有的 `?: break` 只覆盖「找不到分组」），
现与 `GroupPathPresenter.pathOfIndexed` 的既有口径一致——按已访问集合截断。该变化只会让
「原本会挂死」的情形变为「按祖先链展示到环为止」，不改变任何正常库的投影结果。

**边界**：`String.CASE_INSENSITIVE_ORDER`（逐字符 `compareToIgnoreCase`）与
`lowercase()` + 自然序在**极少数 Unicode 码点**（如 U+0130）上的排序可能不同；
本仓标题以中日文 / ASCII 为主，且排序安定性（相等时保持原序）两者一致。
⇒ **不得**读作「全 Unicode 域排序结果逐字节相同」。

### 1.2 `ISSUE-P3-172` 循环内新建重对象（①②③；**④ 处置见 §3**）

**原条目**（原样收录）：

- **背景**：四处同族问题——① `app/.../autofill/AutofillFieldScanner.kt:302` 的
  `value.split(Regex("[^\\p{L}\\p{N}]+"))` 在**函数体内**现编译正则，而 `scan` 对每个节点最多触发 4 次
  ⇒ 30 节点登录页约 100 次编译/请求，与系统 assist 超时预算直接竞争；
  ② `sync/.../webdav/WebDavPropfindParser.kt:42` 每次响应新建 `DocumentBuilderFactory`（逐项设 6 个安全特性），
  `:131` 每次日期解析新建 **3 个 `SimpleDateFormat`**，而该方法按每个远端路径调用一次；
  ③ `database/.../xml/KdbxXmlParser.kt:166` 每次打开库都重新探测并实例化约 5 个
  `SAXParserFactory` + `SAXParser`（平台特性支持是**进程级常量**）；
  ④ `core/.../otp/OtpEngine.kt:75` 每个验证码一次 `Mac.getInstance`（跨周期批量取码时按条目数放大）。
- **整改方向**：① 提为 object 级 `private val`；② 缓存 `factory`（注意 `DocumentBuilder` 非线程安全，只缓存工厂）
  与日期格式常量（`DateTimeFormatter` 或 `ThreadLocal<SimpleDateFormat>`）；
  ③ 加固特性链结果改 `by lazy` 进程级缓存（保留「特性不可用时降级告警」原语义，并顺带消掉每次开库的 WARNING 噪声）；
  ④ `Mac` 按算法持有并 `reset()` 复用。
- **验收标准**：四处均以调用计数或结构断言锁定「不再逐次新建」；XML 加固语义、日期解析等价性
  （含 3 种格式与失败回退）、OTP 码值与 RFC 向量逐项不变。
- **核实时间点与方式**：2026-09-17 主控直读 `AutofillFieldScanner.kt:290-305` 并读
  `WebDavPropfindParser.kt:40-145`、`KdbxXmlParser.kt:150-200`、`OtpEngine.kt:60-90` 核实。
- **风险提示**：`KdbxXmlParser` 的加固特性探测是 `ISSUE-P1-12` / `§83`（DTD 拦截）的证据依据，
  缓存化**不得**删掉降级告警，也**不得**改变「探测失败即降级」的语义。

**本批实现**：

- ① `AutofillFieldScanner`：新增对象级 `private val TOKEN_SPLIT_REGEX = Regex("[^\\p{L}\\p{N}]+")`，
  `tokensOf` 改为 `TOKEN_SPLIT_REGEX.split(value)`（`Regex.split` 与 `String.split(Regex)` 同一实现）。
- ② `WebDavPropfindParser`：DOM 工厂改 `ThreadLocal.withInitial { … }` + `hardenedFactory()`，
  每次解析仍取**全新** `DocumentBuilder`；HTTP 日期格式改按线程构建的 `SimpleDateFormat` 列表复用
  （三种格式的顺序与「首个可解析者胜出」语义不变）。
  **取 `ThreadLocal` 而非进程级单例的理由**：`DocumentBuilderFactory` 与 `SimpleDateFormat`
  均**非线程安全**，按线程持有是「消除逐次新建」与「不引入共享可变状态」的唯一交集。
- ③ `KdbxXmlParser`：探测结论 `private val hardenedFeatureList by lazy { probeHardenedFeatures() }`
  （进程级一次）+ 加固工厂 `ThreadLocal`；`buildHardenedParser()` 收为一行
  `hardenedFactory().newSAXParser()`。原 `buildHardenedParser` 的**「为什么必须探测」KDoc 全文迁入
  companion 的探针函数**（`ISSUE-P1-12` 设备侧实测依据、不 fail-fast 的理由、handler 侧兜底不削弱的声明），
  未删任何一句依据。
- ④ 判定**不实施**，理由与登记落点见 §3。

### 1.3 `ISSUE-P3-173` OTP 引擎的 Base32 解码装箱与线性查表

**原条目**（原样收录）：

- **背景**：`core/.../otp/OtpEngine.kt:123`（`Base32Decoder.decode`）输出缓冲为 `mutableListOf<Byte>()`，
  每个输出字节**装箱**并在末尾 `toByteArray()` 再复制一次；`:128` 以
  `ALPHABET.indexOf(upper)` 查表，而 `String.indexOf(Char)` 是**每字符 32 步线性扫描**（`O(32n)`）；
  `:86` 用 `10.0.pow(digits).toInt()` 取模（浮点路径，`digits=10` 时会饱和到 `Int.MAX_VALUE`）。
- **整改方向**：字母表改 `IntArray(128/256)` 反查表（非法字符置 -1）；输出改预分配 `ByteArray`
  （Base32 输出长度 `n*5/8` 可预知）或 `ByteArrayOutputStream`；`10^digits` 改 `POW10` 常量表，
  把 RFC 4226「模 10^digits」的整数语义显式化。
- **验收标准**：RFC 4648 向量 + 宽容策略（忽略 `=`、空白、字母表外字符）逐例不变；
  新增用例断言解码路径不再产生装箱（或直接以 `ByteArray` 长度契约锁定）；
  护城河式断言：`decode` 仍返回**调用方独占的新数组**（`TASK-46` 借用语义）。
- **核实时间点与方式**：2026-09-17 主控直读 `OtpEngine.kt:70-139` 核实。

**本批实现**：

- `Base32Decoder`：新增 256 项 `DECODE_TABLE`（字母表外为 -1），`valueOf(raw)` 做「小写归一 + 查表」；
  `decode(base32Bytes)` 改**两趟法**——先按有效字符数算出**精确**输出长度
  （恒为 `有效字符数 × 5 / 8`，因每有效字符恰贡献 5 bit），再单趟填满预分配 `ByteArray`，
  全程零装箱、零冗余复制。
- `OtpEngine`：新增 `POW10`（`10^0 … 10^9`）与私有 `tenPow(digits)`；`calculateHotp` 改用 `tenPow`。
  **越界位数回退原浮点路径**（`10.0.pow(digits).toInt()`），故 `digits ≥ 10` 时 `toInt()` 饱和
  到 `Int.MAX_VALUE` 的既有行为**逐字保留**（表只覆盖 `0..9`，调用面按 `TotpKeyUriParser` 钳制为 6 ~ 8）。

**验收判据的落地方式**：既有 `Base32DecoderByteSemanticsTest`（3 例：两入口一致 / 大小写与填充空白不敏感 /
空与非法输入返回空数组）与 `OtpEngineTest`（RFC 向量）即为行为护栏；「不再装箱」对运行时不可观测，
故以 §2 的接线守卫（源码文本）锁定。

### 1.4 `ISSUE-P3-181` 若干常数因子清理（密钥文件 / CSV 导出 / 标签解析）

**原条目**（原样收录）：

- **背景**：① `database/.../file/KdbxKeyFile.kt:54` 无条件 `stripWhitespace(raw)` 先复制整个 keyfile，
  再判定是否为 64 位 hex 文本（对「任意二进制作为密钥文件」的常见分支这次拷贝纯属浪费，
  且每次解锁与每次保存都走一遍）；② `database/.../csv/KdbxCsvExporter.kt:49` 每下钻一层都
  `groupPath + child.name` 复制父路径，`:62` 又对每条目 `groupPath.joinToString(SEPARATOR)`
  ⇒ `O(条目数 × 深度)` 次字符复制；③ `database/.../xml/KdbxXmlGroupReader.kt:94` 与 `:182` 的
  `tagsStr?.split(";")?.map{trim}?.filter{isNotEmpty}` 每个 Group / Entry 各产生 3 个中间列表。
- **整改方向**：① 先单趟扫描统计非空白字节并同时校验 hex 形状，仅在恰为 64 时构造 compact 数组；
  ② 路径改「进组 append / 出组回退」的 `ArrayDeque` 或 `StringBuilder`，并在**组级**拼一次路径供组内条目共用；
  ③ 单趟手写扫描直接产出最终列表（或 `splitToSequence` 惰性链），Entry 与 Group 共用同一私有函数。
- **验收标准**：三处行为等价（keyfile 三种形态判定、CSV 导出逐字节一致、标签解析结果逐项一致）；
  新增用例覆盖「含多行 / 空行 / 非 hex 文本的 keyfile」「空标签 / 多余分号 / 前后空白」。
- **核实时间点与方式**：2026-09-17 读 `KdbxKeyFile.kt:40-80`、`KdbxCsvExporter.kt:40-75`、
  `KdbxXmlGroupReader.kt:85-195` 核实。
- **风险提示**：keyfile 解析属**解锁正确性**路径，改动须覆盖官方三种语义
  （64 位 hex 文本 / XML keyfile / 任意文件 SHA-256），不得改变判定优先级。

**本批实现**：

- ① `KdbxKeyFile`：新增私有 `compactHexKeyOrNull(raw)`——单趟扫描，**非空白字节数 > 64 或遇到非 hex 字节
  立即返回 null**（该情形旧实现必然落入 SHA-256），恰为 64 时才分配并二次遍历拷贝。
  `extractKey` 的判定梯子（裸 32 字节 → XML KeyFile → 64 位 hex → 整文件 SHA-256）与空白字符集合
  **逐字未变**（沿用同一表达式 `b.toInt().toChar().isWhitespace()` 与同一 `isHexDigit`）。
  `stripWhitespace` 本身**未动**（另两处调用方：XML `<Data>` 内容、异常消息预览）。
- ② `KdbxCsvExporter`：递归参数由 `List<String>` 改为 `ArrayDeque<String>` 路径栈（进组 `addLast`、
  出组 `removeLast`），并在**组级** `joinToString` 一次后传给组内全部条目。
  既有 `KdbxCsvExporterTest` 的 4 例**逐字节断言**（含「根条目分组列为空」「子分组反斜杠分层」）即护栏。
- ③ `KdbxXmlGroupReader`：新增文件级 `parseTagsText(raw)`（单趟扫描按 `;` 切分、`trim()`、非空才 `add`），
  Group 与 Entry 两处收拢为同一实现；**可见性由 `private` 放宽为 `internal`** 以供需等价性用例直测
  （本仓同族先例：`KdbxEntryMerger.isModified`），**调用面与语义不变**。

**等价性旁证（次级证据，不得单独作为验收依据）**：本项三处由子代理以 Gradle 缓存中的 Kotlin 编译器
（`K2JVMCompiler`，**不触发 gradle**）把「旧表达式」与「新实现」原样抄录后做差分对拍——
密钥文件字节序列 22 000+、标签串 50 000+（含 `;`、各类空白、NBSP、全角空格、`null` / `""` 等固定夹具）、
随机分组树 5 000 棵，结果 `checks=77019 failures=0`。该旁证**不构成**编译或行为验证，
仅用于在补用例前收敛等价性风险；最终验收以 §2 的主线全量单测为准。

## 3. 刻意不做：`ISSUE-P3-172` ④ 的 `Mac` 实例复用

**判定：不实施**，理由与登记落点如下（登记于 [`docs/architecture/已知工程限界.md`](../../architecture/已知工程限界.md) §9）：

1. **与敏感数据铁律冲突**：复用 `Mac` 意味着该实例长期持有 `init` 传入的 `SecretKeySpec`
   （内含**密钥字节副本**）。调用方（TOTP 种子链路）用毕 `fill(0)` 擦除自己那份的语义前提是
   「自己手上那份即全部副本」；缓存会把这条前提变为「还有一份活到下次 `init`」。
2. **收益是微优化**：TOTP 取码已有按周期号的缓存（§114 `ISSUE-P2-90`），HMAC 只在**周期边界**
   按条目执行一次，而非每秒；省下的是 provider 查找。
3. **项目已接受同类的「以纸面加固换稳定性」反例**：`已知工程限界.md` §3.4 / §2.4 的记录口径一致。

**替代做法（若日后确需优化）**：应按「可取消派生 / 内核下沉」等**不扩大明文驻留面**的方向另立条目，
而不是复用持有密钥的原语实例。

## 4. 边界如实声明（不得外推）

1. **无任何性能实测**：本批验收判据为「不再产生某类工作」的结构性断言 + 行为等价用例，
   **不得**宣称百分比收益，也不得据此推断真机表现。
2. **两处缓存是「按线程」而非进程级**：`DocumentBuilderFactory`（WebDAV）、
   `SimpleDateFormat`（HTTP 日期）、`SAXParserFactory`（XML 加固工厂）均非线程安全，故一律 `ThreadLocal`。
   线程池长期存活的多线程场景下，实际收益仍为「每线程一次」。
3. **`KdbxXmlParser` 的唯一行为差异**：「特性不受支持 / 设置失败」的 WARNING 由「每次解析各一遍」
   变为「**每进程一遍**」（`probeHardenedFeatures` 的 lazy 化）；探测判定顺序、告警文本、
   失败即跳过的语义**均未变**。设备侧曾观测到的该批 WARNING 噪声（§92 / §93 的日志观察项）随本批减少。
4. **WebDAV 的 DOM 工厂仍每次 `newDocumentBuilder()`**：消除的是「重建工厂 + 逐项设 6 个特性」，
   **不得**读作「解析对象已复用」。
5. **`KdbxKeyFile.stripWhitespace` 的另两处调用方未动**（XML `<Data>` 内容、`asciiPreview`），
   仍是无条件拷贝；本批只消除 `extractKey` 主路径上「任意二进制密钥文件」的那一次复制。
6. **`parseTagsText` 的 `internal` 放宽不改变调用面**，仅授予同模块测试可见性。
7. **排序比较器的 Unicode 边界**见 §1.1 末。
8. **子代理的差分对拍（77 019 次 0 失败）只是旁证**，未触发 gradle 编译；
   最终结论以本批全量单测为准。
9. **本批未触及**其他三档的条目（`P3-160` / `P3-161` / `P3-163` ~ `P3-171` / `P3-174` ~ `P3-180`
   与 `P2-91`），它们仍留在 `ACTIVE_ISSUES.md`。
