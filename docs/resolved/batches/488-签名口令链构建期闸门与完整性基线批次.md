## 488.1 原始条目（原样收录）

### `ISSUE-P2-573`：Gradle 配置期执行 PR 可改脚本读取签名口令，恶意 PR 合并后可在维护者本机静默外传口令与 keystore 文件

**背景与影响**：`app/build.gradle.kts:54-56` 在未设 `KEYSTORE_PASSWORD` 环境变量时，经 `:31-34`
`ProcessBuilder("powershell.exe",…,"-File",credManReadScript,…)` 在 **Gradle 配置阶段**执行仓库内脚本
`tools/signing/read-cred.ps1`（`CredReadW` 取凭证管理器中 `KeePasskey/Keystore/StorePassword` 明文，`:64-81`；
`releaseKeyPassword` 链 `:59-61` 同理触发第二目标）。该脚本是 **PR 可改文件**：攻击者 PR 在保持「退出码 0/1/2 +
stdout 语义」调用方契约（`:16-19`）不变的前提下插入外传调用即可伪装；PR 被人工合并后（`PD-04` 登记 main 无分支保护），

口令与 **keystore 文件本身**（同一次执行可连带读取）静默外传——伪造官方更新通道的前提被打开。
三个 workflow 均 `runs-on: ubuntu-latest`（`build.yml:109/155/252/585` 等），CI 永不执行该脚本，无第二道检测。

**整改依据**：构建期读取秘密的代码路径不得依赖 PR 可改的仓库内可变面；与本仓既有供应链纪律

**验收标准**：

## 488.2 前提复核（2026-10-11 直读）

- **条目成立（原实现逐字复现）**：`app/build.gradle.kts` 的解析链在**配置阶段**求值
  `releaseStorePassword` / `releaseKeyPassword`，未设环境变量时经 `readWindowsCredentialPassword` 的
  `ProcessBuilder("powershell.exe", "-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass",
  "-File", tools/signing/read-cred.ps1, "-Name", target)` 执行该 **PR 可改**脚本；脚本以 `CredReadW`
  读「普通凭据」明文（`read-cred.ps1:64-81`）后只写 stdout（`:102`），退出码 0/1/2 契约（`:16-19`）
  与条目引用逐条对齐。开工时实现位于 `:13-61`（条目引 `:26-61` / `:31-34` / `:54-56` / `:59-61`
  语义全部成立），行号按 `ACTIVE_ISSUES.md` 文首纪律视为核实时刻快照——无实质漂移。
- **本机配置面核实（只看字段名、不读口令值）**：`keystore.properties`（44 B）仅存 `storeFile` /
  `keyAlias` 两个**非秘密**字段，与 `keystore.properties.example` 的「走凭证管理器通道后本文件可只保留
  两个非秘密字段」口径一致 ⇒ **口令实际只来自凭证管理器通道**，被指控脚本在本机是口令解析链的
  **唯一生效通道**。由此确立整改路线：**不能删通道**（会直接断掉本机与后续维护者的 release 签名），
  只能「收窄触发面 + 执行前加可核验的完整性基线」。
- **CI 面确无第二道检测**：三个 workflow 全在 `ubuntu-latest`；且 `readWindowsCredentialPassword`
  首行即对 `OperatingSystem.current().isWindows == false` 早退 ⇒ CI 侧永不执行该脚本、也无从校验其完整性
  ——**本机构建脚本内自校验是唯一覆盖该攻击路径的手段**（条目 fix① 的「CI hygiene-gate 哈希基线」
  在本条上不成立，故未采用该字面形态）。
- **触发面核实**：本仓无 configuration-cache ⇒ 配置阶段每次全量执行，改造前**任意** gradlew 任务
  （含 `test` / `lint` / `help` / IDE 同步）都会执行该脚本。
- **技术约束（决定整改形态）**：口令必须在**配置阶段**进入 `signingConfig`（AGP 读取 signingConfig 的
  时机不受本仓控制，本环境不允许以真实密钥库做时机实验），而任务图要到配置结束才可知 ⇒ 条目建议②的
  「taskGraph 就绪回调」形态存在把 release 签名改成失败路径的实质风险，未采用其字面形态；改用**配置阶段
  即可判定**的 `gradle.startParameter.taskNames` 达成同一收窄目标，并以既有 `ISSUE-P3-422` 的 taskGraph
  就绪断言（fail-closed）兜住任务名判据的漏判（见 §488.3③ 与 §488.5）。
- **既有断言面**：`ISSUE-P2-55` 的口令强度断言、`ISSUE-P3-422` 的「未签名包」fail-closed 断言均与
  口令解析链同处配置阶段——本批改动必须保持两者语义不变（仅在 P3-422 报错文案上追加引导语）。

## 488.3 整改

### ① 闸门一：执行面收窄为「命令行显式请求 release 分发产物」（AC① 前半,条目建议②的等价落地）

`app/build.gradle.kts` 新增 `releaseArtifactRequested`（配置阶段判定，**默认拒绝**）：命令行任务名去
`:app:` 前缀后命中等价聚合任务（`build` / `assemble` / `bundle`,其依赖图必然包含 release 产物），
或命中 `<assemble|bundle|install|package|publish>…Release` 形态。`readWindowsCredentialPassword` 在
「非 Windows / 脚本缺失」两道既有早退之后、`ProcessBuilder` 之前新增 `if (!releaseArtifactRequested) return null`
——不满足即**静默降级**到后续通道（环境变量已在 Elvis 链前段 / `keystore.properties` / 无签名）。
`test` / `lint` / `help` / `assembleDebug` / IDE 同步不再触碰该脚本。

### ② 闸门二：执行前 SHA-256 完整性基线（AC① 后半，fail-closed）

新增 `credManReadScriptSha256` 常量（`read-cred.ps1` 当前字节的 SHA-256）与
`verifyCredManReadScriptIntegrity()`：脚本缺失或哈希失配即 `throw GradleException` **中止构建**
（有意不做「告警后继续」——那等于把基线降级为注释）；校验通过时打印一行 `lifecycle` 台账（仅在
release 构建可见，口令值本身绝不出现在任何输出里）。基线常量与脚本同处 PR 可改面这一残余，
已按 AC② 登记限界表 §41。

### ③ 兜底与引导（`ISSUE-P3-422` 断言文案扩展）

`gradle.taskGraph.whenReady` 的「未配置签名却调度 release 产物 ⇒ 拒绝产出未签名包」fail-closed 报错
追加引导：凭证管理器通道自本批起仅在命令行显式请求 release 产物时启用，经非标准入口构建时可改用
`KEYSTORE_PASSWORD` / `KEY_PASSWORD` 环境变量——保证任务名判据漏判时**响亮报错**、绝不静默.

### ④ 测试资产（AC① 的「以机检或测试锁定」）

新增 `app/src/test/java/com/keepasskey/app/security/SigningCredentialChainHardeningTest.kt`
（3 例，纯 JVM；`BackupAndSafHardeningTest` 同范式：向上定位仓库根 + 断言前剔除注释）：
① **基线 ↔ 脚本字节一致**——从构建脚本正则提取 64 位十六进制常量并与实算 SHA-256 比对，
任一侧单独改动即红；② **闸门顺序**——`if (!releaseArtifactRequested)` 位于读取函数内且在
`ProcessBuilder` 之前；完整性校验存在**真实调用点**（除声明外 ≥2 处出现）且在 `ProcessBuilder` 之前；
闸门一先于闸门二；③ **fail-closed 语义**——完整性函数体必须现场重算哈希（`MessageDigest` +
`credManReadScriptSha256` 比较）且失配路径 `throw GradleException`。删除 0 例。

**未新增机检脚本**：`gate_readings.py` 直接解析 `build.yml` 的 hygiene-gate 段落执行清单，向其中加命令

## 488.5 如实声明

- **未采用条目建议②的 taskGraph 就绪回调字面形态**：口令必须在**配置阶段**进入 `signingConfig`
  （AGP 读取 signingConfig 的时机不受本仓控制），而任务图要到配置结束才可知；把解析链搬进 `whenReady`
  存在把 release 构建改成失败路径的实质风险，且本环境**不允许**以真实密钥库做「whenReady 内赋值是否被
  签名任务采信」的时机实验（临时生成密钥库 + 探针脚本的实验被本机执行环境安全策略阻断，未执行）。
  故改用配置阶段即可判定的命令行任务名判据实现同一收窄目标，并以 `ISSUE-P3-422` 就绪断言兜底。
  该判据与「同时改脚本 + 基线」的残余一并登记限界表 §41。
- **fail-closed 失配路径未做运行时负向取证**：完整性**失配 ⇒ 中止构建**的行为由
  `SigningCredentialChainHardeningTest` 静态钉住（函数体必须 `throw GradleException`），但「刻意篡改基线
  常量 → 观察构建中止」的运行时负向实验被本机执行环境安全分类器阻断（判定为「故意破坏构建」），
  **未执行**——不得读作已实测；已实测的是正向路径（`assembleRelease --dry-run` 基线校验通过 +
  非 release 命令零激活）。
- **未采纳条目建议③ `CODEOWNERS`**：`main` 无分支保护、仓库唯一提交者即管理员（`PD-04`），
  CODEOWNERS 在该配置下**只有提示性**、不构成强制 review 面；加入会产生「看起来有保护」的假保证，
  与本批「不引入无法验证的安全声明」口径冲突，故不采纳（如需真阻断，须走 `PD-04` 重开条件）。
- **未改面**：`tools/signing/read-cred.ps1`（被钉脚本，逐字节未动——哈希即证据）、`write-cred.ps1`、
  `new-signing-key.ps1`（不参与构建期执行链，不在本条范围）、Elvis 解析链顺序、`ISSUE-P2-55` 口令强度断言、
  `ISSUE-P3-418` 凭证通道本体（仅在其执行入口加两道闸门）。
- **CI 面**：三个 workflow 仍在 ubuntu（CI 永不执行该脚本，这正是闸门二必须落在本机构建脚本里的原因）；
  新增单测随 `fast-gate` 的 `./gradlew test` 在 CI 执行 ⇒ 「脚本与基线漂移」在 CI 亦会红灯。
- **未跑项如实登记**：`lint` / `assembleRelease` 完整出包 / 设备侧全部未跑（本条不要求）；其中
  `lint` 的行为差异值得留意——本批起非 release 命令行请求下 `hasReleaseSigning=false`（配置期不再读
  凭证管理器），`lint` 属警告不阻断面，未纳入本批验收。
