## 1. 原条目（`ISSUE-P2-529`，用户报告 2026-10-07）

### 库文件级缺「保留副本」出口（四处破坏性取舍处无法「两份都留」）

- **背景**：「云端冲突之后没有保留副本的选项，要么取消，要么删除」。核实结论＝**属实且有界**：
  条目级**已有**「双方保留（云端存副本）」（`KdbxMerger.resolveConflict` 的 `DUPLICATE_BOTH` 分支，
  §289 恢复可达），但**库文件级**没有——四处出口只有破坏性选项或干脆没有出路。
- **核实时间点与方式**：2026-10-07 主控**代码直读**（四处 UI / 流程 + 全仓字符串表）+ 与用户经
  `AskUserQuestion` 核实场景。
- **四处（含涉及文件）**：
  1. **库身份绑定不符**「整库覆盖云端副本？」（`app/.../ui/screens/vault/VaultListDialogs.kt` 的
     `VaultBindingTakeoverDialog`）：**覆盖并绑定当前库 / 取消**——覆盖会整体替换云端原属另一库的数据
     （文案自陈「无法恢复」），**无保留项**；
  2. **密码库管理「移除」**（`app/.../ui/screens/database/VaultRemovalPresentation.kt`）：云端库文件
     落在 `filesDir` ⇒ `PRIVATE_FILE` ⇒ **永久删除 / 取消**，**无先导出/另存副本项**；
  3. **从云端打开遇同名本地文件**（`app/.../sync/CloudVaultImporter.kt`）：只有 fail-closed 提示
     「请换一个展示名称后重试」，**无覆盖 / 以副本导入**出路；
  4. **冲突解决策略**（`strings.xml` 的 `sync_conflict_*` 四项）：无「保留两份」口径。
- **验收标准**：AC① 上述四处破坏性取舍处都能「两份都留」（云端副本另存为独立库 / 本地副本另存后再移除 /
  同名导入以副本落地 / 策略项语义明确）；AC② 另存的副本仍是**密文文件**、以**其自身凭据**可解、
  并在密码库列表中可见（不得引入新的明文落盘面）；AC③ **禁假按钮**——每个新入口端到端可用并有用例钉住
  （本仓「机制存在 ≠ 已接线」纪律）；AC④ 副本落点与命名规则（拟 `<原名> (副本 yyyyMMdd-HHmm).kdbx`，
  与库文件同目录）须随批次文档登记。
- **依赖**：`ISSUE-P2-528`（§467）已闭环——它解释了「云端那份为何与新口令不一致」这一成因；本条是其
  **出口面**的补齐。
- **裁决口径（代理裁决，可逆）**：**不做**「冲突时自动另存副本」的自动策略（会堆积副本且语义模糊），
  只把「保留副本」挂在上述**人为破坏性取舍**处。

**开工前前提复核（条目维护规则 ②，2026-10-08）**：四处文件均存在；`VaultBindingTakeoverDialog` /
`VaultRemovalPresentation` / `CloudVaultImporter` / `sync_conflict_*` 四项的正文前提**逐条成立**
（无消费方已出现、无行号致前提失效）。唯一需就地修正的一处：第 4 处的整改形态为**措辞语义**而非新增策略档
（见 §2.4 与 `PD-78` 边界 3），条目正文中的「策略项语义明确」即为该形态。

## 2. 整改

### 2.0 统一原语（AC④ 的唯一真相源）

新增 `app/.../data/repository/VaultFileCopy.kt`：

- `VaultCopyNaming.copyFileName(原名, 时刻)`：`<原名> (副本 yyyyMMdd-HHmm).kdbx`（**纯函数**）；
  扩展名大小写不敏感、无扩展名时补 `.kdbx`；
- `VaultCopyNaming.uniqueCopyTarget(源文件, 时刻)`：**与源同目录**；同分钟重名按
  `<原名> (副本 yyyyMMdd-HHmm) 2.kdbx`、`… 3.kdbx`… 递增；
- `VaultFileCopy.copyBeside(源文件, 时刻)`：**逐字节副本**，走本仓原子写纪律
  （临时件 → `flush` + `fd.sync()` → `renameTo`）；失败返回 `null` 且**不动源文件**。

「同目录」是刻意选择（AC② 可见性）：应用私有目录内的库按目录扫描发现
（`VaultDatabaseCatalog.buildDatabaseList`），副本无需额外登记即出现在密码库列表；同时它是**密文
`.kdbx` 字节副本**，以其自身凭据可解，不引入任何新的明文落盘面。

### 2.1 库身份绑定不符：**另存云端副本并覆盖**（AC① 之一）

- 新增 `SyncCycleRunner` 的**同包扩展** `backupRemoteVaultCopy()`（`app/.../sync/SyncRemoteVaultCopy.kt`）：
  只下载**当前同步目标（云端副本）**并落为 `filesDir/<远端名> (副本 yyyyMMdd-HHmm).kdbx`；
  **不改动云端任何字节**；fail-closed（无活动库 / 无凭据 / 无 filesDir / 下载或落盘失败一律 `Failure`）。
  以扩展承载而非写进 `SyncCycleRunner`：该文件已贴 `tier2` 档沿，且本项与其生命周期无共同变化理由
  （沿用 `ISSUE-P3-305` 同款拆分惯例，方法体逐字未改）。
- `SyncCoordinator.backupCloudVaultCopy()`：挂**长任务锁**（口径同 `confirmVaultBindingTakeover`）。
- `VaultListSyncController.confirmBindingTakeoverKeepingCopy()`：**先**另存副本、**成功才**覆盖；
  副本另存失败即中止并给用户提示（绝不「副本没落地、云端已被替换」）。
- `VaultBindingTakeoverDialog` 增加第三条动作 `onConfirmKeepingCopy`（error 色，与「覆盖」同为破坏性），
  `VaultListScreen` 接线（新文案 `sync_vault_takeover_confirm_keep_copy`）。

### 2.2 移除应用私有库：**另存副本后移除**（AC① 之二）

- `VaultRepository.removeDatabase(id, kind, saveCopy = false)`：`saveCopy = true` 时删除前先另存副本，
  **副本另存失败即整体失败且不删原件**（`VaultLifecycleCoordinator`）；默认值保证既有调用点语义不变。
- `VaultRemovalConfirmation.saveCopyRes`（仅 `PRIVATE_FILE` 非空）+ `VaultRemovalConfirmDialog`
  的第三条按钮 `onSaveCopy`（外部库**不**呈现该按钮：只摘登记、丢不了数据）；
- `DatabasePickerScreen` → `DatabasePickerViewModel.saveCopyAndRemoveDatabase()`（与 `removeDatabase`
  共用同一 `performRemoval` 实现，仅 `saveCopy` 不同），反馈文案
  `db_picker_msg_copied_removed`。

### 2.3 云端同名导入：**以副本落地**（AC① 之三）

`RealCloudVaultImporter` 遇本地同名库文件时**既不覆盖、也不死路**：一律按统一命名以副本落地，
`CloudVaultImportResult.Success.notice` 携带一条**信息性**提示（`picker_cloud_local_conflict` 改写为
「已以副本形式导入，原文件保持不变」），由 `DatabasePickerOpenVaultImporter` 经**全局** Snackbar 通道
上抛（退栈后仍可见）；凭据按**副本路径**（= 上层登记的库 ID）命名空间提交。

> **口径变更如实留痕**：整改前此处为 fail-closed 拒绝（`CloudVaultImporterTest` 原用例
> `本地同名库文件冲突时拒绝且不触碰网络与存储` 断言 `Failure` + 「不触碰网络」）。按测试资产纪律
> 「用例只允许新增或修改」，该用例**改写为** `本地同名库文件存在时以副本落地_原文件一字不动`，
> 核心不变量「**绝不覆盖既有文件**」原样保留并加强（新增「原文件逐字未动」断言）。

### 2.4 冲突解决策略：**语义明确**（AC① 之四）

`sync_conflict_prompt_desc`（zh / en）显式给出「保留两份」口径：该档弹出的解决器里本就有
`conflict_entry_duplicate_both`「双方保留（云端存副本）」决策（§289 恢复可达），此前策略说明未提，
用户无从知道该策略能「两份都留」。本处**只改措辞、不新增策略档**（理由见 `PD-78` 边界 3）。
