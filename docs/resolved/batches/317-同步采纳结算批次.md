# §317 同步采纳结算批次（`ISSUE-P2-308` 闭环 + 补登 `ISSUE-P2-313`）

> **批次性质**：数据完整性整改。把同步引擎的「基线三步」（缓存交付 / `updateBase` / `writeBaseContent` /
> `recordAccepted`）从「引擎返回结果之前即时落地」改为**随采纳结算句柄延后到 app 层采纳确认之后**，
> 消除「采纳失败 → 引擎状态无回滚 → 本地陈旧树整库覆盖他端」的无攻击者跨端数据丢失链。

## 2. 整改方案：采纳结算句柄（`RemoteAdoptionSettlement`）

### 2.1 根因链（整改前）

`openUncached` / `openCachedWithoutLocalChanges`（远端更新分支）在把 `RemoteSynced` 交还 app 层**之前**即已执行
`receipt.commit → updateBase → writeBaseContent → recordAccepted`；采纳 / 应用远端失败
（PARSE_FAILED / SAVE_FAILED / SESSION_DIVERGED）仅 `return SyncOutcome.Error`，全仓无回滚引擎状态的函数。
此后：cache 工作副本与基线已等于远端内容而会话树仍是旧树 → 下轮 `hasLocalContentChanged` 判真重写缓存 →
`hasLocalChanges` 为真且 baseEtag==remoteEtag → **「本地赢」把陈旧树整库上传覆盖他端改动**。每次保存重生成
masterSeed/IV/KDF salt ⇒ 字节摘要全新 ⇒ `SyncRollbackGuard` 判 Accept，防线不触发。快速提交路径
（`SyncCycleCommitPaths.tryFastCommitPath`）上传成功后本地 `save()` 失败同理：基线已前移，进程死亡后重启
将以旧正式文件内容整库覆盖远端。

### 2.2 方案（AC①）

新增同包接口 `RemoteAdoptionSettlement`（`accept()` / `reject()`，各自幂等且二选一），随结果对象携带：

1. **`SyncOpenResult.RemoteSynced` 增 `adoption: RemoteAdoptionSettlement?`**（仅远端有新内容的路径非 null；
   `equals`/`hashCode` 刻意不含句柄——句柄是身份而非值）。
   - `openUncached` 与 `openCachedWithoutLocalChanges`（远端更新分支）：不再 `receipt.commit()` /
     前移基线 / 记高水位，改为返回结算句柄；下载回执暂存 tmp（唯一临时名 + 孤儿清理既有覆盖）。
   - app 层采纳点 `SyncCycleRemoteOutcomes.handleRemoteSynced` 全分支结算：内容一致分支 → `accept`
     （交付缓存 + 前移 ETag，否则基线滞留旧值每轮重下）；转三方合并分支 → `reject`（远端字节已完整持有，
     合并上传成功后由 `markResolvedAndUpload` 前移基线）；采纳分支 APPLIED → `accept`、
     SESSION_DIVERGED / PARSE_FAILED / SAVE_FAILED → `reject`（基线保持原状，下轮重新下载重试；
     重试不构成重放——digest 尚未进入已接受历史）。
2. **`SyncCommitResult.Uploaded` 增 `settlement`**（`commitLocal` / `commitLocalForce` 上传成功路径）：
   基线前移延后到「本地落盘保存成功」之后。六个消费点全部结算：
   `tryFastCommitPath`（落盘失败 `reject` + 如实报错，成功 `accept`）、
   `establishRemoteBaselineIfMissing` / `takeoverVaultBinding`（上传内容即会话库内容，采纳已隐式完成，
   立即 `accept`）、`applyForcedConflictStrategy`（以本地为准：落盘失败 `reject`）、
   `autoMergeAndUpload` 412 重入分支与 `handleResolveUploadSuperseded` → `adoptMergedDatabase`（采纳失败 /
   落盘失败 `reject`，全部成功 `accept`）。
3. **拒绝 / 失败后的收敛性**（逐路径论证，非猜断）：`RemoteSynced` reject ⇒ cache/base/etag/高水位全保持原状，
   下轮重下同一远端内容；`commitLocal` reject ⇒ 上传已发生但基线未动，meta ETag 仍为旧值 ⇒ 下轮重试上传
   遇远端新 ETag 412 转冲突 → 三方合并收敛（保守语义，无丢失）；合并采纳失败 reject ⇒ 云端已含 merged、
   基线未动 ⇒ 下轮按冲突流程再合并，不丢任何一侧。
4. **实现外置**：结算句柄实现 `DeferredBaselineSettlement` 落同包协作类
   `SyncEngineAdoptionSettlement.kt`（本批整改中 `SyncEngine.kt` 触及 tier1(>500) 规模闸门，拆分口径同
   §308 先例；`cache` / `rollbackGuard` / `recordAccepted(digest)` 三成员随之 `private`→`internal`）。
   `markResolvedAndUpload`（返回 `Result<String>` 无法携带句柄）**本批不动**，残余登记 `ISSUE-P2-313`。

### 2.3 测试（AC② / AC③）

- **AC② 第三轮重试用例**（`SyncMidCycleEditGuardTest` 新增）：第二轮下载窗口内注入「编辑并保存」⇒
  校验-采用如实中止（SESSION_DIVERGED）后，**第三轮** `runSyncCycle` 断言 provider 侧字节仍含「远端新增」
  条目且本地窗口编辑保留（修复前该场景第三轮以陈旧树本地赢上传、对端条目被抹掉——判别力由引擎级
  reject 用例与该端到端用例共同锁定）。
- 引擎级新用例 3 例（`SyncEngineTest`）：reject 后缓存 / 基线 / ETag / 高水位保持原状且重试可收敛；
  `commitLocal` reject 后基线不前移、缓存保留、accept 落地；结算句柄幂等且 reject 后 accept 不再落地。
- 既有引擎用例按「app 层采纳确认」语义适配：`openRemote` / `commitLocal` 返回后先结算再断言缓存与基线
  （21 处调用点 + `SyncEnginePreferenceBranchTest` 1 处）；`LoadedFromRemoteInSync` /
  `UpdatedCachedFileOnLoad` 两事件随 accept 发布，六事件用例同步适配。

## 4. 新发现与残余（如实登记）

- **补登 `ISSUE-P2-313`（P2）**：合并主路径 `markResolvedAndUpload` 仍在引擎内即时前移基线（返回
  `Result<String>` 无法携带结算句柄），两处采纳点（`autoMergeAndUpload` 的 `abortDiverged` 与
  `resolveConflicts` → `adoptMergedDatabase`）失败后同型损失链成立：采纳失败 ⇒ 下轮以「旧树+窗口编辑」
  本地赢整库上传，把云端刚接收的 merged 内容（含他端改动）静默覆盖。触发窗口＝合并上传网络窗口内的
  UI 编辑竞争或本地落盘失败，比 P2-308 窄但形态相同。本批已顺带修掉其 **412 重入侧**
  （`commitLocal` 两处，随 `Uploaded.settlement` 自然覆盖）。
- `openRemote` 决策树 KDoc 已同步声明分支 1 / 2 基线延后、分支 3 / 5（上传本地既有内容、无采纳窗口）
  照常即时前移。
