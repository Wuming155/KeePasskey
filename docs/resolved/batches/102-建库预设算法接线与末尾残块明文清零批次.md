## 102.1 `ISSUE-P2-85`：建库向导选择的加密算法被静默丢弃

### 症状与取证（2026-09-16，直读调用链）

| 环节 | 取证 |
|---|---|
| 向导 UI | `CreateVaultWizardDialog.kt:145-146`：默认 `selectedPreset = "ChaCha20 + Argon2id"`，候选为 `["ChaCha20 + Argon2id", "AES-256 + Argon2id", "Twofish + AES-KDF"]`；确认时把**字符串**上行 |

本条是本仓首次把它变成可执行整改。

### 处置

1. **新增类型化枚举 `CreateVaultPreset`**（`app/.../data/repository/`）作为**唯一真相源**：
   每项同时声明 `label` / `chipLabel` / `cipherUuid` / `useArgon2`；三档覆盖
   `CHACHA20`（默认）、`AES_256_CBC`、`TWOFISH`，均为 `CipherFactory` 已支持的外层算法。
2. **参数贯通**：`SessionOpener.create` 与 `DatabaseSession.create` 新增

   供「库已登记但文件缺失即初始化」这条**无预设入口**沿用，该入口改为显式传常量并留注释）。
3. **全链路去字符串**：`VaultRepository` / `RealVaultRepository` / `VaultLifecycleCoordinator` /
   `DatabasePickerViewModel` / `DatabasePickerScreen` / `CreateVaultWizardDialog`
   的 `preset` 形参一律改为 `CreateVaultPreset`；向导芯片由 `CreateVaultPreset.entries` 渲染，
   裸标签字符串只允许出现在枚举内（由用例反向锁定）。
4. **旧的字符串启发式删除**：`preset.contains("AES-KDF")` 不再存在——由用例断言其不得回归。

## 102.2 `ISSUE-P3-140`：`HmacBlockOutputStream` 末尾残块明文副本未清零

### 症状与取证（2026-09-16，直读源码）

`HmacBlockStream.kt:flushBlock`（修复前）:

```kotlin
val chunk = if (filled == blockSize) buffer else buffer.copyOf(filled)
sink.write(hmacer.compute(blockIndex, filled, chunk, 0, chunk.size))
sink.write(sizeBytes)
sink.write(chunk)
```

- 满块路径 `chunk === buffer`，其清零由 `close()` 的 `finally { buffer.fill(0) }` 承担 ✓；
- **末尾残块路径** `buffer.copyOf(filled)` 是明文的**独立副本**——`buffer.fill(0)` **碰不到它**，
  于是这段明文（KDBX 载荷片段）随局部变量出栈后静默留存至 GC。

**准确来源**：本条即第四轮复核工作目录的 **`NEW-B02-3`**。它在报告 §8 的根因矩阵
（`RC-CLEAR-3 明文缓冲无清零点`）中被**引用过**，但既未成为独立条目、也未被任何批次整改——
属「引用了但没修」的真空档。与 `ISSUE-P3-96`（CBC 流的两处明文副本）同型，正是本仓
「补一处、漏一处」的既有失效模式。

### 处置

`flushBlock` 中把「是否满块」提到前面，并在 `finally` 中对**仅残块路径**的副本清零：

```kotlin
val isFullBlock = filled == blockSize
val chunk = if (isFullBlock) buffer else buffer.copyOf(filled)
try {
    sink.write(hmacer.compute(blockIndex, filled, chunk, 0, chunk.size))
    sink.write(sizeBytes)
    sink.write(chunk)
} finally {
    // 满块时 chunk 即 buffer，清零会波及缓冲本身——那由 close() 收口，此处只清副本
    if (!isFullBlock) chunk.fill(0)
}
```

`finally` 保证**写出抛异常时同样清零**；满块路径**刻意不动**（其清零责任人仍是 `close()`，
提前清会抹掉尚未交付的块）。

### 回归（新增 2 例）与变异验证

`database`：`HmacBlockOutputStreamTailWipeTest`——

1. `末尾残块的明文切片写出后被清零`：以**记录型 sink 持有写入时传出的数组引用本身**
   （不是拷贝），在 `close()` 后直接检查该段内存是否已清零；两条防空扫断言（必须截获到引用、
   截获瞬间必须含明文）保证用例真的观察到了明文切片；
2. `写满的块由 close 的缓冲清零覆盖`：反向锁定满块路径不得被「只清副本」的修复顺手改写。

**变异验证（实做，非纸面）**：把清零语句临时改为 `if (false && ...)` 后复跑，
用例 1 **如期变红**（`tests=2 failures=1`），恢复后回绿——证明该断言确实约束被测行为。

## 102.5 过程缺陷（如实留痕）

1. **观察策略自伤（第二次）**：批量改 Kotlin 文件时先用 shell `sed` 查看再 `edit`，因未走 `read` 工具被文件系统观察策略拒绝
   （`file has not been read`）——**§101 已记录过同一错误**，本次在 `VaultRepository` / `RealVaultRepository`
   两文件上重犯。教训重复出现，说明「先 read 再 edit」必须是默认动作而非事后修正。
2. **测试辅助函数漏 `suspend`**：`VaultCreationCipherTest` 首版把「建库 → 重开」抽成普通函数，
   调用 suspend 会话 API 时编译失败（`Suspend function ... can only be called from a coroutine`），
   改为 `private suspend fun` + 各用例 `runBlocking` 后通过。
3. **真机环境变化（如实声明）**：本批开工时插着 `Redmi 4X`（arm64 / API 37），另按惯例起了
   `Pixel_10` 模拟器（API 36.1）；在**用户告知「连接了实体机，不需要使用虚拟机」后已停用模拟器**。
   ⇒ 本批及后续的设备侧验证**只以真机为准**；§101 记录的「65 例 × 2 设备」为**模拟器 + 真机**的历史数据，
   仍然有效，但**不再作为默认口径**。
4. **全量单测偶发一次（非本批改动引入，已登记）**：本批第一次全量 `test` 运行时
   `SyncCacheTest.\`clear 与 clearAll 均不删除防回滚状态文件\`` 失败，残留 `<大写十六进制键>.CACHE.tmp`；
   该命名**无法从本仓源码复现**（`SUFFIX_CACHE`/键均为小写），与 `RESOLVED_LOG.md` §79.5 第 1 条**逐字一致**，
   属该条明示的「再次观测」。**处置**：单独复跑该类 **3 次全绿**、随后全量复跑 **1941/0/0/13 全绿**，
   并按 §79 的指示**登记为独立线索** —— 新开放项 **`ISSUE-P3-142`**（留表，AC 要求定位写入者后再谈处置，
   且**定位前不得放宽断言**）。
