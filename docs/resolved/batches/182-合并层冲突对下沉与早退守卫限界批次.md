## 3. 逐字性证据

`python tools/doc/check_verbatim_move.py <原文件> <改后文件>`：

- 原文件内容行 **227** 种；
- 找不到仅 **2** 种：`val conflictPair = if (diffFields.isNotEmpty()) {` 与
  `return Pair(mergedEntry, conflictPair)`——即「先存局部变量再返回」被并成一次调用；
- 新侧独有仅 **6** 种：函数签名、形参 `diffFields: List<String>`、返回类型行、
  新调用点、两行新增 KDoc。
- `ConflictedEntryPair(entryId = local.id.toHexString(), ...)` 四行实参**逐字未动**。

**顺带修的是工具自己的一个 off-by-one**：`check_verbatim_move.py` 的参数校验写成 `len(argv) < 3`，
于是「一个原文件 + 一个本体」（单文件内下沉，正是本批形态）这种用法**直接打印 usage 并返回 2、
什么都不核对**——若不发现，本批会「核对了个寂寞」。已改为 `< 2`。

## 4. 度量口径再修一处：`grep -c "<issue"` 把根元素也数了进去

本批跑 `:sync:lintDebug` 时 `grep -c "<issue"` 报 **1**，而按 XML 解析 `findall('issue')` 得 **0**：
`lint-results-debug.xml` 的根元素是 `<issues format="6" by="lint 9.2.1">`，**前缀匹配把它也算了一条**。
⇒ 以此反推 `app` 侧的既有基线：**真实 lint 条目数是 215，不是 216**
（`xml.etree` 统计 `issue` 元素 = 215；`grep -c "^    <issue$"` = 215）。

- §166~§179 各批正文里记的「216（与基线持平）」**一律读作 215**：这些批次**前后用同一把尺**，
  「持平」的结论不受影响，但**数字本身是错的**，在此一次性更正口径，不逐份回改归档正文；
- 正确的复核写法：`python -c "... ET.parse(...).getroot().findall('issue') ..."`，
  或 `grep -c "^    <issue$"`；**不得**再用 `grep -c "<issue"`。
  与 §181 的教训同型：**度量工具必须用已知值反校**（此处已知值为「`<issues ` 恰好 1 行」）。
