## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

### `ISSUE-P2-91` 同步内容变化检测漏比 `times` 与历史内容（可能静默丢弃本地改动）

- **背景**：`app/src/main/java/com/keepasskey/app/sync/SyncContentChangeDetector.kt:93` 的 `isEntryContentChanged`
  比较 14 个字段 + `history.size`，**完全不比 `times`**（`expires` / `expiryTime` / `lastModificationTime` 等），
  历史也**只比条数不比内容**；而合并侧 `sync/.../merge/KdbxEntryMerger.kt:114` 明确把
  `times.lastModificationTime` 计入「已修改」——两处对同一问题给出不同答案（同文件 `isGroupContentChanged:68`
  已按 P1-8 把分组 `tags`/`customData` 纳入检测，条目侧未跟上）。
- **后果（已核实）**：`app/.../sync/SyncCycleRunner.kt:130` 在检测器判「无变化」时，本地字节**直接复用旧缓存快照**、
  不再序列化当前内存树，而这份旧字节即随后上传远端的内容 ⇒ **只改 `times` 的编辑不会被上传**，
  远端分支上还有被远端内容覆盖的风险。
- **整改方向**：补齐 `times` 比较；历史改为内容级比较（逐项字段比较或序列化后摘要比较）；
  两处判定若需保持不同口径，须在 KDoc 显式声明差异与理由。
- **验收标准**：新增用例覆盖「仅 `times` 变化」「历史条数相同但内容不同」两种输入，改造前必红；
  并给出「判定为无变化时不再复用缓存字节」或等价的结构性断言。
- **核实时间点与方式**：2026-09-17 主控直读 `SyncContentChangeDetector.kt:60-109`、
  `KdbxEntryMerger.kt:102-116`、`SyncCycleRunner.kt:127-139` 三处源码核实。
- **未核实（不得当结论）**：**是否存在可达的 UI 编辑面只会改 `times`** 未查；
  若确认存在，本项严重度应升为 P1。

## 2. 开工复核结论（**前提不成立**，据此改定修法）

登记条目时我把「是否存在可达的、只改 `times` 的编辑面」明确留作未核实项；本批开工即复核该前提，
**结论是否定的**，逐条证据如下（2026-09-17 全仓检索 + 逐处读源码）：

| # | 复核项 | 结论 | 证据 |
|:--:|---|---|---|
| 1 | 生产代码是否有写入 `expires` / `expiryTime` 的地方？ | **无** | 全仓命中仅 `KdbxXmlTimesNode.kt:38/40`（XML **读取**端）与 `KdbxXmlTimeHelper.kt:118-119`（默认值构造）；其余命中全在测试 |
| 2 | `times` 还有哪些改写路径？ | `KdbxEntry.withField`（`KdbxEntry.kt:43-50` 经 `times.withModified()`）与 `PasskeyEntryCoordinator.kt:149`（passkey 计数器补丁经 `times.withModified()`） | 前者**同时**改 `fields`、后者**同时**改 `customFields`，两者本就在比较集内 ⇒ 该 `times` 变化**必然伴随**已被检出的变化 |
| 3 | `usageCount` / `lastAccessTime` 是否会被「使用」单独 bump？ | **不会**：全仓无独立写入者，唯一写入点是 `KdbxTimes.withModified()`（由上述两条编辑路径触发） | 此前担心的「复制口令即 bump、进而触发重传」**在既有实现中不成立** |
| 4 | 合并路径写 `times`？ | 是，但与本判定无关 | `KdbxMerger.kt:181`（合并结果打时间戳）、`KdbxGroupMerger.kt:138`（取较晚 times）——都发生在**冲突/合并**流程内，其后必然走上传，不经「判无变化即复用旧字节」这条决策 |

⇒ **「仅 `times` 变化的本地编辑被静默丢弃」在既有可达面上不成立**，原登记的「可能静默丢弃本地改动」
结论**撤销**；同时 **P2 严重度亦不成立**（清单从 P2 段移出，见 §5）。

### 2.1 另一面：按原 AC 原文「补齐 `times` 比较」**反而有害**（故明确不做）

`KdbxTimes` 是**混装**结构：既含**内容语义**（`expires` / `expiryTime`）又含**使用性**字段
（`lastAccessTime` / `usageCount`）与 `lastModificationTime`，而 `KdbxEntry.withField` 经
`withModified()` **一次性改写三者**。若照原文把 `times` 纳入本比较：

- 「打开编辑页 → 原样保存」这类**触碰但内容等同**的操作会被判成「有内容变更」；
- 而本检测器判「有变化」的直接后果是**重新序列化 + 上传 + 前移远端 ETag**——
  这恰是该检测器存在的**理由**（其 KDoc 记 F5：KDBX4 随机 IV 使重序列化字节必然漂移，
  误判会产生无意义重传与多设备协同噪声）；
- 合并侧之所以**必须**比 `lastModificationTime`，是因为它回答的是不同的问题——
  「条目相对 **base** 是否被修改」（用于冲突裁决），不比就会让时间戳更新过的条目退出合并。

⇒ 两处口径**刻意不同**且**各有其正确性理由**，故本批按原 AC 的**另一分支**执行：
「两处判定若需保持不同口径，**须在 KDoc 显式声明差异与理由**」。

### 2.2 `history` 内容比较同样不做（同为口径而非缺陷）

历史只比**条数**。复核可达的历史变更：`recordHistorySnapshot`（追加）、
`HistoryManager.pruneGroupHistoryByAge`（按保留期修剪）、合并侧的并集——**三者都必然改变条数**，
故「等条数、内容不同」在既有可达面上同样不可达。⇒ 保持现状并把该口径与「日后引入等条数原地改写
历史即须改判据」写进 KDoc 与用例（锁定为**刻意不判为变化**）。

## 3. 本批实施

1. **抽出纯比较器**：判定逻辑（原三个 private 函数）逐字搬运为
   `app/src/main/java/com/keepasskey/app/sync/KdbxContentComparator.kt`（`internal object`，
   暴露 `changed` / `groupChanged` / `entryChanged`）。**动机**：该判定此前**零用例覆盖**
   （全仓无任何用例引用 `resolveLocalContentChanged`），而它是「本地编辑被静默丢弃」的唯一判据；
   抽出后可脱离 DI（`SyncDatabaseCodec` / `SyncSessionState`）直测——与本仓既有先例同构
   （§108 的 `ClipboardClearPolicy.resolveScheduledTimeoutSeconds`）。
2. **`SyncContentChangeDetector` 只保留与比较无关的分支**（基线缺失即按有变化保守处理）并转调新比较器；
   随之删除已不再使用的 `KdbxEntry` / `KdbxGroup` 导入。
3. **双向口径声明**（本次的核心交付，按 AC 的第二分支）：
   - `KdbxContentComparator` 类 KDoc 写明：本比较回答「**是否需要重新序列化上传**」，
     刻意不比 `times`，并给出前提复核结论与 `history` 的已知不覆盖；
   - `sync/.../merge/KdbxEntryMerger.isModified` 的 KDoc 增补**互补声明**：本判定回答
     「条目相对 **base** 是否被修改」，**必须**比 `lastModificationTime`；并显式写出
     「两处口径刻意不同，理由各自就地声明」及限界出处——防止后人以「口径漂移」为由
     **任一侧**「顺手对齐」。
4. **语义锁定用例 6 例**（`app/src/test/.../sync/KdbxContentComparatorTest.kt`）：
   - 条目内容字段**每一处**变化都必须被检出（15 个变异项：`fields` / `customFields` / `tags` /
     `attachments` / `iconId` / `customIconId` / `overrideUrl` / `qualityCheck` / `parentGroupId` /
     `previousParentGroup` / `customData` / `autoType` / `backgroundColor` / `foregroundColor` / `history` 条数；
     每项**双向**断言）；
   - 相同条目与空副本不判为变更；
   - **仅 `times` 的变化刻意不判为变更**（4 个变异项：`lastModificationTime` / `usageCount` /
     `lastAccessTime` / `expires` 语义，每项双向断言并在消息里写明理由）；
   - **历史条数相同而内容不同刻意不判为变更**（把 2.2 的口径钉成可执行断言；
     若日后引入等条数改写路径，该断言即失效判据）；
   - 分组字段**每一处**变化都必须被检出（12 个变异项 + 「条目/子分组 id 在新树中缺失」两条分支）；
   - 相同分组与「仅 times 变化的分组」不判为变更。

## 4. 边界与覆盖缺口（**不得**读作已验证）

1. **根级 `changed()` 未覆盖**：`deletedObjects` 比较 + 委托分组比较这一层**无用例**——
   构造 `KdbxDatabase` 需一并提供 `KdbxHeader` 与 `DeletedObject` 夹具，本批未做。
   本批锁定的是真正承载判定逻辑的 `entryChanged` / `groupChanged`。
2. **`history` 内容不覆盖**（见 2.2）与 **`times` 刻意不覆盖**（见 2.1）均为**有理由的口径**，
   分别以「刻意不判为变更」的断言锁定，不是遗漏。
3. **无任何真机 / 集成验证**：本批未改同步决策路径本身（`SyncCycleRunner` 一行未动），
   故未跑真实联调；判定行为的等价性由「逻辑逐字搬运 + 用例锁定」承担。
4. **未证伪「跨设备」场景**：复核针对**本仓生产代码的可达写入面**；
   若外部客户端写入只改 `times` 的条目并由本应用同步，其 `times` 变化同样不会被本判定读作内容变更
   （与「本应用不产生该形态」是两件事）——该边界与解除条件随 §10 一并登记。
5. **附件臂的等值语义**：`KdbxAttachment` 未覆写 `equals`，故附件列表比较实际是**实例级**比较
   （重建列表必然判为变化，方向安全但可能偏保守）。本批未改动，用例只锁定「附件列表变化必被检出」。

## 6. 过程缺陷与留痕

1. **用例设计首版存在等价变异项**：「子分组内容」变异项最初写成与基线**同 id 同 name**
   （`KdbxGroup(id = childGroupId, name = "S")`），分组递归比较对它会返回「无变化」⇒ 该断言会**假红**。
   跑测试**之前**自查发现，改为带 `notes` 的真变化（`notes = "子组改名"`）后语义正确。
   **未进入构建**（无失败留痕），据实记录——它同时说明「变异项必须真的与基线不同」这一纪律。
2. **首版设计曾考虑「整比 `times`」**：在读到 `KdbxTimes` 的字段构成与 `withModified()` 的改写面之前，
   我按 AC 原文准备直接补 `times` 比较；复核后放弃（理由见 2.1）。
   与 §121 的「`Mac` 复用」同属**对条目 AC 的实质修正**，两地均已留痕。
