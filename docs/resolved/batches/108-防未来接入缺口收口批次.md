### 108.1 条目原文（自 `ACTIVE_ISSUES.md` 原样搬迁，**不改写**）

> ### ISSUE-P3-143：`KdbxHeader` 相等性对 KDF secret 不敏感（零消费点的防未来接入缺口）
>
> - **优先级**：P3（INFO——**当前不可利用**；防未来接入）
> - **当前状态**：**开放项**——结构性缺口客观存在（`KdbxHeader.equals` 比较 `kdfParameters`，而 `KdfParameters.Argon2.equals` 忽略 `secretKey`/`associatedData`），但全仓零相等性消费点，故当前无攻击路径。
> - **来源**：第四轮复核工作目录 `NEW-B01-6`（原标 `[U]`：复核者未读到 `KdbxHeader.equals` 结尾）；`ISSUE-P3-141` 收口时**读到函数结尾**，前提被证实而非推翻。逐条取证与该编号的四选一结论见 `docs/security/第四轮复核遗留编号处置.md` 第 3.3 节（工作目录 `.audit-recheck/` 不随仓库分发）。
> - **核实时间点与核实方式（2026-09-16，对 HEAD `2e5ce38`）**：直读 `database/src/main/java/com/keepasskey/database/file/KdbxHeader.kt:29-53`（`equals` 第 39 行比较 `kdfParameters`，`hashCode` 第 51 行取 `kdfParameters.hashCode()`）与 `crypto/src/main/java/com/keepasskey/crypto/kdf/KdfParameters.kt:60,87-105`；全仓检索相等性消费点（`header ==` / `header !=` / `== header` / `equals`）在 `database|crypto|app|sync` 的 `src/main` 与 `src/test` **全部零命中**。
> - **问题描述**：`KdbxDatabase` 是 `data class` 且持有 `KdbxHeader`，`KdbxHeader.equals` 传递比较 `kdfParameters`，而 `KdfParameters.Argon2.equals`/`hashCode` **刻意忽略** `secretKey`（KDBX4 VariantDictionary `K`，秘密材料）与 `associatedData` ⇒ **两个 KDF secret 不同、其余字段相同的库会被判为相等**。忽略本身是**有意设计**（`secretKey` 是 `var`，`clearSensitive()` 就地置 null；纳入哈希会破坏清零后的哈希稳定性，`KdfParameters.kt:60` 已就地注明）。缺口在于：该「秘密不敏感相等性」**经 `KdbxHeader` 对外暴露**，而 `core.database` 恰是 `MutableStateFlow`（`database/…/session/SessionCore.kt:21`；StateFlow 按 `equals` 合并）——一旦未来出现「仅 `secretKey`/`associatedData` 变化」的赋值或集合去重路径，相应赋值/去重会被**静默吞掉**。
> - **当前不可达的依据（不得略去）**：`secretKey` 仅由反序列化赋值（`database/…/file/KdbxKdfParameterCodec.kt:194`），且保存会刷新 KDF salt 与 masterSeed（`database/…/file/KdbxFile.kt:337,342`）⇒ 不存在「其余字段全等、仅 secret 不同」的生产赋值路径。
> - **验收标准**：① 二选一并留痕——(a) 在 `KdbxHeader`/`KdfParameters.Argon2` 的 KDoc 显式声明「相等性是**秘密不敏感**语义，禁止用于『凭据是否变化』一类裁决」；或 (b) 新增回归用例断言该语义（含 `secretKey` 清零前后 `hashCode` 稳定），使未来若被消费时不至静默。② 若未来确有「仅 secret 变化」的赋值路径，须改为显式变更标记（如会话级 revision）而非依赖结构相等。③ 回归用例不得改变既有 `equals` 语义（避免引入「清零后哈希变化」的新缺陷）。
>
> ### ISSUE-P3-144：`armScheduledClear` 的分支顺序使 `customTimeoutSeconds` 无法强制擦除（Fix 陷阱）
>
> - **优先级**：P3（INFO——**当前零行为影响**；防未来接入）
> - **当前状态**：**开放项**——`customTimeoutSeconds` 形参在用户关闭「自动擦除剪贴板」时被静默忽略，且该事实未在 API 契约中声明。
> - **来源**：第四轮复核工作目录 `NEW-B04-05`（原判 `HARDENING`／Fix 方案缺陷）。逐条取证与该编号的四选一结论见 `docs/security/第四轮复核遗留编号处置.md` 第 3.5 节（工作目录 `.audit-recheck/` 不随仓库分发）。
> - **核实时间点与核实方式（2026-09-16，对 HEAD `2e5ce38`；主控 2026-09-16 独立复核）**：直读 `app/src/main/java/com/keepasskey/app/security/ClipboardSecurityManager.kt:174-188`（`:181` 的 `if (!settings.autoClearClipboard) return@launch` 早于 `:183` 的 `customTimeoutSeconds` 消费）；全仓检索调用方，确认**无任何调用点传入非空 `customTimeoutSeconds`**。
> - **问题描述**：`ClipboardSecurityManager.copySensitiveText`/`copySensitiveChars` 暴露 `customTimeoutSeconds: Int?`，其 KDoc（`:135`）只写「若为 null 则遵从 UserSettings」，**未声明**「非 null 也仍被用户的『关闭自动擦除』设置否决」。`ISSUE-P2-43` AC① 的备选方案「在敏感复制路径强制**不可关闭**的短擦除」若照此实现，会被静默满足为「仍然可关闭」——即本仓反复出现的**假加固**失效模式。
> - **为何当前不是漏洞（不得略去）**：① 无调用方传非空值 ⇒ 该分支当前不可达；② `ISSUE-P2-43` 已以「三处默认值同步翻转为关闭」在 §51 闭环，AC① 的「强制擦除」备选**未采纳**（见 `docs/resolved/batches/51-自动填充默认值与内存保护口径批次.md:17`）。
> - **验收标准**：① 在 `armScheduledClear` / 两个公开复制入口的 KDoc 显式声明该**否决语义**。② 新增 JVM 回归用例锁定现状与声明一致：`autoClearClipboard=false` + 非空 `customTimeoutSeconds` ⇒ 不调度清除；反向用例 `autoClearClipboard=true` + 非空值 ⇒ 按自定义秒数调度。③ 若未来采纳「强制擦除」，须改为「敏感路径无条件调度，仅把用户设置作为**上限**而非**开关**」并同步改本 KDoc。

### 108.3 变异验证（两次变异均如实变红后恢复，是「用例有效」的证据）

| 变异 | 结果 |
|---|---|
| **A-1**：`Argon2.hashCode` 纳入 `secretKey` | **3 例变红**：`仅 K 不同的实例哈希必须相同… expected:<1202001843> but was:<1202957174>`；`清零后哈希必须与清零前一致——这正是 secretKey 不得纳入 hashCode 的理由… expected:<1233435228> but was:<1202001843>`；`清零后 hashCode 稳定 expected:<1711927696> but was:<1711896879>` |
| **A-2**：`Argon2.equals` 纳入 `secretKey` | **2 例变红**（并连带既有 `crypto` 用例 `K 不参与 hashCode（既有语义）` 同时变红 ⇒ 两模块语义一致） |
| **B-a**：纯语句调序（生产等价于「`:181` 移到 `:183` 之后」） | **接线层守卫变红**，行为层**不红**——因为提前返回仍短路 ⇒ **该形态只有接线层能抓到** |
| **B-b**：提前返回改为与秒数共同裁决（`if (!autoClearClipboard && timeoutSec <= 0) return null`） | **行为层 3 例变红**（`expected null, but was:<7>` / `but was:<1>`），接线层抓不到 ⇒ **两层互补，缺一即漏** |

> **两层都保留的依据**：`B-a` 与 `B-b` 恰好各自只能被一层捕获——只留行为层会漏掉「纯调序」，
> 只留接线层会漏掉「共同裁决」。这条结论由**实测变异**得出，不是设计偏好。

### 108.6 边界与残余（如实声明）

   将来引入 Robolectric 可补端到端断言。

   故**形参声明顺序变化不再误报**；三条断言的失败消息现附「needle 下标 + 提取体原文」，真失配时可一轮定位。
3. **两条仍为 P3/INFO**：`ISSUE-P3-143` 当前不可利用（全仓零相等性消费点）、`ISSUE-P3-144` 当前零行为影响
