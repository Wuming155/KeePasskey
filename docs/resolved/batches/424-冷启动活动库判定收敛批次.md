## §1 条目原文（自 `ACTIVE_ISSUES.md` 整条剪切，逐字保留）

### ISSUE-P3-458：冷启动回显错库的密钥文件（活动库判定 `id/path/name` 或逻辑致同名库串库）

- **核实时间点**：2026-10-03；**核实方式**：真机 `M332BF` 复现——两个库文件名相同（本地 `vault.kdbx` 与云端 `vault.kdbx`），解锁页杀后台再进，密钥文件回显为「另一个库」那份；热重启（不杀进程）则正常。
- **根因定位**：`VaultDatabaseCatalog.buildDatabaseList` 的活动库判定用 `db.id == x || db.path == x || db.name == x` 的**或**逻辑。两个库文件名相同时（本地 `id="vault.kdbx"`、云端 `id="content://…/vault.kdbx"` 且 `name="vault.kdbx"`），`storedActiveId`（按文件名）会**同时命中两个库**，`firstOrNull { isActive }` 取列表首个（云端项在 `knownExternal` 先于内部项）→ 冷启动回显错库的密钥文件。热重启时内存态的活动库是对的，故只在「杀后台冷启动」暴露。
- **验收标准**：① 冷启动活动库唯一，且优先按 `id` 精确命中（同名库不再同时活动）；② 密钥文件按库命名空间跟随，杀后台再进回显「杀后台前所在库」的那份；③ 全量 test 绿 + 门禁全 PASS；真机走查留痕。

## §2 根因

活动库持久记录 `storedActiveId` 只反映「上次点卡片选中的库」；冷启动由 `buildDatabaseList` 据 `storedActiveId` 还原活动库（第 195-197 行：`sessionActiveIdentifier` 为 null，只用 `storedActiveId`）。其 `isActive` 判定为三条件**或**：

```kotlin
val isActive = (db.id == effectiveActiveId || db.path == effectiveActiveId || db.name == effectiveActiveId)
```

当存在两个 **`name` 相同但 `id` 不同**的库（最常见：本地 `vault.kdbx` 与云端 / content:// `vault.kdbx`），`effectiveActiveId`（按文件名）会同时命中两者 → 两者 `isActive` 皆 `true` → `combined.firstOrNull { it.isActive }` 取 `combined` 首个（外部库先于内部库）→ 冷启动活动库落到「错的那一个」→ 密钥文件按 `SHA-256(dbId)` 自然读到错库那份。

`KeyFileVaultCopyStore` / `RealSettingsRepository` 的按库命名空间本身正确、无需改动；病灶仅在「活动库解析」这一步。

## §3 整改

`VaultDatabaseCatalog.buildDatabaseList`：活动库改**唯一判定**，优先按 `id` 精确命中，仅当 `id` 未命中才回退 `path/name`（兼容历史遗留 `storedActiveId` 可能落为路径 / 文件名的旧记录）：

```kotlin
// 活动库唯一判定：优先按 id 精确命中。仅当 id 未命中时，才回退 path / name
// （兼容历史遗留的 storedActiveId 可能落为路径 / 文件名的旧记录）。
// 不能用 id/path/name 的「或」逻辑：两个库文件名相同时（例如本地 vault.kdbx 与
// content://…/vault.kdbx 同名）会被同时标为活动库，冷启动 firstOrNull{isActive} 取列表首个，
// 从而回显错库的密钥文件 —— 这正是「杀后台冷启动才暴露」的现象。
val resolvedActive = combined.firstOrNull { it.id == effectiveActiveId }
    ?: combined.firstOrNull { it.path == effectiveActiveId || it.name == effectiveActiveId }
val list = combined.map { db ->
    val isActive = db.id == resolvedActive?.id
    db.copy(isActive = isActive, /* lastOpenedAt 同原逻辑 */)
}
```

净变更：`VaultDatabaseCatalog.kt` 234 → 242 行（不触档位）；`VaultLifecycleCoordinator.kt` 未改。

**过程缺陷（如实留痕）**：初版曾尝试在 `unlockActiveDatabase` 成功分支补 `selectDatabase(activeDb.id)`「解锁即登记活动库」作为对齐 P3-464「保存位置即登记」的防御性加固。但该行把 `VaultLifecycleCoordinator.kt` 从 399 → 407 行，跨过 400 行档，令 `tier2(400~500)` 由 36 升 37 越过预算，门禁 `count_line_tiers` fail-closed 转红。复盘判定该加固**冗余**——不同文件名的两个库经选择页点卡片已落盘活动库，唯一真缺陷是同名库撞 `name` 的解析，已由本批精确判定修复；故回退该冗余改动，`VaultLifecycleCoordinator.kt` 维持 399 行，门禁恢复 9/9。
