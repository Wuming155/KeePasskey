# §414 批次：取串通道本地化修复（`StringsProvider` 经 Application context 取串，恒系统语言）

> 本批**更正 §413 的结案结论**。§413（ISSUE-P3-453「硬编码中文清扫」）机检 8/8 PASS、
> `test` 全绿、审计 `21 → 0`，却在真机英文界面下整屏中文——**典型的假绿**。根因不在 §413 改的
> 文案内容，而在**取串通道本身没接应用内语言**。详见 §2。

## 1. 原文收录（触发本批的真机走查原话）

用户 2026-10-03 装机走查（设备 M332BF，`app_language=EN_US` 已落盘，系统 locale `zh-CN`）：

> 更改主密码界面还是中文，同步失败是中文

## 2. 根因与证据链（按证据先后逐个落定，不靠推断）

1. **资源侧无缺失**：`app/src/main/res/values/` 三份中文资源（`strings.xml` + `strings_sync_passkey.xml` +
   `strings_ui_messages.xml`，并集 1429 键）与 `values-en/strings.xml`（1429 键）**键全齐**；
   `values-en` 里**值仍含 CJK 的键只有 1 个**——`settings_lang_zh`（`简体中文 (Simplified Chinese)`，
   语言选择器自身的合理值）。⇒ 「键存在 ≠ 值是英文」此路不通，资源不是根因。
2. **英文通道确实可达**：`unlock_error_invalid_password` 的 en 值为
   `Incorrect master password or key mismatch`，正是用户看到的 `incorrect master...`。
   ⇒ 应用内语言（EN_US）设置生效、资源可达，**不是**「根本切不了英文」。
3. **两条通道口径不一致**：用户报的现象里，唯独「输错密码」是英文、其余五处全中文。这条**不一致**
   就是签名——走 Compose `stringResource(LocalContext.current)` 的拿到 `localizedContextOf` 的
   ContextWrapper（`KeePasskeyApp.kt` 经 `CompositionLocalProvider(LocalContext provides localizedContext)`）⇒ 英文；
   走 `StringsProvider` 的那批拿不到 Wrapper ⇒ 中文。
4. **真凶定位**（`app/src/main/java/com/keepasskey/app/di/StringsProviderModule.kt`）：

   ```kotlin
   @Provides @Singleton
   fun provideStringsProvider(@ApplicationContext context: Context): StringsProvider =
       StringsProvider { id, args -> context.getString(id, *args) }   // ← 修复前
   ```

   `@ApplicationContext` 的 resources 在**进程创建时按系统 locale 定形**，`getString` 永远解析系统语言文案；
   既不会随 `appLanguage` 变更重新配置，也拿不到 UI 层 ContextWrapper。
   §413 恰好把 30+ 个消费点**全改走 `StringsProvider`** ⇒ 中文**一个字都没少**，
   只是从「硬编码中文字面量」换成了「Application context 恒中文」。
5. **机检为何是假绿**：`tools/audit/check_user_visible_cjk.py` 规则 A/B/C 判的是「**内容里有没有中文**」，
   压根不看「**取串通道跟不跟语言**」。文案已全部资源化 ⇒ 字面量零命中 ⇒ 全绿。
   与 ISSUE-P3-305「闸门存在 ≠ 闸门被执行」同源——这次是「机检通过 ≠ 缺陷消除」。

## 3. 整改

- `app/ui/AppShellLocalization.kt`：
  - 新增 `localizedResourcesFor(context, locale)`——按目标 locale 现取 `createConfigurationContext`
    派生 `Resources`，与 UI 侧 `localizedContextOf` 口径完全一致（不是包一层 Wrapper，而是直接重建 Resources，
    供非 Composable 的非 Context 通道使用）。
  - 新增 `@Singleton AppLocaleTracker`——把 `SettingsRepository.getSettings()` 流里的 `appLanguage`
    收敛成可同步读的 `Locale` 字段（`launchIn(CoroutineScope(Dispatchers.IO))` + `snapshot()` 兜底补取）。
    **冷启动刻意不做 `runBlocking` 同步首值**：Hilt 在主线程创建本类，同步首值会让主线程等 DataStore 冷读，
    有启动期 ANR 风险；代价是进程刚拉起的最初一帧可能仍是系统语言（数十毫秒内 Flow 回填）。
- `app/di/StringsProviderModule.kt`：生产绑定改为
  `localizedResourcesFor(context, localeTracker.snapshot()).getString(id, *args)`，并在 KDoc 钉死铁律。
- `tools/audit/check_user_visible_cjk.py`：新增**规则 D**——`StringsProviderModule.kt` 的
  `provideStringsProvider` 若①未见 `localizedResourcesFor(` 派生、或②直接对 `context` 调 `getString(` ⇒ 红。
  自校样本加两例（好样本 0 命中 / 坏样本 2 命中），`"StringsProviderModule.kt"` 文件名级反校，
  避免规则 D 在自校里恒不触发。判据只锁这一个绑定点，不做「全仓禁 Application context 取串」的宽扫
  （误报会诱使后来者放宽判据——误报比漏报更危险）。

## 5. 真机取证（`adb` 实测，非推断）

装机：`com.keepasskey.debug`，`lastUpdateTime=2026-10-03 08:25:28`，设备 M332BF（`warsaw`，`a7eb933d`）。

取证手法（可复用）：`export MSYS_NO_PATHCONV=1` 后
`adb shell am force-stop …`/`monkey` 拉起 → `cmd statusbar collapse` →
`uiautomator dump /data/local/tmp/w.xml` → `adb shell cat` 抽 `text=`。
**两个坑**：① Git Bash 会把 `/sdcard/...`、`/data/local/tmp/...` 本地化成 Windows 路径，
必须 `export MSYS_NO_PATHCONV=1` 且**同一次调用链里全程保留**；② 不收起状态栏时 dump 到的是
`NotificationShade`，拿不到 App 界面。

## 6. 遗留与下一步

- **冷启动首帧**：`AppLocaleTracker` 构造即 `launchIn`，若进程刚拉起的最初一帧取串，可能拿到系统语言文案
  （数十毫秒内 Flow 回填）。已按「宁可一帧、不可 ANR」取舍；若后续有用户报首帧闪中文，再按
  「在 `MainApplication.onCreate` 的 IO 线程预取一次」补，别改回主线程同步首值。
- **机检仍盯不住的通道**：`Toast` / `Snackbar` 直传字面量、`Notification` 文案、`strings.xml` 缺 en 键，
  本脚本/j 检都不覆盖（各自有别的出口）。规则 D 也只锁 `provideStringsProvider` 一个绑定点。
- **§413 §4 的通过标准已作废**（其前提「英文界面下可走查中文残留」在 §413 装机包上不成立），
  更正见 [413-用户可见硬编码中文清扫批次.md](413-用户可见硬编码中文清扫批次.md) §5。
