## 438.1 整改内容

1. `UnlockScreen.kt`（有库分支）：品牌区（锁块 + 标题 / 状态胶囊 / 两条一次性提示）**整组收敛为一个子 `Column`**——
   外层滚动列的顶级子节点自此恒为「品牌组 / 动作组」两个，`SpaceBetween` 的空隙才落在两者之间
   （改版前品牌区与卡片是同级散节点，结构性无法只在一处分缝）。
2. `verticalArrangement` 由 §436 的恒定 `Top` 改为条件式：
   `uiState.hasDatabase && uiState.unlockMode == UnlockMode.QUICK_UNLOCK` → `SpaceBetween`；
   其余（**标准解锁页 / 空状态**）保持 `Top` 不变。判定式是纯呈现口径（不进 `UnlockUiState`，见 438.0-1）。
3. 底部避让由 `imePadding()` 改为 `windowInsetsPadding(WindowInsets.navigationBars.union(WindowInsets.ime))`——
   卡片落底后，原先只有 24dp 内边距的底部会被导航栏 / 手势条压住（三键导航下可达 48dp）；
   并集逐边取最大值，键盘弹起时**不叠加**，故仍满足既有「P0 整改」口径（inset 避让必须在滚动容器**之前**）。
4. `UnlockScreenPreviews.kt`：新增 `UnlockContentQuickUnlockPreview`（浅 / 深各一张）——极速解锁页此前**没有页面级预览**
   （只有 STANDARD 页面级 + 卡片级），而本次投诉的正是这一屏，属 `ISSUE-P3-340` 口径的补态。
5. 机制（已写进代码注释，附出处而非推测）：`fillMaxSize` 的最小高度约束会**穿过** `verticalScroll` 抵达列——
   foundation `Scroll.kt` 的 `ScrollNode.measure` 只 `copy(maxHeight = Constraints.Infinity)`，`minHeight` 原样下传
   ⇒ 内容不足一屏时列仍有一屏高，`SpaceBetween` 才分得出空隙；内容超一屏时空隙为 0
   ⇒ 退化为「顶锚 + 滚动」，与改版前行为一致。**未**引入 `BoxWithConstraints` / `heightIn` 等额外取高手段。

## 438.2 为什么只有极速解锁页改判（取舍留痕）

标准解锁页的主密码行与 IME 耦合：键盘开合会把这份空隙在 0 ↔ 满之间反复挤压（聚焦瞬间白造一次整页跳动），
且该页主按钮本就在屏高 ~77%（拇指区以内），落底收益为零。空状态分支按 §436 口径维持「Logo 置顶 + 居中」不变。
