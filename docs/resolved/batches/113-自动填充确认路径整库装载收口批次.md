## §113 自动填充确认路径整库装载收口批次（2026-09-17，app）：ISSUE-P3-148

> **批次性质**：`ISSUE-P2-88`（§111）修复**新引入**的调用面收口——确认页复用选择器的 ViewModel 以共享取数实现，
> 却连带继承了「整库非敏感投影装载」这一**只对搜索页成立**的固有开销；本条把它按调用路径拆开。
>
> **本条不影响正确性，只影响开销**（原文口径），故本批的验收**不**以真机功能表现为准，
> 而以「确认路径不再装载整库 + 仍取得到凭据」两条**可断言**的行为为准，并附**负向对照**实测。

### 113.1 条目原文（自 `ACTIVE_ISSUES.md` 原样搬迁，**不改写**）

> ### ISSUE-P3-148：自动填充确认页每次确认都加载整库条目投影（实际只需一条）
>
> - **优先级**：P3（开销 / 性能——**不是缺陷**，是 `ISSUE-P2-88` 修复**新引入**的调用面）
> - **当前状态**：**开放项**——不因本条而回退 `P2-88` 的修复（那条路径的正确性已验证通过）。
> - **来源**：`ISSUE-P2-88` 修复过程中发现（确认页复用选择器的 ViewModel 以共享取数路径）。
> - **核实时间点与核实方式（2026-09-17 对 HEAD `92cc25f` + §111 工作区）**：直读
>   `app/src/main/java/com/keepasskey/app/autofill/AutofillPickerViewModel.kt`——
>   `:41` / `:44` 的 `_entries` 状态、`:51-56` 的 `init` 装载 `vaultRepository.getKdbxEntries()`（**整库**）、
>   以及 `:95` 的 `cachedUsername(entryId) ?: vaultRepository.getKdbxEntries()`（**回退分支同样装载整库**）；
>   对照 `AutofillConfirmActivity` 中新增的 `AutofillPickerViewModel by viewModels()` 注入点。
> - **问题描述**：选择器页本就装载整库投影（该页要搜索，属其固有开销）；但**确认路径**是本批**新增**的调用方——
>   它每次只处理**一条**条目（`EXTRA_ENTRY_ID` 已给出），却会触发整库投影装载，且在缓存未命中时**再装载一次**
>   （`:95` 的回退）。⇒ 大库上每次「确认填充」多付一到两次与库规模成正比的装载成本。
> - **验收标准**：① 确认路径改走「按 id 取单条」的路径（或给仓库层加「优先单条查询」的接口），
>   不再触发整库装载；② **不改变** `ISSUE-P2-52` 的锁定态 fail-safe 语义（空用户名降级，不得改为抛错/放行）；
>   ③ 回归覆盖两条：确认路径**不再**装载整库、且**仍取得到**凭据（用户名与口令）。
> - **注意**：本条**不影响正确性**，只影响开销；也**不**要求改选择器页（其整库装载是设计使然）。
> - **依据**：`RESOLVED_LOG.md` §111；`app/src/main/java/com/keepasskey/app/autofill/AutofillPickerViewModel.kt`；`AutofillConfirmActivity.kt`。

### 113.3 整改内容（3 个面，共 6 个文件）

**① 仓库层新增「优先单条查询」接口**

- `VaultRepository.getKdbxEntries()` 补**调用面约束**（只允许确实需要全库的调用方；只处理一条已知 id
  的调用方一律改用 `getKdbxEntry`），并新增 `suspend fun getKdbxEntry(entryId: String): KdbxEntry?`——
  **不设默认实现**（本仓具体实现仅 `RealVaultRepository` 与测试替身 `FakeVaultRepository` 两处，
  都同批实现；设默认实现会给未来实现方留一条「悄悄退化为整库装载」的路，与本条要消灭的形态同型）。
- `RealVaultRepository.getKdbxEntry`：`parseKdbxUuidOrNull` + `db.rootGroup.findEntry(uuid)`——深度优先
  短路搜索，**不**物化整份条目列表。会话锁定 / 库未打开 / id 非法 / 条目不存在一律 `null`。
- `FakeVaultRepository.getKdbxEntry`：Fake 无树结构，按同 id 语义在既有快照上取首条（**仅供单测**）。

**② VM 的整库装载改为**显式惰性**，且退出确认路径**

- `AutofillPickerViewModel.init` **只保留会话锁定观察者注册**，不再装载整库（新增 `entriesLoadStarted`
  字段 + `loadEntries()`：幂等，供选择器页调用）。
- `resolveCredentials` 的缓存未命中回退由 `getKdbxEntries().firstOrNull { … }` 改为 `getKdbxEntry(entryId)`；
  缓存**命中仍优先**（选择器选中场景免一次仓库查询，行为不变）。KDoc 同步更正。
- `AutofillPickerActivity.onCreate` 显式调用 `viewModel.loadEntries()`——**选择器页的整库装载是设计使然，
  本批不削减**（条目「注意」项），只是把发起方从 VM 内部挪到唯一需要它的页面。
- `AutofillConfirmActivity` 的复用注释补明「本页**不**调用 `loadEntries`，取数全走单条查询」。

**③ 按 id 读取条目一律走 `findEntry`（免整表物化）**

- `VaultEntrySecretReader` 内 **9 处** `currentDb.rootGroup.allEntries().firstOrNull { it.id == targetUuid }`
  → `currentDb.rootGroup.findEntry(targetUuid)`（口令 / 历史修订口令 / 修订快照 / 受保护自定义字段 /
  TOTP 计算 / TOTP 配置原文 / 附件数据）。语义等价性：`allEntries()` 的扁平化顺序（本组条目 → 各子组递归）
  与 `findEntry` 的深度优先短路顺序**逐层一致**，故「首个命中项」同一；差异只在**成本面**——后者不构造列表。
  类 KDoc 补上该口径，避免后人改回。

### 113.6 验证与边界

**验证**：`.\gradlew.bat test --rerun-tasks --max-workers=1` → `BUILD SUCCESSFUL in 1m 50s`（114 tasks executed），
聚合 `tests=1977 skipped=13 failures=0 errors=0`（相对 §111 的 1975 例 **+2**，即本批新增 3 例、
重写前旧例 1 例）；`bash tools/audit/check_recheck_consistency.sh` → `PASS`（本批未触碰任何复核报告）。

**边界如实声明**：

1. **无性能实测**。本批**没有**做「大库上确认一次到底省了多少 ms」的基准测量，也未在设备侧验证；
   证据只有**调用面**断言（整库装载调用数 = 0）与代码路径直读。理由：本条 AC 的判据是「不再触发整库装载」，
   未要求量化收益；且宿主 JVM 上的微基准不能代表设备侧大库表现。
2. **复杂度未改善**。`findEntry` 仍是 **O(N) 遍历**（深度优先、首命中短路），本批消除的只是
   「**整份条目列表的物化**」与随之而来的分配 / 拷贝成本，**不得**读作「确认路径已是 O(1)」；
   若未来要进一步降低，需在会话内建 id → 条目的索引，属**另行裁决**的结构变更（本批不做）。
3. **`getKdbxEntry` 不设默认实现是有意的**（见 113.3 ①），代价是未来新增 `VaultRepository` 实现方
   必须显式实现它——这是「宁可编译期报错、也不静默退化为整库装载」的取舍。
4. **整改范围**以条目正文点名的调用面 + 同一验收标准覆盖的按 id 读取面为限；仓库层其余
   `allEntries()` 调用点（写路径 `VaultEntryWriteCoordinator` / 回收站 `RecycleBinCoordinator` /
   克隆 `EntryDuplicateCoordinator` / `PasskeyEntryCoordinator` 等）**未动**——它们不属于
   `ISSUE-P3-148` 描述的确认路径，其成本特征与调用频次需另行评估（**未声称**全仓已无同类模式）。
5. 未跑 `assembleRelease`（本批无 R8 / 资源相关改动）。
