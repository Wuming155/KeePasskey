### ISSUE-P3-447：SAF（自选位置）通道是「二等公民」——本地建库无法云同步 + 外部修改漂移防护缺真实元数据管道

- **进展（§411，2026-10-02）**：**AC① 已收口**——同步周期对本地文件的唯一依赖是「远端路径默认名」，`runSyncCycle` / `takeoverVaultBinding` / `resolveRemotePathForProbe` 三处改为「活动文件名优先、库 meta 名兜底（`<库名>.kdbx`）」，SAF 库得以进入同一同步周期；绑定 / 缓存 / 防回滚键同构不变。用户反馈的「下滑提示当前无打开的密码库文件」根因即此（该库已配置云同步，`isSyncConfigured` 为 true，进周期后在 `currentFile` 早退）。剩余 ②③ 未动。
- **核实时间点**：2026-10-02；**核实方式**：用户 §408 批次装机走查反馈「云端同步不能将本地建的库同步到云端」「保存失败并提示磁盘文件被修改」；代码直读 + 真机取证（`run-as com.keepasskey.debug` 私有目录无 `.kdbx` ⇒ 走查库为 SAF 自选位置通道）。
- **背景**：SAF 库的会话无本地 `File`（`DatabaseSession.currentFile` = null），三处按本地文件假设实现的功能对 SAF 失效：① `SyncCycleRunner.runSyncCycle` 首行 `currentFile ?: Error(sync_error_no_open_vault_file)`——SAF 库同步恒报错（同步本体只需内存树 + 文件名，`activeFile` 仅用于推导远端文件名）；② 漂移防护（P2-378）：基线在 SAF 打开时曾落 `fromMetadata(path,0,0)` 占位假值、保存时 `current` 恒 null ⇒ 恒判漂移 ⇒ **SAF 库每次保存被中止**（2026-10-02 临时止血：`VaultFileBaselineHolder.capture` 对 `file == null` 不落基线，按「元数据不可读 ⇒ 宁可不提示」口径放行，SAF 库保存恢复可用，但漂移防护在 SAF 通道**暂缺位**）；③ 保存中止后列表仍呈现内存态未落库条目，用户无从分辨「已保存 / 仅内存」（P2-378 设计如此，缺可感知性）。
- **验收标准**：  
  ① SAF 库可配置云同步并完整走通同步周期（远端文件名经 `ContentResolver` / `DocumentsContract` 查显示名或以库 meta 名兜底，绑定 / 缓存 / 防回滚键与本地库同构）；  
  ② SAF 通道接入真实 `DocumentFile` 元数据管道：打开 / 保存两时点取真实 lastModified + size 重建漂移基线（替换本次止血口径），漂移防护在 SAF 与本地 File 两通道同强度；  
  ③ 保存被中止（或仅内存态）时，列表页对未落库条目有显式「未保存」可感知标记或提示（低危，可随批降级为核实结论登记）；  
  ④ 全量 test 绿 + 门禁全 PASS；真机 SAF 库走查保存 / 同步两链路留痕。

- **定性＝宿主 NTFS 目录枚举鬼影，不是生产竞态**：残留名 `<大写HASH>.VERSION.tmp` —— **大写、无 UUID**，
  与 `SyncCacheFiles.tmpFileFor`（`<名>.<UUID>.tmp`，恒小写）不同构；全仓检索确认**没有任何代码路径会产出该名**

  §7 已明书更强判别式「**同路径短时有界重枚举（15 ms × 4，实测 380 例假阳性 0 命中）**——刻意未采纳…**可按需启用**」；
  本条即其启用点。
- **同时发现的真生产缺口（同族，故同批修）**：`SyncCache.writeCache` / `writeCacheStreaming` 与

  `updateBase` / `receiveRemote` 都有）——写盘或原子交付任一步失败，承载 KDBX 密文片段的 `.tmp` 会留在

### 2.2 P3-447：SAF 漂移为何必须连「重载 / 合并」一起做

- 只打开漂移检测而不补 SAF 的处置路径会造出**死路**：`VaultFileDriftResolve` 的重载 / 合并两分支都硬要求
  `localFile != null`（`reloadFromDisk` / `mergeAndSave` 首行判「磁盘库文件不可读」）⇒ SAF 库一旦检出漂移，
  用户在「放弃 / 重载 / 合并」里选后两者只会得到失败，**此后无法保存**。故 AC② 的实现面必然包含
  「SAF 通道的重载 / 合并」。
- 「元数据不可读」必须与「文件消失」分开：本地 `File` 通道下 `current == null`＝文件已消失 ⇒ 判漂移（宁可提示）；
  SAF 通道下 `current == null` 通常只表示**提供方不暴露该列** ⇒ 必须放行（这正是 2026-10-02 那次
  「每次保存都被中止」的教训）。
- AC③ 的现状核实：保存中止时确有**全局三选对话框** + `ext_mod_save_aborted` 失败文案，但**列表页本身无任何标记**
  ——条目照常渲染（内存树），用户关掉对话框后无从判断「哪些改动没写进磁盘」。故 AC③ 不是空缺口，
  本批按「提示」形态实现（列表页横幅），未降级。

### 2.3 P3-466：三个可疑面逐条对上代码

- ① `UnlockViewModel` 的活动库判定 `databases.firstOrNull { it.isActive } ?: databases.firstOrNull()` ——回退首项
  会**改写 `activeDatabaseId`**（密钥文件记忆 / 封印凭据的命名空间），列表刷新瞬时无显式活动项即误绑、误触发复位。成立。
- ② `MasterPasswordUnlockSession.onUnlockSuccess` 调 `wipe()` 清表单，但 `keyFileUserTouched` **不复位**；
  锁库回解锁页同库同 VM 不满足「活动库切换」⇒ 既无恢复入口、标记还挡着恢复 ⇒ 表现即「选择没保存」。成立。
- ③ `DatabasePickerViewModel.removeDatabase` 删库只清副本（`keyFileVaultCopyStore.clear(id)`），**不清按库记忆键**
  ⇒ 真机取证「按库记忆 5 条 vs 副本 2 个」的无主陈旧记录累积。成立。

### 3.2 P3-466（四条整改方向逐一落地）

- **① 恢复决策探针**：`KeyFileRestoreChain.probeRestore`——每次恢复只记
  `密钥文件恢复探针: branch=<分支>, dbIdHash=<SHA-256 前 4 字节>`；分支含
  `access_unavailable` / `user_touched` / `copy` / `copy_missing` / `copy_discarded_user_selected` /
  `disabled_without_copy` / `no_record` / `memory` / `memory_unusable` / `memory_unreadable`。
  **不落**库 id 原文、Uri、显示名或任何密钥材料。
- **② 只认显式活动项**：`UnlockViewModel` 的 databases collect 拆出 `explicitActive`（`isActive`）与
  `displayActive`（回退首项）。**回退首项只用于展示**（库名 / 状态 / 快速解锁可用性查询也改取显式 id，
  无显式项时沿用上次 dbId，仍无则按不可用 fail-closed），**绝不改写 `activeDatabaseId`** ⇒ 不误触发复位、不误恢复别库。
- **③ 回前台再恢复 + 解锁成功消费选择**：`KeyFileRestoreChain.shouldRestoreOnResume`
  （表单为空 + 非用户显式清除 + 有活动库 + 无在途读取）＋ `KeyFileSessionCoordinator.restoreOnResumeIfIdle`
  （在途任务取消与发起时机收口在协调器，Screen 只转发 `ON_RESUME`）；
  `MasterPasswordUnlockSession.onUnlockSuccess` 在 `wipe()` 后调 `consumeSelectionAfterUnlock()`
  复位「用户显式选择」标记 ⇒ 锁库回解锁页可按本库记录重新恢复。**显式清除**（`clearKeyFile` /
  `onKeyFileReadFailed`）仍挡住恢复（尊重用户意图）。
- **④ 删库同批清按库记忆键**：`DatabasePickerViewModel.removeDatabase` 成功路径新增
  `keyFileAccess?.forget(id)`（与既有副本清除同批）。
- **结构拆分（§280 单文件阈值）**：恢复裁决链（分支判定 + 探针 + 副本 / 按库记忆两级恢复）自

  字段所有权仍只属协调器）；「何时发起恢复」与在途任务保留在协调器（它才持有 `scope`）。
