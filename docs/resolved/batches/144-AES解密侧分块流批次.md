# §144 · AES 解密侧分块流批次（ISSUE-P3-155 闭环）

> **批次主题**：`AesCipherEngine.createDecryptingStream` 由 `CipherInputStream`（内部 512 B 缓冲）
> 切换为既有 `CbcDecryptingInputStream` 分块骨架（64 KiB + `AES/CBC/NoPadding` 变换）。
> **闭环条目**：`ISSUE-P3-155`。
> **实测依据**：[`records/真机吞吐实测记录_2026-09-17.md`](../../records/真机吞吐实测记录_2026-09-17.md) §1（采纳前后同机同探针对比）。

---

## 1. 条目原文要点（开工复核结论）

- 前提复核成立：`AesCipherEngine` 流包装即 `CipherInputStream` / `CipherOutputStream`，前者内部
  固定 512 B 缓冲（无构造参数可调）；既有 `CbcStreams.kt` 是为原生 Twofish 写的分块流先例。
- **范围收窄（依据真机实测 §1）**：加密侧 `CipherOutputStream` 对 ≥512 B 写入本已直通
  `Cipher.update`（实测 1.0× 无收益），**仅解密侧整改**；条目原文「512 B 瓶颈」的表述据此修正。
- 契约约束：`Cipher` 自带链值状态，与 `CbcBlockTransform` 的「iv 原地演化」契约不匹配——
  本批的解法是 **NoPadding 变换 + Cipher 自持链值**（见 §2），未触碰 Twofish 路径。

## 2. 实现（单文件，`AesCipherEngine.kt`）

- `createDecryptingStream`：改返回 `CbcDecryptingInputStream(source, key, iv, transform)`，
  其中 `transform` 为**流实例私闭包**：`(key, iv, data) -> NoPadding Cipher.update(data)`。
- **契约匹配的关键**：JCE `AES/CBC/NoPadding` 对分组整数倍输入的全量解密**无「持有块」语义**，
  与 `CbcBlockTransform` 的「全量返回、独立数组」契约兼容——同形先例是
  `CbcStreamFramingTest.bcCbcDecryptTransform`（Twofish/BC，框架层已有 JCE-作-变换的实证）；
  PKCS#7 去填充由流包装的 `Pkcs7.unpad` 承担，与 Twofish 原生路径**共用同一填充实现**。
- 链值由 `Cipher` 自持，`iv` 形参不回写（一个流恰一个 `Cipher`，观测结果与「链值随变换推进」等价）。
- `cipher.update` 返回 `null` 时 fail-closed 抛 `CryptoException`（不静默吞字节）。
- 加密侧逐字未动（`CipherOutputStream` + PKCS5）；`encrypt` / `decrypt` 整块 API 未动；
  `CbcStreams.kt` / `Pkcs7` 零改动（Twofish 路径不受影响）。

## 4. 过程缺陷与如实声明

- **用例自身缺陷一次**：首版对拍用例在比对基线**之前**就把 `restored` 清零（use-after-wipe），
  误报「length=1 基线不一致」；修正断言顺序后通过——**新路径本身正确**，教训与 §140 同源
  （断言写错，不是实现错）。
- **基线口径漂移一次**：条目与框架 KDoc 均记载「空输入 → 基线抛 `IOException`」，该结论实测自
  **Twofish/BC**；本组合实测宿主 **SunJCE** 对空密文**不抛异常、静默产出空**。按 fail-closed
  原则维持框架行为并在用例 KDoc 登记差异（生产不可达 + 静默空明文是更危险形态）。
- Twofish 的 **JCE 兜底**解密路径未同批分块化（原生内核在真机可用〔§143 修复探活后〕，
  兜底仅存在于缺 ABI 的极端形态；如未来需要可同法处理）。
- 未跑 `lint` / `assembleRelease`；设备侧在单台 Redmi 4X 完成。
