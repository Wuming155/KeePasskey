- **暂停前交接（2026-10-13，只读调用链核对）**：没有591代码增量。待593/601稳定身份、代次和写入边界后，用同一独立快照票据贯穿各上传、采纳、ETag与本地文件检查点；A上传期间保存B时，B必须仍为待同步，不得把B记为A的检查点。

- **整改方案**：[ISSUE-P1-591 独立方案](../../architecture/问题整改方案/P1/ISSUE-P1-591/同步提交快照一致性方案.md)；方案已编制，尚未实施。

- **核实时间点 + 核实方式**：2026-10-13；直读同步起点快照、上传成功分支及内容变化检测优先级，构造 A 上传 / B 保存交错；动态复现待补。
- **背景 / 位置**：`app/.../sync/SyncCycleCommitPaths.kt:114-115` 等分支使用 `databaseSession.databaseFlow.value` 更新 `lastSyncedDb`，不是实际上传的 `localDbSnapshot`。`SyncContentChangeDetector.kt:59-65` 优先使用该基线。
- **触发 / 后果**：上传 A 的网络等待期间用户完成并保存 B；上传后误将 B 设为基线，后续可能继续使用 A 缓存并将远端改动覆盖 B。
- **建议 / 验收**：上传字节、内容树、凭据版本和文件检查点须对应同一快照；补受控网络暂停下「上传 A→本地 B→完成→再次同步」及他端 C 交错，保证 B 被上传或进入冲突而不被无提示丢弃。
- **详细证据**：[全面软件审计](../../security/全面软件审计_2026-10-13.md)。

## 2. 实施与验收

- **前提复核（认领时，2026-10-14；直读 + 逐分支核对）**：前提成立——五条提交 / 采纳路径
  （`tryFastCommitPath`、`establishRemoteBaselineIfMissing`、`handleRemoteSynced` 两处、`takeoverVaultBinding`、
  `LocalWinAutoUploaded` / `RemoteLostRestored`、`SyncConflictController.applyForcedConflictStrategy` 的 TakeLocal）
  一律在结算时刻读取 `databaseSession.databaseFlow.value` 赋给 `session.lastSyncedDb`；行号随历次重排漂移，
  对象与事实全部在案。依赖 593/601 的共享身份契约已分别于 §505 / §510 / §504 闭环。

- **改动一（新增 `SyncUploadSettlement.kt`：基线结算原语）**：新增
  `internal enum UploadSettlement { CONVERGED, LOCAL_DIVERGED }` 与
  `settleSyncedVersion(session, uploaded, active)`。判据＝**「会话活动树 `active` 与实际上传 / 已确认版本
  `uploaded` 是否同一实例」**——`KdbxDatabase` 走 copy-on-write，每次编辑 / 保存产出新实例，故
  **实例身份 ≡ 内容修订号的进程内代理**（与既有 `DatabaseSession.adoptDatabaseIfUnchanged(expectedSnapshot)`
  同一把尺）。同一实例 ⇒ 前移基线并回报 `CONVERGED`；不同实例 ⇒ **不动基线**、**不持有非活动树引用**
  （敏感擦除仍由活动树那一次 `clearSensitiveData()` 承担，见 `ISSUE-P3-235` G2 口径），回报 `LOCAL_DIVERGED`。

- **改动二（新增结论 `SyncOutcome.LocalPendingChanges`）**：显式表示「远端已接受本轮上传 / 确认的版本，
  但上传窗口内用户又保存出新版本 ⇒ 本地仍有待同步修改，下一轮才上传」。它**不是**「已收敛」结论：
  `SyncLocalFileCheckpoint.isInSyncWithRemote()` 明确将其排除（否则会把 B 误记成本地文件检查点，下一轮判定
  「本地文件自上次同步未变」而错过 B）。

- **改动三（六条路径统一改走 `settleSyncedVersion`，基线只前移到实际发送 / 已确认版本）**：
  - `SyncCycleCommitPaths.tryFastCommitPath`：快速提交成功支——**注意此地 `databaseSession.save()` 可能已把
    窗口内新版本 B 写入本地正式文件**，基线必须停在 A；
  - `SyncCycleCommitPaths.establishRemoteBaselineIfMissing`：首传成功支（`localBytes` 即首传版本）；
  - `SyncCycleRemoteOutcomes.handleRemoteSynced`：**两处** `UpToDate` 支（缓存命中 / 远端内容一致）；
  - `SyncCycleRunner`：`takeoverVaultBinding` 与 `LocalWinAutoUploaded` / `RemoteLostRestored` 两支；
  - `SyncConflictController.applyForcedConflictStrategy` 的 TakeLocal（「以本地为准」上传的即 `localBytes` 快照）。
  `SyncDatabaseCodec.loadAndApplyRemoteBytes` 的 APPLIED 支**有意不改**：采纳路径带「校验-采用」守卫，
  采纳成功即活动树 == 采纳树，与 `settleSyncedVersion` 判据等价。
  为让各调用点拿到「与字节等价的本地内存树」，有关函数签名新增 `localDbSnapshot: KdbxDatabase`
  （首传 / 快速 / 强制 / 常规 / 接管五处传参均为**周期起点快照** `ctx.currentDb` / `ctx.localDbSnapshot`）。

- **改动四（回显按新结论分型，三处）**：`SyncOutcomeDescription` 新增分支；
  `VaultListSyncController` / `SettingsSyncController` 的 `when` 各增一支 ⇒ 出
  `UiMessage(R.string.sync_feedback_local_pending)`，**不置「已同步」时间、不谎报已同步**；
  `values/strings.xml` + `values-en/strings.xml` 成对新增 `sync_feedback_local_pending`。

- **测试（新增 `SyncUploadSnapshotConsistencyTest`，4 例；回读 XML `tests=4 failures=0 errors=0 skipped=0`）**：
  复用 `SyncMidCycleEditGuardTest` 的「窗口编辑」钩子（记录型 `WindowEditProvider` 在 `upload()` 落库**之后** /
  `getMetadata()` 返回**之前**真实执行一次 `saveEntry + save`，即生产上窗口内的事件序列），用例：
  ① **上传 A 期间保存 B**（AC 第 1 行）：本轮报 `LocalPendingChanges`、`isInSyncWithRemote()` 为 false、
     远端为 A（含「本地A」不含「窗口内B」）、B 仍在会话树、`lastSyncedDb` **仍为 L0 不前移**，第三轮收敛后

  ③ **两端一致（未上传）窗口内保存 B**：常规 `RemoteSynced` 内容一致支不谎报 `UpToDate`、基线保持 L0；

## 4. 限制与后续边界

- **「他端 C 交错」未直接注入**：方案 §4 第 2 行「上述时序后另一端写 C ⇒ B 与 C 合并或进入冲突，B 不静默
  丢失」**未**新增用例（未在夹具中模拟第三端写 C）。**结构上已保证**：本轮基线不前移（停在 L0），
  下一轮内容变化检测仍将本地判为「已变」，B 必然被送进既有**合并 / 冲突**机制（该机制由
  `SyncConflict*` / `KdbxMerger` 既有用例常态锁定）——即「B 不被静默丢弃」由基线不变量承担，
  而非由本批新用例逐帧复现。如实留痕。
- **强制策略 / 接管路径未逐条用例化**：`TakeLocal`（`applyForcedConflictStrategy`）与 `takeoverVaultBinding` /
  `LocalWinAutoUploaded` / `RemoteLostRestored` 三支的代码面已统一改走 `settleSyncedVersion`，但**仅**
  `tryFastCommitPath`（用例①）与「常规 / 首传」被用例覆盖；强制策略分叉分支**未**新增定向用例
  （其分支判定与用例④同型，属薄调用）。如实留痕。
- **方案 §3 步 1 的「凭据代次」未单独建模**：本批以**实例身份**作内容修订号 / 换库判据（`active !== uploaded`
