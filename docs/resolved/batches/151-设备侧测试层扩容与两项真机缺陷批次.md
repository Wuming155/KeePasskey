2. **`sync` 设备层只有 1 个类（`SyncCache` 文件权限 3 例）**，`WebDavPropfindParser` 走的

3. **名为「真机契约」的用例其实在自证**：`PasskeyCreationDeviceTest` 的类名与 KDoc 声称

   （import 而未用）；`CredentialManagerBindingDeviceTest` 用**合成 hex 字符串**喂
   `CallerCertDigests`，真实 `SigningInfo` 面零覆盖。
   旁证：`grep -rl "androidx.credentials" app/src/test` **命中 0**，
   `CredentialManagerCallerBindingWiringTest` 只对**源码文本**做 `contains` 断言。
4. **`app` 层大量 AndroidKeyStore / BiometricPrompt / WorkManager / 剪贴板 / 通知 / SAF 消费方**
   只有宿主假实现作证据（清单见 `ISSUE-P2-192`）。

**设备用例的注入形态（值得单记）**：API 34+ 上 `PendingIntentHandler.retrieveProviderGetCredentialRequest`
读的是**平台** `android.service.credentials.GetCredentialRequest`（键
`CredentialProviderService.EXTRA_GET_CREDENTIAL_REQUEST`），**不是** androidx 自己的
`ProviderGetCredentialRequest.asBundle(...)` 那条（仅 `Api23Impl` 使用）。本批用例因此改走
「androidx 公开构造器产出规范 Bundle → 平台 `CredentialOption.Builder` → 平台请求 → Intent」，
并在装配处自检 `credentialRetrievalData` 槽位（形参顺序若错，换型会**静默降级**为
`GetCustomCredentialOption`，用例仍可能「看起来通过」）。

## 4. 发现① `ISSUE-P1-190`：向 `Mac.getInstance` 传 `"AndroidKeyStore"` provider 致防回滚在真机静默停用

**发现方式**：本批新增的 `AndroidKeystoreSecretGuardsDeviceTest` **真机首跑即红**
（`KeystoreSyncIntegrityMac.compute()` 返回 `null`）。

**缺陷形态**：`app/src/main/java/com/keepasskey/app/sync/KeystoreSyncIntegrityMac.kt` 的
`compute()` 原写 `Mac.getInstance(ALGORITHM, KEYSTORE_PROVIDER)`。AndroidKeyStore 是
**KeyStore provider**，不注册 `Mac` 服务 ⇒ 该调用抛 `NoSuchAlgorithmException`
（口径沿用 `UnlockThrottleIntegrity` 在 **ISSUE-P0-10** 已真机验证并明文写下禁令的诊断原文；
本用例未捕获该异常字符串，因为 `compute` 的 `catch (_: Throwable)` 把它吞成了 `null`——**这本身是第二层缺陷**）。
`compute` 返回 null 后 `verify` 恒 false，而 `SyncRollbackGuard` 对「校验不过」的处置是
**视状态为不可信（等同无历史）** ⇒ **防回滚（拒绝旧库重放）在每一台真机上永久停用**，
且**零留痕**：宿主 JVM 的假实现注入固定密钥，全绿。

**这是同类缺陷的复发**：`ISSUE-P0-10` 已在同仓另一处 HMAC 消费方写下禁令
（`UnlockThrottleIntegrity.kt:106-111`：「**不得**向 `Mac.getInstance` 传 AndroidKeyStore provider……
密钥仍由 AndroidKeyStore 持有与运算」），而 `KeystoreSyncIntegrityMac`（ISSUE-P2-18 引入）
未落在该禁令的射程内——**禁令只存在于一个文件的注释里，就等于不存在**。

**修复（生产代码，最小面）**：
1. `Mac.getInstance(ALGORITHM)`（**不传 provider**），密钥仍由 AndroidKeyStore 持有并在其内运算；
2. `catch` 不再静默：落 `AppLog.w` **只记异常类型**（绝不记载荷 / 密钥材料），
   使「防线整体失效」在下一次真机跑或线上日志里可见。
   同批留痕：全仓另检索 `getInstance(…, "AndroidKeyStore")` 的同类误用，
   命中面为 `KeyGenerator` / `KeyStore` / `SecretKeyFactory`（三者均**注册在**该 provider 下，合法）
   与 `KeyFactory.getInstance(privateKey.algorithm, …)`（EC/RSA/ED25519 已注册，合法）⇒ **无第二处**。

**回归锁**：`AndroidKeystoreSecretGuardsDeviceTest` 的 5 例（真机 **5/5 绿**）——
其中「MAC 必须可往返」这条就是本缺陷的红→绿判据。

## 5. 发现② `ISSUE-P1-191`：Android 平台 DOM 对 `setXIncludeAware(false)` 抛错，致 PROPFIND 解析整体落空

**发现方式**：本批新增的 `WebDavPropfindParserDeviceTest` **首跑 3 例红**，且红的是**对照用例**
（一份完全合法的 multistatus 报文，etag 却解析为空）——即「加固代码自己让解析通路死掉」，
而非安全防线被绕过。为定位真因，在设备侧跑了临时隔离探针（逐项 setter + 逐项换型），实测事实：

```
IMPL   = org.apache.harmony.xml.parsers.DocumentBuilderFactoryImpl
FEATURES = disallow-doctype-decl=ParserConfigurationException
           external-general-entities=ParserConfigurationException
           external-parameter-entities=ParserConfigurationException
           load-external-dtd=ParserConfigurationException
setXIncludeAware(false)              -> UnsupportedOperationException: This parser does not
                                        support specification "Unknown" version "0.0"
setExpandEntityReferences(false)     -> OK
newDocumentBuilder()（生产顺序）      -> UnsupportedOperationException（同上）
newDocumentBuilder()（仅 ns=true）    -> OK，且无 DOCTYPE 的对照报文 etag 正常解析
XXE 探针（文件实体 / 外部 DTD 子集）  -> 哨兵明文未出现在任何结果字段
```

**缺陷形态与后果**：`WebDavPropfindParser.hardenedFactories`（ISSUE-P3-172 引入的按线程工厂缓存）
把 `isXIncludeAware = false` 以**裸赋值**写在容错 helper 之外 ⇒ 异常顺着 `ThreadLocal` 初始化落到
`parse` 的 `catch (Throwable)` ⇒ **真机上每一次 PROPFIND 解析都返回空元数据**。
后果按 `WebDavSyncProvider:138-155` 的口径逐条落实：
`etag` 恒空 ⇒ 只能退回 207 响应的 HTTP `ETag` 头（多数服务端不下发）⇒
`SyncEngine` 的基线比较 / `If-Match` 条件请求 / 防回滚高水位失去远端标识；
`contentLength` 恒 `-1` ⇒ 退回 207 报文自身的 `Content-Length`——**正是该类注释点名的「撒谎」面**
（「误当文件大小会让零字节文件元数据撒谎并污染同步基线比较」）；`isDirectory` 恒 false。
桌面 Xerces 支持该项 ⇒ 宿主 `WebDavPropfindParserTest` 一直全绿。

**修复（生产代码）**：
1. 两项布尔加固改经**新的就地容错** `applyXxeGuardSetting`（与四项特性同一「尽力加固 + 可观测告警」
   口径；该方法刻意写成扩展函数，**不得**回头调 `hardenedFactory()`——那会在 `ThreadLocal`
   初始化内自入重入循环）；
2. **补上平台侧真正有效的 XXE 防线**：`newHardenedBuilder()` 为每次解析的 `DocumentBuilder`
   装配空实体 `EntityResolver`（任何外部实体一律以空输入兑现）。理由：四项 Xerces 特性名在
   Android 上**全部未生效**（实测仅落告警），意味着 KDoc 里「禁用外部实体」这条纵深防御
   在设备上从未真正存在过——原注释「`isExpandEntityReferences = false` 与不加载外部 DTD 的
   默认语义仍在」**已作为错误推定就地更正**（真机证据见上）。桌面侧仍另有特性项把关。

**回归锁**：`真机加固不得让整篇PROPFIND解析落空`（合法报文四字段逐项必须真实采信）+
`真机平台DOM不得展开外部实体`（两类 payload + 无 DOCTYPE 的反向对照，避免「整篇没解析」的假阴性）
+ 深度 / 日期 / 畸形共 **6 例真机全绿**。

## 6. 过程留痕（用例侧的三条契约教训，均非生产缺陷）

1. **`BeginCreatePublicKeyCredentialRequest` 的 `callerToken` 不可传 `Bundle.EMPTY`**——
   构造函数会向该 Bundle 写入（`ArrayMap is immutable` 直接抛 `UnsupportedOperationException`）。
   真机首跑即红，改传新建 `Bundle()` 后通过。
2. **特权白名单的指纹形态**：`certDigests` 产出**无冒号**大写 hex，而 androidx `getOrigin` 的
   校验器比对的是**大写冒号分隔**形态（`SignatureVerifier` 内 `joinToString(":") { "%02X" }`）。
   生产侧由 `toColonSeparatedUpper` 统一派生，用例首版直接把 `certDigests` 喂进
   `buildAllowlistJson` ⇒ 正例红。修正在用例侧（显式走同一转换函数），
   顺带证明：**若生产侧漏了这一步，本用例会以同样的形态变红**。
3. **`android.credentials.CredentialOption.Builder` 的 Bundle 形参顺序**：
   `(type, credentialRetrievalData, candidateQueryData)`。首版按 `(type, candidate, retrieval)`
   传参被**自证断言**当场抓住（装配后 `credentialRetrievalData` 为空）——
   该自证断言是本批唯一能在「换型静默降级」时仍然报红的护栏，保留在用例内不删。
