## 2. 逐项实现

- **① KDoc 失效表述**：原文写「内核级吞吐**显著领先**（真机 158.7 / 249.2 MB/s）……见实测记录 **§7**……
  该对照须以**连续多轮**实测为准，**单轮不作结论**」——三处均已过期：① 「显著领先」已由 §8 证伪
  （现代机 Rust 内核本体加密 13.3 ms **慢于** JCE 全程 9.2 ms）；② 158.7 / 249.2 是**单机（A53）**数字，
  正是限界 §17 明令「不得外推」的用法；③ 数据已迁 §8、结论已定。
  现改为指向限界 **§17** 的定论（取向 = 统一与审计一致性，不以性能为由）。
- **② 密钥长度闸门**：原生内核 fail-closed 拒绝非 32 字节密钥，而 **JCE 会接受 16 / 24 字节**
  （静默按 AES-128 / 192 加密）⇒ **同一输入两种行为**。现于 `encrypt` / `decrypt` /
  `createEncryptingStream` / `createDecryptingStream` **四条入口**统一 `requireAes256Key`。
  KDBX 的 `cipherKey = resize(masterSeed‖transformed, cipherKeyLen)` 对 AES 恒为 32 字节 ⇒
  对合法输入**零影响**（由全量 2144 例 + 设备侧套件回归证明）。
  Twofish **无此分歧**（其内核与 BC 都接受 16 / 24 / 32，`TwofishNativeParityTest` 已覆盖）。
- **③ 探活扩到 4 分组**：单分组向量**测不出「链值推进写错」**，而链值推进（`dst = E(src ⊕ chain)`
  后以密文更新链值并回写 `iv`）恰是流式分段的核心契约。现探活额外断言 **加/解后 `iv` 均等于末组密文**；
  若破损则探活 fail-closed（按设计回退 JCE），并由设备侧 `AesNativeDeviceTest.原生内核探活_真机必须可用`
  的硬断言**响亮失败**——即「降级静默」与「失效可观测」两者兼得。
- **④ 兜底常态回归**：三个引擎的兜底路径（JCE / BC）原本**只在「原生不可用」时执行**，
  而原生可用时（CI 装了 cargo、本地开发机、全部真机）**一律走原生** ⇒ 兜底近乎无常态覆盖。
  现以 `internal constructor(...)` 形参强制兜底（**公开无参构造保持不变**，`CipherFactory` 与设备侧
  用例行为零变化），新增 `CipherFallbackParityTest` **7 例**：
  - 无条件运行：三引擎兜底路径的整型 / 流式往返正确（长度含空 / 单字节 / 跨分组 / 跨 64 KiB）；
  - 原生可用时：**兜底产物与原生逐字节一致**（整型 + 流式，覆盖同长度集）；
  - AES 追加：**非 32 字节密钥在兜底路径同样 fail-closed**（与闸门同口径）。
- **⑤ 立规**：`AGENTS.md` §5 新增「原生面改动的验证义务」——改 `crypto/src/main/rust/**`、
  `jni_bridge_ext.rs`、任一 `Native*` 绑定 / 引擎的原生分派与**探活**，**必须**跑完设备侧三层
  `connectedDebugAndroidTest` 方准入库（宿主单测看不见 Android 运行时差异：§147 的「全零密钥解密」=
  宿主 100% 绿、仅真机失败；§143 的「平台 BC 抢占 `"BC"`」同源）。
- **⑥ 登记**：`PD-06`（密码学实现收敛到 Rust，**不引入 Botan**——效率无收益 / 可维护性净负 /
  供应链纪律冲突；重开条件 = 出现非 Android 分发目标）、`PD-07`（**流语义两套刻意保留**——JCA
  `CipherInputStream` 内部 512 B 缓冲会把解密压到 15.3 MB/s，自研骨架 64 KiB 达 55.5 MB/s；
  代价由 `CbcStreamFramingTest` + `CipherFallbackParityTest` 双重锁定等价）。
  `ISSUE-P3-187` 追加：**第三条候选路线 `CipherSpi`（有状态 Provider）**、**AC ⑤「有状态 vs 无状态」四维对照**、
  以及 **JNI 面现状覆盖清单**（把该条目的「未闭合项」定义为唯一：零拷贝 + 有状态形态）。

> **设备侧为何必须跑（本批新立的规则自身也适用于本批）**：本批改了**探活逻辑**（①③）与**引擎原生分派**

> 「原生被静默弃用」暴露出来）。本次 4/4 绿 ⇒ 新旧探活在真机上均通过。

## 4. 如实声明：**本批不改善性能**

| 指标（10 MiB） | 整改前 | 整改后 |
|---|---|---|
| AES 生产整块加密（现代机） | 48.1 ms | **48.1 ms（不变）** |
| AES 生产整块加密（A53） | 250.9 ms | **250.9 ms（不变）** |
| 对平台 JCE 的差距 | 5.2× | **5.2×（不变）** |

- 本批收益的正确衡量方式是「**靠人记住 / 靠注释承诺的薄弱点从 4 处降到 0**」，
  而非「快了多少」；性能的唯一改善口子是 `ISSUE-P3-187`（零拷贝），且其最好情况**仅追平** JCE。
- **不得**把本批读作「AES 下沉的性能问题已解决」。

## 5. 过程留痕与如实声明

- **① 本批的起因是一件我自己的缺陷**：§147 落地时我在 `AesCipherEngine` KDoc 里写下了
  「内核级吞吐显著领先」并引用单机数字——那是**用单机内核数字外推**，正是我随后在限界 §17 里
  明令禁止的用法。**同一批工作里写下了规则又违反了它**，这条留痕保留不美化。
- **② 方法学承接**：本批沿用 §147 的教训——结论必须有实测支撑（探活/等价断言均为可执行证据），
  且**测试只增不删**（本批为纯新增：1 个测试类 + 7 例，无任何删除）。
- **③ 如实说明**：`internal constructor` 形参是**为可测试性给生产类加的一点复杂度**，
  属有意取舍；替代方案（测试内反射 / 全局可变开关）更差。公开构造与生产行为**零变化**已由
  `CipherFactory`（无参构造）+ 全量 2144 例 + 设备侧套件三方证明。
