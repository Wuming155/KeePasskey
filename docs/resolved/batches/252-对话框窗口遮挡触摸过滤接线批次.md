## 2. 整改内容（逐条对 AC）

### AC① 生产代码：`SecureDialogWindowEffect()` 同一 `DisposableEffect` 内叠加遮挡触摸过滤

- **施加**：进入时取 `dialogWindow?.decorView` 的 `filterTouchesWhenObscured` 原值并置 `true`；
  `onDispose` 时**恢复原值**（save/restore 语义，与 `ApplyObscuredTouchFilter` 同款）。
- **fail-safe 不变**：`dialogWindowOrNull()` 返回 null 时 `previousFilterTouchesWhenObscured` 亦为 null
  ⇒ 既不写入、也不回写**任何**窗口（不误改 Activity 窗口）。
- **既有 `FLAG_SECURE` 语义一行未改**：`addedByThisWrapper` 的判定、`addFlags` / `clearFlags` 的调用
  条件与 `SecureDialogFlagPolicy` 的两条不变式**逐字保持**（本批只在其后追加过滤段）。
- **`dialogWindowOrNull()` 由 `private` 改 `internal`**：设备侧用例须以**同一解析口径**取窗口
  （否则断言的只是「另一种取窗口方式的结果」）。KDoc 已记该可见性理由。
- **KDoc 新增「遮挡触摸过滤」整节**，逐条落三项结论：
  1. **为何用对话框窗口的 `decorView`**：与 `FlagSecureGuard.applyObscuredTouchFilter` 对 Activity 窗口
     的既有施加点同口径（同一威胁面用同一施加点，便于审计）；`decorView` 即窗口根（`DecorView`，`ViewGroup` 子类）。
  2. **为何不用 `Window.setHideOverlayWindows(true)`**：该 API 是 `Window` 级，语义为「阻止非系统悬浮窗
     **绘制**在本窗口之上」（javadoc 原文 "Prevent non-system overlay windows from being drawn on top of
     this window"，`Window.java:1151-1153`；须持 `HIDE_OVERLAY_WINDOWS` 权限，本仓已在 Manifest 声明）
     ——抑制的是**绘制 / 可见性**，**不**等价于「触摸一定被丢弃」；且依限界 §3.3 既有结论，它只阻断
     **新**覆盖、**不**解除**已存在**的遮挡窗口。
  3. **API 文档与过滤覆盖面**：见 §5 第 2 条（规格所引措辞与 SDK 实际 javadoc **不符**，已按直读原文落地）。
     另核实：`FILTER_TOUCHES_WHEN_OBSCURED` 自 API 1 即有，`setFilterTouchesWhenObscured` /
     `getFilterTouchesWhenObscured` 在本地 SDK 源（`android-36.1`）**无** `@RequiresApi` /
     `@RequiresPermission` 标注 ⇒ **无权限、无版本门槛**。
- **`可测性` KDoc 同步更正**：原文「真正的 `addFlags`……**留待设备侧验证**」改为指向本批的真机用例，
  并把「不证明什么」的边界一并写入（见 §5）。

### AC② 宿主守卫：`ObscuredTouchWiringTest` 新增第 3 条不变式

新增 `对话框窗口加固同时施加防截屏与遮挡触摸过滤`——源码文本比对 `SecureDialog.kt` 四项判据：
① 有 `addFlags(… FLAG_SECURE)`；② 有 `clearFlags(… FLAG_SECURE)`；
③ 有 **`filterTouchesWhenObscured = true` 这一行**（**仅剩**「读原值 / 还原」两处出现**不算**通过——
那正是「把施加那行删掉」的故障形态，也是本批反向反校 ① 的判据）；④ 有对话框窗口解析
（`dialogWindowOrNull()` 或 `DialogWindowProvider`）——缺第 ④ 项则前三项可能作用在 Activity 窗口上。
**既有两条清单与判据一行未改**（`rootComposableScreens` / `setContentWindows` 与两条用例原样保留）。

### AC③ 真机实证：`DialogWindowHardeningDeviceTest`（2 条用例）

**宿主方案（含一处规格未列的必需新增）**：宿主 Activity 必须位于**被测应用**的清单/进程，故放在
`app/src/debug/`（`DialogWindowHardeningHostActivity.kt` + `app/src/debug/AndroidManifest.xml`）。
理由与现场留痕：首轮把宿主声明在 `app/src/androidTest/AndroidManifest.xml`（测试 APK 包
`com.keepasskey.app.test`）时，`ActivityScenario.launch` 在真机上直接抛
`java.lang.RuntimeException: Intent in process com.keepasskey resolved to different process
com.keepasskey.test`（`Instrumentation.startActivitySync` 拒绝跨进程启动组件）；且即便绕过，
对话框窗口会组合在**另一进程**、测试进程读不到。`release` 变体不含 `src/debug` ⇒ 生产包（含其清单）零改动。

**用例 1 `对话框窗口获得遮挡触摸过滤并携带遮罩且关闭后撤销遮罩`**（宿主窗口**带** `FLAG_SECURE`,
等价生产 `MainActivity` 的「会话锁定 / 防截屏开关开启」态）：三条断言全部通过——
① `decorView.filterTouchesWhenObscured == true`；② 对话框窗口 `flags=0x1802002`（含 `FLAG_SECURE=0x2000`）；
③ 关闭对话框后 `flags=0x1800002`（该位已清）。

**用例 2 `宿主窗口未携带FLAG_SECURE时对话框遮罩被Compose清除`**（宿主窗口**不带**，等价生产
「已解锁 + 用户关闭防截屏开关」态）：正面锁定本批成果——**过滤照样施加**（`filterTouchesWhenObscured=true`，
与宿主窗口状态无关）；同时**锁定并留证**新发现的缺口 `ISSUE-P2-246`：对话框窗口 `dialogFlags=0x1800002`
**不含** `FLAG_SECURE`（宿主窗口 `0x81810100` 亦不含）。该断言的失败信息已写明「修掉缺口后本断言即红，
须同步更新 `ISSUE-P2-246`」。

## 5. 如实声明

1. **改动面**：`SecureDialog.kt`（AC①，生产代码，+51/-2 行）、`ObscuredTouchWiringTest.kt`（AC②，+1 例）、
   新建 `app/src/androidTest/.../DialogWindowHardeningDeviceTest.kt`（AC③）、
   新建 `app/src/debug/java/.../DialogWindowHardeningHostActivity.kt` 与 `app/src/debug/AndroidManifest.xml`

   `SecureDialogFlagPolicy` 与 `SecureDialogFlagPolicyTest` 的既有断言、四个对话框文件本身（一行未改）。
2. **AC① 要求的 API 文档引用与 SDK 实际措辞不符（规格与事实不一致，按直读落地）**：
   规格要求引用 `View#setFilterTouchesWhenObscured` 的 **"the view and its descendants"** 措辞；
   本地 SDK 源（`~/AppData/Local/Android/Sdk/sources/android-36.1/android/view/View.java`）直读结果是：
   类级 Security 段为「…the framework will discard touches that are received whenever **the view's window**
   is obscured by another visible window at the touched location. As a result, **the view** will not receive
   touches whenever the touch passed through a toast, dialog or other window…」，
   `getFilterTouchesWhenObscured()` 的 javadoc 同义——**全仓源中无 "the view and its descendants" 字样**。
   故 KDoc 改引**真实原文**，并补上「连同后代一并丢弃」的**实现**依据（`View.onFilterTouchEventForSecurity`
   在遮挡且带 `FILTER_TOUCHES_WHEN_OBSCURED` 时返回 false，`View.java:16854-16860`；
   `ViewGroup.dispatchTouchEvent` 以该返回值包住整段子视图派发，`ViewGroup.java:2658`）。
   网络不可用（`FetchURL` / 搜索引擎均失败），故以**本地 SDK 源**为权威依据。
3. **调用点计数与规格不一致**：规格称 6 处，**实测 7 处**（`CreateVaultWizardDialog.kt:67` 未被规格枚举），
   已在 §1 与限界 §3.3 按实测值记录。
4. **AC③ 的第 2 条断言的「归因」不可达（本批最重要的如实声明）**：规格要求断言「该对话框窗口
   `FLAG_SECURE` 位已置……**同时补上 `SecureDialogFlagPolicyTest` 自陈的『真实 `addFlags` 未覆盖』缺口**」。
   真机实测表明该归因**不成立**：Compose `Dialog` 默认 `DialogProperties.securePolicy =
   SecureFlagPolicy.Inherit`，以**调用方（宿主）窗口**的 flag 位为准
   （`AndroidDialog.android.kt:251/263` 取宿主 `LocalView` 作 `composeView`，`:675` 求值，
   实现见 `AndroidPopup.android.kt:1110-1116`），宿主窗口不带该 flag 时执行
   `setFlags(FLAG_SECURE.inv(), FLAG_SECURE)` 即**清除**本包装刚施加的那一次
   ⇒ **无论宿主窗口带不带该 flag，对话框窗口的 `FLAG_SECURE` 都不是由本包装的 `addFlags` 保住的**。
   该缺口**已如实登记为 `ISSUE-P2-246`**（含两选一整改方向），并用设备用例第 2 条**锁定留证**；
   **本批按上级约束「既有 `FLAG_SECURE` 施加/撤销语义一行不得改」未做整改**，亦未擅自扩大批次范围。
