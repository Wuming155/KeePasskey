## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：`database/.../session/DatabaseSession.kt:290` 每次 `save()` 调
  `HistoryManager.pruneGroupHistoryByAge(rootGroup, maintenanceHistoryDays)`（默认 365 ⇒ 恒执行）；
  `history/HistoryManager.kt:130` 的实现为 `group.entries.map{…}` + `group.subgroups.map{…}` 递归，
  即便整库无一条历史快照，也仍为**每个分组各分配两个新 List**（现有 `changed` 判定只避免了 `group.copy`）。
- **整改方向**：先做 O(1) 的「本库是否存在历史快照」闸门（解析 / 变更时维护计数或惰性标记），无历史直接跳过；
  递归改为「仅当子树确有变化时才新建列表」。
- **验收标准**：无历史库的保存路径不再产生分组规模的新列表（结构断言或分配计数）；
  有历史库的修剪结果与现状等价；保留期边界用例全绿。
- **核实时间点与方式**：2026-09-17 读 `DatabaseSession.kt` 保存路径与 `HistoryManager.kt:130` 实际内容核实。
- **风险提示**：历史修剪涉及**用户数据删除**，闸门必须是「保守不修剪」方向（宁可多跑一次）。

---

## 2. 本批实现：递归改为**惰性分配**

`pruneGroupHistoryByAge` 的每层改为「`forEachIndexed` + 首次发现变化时才 `toMutableList()`」，
两个列表各自独立惰性：

```kotlin
        var newEntries: MutableList<KdbxEntry>? = null
        group.entries.forEachIndexed { index, entry ->
            val pruned = pruneHistoryByAge(entry, maintenanceHistoryDays, now)
            if (pruned !== entry) {
                val list = newEntries ?: group.entries.toMutableList().also { newEntries = it }
                list[index] = pruned
            }
        }
        // subgroups 同理
        if (newEntries == null && newSubgroups == null) return group
```

**语义逐字未变**：
- 递归范围与判据不变（`maintenanceHistoryDays <= 0` 直接返回；`pruneHistoryByAge` 的
  「无历史 / 无超期即返回同一实例」不变）；
- 「无变化 ⇒ 返回同一根实例」不变（`newEntries == null && newSubgroups == null` ⇒ `return group`）；
- 「有变化 ⇒ `group.copy`」不变，且**未受影响的子树与条目仍按同一实例进入新树**（路径复制契约）；
- 调用方 `DatabaseSession.save`（`:290-296`）依赖的 `prunedRoot !== db.rootGroup` 判定**未动**，
  连同其 `ISSUE-P2-06` 的定点擦除分支一并保持原样。

⇒ 消除的是「无人修剪时仍为每个分组各分配两个列表」这一项；**递归本身仍是 O(节点数) 的免分配扫描**。

## 3. 刻意不做：O(1)「本库是否存在历史快照」闸门（AC 的第一半）

AC 建议「解析 / 变更时维护一个计数或惰性标记，无历史即直接跳过」。**本批不做**，理由：

1. **维护点必须覆盖全部写路径**：条目历史由 `recordHistorySnapshot` 写入，但整棵树还会经
   解析（打开库）、编辑保存、冲突合并、远端接管、模板导入等多条路径被**整体替换**
   ⇒ 计数需要在**每一处**同步维护；**漏一处就会让修剪静默失效**（在保存路径上「跳过」= 该库的历史
   永不按保留期清理，属**用户数据不删**方向的静默行为变更，也是本条目「风险提示」要求保守的方向）。
2. **收益已被本批吃掉的等价部分**：不加闸门的代价原本是「每个分组两个列表」；
   惰性分配已把这部分降到**零分配**，剩下的是 O(节点数) 次「读 `maintenanceHistoryDays` +
   逐条目判 `history.isEmpty()`」的免分配扫描——与维护计数的复杂度同阶。
3. **风险不对称**：为了省一次 O(节点数) 的免分配扫描而引入一条「计数维护错即静默不修剪」的路径，
   不符合本条「保守不修剪」的取向。

⇒ 若日后确实需要 O(1) 闸门，正确形态是**把计数收进 `KdbxDatabase`/会话树的唯一变更入口**
（并要求所有整树替换路径显式重建该标记），或干脆在**解析期**给每个分组维护「子树是否含历史」的
布尔缓存——两者都属独立的结构性改动，本批不涉及。

## 4. 本批新增用例（1 例）

`database/src/test/.../HistoryManagerTest.kt` 增 **`修剪只复制受影响路径且未受影响子树按同一实例复用`**：
构造「含超期快照的子树 + 未超期条目的兄弟子树」，断言
① 根实例更换；② 受影响子树被复制；③ **未受影响的兄弟子树按同一实例复用**（`assertSame`）；
④ **未超期条目按同一实例复用**；⑤ 受影响条目的超期快照被清除。

**该用例是「只消除分配」这一改动的唯一可观测守护面**：实现里若把「未变化」分支也复制一次，
③④ 即失败（而「修剪结果正确」本身不会失败）。

**行为面依据（既有，全绿）**：`HistoryManagerTest` 原有 10 例（记录与回滚 / 数量上限 / 体积上限 /
零数量上限 / 默认容量 / 保留期修剪 / 保留期为零不修剪 / **无超期快照返回同一实例** /
**整树递归且无变化免拷贝**）+ `DatabaseSession` 相关保存路径用例。

## 5. 边界如实声明（不得外推）

1. **无任何性能实测、也无分配计数**：AC 要求的「无历史库的保存路径不再产生分组规模的新列表」
   是**运行期计数**，本批以**路径复制契约用例**（`assertSame`）替代——它证明「未变化的子树/条目
   未被复制」，但**不直接证明**列表分配次数为 0（例如「复制了但内容相同」的实现仍可能通过）。
   ⇒ **不得**读作「已用运行期计数证明零分配」。
2. **递归的 O(节点数) 扫描仍在**（免分配，但仍是每次保存的固定成本）；
   即「每次保存都会遍历整棵树做一次保留期判定」这一事实**未变**，本批只消除其分配。
3. **`maintenanceHistoryDays <= 0` 的短路在函数入口**，与批次的默认 365 天配合 ⇒
   默认配置下**每次保存都会走完整递归**（本批未改变触发条件）。
4. **未跑设备侧 / `assembleRelease`**；保存路径的正确性依据是既有 `DatabaseSession` 用例
   + 本批新增的路径复制契约，**未做真机端到端保存验证**。
