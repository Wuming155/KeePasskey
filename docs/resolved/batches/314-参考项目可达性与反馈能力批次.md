## 2. 逐项结论与整改内容（AC①：逐项给「补齐 / 维持并登记」结论）

### ① 外部打开入口（补齐）

- **前提复核**：三份 Manifest 检索确认唯一 VIEW 出现在 `<queries>`（包可见性声明，非入口）；`MainActivity` 受 `ExportedComponentHygieneTest` 约束不得消费任何外部 intent 数据 ⇒ 入口须另立 Activity。
- **整改**：新增 `OpenVaultEntryActivity`（exported、无权限可用，白名单登记并附理由）——承接 `ACTION_VIEW` / `ACTION_SEND`（`EXTRA_STREAM`；文字 extras 一律忽略），仅接受 content/file scheme 且显示名以 `.kdbx` 结尾的对象，非法输入拒绝回落主界面；校验通过后调用**既有** `importExternalDatabase`（与页内 SAF 选择器同一链路：含持久化授权尝试与脱敏告警、自动置为活动库）并拉起 `MainActivity` 落在解锁页。
- **Manifest**：`application/octet-stream` + `application/x-kdbx` 两 MIME × VIEW/SEND 两 filter（不登记更宽通配，最小可达性）；`excludeFromRecents`。
- **安全面（如实声明）**：本页是有意新增的受控数据消费入口；库内容可用性仍由主密码 / 密钥文件解密 fail-closed 裁决，非 KDBX 对象登记后无法解锁。

### ③ 同步请求级重试与退避（补齐）

- **前提复核**：`PeriodicSyncWorker` 全路径 `Result.success()`、`SyncHttpClientFactory` 只设超时，瞬时 5xx/429 只能等下个周期——属实。
- **整改**：新增 `sync/network/TransientHttpRetry.kt`——指数退避（500ms × 2^attempt，封顶 4s，默认 3 次尝试，参数经 `SyncNetworkOptions` 新增两字段注入）。
- **重试安全边界（AC③：与 §272 乐观锁语义合流）**：
  - **读请求**（PROPFIND / GET / HEAD / DELETE）恒可重试；
  - **写请求仅在实际携带服务器预条件时重试**（WebDAV `If-Match` / MOVE `If` tagged list、S3 `If-None-Match: *` / `If-Match`——S3 条件写无从构造时本就 fail-closed 拒发）——预条件在服务端**逐次重验**，即「重试前重新校验基线」的协议级实现：基线被推进即 412 → `ConflictError`，**绝不静默覆盖**；
  - **无条件 PUT 禁止重试**：WebDAV `upload()` 在 `expectedEtag` 空白或弱形态（If-Match 被 §272 AC② 剥除）时恒单次；临时文件 PUT 亦单次；
  - `SyncException`（鉴权 / 协议 / 冲突 / 不存在）不是 `IOException`，一律不重试；`CancellationException` 原样上抛。
- **落点**：`WebDavSyncProvider` 统一经新增 `executeTransientRetryable(retryable, requestFactory)` 出口（每尝试重建请求），`uploadAtomic` 的 MOVE 循环内部包裹（外层既有重试语义不变）；`S3SyncProvider` 在 `executeSignedRequest` 统一缝隙包裹（S3 全部写均带预条件）。
- **限界（如实声明）**：下载体为流式契约（§P3-206），重试只覆盖「取得响应 + 状态判定」边界——一旦开始向 sink 写入，传输中断不再重试（部分写入后重放会污染缓存文件，交由调用方既有清理面处置），此时仍等下个周期。

### ④ 后台同步失败可见性（补齐）

- **前提复核**：`syncEvents`（SharedFlow）全仓 0 订阅者属实（`recentSyncEvents` 是另一条 StateFlow，属 §274 装配段守卫探针面）；两条通知通道与 AC 所述一致。
- **整改**：
  - `SyncCoordinator` 新增 `lastOutcome: StateFlow<SyncOutcome?>`（`syncNow` / `confirmVaultBindingTakeover` 收尾处写入）——周期结果不再只经返回值交付；
  - 新增 `SyncFailureNotifier`（`MainApplication.onCreate` 冷启动点启动）：**订阅 `lastOutcome`**（`Error` → 发/更新静默失败通知，其余结果 → 撤下）+ **订阅 `syncEvents`**（AC② 要求的真实订阅者；`CouldntSaveToRemote` / `CouldntOpenFromRemote` 引擎级失败 → 同通知）。前台手动同步的失败同样可见；
  - 新增通知通道 `SYNC_FAILURE`（`IMPORTANCE_LOW` + `setSilent`）：**可静音**（通道级低重要度）、**可关**（用户在系统通知设置中关闭该通道即关闭面，应用内不另设重复开关——避免双口径假开关，对齐 PD 假开关处置先例）；通知文案固定通用（不含库文件名等用户数据）、`VISIBILITY_SECRET`、点击回主界面；
  - `PeriodicSyncWorker` 的 `Result.success()`（防退避风暴的既有裁决）**保持不变**：结果已写入 `lastOutcome`，失败不再被吞（AC② 口径：不再吞掉的是**可观测性**，不是退出码）。
- **决策单测**：`SyncFailureSignal`（六事件仅两类失败触发；仅 `Error` 结果触发，冲突 / 绑定不符 / 离线各有既有承接面）。

### ⑤ OTP 直填（补齐 · `AutofillValue` 正规通道）

- **前提复核**：`AutofillPostFillTotpActions` 只复制 / 通知、`AutofillFieldScanner` 把 `otp` 列入非凭据排除词（定向检索 0 命中）属实；设置页文案自我限定为「复制 / 通知」、未宣称填充——属未实现对齐项。
- **整改**：
  - **扫描器**：新增 OTP 通道（`ScanResult.otpId`）——hint 白名单（W3C `one-time-code`、平台 `smsOtpCode` / `2faAppOtpCode`，归一化精确匹配）HIGH + htmlName/idEntry 含 `otp`（覆盖 totp/hotp 拼接形态）MEDIUM；**不用 label**（「验证码」一词同时用于短信与图形验证码，误填风险高）；判定先于搜索 / 非凭据排除（`otp` 同在排除词表内）；不可见 OTP 框不参与；OTP 框不再可能被误判为账号 / 密码框。
  - **值通道**：全链 `AutofillValue.forText(code)` 正规通道——已解锁候选数据集（`buildCandidateDataset`）、认证回传载荷（`buildAuthenticationResultDataset` 新增 `otpId`/`otpCode` 参数）、确认页 / 选择器交付时刻**现算** TOTP（值新鲜度以交付为准）。
  - **链路转发**：OTP 框 id 经解锁引导数据集 → `AutofillUnlockActivity`（透传，不参与路由判据）→ 选择器 / 确认页两分支全链不断。
  - **既有路径不移除（AC④）**：复制 / 通知二次动作（`AutofillPostFillTotpActions`）原样保留，与本通道正交。
  - **裁决：仅 TOTP 直填**——HOTP 当前码不推进计数器（推进是「取下一个码」的显式动作），直填会给出与服务端不同步的旧值，故 `isHotp` 条目不参与（复制 / 通知不受影响）。
  - 未设应用内开关：OTP 直填仅在**表单显式声明** OTP 框时发生（页面作者主动标注），无隐性扩散面。

### ⑥ CM 通道「上次使用置顶」（补齐 · 数据源自建）

- **前提复核**：`CredentialResponseAssembler` 未用 `AutofillLastFilledStore`、`onCompleteGetCredentialRequest` 全仓 0 命中——属实（AC⑤ 要求先取框架侧权威依据）。
- **框架依据（已取得）**：androidx.credentials **1.6.0 源码**（Gradle 缓存 sources jar 逐条核对）——`PasswordCredentialEntry.Builder` / `PublicKeyCredentialEntry.Builder` 均有 `setLastUsedTime(Instant?)`，且经 Slice 序列化下发系统 UI（`fromSlice` / `toSlice` 双向）；`@property lastUsedTime` KDoc 原文「the last used time the credential underlying this entry was used by the user」。系统 UI 是否据其排序属系统侧行为，本仓保证**如实提供**数据源。
- **整改**：
  - 数据源**不是**框架回调（不可得），而是本应用自己的 CM 交付落地页——新增 `CredentialLastUsedStore`：`PasswordFillActivity.deliverPassword`（回传 `RESULT_OK` 前）与 `PasskeyAssertionActivity.signAndReturn`（断言回传前）各记一次 `entryId → epochMillis`（仅 UUID + 时刻戳，非敏感；跨锁定会话留存——与「上次填充」的会话级置顶语义刻意不同，故不实现 `SessionLockObserver`）；
  - 候选组装侧（`CredentialResponseAssembler`）对密码与公钥两类候选按记录设置 `setLastUsedTime`，其余组装判定零改动。

## 5. 过程缺陷（如实留痕）

1. **`| tail` 管道掩蔽退出码重演**（§311 同款坑）：一次全量验证 `BUILD FAILED` 却以退出码 0 通过管道——改用 `> log 2>&1; echo EXIT=$?` 保留退出码后复跑。
2. **规模闸门回压**：本批向 `KeePasskeyAutofillService.kt` 加线后达 509 行，`count_line_tiers` tier1 红——按 §305 先例把 `TargetFields` + `resolveTargetFields` 原样拆至新文件 `AutofillTargetFieldResolver.kt`（该文件回落 461 行，tier1=0）。
3. **三例旧契约用例按纪律「修改不删除」**：`S3SyncProviderTest` F6 用例与两处 scenario 场景 3 原锁「5xx 立即单次失败」，与新重试行为冲突——改为锁新契约（瞬时 5xx 重试耗尽后仍收敛类型化 `ProtocolError` / fail-closed 绝无 PUT；401 与无条件 PUT 单次语义原样保留）。
4. **重试耗尽的异常类型收敛**：初版耗尽后以 `RetryableStatus`（IOException 家族）上浮，会让既有「按 SyncException 家族归类用户文案」的调用方失焦——补收口：耗尽仍为可重试状态码时映射 `ProtocolError`。
