## 1. 排查过程（证据链）

1. **登记出口穷举**：`saveKnownDatabases` 全仓仅 `VaultLifecycleCoordinator` 两个调用点
   （`importExternalDatabase` 写入 / `removeDatabase` 摘除），不存在 URL 形态的云端条目登记。
2. **结构性重复定位**：云端导入把库文件物理落地 `filesDir` 并登记
   `KnownDatabaseEntry`（`id` = 绝对路径）；`buildDatabaseList` 的目录扫描又为同一文件产出
   内部条目（`id` = 文件名）。末尾 `(knownExternal + internalEntries).distinctBy { it.id }`
   因两侧 id 形态不同**挡不住**这对重复 ⇒ 两张卡恒现。这是结构性重复，与用户操作路径无关。
3. **参考口径**：keepass2android 云端库 = 单一 IOConnection 条目，本地副本是不可见缓存
   （`docs/references/keepass2android-架构分析.md` §CachingFileStorage：`OfflineCache/` 下以
   `SHA256(ioc.Path)` 为键，列表与「最近文件」只见远端条目）。本应用对齐「一个库一张卡」。

## 2. 整改

- **`VaultDatabaseCatalog.buildDatabaseList` 按规范化本地路径去重**：登记表条目
  （非 `content://` 路径取 `File.canonicalPath`，`runCatching` 容错）构成集合，
  目录扫描侧先剔除已登记路径再发卡——登记表条目对同一本地文件**恒优先**，
  云端卡片成为该库唯一展示，本地副本只是它的落地实现细节；
- **纯结构性抽函数**：单条登记 → 投影的映射抽为 `knownEntryToInfo`
  （`buildDatabaseList` 因新增去重逻辑涨至 102 行触发 `long_functions` 红线，抽出后回绿，
  行为零变更）；
- 未登记的沙盒 `.kdbx` 照常列出（无回归）；`content://` 外部库路径不参与该去重，不受影响。

## 3. 验收

- AC① 同一物理文件只允许一张卡：沙盒内 `cloud_vault.kdbx` 经 `importExternalDatabase`
  以云端标签登记后 `getDatabases` 恰 1 条且 `isRemote=true`、自动置活动
  （`RealVaultRepositoryTest` 新增 1 例）；
- AC② 无回归：去重只作用于已登记路径——同目录未登记的 `plain_local.kdbx` 照常列出
  （新增 1 例，云端 + 本地恰 2 条）；
- AC③ 活动态 / 移除 / 解锁对合并后单卡行为不变：登记条目 `name` = 文件名，
  活动态三重匹配（id / path / name）与 `VaultRemovalKind` 判定均未触碰；
- AC④ 全量 `test --rerun-tasks --max-workers=1` 绿 `xml=493 tests=3197 failures=0 errors=0
  skipped=13`（§370 基线 493/3195 ⇒ +2 例）+ 门禁 8/8（§5）。

## 4. 过程留痕

- 首轮整改后 `long_functions` 红（`buildDatabaseList` 102 行 ≥ 100）——把既有映射段抽为
  `knownEntryToInfo` 回绿，同批如实留痕；
- 范围裁定：本批只消除**结构性**重复（同一物理文件）。若用户以不同展示名对同一远端文件
  重复云端打开，`CloudVaultImporter` 的同名冲突 fail-closed 守卫（ISSUE-P2-399）本就拒绝落地，
  不产生第二份副本；基于库内容（根分组 UUID）的跨文件身份合并属更大工程，未纳入本批。
