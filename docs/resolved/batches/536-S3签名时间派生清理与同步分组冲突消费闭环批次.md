### ISSUE-P3-656 S3目录XML修改时间被按HTTP日期解析而丢失

- 核实：2026-10-16（Asia/Shanghai），当前源码与协议消费链；静态确认；置信度：高。
- 问题：ListObjects XML的LastModified使用ISO时间，但S3DirectoryList调用只认RFC1123的S3HttpDateCodec，解析失败回0。仓内fixture已含2026-10-06T00:00:00.000Z却未断言时间字段。
- 影响与触发：S3目录列表元数据中的真实修改时间丢失，依赖该接口的展示或排序不能得到正确值；不外推为同步ETag失效。 复现与反证详见方案。
- 位置：`sync/src/main/java/com/keepasskey/sync/s3/S3DirectoryList.kt:135`；`sync/src/main/java/com/keepasskey/sync/s3/S3HttpDateCodec.kt:15`。
- 已实现（2026-10-17）：新增 `S3XmlTimeCodec`（ISO-8601：`Instant` / `OffsetDateTime` / 无时区按 UTC），`S3DirectoryList` 的 `<LastModified>` 改走该解析器；HTTP 响应头仍走 `S3HttpDateCodec`（RFC 1123，协议归口不混用）。JVM：fixture 时间断言为 `1791244800000`、无小数秒与带 `+08:00` 偏移同值、非法值降级 0、HTTP 解析器不认 ISO，共 7 例 0 失败。
- 尚未完成：真实 S3 服务端到端（目录列表回读时间）。模型层 `0 = 未知` 与合法 1970 同值属既有字段边界，本项不改变该契约。
- [独立整改方案](../../architecture/问题整改方案/P3/ISSUE-P3-656/整改方案.md)：目标、模块、步骤、失败处理、验收与回退。

### ISSUE-P3-657 S3签名密钥级联派生在中途异常时遗漏清理

- 核实：2026-10-16（Asia/Shanghai），当前源码与协议消费链；静态确认异常出口缺口；置信度：高（控制流）；异常触发概率低。
- 问题：kDate/kRegion/kService在第一个try内依次生成，该finally只清kSecret；清前三级的第二个try只有全部派生完成后才进入。中间HMAC抛异常时，已分配派生数组跳过清理。
- 影响与触发：异常路径的可擦派生秘密等待GC；正常路径已有清理，真实HMAC异常/资源错误才触发。无外部未授权读取内存证据，不是签名密钥直接外传。 复现与反证详见方案。
- 位置：`sync/src/main/java/com/keepasskey/sync/s3/S3RequestSigner.kt:174`。
- 已实现（2026-10-17）：三个中间派生量改为可空持有、逐级「先赋值再使用」，并登记在**同一最外层 finally** 的擦除面上；派生链抽为可注入 HMAC 的 `deriveSigningKeyChain`（正常与故障共用同一清理路径）。JVM：`S3SigningKeyDerivationTest` 5 例（第 2/3/4 步受控异常 + 成功路径不擦最终 key + 空 kSecret），0 失败。
- 尚未完成：真实服务签名端到端（既有签名场景用例保持全绿，不代替该项）。
- [独立整改方案](../../architecture/问题整改方案/P3/ISSUE-P3-657/整改方案.md)：目标、模块、步骤、失败处理、验收与回退。

### ISSUE-P2-660 同步（云端）路径的**分组**同字段双侧异值仍为字段级 LWW，不进冲突面

- 核实：2026-10-16（Asia/Shanghai），`ISSUE-P1-631` 第三轮审计；静态确认；置信度：高。
- 问题：合并器现已产出 `MergeResult.groupConflicts`，**漂移面**已据此阻断并裁决；但 `sync` 路径的消费方只读 `MergeResult.conflicts`（条目级），**不读** `groupConflicts` ⇒ 云端同步时分组同字段双侧异值仍由 `KdbxGroupFieldMerge` 按 LWW 静默定案，用户无任何提示。
- 影响与触发：两端各自修改同一分组的组名 / 备注 / 图标 / 父组 / 组级自定义数据且取值不同时，一端修改被静默丢弃。触发序列：设备 A 改分组名 → 设备 B 改同一分组名为另一值 → 任一端同步。
- 定级：P2（与漂移面同源同型；漂移面已证成可行，同步面照同一条路即可）。范围说明见限界 §46（第三轮已把「分组级差异不产生冲突清单」的旧边界改写为「漂移面已修 / 同步面仍 LWW」）。
- 位置：`sync/src/main/java/com/keepasskey/sync/merge/KdbxGroupFieldMerge.kt`；`sync/.../KdbxMerger.kt`（`MergeResult.groupConflicts`）；`app/src/main/java/com/keepasskey/app/sync/SyncConflictController.kt`（决策清单与 `groupConflictFlow`）；`app/.../sync/SyncGroupConflictResolution.kt`（与漂移面共用的落树原语）。
- 已实现（2026-10-17）：`SyncConflictDecision` 携带 `entries` / `groups` / `meta`，`handleConflictMerge` 任一非空即进待决（不再只判条目）；新增 `groupConflictFlow` 独立通道，列表页冲突入口与冲突页同时消费。`resolveConflicts` 增加 `groupResolutions`，落树复用与漂移面**同一实现** `applyGroupConflictChoices`（只重裁差异字段；「双方保留」由 `KdbxGroupDuplicator` 复制整棵子树并重生成 UUID）；冲突页新增分组卡片（整组取本地 / 整组取云端 / 双方保留），副本后缀为「云端冲突副本」（与漂移面「磁盘冲突副本」区分）。JVM：`SyncGroupConflictResolutionTest` 7 例 0 失败（含多组同批裁决、目标缺失与根组 fail-closed）。
- 关闭条件：同步消费方读 `groupConflicts` 并复用 `KdbxGroupConflictResolver` / `KdbxGroupDuplicator`，且限界 §46 收窄为「已对齐」。

## 536.1 修复（逐条）

### 536.1.1 P3-656：XML 时间按 ISO-8601 解析

- 新增 `sync/.../s3/S3XmlTimeCodec.kt`：`Instant.parse` → `OffsetDateTime` → 无时区按 UTC 三级回退；
  空串 / 非法值返回 `null`（调用方保留模型既有「0 = 未知」，不伪造时间、不中断整页列举）。
- `S3DirectoryList.parseListObjects` 的 `<LastModified>` 改走该 codec；HTTP 响应头仍走
  `S3HttpDateCodec`（RFC 1123）——**协议归口不混用**，这是缺陷根因。
- 用例 `S3DirectoryListMetadataTest`（7 例）：fixture `2026-10-06T00:00:00.000Z` → `1791244800000`、
  无小数秒与 `+08:00` 偏移同值、非法值降级 0、缺元素不导致整页失败、HTTP 解析器不认 ISO。

### 536.1.2 P3-657：级联派生中途异常的清理

- `S3RequestSigner.getSignatureKey` 的三级中间量（kDate / kRegion / kService）改为**可空持有**，
  逐级「先赋值再使用」，统一登记在**同一最外层 finally** 的擦除面上；最终 signingKey 所有权移交调用方。
- 派生链抽为可注入 HMAC 的 `deriveSigningKeyChain`：正常与中途异常走同一条清理路径，
  不再依赖「四级全部成功」这一控制流前提（原缺陷的成因）。
- 用例 `S3SigningKeyDerivationTest`（5 例）：第 2 / 3 / 4 步受控异常时，此前已分配的数组全部被填零；
  成功路径擦中间量且**不擦**最终 key；空 kSecret + 立即失败不崩溃。

### 536.1.3 P2-660：同步路径消费分组冲突

关闭条件逐条核对（原文）：①「同步消费方读 `groupConflicts`」→ `SyncConflictDecision(entries, groups, meta)`
由 `decisionConflictsOf` 产出，`handleConflictMerge` 以 `!decisionConflicts.isEmpty` 判待决；
②「复用 `KdbxGroupConflictResolver` / `KdbxGroupDuplicator`」→ 落树原语 `applyGroupConflictChoices`
（`app/.../sync/SyncGroupConflictResolution.kt`）内部即这两者，且**漂移面与同步面共用同一实现**；
③「限界 §46 收窄为『已对齐』」→ 已改写并注明验证层级。

- 新增 `SyncConflictController.groupConflictFlow`（与条目、库级 Meta 各自独立通道）；
  `VaultListViewModel.hasPendingConflictFlow` 与冲突页同时消费三条通道。
- `SyncCoordinator.resolveConflicts(groupResolutions = …)` → `SyncConflictResolution`：以合并产物为底版
  只重裁差异字段；「双方保留」复制整棵子树（UUID 全重生成），云端副本后缀「云端冲突副本」。
- 冲突页：新增分组卡片（整组取本地 / 整组取云端 / 双方保留）+ 警示卡分类计数；
  卡片与差异映射分别下沉 `ConflictResolutionCards.kt` / `ConflictResolutionDiffMapper.kt`（行数门禁）。
- 防御（实施中发现）：`applyResolvedGroupsToTree` 对**根组**替换会丢掉整棵子树 ⇒ 共用函数里
  显式 `fail-closed` 返回 null（`KdbxGroupMerger` 本已排除 rootId，此处只作结构异常兜底）。
- 用例 `SyncGroupConflictResolutionTest`（7 例）：只重裁差异字段、双方保留复制子树并全部换新 UUID、
  目标缺失 / 根组 fail-closed、无冲突返回原实例、多组同批裁决。

## 536.9 RustFS TLS S3-compatible 服务验签与 API 36 AVD 复验（2026-10-18；不结案）

- 本机测试服务使用 RustFS 1.0.1，绑定 `127.0.0.1:9000`，启用 TLS，关闭 Console，仅以虚构凭据和临时数据运行；`adb reverse` 只映射给隔离 `emulator-5554`。服务版本包校验值：`SHA-256 624259622524255D0000131E095F37A11299FD76926AABFD8F831A9DBE6A39F7`。
- 服务端签名负向对照由独立 boto3 SigV4 客户端执行：正确 secret 的 bucket HEAD 为 HTTP 200；错误 secret 为 HTTP 403 / `SignatureDoesNotMatch`。因此与 Moto 不同，RustFS 可作为会验签的独立实现证据。
- 为 sync instrumentation 测试 APK 增加本地证书资源与**仅 `localhost` / `127.0.0.1` domain-config**信任锚；base-config 仍只信系统 CA，生产配置未变。证书与现有 app debug 测试证书 SHA-256 一致。
- AVD：`:sync:connectedDebugAndroidTest`，`S3IndependentServiceDeviceTest`，非空 XML `tests=2 failures=0 errors=0 skipped=0`。生产 `S3SyncProvider` 完成 TLS SigV4 HEAD、`notes&archive/` 两页 ListObjectsV2、对象键 / 页游标 / ISO `<LastModified>` 解析；第二例验证错误 secret 被生产客户端映射为 `AuthenticationError(403)`。
- AVD：`:app:connectedDebugAndroidTest`，`SyncMetaConflictDeviceTest`，非空 XML `tests=2 failures=0 errors=0 skipped=0`。内存用例与 RustFS HTTPS 生产路径均通过；实际冲突 UI 点选云端库名、本地颜色后上传，重新从服务下载并解析，验证描述 / 默认用户名 / customData 自动合入及身份字段保留。
- 范围边界：RustFS 是独立 S3-compatible 服务，不是 AWS S3 / MinIO；因此 P3-656 / P3-657 仍保留其目标服务验收边界，P2-659 的 AWS / MinIO 多端回读与独立 KeePassXC 读取同一导出 KDBX 仍未完成。此节仅登记补充证据，不代表三项结案。
