## §1 条目原文（自 `ACTIVE_ISSUES.md` 整条剪切，逐字保留）

### ISSUE-P3-339：仿冒域能否唤醒通行密钥（本地 RP 实验室）——**浏览器半环搁置**

- **状态（2026-09-27 用户指示）**：**暂时搁置**。剩余部分需要外部资源（自有域名 + ACME DNS-01，或企业策略放行自建 CA，或换自带信任库的浏览器并相应重述判据），用户裁「先精简描述、暂不做」。
- **威胁模型（勿在后续复用时被悄悄替换）**：**真实攻击者只有公开 DNS 与公网可信证书，没有任何设备篡改能力**。⇒ 一切结论必须出自**攻击者可达的**配置。
- **已闭环半环（代码层，2026-09-27）**：见批次与历史条目；`CredentialProviderLookalikeMatchTest` 已锁定跨域泄露收紧与 `extractDomain` 去尾点。
- **红线（不变）**：**在破不通真实信任锚之前，本条目下不得出现任何「仿冒域不会唤醒」的结论**。今天能声称的只有「本应用对给定 rpId 的接受/拒绝判定」，**不是**「Chrome 不唤醒仿冒站」。

## §2 闭环理由（用户 2026-10-03 裁决：直接闭环）

条目原于 2026-09-27 搁置，因剩余「浏览器半环」需外部域名 + ACME DNS-01（或企业 CA / 自带信任库浏览器）才能实验验证 Chrome 是否会把仿冒站的 passkey 唤起。用户 2026-10-03 裁决：在现实威胁模型下该攻击条件不可达，直接闭环。

**修正后的归档理由（落档口径，避免踩红线）**：用户直觉「现实中遇不到攻击条件」应精确表述为——

1. **攻击设置本身可达、攻击成功不可达**：攻击者注册仿冒域名并以 Let's Encrypt DNS-01（仅需 DNS 控制权）取得公网可信证书，这套「目标攻击条件」在现实里随手可得，**并非不可达**。真正不可达的是「攻击成功」，而它在既定威胁模型下被平台边界挡住。
2. **代码层半环已锁（2026-09-27）**：`CredentialProviderLookalikeMatchTest` 已锁定跨域泄露收紧与 `extractDomain` 去尾点；本仓作为 Credential Provider 一侧对给定 rpId 的接受 / 拒绝判定是确定的。
3. **浏览器半环在既定威胁模型下无意义**：仿冒域（如 `examp1e.com`）是**不同的 registrable domain = 不同的 rpId**；平台 WebAuthn 的 rpId 匹配边界（请求方 origin 的注册域后缀约束）使凭据根本不会被唤起给仿冒站。攻击者绕过该边界的唯一途径是设备篡改 / 破信任锚——正是威胁模型明确排除的能力。
4. **这恰好停在红线所指的边界上**：红线禁止「在没有破信任锚之前声称『仿冒域不会唤醒』」。本闭环不是声称「测过 Chrome 内部行为」，而是依据通行密钥赖以为安全基础的 **rpId 匹配不变量**——该不变量在既定威胁模型下即构成消解，无需再搭域名 + 证书做实验。

## §3 红线注记（保留为残余边界，不删测试）

- 红线那句「不得出现『仿冒域不会唤醒』的结论」转为**残余边界注记**：本闭环是「既定威胁模型下由平台边界消解」的推理结论，**不是**「本仓实测 Chrome 不唤醒」；措辞上不得写成已实测。
- 不删除 `CredentialProviderLookalikeMatchTest`（测试资产纪律①：用例与对拍向量只允许新增或修改，不得因「暂时用不上」删除）。
