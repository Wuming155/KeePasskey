> 「通行密钥和账号密码均无法保存到软件中。在登录界面输入账号密码或使用通行密钥后，系统会弹出『保存』或『继续』按钮，但点击『保存』后，信息无法成功保存到软件内。」

复现工具（本批新增，**设备侧真实客户端**，非产品代码）：
`app/src/androidTest/java/com/keepasskey/app/passkey/CredentialSaveClientActivity.java`
—— 声明在**测试 APK 自己的包名**（`com.keepasskey.test`）与进程内，语义等价于第三方应用调用
`CredentialManager.createCredential`，从而让「系统 → provider」这半段可被真机驱动。
配套回归用例 `CredentialSaveChainDeviceTest`。

## 2. 定位过程（逐步收敛，含被证伪的分支）

### 2.1 先排除的两项

1. **设备上装的是过期构建**：设备 APK 构建于 2026-09-20 14:18，而 §229 的保存链路修复提交
   （`b4670f2`）在 **15:25**。重装 HEAD 后，`PasswordSaveActivity` 手工拉起不再报
   「缺少待保存的密码数据」，说明该现象属旧构建，**不是本次根因**。
2. **provider 声明面**：清单 `<service>` 的 action / `BIND_CREDENTIAL_PROVIDER_SERVICE` /
   `credential_provider_service.xml` 的两条 `<capability>` 均正确；`dumpsys package` 的
   Resolver Table 亦正确登记（`com.keepasskey/.app.passkey.KeePasskeyCredentialProviderService`）。

### 2.2 决定性现象

用真实客户端发起保存请求，系统侧日志：

```
I/CredentialManager: starting executeCreateCredential with callingPackage: com.keepasskey.test
W/CmSaveClientTest: CM-SAVE-STATUS:onError type=android.credentials.CreateCredentialException.TYPE_NO_CREATE_OPTIONS
```

**系统根本没有向本应用发起创建请求** —— 用户点「保存 / 继续」自然毫无反应。

### 2.3 归因实验（四条，逐条列出结论）

| # | 操作 | 结果 | 结论 |
|:--:|:--|:--|:--|
| E1 | 仅把 `Settings.Secure.credential_service` 设为真实组件 | 请求**被路由**，provider 应答 `SAVE_ENTRIES_RECEIVED` | 该键是路由的**必要条件** |
| E2 | 仅把 `credential_service_primary` 设回错误值（保留 E1） | 仍**被路由** | `credential_service_primary` **不影响路由** |
| E3 | 全新安装后仅写 `credential_service_primary`（不写 `credential_service`） | `TYPE_NO_CREATE_OPTIONS` | **仅 primary 不足以放行** |
| E4 | 冷启动（`force-stop` 后）触发保存 | `Remote provider response timed out`，我们的回调**晚于超时**才打印 | 存在**第二处**独立失效：冷启动超系统应答预算 |

### 2.4 根因（三条，互相独立）

**R1（环境 / 系统侧，主因）**：本机 `Settings.Secure.credential_service`（**已启用凭据提供者清单**）为
**空**，而 `credential_service_primary` 指向 `com.keepasskey.app/...` —— 该包**根本不存在**
（应用实际包名是 `com.keepasskey`，`com.keepasskey.app` 只是其**命名空间**）。
→ 系统判定「没有任何已启用的 provider」，创建请求在框架层即被丢弃。
**这不是应用代码缺陷，但用户完全不可见、也无从自行排解**（见 §4 的 `ISSUE-P2-239`）。

**R2（应用侧，已整改）**：冷启动时延逼近系统预算。同机多次实测：

| 轮次 | `Start proc` → `onBeginCreateCredentialRequest` 首行 | 系统判定 |
|:--|:--|:--|
| 修前 #1 | 3.05 s | **超时丢弃**（预算约 3.0 s） |
| 修前 #2 | 2.49 s | 勉强通过 |
| 修后 | 2.38 s | 通过 |

**R3（应用侧，已整改）**：`res/drawable/ic_launcher.xml` 为**非法资源**：

```xml
<bitmap android:src="@mipmap/ic_launcher" />
```

`<bitmap>` 的 `src` 必须是位图，而 `@mipmap/ic_launcher` 在 API 26+ 解析为 **adaptive-icon XML**
（`mipmap-anydpi-v26/ic_launcher.xml`）⇒ 该 drawable **在任何消费方都无法加载**。真机日志：

```
E/Icon: Unable to load resource 0x7f08006a from pkg=com.keepasskey
E/Icon: Caused by: org.xmlpull.v1.XmlPullParserException:
        Binary XML file line #3: <bitmap> requires a valid 'src' attribute
E/Icon:  at com.android.credentialmanager.CreateFlowUtils$Companion
            .toSortedCreationOptionInfoList(DataConverter.kt:492)
        at ...toEnabledProviderList(DataConverter.kt:244)
```

系统凭据面板每构建一次创建项列表就抛一次异常；自动填充内联建议的
`AutofillInlinePresentationFactory.setStartIcon` 同理。该缺陷由 `a1c1dce`
（「替换应用启动图标为自适应图标方案」）引入：上一版 `drawable/ic_launcher.xml` 是**矢量图**，
重构时被替换为上述非法 `<bitmap>` 垫片。

## 3. 整改与会话内验证

### 3.1 应用侧代码

1. **R3**：`app/src/main/res/drawable/ic_launcher.xml` 由非法 `<bitmap>` 改为 **`<layer-list>`**
   （`@mipmap/ic_launcher_background` + `@mipmap/ic_launcher_foreground` 两个 PNG 层）——
   保持 `R.drawable.ic_launcher` 这一既有资源名与 5 处调用点不变（最小爆炸半径），
   KDoc 写明「两个 item 必须指向位图资源」的反向约束。
2. **R2**：`MainApplication.onCreate` 中原**同步**执行的
   `periodicSyncScheduler.applySavedSchedule()` 移入新增的 `coldStartBackgroundScope`
   （`Dispatchers.IO`）。该调用会拉起 WorkManager（其自身要打开数据库与 executor），是冷启动
   主线程上最重的一段，而「按偏好恢复周期调度」**没有任何冷启动时序依赖**。
   其余冷启动工作（易失缓存清理、剪贴板对账、自动锁定注册、完整性探测、通知通道）
   **一律保留同步位置**——它们或承担安全对账语义，或必须早于任何会话入口。

### 3.2 环境侧处置（R1，本机已执行并验证）

```bash
adb shell settings put secure credential_service \
  com.keepasskey/com.keepasskey.app.passkey.KeePasskeyCredentialProviderService
```

或在系统设置「凭据提供程序 → 首选服务」中重新选择 KeePasskey（**本机 ROM 的该入口只写
`credential_service_primary`，不写 `credential_service`，实测单独操作不生效**）。

### 3.3 真机验证证据

处置 R1 + 整改 R2/R3 后，用 `CredentialSaveClientActivity` 走完整链路：

```
I/KeePasskeyCredProvider: onBeginCreateCredentialRequest 收到系统创建请求: BeginCreatePasswordCredentialRequest
I/CredentialManager: Remote provider responded with a valid response: ComponentInfo{com.keepasskey/...}
I/CredentialManager: Provider status changed: SAVE_ENTRIES_RECEIVED
I/CredentialManager: For ui, provider data size: 1
```

系统保存面板呈现「KeePasskey / 要保存密码以便登录『com.keepasskey.test』吗？/ cm-probe-user / 继续」；
**点击「继续」**后：

```
I/ActivityTaskManager: START u0 {cmp=com.keepasskey/.app.passkey.PasswordSaveActivity (has extras)}
    ... (BAL_ALLOW_VISIBLE_WINDOW [realCaller])
ResumedActivity: com.keepasskey/.app.passkey.PasswordSaveActivity
```

即**系统面板 → 本应用保存落地页**这一段在真机上闭环成立；R3 修复后
`grep -cE "E/Icon|bitmap requires|XmlPullParser"` 由「每次非零」降为 **0**。

## 5. 如实声明（边界与未验证项）

1. **R1 未定位到「谁写坏了该键」**：本机 `credential_service` 为空、`credential_service_primary`
   带命名空间前缀包名的成因**未证实**。已尝试的两条实验（切换系统选择器强制写入、
   改 `settingsActivity` 前缀后重装再切换）**均未观察到任何写入**，故**不得**断言
   「是本应用命名空间与 `applicationId` 不一致导致系统推导错包名」——该假设**未成立亦未证伪**，
   本次不作结论。用户侧处置与验证只到「纠正该键后链路即通」为止。
2. **未点击系统面板的「保存 / 继续」以外的分支**：未验证「选择其它 provider」路径。
3. **通行密钥注册方向未做同口径真机复算**：密码与通行密钥共用同一
   `onBeginCreateCredentialRequest` 入口与同一 `CreateEntry` 装配（含同一图标资源），
   故 R2 / R3 对两者同源成立；但**未**在真机上单独跑一遍 passkey 注册链路，
   且非浏览器调用方的 `PasskeyRegistrationGate` DAL 门控属既有设计（限界表已登记），
   本批**未**改动。
4. **冷启动时延未做统计意义上的测量**：本批为**单机、多轮次**的点测（2.38 / 2.49 / 3.05 s），
   **不得**据此宣称任何百分比收益。
5. **新设备侧用例在本机恒为 skipped**：判据是「15 s 内观察到 provider 收到创建请求」，
   而本机在**全新安装后**系统不会自动登记本应用（E3），故该用例在当前 ROM 上
   只有先手工执行 §3.2 才会转绿——这是**环境前提**而非用例缺陷，KDoc 已写明。
6. **本批未触** `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 与任一原生绑定；
   新增 `app/src/androidTest/**` 组件（`CredentialSaveClientActivity` + 用例）已按
   「测试资产纪律」②在真机实跑（见 §3.4）。
