### 72.2 设备侧实测（arm64 真机：Redmi 4X / LineageOS / Android 17 / **API 37** / `arm64-v8a`，经 ADB）

**正对照（启用无障碍服务后）**——把系统自带的
`com.android.systemui.accessibility.accessibilitymenu/.AccessibilityMenuService` 经
`settings put secure enabled_accessibility_services` 置为启用（`dumpsys accessibility` 确认
`Enabled services:{{…AccessibilityMenuService}}`），随后创建真实密码库并冷启动进入**锁定态主密码页**，
`uiautomator dump` 实测：

| 观测项 | 结果 |
|---|---|
| 主密码页是否出现无障碍提示 | **出现**：`已启用无障碍服务` + `本机已启用无障碍服务（非本应用）。该类服务可读取你在屏幕上输入的内容，包括主密码。…` |
| 主密码输入框语义 | `password="true"`（该页 `EditText` 共 1 个，计数 = 1） |
| 其余敏感通道是否被降级 | **未被降级**：生物快速解锁 / 自动填充策略未变（等级仍 `TRUSTED`，与策略单测一致） |

**负对照（关闭无障碍服务后）**——`enabled_accessibility_services=null`、`accessibility_enabled=0`，
同样冷启动进入主密码页：

| 观测项 | 结果 |
|---|---|
| 无障碍提示 | **不出现**（字符串命中数 = 0） |
| 主密码输入框语义 | 仍为 `password="true"`（计数 = 1） |

⇒ 提示确由**该信号**驱动（非恒显示），且口令语义在两种状态下均成立。

### 72.3 前提更正（AC② 的机械实施被实测否决，如实留痕）

条目原文称「`SecurePasswordField` **未**设置 Compose 的 `Modifier.semantics { password() }`」
⇒ 语义缺失。**实测与源码双向核实后确认该前提不成立**：

1. **源码实证**：`androidx.compose.foundation` 1.12.1
   `CoreTextField.kt:438` 为 `val isPassword = visualTransformation is PasswordVisualTransformation`，
   而 `CoreTextFieldSemanticsModifier.kt:165` 为 `if (isPassword) this.password()` ——
   框架**会自动**从视觉变换推导该语义；
2. **设备实证**：改动**前**，遮蔽态与「显示密码」态的无障碍树均报 `password="true"`（见 72.2 表）。

**本批的处置**：不做「修复一个已观测的缺失」，而是把该不变量**从框架隐式推导改为组件显式声明**
（`SecurePasswordField` 内的 `semantics { password() }`），理由是消除「语义随显隐切换而消失」的
隐式耦合；**并如实声明**：改动**前后设备侧无障碍树逐项一致**，
故本次**不是**功能修复，而是不变量归属的显式化 + 回归锁定（`AccessibilityNoticeWiringTest`）。
若后续 Compose 调整推导规则，本仓行为不再随之漂移。

### 72.4 设计裁决：无障碍信号**只提示、不降级**

启用无障碍是**合法且必要**的可及性配置（视障用户依赖），若因此禁用生物快速解锁 / 自动填充，
等于以安全之名剥夺可及性，且会命中**系统预装 TalkBack** 的正常用户。故：

- 本信号**不参与** [RuntimeRiskLevel] 判定，**不**置位 `disableBiometricQuickUnlock` / `disableAutofill`；
- 只置位 `requireAccessibilityNotice`，在**主密码输入页**（最需要知情的位置）如实告知
  「无障碍服务可读取输入内容」；
- 与 `requireRiskNotice`（由完整性等级驱动、伴随通道降级）**正交**，两者各有唯一消费点。

**已知边界（如实声明）**：首次扫描完成前快照为 `UNDETERMINED`，此时
`requireAccessibilityNotice` 为 false（不提示）——属「未判定不冒充已判定」的既有语义，
首次扫描完成后自然纠正；本项**不**参与 fail-closed 门控，故该窗口不构成放行风险。

### 72.6 过程缺陷（如实留痕）

1. **`uiautomator dump` 报的是应用窗口坐标，按钮可能被软键盘遮挡**：向导弹出 IME 后，
   「创建」按钮在 dump 中仍报 `y≈942`，但该位置实际已被键盘覆盖——注入点击**落在键盘上**，
   把字符灌进了密码框，表现为「两次输入的密码不一致」。
   ⇒ 纪律：**注入点击前先收键盘**（`input keyevent KEYCODE_BACK`）并**重新 dump 取坐标**；
   凡「点击后状态反而变坏」，先怀疑点击落在了别处。
2. **界面未就绪时的点击会被静默吞掉**：同一坐标首次点击无任何效果（dump 前后一致），
   重试即成功。⇒ 纪律：关键导航后必须**轮询确认界面已切换**（重新 dump 比对文本），
   不得以「点击已发送」推断「导航已完成」；本次实测中该形态一度被误判为「应用卡死」，
   经 `KEYCODE_BACK` 验证输入通路正常后才定位为时序问题。
3. **AC 的机械实施需先复核**：本条 AC② 若照做，会得到一个「改了但设备侧毫无变化」的改动，
   却记成「修复了语义缺失」的假结论。⇒ 纪律：**先测量再改**；改动前后**逐项可比**的观测记录
   是区分「修复」与「显式化」的唯一依据。
