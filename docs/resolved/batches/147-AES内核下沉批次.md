# §147 · AES 内核下沉批次（`ISSUE-P3-155` 追问立项 · **取向为可靠性/可维护性，非性能**）

> **批次主题**：AES-256-CBC 由平台 JCE 统一到 Rust 内核（`NativeAes` + `aes_cbc.rs`），
> 使 KDBX 三种外层 cipher（AES / ChaCha20 / Twofish）与 Passkey 签名共用同一份原生实现与同一套
> 对拍纪律；PKCS#7 与流式语义仍由 Kotlin 侧单一实现承担。
> **立项依据**：用户 2026-09-17 就 `ISSUE-P3-155` 的追问——「AES-256-CBC 加密使用 Rust 虽然没有什么
> 收益，但建议还是统一吧，避免跨语言边界的复杂度上升」，并裁定「AES 全下沉 Rust」。
> **判据变更（2026-09-18，用户）**：`minSdk 36` 面向**现代设备**，主库体积普遍 **<5 MB** ⇒ 额外
> 10~20 ms 属**无感区**；本项按**可靠性 / 稳定性 / 可维护性**保留，**性能不作为理由**。
> **清单条目**：本批**无待办条目可剪切**（系用户追问立项）。反向新增一条**开放评估项**
> `ISSUE-P3-187`（JNI 零拷贝评估），见 [`ACTIVE_ISSUES.md`](../../ACTIVE_ISSUES.md) P3。
> **实测数据**：`docs/records/真机吞吐实测记录_2026-09-17.md` **§8**（双机 10 轮 + 内核分解）。

---

## 1. 供应链闸门

- **零新增依赖**：复用 §143 已入库的 `aes = { version = "0.9.3", default-features = false, features = ["zeroize"] }`
  （RustCrypto 官方；`zeroize` 使密钥调度随对象析构归零，与 `twofish` / `chacha20` 同纪律）。
- `cargo deny check` 沿用既有结论（`wildcards = "deny"` 零违例 / 无重复密码学实现）。

## 2. 实现

- **Rust**：`src/aes_cbc.rs` 纯函数内核（**与 `twofish_cbc.rs` 同构，仅内核不同**）——
  `cbc_encrypt` / `cbc_decrypt`（AES-256，`KEY_LEN = 32` fail-closed 拒绝其余长度）、
  `ecb_encrypt_block`（仅供 KAT）；链值用单个 `Zeroizing<[u8;16]>` 承载，
  **逐块零分配**（直接写入预分配输出的对应切片，不经 `Vec::push`、不逐块构造 `Zeroizing`）；
  `iv` 为**输入输出参数**（演进为末组密文 = 下一段链值，流式分段的直接依据）。
- **JNI**：`Java_com_keepasskey_crypto_cipher_NativeAes_cbcEncryptBlocks` / `_cbcDecryptBlocks`
  （与 `twofish_cbc_jni` 同构：失败归一 `null`、`catch_unwind` 不越界 unwind、入参与中间缓冲全程 `Zeroizing`）。
- **Kotlin**：
  [NativeAes.kt](../../../crypto/src/main/java/com/keepasskey/crypto/cipher/NativeAes.kt) 探活 =
  **NIST CBC-AES256 官方向量加/解双向自测**（自包含、不依赖 JCE）；
  [AesCipherEngine.kt](../../../crypto/src/main/java/com/keepasskey/crypto/cipher/AesCipherEngine.kt)
  改**原生优先 + JCE 兜底**双路径（对齐 `TwofishCipherEngine` 先例），整型与流式四条路径同构接线。
- **契约修复（本批的实质缺陷修复，见 §5）**：
  [CbcStreams.kt](../../../crypto/src/main/java/com/keepasskey/crypto/cipher/CbcStreams.kt) 的
  `CbcEncryptingOutputStream` / `CbcDecryptingInputStream` 新增 `ownedSecrets: List<ByteArray>`
  构造参数——原生变换**惰性**读取密钥，故流必须**自持副本并在 `close()` 时确定性擦除**；
  `TwofishCipherEngine` / `ChaCha20CipherEngine` 同步接线（三者契约一致）。
- **CI**：`native-gate` 期望符号集 **8 → 10**（新增 NativeAes 两条），沿用 §146 的**逐名集合核对**
  （缺失/多余分别打印，`set -euo pipefail` 下无命中即失败 = fail-closed）。

## 4. 判据数据（双机 10 轮；**倍数与绝对差并报**）

| 对比（10 MiB） | Redmi 4X（A53） | M332BF（现代） |
|---|---|---|
| 生产·整块加密 | 250.9 ms | **48.1 ms** |
| 生产·流式加密 | 291.2 ms | **54.9 ms** |
| 生产·整块解密 | 259.6 ms | **34.3 ms** |
| 生产·流式解密 | 315.3 ms | **49.1 ms** |
| 对照·JCE 最优（`doFinal` / 64 KiB 分块） | 34.4 / 101.3 / 93.5 ms | **9.2 / 19.5 / 14.3 ms** |
| **额外开销（绝对差）** | **+166~222 ms** | **+20~39 ms** |
| 倍数 | 2.8~7.3× | 2.4~5.2× |

**成本构成（现代机 48.1 ms）**：算法本体 **13.3 ms（28%）** + JNI 边界 **21.2 ms（44%）** +
PKCS#7 整缓冲垫片与明文擦除 **13.6 ms（28%）**；对照 JCE `doFinal` **全程 9.2 ms**。

**两条可证伪的否定结论**（本批最重要的产出）：
1. **AES 加密下沉无法靠优化翻盘**：现代机 Rust **内核本体**（13.3 ms）已慢于 JCE **全程**
   （9.2 ms）；CBC 加密为串行依赖、逐块调用吃不到 ILP，追不上 OpenSSL 汇编。
2. **差距全在边界而非算法**：现代机上 AES-CBC **解密内核仅 2.0 ms、生产路径 34.3 ms（17× 放大）**；
   同形对照 ChaCha20（内核 16.3 / 单次 JNI 24.7 ms）证明该边界成本**与算法无关**。

**必须并排看的反例**：同批下沉的 ChaCha20 在两个时代都是**绝对巨益**
（现代 244.2 → 24.7 ms，省 **219.5 ms**；A53 3712.5 → 85 ms，省 3627 ms）。

## 5. 过程缺陷与如实声明

- **① 密钥所有权契约漏洞（真实回归，仅真机暴露）**：原生路径接线后宿主单测全绿，但真机
  `KdbxCompatibilityAndSecurityTest#testLegacyCipherKeyFallbackAndAutoMigration` 红
  （`IOException: CBC 解密流：PKCS#7 填充非法`）。根因：`KdbxFile` / `KdbxCipherKeyResolver`
  依据「`SecretKeySpec` 构造时已克隆密钥」的 **JCE 假设**，在建流后**立即擦除**调用方密钥数组；
  而原生变换**惰性**读取密钥（每块一次 JNI）⇒ 以全零密钥解密。修复：`ownedSecrets` 契约
  （流自持副本并负责擦除）+ 新增 `StreamKeyOwnershipContractTest`（三引擎契约用例，**时序为
  「先建流 → 立即擦除调用方数组 → 再读写」**，首版时序写错曾漏检）。**该漏洞已登记为限界 §17 的
  残余风险面**：新增任何原生流式变换必须一并核对该契约。
- **② 包装类方案被推翻**：初版为流式路径新增包装类，导致 `AesCbcChunkedDecryptStreamTest`
  因返回类型变更而红 → 改为在 `CbcStreams` 内原生支持 `ownedSecrets`（更小的侵入面）。
- **③ 方法论缺陷（用户纠正）**：曾据**两次**测量即判定「AES 下沉倒退」并回退实现；用户指出
  「**不要一次测试就得出结论**，连续测试 10 次」。遂撤销回退、恢复实现，并改为
  **连续 10 轮 + 双机 + 倍数与绝对差并报**。结论方向未变（确为倒退，且 10 轮离散度 ≤4.8%、
  无一轮接近 JCE），但**证据强度与表述口径**是本批修正的实质内容。
  同一回退动作还**连带删除了两个 AES 测试文件**（`AesNativeParityTest` / `AesNativeDeviceTest`），
  而它们当时**尚未入库**（`git log --diff-filter=D` 查无此文件）⇒ 只能按范式重写。用户据此立规
  **「测试资产不删除」**：`AGENTS.md` §5 + `.codebuddy/rules/engineering-rules.md` §「测试资产纪律」
  ——测试用例 / 对拍向量只增不删；确需删除须「无被测对象 + 理由登记 + 与生产代码同次提交」三条件齐备。
  **本批的实质教训**：**回退实现时不得顺手删测试**，且新增测试必须与生产代码同一次提交入库。
- **④ §7.3 基线口径漏洞（本批更正）**：§7.3 的「加密 1.58× / 解密 4.49×」加速比，其对照物是
  **当时的 JCE 流式生产路径**（100.2 / 55.5 MB/s），**不是 JCE 最优路径**。以 JCE `doFinal`
  （318.7 MB/s）为基线，**内核级 Rust 加密即已慢 2.0×**——「内核层占优」在加密侧不成立。
  已更正于实测记录 §8.3。
- **⑤ 探针改动后编译失败一次**：`DeviceThroughputProbeTest` 新增分解用例时使用了 `NativeAes`
  但未补 import（`unresolved reference`，编译期抓获，未入库）。
- **如实声明（不得据本批做以下推断）**：
  1. **不得**以「下沉更快」描述 AES 本项（内核层与现代设备均不占优，见 §4）；
  2. **不得**把「无感」外推到「老设备 × 大库」（A53 级 5 MB 库约 +83~111 ms）；
  3. **不得**用单一机型的内核数字外推全部机型——同一份 Rust 代码的 CBC 解密在 A53 为 249 MB/s、
     现代机为 **5072 MB/s**（现代 OoO 核可把硬件 AES 延迟流水化），差异 **20×**；
  4. **不得**把 ChaCha20 的收益口径外推到 AES（方向相反）。
- **刻意不做**：**JNI 零拷贝**（`GetPrimitiveArrayCritical` / `DirectByteBuffer`）。理由：与桥的
  「`catch_unwind` + `Zeroizing` 全路径擦除」范式冲突，属独立高风险面改动；已按用户裁定
  **单独立项** `ISSUE-P3-187` 先评估契约与收益，再决定是否实施。
