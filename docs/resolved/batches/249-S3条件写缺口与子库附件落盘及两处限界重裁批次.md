## 2. 整改内容（逐条对 AC）

### ① `ISSUE-P2-244`：S3 覆盖前 HEAD 无 ETag ⇒ fail-closed

- **AC①（分支改为 fail-closed）**：`S3SyncProvider.upload` 的 `metaResult.isSuccess ->` 分支改为
  先取 `val probedEtag = metaResult.getOrThrow().etag`，`if (probedEtag.isBlank())` 即抛
  `SyncException.ProtocolError(200, "S3 覆盖前 HEAD 未返回 ETag，无法构造条件写，已拒绝无条件 PUT")`。
  **选型理由写进该函数的 KDoc**（行内只留一行指针注释）：网络是通的、服务端也返回了 200，坏的是
  「响应不含条件写所需的版本信息」这一**协议层可用性**，与 `testConnection` / `getMetadata`
  对协议级不可用响应的既有归类一致；若选 `NetworkError` 会把「服务端应答正常但内容不合用」
  谎报为网络故障。（注：既有用例 `测试首传前置探测网络失败时快速失败不发无条件PUT` 断言的
  `ProtocolError` 来自 HEAD 返回 500 时的 `getMetadata` 映射，与本分支同族而不同源。）
- **AC① 附带**：`precheckEtag` **绝不**被置为空白值；同时**移除**发送侧的
  `precheckEtag?.takeIf { it.isNotBlank() }?.let { … }`——那正是「条件值为空 ⇒ 不发条件头」的后门。
  改为无条件写 `If-Match`（`cleanEtag(precheckEtag.orEmpty())`）：正常路径值必非空，
  最坏情形退化为 `If-Match: ""`，由服务端 412 拒绝并映射为 `ConflictError`，仍是 fail-closed。
- **AC②（宿主用例锁定）**：新增 `测试覆盖前 HEAD 未返回 ETag 时快速失败不发无条件 PUT`——
  `MockResponse().setResponseCode(200)`（**不带** `ETag` 头）、`upload(..., expectedEtag = null)`
  ⇒ 断言 `result.isFailure`、异常为 `SyncException.ProtocolError`、`server.takeRequest().method == "HEAD"`、
  `server.requestCount == 1`（**绝无 PUT 发出**）。体例照抄既有 `测试首传前置探测网络失败时快速失败不发无条件PUT`。
- **AC③（不得放宽既有语义）**：`412` / `401` / `403` 映射与 `signV4` 头构造一行未改。
- **KDoc 更正**：第 2 点原写「HEAD 预检仅作快速失败优化，正确性**完全**由 PUT 的 If-Match 服务端校验保证」
  ⇒ 改为「HEAD 预检作快速失败优化，正确性另由 PUT 的 If-Match 服务端校验保证」并补
  「HEAD 成功但未返回 ETag 时**不再退化**为无条件 PUT，而是 fail-closed（`ISSUE-P2-244`，2026-09-21）」；
  第 3 点保留「兼容存储忽略 `If-Match` ⇒ 退化为 HEAD 预检 + 无条件 PUT」的既有降级说明，
  并补一句区分：「服务端忽略既有条件头」与「本地根本构不出条件」是两回事，不可混同。

### ② `ISSUE-P2-243`：子库只读会话传入 `BinaryStore`

**定案理由（照录，不改）**：`ISSUE-P2-67` 立的不变量是「新增装载调用方**不得忘记**传 `BinaryStore`」，
子库这条路径是唯一残余反例；限界 §1.1 的取向是「超阈值附件落盘、池中只留引用」优于整树明文驻留。
子库与根库同属应用私有缓存、共享同一清理面（会话锁定 / 冷启动），故**不新增**独立的清理语义。

- `ChildReadOnlySession` 构造器新增 `private val binaryStore: BinaryStore`（`com.keepasskey.core.security.BinaryStore`），
  `loadProjection` 改为 `KdbxFile.load(input, password, keyFile, binaryStore)`。
- `ChildDatabaseSessionManager` 注入该 store 并传入两处生产构造点（`:186` / `:330`）。
- **偏离说明（唯一一处）**：规格要求注入的形参类型写 `com.keepasskey.app.data.binary.FileBinaryStore`，
  但（a）DI 图中无 `BinaryStore` 接口绑定而宿主单测需要注入内存替身、（b）管理器依赖抽象更符合本仓
  「依赖倒置」取向，故管理器形参取抽象 `BinaryStore`，并在 `ChildDatabaseModule` 新增
  `@Binds @Singleton bindBinaryStore(fileBinaryStore: FileBinaryStore): BinaryStore` 别名绑定。
  **生产行为与规格完全一致**：绑定到的是**同一个 `@Singleton FileBinaryStore` 实例**（与根库
  `DatabaseSession` 共用），**未新建任何 store 实例**、**未新增任何清理路径**（该单例本就既是
  `SessionLockObserver` 又在 `MainApplication.onCreate` 冷启动清理）。
- KDoc（「敏感数据边界」段）补一行：落盘沿用应用级 `FileBinaryStore`，清理由**会话锁定 / 关闭**与**冷启动**
  统一收口（同限界 §1.1 / §1.2 口径），并注明**投影仍不携带附件字段**。
- **AC（端到端宿主用例，未走退路）**：`ChildReadOnlySessionTest` 新增
  `含大附件的子库装载时附件经 BinaryStore 真实落盘`——现场用生产写入管线 `KdbxFile.save`
  造含 **1 200 000 B**（> `BinaryStorePolicy.DEFAULT_THRESHOLD_BYTES` = 1 MiB）附件的子库语料
  （新增 fixture `ChildDatabaseFixtures.kdbxBytesWithLargeAttachment`），以 `RecordingBinaryStore`
  替身记录 `storeFromStream` / `store` 调用，断言 `spillCalls > 0`、落盘内容非空且字节数等于附件声明尺寸。
  **判别力**：见 §3 第 2 条（改回三参调用即红）。

### ④ `ISSUE-P3-250`：限界 §18 / §20 重新裁定（只改措辞，不动这两处代码）

1. **§18 收窄授权**（非放宽判据）：把「成员**全部**为一行委托」改为如实描述——成员**绝大多数**为一行委托，
   另有 5 处薄编排（现跑行数：`verifyConnectionThenSync` 15 / `refreshPrivilegedBrowsers` 6 /
   `setPrivilegedBrowserEnabled` 7 / `enableBreachCheckAndScan` 4 / `clearBlockedFields` 已收为 1）
   与 `init{}` 编排；明确该文件**已不符合**原前提 ⇒ 授权降级为「**不得新增**含实现体的成员」，
   5 处列为**待消化清单**（消化方式：下沉到已持有 `CoroutineScope` 的控制器）；
   并写明**不得**据此放宽 `.codebuddy/rules/engineering-rules.md` 的巨型类阈值、**不得**外推到其它文件。
2. **§20 按现值重新裁定**：`processFillRequest` 现 **65 行**（含 4 段早退守卫，其中黑名单命中走命名谓词
   `rejectsDatasetDelivery`），**重新裁定为接受为限界**——理由：4 段早退均为 fail-closed 出口、
   唯一行为级证据在设备侧 `AutofillAuthChainDeviceTest`（本批无设备），改写控制流的风险仍大于收益；
   **解除条件更新为**：① 设备侧该用例常态化跑绿、可即时证伪改写时，允许把早退改写为**可观测的拒绝计数**
   并在**同一次改动**里降到 ≤50 行；② 该函数因新需求继续增长时**不得再顺延**，必须当批达标。
3. **代码侧唯一极小改动**：`SettingsViewModel.clearBlockedFields()` 由 `{ preferences.clearBlockedFields() }`
   收为**单语句委托** `fun clearBlockedFields() { preferences.clearBlockedFields() }`。
   **如实留痕**：规格给的表达式体形式 `fun clearBlockedFields() = preferences.clearBlockedFields()` **不被 Kotlin 接受**——
   控制器返回 `Int`，而回调类型是 `() -> Unit`（`AutofillSettingsScreen.kt:67`），实测编译错误
   `Return type mismatch: expected 'Unit', actual 'Int'`；`fun clearBlockedFields(): Unit = …` 同样被拒。
   故取等价的**单语句块体**（同为一行委托，返回类型保持 `Unit`）。其余 4 处**不动**：下沉需要新增
   scope / `StateFlow` 归属，属独立改动，且 §18 已把授权收窄为「不得新增含实现体成员」。
