## 1. 原条目（自 `ACTIVE_ISSUES.md` 原样收录）

- **背景**：① `sync/.../engine/SyncEngine.kt:108-114` 一次接受流程对**同一份远端字节**算 3~4 遍全库 SHA-256
  （`SyncRollbackGuard.inspect` 的 `:119`、`SyncCache.writeCache` 的 `:117`、`recordAccepted` 的 `:135`，
  ETag 缺失路径再加一次）；② `sync/.../engine/SyncEngineSupport.kt:60-61` 的 `advanceBaseAndPersist`
  恒执行 `writeCache` + `writeBaseContent`，两者各自「写 tmp → flush → `fd.sync()` → rename」
  ⇒ 每次基线前移 `2×N` 字节顺序写 + 2 次 fsync，且 `cacheDir/sync` 对每个远端路径常驻**两份完整密文**。
- **整改方向**：① 让摘要只算一次并作参数贯穿（`isReplay(path, bytes, digest)` / `recordAccepted(path, bytes, digest)`），
  或由 `writeCache` 回传摘要；② `writeBaseContent` 前先比对目标长度 + 摘要，内容一致则整段跳过。
- **验收标准**：接受流程内 SHA-256 计算次数降为 1（调用计数断言）；基线与缓存内容相同时不再产生第二次写盘与 fsync；
  防回滚裁决与缓存/基线内容回归全绿（`§90` 的两例不变量不得放宽）。
- **核实时间点与方式**：2026-09-17 读 `SyncEngine.kt:100-120`、`SyncRollbackGuard.kt:118-143`、`SyncCache.kt:105-123` 核实。
- **风险提示**：摘要链路与防回滚强耦合，**不得**为省一次哈希而改变 MAC / 摘要载荷格式（见 `已知工程限界.md` §5）。

## 2. 本批实现（① 摘要一次化）

1. **`SyncRollbackGuard` 增加「摘要已知」重载**：
   `inspect(remotePath, contentDigest: String)` 与 `recordAccepted(remotePath, contentDigest: String)`；
   原字节重载保留并改为**委托**（`= inspect(remotePath, SyncCache.sha256Hex(content))`），
   故既有调用点行为逐字不变、无需改动。**载荷格式与 MAC 计算未动**（风险提示的那条硬约束）。
2. **`SyncCache.writeCache` 增加 `precomputedDigest: String? = null`**（默认 null ⇒ 现算，既有调用点不变）；
   调用方已算出摘要时直接复用，跳过 `sha256Hex(data)`。
3. **`SyncEngine` 的接受路径改为「一次算出、三处共用」**：
   ```kotlin
   val remoteDigest = SyncCache.sha256Hex(remoteBytes)
   if (isReplay(remotePath, remoteDigest)) { return …RollbackRejected(remoteBytes, meta.etag) }
   val hash = cache.writeCache(remotePath, remoteBytes, precomputedDigest = remoteDigest)
   advanceBaseAndPersist(cache, remotePath, meta.etag, hash, remoteBytes)
   recordAccepted(remotePath, remoteDigest)
   ```
   `isReplay` / `recordAccepted`（`SyncEngine` 内的私有包装）同样拆为「字节」与「摘要」两个重载，
   字节版委托摘要版 ⇒ 其余调用点不变。

**实际收敛范围（须精确理解）**：本批只收敛**接受远端内容这一条路径**上对**同一份 `remoteBytes`** 的
3 次全库 SHA-256 ⇒ **1 次**。其余四个重放裁决点（`已知工程限界.md` §5 记的 5 处裁决点中的另外 4 处）
仍走字节重载、各自现算一次摘要——它们并不共享同一份字节（分别处理本地字节 / 上传前内容等），
本批**未**、也**不应**据此声称「全链路摘要只算一次」。ETag 缺失路径上
`RemoteConsistencyProbe.isRemoteUnchanged()` 的摘要属另一份下载字节，同样不在本批范围。

## 3. 刻意不做（② 基线前移的「重复写盘」跳过）——登记 `已知工程限界.md` §11

原条目 ② 建议「`writeBaseContent` 前先比对目标长度 + 摘要，内容一致则整段跳过」。**复核后判定不做**：

1. **逐字节判定不是免费的**：判定须先读全量内容并哈希（长度预检只能排除尺寸不同者），
   而 `advanceBaseAndPersist` **总在内容刚变更之后**被调用（上传成功 / 接受远端内容）
   ⇒ 在最常见路径上「先读一遍再决定不写」**净增**工作量，只在「内容恰好未变」时才有收益。
2. **廉价推断不安全**：以「`basecache` 存在且 `<hash>.baseversion` 已等于该摘要」为判据看似零成本，
   但本函数的写序是 `updateBase` → `writeBaseContent`，两步之间崩溃会留下
   「baseversion 已前移、basecache 仍旧字节」⇒ 跳过写盘会把**陈旧基准永久固化**，
   而基准快照存在的意义正是避免「base 被本地修改版污染 ⇒ 三方合并退化为远端全胜」。

两处写盘**各自是必要的**（缓存快照会被工作副本覆盖，基准快照必须与之一致性解耦），
故「两份完整内容并存」不是缺陷而是设计。结论、理由与解除条件登记于 `已知工程限界.md` **§11**，
并在 `advanceBaseAndPersist` 的 KDoc 就地留痕（未来优化者会先看那里）。

## 5. 边界如实声明（不得外推）

1. **无任何性能实测**：「3 次 → 1 次」是**源码级调用点计数**（同一函数体内的三处共用一份摘要），
   非运行期计数；**不得**宣称百分比收益，也不得据此推断真机同步耗时。
2. **收敛范围仅限接受远端内容这一条路径**（见 §2 末）——其余 4 处重放裁决点与 ETag 缺失探测路径
   **仍各自现算摘要**。
3. **`precomputedDigest` 是**可选参数**，调用方传入错误摘要会静默改变裁决结果**（不校验）。
   本批只有一处生产调用方，它在同一函数体内由同一份字节算出 ⇒ 无漂移风险；
   若日后新增调用方，须保证「摘要与字节同源」。
4. **本批未做任何「调用计数断言」**：`SyncCache.sha256Hex` 是伴生对象上的静态方法，
   宿主侧无法在不改实现的前提下计数；故等价性靠**行为用例**（8 + 1 例）与**源码级阅读**承担，
   **不得**读作「已用运行期计数证明」。
5. **基线写盘行为零变化**（本批 ② 判不做）⇒ 「每次基线前移 2×N 字节写 + 2 次 fsync」与
   「每个远端路径常驻两份完整密文」**依旧成立**。
