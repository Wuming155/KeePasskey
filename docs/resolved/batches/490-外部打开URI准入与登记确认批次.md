## 490.1 原始条目（原样收录）

### `ISSUE-P3-575`：`OpenVaultEntryActivity` 对 URI 无 scheme 校验并静默覆写活动库指针，任意普通 App 零前置可达

**背景与影响**：`OpenVaultEntryActivity` exported 且无权限保护（`AndroidManifest.xml:142-157`）；
`extractKdbxUri`（`OpenVaultEntryActivity.kt:78-84`）对 URI **全程无 scheme 校验**（比
`ExportedComponentHygieneTest.kt:151-164` 白名单理由声称的「仅接受 content/file scheme」更宽），唯一校验为显示名
`endsWith(".kdbx")`（`:59`）。任意普通 App（无需任何权限）显式 Intent 携带 `file://` 任意路径（无需 FLAG_GRANT）
→ `:67` `importExternalDatabase` → `VaultLifecycleCoordinator.kt:301-312` **无确认覆写活动库指针** `saveActiveDbId`
→ 解锁分支 `:66-80` `File(path)` 按**相对路径**解析 → `:102-108` 文件不存在即走「以主密码新建空库」分支。
影响为库列表污染 / 顶掉活动库 / UI 混淆，无凭据外泄路径；**本轮 14 条发现中唯一普通恶意 App 零前置可达**。

**验收标准**：
1. `extractKdbxUri` 增加 scheme 白名单（`content://` 与受 FLAG_GRANT 的 URI；`file://` 收敛到可预期来源或拒绝）；
2. 登记新库 / 覆写活动库指针前引入用户确认，不以外部输入静默改状态；
3. 纯 JVM 单测锁定（攻击者 scheme / 相对路径 / 伪装后缀用例），并同步修正
   `ExportedComponentHygieneTest` 白名单理由表述（与代码不符）。

**核实时间点 + 核实方式**：2026-10-11，数据流安全审查工作流（同 P2-573 口径），基准提交 `cd223701`；六要素详情见
[`security/数据流安全审查_2026-10-11.md`](../../security/数据流安全审查_2026-10-11.md) 发现 3（verdict=confirmed，
复核确认三处攻击面 safeNote 与代码不符，以复核为准）。来源攻击面：其他攻击面兜底。

## 490.2 前提复核（2026-10-11 直读）

- **条目成立（快照一致）**：`OpenVaultEntryActivity.kt` 中 `extractKdbxUri` 仍为
  `ACTION_VIEW → intent.data` / `ACTION_SEND → EXTRA_STREAM` 两分支**全程无 scheme 校验**；
  `resolveDisplayName` 对 `scheme == "file"` 取 `File(path).name`；唯一准入判据是
  `!displayName.endsWith(".kdbx")`；命中后 `:67` 直接 `importExternalDatabase(displayName, uri.toString())`。
  `VaultLifecycleCoordinator.importExternalDatabase`（`:281-321`）末端 `catalog.saveActiveDbId(entry.id)`
  **无任何确认**覆写活动库指针；`unlockActiveDatabase`（`:54-122`）在 `activeDb.path` 非 `content://` 时
  直接 `File(activeDb.path)` ——条目所引行号与语义逐条吻合（`:301-312` 即登记 + 置活动块；`:66-80` 即
  content 分支与 `File(...)` 起手）。
- **safeNote 矛盾属实（三处声称 vs 代码）**：`ExportedComponentHygieneTest.kt:151-164` 白名单理由、
  `OpenVaultEntryActivity.kt:30-32` 类 KDoc、`AndroidManifest.xml:136-141` 组件注释**三处**均写
  「只接受 content/file scheme」——而代码连 scheme 都不看。按 AC③ 三处一并修正（见 §490.3 ④）。
- **`file://` 收敛面核实**：本仓无任何自有 FileProvider / `grantUriPermission`（安全审查「其他兜底面」已证），
  且 Android 7+ 调用方在跨进程传 `file://` 时自身会触发 `FileUriExposedException`（`StrictMode`），
  现代文件管理器 / 云盘一律改用 `content://`（DocumentsProvider）——故 `file://` 到达本入口的形态
  在正常来源里**近乎不存在**，其主导来源即攻击者手写 Intent。这支持 AC① 取「一律拒绝」而非「收敛白名单」。
- **既有用例面（影响判据）**：`RealVaultRepositoryTest` 以宿主临时目录的**绝对路径**登记外部库后调
  `unlockActiveDatabase`（`:643-674`）；该路径在 Windows 宿主为 `C:\…`、在 Linux/CI 为 `/…`——任何「路径形态」
  守卫都必须用**平台绝对**语义，否则本机假红（本批首轮全量实测的唯一致命点，见 §490.4）。

## 490.3 整改

### ① 准入策略：新增纯函数 `VaultOpenUriPolicy`（AC① / AC③ 可测性）

`app/src/main/java/com/keepasskey/app/security/VaultOpenUriPolicy.kt`（新增）：把此前混在 `Intent` / `Uri` /
`ContentResolver` 之间、宿主 JVM 无法单测的判据抽成**只吃 `String` 的纯函数**（`java.io.File` 为 JDK 标准类，
宿主可用；不含 `Uri.parse`）。三条判据各自 fail-closed：

- `acceptInboundUri(uriString)`：**只接受 `content://` 前缀**；`file://` / `http(s)://` / 相对路径 / 空 scheme
  一律 `Reject(UNSUPPORTED_SCHEME)`，空串 `Reject(EMPTY_URI)`；
- `acceptDisplayName(name)`：非空、**不含路径分量**（`/` `\`）、以 `.kdbx` 结尾（大小写不敏感）；否则
  `EMPTY_NAME` / `PATH_SHAPED_NAME` / `NOT_KDBX_NAME`；
- `isUnlockableStoredPath(path)`：`content://` **或平台绝对路径**（`File(path).isAbsolute`）才放行。

### ② 外部入口：scheme 白名单 + 显示名形态 + 登记前确认（AC① / AC②）

`OpenVaultEntryActivity.kt` 重写 `onCreate` 准入与登记流程：

- **scheme 白名单**：`uri == null || acceptInboundUri(uri.toString()) !is Accept` 即拒绝；
  `file://` 未证明存在「可预期来源形态」，按条目最小建议①取**最稳妥的一律拒绝**（AGENTS.md §3 防御性安全）。
- **显示名形态**：`resolveDisplayName` 收敛为**仅 `content://` 经 OpenableColumns 查询**（`file://` 分支随
  准入拒绝而删除）；`acceptDisplayName` 拒一切带目录分量 / 非 `.kdbx` 的显示名（`evil.kdbx` 这类「名字对、
  内容非 KDBX」由密码学层 fail-closed 兜底）。
- **登记前确认（AC②）**：`importExternalDatabase` 会覆写活动库指针，而外部 Intent 由任意应用可发，故
  **一律先弹确认**（`android.app.AlertDialog`，本页主题 `Theme.Material.NoActionBar` 提供对话框样式）：
  确认 → `performImport`；取消 / 返回 → 仅回落主界面、**不改任何状态**。确认对**首次安装（当前无活动库）**
  同样生效——AC② 原文即「登记新库 / 覆写活动库指针**前**引入用户确认」，未以「已有活动库」为条件，
  故取**无条件确认**（比条目建议③的条件式更严），顺带封住「空列表被恶意登记污染」形态。

### ③ 解锁链：不可解锁路径形态 fail-closed（条目建议②）

`VaultLifecycleCoordinator.unlockActiveDatabase` 在 `File(activeDb.path)` **之前**插入
`if (!VaultOpenUriPolicy.isUnlockableStoredPath(activeDb.path)) return KdbxResult.Failure(...)`：
含 scheme 前缀（`file:/…`）或相对路径一律显式失败（新文案 `repo_unsupported_db_path`），堵死
`File("file:/…")` 相对解析 → 文件缺失 → 「以主密码新建空库」的分支。判据用 `File(path).isAbsolute`
而非硬编「以 `/` 开头」：后者在 Windows 宿主上把合法绝对路径误判为相对（§490.4）。

### ④ 文档理由修正（AC③ 后半句）

- `ExportedComponentHygieneTest` 白名单理由：**已修正的白名单理由原文**「仅接受 content/file scheme 且文件名以
  `.kdbx` 结尾的对象」→ **改后表述**「仅接受 `content://` scheme（`file://` 与其它 scheme 一律拒绝，
  `ISSUE-P3-575`）且显示名为纯文件名并以 `.kdbx` 结尾的对象」，并补「登记前须用户确认（`ISSUE-P3-575` AC②）」。
- 同批修正 `OpenVaultEntryActivity` 类 KDoc 与 `AndroidManifest.xml` 组件注释中同款失实表述（三处口径统一）。

### ⑤ 文案（中英成对）

新增 `external_open_confirm_title` / `external_open_confirm_message`（携显示名 `%1$s`）/ `external_open_confirm_ok` /
`external_open_confirm_cancel` 与 `repo_unsupported_db_path`，`values/` 与 `values-en/` 逐键成对。

## 490.5 如实声明

- **`file://` 取「一律拒绝」而非「收敛白名单」**（条目 AC① 的二选一）：未证明存在可预期来源形态——
  现代文件管理器 / 云盘一律经 `content://`（DocumentsProvider），`file://` 到达本入口的形态主导来源即
  攻击者手写 Intent；且本仓无 FileProvider / `grantUriPermission`，无法对 `file://` 施加「受 FLAG_GRANT」这一
  身份约束（`file://` 无 FLAG_GRANT 概念）。**残余**：极端老旧 / 非标准来源若仅提供 `file://`，其「打开方式」
  将回落主界面并提示改用「选择文件」。此为**有意收敛**，非缺陷。
- **确认取「无条件」而非条目建议③的「仅当已有活动库 / 已解锁会话」**：AC② 原文是「登记新库 / 覆写活动库指针**前**
  引入用户确认」，未设条件；无条件确认同时封住「空列表被恶意登记污染」形态。**残余**：`OpenVaultEntryActivity`
  为 `excludeFromRecents` 的瞬时路由页，引入模态确认后其存活期延长至用户应答为止；页面仍不承载任何凭据明文
  （仅显示显示名），故未追加 `FLAG_SECURE`（与既有 KDoc「无内容渲染」声明一致）。旋转重建会重弹确认
  （`onCreate` 重跑），**不会**造成重复登记（`importExternalDatabase` 按 `path` 去重），亦不会在用户已确认后重复导入。
- **未采纳项**：条目「可选加固 / 白名单方案」中的「`file://` 收敛到可预期来源」未采纳（理由同上）；
  身份约束「受 FLAG_GRANT 的 URI」对 `content://` 属**平台默认**（跨进程 `content://` 无授权时
  `openInputStream` 即抛异常，且 `importExternalDatabase` 已尝试 `takePersistableUriPermission`），本批未额外加
  显式 grant 校验（`Intent.FLAG_GRANT_READ_URI_PERMISSION` 的显式断言属纵深防御微项，未纳入本轮）。
- **行数棘轮驱动的同方法局部压缩（须留痕）**：`VaultLifecycleCoordinator.kt` 原 **398** 行，`tier2(400~500)`
