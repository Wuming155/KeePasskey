## 224.1 条目原文（认领时登记内容）

### ISSUE-P3-215 解锁页（首页）常驻「已启用无障碍服务」提示，属冗余展示

- **核实时间点与方式**：2026-09-20 用户实机反馈「进首页即提示已启用无障碍服务」；经全仓
  `grep accessibilityRiskNotice` 核实消费点为 `UnlockScreen.kt`（ISSUE-P2-44 遗留接线，全仓唯一）。
- **现象**：进入解锁页即常驻渲染「已启用无障碍服务」Banner；该信号与主密码输入交互无直接关系，
  且用户在本机未主动开启无障碍服务时同样出现，构成对主流程的干扰与冗余信息。
- **整改口径**：
  ① 解锁页移除该提示（连同 `UnlockUiState.accessibilityRiskNotice` 提示位、`UnlockViewModel` 的订阅
  与 `UnlockScreen.AccessibilityInputNotice` 渲染）——解锁页不得再消费该信号；
  ② 迁移至设置页「安全策略」二级页安全分区（`SecuritySettingsScreen`）以 `AccessibilityStatusCard`
  展示（信息性、只告知不降级；卡内可点直达系统无障碍设置页，系统不响应时退回纯文案，无死链）；
  ③ 判定与「只提示、不降级通道」语义**不变**（不因此禁用生物快速解锁 / 自动填充）。
- **涉及文件**：`UnlockScreen.kt` / `UnlockUiState.kt` / `UnlockViewModel.kt` /
  `SecuritySettingsScreen.kt` / `SecuritySettingsComponents.kt` / `strings.xml` ×2 /
  `AccessibilityNoticeWiringTest.kt`
- **验收标准**：
  - AC① 解锁页源码不含 `accessibilityRiskNotice` / `unlock_accessibility_notice`（守卫测试静态锁定，防回潮）；
  - AC② 设置页按 `RuntimeIntegrityPolicy.requiresAccessibilityNotice(integrityReport)` 渲染状态卡；
  - AC③ 无障碍信号不参与 `RuntimeRiskLevel` 判定与通道降级（既有行为断言保持全绿）；
  - AC④ `.\gradlew.bat test` 全绿。

## 224.3 设计裁决与语义边界（不变项）

- **「只提示、不降级」不变**：本迁移**只改承载位置**。`RuntimeIntegrityPolicy.requiresAccessibilityNotice`
  仍是该信号唯一消费点；`thirdPartyAccessibilityEnabled` 依旧**不参与** `RuntimeRiskLevel` 判定，也不触发
  生物快速解锁 / 自动填充降级（`RuntimeIntegrityPolicyTest` 行为断言**零改动**即通过，为该不变项的机检证据）。
- **为何是设置页而非首页**：该信号描述的是「本机可及性配置」，与主密码输入这一交互动作无因果关系；
  置入设置页「系统环境防泄露保护」分区与 `IntegrityRiskCard` 同处，语义归位且不干扰解锁主流程。
- **用户「根本没启用」的如实声明**：判定口径仍是官方
  `AccessibilityManager.getEnabledAccessibilityServiceList(FEEDBACK_ALL_MASK)` 中「服务包名 ≠ 本应用包名」即真
  （**含系统预装的 TalkBack 等**，见 `IntegritySignals.thirdPartyAccessibilityEnabled` KDoc）；本批**未改变**该口径
  （不排除系统预装服务是有意为之：系统签名不改变其读取输入的能力）。设置页卡片同时提供直达系统
  无障碍设置页的入口，用户可一次点击自行核对系统侧实际开启项。

## 224.5 遗留与后续

- 用户在真机上观察到「未主动开启无障碍服务却被告知已启用」的**成因未定位**（本机不可复现，无法取得
  `getEnabledAccessibilityServiceList` 实际读数）。本批按「不改判定口径」处理，改由设置页承载 + 提供直达
  系统无障碍设置页的入口供用户自行核对。若后续复现，应改从**设备侧读数取证**入手（登记新条目），
  不得直接放宽判据。
