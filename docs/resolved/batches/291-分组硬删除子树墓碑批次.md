## 1. 条目正文（原样收录）

### `ISSUE-P2-284`：分组硬删除只为组自身立墓碑，子条目与子组无墓碑 ⇒ 跨设备合并复活

- **核实时间点**：2026-09-23 经删除分流与墓碑产出核对。**注**：本条在对抗轮未列为独立攻击对象，仅经官方源码旁证（对照段）+ 同文件反向口径支撑，开工前须按规则 6.1② 自行复核调用链。
- **核实方式**：`app/.../data/repository/RecycleBinCoordinator.kt:105-110` 的物理删除分支（回收站禁用 / 与回收站相关时）只追加 `DeletedObject(id = uuid)` 一条，即**组自身**；底层 `database/.../session/SessionTreeEditor.kt:265-278` 的 `removeGroup` 直接摘除整棵子树、不产出子对象墓碑；`sync/.../merge/KdbxTombstoneMerger.kt:22-27` 按 UUID 精确匹配，父组墓碑**不覆盖**子项 ⇒ 他端仍持有条目并将其作为存活对象合回。同文件 `emptyRecycleBin`（`:178-188`）已采用逐对象墓碑口径，构成同文件内直接对照。
- **对照（经核实为真）**：官方 `PwGroup.cs:1367-1386` 的 `DeleteAllObjects` 为**每个子孙 entry 与 group** 追加 `PwDeletedObject`。
- **涉及文件**：`app/src/main/java/com/keepasskey/app/data/repository/RecycleBinCoordinator.kt`、`database/src/main/java/com/keepasskey/database/session/SessionTreeEditor.kt`、`sync/src/main/java/com/keepasskey/sync/merge/KdbxTombstoneMerger.kt`。
- **验收标准**：AC① 组硬删除递归产出子孙条目 / 子组墓碑，并与 `emptyRecycleBin` **复用同一函数**（禁两份实现）；AC② 用例锁定「删组后本库墓碑数 = 子孙对象数 + 组自身」与「他端存活副本经合并后被清除」；AC③ 补 `:database:` / `:sync:` 端到端合并往返；AC④ 与 §246、`ISSUE-P1-03` 的删除语义一致，不得引入「物理删除但无墓碑」的新分支。

**开工前前提复核（2026-09-23，按规则 6.1② 自行复核调用链）**：成立。① 生产路径复核——`deleteGroup` 硬删分支确只立组自身一碑；`emptyRecycleBin` 的逐对象口径构成同文件对照。② **复活机理复核（比条目更精确）**：base 含子对象且对端未改时，现行合并（`isRemoteDeleted` 凭 base 推断 + 「修改胜」）恰好也能清除副本——复活须满足「对端自 base 起**有任何**修改」或「base 缺该对象」（陈旧 base 设备）——因 `mergeSurvivingEntries` 的删除 vs 修改判据是「是否自 base 有改动」，**不与删除时刻比时间**。这意味着**仅补墓碑不足以闭合**：墓碑在且对端修改早于删除时刻时，旧判据仍判「修改胜」复活。故本批整改 = 墓碑产出 + **合并裁决时间口径**两件（见 §2.2）。

## 2. 整改

### 2.1 AC①：递归墓碑 + 复用同一函数

`RecycleBinCoordinator` 新增私有 `permanentlyDeleteObjects(entryIds, groupIds)`（批量删条目 → 逐组摘除（父组摘除后子组调用为安全 no-op）→ 一次性追加全量墓碑），**组硬删除分支**与 **`emptyRecycleBin`** 共用同一实现（禁两份）。组硬删除的墓碑集合 = 组自身 ∪ 子孙条目 ∪ 子孙子组（官方 `PwGroup.DeleteAllObjects` 同口径）；分流逻辑（`binRelated || !recycleBinEnabled`）一行未动（AC④）。

### 2.2 合并裁决时间口径（前提复核揭出的同族根因，不修则 AC② 空转）

`KdbxEntryMerger.mergeSurvivingEntries` 与 `KdbxGroupMerger.mergeSurvivingGroups` 的「删除 vs 修改」判据改为：**墓碑存在时按官方口径比时间**（`PwDeletedObject.DeletionTime` vs `LastModificationTime`——仅「修改晚于删除时刻」才复活）；**无墓碑**（仅凭 base 推断删除）时保持「修改胜」旧口径。四个分支（条目 / 分组 × 本删 / 对删）同一形态。官方依据：KeePass `MergeIn` 对删除与修改冲突即比较两时刻（晚者胜）。

### 2.3 AC③：两端往返

`:database:` 子树墓碑集合整库加密往返逐个保留（UUID + 删除时间）；`:sync:` 端到端合并（§3.1）。
