## 1. 条目原文（本批认领的三条）

### 1.1 `ISSUE-P1-533`：同类闪退面未收口（消费 / 检索 / 交付面 + 编辑路径时序）

§473 只把 `VaultEntryMapper` / `VaultEntryTotpMapping` 两个文件降级，而 `ProtectedString` 的就地清零是
**可变的共享引用**——任何持旧树快照的读点都命中同一异常；同时根因链第 1 条（擦除时序）在**最热的编辑路径**
上原样保留。审计给出 5 类消费面 + 3 条编辑路径。

### 1.2 `ISSUE-P2-534`：展示读口 TOCTOU、fail-open 读口无使用面约束、机检盲区

① `readStringForDisplay` 的「检查-再读」不是原子的，承诺的「不抛」不成立，且并发下可能**解出垃圾明文**；
② 机检是「2 文件白名单」：真机崩溃点其实走 `KdbxEntry.getUserName`（getter 定义在 core，改回 getter 时闸门
**全绿**）、`useChars` / `useUtf8` 不在判据内、fail-open 读口（展示读口）用在写路径会静默写空值却**零机检**。

### 1.3 `ISSUE-P3-535`：约定漂移 + 兜底自抛 + 应用级 scope 无异常处理器

① `KdbxGroup.clearSupersededSensitiveData` 的 KDoc 调用约定与 §473 整改后的现状相反；
② `launchGuarded` 的 `onFailure` 自身抛异常会重新逃逸；③ 应用级 scope 逐点接线漏一处即复发。

## 3. 整改内容

### 3.1 `core`：消除展示读口的 TOCTOU，并把「已清零缓冲」收敛为 fail-closed

- `ProtectedString.isCleared` 加 **`@Volatile`**（跨线程共享的可变引用，无 volatile 时读侧可能长期看不到置位）；
- `readStringForDisplay` / `readUtf8ForDisplay` 改为**以 `try/catch` 包住唯一判据点**（`readString` / `readUtf8`
  内部的 `checkNotCleared`），从构造上消除「先查后读」的两步式；
- `plainBytes()` 在解密后**复核等值标签**（`InMemoryCipher.equalityTag` 新增），不匹配即清零缓冲并按
  「已清零 / 已损坏」fail-closed —— 这条是审计未覆盖的**静默垃圾明文**面的唯一出口；
- 非保护实例（无标签）的残余窗口如实写进 KDoc（已接受：填零只会得到「部分明文」而非垃圾串）。

### 3.2 `core`：条目级展示读口 + `cleared` 预判，替换「异常做流程控制」

- `KdbxEntry` 新增 `displayTitle()` / `displayUserName()` / `displayUrl()` / `displayNotes()`（**成员**，非扩展：
  调用点零 import，也更容易被后续开发者选用）与 `hasClearedFields()`（交付 / 凭据面预判中止）；
- `PasskeyData.fromCustomFields`：形状短路阶段 `if (field.value.cleared) continue`，三个必需键
  `takeUnless { it.cleared }` ⇒ 已清零条目**自然返回 null**，`VaultEntryMapper` 侧的 `catch (IllegalStateException)`
  随之删除（本仓定则：据 `cleared` 降级，不以异常做流程控制）。

### 3.3 `database`：编辑路径统一「先发布、后擦除」

`saveEntry` / `saveGroup` / `updateEntryById` / `batchMoveEntries` 四条；擦除原语与身份集合判定**逐字未动**，
`updateEntryById` 的「读回落树实例」契约不受影响（擦除只触碰 `replaced`）。约定同步写进
`KdbxGroup.clearSupersededSensitiveData` 与 `SessionContentMutations` 类 KDoc。

### 3.4 `app`：消费面收口 + 交付面预判 + 凭据面重取快照

- **展示 / 检索面**（`AutofillEntrySearch`、`AutofillCandidateRanker`、`AutofillPickerScreen`、
  `AutofillStructuredDatasets`、`AutofillUnlockActivity`、`DuplicateEntryScanner`、
  `ConflictResolutionViewModel`）改走展示读口；冲突页的敏感线索另走新增的
  `readCharsForDisplayOrNull()`（独占副本 + `finally` 清零，取代 `useChars` 的 fail-fast 形态）；
- **交付面**（`AutofillDatasetBuilders.buildCandidateDataset`）改为**返回 `Dataset?`**：候选若
  `hasClearedFields()` 即跳过并留脱敏日志 —— 绝不把已清零字段读成空串填给目标应用；
- **凭据面**（`VaultEntrySecretReader`）新增 `guardedCredentialRead`：撞上并发替换时**重取快照重试一次**
  （数据并未丢失，比重报失败更贴合事实），仍失败则如实上抛；凭据面**不降级成空值**；
- **兜底**：`launchGuarded` 的 `onFailure` 包 `runCatching`；新增 `guardedScope` 工厂并接入全部 15 处应用级 scope。

### 3.5 机检加固（`tools/doc/check_projection_read_safety.py`）

三条判据（任一命中即红，`--selftest` 三向反校）：

1. 投影面不得裸 `readString()` / `readUtf8()` / `readChars()` / `useChars {` / `useUtf8 {`；
2. 投影面不得引用 `KdbxEntry` 的四个 fail-fast getter（**真机崩溃点走的正是 getter**；UI 模型同名接收者
   经行内豁免片段区分，豁免失配会在原处重新判红）；
3. **展示读口反向白名单（fail-closed）**：仓内任何非测试文件调用展示读口（`displayTitle` /
   `readStringForDisplay` / `readCharsForDisplayOrNull` 等）必须在白名单登记，**新调用点未登记即红**。

投影面清单由 2 个文件扩到 **10 个**（条目投影 + 检索 / 排序 / 交付装配 / 选择器 / 差异展示）。

## 4. 过程缺陷如实留痕

1. **首轮全量 `test` 红 1 例**：`AlgoHotPathGuardsTest#自动填充评分不得逐条目重复解密与建 Map`
   —— 该守卫按**源码文本**锚定 `val entryUrl = entry.url`，整改后文本变为 `entry.displayUrl()` 故计数为 0。
   按 `ISSUE-P3-489` 纪律**先**跑 `preserve_test_failures.py` 留存证据
   （`build/failure-evidence/unit-test-failures-20261008-024453.txt`）**再**修改**守卫判据**（锚定新形式，
   「url 只允许读一次」的意图逐字不变），**未放宽**任何判据。
2. **机检自身首轮 `--selftest` 红**：红样本夹具把「已登记的展示读口文件」写到了 `PROJECTION_FILES` 之内，
   覆盖了该文件的样本体 ⇒ RULE1/RULE2 少算一份（18 ≠ 20）。这正是「度量工具须用已知值反校」的价值：
   夹具改为「白名单减去投影面文件」后复绿。**闸门先跑出红再转绿**，非仅跑绿态。
3. **扩面即现形**：投影面清单从 2 个扩到 10 个后，机检当场报出 4 处残留（`AutofillDatasetBuilders` 的
   2 处 `entry.title`、`ConflictResolutionViewModel` 的标题与 `useChars`），已全部整改 ——
   印证审计 #2「2 文件白名单挡不住最可能的复发路径」。
4. **规模棘轮红两次（收工线）**：① `PasskeyData.kt` 因本批新增 `cleared` 判据达 **508 行** ⇒
   `tier1(>500)=1` 红；压缩为等价实现（`takeUnless` 内联 + 注释合并）回到 **500 行**。
   ② 回到 500 后 `tier2(400~500)` 变 **36 > budget=35** 红 —— 定位到**唯一新进者**是
   `ClipboardSecurityManager.kt`（**399 → 400**，仅因 `guardedScope` 接入多了一行 import）；
   删去随之**失效的 `SupervisorJob` import**并把新 import 归位 ⇒ **399** 转绿。
   两次都**未**动预算、**未**放宽判据（棘轮只紧不松）。
