### 76.2 实测结果（arm64 真机 Redmi 4X / LineageOS / Android 17 / **API 37** / `maxHeap = 192 MiB`）

**M-2 分路径（复核的确切题面）**

| 观测项 | 实测 |
|---|---|
| codec 动态堆门槛接受 `M = 堆/2`（96 MiB） | 是 |
| codec 拒绝 `M = 堆/2 + 1 MiB` | 是（`KdbxCorruptFileException`，**边界双向核对**） |
| JVM 兜底闸门（`0.6 × maxHeap` = 115 MiB）接受 `M = 堆/2` | 是 ⇒ 对 JVM 路径而言 **codec 那道更紧** |
| **原生路径无第二道闸**（复核断言） | **确认**：以 `M = 堆/2` 真实派生成功（0.750 s / 0.748 s，I=1） |
| **实际到达内核的内存** | **98 304 KiB = 96 MiB** |
| 本机**有效内存上界** | **96 MiB**（静态封顶 4 GiB 本机不可达）——纠正原文推算的「128–256 MiB」 |
| `M = 512 MiB × I = 20` 可否解锁 | **否**（被动态堆门槛拒绝） |

**M-1 墙钟**

| 配置 | 实测秒数（两次独立运行） |
|---|---|
| 默认（64 MiB × I=2 × P=2） | **0.609 / 0.635 s** |
| 重载（96 MiB × I=8 × P=2） | **2.470 / 2.537 s** |
| **实测吞吐** | **2.204×10⁸ / 2.115×10⁸ 字节·轮/秒** |
| 当前联合预算（`I×M ≤ 2^40`，**实测 codec 接受**）最坏合法配置的墙钟 | **≈4 988 / 5 198 s ≈ 1.39 / 1.44 小时**（按实测吞吐**换算**，用例已标注 `extrapolated_`，未实跑） |

### 76.3 这组数字改变了什么（结论）

1. **「原生路径无第二道闸」确认为事实，但实际约束来自 codec**：两条路径的有效上界都是 codec 的
   `M ≤ 堆/2`（本机 96 MiB），故该缺口的**实际影响面小于复核推测**——不必新增第二道闸；
   但**必须保留**「codec 是唯一动态界限」这一认知，`Argon2KdfEngine` 的镜像上界
   （`isWithinKdfBounds`）是**静态**的，不能替代动态堆门槛。
2. **可用性 DoS 实测成立且量级明确**：当前预算允许的最坏合法配置在本机需 **≈1.4 小时**，
   而派生发生在 Header HMAC **之前**（无口令可达，同步路径亦可触发）。
   ⇒ `ISSUE-P2-49 AC②` 的处置路径据此**定为**：协程 `withTimeout` 对阻塞式原生派生**无效**
   （复核定版已确认，本批亦以「派生耗时 0.6~2.5 s 全额计入且不可中断」佐证），
   有效方案只有两条——① **收紧联合预算**（静态或按设备实测锚定）；② 原生内核支持
   **可取消派生**（pass 之间检查取消标志）。②为治本，属独立批次。
3. **题面更正**：`I = 2²⁴` 与 `M = 堆/2` 的组合（≈`2^51` 字节·轮）已被联合预算拒绝
   （实测断言 `originalPremise_i2pow24_mHeapHalf_rejected=true`），条目原文的测量对象已不存在。

### 76.5 过程缺陷（如实留痕）

1. **把「应当成立」写成了断言**：首跑的失败断言来自我对 `KdfBenchmark` 自荐上界（「≤512 MiB × 20」）
   与**动态堆门槛**关系的误判——前者是**静态**建议值，后者才是真机实际约束。
   ⇒ 纪律：**设备侧用例的每条断言都必须先问「该前提在本机 maxHeap 下是否可能成立」**；
   把不确定的前提写成断言，失败信息本身即证据（本次正因此拿到 96 MiB 这个关键数字）。
2. **失败信息的价值取决于是否携带上下文**：本批首跑失败直接给出「期望接受/实际拒绝」，
   一次定位；对照 §74 那条「偶发红、只报 `cleared=false` 无上下文」的旧例——
   ⇒ 纪律延续：**清理 / 判定类断言必须把可判定的事实（数值、边界、日志）一并写进消息**。
