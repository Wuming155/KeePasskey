## 3. 逐项证据

### 3.1 注册闭环（第 1 项）

| 阶段 | 真机证据 |
|:--|:--|
| ① provider 产出创建项 | `onBeginCreateCredentialRequest 收到系统创建请求: BeginCreatePublicKeyCredentialRequest` → `Provider status changed: SAVE_ENTRIES_RECEIVED`（库已解锁时回调仅 **11 ms**） |
| ② 面板确认 | 点「继续」→ `PasskeyCreateActivity` 被拉起 |
| ③ 门控放行 | `W/PasskeyCreateActivity: 用户已显式开启「跳过 DAL 校验」，本次注册不执行远程声明验证` |
| ④ 用户验证 | 确认页如实呈现降级：「即将为『example.com』创建通行密钥。本设备无可用生物识别或锁屏凭据，新凭据将如实标记为『创建时未执行用户验证』(UV=0)…」，按钮「取消 / 允许」 |
| ⑤ 生成 + 落库 + 回传 | 点「允许」→ 调用方（测试 APK 独立包名）日志 `CM-SAVE-STATUS:onResult`；`PasskeyCreateActivity` 随即 `visibilityChanged …false`（正常收尾） |
| ⑥ 落库物证 | 库列表出现条目：标题 `cm-probe-user@example.com`、**`Passkey` 角标**、用户名 `cm-probe-user`、绑定 `android://com.keepasskey.test` |

第 ⑥ 项的「绑定 `android://<调用包名>`」正是设计口径：非浏览器调用方（origin 为
`android:apk-key-hash:…`）由 `PasskeyCreateActivity` 以系统背书包名落库。

### 3.2 DAL 门控两侧（第 2 项）

**拒绝侧（真机，走真实网络）**：

```
W/DalVerifier:           DAL 响应非 2xx，视为无声明
I/DalVerifier:           DAL 校验完成: result=NOT_VERIFIED
W/PasskeyCreateActivity: 注册门禁拒绝（DAL_UNVERIFIED），fail-closed 不创建 Passkey
```

界面呈现**用户可见原因**（ISSUE-P2-220 的效果）：

```
无法创建通行密钥
无法确认调用应用对本站点的归属声明，已拒绝创建通行密钥。
知道了
```

**放行侧（用户显式降级）**：开启设置中该开关后重跑，日志
`用户已显式开启「跳过 DAL 校验」，本次注册不执行远程声明验证`，门控放行并完成注册（§3.1）。

**正向 `VERIFIED`：真机不可达（如实声明）**——`DigitalAssetLinksVerifier` 校验的是
`https://<rpId>/.well-known/assetlinks.json` 中**调用方包名 + 证书指纹**的声明，
要真机跑通必须存在「自控且能发布声明、且 TLS 受系统信任」的域名；本环境不具备
（本应用还刻意拒绝自签信任锚，见 `ISSUE-P2-192` 的设备侧用例）。
该路径由**宿主**用例覆盖：`DigitalAssetLinksVerifierTest` 的 12 例含
`远程声明_包名与指纹匹配_校验通过`、`远程声明_冒号指纹与无冒号指纹跨格式匹配`、
`远程声明_恰好等于字节上限且内容合法_仍可校验通过` 等；门控映射
（`VERIFIED → 放行`）由 `CredentialRejectionFeedbackTest` 覆盖。

### 3.3 面板分支（第 3 项）

- **取消**：在面板上按返回 → 调用方 `onError: android.credentials.CreateCredentialException.TYPE_USER_CANCELED`。
- **更换提供方**：对面板做**全部文本节点穷举**后确认——面板只含
  「KeePasskey / 要创建通行密钥以便登录…吗？/ 副标题 / 条目（标题+副标题）/ 继续 / 底部说明」，
  **不存在**提供方切换或「更多选项」入口。故该项在本 ROM 上**无对应可点分支**（不是「未测」）。
  这与「首选服务」机制一致：本应用既是首选又是唯一已启用提供方，系统直接呈现确认式面板。

### 3.4 冷启动统计（第 4 项）

方法：每轮 `force-stop` 应用与客户端 → 清缓冲 → 由客户端发起保存请求 →
取 `ActivityManager: Start proc …KeePasskeyCredentialProviderService` 与
`KeePasskeyCredProvider: onBeginCreateCredentialRequest` 两条时间戳求差。共 **10 轮**：

| 轮 | 时延 | 轮 | 时延 |
|:--:|--:|:--:|--:|
| 1 | 2.568 s | 6 | 2.393 s |
| 2 | 2.354 s | 7 | 2.351 s |
| 3 | 2.357 s | 8 | 2.352 s |
| 4 | 2.354 s | 9 | 2.361 s |
| 5 | 2.366 s | 10 | 2.371 s |

**统计**：样本 10，最小 **2.351 s**，最大 **2.568 s**，中位 **2.359 s**，均值 **2.383 s**；
**超时 0 轮**，10/10 全部 `SAVE_ENTRIES_RECEIVED`。

对照（§240 修前，同为冷启动）：2.49 s（勉强通过）/ **3.05 s（`Remote provider response timed out`）**。
⇒ §240 把 `applySavedSchedule()` 移出关键路径后，分布收敛到 2.35 ~ 2.57 s、稳定落在系统
约 3.0 s 预算之内，**余量约 0.4 ~ 0.65 s**。

## 4. 同轮新发现缺陷：`ISSUE-P2-240`（设置页开关文案与真实语义不符）

为完成第 2 项的「放行侧」，需要按用户路径打开那个开关；打开时发现：

- 界面上该行是 **「跳过浏览器兼容层」/「不通过浏览器兼容适配直接填充原生表单」**；
- 但它接线的是 `onSkipDalVerificationToggle` → `ExtendedSettings.skipDalVerification`
  （`AutofillSettingsComponents.kt:238-244`），消费方是 `PasskeyCreateActivity` 的**注册门控**；
- 真机点击后 `keepasskey_extended_settings.xml` 写入 `<boolean name="skip_dal_verification" value="true" />`，
  随后注册日志出现「跳过 DAL 校验」留痕 —— **文案与实际行为确证不符**。

影响：`DigitalAssetLinksVerifier` 的 KDoc 称「用户如确有离线注册需求，可经设置中
『跳过 DAL 校验』显式授权降级」，但**用户根本看不到这个入口的名字**；他看到的是
「浏览器兼容层 / 原生表单填充」，与「通行密钥注册的站点归属声明校验」无关，
无法据此做出知情决策。已登记为 `ISSUE-P2-240`（详见 `ACTIVE_ISSUES.md`）。

## 7. 如实声明

1. **`ISSUE-P1-238` 未闭环**：AC① 要求 10 轮全部 ≤ 1.5 s，实测 2.35 ~ 2.57 s **未达标**；
   本轮的价值是把「点测」升级为「10 轮统计」，并确认 §240 的改动使分布稳定落在预算内。
   该条目保持开放。
2. **DAL 正向 `VERIFIED` 真机不可达**（原因见 §3.2），只有宿主级证据；**不得**读作「DAL 正向已真机验证」。
3. **未做通行密钥产物的外部对拍**：`tools/passkey-interop/verify_interop.py`（规则 8 的 KPEX 出口）
   本批**未跑**——它校验的是 `PasskeyData` 落库格式与外部实现互操作，与本批四项无关，
   且需要 `:database:` 侧探测产物；本批不对其结论作任何声称。
4. **私有口令纪律**：新建密码库使用**虚构测试口令**，本文件不记录其取值。
5. **面板只在「本应用为唯一已启用提供方」的环境下测过**；多提供方并存的呈现差异未覆盖。
6. 本批未触 `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 与任一原生绑定，
   亦未新增 / 修改任何自动化用例（改动仅为注释与文档）。
