## 1. 背景与原貌（原样收录自待办条目）

### ISSUE-P2-226：自动填充服务对自身界面下发候选与保存提示（缺自我包名排除）

- **核实时间点**：2026-09-20 经用户真机反馈 + 全仓代码走查核实。
- **核实方式**：① `KeePasskeyAutofillService.kt:126` 取 `structure.activityComponent.packageName` 后仅过 `rejectsDatasetDelivery`（`:181-199`），而闸门 `AutofillAccessPolicy.kt:32-40` 只有 `INTEGRITY_RISK` / `BLOCKLISTED` 两个枚举，**无自身包名分支**；② `onSaveRequest`（`:282-360`）同样只有完整性 + 两道黑名单；③ 全 `app/src/main/java` grep `APPLICATION_ID|packageName == context.packageName|SELF_PACKAGE` 仅命中 `InstalledAppsCatalog.kt:62`；④ `res/xml/autofill_service.xml` 无 `packageNames` 属性；⑤ 反向确认触发源：`SecurePasswordField.kt:125-128` 声明 `KeyboardType.Password`、`:170` `semantics { password() }`，UI 层 grep `AutofillType|textContentType|importantForAutofill` **零命中**（从未关闭过自身参与）。
- **背景与根因**：用户在 KeePasskey 自己的解锁页 / 条目编辑页 / 新建库向导里输入口令时，系统仍弹出本应用的填充建议（含「解锁 KeePasskey」引导条与保存气泡）。根因两条并列：应用侧 `AutofillService` 对「调用包名 == 自身包」**从未做过任何短路**；自家口令输入框从未声明不参与自动填充。**既有文档的前提已被证伪**：`docs/resolved/batches/109-…批次.md:54` 写「自动填充服务对自身包名不生效」——框架并不禁止自身发起填充请求。
- **验收标准**：AC① `AutofillAccessPolicy` 新增自身包名拒绝枚举并在 fill / save 两条路径**前置生效**（命中即不下发解锁引导、数据集、`SaveInfo`，且绝不落库）；AC② 判定为纯函数、JVM 可测，新增用例覆盖「自身包 == 调用包」「自身包大小写/空白变形」「外部包名不受影响」三类；AC③ 日志不得携带包名明文（ISSUE-P1-10 口径）。

## 2. 整改方案与架构落地

- **判定收敛到闸门**：`AutofillAccessPolicy` 新增 `AutofillRejection.SELF_APP` 与纯函数
  `isSelfApp(callingPackage, selfPackage)`（trim + `Locale.ROOT` 小写等值比较），并把它作为
  `rejectReason(enforcement, callingPackage, selfPackage, isBlocklisted)` 的第 3 个入参——
  「能否向该调用方下发」这一决策**只有一个归属**，服务侧不再有第二份判据。
  - 归一化刻意**不**套 `AutofillPackageNames.normalize` 的合法性正则：两侧包名同源自框架
    （调用方由系统背书、自身由 `Context.packageName`），且非法形态随后仍被黑名单侧 fail-closed 拒掉；
  - 空调用包名与空 `selfPackage` **一律不判为自身**，避免以异常装配的空串吞掉全部调用方；
  - 优先级：`INTEGRITY_RISK` > `SELF_APP` > `BLOCKLISTED`（完整性风险仍最先报告，既有语义不变）。
- **填充路径**（`processFillRequest`）：在 `awaitEnforcement()` **之前**以 `isSelfApp` 短路并 `onSuccess(null)`。
  动因除正确性外还有开销——`awaitEnforcement()` 内含一次重扫（`/proc/self/maps` 扫描上限 16 MiB +
  root/Magisk/Frida 路径探测），自家口令框每次聚焦都触发一轮并无意义；闸门内的 `SELF_APP` 分支同时保留为兜底。
- **保存路径**（`handleSaveRequest`）：调用包名空白与「即本应用」合并为同一守卫，按 `onSuccess()`
  （「本次无需保存」）**静默收尾而非 `onFailure`**——本应用内凭据写入走自有写盘链路，不经框架保存提示，
  给用户报「保存被拒」反倒是误导；闸门内的 `SELF_APP` 分支同样保留。
- **契约文档化**：`KeePasskeyAutofillService` 类 KDoc 行为清单增第 8 条（自我排除）。
- **不改的东西**：`res/xml/autofill_service.xml` 未加 `packageNames` 属性（该属性是**白名单**语义，
  列举即等于限制可填充范围，无法表达「除自身之外全部」）；`SecurePasswordField` 未增
  `importantForAutofill` 声明（见 §4.2 残余）。

## 4. 残余与未执行声明

### 4.1 设备侧未核对（如实登记）
本批未新增或修改 `*/src/androidTest/**` 用例，故无「设备侧必跑项」（AGENTS.md §5 ②的触发条件不成立）。
但**整改效果本身需真机复核**：自家解锁页 / 条目编辑页 / 新建向导的口令框上不再出现本应用的填充建议条与保存气泡
——本环境**无可用设备/AVD**（`android-cli.exe studio devices` 挂住，见 `docs/architecture/已知工程限界.md` §4.1
手工冒烟边界），**未执行**，须由用户在已连真机上冒烟确认。

### 4.2 本批刻意不覆盖的面
- **第三方填充提供程序**仍可在本应用口令框上呈现其候选（那是那些应用与本应用无关的 `AutofillService` 行为）；
  本批只收口「KeePasskey 给自己填」这一路。若后续要在自家口令框上关闭**所有**外部填充参与，
  需评估 Compose 侧的 `importantForAutofill` / `AutofillType` 声明手段（当前 UI 层零声明），
  并须先确认不会连带切断「应用内主动选外部凭据」等既有能力——**未排期**；
- **凭证提供方（Credential Provider）通道**不受本批改判影响：它由系统按调用方 `origin` 派发，
  本应用自身从不作为 RP 发起 `GetCredential`，无自我填充面。
