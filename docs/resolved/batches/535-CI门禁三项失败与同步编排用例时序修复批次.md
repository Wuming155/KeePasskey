## 535.1 P2-658 修复（用例时序，不改断言口径）

`已验证连接直接同步且不再重复测试` 的单次 `testScheduler.runCurrent()` 改为
`pumpUntil { syncFeedbackMessage?.resId == R.string.sync_feedback_error }`：

- 断言的**语义未放宽**：仍要求「跳过重复测试（`testCalls == 0`）」+「直接触发同步（反馈落到 `sync_feedback_error`）」+「`isSyncing` 复位」+「已验证结论不被清掉」；
- 停止条件是**反馈收敛**而非固定时长 `sleep`，机器快慢不会改变判定；
- 若「直接同步」被移除，反馈停在上一轮 `sync_feedback_done`，`pumpUntil` 超时后同一断言判红（失败方向不变）。

## 535.2 P2-645 修复（门禁三项，逐项）

### 535.2.1 取消语义 12 处 → 0（`check_cancellation_semantics`）

| 落点 | 处置 | 理由 |
|---|---|---|
| `ChildReadOnlySession` / `SessionExternalParser` / `SessionOpener` 共 5 处 | 新增 `core` 的 `suppressCleanupFailure(primary) { cleanup }`（非挂起内联函数），清理失败并入主异常 | 内层 `catch(Throwable)` 只是「清理失败并入主异常」，其兄弟分支判定被更近的内层 `try` 遮挡；抽成非挂起函数后取消不可能在清理段被观测，主异常仍由外层 `if (t is CancellationException) throw t` 原样处理 |
| `CancellableOkHttpCall` 1 处 | 新增 `catch (cancellation: CancellationException) { continuation.cancel(cancellation) }` | 取消以续体取消收口，避免被 `resumeWithException` 归一为业务失败 |
| 锁态上传两处 `withContext(IO)`（原 `SyncCoordinator:755/911`） | 补 `catch (cancellation: CancellationException) { payload.fill(0); throw cancelled }` | 保护段含挂起点（`withContext`），且**密文缓冲必须先清零再上抛** |
| 密文摘要一处（原 `:950`） | 补取消重抛 | 同上，保护段含挂起点 |
| 配置目标探测一处（原 `:563`） | 就地标注 `cancel-n/a: configuredTarget 为同步函数，保护段不含挂起点` | 补守卫是死代码 |

### 535.2.3 拆分过程中发现并修正的真实缺陷（如实留痕）

1. **锁态上传失败分型回归**（`SyncLockedUploader`）：拆分时把「上传以 `Result.failure` 返回」的
   `REJECTED` 分支错写成 `RemoteRejected`，而原实现是 `REMOTE_CHANGED`（412 预条件拒绝 ⇒ 远端已被改写）。
   `SyncCoordinatorTest.锁定Worker条件上传持久密文并在解锁后安全收敛` 实测红后修正为 `Rejection.REMARK_CHANGED`。
2. **构造期触达 `context.filesDir`**（`SyncRecoveryQueries` / `SyncLockedProbeRunner` / `SyncLockedUploader`）：
   首版把上传队列存储作为构造参数直接注入，使 `SyncCoordinator` 的惰性协作方在**构造期**读 `filesDir`
   （生产上是构造期 IO，测试上是无 `filesDir` 的假 Context 直接抛错 / 自递归 `StackOverflowError`）。
   改为 `() -> PeriodicSyncPendingUploadStore` 惰性取用，恢复「构造期零 IO」的既有口径。
