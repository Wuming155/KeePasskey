# §319 附件写读口径同源批次（`ISSUE-P2-311` 闭环）

> **批次性质**：数据完整性整改。写读两侧对「64 MiB」这一量级的口径此前互斥——UI 上界（64 MiB，`>` 判）
> 恰好放行写侧单字段上限值的附件，而其字段长（64 MiB + 1）被读侧单字段上限判损坏；
> 写侧此前也**零累计闸**，多份大附件组合「写得出、读不进」。本批以**同源派生**消除互斥，并在写侧补累计闸。

---

## 1. 整改对象

| 条目 | 判据来源 | 本批处置 |
|---|---|---|
| `ISSUE-P2-311` 自产 64 MiB 附件被自家解析器判损坏（写读两侧对同一常量口径互斥）（★） | 2026-09-24 同步/加密/passkey 安全审计 | **闭环**（AC① / AC② / AC③ 全部达成，见 §2 / §3） |

## 2. 整改方案

### 2.1 AC①：UI 上界同源派生（消除写读互斥）

`AttachmentSizeLimits.MAX_ATTACHMENT_BYTES` 由独立字面量 `64 MiB` 改为
**`InnerHeader.MAX_INNER_FIELD_BYTES − 1`**（BINARY 字段 = 1 字节 flags 前缀 + 内容）——
UI 放行的最大附件写出的恰好是读侧能接受的**最长合法字段**（读侧 `>` 判：等长合法），两侧不再可能互斥。
数值与旧值差 1 字节；`AttachmentBudget.MAX_INLINE_MATERIALIZED_BYTES` /
`MAX_POOL_ITEM_MATERIALIZED_BYTES` 随之 `const` → `val`（上游不再是编译期常量）；
`EntryEditPickers` 的超限文案改为 1 MiB **向上取整**显示（floor 会显示 63，与「不超过 64 MiB 即可添加」
的实际语义相悖）。

### 2.2 AC②：写侧池累计闸（单值同读侧）

新增类型化异常 `KdbxAttachmentPoolBudgetExceededException`；`InnerHeader.serialize` 在**任何字段写出之前**
对池累计（Σ `bin.size`，落盘条目即 `spilledSize`）执行 `> MAX_BINARY_POOL_TOTAL_BYTES` 判——
与读侧 `deserialize` 的累计闸**同一单值、同一判式**。该守卫与 §318 的 `verifySpillIntact` 一并前置于
写前置守卫段（任何输出发生前 fail-closed）。

### 2.3 AC③：参数化 save→load 往返 + 临界取证

- `AttachmentWriteReadLimitParityTest`（新增，参数化 2 组）：
  ① 单附件 = `MAX_ATTACHMENT_BYTES`（64 MiB − 1）本身；② 多附件累计临界
  `2 × (64 MiB − 1 − 1 KiB) = 128 MiB − 2 KiB`。两组 save→load 往返逐字节等价必通。
- `AttachmentPoolBudgetWriteGuardTest`（新增）：3 × 50 MiB = 157286400 > 134217728 的组合在保存期被
  `KdbxAttachmentPoolBudgetExceededException` 拦截（异常信息含累计值与上限）。

### 2.4 实测新发现（如实登记，含一处 AC③ 参数就地修正）

参数化首轮实跑把「多附件累计临界」的真实约束面暴露了出来，**如实登记**：

- 读侧可接受池累计的真实上界受**整包解压上限**（`MAX_DECOMPRESSED_PAYLOAD_BYTES` = 128 MiB，
  GZip 解压护栏，**含池 + flags + XML**）**先于**池累计闸约束——恰为 `2 × (64 MiB − 1)` 的组合
  （128 MiB − 2 + 2 字节 flags + XML）在解析期先撞整包 GZip 守卫（`KdbxCorruptFileException`），
  轮不到池累计闸。这与既有登记一致：`MAX_BINARY_POOL_TOTAL_BYTES` 对生产解析路径是
  defense-in-depth（非 binding，见其 KDoc「防线定位」）。
- 因此 AC③ 的「累计临界必通」取**可过临界**（128 MiB − 2 KiB，低于整包上限）；AC② 的写侧闸仍按条目
  原文取读侧池闸同一单值——两闸同源（均由整包上限派生）、整包恒先触发，写读不互斥的结论不变；
  「写侧池闸放行但整包上限拒收」的残余窗口由整包上限自身在写侧的同源性收口（写侧无法预知 XML 尺寸，
  该形态与读侧既有非 binding 定位一致，不再单独立条）。
