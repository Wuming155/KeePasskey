## 2. 取证与定性（先取证后动手）

用户走查回执「不行」。真机截屏（`swords.kdbx` 解锁页）直接暴露矛盾：
提示栏「已自动载入记住的密钥文件: **pawords.keyx**」vs 密钥文件行「已加载密钥文件: **sjxnekdn**」——
**两名不同源**；`adb logcat` 补刀：`11:37:06 主密码解锁失败 KdbxInvalidCredentialsException`
（切库后表单驻留的仍是上一库的密钥文件，带旧因子输新库密码必败）。

KeePassDX 口径（竞品报告 §4.4）：密钥文件记忆＝库行上的 `keyfile_uri`——**记住的就是用户实际
保存的那个文件**，解锁现读，名字/位置/内容单一真相源，切库天然无串扰。本仓缺口：
① 生成型密钥文件 `saveTo` 成功后未把**保存位置**登记为本库记忆（要等解锁成功且用户手选）；
② 活动库切换时解锁页驻留密钥文件与「已自动载入」提示不复位（陈旧信息跨库残留）；
③ 因此恢复提示名与实际加载名可能不同源。

## 3. 整改

- **① 保存位置即登记**（`DatabasePickerKeyFileDeliveryController.saveTo` 成功路径，回写副本
  显示名之后）：`isRememberEnabled() && persistReadPermission(保存Uri)` 通过即
  `remember(dbId, 保存Uri, 实际显示名)`——**用户保存的那个文件**从此就是本库的已登记密钥文件
  （尊重「记住密钥文件位置」偏好与最小权限口径；未登记时副本仍在、恢复链不受影响）；
- **② 活动库切换复位**（`KeyFileSessionCoordinator.onActiveVaultChanged` 新方法）：清零驻留字节、
  复位来源与 `keyFileUserTouched`（否则会挡住新库恢复）、清空表单与一次性提示；
  `UnlockViewModel` 的 databases collect 改为**活动库 id 变化驱动**复位+按新库 `restoreRememberedKeyFile`
  （替代 init 时的一次性恢复——后者与切库不同步，正是两名不同源的根因；新切换取消在途恢复任务防互踩）；
- ③ 随 ② 自然成立：提示与密钥文件行同出一次恢复，恒同名。
