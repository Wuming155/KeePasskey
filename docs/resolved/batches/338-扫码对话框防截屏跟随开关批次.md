## 338.0 原文收录（`ACTIVE_ISSUES.md` 条目正文，原样剪切）

> ### ISSUE-P3-332 扫码取景对话框不跟随「禁止截屏与录屏」开关（用户直报）
>
> - **优先级**：P3（口径 / 体验一致性；关闭开关后仍被遮罩＝偏安全方向，无泄露面）
> - **背景**：设置页关闭「禁止截屏与录屏」（`flagSecureEnabled=false`）后，Activity 窗口经 `FlagSecureGuard`
>   「开关即生效」模型真实解除遮蔽，但 TOTP 扫码取景对话框（`TotpScanDialog`）仍被**无条件** `FLAG_SECURE`
>   遮罩、无法截屏。该强制遮罩自 `ISSUE-P3-71`（`SecureCaptureActivity.onCreate` 无条件施加）延续至
>   `ISSUE-P3-319`（迁为 Compose 对话框后硬编码 `SecureFlagPolicy.SecureOn`），**从未接入用户开关**；
>   而 `docs/security/Privacy-Policy.md` 承诺「解锁态随开关真实生效」。
> - **核实时间点**：2026-09-26
> - **核实方式**：用户真机直报「关闭截屏限制之后，在扫码的时候还是无法截屏」；同日经全仓 grep 与源码直读核实——
>   `TotpScanDialog.kt` 硬编码 `securePolicy = SecureFlagPolicy.SecureOn` 且 `ScanDialogWindowHardening` 内
>   `SecureDialogWindowEffect()` 无条件 `addFlags(FLAG_SECURE)`，两处均不读 `flagSecureEnabled`；
>   `SensitiveWindowHardeningTest` 以静态守卫锁定该无条件形态。
> - **整改依据（产品裁决）**：用户 2026-09-26 裁决「改为跟随防截屏开关」→ 登记 `PD-47`。
>   **边界（不随本条放宽）**：4 类敏感对话框（主密钥修改 / 子库凭据 / 附件预览 / 明文差异）仍**无条件强制遮罩**
>   （`SecureDialog` KDoc 口径不变，`SecureDialogFlagPolicyTest` 清单与断言一行不改）。
> - **涉及文件**：`app/src/main/java/com/keepasskey/app/ui/screens/edit/TotpScanDialog.kt`、`EntryEditPickers.kt`、
>   `EntryEditViewModel.kt`（注入 `SettingsRepository` 下传开关）、`app/src/main/java/com/keepasskey/app/security/SecureDialog.kt`
>   （`SecureDialogWindowEffect` 增开关参数，默认值保持既有语义）、`app/src/test/.../security/SensitiveWindowHardeningTest.kt`
>   （守卫改判为条件形态 + 上行链路接线）。
> - **验收标准（AC）**：
>   1. 开关关闭：扫码对话框窗口**不带** `FLAG_SECURE`（`securePolicy = SecureOff` 且包装不施加），可截屏；
>   2. 开关开启：仍强制遮罩（`SecureOn`），与整改前一致；反 overlay（`setHideOverlayWindows`）与遮挡触摸过滤
>      两路防护**不随开关变化**，始终施加；
>   3. 静态守卫改判：`SensitiveWindowHardeningTest` 锁定「`securePolicy` 由 `flagSecureEnabled` 条件驱动」+
>      「设置值经 ViewModel → Pickers → 对话框的上行链路已接线」，回退为无条件 `SecureOn` 即报红（反向反校留痕）；
>   4. 四类敏感对话框既有守卫（`SecureDialogFlagPolicyTest`）不放宽；全量 `test` 全绿 + `gate_readings.py` 7/7 PASS；
>   5. `PD-47` 登记，`实现约定与验证现状.md` §3.3 与相关 KDoc 同步，批次归档（`RESOLVED_LOG` §338）。

## 1. 整改内容

1. **`TotpScanDialog` 的 `FLAG_SECURE` 改为条件驱动**（`TotpScanDialog.kt`）：
   - 新增 `flagSecureEnabled: Boolean` 参数（**无默认值**——实参下传由编译器强制，漏传即编译红）；
   - `DialogProperties.securePolicy = if (flagSecureEnabled) SecureOn else SecureOff`——两支都显式写出：
     开 ⇒ 强制遮罩（与整改前一致）；关 ⇒ `SecureOff` 显式不遮罩。**不得**回退为省略参数的 `Inherit`
     （`ISSUE-P2-246`：`Inherit` 以宿主窗口为准、会清除本窗 flag，语义为「宿主状态镜像」而非「开关镜像」）；
   - `ScanDialogWindowHardening(flagSecureEnabled)` → `SecureDialogWindowEffect(flagSecure = flagSecureEnabled)`；
   - **反 overlay（`setHideOverlayWindows(true)`）与遮挡触摸过滤两层不动**——它们不防截屏，与本裁决正交。
2. **`SecureDialogWindowEffect` 增 `flagSecure: Boolean = true` 参数**（`SecureDialog.kt`）：
   - 默认 `true` ⇒ 4 类敏感对话框与 debug 宿主的**既有调用点零改动**、语义零变化（`SecureDialogFlagPolicyTest`
     按文件计数的 `SecureDialogWindowEffect()` / `SecureOn` 清单一行未改）；
   - `flagSecure=false` 时跳过 `addFlags(FLAG_SECURE)`（`addedByThisWrapper=false` ⇒ `onDispose` 同样不触碰
     flag），**遮挡触摸过滤不受该参数影响、始终施加**；`DisposableEffect` 键加入 `flagSecure`；
   - KDoc「与 `flagSecureEnabled` 开关的关系」一节补 `PD-47` 例外说明，四类强制遮罩口径原文保留。
3. **开关值上行链路**（`EntryEditViewModel.kt` + `EntryEditPickers.kt`）：
   - `EntryEditViewModel` 注入 `settingsRepository: SettingsRepository? = null`（沿用 `stringsProvider` /
     `databaseSession` 的「生产 Hilt 注入真现、纯 JVM 单测 null」既有模式），新增
     `flagSecureEnabled: StateFlow<Boolean>`（初值 `true` = fail-closed；`init` 内 collect 设置流刷新；
     null 仓库时恒 `true`，不因缺注入放宽遮罩）；
   - `EntryEditPickers` `collectAsStateWithLifecycle` 取值并以具名实参下传 `TotpScanDialog`。
4. **文档同步**：`产品裁决登记.md` 新立 `PD-47`（含不变边界与风险声明）；`实现约定与验证现状.md` §3.3
   增「扫码对话框例外面」条目；`SecureDialog.kt` / `TotpScanDialog.kt` KDoc 同批改写。

## 2. 测试资产与反向反校

- **守卫改判（只改不删）**：`SensitiveWindowHardeningTest` 既有 1 例改造 + 新增 1 例，无删除：
  - 例 1「两路防护」：`securePolicy` 断言由「含 `SecureOn`」收紧为「**同时**含 `SecureOn` +
    `SecureOff` + `flagSecureEnabled`」（回退无条件 `SecureOn` ⇒ 缺后两者，红；改回省略参数 ⇒ 三者皆缺，红）；
    包装接线断言由 `SecureDialogWindowEffect()` 收紧为 `SecureDialogWindowEffect(flagSecure = flagSecureEnabled)`；

## 5. 如实留痕

- **真机截屏效果未实测**：本批未在真机上执行「开关关 → 扫码页截屏成功 / 开开关 → 截屏全黑」的
  像素级对拍（`FLAG_SECURE` 运行时效果属手工冒烟项，同 `ISSUE-P2-245` / `P2-246` 的既有边界声明）；
  本批证成的是**接线与裁决内核**（静态守卫 + 行为用例 + 反向反校）。用户下轮真机验证即可核 AC① ②。
- **风险确认文案未改**：`sec_flag_secure_risk_message` 关闭前风险确认仍列举「密码明文、一次性验证码与
  通行密钥」，未点名「扫码取景」——按最小改动未扩面；文案本身已含「建议保持开启」总括，
  若日后认定须逐面点名另起条目处置。
- **守卫例 1 为多条件单断言**：三个子条件合在一条 `assertTrue`（先红者先报），反校 ① ② 分两轮跑
  以分别取到两条失败消息，非一次跑双红。
- **`SecureCaptureActivity` 归档口径**：`SensitiveWindowHardeningTest` KDoc 中对该已删类型的引用系
  历史背景描述（`ISSUE-P3-71` 起源），非现存代码引用，随本批改写为改判后口径。
