## 2. `ISSUE-P3-158`：TOTP 倒计时与跨周期重算的「全局 30 秒」口径

### 2.1 缺陷面（本批新登记，同批闭环）

**核实时间点与方式**：2026-09-17 逐处阅读 `VaultListTotpTracker` / `VaultEntryRowLayouts` /
`AuthenticatorScreen` / `EntryDetailCards` 四处 TOTP 呈现点，并与 `VaultEntryMapper`（投影层）、
`AuthenticatorViewModel`、`EntryDetailTotpTicker`（**均已按条目自身周期**）逐一对照。

**事实**：`period != 30` 的条目在三处呈现点被按全局 30 秒网格处理：

1. **列表徽标倒计时**（`VaultListTotpTracker.calculateCurrentRemainingSeconds`）：以
   `nowSec % 30` 计算剩余秒数 ⇒ 60 秒条目每 30 秒归零一次、相位错误；
2. **列表跨周期重算触发**（同文件 `previousRemaining in 1..remaining` 判据）：同样只在 30 秒边界判翻转
   ⇒ `period < 30` 且**不整除 30**（如 45 / 20）时**验证码会滞留到下一个 30 秒边界**，
   界面显示**过期验证码**——这是正确性缺陷，不只是观感问题；
3. **两处进度环分母**：`AuthenticatorScreen` 写死 `remainingSeconds / 30f`、
   `EntryDetailCards` 用 `TotpMiniGauge` 缺省 `totalSeconds = 30` ⇒ `period > 30` 时环比例 > 1。

§114 的边界声明只记了第 1 条的列表徽标形态（且记为「历史行为、本批未改」），**漏记**第 2、3 条
——本批按条目维护规则 1 一并登记。

### 2.2 整改

- **节拍通道改为下发刻度**：`VaultListTotpTracker.remainingSeconds: StateFlow<Int>` →
  `nowSeconds: StateFlow<Long>`（自 1970 起的整秒，仍由注入的 `nowMillis` 提供、仍走
  `WhileSubscribed` 订阅驱动、仍 `flowOn(dispatcher)`）——**§114 的性能契约逐条保留**（
  窄通道仍只有一个状态对象、仍只在徽标内读取、整页状态不随 tick 重建）；
- **倒计时由订阅方按条目自身周期现算**：`EntryTotpBadge` 收 `periodSeconds = entry.totpPeriod`，
  经 `OtpEngine.getRemainingSeconds`（全仓唯一换算入口）得出剩余秒数，进度环分母同取该周期；
- **跨周期判据改为「周期序号变化」**：`crossedAnyEntryPeriodBoundary` 用
  `entryPeriods()`（当前带 TOTP 条目的**去重周期**，`<= 0` 兜底为 30）逐周期判
  `previous / p != second / p`；首拍恒视为跨周期（保持「重新订阅必刷新一次」的既有语义）；
- **两处进度环分母改取条目自身周期**：`AuthenticatorScreen` 用 `item.periodSeconds`
  （`TotpCardItem` 新增该字段，ViewModel 已算出的 `period` 直接填入）、`EntryDetailCards` 传
  `totalSeconds = entry.totpPeriod`；`TotpMiniGauge` 内部对 `totalSeconds <= 0` 兜底（避免下游重复防御）；
- **预览缺省值**：`TOTP_PREVIEW_REMAINING_SECONDS = 30` → `TOTP_PREVIEW_NOW_SECONDS = 0L`
  （`30 - 0 % 30 = 30`），使预览 / 截图基线与改动前**逐像素一致**。

### 2.3 验证

- **行为面（虚拟时钟，确定性）**：`VaultListTotpTrackerTest` 新增 2 例、既有 2 例改用刻度换算后全绿——
  | 用例 | 断言 |
  |---|---|
  | `周期不等于 30 的条目按自身周期重算，不得漏在全局 30 秒网格上` | period=10：1..9 拍零重算、第 10 拍必重算；剩余秒数按 10 换算 |
  | `周期 60 的条目在 30 秒时刻不得重算` | period=60：第 30 拍**不得**重算（旧网格在此多算一次）、第 60 拍恰好重算一次 |
  | （既有）`周期内逐秒推进不得重算验证码，跨周期才重算` | 全 30 秒场景与改动前**逐拍等价** |
  | （既有）`无人订阅时不计时也不重算验证码` | 订阅驱动语义未变 |
- **接线面（源码文本守卫）**：新增 `TotpPeriodWiringGuardTest`（4 例）——UI 组件只能在设备侧渲染，
  宿主单测无法覆盖「是否传了周期」，故按仓内既有做法（`AutofillAuthResultWiringTest`）以源码文本守卫，
  并在断言前**剥离注释**（本批注释为解释动机刻意引用了旧写法「此前写死 30」）；
- **变异验证（逐条实测后逐字节还原）**：
  | 变异 | 实测结果 |
  |---|---|
  | **M1** 把重算判据退回全局 30 秒网格 | 两条新用例**同时红**：`30 秒时刻不是 60 秒条目的周期边界，不得重算 expected:<1> but was:<2>`、`period = 10 的条目必须在自身边界重算，否则列表显示过期验证码 expected:<2> but was:<1>` ✔ |
  | **M2/M3** 验证器页分母退回 `30f` + 列表迷你环退回缺省分母 | `TotpPeriodWiringGuardTest` **2 例红**：`不得再把进度环分母写死为 30（period != 30 时环比例错误）`、`迷你进度环分母必须取条目周期，不得沿用缺省的 30 秒` ✔ |

**边界（如实声明）**：无真机渲染验证——Compose 组件的实际呈现（环比例、文本）仍**未**在设备侧核对，
本批的 UI 侧证据是**接线守卫 + 编译期契约**，**不得**读作「已真机确认视觉正确」；
`period <= 0` 的库属异常输入，兜底为 30 秒（不改判据语义）。

## 3. `ISSUE-P3-159`：语料脚本环境自检的假失败

### 3.1 缺陷面

**核实时间点与方式**：2026-09-17 在本机（Windows / KeePassXC **2.7.12** / 中文界面）执行
`AGENTS.md` §5 记载的闸门 `python tools/kdbx-corpus/generate_corpus.py --check` ⇒ **exit=3**，
报文为「`keepassxc-cli` 不支持 `db-create` 子命令（rc=1）」并给出**误导性**指引
（「请先安装 KeePassXC 官方 CLI」）——而同一台机器上 `db-info` / `ls` / `export` **全部可用**。

**根因**：`probe_cli` 以 `keepassxc-cli db-create --help` 的**退出码**判定子命令可用性；
该版本对 `db-create --help` / `-h` / `-?` **一律**先打印用法再以 rc=1 退出
（报文「缺少位置参数。」⇒ 位置参数校验早于选项解析），故装了 CLI 的机器上 `--check` **恒失败**。

### 3.2 整改与验证

判据改为**顶层命令清单**：`keepassxc-cli --help`（rc 恒 0）的文本中必须出现 `db-create`
（命令名不随界面语言本地化），开关探测只解析 `db-create --help` 的用法文本、**不再看退出码**。

- 修复前实测：`--check` **exit=3**（即负向对照，报文把已安装的 CLI 判为未安装）；
- 修复后实测：**exit=0**，`版本：2.7.12` / `db-create 可见的 KDF 相关开关：--decryption-time` /
  两个落位目录可写（与 `README.md` 对该命令的描述一致：探测存在性、版本与 `db-create` 可用性）。

## 6. 过程留痕

1. **首个用例断言写错（非实现错）**：新增的两条 tracker 用例初版断言「订阅后首拍即重算」，
