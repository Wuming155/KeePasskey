**附带前提更正（就地修正，不改条目结论）**：原条目称「连同 `.bak` 也不在保护之列」。现查实
`<库>.kdbx.bak` 是 `AtomicFileWriter` 的**滚动备份**（保存时按偏好生成，默认开启；`MainApplication`

该差异**不改变**「私有库移除即永久删库」的结论，但影响边界陈述——如实记于 §9。

## 4. AC③ 的裁决：维持「移除即删除」，把它说清楚（落 `PD-17`）

**裁决 A**。理由（**技术事实**，非偏好）：

1. **应用私有库不存在「只移除关联」这个状态**。列表由 `buildDatabaseList` **按目录扫描** `filesDir/*.kdbx`
   构建，判定只认文件本身；登记表里根本没有内部库的条目。若「移除」不删文件，则下一次列表刷新
   该卡片**必然原样回来**——这不是「移除」，而是「按了没反应」。
2. 走方案 B（改成不删文件）就必须**新增一层「已忽略文件」持久化 + 与目录扫描的差集逻辑**，
   且默认动作变成**静默无效**：用户以为移除了、其实只是被隐藏。把破坏性动作藏到第二层入口，
   危险并未减少（真删仍在），却新增了一个「看起来成功其实没动」的默认路径。
3. **本项的根因是「说的和做的不一样」，不是「删了文件」**。对私有库而言删除是让它从列表消失的
   **唯一**动作，故正确处置是照实说（红色危险按钮 + 指名文件 + 明示不可恢复），
   而不是把动作改成不生效。

口径、边界与重开条件见 [`../../architecture/产品裁决登记.md`](../../architecture/产品裁决登记.md) `PD-17`。

## 5. 判据与删除动作的单点化

| 环节 | 实现 | 说明 |
|---|---|---|
| 存储类型 → 真实对象 | `ui/model/VaultRemovalKind.of(vaultPath, filesDirPath)`（新增） | 纯路径运算、**无文件系统 I/O**；「该库文件的父目录**就是** `filesDir`」⇒ `PRIVATE_FILE`，其余一律 `EXTERNAL_LINK`（含 `content://` / 应用外绝对路径 / 用户填的裸相对名 / 远端 URL） |
| 兜底方向 | `filesDirPath` 为 `null`/空 ⇒ `EXTERNAL_LINK` | **判不出就不删**：反过来的错误（承诺不删却真删）正是本项要根治的形态 |
| 真实对象 → 文案与动作 | `ui/screens/database/VaultRemovalPresentation.of(database, filesDirPath)`（新增） | 一份投影同时给出标题 / 正文（含被删文件名）/ 确认按钮 / `destructive`（是否红底危险按钮） |
| 文案与动作 → 界面 | `DatabasePickerScreen` 只调用上面这一个函数，并把 `confirmation.kind` **原样**下行 | 界面**不再**自行比较路径（守卫机检 `parentFile` 零命中） |
| 真实对象 → 是否删文件 | `VaultRepository.removeDatabase(id, kind)` 新增 `kind` 形参；`VaultLifecycleCoordinator` 只在 `kind == PRIVATE_FILE` 时执行 `File(filesDir, id).delete()` | 删除判据与文案判据**同源**；`kind` 与 `id` 不一致时最坏结果是「该删的没删」（卡片仍在），**不会**反向变成「不该删的删了」 |
| 注册表条目匹配 | 由 `it.id == id \|\| it.path == id \|\| it.name == id` 收紧为 `it.id == id \|\| it.path == id` | 外部登记的 `name` 只是展示名，与其它库文件名撞车时会摘掉**另一个库**的登记（同函数内相邻缺陷，本批一并收紧并留痕） |

## 9. 如实声明（边界与未验证项）

1. **`.bak` 仍留在沙盒内**：删除只作用于 `<库>.kdbx` 本体；`AtomicFileWriter` 生成的
   `<库>.kdbx.bak`（滚动备份，属用户数据）**不随删除移除**，且因扩展名不是 `.kdbx` 而不会出现在
   库列表。本批**有意不删**它（删它只会扩大破坏面），也**不**在界面文案里把它写成恢复承诺——
   应用内无任何入口可读回该文件，普通用户实际取不回来。该残余已如实记于此，不登记为限界项
   （它不是「无法整改的风险」，而是「刻意保留更少破坏」的选择）。
2. **一条误判不可能、但「该删没删」可能**：`kind` 由界面按条目 `path` 判定，若某条目的 `path`
   与其实际落点不符（登记表被外部改写），最坏结果是**该删的没删**（卡片仍在列表里），
   **不会**反向变成删错对象——这是本批刻意选择的方向。
3. **真机只在 Android 17 / API 37 的 Redmi 4X 上取证**：`android layout` 一度返回
   `Unrecognized response from instrumentation server`（设备处于 Dozing 且通知栏持焦时），
   `KEYCODE_WAKEUP` 后恢复；`uiautomator dump` 在该 ROM 上被 `SIGKILL`（rc=137），
   故界面取证全程只用 CLI 的 `layout`。
4. **未覆盖的相邻面**：① 「自选位置（系统文件选择器）」建库的库被移除时的弹窗（其 `id` 是
   `content://` uri ⇒ 判为外部库，由 §7 的类型穷举与 §6.2 的外部实测共同覆盖，但**未**在真机上
   对该来源单跑一遍）；② 列表卡片图标（`content_desc=删除`）未随类型区分——本批只改弹窗，
   卡片入口保持原样；③ 中文长文件名的正文换行观感未取证（本批测试库名为 ASCII）。
5. **本批未触** `crypto/src/main/rust/**`、`jni_bridge_ext.rs` 与任一原生绑定，亦未新增 / 修改
   `*/src/androidTest/**` ⇒ 按「测试资产纪律」②**无设备侧必跑项**；该结论不豁免 §6 的手工冒烟。
