## 为什么这样拆

- 原先的整册文件达数百 KB / 上千行，难以逐条引用与审阅；拆为**一批次一文件**后每份自成一体。
- **索引只做引用、不复制正文**，避免同一结论在两处漂移。
- 例外：单批次本身即长篇（如 §42 234 行、§43 195 行、§49 190 行、§27 181 行），
  **保持整节完整**而不按小节切碎——批次叙事被切断会降低可读性。

## 维护规则

1. **新增批次**：在 [`../RESOLVED_LOG.md`](../RESOLVED_LOG.md) 索引末尾加一行，并在 `batches/` 新增
   `<NN>-<中文短名>.md`（编号零填充两位，便于排序）。
2. **编号不复用**：§ 编号全局递增；当前最大为 **§306**，下一批次从 **§307** 起。
  > 本行是「当前最大编号」的**唯一**维护处（`RESOLVED_LOG.md` 的索引标题与 `docs/README.md` 的份数均已改为现查，
  > 不再复制该可变事实）；**每批同步本行**——历史上曾两度失效，见 §152。
  > **机检（§218 立规，§282 扩判据，强制）**：本行与索引完整性由
  > `python tools/doc/check_resolved_index_sync.py` 机检（①正文→分册 ②分册→正文或豁免 `{§42, §43}`
  > ③本行==正文最大编号 ④分册不得重登 ⑤正文→`RESOLVED_LOG` 且不得重登）。
  > **改本文件 / 任一 `BATCH_*.md` / 新增批次后必跑**，退出码 1 即不一致。
  > 立规缘由：2026-09-19 实际发生「`BATCH_158_PLUS.md` 止于 §202 而正文已有 §203~§215」
  > 与「本行仍写 §202」两处不同步，而 `check_md_links.py` 只校验链接**可达**、**不校验漏登**。
   > **滚动分册（2026-09-15 起）**：分册文件名固定（`BATCH_58_PLUS.md` / `BATCH_158_PLUS.md`），**不再随批次增长改写**；触顶 100 数据行即另立下一册（§158 已按此立分册 05）
   > （此前每新增一批即需重命名一次，属无谓改动）。其覆盖范围以册内实际行数为准，**超过 100 行时另立分册 05**。
   > **注（2026-09-15 已闭环）**：`AGENTS.md` §1 / §6 与 `ACTIVE_ISSUES.md` 曾引用 §68
   > （ISSUE-P3-116 闭环）而正文未落本目录——该缺口已由 `ISSUE-P3-129` ① 收口，
   > 正文见 [`batches/68-退出前清理易失缓存批次.md`](batches/68-退出前清理易失缓存批次.md)。
3. **只搬迁、不改写**：确需更正时**新增更正节**并保留原文（如实留痕）。
4. **回溯**：拆分前的完整单文件版本见 git **`a144d21`**：
   `git show a144d21:docs/RESOLVED_LOG.md`（含当时的三册全文）。
