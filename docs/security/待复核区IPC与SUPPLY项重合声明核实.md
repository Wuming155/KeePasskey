### 1.3 判定口径

- **重合声明成立**：该编号所述机制已被其指向的既有条目**完整覆盖**（含同批联动项），无独立残余。
- **部分成立**：机制的主要部分已被覆盖，但存在**该条目未覆盖、且未被其它条目/登记表承接**的残余。
- **不成立**：指向的条目与所述机制无关，或该条目裁决与机制冲突。
- **独立残余**：不以「是否已闭环」为标准，而以「**是否有受跟踪落点**」为标准——已闭环但残余仅写在批次正文或
  代码 KDoc、未进 `docs/architecture/已知工程限界.md`（登记纪律「未登记即视为未处理缺陷」）者，仍计残余。

### 3.1 `R-1`：`IPC-11` 族在 CM 通道的 `UNBOUND` 越权面（未进限界登记表）

- **缺陷**：`CredentialManagerPackageBindingGate` 的 `UNBOUND` 分支对**从未绑定过**的包名
  **退回「条目 `android://` 绑定包名 == 调用包名」的纯字符串放行**
  （`CredentialManagerPackageBindingGate.kt:24-33,46,69-70`）。即：若某条目带 `android://<pkg>` 绑定
  （**存量为导入库 / 手工建库 / 其它管理器迁入的条目**），而 `<pkg>` 从未经本应用的保存 / 注册流程绑定过，
  则同 `applicationId` 的侧载应用在 **CM 通道**仍可命中——这正是 `IPC-11` / `P2-46` / `P2-83` 所指的越权形态。
- **为何不能简单 fail-closed（须连同结论一起读）**：§82.2 的论证成立——CM 通道**没有自动填充那样的选择器中立面**
  （候选为空则用户在系统 UI 上既看不到任何东西、也无处授权），且「首次填充即绑定」会把**首个到来的调用方**
  （可能是侧载顶替应用）记成参照，致真应用**永久失效**。故这是**有理由的取舍**，不是遗漏。
- **残余的实质**：该取舍已在**代码 KDoc**（`:26-33`）与**批次正文**（`82-…批次.md:37-40`）**逐字声明**，
  但 `docs/architecture/已知工程限界.md`（本仓**唯一**的已接受限界登记表，判「是否为已知限界」只认此表）
  **未登记**。按登记纪律「**未登记即视为未处理缺陷，不得以『架构如此』口头豁免**」，
  该残余目前处于「已论证但未登记」状态。
- **建议严重度**：**P3 / INFO**（触发前提 = 条目带 `android://` 绑定且目标包名从未经本应用保存 / 注册流程绑定；
  属 `P2-83` 同期**已论证的取舍**，非本轮新增的可利用面）。
- **建议处置（二选一，由主控裁决）**：① 在 `已知工程限界.md` 新增一条（事实 / 边界 / 依据 / **解除条件**——
  解除条件可写「CM 通道获得不依赖首次绑定的中立授权面后，`UNBOUND` 改为 fail-closed」）；
  或 ② 单开条目跟踪。
- **本轮未做**：不改代码、不改限界登记表（均在本轮禁改面内或由主控按纪律处理）。
