## 1. 结论与审计边界

确认 **18 项缺陷：Critical 0、High 8、Medium 9、Low 1**。没有确认远程无条件解密数据库、无认证绕过 Keystore 或普通应用直接获取任意凭据的 Critical 漏洞；这不是不存在此类漏洞的证明。High 主要是凭据可用性、持久化错误、同步竞态和数据丢失风险，不能因为构建/既有单测通过而忽略。

这是全项目跨模块、按安全边界和核心数据流展开的第一阶段审计，覆盖下列 18 个面；不是逐行穷尽全部文件、设备渗透测试或全型号兼容认证。生产调用链、关联模型、错误/取消分支、既有测试与产品裁决交叉检查；用现有编译类和临时合成对象补证六项关键发现。没有向真实 RP、云端或用户数据库发起写操作，也未安装或卸载设备应用。

**证据等级**：

- **运行补证**：宿主直接调用当前编译的生产类，合成数据、临时库；可以确认被调用逻辑，不外推为 Android 原生、系统回调或官方客户端互操作实测。

- **需要进一步验证**：证据不足的假设列于 §6，不计入 18 项确证缺陷，也不作为已确证漏洞登记。

## 2. 项目架构理解

### 2.1 模块及信任边界

```text
app ──> database ──> crypto ──> core
 ├────> sync ─────────────────> core
 └────> crypto
```

| 模块 | 主要职责 | 审计关注的边界 |
|---|---|---|
| core | 不可变树模型、ProtectedString、二进制来源、Result、日志及通用格式常量 | 模型不可变不代表内部秘密数组不可变；附件借用/拥有语义和共享擦除 |
| crypto | 组合密钥、Argon2/AES-KDF、CBC/流密码、Rust/JNI、Passkey 签名及强度评估 | 输入接受域、宿主兜底/原生等价、分配/派生/擦除和 JNI 绑定 |
| database | KDBX 头部/认证块/内层头/XML、会话、历史、原子写盘 | 解锁及保存状态机、保存提交点、凭据轮换、异常和取消 |
| sync | WebDAV/S3、缓存、ETag 乐观并发、三方合并与防回滚辅助 | 不信任远端明文语义；加密文件完整性与内容新鲜性是两件事 |
| app | Compose/Hilt/Flow、库仓库、设置、生命周期、Keystore、生物识别、Autofill/CM、平台入口 | 用户意图如何变为持久化事务；调用方绑定、活动页面与进程级安全守护 |

分层总体合理，未发现需要反向依赖才能修复这些问题的架构障碍。但持久化规则散在仓库、设置和会话入口，导致保护旁路与错误结果丢弃；同步内容判据与合并字段词汇表分散，产品新写入口出现后没有同步更新。这比文件行数是否合规更重要。

### 2.2 数据库主流程与状态

- **选择/创建**：库注册表记录路径或 SAF URI，创建向导交给 VaultLifecycleCoordinator 和 DatabaseSession。文件存私有目录或经显式授权的提供方；新建本应与覆盖操作区分，当前有 AUD-06。
- **解锁**：口令 CharArray/密钥文件 ByteArray→组合密钥→KDF→头部 HMAC→认证块→解密/解压→内层头/XML→KdbxDatabase 树。读取 KDBX **4.x**；major 小于 4 被拒绝，不能以旧文档“3/4”推定支持 3.x。
- **会话**：CLOSED / LOCKED / OPENED / DIRTY；缓存主凭据用于保存。DatabaseSession 的 Mutex 保护会话操作；凭据缓存另有锁，锁观察者驱逐派生状态。树的 copy 可能仍共享 ProtectedString 或附件资源，旧实例擦除需按所有权处理。
- **编辑/保存**：合并 UI 与旧条目→形成历史→会话 DIRTY→重新生成随机种子、盐、IV 和内流密钥→全库序列化→文件写入/备份→OPENED。普通文件使用临时文件、同步和替换；备份不是全部失败窗口的事务恢复日志。SAF 写回受提供方能力限制。
- **锁定/进程死亡**：自动锁守护在 Application 初始化，独立 Autofill/CM 冷启动入口也覆盖；主动锁会清凭据、树及附件来源。冷启动清理附件缓存、对账剪贴板、处理异常关闭标记。操作系统杀进程不会可靠执行 finally/锁回调，持久数据只能以已提交磁盘为准；没有把主密码写入 SavedState 作为恢复手段。

### 2.3 同步与凭据交付流程

同步采集本地树/文件快照，与上次缓存和远端元数据比较；无冲突条件提交，有分歧下载并三方合并，采纳后落地和前移基线。SyncSessionState 的 Mutex 串行同步流程，但普通编辑不取该锁。现有采纳 CAS 防止下载等待期间覆盖用户新编辑；**上传成功路径仍有不同的快照错配**（AUD-03）。

Autofill 根据 AssistStructure、PSL/域名、可信浏览器与应用关联筛选候选，锁定时用受保护 Activity 解锁/选项；CM 基于系统 CallingAppInfo、证书、调用方绑定及 DAL 校验 RP 归属，再回传口令或 Passkey 结果。Passkey 私钥按 KPEX/PKCS#8 兼容字段存库，PRF/计数等附属信息仍需与持久化结果一致。签名成功不是计数已持久化，注册 JSON 成功不是私钥已安全落盘（AUD-02）。

## 3. 安全模型理解

### 3.1 保护目标与假设

保护未解锁数据库的机密性/完整性，限制解锁态凭据交付给正确调用方，降低明文驻留，并尽可能保证编辑与同步不丢数据。合理对手包括：拿到库文件的离线攻击者、普通恶意 Android 应用、不可信云端/内容提供方、网络中间人，以及极端时序和系统回收。

系统应用隔离、系统 CA、Android Keystore 和系统认证路径属于依赖的信任基础；不承诺对 root、运行时注入或已控制解锁进程的攻击完全防护。PD-45 已移除完整性/Hook 检测，不能把历史报告中的检测器当成现行门控。

KDBX 头部/认证块保护的是文件真实性与完整性。[KeePass 官方格式说明](https://keepass.info/help/kb/kdbx_4.html)明确区分头部认证与数据块认证；它不证明云端版本最新、不证明并发同步基线正确，也不阻止持有库密钥的一方形成另一份有效库。防回滚辅助状态不是强服务器一致性协议。

### 3.2 当前存在的防护

- 密码与密钥主要使用可清理数组；ProtectedString 使用进程内存保护与受控读取，Rust 敏感内核使用 Zeroizing/RAII。日志封装限制 release 敏感消息。
- KDBX 读取校验头部 SHA/HMAC、块 HMAC；KDF 参数、XML 深度/节点/体积等有防御性边界。保存更换随机材料，防止重用既有库头派生上下文。
- 快捷解锁使用 Keystore AES-GCM 密钥与每次强生物识别认证，优先 StrongBox、退 TEE；软件/未知安全等级需按策略获得用户明确降级许可。[Android Keystore 官方说明](https://developer.android.com/privacy-and-security/keystore)是硬件等级及密钥使用授权语义的依据，不能把宿主测试当成设备硬件证明。
- 生物识别新载荷仅封存密码，密钥文件可来自加密的本库私有副本/记忆恢复；它便利地代持第二因子，不代表原密钥文件一定需要每次在外部呈现。
- 平台禁明文网络，OkHttp TLS-only，系统 CA 信任，无自定义跳过证书验证；DNS/连接期 SSRF 守卫，显式配置的内网 HTTPS 端点有受控豁免。
- Manifest 禁系统备份并列出迁移排除；Credential/Autofill/Accessibility 服务虽 exported=true，但由对应系统绑定权限保护，不能只据 exported=true 判漏洞。凭据落地 Activity 大多不导出；外部开库入口限 content URI 并经确认。
- 剪贴板敏感标记、超时/后台/熄屏清理与冷启动对账；受保护窗口、遮挡触摸过滤及锁观察者清理展示状态。防截屏的实际行为以用户开关为准，见 AUD-17。

这些是审查到的防护措施，**不是所有异常路径已无遗漏的安全认证**。

### AUD-01 解绑密钥文件后，下一次保存重新引入旧因子

- **ID / 登记**：AUD-01 / ISSUE-P1-589。
- **严重程度**：High。
- **所在文件和代码位置**：[SessionCredentialCache.kt](../../database/src/main/java/com/keepasskey/database/session/SessionCredentialCache.kt)：106–113；[SessionPersistence.kt](../../database/src/main/java/com/keepasskey/database/session/SessionPersistence.kt)：92、187–194。
- **问题描述**：双参换密接口的 null 表示解绑，但缓存只在新密钥文件非 null 时替换。第一次重加密按 null 生成，缓存仍保留旧文件；随后的保存恢复使用旧因子。
- **触发条件**：密码 + 密钥文件库执行解绑，再保存条目、设置或同步。
- **潜在后果**：用户在看到解绑成功后删除旧文件，之后可能再也打不开数据库；界面意图与磁盘保护因子不一致。
- **修复建议**：无条件按双参意图轮换密钥文件缓存并擦除旧因子；覆盖解绑后第二次保存、导出缓存为空、失败回滚和仅密码重开。
- **判断可信度**：高；宿主现有生产类临时库复现。
- **判断依据及边界**：解绑第一次产物仅密码可开；缓存仍有旧文件；第二次保存成功后仅密码不可开、旧文件加密码可开。现有 ChangeCredentialsKeyFileRebindTest 只检查第一份解绑产物。

### AUD-02 Passkey 落盘失败仍向注册/断言调用方返回成功

- **ID / 登记**：AUD-02 / ISSUE-P1-590。
- **严重程度**：High。
- **所在文件和代码位置**：[PasskeyEntryCoordinator.kt](../../app/src/main/java/com/keepasskey/app/data/repository/PasskeyEntryCoordinator.kt)：147–152、171–188、301–317；[PasskeyCreateActivity.kt](../../app/src/main/java/com/keepasskey/app/passkey/PasskeyCreateActivity.kt)：339–366；[PasskeyAssertionActivity.kt](../../app/src/main/java/com/keepasskey/app/passkey/PasskeyAssertionActivity.kt)：274–303。
- **问题描述**：创建、替换及签名计数器更新在 persistSession 返回 Failure 后只写日志，继续返回条目/新计数。Activity 用该返回值回传系统成功。
- **触发条件**：磁盘满、提供方写失败、外部漂移保护拒绝保存；随后锁库或进程死亡。
- **潜在后果**：RP 已注册的私钥没有持久化，凭据永久失效；签名计数重启后回退，可能被 RP 当作克隆风险。不能用内存原子计数证明落盘成功。
- **修复建议**：在系统成功回执前保证持久化完成并传递 Failure；设计失败时的内存回滚/重试。注入写盘失败验证注册不成功、计数器失败拒签及用户反馈。
- **判断可信度**：高；失败分支与 Activity 成功调用链静态确证，尚未连接 RP 动态验证。
- **判断依据及边界**：现有签名计数并发测试验证 32 次内存更新，其持久化注入恒为 Success，未覆盖此失败链。

### AUD-03 上传结束用活动树前移基线，把未上传的新编辑当成已同步

- **ID / 登记**：AUD-03 / ISSUE-P1-591。
- **严重程度**：High。
- **所在文件和代码位置**：[SyncCycleCommitPaths.kt](../../app/src/main/java/com/keepasskey/app/sync/SyncCycleCommitPaths.kt)：48、114–115；[SyncCycleRunner.kt](../../app/src/main/java/com/keepasskey/app/sync/SyncCycleRunner.kt)：285–286、345–351；[SyncContentChangeDetector.kt](../../app/src/main/java/com/keepasskey/app/sync/SyncContentChangeDetector.kt)：59–65；[SyncCycleSetup.kt](../../app/src/main/java/com/keepasskey/app/sync/SyncCycleSetup.kt)：196–205。
- **问题描述**：上传的是周期快照 A，成功分支却把当时 databaseFlow 中的树记为 lastSyncedDb。同步互斥锁不能约束普通编辑；长任务保护只延迟自动锁定。
- **触发条件**：网络上传 A 等待期间，编辑并保存 B；上传后补存当前 B，然后设 B 为已同步基线。
- **潜在后果**：实际远端/缓存仍为 A，变化检测却认为 B 未变，后续继续复用 A；若另端产生 C，下一周期还可能把 B 作为无本地修改而接管 C。B 的不上云链明确，最终覆盖需要该后续交错。
- **修复建议**：基线对应实际上传字节与树，附带同版本凭据和检查点；周期完成只确认该快照。对上传暂停→编辑 B→完成→再次同步及另端 C 做确定性交错验证。

- **潜在后果**：两个系统保存入口串用后一请求的账号/口令/目标上下文；尚未证明实际跨应用凭据泄露。
- **修复建议**：每请求唯一身份及生命周期回收，验证双请求并存和进程重建不串凭据；设备端点击交错待验证。
- **判断可信度**：高（令牌身份及平台语义）；设备双请求交错需要进一步验证。
- **判断依据及边界**：Android 官方 PendingIntent 文档明确 extras 不作为身份差异，并说明 FLAG_UPDATE_CURRENT 对 IMMUTABLE 仍有效。

### AUD-16 DAL 接受重定向来源及非 200 成功响应

- **ID / 登记**：AUD-16 / ISSUE-P2-604。
- **严重程度**：Medium。
- **所在文件和代码位置**：[DalVerifierModule.kt](../../app/src/main/java/com/keepasskey/app/di/DalVerifierModule.kt):75-82 使用默认跟随重定向的同步客户端；[DigitalAssetLinksVerifier.kt](../../app/src/main/java/com/keepasskey/app/passkey/DigitalAssetLinksVerifier.kt):143-164 仅检查最终 isSuccessful，未核验原地址直返 200 或 Content-Type。。
- **问题描述**：DAL 验证把共享同步客户端的最终 2xx 响应当作原 RP 的声明，忽略声明获取的来源与状态约束。
- **触发条件**：assetlinks 端点返回重定向，最终 JSON 被当作原 RP 声明；若该端点有可控跳转则削弱域名授权边界。协议偏差确认，真实域名可利用条件未验证。
- **潜在后果**：不符合 DAL 信任约束。只有原端点本身存在攻击者可控跳转等前提时，才能推导冒用域名授权；当前未证明真实域名可利用。
- **修复建议**：DAL 专用客户端禁止重定向，严格 200 与声明媒体类型；测试跨主机、同主机重定向和 201/206。依据 Google 官方声明位置规则。
- **判断可信度**：高（协议偏差及依赖默认行为）；利用前提需要进一步验证。
- **判断依据及边界**：缓存中的 OkHttp Android 5.5.0 官方 sources.jar：commonJvmAndroid/okhttp3/OkHttpClient.kt:599 的 followRedirects=true。生产工厂未改写；Google DAL 要求原端点 200、不跟随 301/302、application/json。JShell 客户端探针因 AAR classpath 缺失失败，未当成运行证据。

### AUD-17 隐私政策与旧裁决表承诺了已移除的锁定态强制防截屏

- **ID / 登记**：AUD-17 / ISSUE-P3-605。
- **严重程度**：Low。
- **所在文件和代码位置**：`docs/security/Privacy-Policy.md:99`；`docs/architecture/产品裁决登记.md` PD-47 / PD-48；[FlagSecurePolicy.kt](../../app/src/main/java/com/keepasskey/app/security/FlagSecurePolicy.kt)：23。
- **问题描述**：现行代码按归档批次 411 用户裁决，全程服从防截屏开关；政策与旧裁决表仍声称锁定态强制遮蔽。
- **触发条件**：用户关闭防截屏但依据政策以为锁定态仍受强制保护。
- **潜在后果**：隐私承诺与实际配置不一致，造成错误安全预期。运行时开关行为属于已裁决产品选择。
- **修复建议**：同步政策与裁决表，明确批次 411 对 PD-47/48 的替代关系；检查发布页同类承诺。
- **判断可信度**：高；源码、政策和当前裁决对照。
- **判断依据及边界**：不建议悄然恢复用户已明确取消的强制模式；问题是文档事实失真。

### AUD-18 Autofill 保存密码数组在等待解锁阶段缺少取消清理

- **ID / 登记**：AUD-18 / ISSUE-P2-606。
- **严重程度**：Medium。
- **所在文件和代码位置**：[PasswordSaveActivity.kt](../../app/src/main/java/com/keepasskey/app/passkey/PasswordSaveActivity.kt):70 在 requireUnlocked 前构造口令数组，而清理在后续 startSave 的 finally（:140）；未解锁即退出不会进入该 finally。。
- **问题描述**：保存协程的 finally 只覆盖解锁成功后的流程，之前建立的口令数组缺少取消回调所有者。
- **触发条件**：用户取消解锁或 Activity 关闭，捕获的口令数组未显式擦除，仅等待 GC。
- **潜在后果**：取消创建凭据后口令数组等到 GC 才释放，显式擦除承诺有缺口。平台原生 String 的固有限界另列，不重复作为新问题。
- **修复建议**：把数组所有权覆盖整个解锁等待阶段，取消/销毁/成功移交均闭环；验证取消解锁和 Activity 重建不会泄漏或双重清理。
- **判断可信度**：高（源代码生命周期/所有权缺口）；实际设备影响需要进一步验证。
- **判断依据及边界**：CredentialUnlockPresenter 只接收 onUnlocked，无取消载体清理回调；Activity startSave finally 未涵盖等待期间。

## 8. Critical / High 优先级、深入检查与发布条件

**Critical：本阶段没有确证项。** 不代表可直接正式发布。建议先处理 High 事务和数据丢失问题：

1. **AUD-01 / 05 / 07**：保护因子与可重开性。先确保解绑/换密/参数变更在成功、失败、取消、锁定后都能以明确的凭据重开。
2. **AUD-02 / 04 / 14**：定义落盘成功回执及写失败恢复。Passkey注册不可将只在内存的私钥报告成功，自动锁定不能把唯一新版本无提示销毁。
3. **AUD-03 / 08 / 09**：校正同步快照身份与完整内容语义；保住上传等待中新增的编辑和独立远端有效期设置。
4. **AUD-06 / 13**：同名新建及所有持久化入口的覆盖保护。普通编辑已有的漂移保护不能被设置/换密入口旁路。

建议继续深入的模块按优先级为：**database/session 与 app/repository/settings**（提交点、取消、回滚、漂移统一）；**app/sync 与 sync/merge**（快照绑定和字段覆盖）；**app/passkey/autofill**（持久化成功、DAL与系统令牌生命周期）；**biometric/Keystore 与附件内存来源**（所有权、失效、进程死亡、Native资源）。

正式发布前应具备/补齐的是可靠的失败保存恢复、统一覆盖保护、可执行的跨步骤故障验证和真实平台发布验证；并不建议趁审计擅自添加已被拒绝的PIN、AutoType执行、完整性检测等功能。现有导出/备份入口的存在不能替代恢复成功率测试。建议在上述 High 收敛后，以干净设备测试数据执行 V-03/04/06/08，再做生产服务兼容与发布包核验。
