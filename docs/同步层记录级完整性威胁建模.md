# 同步层记录级完整性威胁建模（ISSUE-P3-77）

> **文档定位**：对「密文跨记录 / 跨上下文置换」威胁的正式威胁建模与结论。
> **立规缘由**：参考项目 Monica 采用 mdbx 的 `MDBXAE1\0 || commitment || nonce || ciphertext`
> 记录级密钥承诺（key commitment）抗置换攻击，本项目需判定是否跟进。
> **核实基线**：2026-09-12。结论为**明示接受残余风险、不改动 KDBX 字节布局**（论证见 §5）。

---

## 1. 范围与非目标

- **目标**：判定「跨记录 / 跨上下文密文置换」在 KeePasskey 威胁模型下的实际可利用性，
  以及既有 KDBX 头部 / 块 HMAC 与同步层 MAC 的覆盖边界；据此决定是否需要引入记录级承诺。
- **非目标**：本地文件级攻击者（其可 Hook 进程、读进程内存，本就不在任何纯文件完整性方案的可防范围内）。

---

## 2. 资产与信任边界

| 项 | 界定 |
|---|---|
| 核心资产 | 用户库（KDBX4 单文件：条目 / 分组 / 附件 / 历史）、主凭据、通行密钥凭据 |
| 设备本地 | **半可信**：Assume Breach——同机恶意应用可有限篡改本地文件，但**不可获得** Keystore 内不可导出的 HMAC 密钥与进程内主密钥 |
| 云端（WebDAV / S3） | **不可信**：Assume Breach——可读、改、替换、重放、删除远端任意字节 |
| 攻击者能力上界 | 拥有远端全部密文，可任意操纵；**不具备主密钥与由其派生的任何密钥** |

---

## 3. 既有完整性机制与覆盖边界

### 3.1 KDBX 头部

- KDBX4 头部由**头部 SHA-256**（主密文前 32 字节）与**头部 HMAC**共同认证，覆盖含
  `EndOfHeader` 数据的完整头部，认证根为主密钥派生。
- 落点：[`KdbxHeader.kt`](../database/src/main/java/com/keepasskey/database/file/KdbxHeader.kt)
  （字段 0 注释明确「头部 SHA-256 / HMAC 覆盖含该数据的完整头部」）。

### 3.2 KDBX 块 HMAC

- 每块摘要 = `HMAC-SHA256_{SHA-512(LE64(index) ‖ hmacKey64)}(LE64(index) ‖ LE32(size) ‖ data)`，
  块密钥**把块索引并入密钥**；终止块（`size=0`）单独认证。
- 因此块**不可重排、不可跨位置替换、不可截断**；流式校验「边解密边校验，错误尽早暴露」，
  篡改一律 fail-closed（`KdbxInvalidCredentialsException` / `KdbxCorruptFileException`）。
- 落点：[`BlockHmac.kt`](../database/src/main/java/com/keepasskey/database/file/BlockHmac.kt)、
  [`HmacBlockStream.kt`](../database/src/main/java/com/keepasskey/database/file/HmacBlockStream.kt)。

### 3.3 同步层防回滚

- 设备侧维护「已见内容摘要链」（`current` + 有界 `recent` ≤ 32 条），状态文件由
  **AndroidKeyStore 内不可导出 HMAC 密钥**认证；远端返回**设备侧曾接受过的历史版本**即判
  `ReplayDetected` 并拒绝写入缓存与基线。
- 状态文件 MAC 校验失败 → 按「无历史」处理（fail-safe，不产生误报回退）。
- 落点：[`SyncRollbackGuard.kt`](../sync/src/main/java/com/keepasskey/sync/engine/SyncRollbackGuard.kt)、
  [`SyncIntegrityMac.kt`](../sync/src/main/java/com/keepasskey/sync/engine/SyncIntegrityMac.kt)、
  [`KeystoreSyncIntegrityMac.kt`](../app/src/main/java/com/keepasskey/app/sync/KeystoreSyncIntegrityMac.kt)。

## 4. 威胁分析：跨记录 / 跨上下文置换

**关键前提**：KDBX 是**单体加密 XML 流**——所有条目 / 分组同处一条（分块）密文内，
「条目」不是独立认证的存储记录。故须把「跨记录置换」拆为三类分别评估。

### 4.1 条目置换（单体内部）

- 条目位于加密封包内部，密文经 AES-256 / ChaCha20 / Twofish 加密，密钥源于主密钥。
- 攻击者无主密钥 → **无法构造可在解密侧成立的置换密文**；任何密文字节改动都会在块 HMAC 或
  解密 / 填充校验处暴露。
- **结论：不可利用（需密钥）。**

### 4.2 块级置换

- 块密钥 = `SHA-512(LE64(index) ‖ hmacKey64)`，索引同时进入密钥与摘要 → **同文件内跨位置置换**在
  HMAC 校验即失败。
- **跨文件块置换**需 `hmacKey64` 相同（即同主凭据 + 同 KDF 派生）且密文可被同一分组密钥解密；
  两库凭据不同则解密失败。
- **结论：不可利用（需密钥一致）。**

### 4.3 跨路径整文件置换（唯一残余面）

- 不可信云端可把**路径 A 的合法密文**回给**路径 B**：密文有效且（同一主凭据时）可解密，
  而路径 B 的防回滚状态不含该摘要 → 判 `Accept`。
- **前提**：攻击者已持有用户合法的加密库字节——其作为云端本就可见。
- **影响面**：**数据混淆 / 误覆盖**（用户可能在 B 上继续写入，令 A 的内容污染 B）；
  **不构成机密性或完整性破坏**（无密钥无法伪造内容；密文仍是用户自己的合法快照）。
- **现有缓解**：三哈希状态机与防回滚链限制「旧版本重放」；跨路径混淆因各路径状态独立而不被拦截。
- **可利用性：低**——需攻击者精确操纵路径映射，且用户需在内容明显异常（显示成另一个库）后仍继续写入而不察觉。

### 4.4 与 mdbx key-commitment 攻击面的关系

- mdbx 记录级承诺要解决的是：**同一 AEAD 密钥下**，攻击者把记录 A 的密文搬到记录 B 的上下文而**仍能通过认证**
  （AEAD 缺少对密钥 / 上下文承诺）。该攻击面成立的前提是「存在互相独立的 AEAD 记录」。
- 本项目**不存在**互相独立的 AEAD 记录：条目非独立记录（§4.1），块已把序号并入密钥（§4.2），
  整文件由头 HMAC + 块链约束。故 mdbx 所述攻击面在 KDBX 单体模型中**不成立或已被覆盖**。
- 引入记录级承诺必须**改动 KDBX 字节布局** → **直接破坏与 KeePass 2.x / KeePassXC 的互操作**
  （本条 AC 明令禁止）。

---

## 5. 结论与决策

1. **不引入** mdbx 式记录级 AEAD 承诺，**不改动 KDBX 字节布局**，保持跨端互操作。
2. **不**把同步层 MAC 扩展为「远端路径 + 版本 / epoch + 内容哈希」上下文绑定。理由：
   - 现有同步 MAC 的认证对象是**本地**高水位状态文件（本地文件级攻击者不在模型内），
     对 §4.3 的**远端**混淆无直接拦截力；
   - 远端内容本身已由 KDBX 头部 / 块 HMAC 在**用户密钥下**完成认证；
   - 「同一内容出现在多个路径」是合法场景（同一库的多路径 / 备份），强制路径绑定会引入误报；
   - 额外绑定的安全增益与误报代价、改动风险不成比例。
3. **残余风险（明示接受）**：§4.3 的跨路径整文件混淆为**低危**，且不触及机密性与完整性；
   由「内容可见异常」「三哈希状态机」「防回滚链」共同限制。**本条以「明示接受风险」结案。**
4. **触发重评估的条件**：若未来改为 per-record（按记录独立存储 / 独立 AEAD）架构，
   须重新评估记录级承诺；届时同步层可复用 `SyncIntegrityMac` / `KeystoreSyncIntegrityMac`，
   将 MAC 输入扩展为「远端路径 + 版本 / epoch + 内容哈希」上下文绑定，**不新增密钥体系**。
