# 交互体验的参考项目对照（keepass2android vs KeePasskey）

> 调研触发：用户提出「本软件交互体验比 keepass2android 差很多」，并举例「匹配到密码不存在之后两边怎么做」。
> 方法：先读 `docs/references/README.md` 与 `keepass2android-架构分析.md`（文档优先），再对
> Kp2a 与本仓各自的目标文件做**定向取证**（无目标全仓扫描未做）；参考项目只读，零修改。
> 核实时间点：2026-09-28；核实方式：源码逐处阅读 + `rg` 抽查关键字符串（证据见 §5）。
> 结论分流：可执行差距登记为 `ISSUE-P3-352`（见 `ACTIVE_ISSUES.md`）；属取舍的进 §4C 待裁决，不进待办清单。

## 1. 核心示例：匹配不到条目之后

### 1.1 Kp2a 的行为链（从不静默）

**系统 Autofill 层**（`AutofillServiceBase.cs`）：

1. `OnFillRequest` **从不因「零候选」返回空 response**。无条目时仍构建 FillResponse，恒含一个
   **查询 Dataset**——占位文案 `Fill with Keepass2Android`（`strings.xml:1291`），带认证
   PendingIntent（`AddQueryDataset`，`AutofillServiceBase.cs:354-357`）。
2. **数据库未解锁时同样给查询 Dataset**（`Kp2aAutofillService.cs:55-56` 只是让条目候选为空字典），
   点击后进 `SelectCurrentDbActivity`，锁库则跳 `QuickUnlock`，解锁后**继续原搜索闭环**——
   「未解锁 ≠ 无出口」。
3. 纯 App（无 WebDomain）场景回退 `androidapp://<pkg>` 伪 schema（`:235`），两个维度都给出口。

**业务闭环层**（点查询 Dataset 之后）：

```
查询 Dataset → ChooseForAutofillActivity → SearchUrlTask（跨库搜 URL）
    → 0 条 → ShareUrlResults 空态：双按钮「Select another entry」/「Create entry for URL」
    → 1 条且允许自动返回 → 直接打开条目
    → 多条 → 列表手选
新建 → CreateEntryThenCloseTask（预填 URL）→ 条目页 → SelectEntryTask 回传填充
```

- 空态双按钮：`searchurlresults_empty.xml` + `ShareUrlResults.cs:147-203`
  （`Create entry for URL` 仅在有可写库时显示）。
- **匹配深度五级降级**（`ShareUrlResults.cs:213-251`）：exact URL → host → host(allowSubdomains)
  → 全文 URL → 全文 host；跨所有已打开库合并。`SearchForHost` 支持**父域命中子域查询**与
  **去 `www.` 前缀**（`SearchDbHelper.cs:122-149`）。
- **自愈机制**：用户手选的条目 URL 不覆盖搜索词时，弹
  `"Remember search text?"` 对话框询问把搜索词写进条目（`AppTask.cs:494-534`）——
  下次自动命中，匹配错误被用户一次操作修正。

**应用内文本搜索空态是 Kp2a 的弱项**：`SearchResults` 空结果只有 `"No search results"`
（`group_empty.xml`），**没有**新建出口（见 §4C）。

### 1.2 KeePasskey 的行为链

**系统填充双通道**（已对齐，见 §4B）：

- 传统 Autofill：零候选时恒下发「手动搜索兜底」认证 Dataset（`autofill_picker_entry_title`
  「搜索全部条目…」）+ SaveInfo（`AutofillDatasetBuilders.kt:393-395`）；锁库时给
  「解锁 KeePasskey 查看凭据」引导 Dataset（`:99-100`），解锁后链式回传。
- Credential Manager：零候选时挂「新建密码条目」Action（`CredentialResponseAssembler.kt:54-58`
  四门控，`PD-51` 口径）；锁库挂 `AuthenticationAction`「解锁 KeePasskey 填充凭据」。
- 就地新建闭环：`PasswordDraftActivity` 预填 URL / 用户名 / 绑定标签，保存后直接回传完成登录
  （`ISSUE-P3-345` / §347 已闭环）。

**应用内搜索空态——差距所在**（2026-09-28 核实）：

- 顶栏胶囊搜索框、300ms 防抖、即时过滤（`VaultListTopBars.kt:98`、`VaultListViewModel.kt:215-216`）。
- **搜索无结果**：`VaultEmptyState` 搜索态只有 `SearchOff` 图标 + **复用空目录文案**
  `vault_empty_title`「暂无内容」（`VaultListComponents.kt:365,372`）——
  ① 文案没有告诉用户「这是搜索无结果」；② **零出口**：没有「新建条目（预填搜索词）」、
  没有「清除搜索」，用户只能自己找到常驻 FAB 或手动清空输入框。
- 匹配为纯**子串**（`VaultSearchMatching.kt:26-41`），URL 字段亦按子串命中——
  查询 `accounts.example.com` 找不到 URL 为 `https://example.com` 的条目
  （Kp2a `SearchForHost(allowSubdomains)` 能命中）。

### 1.3 对照结论（就用户举例而言）

| 场景 | Kp2a | KeePasskey | 判定 |
|---|---|---|---|
| 系统填充零候选 | 恒有查询 Dataset 出口 | 恒有「搜索全部条目…」+ CM 新建 Action | **已对齐**（本仓另有就地新建，更强） |
| 锁库时零候选 | 查询 Dataset 直通解锁再搜 | 解锁 Dataset / AuthenticationAction 链式回传 | **已对齐** |
| 填充侧空态出口 | 「换入口 + 为 URL 新建」双按钮 | 「新建条目并填充」按钮（选择器空态） | **已对齐**（`ISSUE-P3-345`） |
| **应用内搜索空态** | 「No search results」（无出口） | 「暂无内容」（文案错位 + 无出口） | **两者都弱，本仓更弱**（文案连「无结果」都没说） |
| **URL/域名匹配深度** | 五级降级 + 父域/子域 + 去 www + 跨库 | 字段子串匹配 | **本仓明显弱** |
| 匹配自愈 | 「Remember search text?」 | 无 | **本仓缺** |

## 2. 应用内搜索形态对照

| 维度 | Kp2a | KeePasskey |
|---|---|---|
| 入口 | ActionBar 菜单内嵌 SearchView（可偏好自动展开） | 主顶栏胶囊搜索框，常驻 |
| 过滤时机 | **非即时**：`OnQueryTextChange` 返回 false，回车才进结果页（`GroupBaseActivity.cs:1049-1068`） | **即时**：300ms 防抖过滤 |
| 下拉建议 | `SearchProvider` 实时跨库建议（系统 SearchManager 形态） | 无（即时过滤已覆盖大半） |
| 匹配档 | 字段/正则/大小写/排除过期（`SearchActivity.cs:93-115` 高级选项） | CONTAINS / ALL_TERMS 两档（`SearchMatchMode`） |
| 覆盖字段 | 文本搜索跨所有已开库 | 标题/用户名/URL/备注/标签/非保护自定义字段（单库内） |
| 空态 | 「No search results」，无出口 | 「暂无内容」，无出口 |

本仓的**入口与过滤时机优于 Kp2a**（常驻即时过滤 vs 回车才搜）；差距在**匹配深度、
高级选项与空态出口**。

## 3. 其他交互触点对照

## 4. 改善建议分档

### A. 采纳 —— 登记 `ISSUE-P3-352`（P3 体验整改）

1. **搜索空态重做**：
   - 搜索态专用文案（「无搜索结果」类，不再复用「暂无内容」）；
   - 双出口按钮：「新建条目」（预填当前搜索词为标题/URL 起点，复用 `PasswordDraft` 或
     新建入口的预填通道）+「清除搜索」。
   - 先例：Kp2a `ShareUrlResults` 空态双按钮（`searchurlresults_empty.xml`）。
2. **应用内搜索叠加域名感知匹配档（加性，不放宽既有安全口径）**：
   - 查询串形如域名时，在子串命中之外叠加 Kp2a 式 host 降级：exact host → 子域后缀 → 去 `www.`；
   - ⚠️ 红线：`DomainMatcher`（passkey rpId 判定，`passkey/DomainMatcher.kt:84-100`
     「严禁模糊双向 contains」）**一律不动**——本条只给**应用内搜索**加一层 OR 命中源，
     不改凭据供给与签名的域判定。
3. **剪贴板自动清空可见反馈**：清空时给一条轻提示（Snackbar / 低优先级通知，
   文案向 Kp2a 的 "Clipboard cleared…" 看齐），消除「到底清没清」的不确定感。

### B. 不采纳 —— 本仓已更优或已对齐

- **系统填充零候选出口**：查询 Dataset / 解锁引导 / 就地新建均已具备且经真机坐实（§347），
  不重复建设。
- **搜索入口与过滤时机**：保留本仓常驻胶囊 + 即时过滤，不回退 Kp2a 的回车才搜。
- **非即时过滤 + 系统 SearchProvider 建议**：不引入。

### C. 待裁决 —— 有先例但成本/价值需产品裁决（不进 `ACTIVE_ISSUES.md`）

| 项 | Kp2a 先例 | 说明 |
|---|---|---|
| 「记住搜索词」自愈 | `AppTask.cs:494-534` 对话框 | 选中条目 URL 不覆盖搜索词时询问写入；实现涉及「选择结果回灌」链路，评估成本 |
| 高级搜索选项页 | `SearchActivity.cs:93-115`（字段勾选/正则/大小写/排除过期） | 正则引入注入面与性能预算，需单独评估 |
| 复制通知快捷动作 | 合并通知 + Copy user/pass/TOTP action | 通知面扩展，涉及敏感字段在通知中的暴露口径（须过安全复核） |
| 内嵌新手帮助 / onboarding | `Kp2aShortHelpView` | 纯增量 UX，价值取决于目标用户群 |
| QuickUnlock 快速解锁 | 尾部字素比对 + 通知栏入口 | Kp2a 自认主密码驻留是固有弱点（架构分析 §9.3），若做须按「派生凭证而非密码本体」设计 |
