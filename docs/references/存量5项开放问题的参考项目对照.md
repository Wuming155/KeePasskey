## 1. `ISSUE-P2-47`：同步与封印凭据的回滚防护

### 1.1 本仓现状（对照基线，非本次新增取证）

  命中 `recent` 即 `ReplayDetected`，`SyncEngine` **5 处**裁决点全部**不应用**远端内容
  （`sync/.../engine/SyncRollbackGuard.kt:118-127`；裁决点 `SyncEngine.kt:108/:173/:215/:236/:277`）。
- `State.sequence` 已持久化但**不参与裁决**（`SyncRollbackGuard.kt:76-80` 类 KDoc 自认）。

### 1.3 对照结论

- **可借鉴（形态，不是代码）**
  1. **kp2a `SaveDB.cs:146-200` 的 Sync / Overwrite / Cancel 三选一**——就是 AC①「回退**强制走冲突裁决 UI** 而非静默覆盖」
    的现成交互形态，且本仓**已有** `ui/screens/conflict/ConflictResolutionScreen.kt` 承载面（`SyncCoordinator.kt:187-206`
    已有 `ConflictNeedsUser` 与 `resolveConflicts`）。差别只是：kp2a 把它放在**保存**路径，**同步接收路径无人实现**。
  2. **Monica 的 `blockedReason` 持久化阻塞态**——把「拒绝」落成**可展示、可恢复的持久状态**而非一次性错误，
     与本仓 `SyncOutcome.Error(sync_error_rollback_rejected)` 相比多一层「用户可见且可恢复」的落点。
- **不可借鉴（反面教材）**
  - kp2a 的**单哈希 baseversion** 原理上识别不了回退（旧内容与正常更新同判「远端已修改」）；
  - kp2a 的「**远端改 + 本地未改 ⇒ 静默 `LoadDb` 重载**」正是本仓 AC① 要堵的路径；
  - KeePassDX 的**单向 mtime 判据**（`+10 s`）对回退零覆盖。
- **参考项目也没有做**：**文件级防回滚在 5 个项目中无人实现**。⇒ 本仓的 AC① 实质（本地摘要链 + 引擎拒绝落地）
  **不属于「照抄参考项目」，而是本仓自有的加固**；这一点应在条目正文里写明，以免后续把「参考项目都没做」误读为「不必做」。
- **本次未专项取证的相邻面（如实声明）**：`P2-47` AC② 涉及的「**封印凭据（快速解锁）回滚**」在参考项目中的做法，
  本次**未做定向取证**；既有分析文档记载的 kp2a QuickUnlock（主密码尾部截取，`keepass2android-架构分析.md:393-397`）
  与 KeePassDX DeviceUnlock（Keystore 封装主凭据存 Room，`KeePassDX-架构分析.md:542`）**均未提到**绑定「库摘要 + 封印序号」。
  该结论**只到「既有文档未见此机制」**，不等于「源码中不存在」。

## 2. `ISSUE-P2-79`：KDF 强度基线未对齐

### 2.1 本仓现状（对照基线）

- 建库默认 `Argon2id m=64 MiB / t=2 / p=2`（`KdbxHeader.kt:168-170`）；`KdfBenchmark` 生产消费方**唯一**且**仅设置页展示**
  （`SettingsKdfBenchmarkController.kt:39`），建库路径**零消费**（`SessionOpener.kt:69-72` 直走 `KdbxHeader.createDefault`）。
- 读取路径接受极弱参数（Argon2 内存下界 `8192` 字节、`t≥1`、`p≥1`；AES-KDF `R≥1`），保存时**逐字保留**工作因子
  （`KdbxFile.kt:332` / `:337` 只换 seed / salt）。
- 第四轮定版口径指出的「**降强陷阱**」：本仓 `KdfBenchmark` 建议值区间为 `m ∈ [8 MiB, 512 MiB]`、`t ∈ [1, 20]`、

- **可借鉴（直接对应本仓 AC③）**：官方 C# 的「**弱参数告警 + 一次性替换为默认值**」闭环
  —— `KeyUtil.cs:452-510`：`AreParametersWeak` 判定 → Yes/No 对话框（`:480-481`）→ 支持「不再提示」（`:476`）→
  接受即 `p = kdf.GetDefaultParameters()`（`:504-508`），开关默认 `true`（`AceSecurity.cs:101-107`）。
  这是 5 个项目中**唯一**的弱参数导入处理形态，可直接作为本仓 AC③ 的设计参照（**判据须换成逐参数口径**）。
- **可借鉴（有限）**：DX / KXC 的「建库自动校准」证明该 AC 在产品上可行；但两者**都只调一个维度**
  （DX 调 `m/p/I` 并降强、KXC 只调轮数），**没有一个可原样照抄**。
- **参考项目也没有做**：**「只升不降」的 max 守卫在 5 个项目中全部不存在**。⇒ 本仓「`max(建议值, 现默认)` 逐参数施加」
  是**超出全部参考项目**的自创加固；实施时须自证「不破坏既有库解锁与官方客户端互操作」（即本仓 AC④）。
- **可作维持现状的反证**：`P2-79` 的用户裁决（不接入 `KdfBenchmark`）与 DX / KXC 的做法相反，但两家的自动校准
  **确有降强面**（DX 尤甚）⇒ 该裁决**并非无据**；若将来重启 AC②，DX 的 `KdfEngine.kt:79-83` 就是**必须避开**的写法。
- **一处口径差异（供 AC① 产品确认参考）**：本仓建库默认落在 **Argon2id**，而官方默认是 **AES-KDF 600 000 轮**、
  DX 是 AES-KDF 500 000 轮 —— 三者的「默认强度」不在同一坐标系，讨论「基线」时须先声明坐标。

## 3. `ISSUE-P2-86`：解锁成功后框架不重发 `onFillRequest`

### 3.1 本仓现状（对照基线）

- `AutofillUnlockActivity.kt:20-22,70` 的 KDoc 前提 = 「解锁成功后 `setResult(RESULT_OK)` + `finish()`，
  **框架会自动重新发起 `onFillRequest`**」。
- 真机实测（Android 17 / API 37）：25 秒窗口内 `onFillRequest` **未重发**、框架侧会话事件新增 0 条
  （`docs/records/自动填充认证链路真机实测记录.md` §7.1）。
- 实验（回传真实 `Dataset`）**仍未写入**，成因未定位；**未测**候选变量 = 认证 `PendingIntent` 的**可变性**（AC② 裁决维持不改）。
- 本仓构造差异（**本次核实**）：
  - 解锁入口：PI = `FLAG_IMMUTABLE or FLAG_UPDATE_CURRENT`（`AutofillDatasetBuilders.kt:91`），
    基 Intent = `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP`（`:84-85`）→ **不重发**；
  - 二次确认入口：PI = `FLAG_IMMUTABLE`（`:256`），基 Intent 同样带 `NEW_TASK|CLEAR_TOP`（`:189-191`），
    回传载荷为 `Bundle.EMPTY`（`AutofillConfirmActivity.kt:264-272`）→ **写入恒为空**；
  - 选择器入口：PI = `FLAG_MUTABLE or FLAG_UPDATE_CURRENT`（`:290`），基 Intent **不带任何 Activity flags**（`:277-284`），
    回传**真实 `Dataset`**（`AutofillPickerActivity.kt:227-230`）→ **真机实测填充成功**。

### 3.3 对照结论

- **参考项目给出的结论（证据级）**：**「框架会在解锁后自动重发 `onFillRequest`」不是这两家的实现前提**；
  正确形态是「**认证 Activity 持有请求上下文 → 解锁后自行重建载荷 → 经 `EXTRA_AUTHENTICATION_RESULT` 回传**」。
  ⇒ 本仓 `AutofillUnlockActivity.kt:20-22` 的 KDoc 前提，**在两家主参考中都没有对应物**，`ISSUE-P2-86` AC④(b)
  「更正 KDoc 并把『解锁后需用户再次点按字段』登记为已知行为边界」因此**有直接先例支撑**。
- **官方语义解释「确认路径写入为空」**：认证数据集里服务端预置的值**会被认证结果替换**（官方 autofill services
  「Require user authentication」；数据集级回传 `Dataset`、响应级回传 `FillResponse`）。本仓确认路径预置真值却回
  `Bundle.EMPTY`（`AutofillConfirmActivity.kt:264-272`）⇒ **写入恒为空与官方语义一致**，不是框架缺陷。
- **可执行的下一步（最小对照实验，属推断）**：本仓内部已有一组**天然对照**——可用的选择器路径
  （`FLAG_MUTABLE` + 无 Activity flags + 回真实 `Dataset`）与不可用的解锁 / 确认路径（`FLAG_IMMUTABLE` +
  `NEW_TASK|CLEAR_TOP` + 空载荷）在**构造上恰好相反**，且两家的可行构造与选择器路径**一致**。
  因此「先只改认证 PI 的**可变性**与**基 Intent 的 Activity flags**、其余一字不动」是代价最小的一次对照实验。
  **注意**：这只是**推断**——「`FLAG_IMMUTABLE` 阻止框架 `fillIn` 注入」的因果**未被证实**（本机无 AOSP
  `AutofillManager.java` 源码、AOSP 在线镜像不可达），且该实验**跨越 AC② 裁决边界**，须先取得用户裁决。
- **不可借鉴 / 需要警惕**：两家**都没有**说明 `FLAG_MUTABLE` 为何必需（无解释性注释），也**都没有**补偿性重试逻辑
  ⇒ 不能从参考项目推出「改了 flags 就一定能修好」。
