## 0. 一页结论（判据 × 分组）

**判据三条**（沿用 [`本地文件级防护层的参考项目对照.md`](本地文件级防护层的参考项目对照.md) §0 既有口径）：

1. 对**在威胁模型内的对手**是否提供增量；
2. **品类先例**——参考项目做没做（同族经验的方向比「有没有」更重要）；
3. **维护成本**——双实现 / 门禁 / 台账带来的固定成本是否与收益成比例。

| 分组 | 项数 | 一句话净结论 |
|---|---|---|
| **A 有据 / 有先例** | 8 | 均有品类先例或真机实测支撑，**不宜误裁**（§2） |
| **B 存疑过度设计** | 5 | 与参考项目相比增量不足或成本不成比例，其中 **B1 / B2 最重**（§3） |

**总体判断**：本仓与参考项目的差异**不在产品复杂度**——KDBX 解析、通行密钥、WebDAV/S3 同步、
泄露检测、健康审计在品类内都有同构实现；差异集中在两处：① **工程治理面**（自研门禁链、文档台账、
多层验证义务）显著超出品类形态；② **少数自研替代**——在「口令强度估算」这个品类普遍采用成熟第三方实现
（`zxcvbn`）的位置上，本仓自建了一套模型并维护两份实现。
前者是「为 AI 协作流程而生」的成本，后者是「供应链纪律」与「重复实现」之间的真实取舍。

## 3. B 组：与参考项目相比**存疑的过度设计**（5 项，按可疑度降序）

### B1 自研机检门禁链（治理流程面，最重）

- **现象**：14 道 CI 门禁（`build.yml:133-146`：`count_line_tiers` / `long_functions` / `check_md_links` /
  `check_resolved_index_sync` / `check_tautological_assertions` / `check_recheck_consistency` /
  `check_bounded_type_names` / `check_box_slot_children` / `check_launch_language_seed` /
  `check_projection_read_safety` / `check_raw_coroutine_scope` / `check_archive_monotonicity` /
  `check_plaintext_carrier_to_string` / `check_message_not_in_user_text`）+ `gate_readings.py` 汇读仪式
  （`AGENTS.md` 规则 6.2 要求批次文档**原样粘贴读数块**）。机检脚本自身 4,515 行。
- **对照**：`docs/references/` 全部 19 篇文档中**没有**任何参考项目维护自研静态门禁链的记载；
  品类形态是单元测试 / 已知答案测试（官方 C# `SelfTest` KAT，`references/KeePass-2.61.1-架构分析.md:458`）/ 对拍。
- **问题不在单道门禁**——每道都有真实事故编号（`ISSUE-P3-305`「闸门存在 ≠ 闸门被执行」、`ISSUE-P2-546`
  归档面静默回退等）——而在**边际成本递增、鉴别力递减**：
  - `ISSUE-P2-556`（该条本身已于 **§483 闭环**，两道门禁已按其 AC①~⑤ 修复）的实测探针曾证明第 13 / 14 道门禁
    可被**合法 Kotlin 写法绕过**（探针 5 形态：message 护栏 3 处真违规只命中 1；明文载体 2 处真泄漏
    **全部漏检**且 `PASS` / EXIT 0）⇒ 出现过「为护栏本身立护栏」的卫滑；修复后判据面收宽，
    但「门禁数量增长快于鉴别力」的结构性趋势仍在；
  - `check_box_slot_children.py`（575 行）、`check_tautological_assertions.py`（433 行）等单脚本维护成本，
    高于其在 23 万行库上的实际年检出量（本文**未统计**各门禁年检出量，属未核实边界，见 §6）。
- **净判断**：对单人 / AI 协作工程属**流程过度**。方向应是**收敛而非扩张**——`ISSUE-P2-556` AC⑤
  （新门禁须以「反样本覆盖」为前置）方向正确，建议通用化为：**新门禁须同时给出年检出量预估与反样本矩阵，
  否则不挂 CI**。
- **可裁点**：对长期零检出的门禁降级为「按需运行」而非每批必跑；读数块入批次文档即可，不必全文搬移。

### B2 文档台账体系（为 AI 协作而生，不为产品而生）

- **现象**：docs = 代码字节的 **1.51 倍**（8.94 MB vs 5.91 MB）；479 个归档批次；`ACTIVE_ISSUES.md` +
  `产品裁决登记.md`（81 条）+ `已知工程限界.md` + `docs/README.md` 地图**四件套**交叉同步；
  且有 3 道门禁（`check_md_links` / `check_resolved_index_sync` / `check_archive_monotonicity`）专门维护
  **文档自身的一致性**。
- **对照**：参考项目为 README + CHANGELOG 级；无批次号、无「读数块」、无四表同步概念。
- **净判断**：收益是**真实的**（AI 协作的可追溯与上下文恢复），但它服务的是**协作过程**而非**产品**。
  当前形态（每批贴读数、跑 6+ 自检脚本、四表同步、批次正文一文件一批）的固定成本，在迭代密度上升后会
  开始反噬交付速度。**属产品 / 流程口径，须用户裁决，不宜代理决定**（对应 `产品裁决登记.md` 的分工）。
- **可裁点**：结论库保留、仪式瘦身——读数块只入批次文档；限界表 / PD 表提供统一检索入口而非逐条互链。

### B3 口令强度：自研模型 + 双实现

- **现象**：`crypto/src/main/rust/src/strength.rs` **710 行——最大的内核文件，超过四个 cipher 内核之和
  （144+111+154+57 = 466 行）**；Kotlin 侧另有一份 **307 行**的字节级近似兜底
  （`crypto/src/main/java/com/keepasskey/crypto/strength/PasswordStrength.kt`），两侧 `FLAG_*` 逐位对齐、
  JNI 返回定长 3 元 `IntArray [score, log10×100, flags]`；已引发 `QE-08` / `QE-10` 两轮性能返工
  （`docs/records/软件工程质量审查记录_2026-10-05.md`）。
- **对照**：KeePassXC 用 `thirdparty/zxcvbn`、Monica 集成 `zxcvbn`
  （`references/KeePassXC-架构分析.md:576`；`references/Monica-架构分析.md:254`）——**两家都用成熟第三方估算器**。
- **本仓理由（已写在 `strength.rs` KDoc，原文可查）**：不引 `zxcvbn` crate 是为「最小化依赖面 /
  供应链收敛」（与 `Cargo.toml` / `deny.toml` 审计面冲突），且「口令只在 `Zeroizing` 缓冲中驻留」。
- **净判断**：供应链理由**成立、不宜推翻**；但 710 行自研熵模型 + 307 行独立兜底，服务于
  「长度 < 8 阻断 + 强度 < 40 bits 二次确认」（`PD-38`）这样一个**轻量用途**，且该安全门槛
  **架在一个无外部校准的自研模型**上。这是真实取舍，不是可随手删的浪费。
- **可裁点**（若日后整改，均为有界改动）：① 兜底收敛为「Rust 实现的直译」而非独立近似（消一份漂移面）；
  ② 惩罚项从当前 10 类模式削减到门槛真正消费的维度。

#### B3-R 估算器替换选型结论（2026-10-09 追加；纯调研，**未动代码、未立条目**）

> 用户在 B3 结论基础上裁定「换成熟第三方估算器」。本节是**选型结论与整改账单**，不是实施记录；
> 真要动工须走一次完整批次，并按 §5 处置顺序 3 与 `PD-38` 重新标定。

**结论（双端同族）**：

- **Rust 主估算器：`zxcvbn` crate 3.1.1**（`shssoichiro/zxcvbn-rs`，crates.io `zxcvbn`）——
  3.1.1 发布于 2026-04-24，MIT，`rust-version = 1.66`，累计下载 12,441,962；
  直接依赖 `fancy-regex 0.18` / `itertools 0.14` / `lazy_static 1.3` / `regex 1` / `time 0.3`
  （`default-features = false` 可关掉默认 `builder` 特性从而去掉 `derive_builder`）；
  上游 badge 为 **passively-maintained**。
- **JVM 兜底：`com.nulab-inc:zxcvbn` 1.9.0**（`nulab/zxcvbn4j`）——1.9.0 发布于 2024-04-06，
  MIT，**零传递依赖**（词典随 jar 资源），`measure()` 自 1.3.0 起收 `CharSequence`
  （README 自陈「aims to avoid using Strings for any sensitive intermediate objects」）；
  移植自上游 zxcvbn 4.4.2，Cryptomator / JetBrains Hub 在用，README 明示 Android 可用。

**候选对比与排除理由**：

| 候选 | 维护状态 | 许可 | 依赖面 | 结论 |
|---|---|---|---|---|
| `zxcvbn` 3.1.1（shssoichiro） | 2026-04 仍在发版 / 1244 万下载 / passively-maintained | MIT | 5 直接依赖，传递闭包约 +11~15 crate（regex 全家 + time 全家，含 proc-macro `time-macros`） | **Rust 侧首选** |
| `com.nulab-inc:zxcvbn` 1.9.0（nulab） | 2024-04 发版，CI 在跑 | MIT | **零传递依赖**（词典约 1MB+） | **JVM 侧首选** |
| `xd009642/zxcvbn-rs` | **2025-02-11 已归档**，README 自陈 not actively maintained，6 star | MIT | — | 排除 |
| `zxcvbn-ts` | 上游最活跃分支 | MIT | 需 JS 引擎 | Android 不适用 |
| nbvcxz（JVM） | 小众 | MIT | — | 非主流，排除 |

**为何双端搭配而非只换一侧**：① 主路径必须是 Rust——这本就是 `strength.rs` 原生的首要理由
（口令只在 `Zeroizing` 缓冲、不进 JVM 堆），换估算器不改变该前提；② 兜底**不**降级为「不可用」——
`PD-38` 的 40 bits 门槛若在原生探活失败时静默失效，正是本仓反复审计的「静默降级」形态，
且 cipher 层已有「JVM 兜底 + 对拍锁定等价」先例（`PD-07`）；③ 两端同族带来额外好处——
健康审计的强度数字与 KeePassXC（`thirdparty/zxcvbn` C++ 移植）**同源可比**；
两端差值属「同族版本差」而非「语义差」，两侧契约由「字节级近似」改「同族 + fixture 容差」即可。

**整改账单（五件必须一并办的事）**：

1. **`PD-38` 门槛重新标定**：模型更换后数值体系不可比（NIST 字符集基线高估
   `Tr0ub4dor&3` 类口令，zxcvbn 对其约 26 bit）⇒ 40 bits 换成 zxcvbn guesses 后语义已变，
   须用一批典型口令重新定档，否则门槛会静默变松或变紧。
2. **翻转 `strength.rs` KDoc 的旧理由**：该 KDoc 明写「不引 `zxcvbn` crate（供应链最小化面，
   与 `Cargo.toml` / `deny.toml` 冲突）」并「禁止称 zxcvbn」。按本仓「措辞即结论」纪律，
   翻转须走一次完整批次并在 `产品裁决登记.md` 登记，不得只改代码。
3. **依赖面实价**：Rust 侧 +5 直接 / 约 +12~15 传递 crate——当前 `keepasskey_argon2`
   仅 9 个 direct 且全部 feature 收敛，属成倍扩张；`time` 仅为日期模式匹配就引入 proc-macro
   `time-macros` 与 `libc`。JVM 侧仅 +1、零传递。须跑 `tools` 的 CVSS 闸门
   （`AGENTS.md` §5 `check_dependency_cvss.py`，fail-closed）与 `deny.toml` 审计面复核。
4. **全库审计性能与长度截断**：zxcvbn 显著重于 NIST 基线（模式匹配 + 词典）。
   KeePassXC 有现成先例——提交 `65a1d1b0`（2022-04-03）「Limit zxcvbn entropy estimation length」
   即为超长口令耗时失控所加（见 [`参考项目Git历史对照/04-keepassxc.md`](参考项目Git历史对照/04-keepassxc.md) 行 19 / 行 110）。
   本仓现有的 `MAX_ANALYZED_CHARS` + O(n) 保证会被 crate 语义取代，须自建截断并登记
   （正面回答 `QE-08` / `QE-10`）。
5. **横切契约重设计**：现有 JNI 定长 3 元 `IntArray[score, log10×100, flags]` 与两侧
   `FLAG_*` 逐位对齐作废（zxcvbn 无 flags，只有 `feedback.warning / suggestions`）⇒
   新契约建议 `score(0..4) + guessesLog10×100 + warning code`；既有强度用例按测试资产纪律 ①
   **只能改造不能删除**。

**中间选项（不换模型、只换数据）**：若想省掉 Rust 那 ~15 个传递 crate，可取 zxcvbn 的
**词典数据**（约 3 万条频率排序口令 + 常见姓名 / 维基与影视词表）而模型维持轻量 NIST 基线 +
频率词典——准确率大头来自那份带排序的语料而非惩罚项，供应链代价近零。代价：不算「换成熟估算器」，
且第 1 条门槛标定问题依旧存在。

**风险与未验证点（如实声明）**：

- `zxcvbn` 3.1.1 是否支持自定义词典子集**未确认**（3.x 的 builder API 已 deprecate，
  关系到 .so 能否瘦身）；
- nulab 端 `CharSequence` 入口内部是否物化 `String`、Android 上从 jar 资源加载词典能否过
  R8 / AGP 资源打包**未验证**（README 自称 Android 可用，但本仓构建链需实测）；
- 两端数值差**未实测**（仅有「同族移植」的定性判断），容差须以 fixture 跑出后登记；
- 上游 Rust 移植为 passively-maintained，长期活跃度一般（2026-04 仍有发版）；
- 许可兼容：双端 MIT → 主仓 GPL-3.0 单向兼容（FSF 口径），无实质冲突；**未经法务确认**。

### B4 健康检查的「系统服务探针」面

- **现象**：`AutofillHealthProbe.kt`（139 行）/ `CredentialProviderHealthProbe.kt`（77 行）/
  `AutofillHealthPolicy.kt`（182 行）/ `AutofillHealthViewModel.kt` 等，共约 460 行，在设置页自检
  系统自动填充 / 凭据提供者状态（`app/src/main/java/com/keepasskey/app/ui/screens/settings/`）。
- **对照**：KeePassXC Reports 只做**库内容审计**（弱口令 / 重复 / HIBP），**无系统服务探针**；
  参考项目以「跳转平台设置页」代替。
- **净判断**：收益是排障友好，属**体验面增量**而非威胁模型增量；代价约 460 行 + 9 个健康相关测试文件。
  可留（用户价值明确）亦可裁（无品类先例、无安全增量）。

### B5 测试与验证义务的绝对规模

- **现象**：测试 / 主代码 = **46.5%**（108,469 / 233,043 行）；45 个 `androidTest` 文件；
  「任何改动四层 `connectedDebugAndroidTest`」义务 + `check_connected_device_results` 空转断言
  （`ISSUE-P3-493`）+ `check_installed_build` 装机走查前置（§434）+ 截图测试包装编译门禁。
- **对照**：KeePassXC 测试体系在品类内已属重（TestKdbx3/4、TestMerge、TestPasskeys、TestBrowser），
  本仓在其之上再叠「宿主 + 设备 + 截图 + 互操作对拍」四层。
- **净判断**：对密码管理器**可辩护**——规则 ②③ 的每项义务都源自真实逃逸事故（§143 平台剥离版 BC 抢占、
  §147 全零密钥解密均「宿主 100% 绿、仅真机失败」；`ISSUE-P3-493` 的 `am instrument` 零用例成功码）。
  但它是本仓**迭代速度的最大单项成本**。建议周期性地做「义务 ↔ 逃逸事故」复核，裁掉未再捕获缺陷的层，
  而不是继续加层。
