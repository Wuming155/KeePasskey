## 1. 解锁失败节流（`ISSUE-P1-277`）

### 1.1 本仓现状（对照基线，非本次新增取证）

- 处理：`UnlockThrottlePolicy`（纯函数，`FAILURE_THRESHOLD=5`、`BASE_BACKOFF_MS=30s`、`MAX_BACKOFF_MS=30min`）
  由 `UnlockThrottleManager` 驱动，`SharedPrefsUnlockThrottleStore` 跨进程持久化；
  出厂 `unlockThrottleEnabled = false`（`SettingsRepository.kt:56`）。
- 追加层（本次被质疑的对象）：`UnlockThrottleIntegrity` 的 Keystore HMAC + 每库一条存在性标记。
- 现存缺陷（详见 `ISSUE-P1-277`）：完整性分支不受开关门控、且在 Keystore HMAC 持续不可用时**不可自愈**
  （每次 `gate` 重锁 30 分钟）。

### 1.2 参考项目做法

| 项目 | 有无「主密码失败计数 / 锁定」 | 证据（路径:行号） |
|---|---|---|
| **KeePassDX** | **无** | `app/src/main` 内 `lockout\|failed attempt\|throttle` 命中**全是文案**（`strings.xml` 多语言的 `rounds_explanation` 讲 KDF 轮数抗暴力）与一句注释「Encrypt the master key a few times to make brute-force key-search harder」（`database/.../DatabaseKDB.kt:120`）；无计数、无锁定 |
| **KeePass 官方 C#** | **无** | `KeePass/` 内唯一命中是 `XmlSerializerEx.cs:298-301` 的局部变量 `iBackOffset`（`LastIndexOf('.')` 的偏移）——纯假阳性 |
| **KeePassXC** | **无** | 命中仅在口令强度估计（`src/cli/Estimate.cpp:71-99` 的 `BRUTE_MATCH`）与 KDF 提示文案（`DatabaseSettingsWidgetEncryption.cpp:319`） |
| **keepass2android** | **仅 QuickUnlock PIN 有计数，且形同不设** | `src/keepass2android-app/QuickUnlock.cs:56-57`：`private int numFailedAttempts = 0; private int maxNumFailedAttempts = int.MaxValue;`；`:167` 由 **bundle** 读回（`:205-210` 键 `FailedAttempts`，走 `onSaveInstanceState`）⇒ **不落盘、进程死亡即失**、上限 `int.MaxValue` 从不锁定 |
| **Monica** | **无应用层计数，显式交给平台** | `utils/BiometricAuthHelper.kt:175` 注释：`// Keep the native prompt open; Android owns retry/lockout policy.` |

### 1.3 对照结论

- **参考项目也没有做**：**五项目无一实现「主密码失败计数 + 持久化节流」**。⇒ 本仓的**基础节流层**
  （计数 + 指数退避，恰好对「UI 驱动 / 物理接触」这类**无文件写权限**的对手有效）本身已属**自创加固**；
  被质疑的**完整性层**则是叠加在自创加固之上的第二层。
- **品类共识是「把锁定交给平台」**：Monica 的注释与 `AGENTS.md`/`PD-45` 的「安全边界归位平台原语
  （Keystore / 生物识别 / 系统自动填充）」同向；参考项目中**没有任何一个**在主密码路径自建锁定状态机。
- **可用的判据只有「增量」**：既然完整性层要防的对手（本地文件级写者）要么升级为同 UID/root
  （可读 `filesDir/*.kdbx` 离线爆破 —— 节流失去意义），要么在本机上不存在（备份 / 设备迁移路径已被
  `allowBackup="false"` + 九域 exclude 封闭），该层对**在模型内的对手**不提供增量；
  且它自身引入了**不可自愈**的 fail-closed 面（本仓独有，参考项目中无对应风险）。

## 2. 本地防回滚状态文件的完整性认证（`ISSUE-P3-326`）

### 2.1 本仓现状

- `SyncRollbackGuard` 维护「已见内容摘要链」，状态落 `filesDir/rollback/`，由 `KeystoreSyncIntegrityMac`
  （AndroidKeyStore 内不可导出 HMAC 密钥，别名 `com.keepasskey.sync_rollback_integrity`）认证。
- 其类 KDoc **自陈**：「本地文件级攻击者不在本威胁模型内（其本可 Hook 进程），远端攻击者无法触碰本地状态文件」
  （`sync/.../SyncRollbackGuard.kt:59-69`）；MAC 失效 → `load` 返回空 `State`（`:177`，**fail-open**）。
- 历史事故 `ISSUE-P0-10`：provider 传参错 → 真机 MAC 恒 `null` → 防回滚静默下线（现补 `AppLog.w` 留痕，
  `app/.../sync/KeystoreSyncIntegrityMac.kt:39-45`）。

### 2.2 参考项目做法

| 维度 | 结论 | 证据 |
|---|---|---|
| 文件级防回滚 | **五项目无一实现** | [`存量5项开放问题的参考项目对照.md`](存量5项开放问题的参考项目对照.md) §1.2 全表（kp2a 单哈希 `baseversion`；KeePassXC 无远端版本概念；官方 C# 仅会话内哈希；Monica 段协议只回看一步；KeePassDX 单向 `mtime+10s`） |
| 「已见状态」是否做完整性 MAC | **有状态机的 Monica 亦为零** | `Monica for Android/.../data/MdbxSyncState.kt` 内 `hmac\|\bmac\b` 命中 **0**（该文件持久化 `nextSequence` / `checkpoint` / `lastAppliedDigestHex` / `blockedReason`，**无 MAC**） |
| kp2a 的本地版本记录 | **明文哈希，非 MAC** | `.cache.baseversion` / `.version`（既有对照 §1.2 已取证 `CachingFileStorage.cs:168-176`） |

### 2.3 对照结论

- **本层无先例**：既没有「文件级防回滚」，更没有「对本地回滚状态做密码学认证」。⇒ 本层是**本仓自创加固**，
  不得以「参考项目也做」为保留依据。
- **风险面是本仓独有**：参考项目即便有回滚相关状态（kp2a 明文哈希 / Monica 无 MAC 的序列状态），
  都**不存在**「MAC 计算路径故障 ⇒ 防护静默下线」这一失效面；本仓已因 `ISSUE-P0-10` 真实发生过一次。
- **其防御方向为 fail-open**，因此它**不会**像 `ISSUE-P1-277` 那样误锁用户；移除与保留的差别只在
  「是否值得维持一条无外部先例、且在模型内对手面前无效的认证依赖」——属取舍，须用户裁决。

## 3. 快速解锁断言的 signCount 反克隆与登记记录防篡改（`ISSUE-P3-327`）

### 3.1 本仓现状

- 断言私钥为 ES256（P-256）**硬件内不可导出**密钥对，`setUserAuthenticationRequired(false)`
  （规格单点见 `UnlockPasskeyKeyPolicy.kt`；边界登记于 [`../architecture/已知工程限界.md`](../architecture/已知工程限界.md) §3.6）。
- 验证侧强制 `signCount` **严格单调**，回退即判克隆并 fail-closed（`UnlockPasskeyManager.kt:239-261`）；
  登记记录（公钥 / credentialId / signCount）经 Keystore HMAC 封存（`BiometricCredentialStorage.kt:160-224`）。
- 自陈边界：`BiometricCredentialStorage.kt:165`「同 UID 任意代码执行者可调用 Keystore 重算 MAC，
  该威胁域本层不设防」。

### 3.2 参考项目做法

| 项目 | 是否记录 / 校验 signCount | 证据 |
|---|---|---|
| **KeePassDX** | **零命中（不使用）** | `grep -riE "signcount\|sign_count"` 于 `KeePassDX-master/app/src/main` → **0**；其自实现 WebAuthn 二进制层 `credentialprovider/passkey/data/AuthenticatorData.kt` 内 `counter` 亦 **0** ⇒ 结构里不带计数器 |
| **KeePassXC** | **零命中** | `grep -riE "signcount" keepassxc-develop` → **0**（其 `KPEX_PASSKEY_*` 键集合亦无计数器项，本仓 `SignCount` 属**自扩展键**） |
| **Monica（唯一有该字段者）** | **有字段，但有意恒写 0** | 字段与语义：`data/PasskeyEntry.kt:31`「@property signCount 签名计数器（用于检测克隆攻击）」；**实际行为**在 `passkey/PasskeyAuthActivity.kt:477-496`：原文「签名计数器永远写 0：WebAuthn spec §6.1.1 明确允许 authenticator 始终返回 signCount = 0…Bitwarden / 1Password / iCloud Keychain 这类"同步型 passkey"都走这条路…如果还按 signCount + 1 推进，多设备 / 跨设备恢复后必然分叉…把 newSignCount 固定为 0 就彻底回避这个分叉问题」 |
| 记录防篡改（HMAC 封存） | **两家均无** | Monica 的 HMAC 命中全部在 Bitwarden 附件 / 服务端加密（`attachments/crypto/BitwardenAttachmentCrypto.kt:114,174` 等），**与 passkey 登记记录无关**；KeePassDX 直接把 passkey 字段写 KDBX 条目（`database/model/PasskeyEntryFields.kt`） |

### 3.3 对照结论

- **反克隆在本仓是空转**：Monica 的「计数器推进 ⇒ 多设备分叉 ⇒ passkey 突然失效」前提是
  **私钥可漫游 + 全量备份**；本仓断言私钥**设备绑定、不可导出**，**不存在可被克隆的对象**（把记录 / 密文复制到
  另一台设备既签不出、也解不开）。⇒ 严格单调校验在本仓拦不到任何在模型内的对手，只增加一条失败面。
- **记录 HMAC 的对手域被文档自陈排除**，且其声称能防的「仅具备文件级写能力」对手在本机不存在（§0 前提前提）。
- **品类对 signCount 不做强制**：唯一实现了该字段的 Monica **主动放弃**推进（并点名 Bitwarden /
  1Password / iCloud Keychain 同为「恒 0」路线）⇒ 本仓若要保留该断言，保留理由只能是
  「WebAuthn 形态对齐 / 为限界 §3.6 解除条件预留」，**不能**是「反克隆防护」。
- **不得据此断言**「参考项目都不做所以我们也不该做」——同 §0 净影响。

## 4. 自动填充屏蔽记录的持久化形态（`ISSUE-P3-328`）

### 4.1 本仓现状

- 屏蔽记录只落**定长 hex 签名**（Keystore HMAC-SHA256），密钥不可导出，自陈「即便攻击者拿到应用私有目录
  也无法离线枚举签名」（`autofill/KeystoreHmacFieldSignatureSource.kt:16-23`）。
- 迁移沿革：v1 为「随机盐 + SHA-256，**盐与签名同文件**落盘」（`autofill/AutofillFieldBlocklistStore.kt:144-162`），
  v2 起换 Keystore HMAC 并删除旧盐。

### 4.2 参考项目做法

| 项目 | 屏蔽记录的持久化形态 | 证据 |
|---|---|---|
| **KeePassDX** | **明文包名 / 域名集合** | `settings/PreferencesUtil.kt:838-843` `applicationIdBlocklist()` 用 `prefs.getStringSet(...)` 读默认 SharedPreferences；`:860-870` `addApplicationIdToBlocklist()` 用 `putStringSet(...)` 写回；`credentialprovider/autofill/KeeAutofillService.kt:75-76,102-103` 消费 `applicationIdBlocklist` / `webDomainBlocklist` |
| **keepass2android** | **仅内存固定三条默认值** | `services/AutofillBase/AutofillServiceBase.cs:58-74`：`private HashSet<string> _internal_blacklistedUris`，内容为 `AndroidAppScheme + "android"` / `+ "com.android.settings"` / `+ 本应用包名` 三条硬编码；**未见**用户项的持久化读写 |
| **KeePassXC / KeePass 官方 C# / Monica** | 无对应面（无「按包名 / 域名屏蔽自动填充」机制） | KeePassXC 的命中是 **AutoType 窗口类黑名单**（`src/autotype/xcb/AutoTypeXCB.cpp:64-68` 硬编码 `gnome-panel` / `Plasma` 等桌面面板类名，`AutoTypeXCB.h:75` `m_classBlacklist`）——与自动填充屏蔽无关；官方 C# 的命中是 `Forms/PluginsForm.cs:44-161` 的 `m_bBlockListUpdate`（插件列表重入标志）——纯假阳性；Monica 无对应生产实现 |

### 4.3 对照结论

- **「不可枚举」形态无先例**：品类内最接近的 KeePassDX 直接**明文**存包名与域名集合，
  kp2a 连用户项都不持久化。⇒ 本仓 v2 是**自创加固**。
- **但它是四条中唯一在模型之外仍有真实收益的一条**：对照 v1 形态，v2 把「用户屏蔽了哪些站点」
  这类**明文元数据**收敛为一个无法解读的 hex 集合（读取 prefs 仍需同 UID / root，故整体仍是 T2 邻域）。
  ⇒ 属**信息收敛**而非新增防线，低优先级保留是合理的，**不构成**与 §1 / §3 同级的冗余问题。
- **可借鉴的反面**：若照抄 KeePassDX 的明文 `StringSet` 形态，会**退回到**本仓 v1 的元数据泄露面；
  该形态**不得**作为「简化本仓实现」的依据。

## 5. 检索符号清单与诚实性声明

### 5.1 实际使用的检索符号（定向，非全仓扫荡）

- **① 节流**：`lockout|failed.?attempt|throttle|backoff|brute`（各项目 `--include=*.kt/*.java/*.cs/*.cpp/*.h/*.xml`）；
  命中逐条判读（剔除 `HashedBlockOutputStream` / `iBackOffset` / `BRUTE_MATCH` 等假阳性）。
- **② 本地状态完整性**：Monica `MdbxSyncState.kt` 内 `hmac|\bmac\b`；kp2a `baseversion` 沿用既有对照 §1.2 取证。
