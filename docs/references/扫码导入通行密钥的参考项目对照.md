## 1. CXF 实现状况：零命中（可复跑）

```
grep -rn -iE "hmacCredentials|credWithUV|credWithoutUV|Credential Exchange Format|credential_exchange|credentialExchange"
  参考项目/passkeys参考      →  0 命中
grep -rn -iE "bluetooth|cable|proximity"  fenris-authenticator-main/app/src/main/java  →  12 命中，
  逐条核验后全部是 Cancelable / Unstable 一类**子串误命中**，无任何蓝牙代码
```

⇒ 三项目**均不实现** FIDO CXF，也**不消费** `fido2Extensions`。
唯一带「passkey 导入」字样的是 fenris 的**死钩子**：`importformat/ImportFormatDecoder.kt:16`
的 `DecodedImport.passkeys: List<NewPasskey>` **无任何填充方**，其 `vault/Passkey.kt:94`
的 `NewPasskey.privateKeyDER` **无消费方**；已注册的解码器只有 Google Authenticator
（`importformat/ImportFormatDecoder.kt:30-36` → `importformat/GoogleAuthenticatorDecoder.kt:38-48`，纯 TOTP protobuf）。

**含义**：`ISSUE-P3-337` 的解析器、字段判据、PRF 口径**没有**同行实现可参照；
能参照的只有**规范原文**（其自相矛盾处见 `../ACTIVE_ISSUES.md` 337 核实 10）与互操作对拍（`AGENTS.md` §3 规则 8）。

## 2. 逐项目读数

### 2.1 fenris：QR 只装种子，正文走文件

| 读数 | 出处 |
|---|---|
| 全库**唯一** QR 生成点：zxing `QRCodeWriter().encode(uri, QR_CODE, 200, 200)`，**无 hint**（⇒ 纠错等级取默认、版本自动） | `ui/components/backupseed/BackupSeedDisplay.kt:133-152` |
| 载荷只有 `fenris://seed/<43 字符 b64url(32 B)>` ≈ 57 B | `crypto/BackupSeed.kt:32-36` |
| **无分片 / 无多页 / 无动画 QR**；备份正文（`VaultExportEnvelope`）走 SAF 文件输出流 | `viewmodel/SettingsViewModel.kt:66-84`、`vault/Export.kt:19-23,95-122` |
| 相机解码：裁**中心 2/3**，而取景框画的是 **0.65** —— 两个常数**不同源** | `codec/QrCode.kt:55-72` vs `ui/components/QrScanner.kt:236-259` |
| 相册解码：整图**不降采样**直接 `getPixels`（大照片有 OOM 面） | `codec/QrCode.kt:30-43`、`ui/components/AddSecretsSheet.kt:44-48` |

**对本仓的关系**：① 我们**没有**「多张 QR 装配」的先例可抄 ⇒ 单张上限只能自己定（337 口径 9）；
② 它的「取景框与解码区不同源」是一类**会在真机上莫名掉成功率**的缺陷，而本仓相机通路
**整帧解码、不裁剪**（`app/.../ui/screens/edit/TotpScanDialog.kt:282-301`，`ImageAnalysis` 未设分辨率），
所以本仓的对应风险点是**分辨率**而不是裁剪区（⇒ 337 口径 10）；
③ 本仓相册侧已有 `MAX_GALLERY_IMAGE_DIMENSION=2400` 有界解码（`TotpGalleryImport.kt:67,189-193`），
这一层**强于** fenris，不构成待改项。

### 2.2 fenris：passkey 落库字段与私钥形态

`vault/Passkey.kt:11-27` + Room schema `app/schemas/.../4.json` 列集
= `credentialId / sortOrder / userId / userName / displayName / rpId / keyAlias / publicKey / encryptedBackupPrivateKey / timeOfCreation / timeOfLastUse / algorithm`。

| 读数 | 出处 | 与本仓差异 |
|---|---|---|
| 私钥：**PKCS#8 DER**（`keyPair.private.encoded`）经 AES-GCM 后存库列，可用副本再导入 AndroidKeyStore（`isStrongBoxBacked=true`） | `vault/Vault.kt:172`、`crypto/Cryptographer.kt:190-213,281-287,432-437` | 本仓驻留形态是 **PKCS#8 PEM**（`KPEX_PASSKEY_PRIVATE_KEY_PEM`），且**不**入 KeyStore（软件密钥） |
| 公钥存 **SPKI/X.509**，COSE CBOR **只在签发时现拼** | `codec/Base64.kt:37-38`、`credentialprovider/webauthn/CreateResponse.kt:28-39` | 同向（本仓亦由私钥现算公钥） |
| **无 signCount**：authData 的计数器恒 4 字节零 | `credentialprovider/webauthn/AuthResponse.kt:23-24`、`CreateResponse.kt:46` | ⚠️ 本仓**有**并自增（`core/.../PasskeyData.kt:105-107,396-399`、`app/.../PasskeyAssertionActivity.kt:238`）⇒ **不得**照抄恒 0；但「导入的凭据计数器起点未知」是本仓真问题（⇒ 337 未决 6） |
| BE/BS **不落库**，标志位硬编码 `{UP,UV,BE}` | `Constants.kt:64-69`、`CreateResponse.kt:44` | 本仓 `_FLAG_BE` / `_FLAG_BS` 落库（PD-09） |
| `credBlob` / `largeBlob` / `hmac-secret` / PRF **完全不存在**，`clientExtensionResults=emptyMap` | `CreateResponse.kt:83` | 本仓 `_PRF` 存在 ⇒ CXF 扩展处理是**本仓独有面**，无同类实现可参照 |
| attestation `fmt:"none"`，不存任何 attestation；AAGUID 常量 | `CreateResponse.kt:49-55`、`Constants.kt:13` | 同向 |

### 2.3 open-passkey：RP 侧判据（不是同类实现，但可校准判据）

| 读数 | 出处 |
|---|---|
| 算法分派**只从存储的 COSE key 读 `alg`**（label 3），switch `-7/-49/-52`，各 verifier 再核 kty/crv | `packages/core-ts/src/authentication.ts:17-20,228-242,31,127,156` |
| **但** packed full 走自述 `attStmt.alg`，且**注册阶段从不校验**凭据 COSE key 的 alg（要等断言才炸） | `packages/core-ts/src/registration.ts:159,91-142` |
| 回滚检测只在 `storedSignCount > 0 && new <= stored` 时报错 ⇒ **恒 0 / stored=0 的凭据永远放行** | `packages/core-ts/src/authentication.ts:246`（Go 侧同口径 `webauthn.go:1429`） |
| `BE=0 且 BS=1` 直接判 `invalid_backup_state`；**但不校验 BE/BS 相对已存值的单调性** | `registration.ts:103-105`、`authentication.ts:222-224` |
| PRF：服务端发 32 B 盐、断言按 `evalByCredential[base64url(credId)]` 索引；**RP 完全不校验 `prf.results`，纯透传**；全仓无 `hmac-secret` / `credWithUV` / 双值语义 | `packages/server-ts/src/passkey.ts:102,130,212-229`、`packages/sdk-js/src/index.ts:210,302-322` |
| `spec/vectors/` 31 条向量**全是 RP 验证输入**（含完整 `attestationObject` / COSE key / 非标准 CBOR 键序 / BE-BS 与 signCount 负例），**零私钥、零 PKCS#8、零 PRF 输入输出对** | `spec/vectors/registration.json`、`spec/vectors/authentication.json` |
| 全仓唯一产出 PKCS#8 私钥处：软件认证器（WebCrypto 导 `pkcs8`、`credentialId=randomBytes(32)`、flags 硬编码 `0x5d/0x1d`、signCount 0→+1） | `packages/authenticator-ts/src/create.ts:21-42,37` |

**净结论**：**不能**当 `ISSUE-P3-337` 的导入夹具（无私钥样本、非 CXF）；
但其「alg 只从结构实证、不信载荷自述」正是本仓「规范无 `alg` 成员 ⇒ 由 PKCS#8 DER 的 OID 判定」这条口径的
**同向第三方实现**（337 口径 3）。其「注册阶段不校验 alg」是本仓**不该学**的那一半。

### 2.5 fenris：导入前「不兼容清单」确认

`importformat/ImportFormatDecoder.kt:17,20-27` 定义 `incompatible: List<IncompatibleItem>`（携带 `type` 与 `displayName`），
UI 侧 `ui/screens/main/secrets/sheets/ConfirmImportSheet.kt` 先呈现清单、用户确认后才导入；
内层 JSON 反序列化用 `ignoreUnknownKeys=true`（`vault/Export.kt:124-141`）——
两者**合起来**才是它的完整口径：**未知键不报错，但「本实现不支持的项」必须显式列出并等确认**。
单条导入失败计数后抛 `ImportFailedException`（`vault/Vault.kt:491-497,526-532`），整体失败则 wipe 回干净态
（`viewmodel/SetupViewModel.kt:62-67`）。

⇒ 比 `ISSUE-P3-337` AC⑪② 现写的「丢弃后如实提示」**更强一层**（确认在先），已回填为该条 口径 4′。

### 2.6 无 GMS 的凭据提供方接线（印证性读数）

- fenris：`credentialprovider/FenrisCredentialProviderService.kt:40` extends `androidx.credentials.provider.CredentialProviderService`；
  manifest `app/src/main/AndroidManifest.xml:40-53` 声明 AOSP action `android.service.credentials.CredentialProviderService`
  + `BIND_CREDENTIAL_PROVIDER_SERVICE`；WebAuthn JSON 自解析（`credentialprovider/webauthn/RequestOptions.kt`），
  authData / COSE 自拼，密钥运算走自家 `Cryptographer` over AndroidKeyStore；RP / origin 校验用内置特权浏览器表 + TLD 表
  （`credentialprovider/Util.kt:110-127`、`webauthn/Validation.kt`）。
- Authnkey：`AuthnkeyCredentialService.kt:30` 同基类；`AndroidManifest.xml:43-55` 额外用
  `<meta-data android:name="android.credentials.provider" android:resource="@xml/credential_provider_config"/>`，
  配置文件只声明一个能力 `TYPE_PUBLIC_KEY_CREDENTIAL`（`res/xml/credential_provider_config.xml:5`）；
  浏览器 RP 场景取 origin 依赖 `res/raw/privileged_apps.json` 白名单 + `CallingAppInfo.getOrigin(allowlist)`
  （`CredentialProviderActivity.kt:1602-1633`）。

⇒ 与本仓既有接线同构，**不新增整改项**；对 `ISSUE-P3-337` 的唯一实际意义是 AC⑧ 的硬前置：
真机上要拿 `https://<rpId>` 级别的 origin，特权应用白名单是必经路（本仓对应 `PD-10` / `CallingOriginResolver`）。

### 2.7 跨设备 hybrid / caBLE：零实现

三家全仓大小写不敏感检索 `hybrid` / `cable` / `ble` / `bluetooth` / `websocket` / `proximity`：
fenris 只有 §1 的子串误命中；Authnkey 只有两行死常量（§2.4）；
open-passkey 的「hybrid」全部指**后量子复合签名**（ML-DSA-65-ES256），与 CTAP hybrid 传输无关
（`README.md:3,7,9`），且无任何 CTAP 客户端 / 传输代码。

⇒ 与既有结论一致：**生产可用的第三方 hybrid 认证器实现≈零**，跨设备扫码注册继续**另案**（337「关联」末条）。
