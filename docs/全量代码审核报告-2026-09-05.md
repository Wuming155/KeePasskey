## 一、执行摘要

工程的**安全骨架是真做过的**，不是装饰：KDBX4 主派生管线（`compositeKey` → `transformedKey` → `cipherKey = SHA-256(masterSeed‖transformedKey)` → `hmacKey64 = SHA-512(…‖0x01)`）与六个格式 UUID 经逐字节核对与官方一致；认证先于解密（encrypt-then-MAC）、`HmacBlockStream` 终止块补校验、XXE 四项加固、`SyncCache` 真原子写、TLS 零削弱、QuickUnlock 的 PBKDF2 校验器 + 指数退避熔断 + 全程 CharArray、模块依赖零违规、零 mock 框架（全部手写 Fake + 真加解密）、13 处随机量全走 `SecureRandom`。核心链路的质量高于同类个人项目的常见水平。

但 `AGENTS.md` 的两项自我评价**不成立**，需要如实修正：

1. **「Mock/假桩清零、所有 UI 功能真实接线」不成立**。关键词层面确实干净（`src/main` 内 `TODO`/`FIXME`/`stub`/`mock` 零命中），但"接线断裂"形态的假功能大量存在：设置模块约 35 个开关是**纯内存回显**（不持久化、除设置页自己以外零消费者，含「接受所有证书」「允许明文流量」「跳过 DAL 校验」这类有安全语义的开关）；7 处按钮点了只弹 Snackbar（导出 KDBX / 导出 XML / 导入 / 模板安装 / 子库挂载 / 密钥文件导出 / 调试日志导出）；**「更改主密钥」是完全假的**——用户改完密码收到"主密钥已更新"，而数据库主密码毫发无损。
2. **测试数字三处互不相同且都不等于实际**。实际 228 个（app 70 / core 21 / crypto 35 / **database 55** / sync 47）；`AGENTS.md:94` 写 223（database 50），同一文件 `:50` 写 212，`DELIVERY_PLAN.md` 三处写 114。且 app 的 70 个里有 14 个在测 `FakeVaultRepository` 这个测试替身本身，对回归保护贡献为零。

### P0-4 ChaCha20 保存时写出 16 字节 EncryptionIV，官方 KeePass 无法打开该文件

**位置**：`database/src/main/java/com/keepasskey/database/file/KdbxFile.kt:328-331`、`crypto/src/main/java/com/keepasskey/crypto/cipher/ChaCha20CipherEngine.kt:66-68`

```kotlin
// KdbxFile.kt:328-331 —— 与 header.cipherUuid 无关，恒 16 字节
val freshEncryptionIv = ByteArray(16)
secureRandom.nextBytes(freshEncryptionIv)

// ChaCha20CipherEngine.kt:66-67 —— 静默截断，掩盖了上面的错误
val nonce = if (iv.size > 12) iv.copyOfRange(0, 12) else iv
```

**现象**：KDBX4 规范要求 Header 字段 7 的长度等于所选算法的 IV 长度（ChaCha20 = 12）。KeePass 2.61.1 的 `ChaCha20Cipher` 构造器对 `pbIV12.Length != 12` 直接抛 `ArgumentOutOfRangeException`，KeePassXC 同样硬校验。因此：凡以 ChaCha20 保存的库都是官方客户端**打不开的文件**；用 12 字节 IV 的 KeePass 原文件被本应用保存一次后即被破坏。因读侧对称截断，往返自测永远通过 —— 这是"自读自写闭环掩盖互操作缺陷"的典型。

**修法**：IV 长度按 `cipherUuid` 决定（ChaCha20 → 12，AES-CBC/Twofish → 16），并把引擎里的静默截断改成长度不符即抛 `CipherException`。

### P0-5 未认证的 Header 字段长度直接驱动数组分配

**位置**：`database/src/main/java/com/keepasskey/database/file/KdbxHeader.kt:190-195`、`database/src/main/java/com/keepasskey/database/io/LittleEndianUtil.kt:40-41`；同一模式见 `crypto/.../VariantDictionary.kt:178-183`、`database/.../file/InnerHeader.kt:95-96`

```kotlin
// KdbxHeader.kt:190-195 —— 此时尚未做任何 SHA-256 / HMAC 校验
val fieldLenBytes = LittleEndianUtil.readBytes(inputStream, 4)
val fieldLen = LittleEndianUtil.bytesToInt(fieldLenBytes)
val fieldData = LittleEndianUtil.readBytes(inputStream, fieldLen)   // ByteArray(length)
```

**现象**：`fieldLen = 0x7FFFFFFF` → 立即尝试分配 2 GiB（`recordingStream` 再复制一份）；`0xFFFFFFFF` → `length = -1` → `NegativeArraySizeException`，既非 `KdbxCorruptFileException` 也非 `IOException`，穿透了"解析失败抛类型化异常"的契约。头部与 KDF 参数区在 HMAC 之前解析，因此这是**无需口令即可触发的拒绝服务面**（打开任意恶意 `.kdbx` 即崩溃/OOM）。与已经做得很好的 Argon2 参数上界校验（`KdbxHeader.kt:318-344`）标准明显不一致。

**修法**：`readBytes` 增加 `require(length in 0..MAX_FIELD_BYTES)` 并抛 `KdbxCorruptFileException`，头部字段上界取 1 MiB 量级；`VariantDictionary` 与 `InnerHeader` 同步加固。

### P0-6 受保护值 Base64 解码失败时静默降级，导致其后所有密码字段解密错乱

**位置**：`database/src/main/java/com/keepasskey/database/xml/KdbxXmlGroupReader.kt:251-263`

```kotlin
override fun end() {
    val value = rawValue ?: return
    val protectedString = if (isProtected && innerStreamCipher != null) {
        val decoded = try {
            Base64.getDecoder().decode(value)
        } catch (_: Exception) {
            value.toByteArray()          // ← 长度与原文不同，keystream 位置就此偏移
        }
        val plainBytes = innerStreamCipher.processBytes(decoded)
```

**现象**：`InnerRandomStreamCipher` 是**有状态流密码**，keystream 消费必须与文档顺序严格对齐。一旦某个 `<Value Protected="True">` 解码失败并用原始字符字节顶替，其后**每一个**受保护字段都会解出乱码，且全程无任何异常 —— 用户只会看到一堆乱码密码，并可能把乱码保存回库（`saveEntry` 对非空受保护字段照原样回写）。另注意此处未 `trim()`（对照 `KdbxXmlValueUtil.parseRequiredUuid:16` 是 trim 的），任何带缩进/换行的 `<Value>` 都会走进这条降级路径。

**修法**：删除 fallback，解码失败直接抛 `KdbxCorruptFileException`；解码前 `trim()`。

### P0-7 Passkey 私钥被物化为不可变 String

**位置**：`app/src/main/java/com/keepasskey/app/passkey/PasskeyAssertionActivity.kt:135-148`；同源问题见 `crypto/src/main/java/com/keepasskey/crypto/passkey/PasskeyCryptoEngine.kt:94-95,134,150,187,203,372,384`

```kotlin
val privChars = passkeyData.privateKey.readChars()
val privBytes = try {
    val privStr = String(privChars).trim()      // ← 私钥落地为不可变 String
    ... BigInteger(privStr, 16) / Base64.getDecoder().decode(privStr)
} finally { Arrays.fill(privChars, '0') }
```

**现象**：`CharArray` 清零了，但 `String(privChars)`、`.trim()`、`BigInteger` 内部 `int[]` 副本都无法擦除，留在堆里等 GC —— 一次堆转储即可读出 FIDO2 私钥。生成侧同病：`PasskeyCryptoEngine.kt:94` 用 `String.format("%064x", priv.d)` 承载 ES256 标量、`:134/:187` 用 Base64 String 承载 Ed25519 种子与 RSA PKCS#8，而 `:91-93` 的 KDoc 声称"字节数组与 BigInteger 中间量均不落 String"，与代码直接矛盾。

**违反**：敏感数据铁律（硬约束 2）。

**修法**：`ProtectedString` 已有 `ByteArray` 直入构造路径；私钥全程 `ByteArray` + `Arrays.fill`，hex/Base64 若为格式必需则自写 `CharArray` 编解码并清零。注：`KdbxEntry` 受保护字段以字符串承载是 KDBX 格式层边界（`AGENTS.md` 已如实声明），但**编解码中间量不该再放大这一暴露面**。

### P1-10 仅密钥文件（无密码）的官方库无法打开

**位置**：`database/.../file/KdbxFile.kt:422-441`


## 八、已核实无误的关键点

列出抽查确认正确的重要实现，避免上面的清单造成"全盘崩坏"的误读。

**KDBX4 密钥派生管线**（逐项对照 KeePass 2.61.1 `KdbxFile.ComputeKeys` + `CryptoUtil.ResizeKey`，`KdbxFile.kt:444-472`）
- `compositeKey = SHA-256(SHA-256(pwUtf8) ‖ keyFileKey)`，密码字节与 `passwordHash` 用后立即 `Arrays.fill`；`transformedKey` 拼入 65 字节缓冲后立即擦除。
- `cipherKey = SHA-256(masterSeed ‖ transformedKey)`、`hmacKey64 = SHA-512(masterSeed ‖ transformedKey ‖ 0x01)`、`headerHmacKey = SHA-512(LE64(0xFFFF_FFFF_FFFF_FFFF) ‖ hmacKey64)`，读写两侧完全对称，与 pykeepass / KeePassXC 交叉一致。

**HMAC 块流**（`HmacBlockStream.kt:32-35,199-215,271-276`）：`blockKey = SHA-512(LE64(blockIndex) ‖ hmacKey64)`、签名数据 `LE64(index) ‖ LE32(size) ‖ data`、`size == 0` 终止块单独校验，与官方逐字节一致；`verifyEndOfStream()` 弥补了 GZip 提前停止拉取导致终止块漏校验的经典缺口 —— 这个设计很到位。

**认证先于解密**（`KdbxFile.kt:128-150`）：`HmacBlockInputStream` → `createDecryptingStream` 的顺序保证每块明文交付前已通过 HMAC，同时消解了 JDK `CipherInputStream` 静默吞掉 `BadPaddingException` 的已知隐患。

**载荷层序与内层随机流**：解密 → GZIP → 内层 Header → XML 与官方 `Read.cs/Write.cs` 一致；ChaCha20 取 `SHA-512(streamKey)[0,32)` 为 key、`[32,44)` 为 nonce，Salsa20 取 `SHA-256(streamKey)` 且 IV 为官方常量，派生中间量均在 `finally` 清零。

**六个格式 UUID** 全部与官方一致（AES256-CBC / ChaCha20 / Twofish / AES-KDF / Argon2d / Argon2id，`KdbxConstants.kt:72-85`）。

**KDF 参数上下界**（`KdbxHeader.kt:318-344`）：内存 `[1MiB, 4GiB]`、迭代 `[1, 2^24]`、并行度 `[1,64]`、AES 轮数 `[1, 2^28]` + `maxMemory()/2` 动态门槛；UInt64 溢出被正确吸收（`0xFFFF…FF` 读作 `-1L` 后被 `< min` 拒绝）。`getUInt32/getUInt64` 的 Int/Long 双形态宽容正是与官方互操作所必需的。

**XXE 与实体膨胀**（`KdbxXmlParser.kt:41-58`）：`disallow-doctype-decl` + 禁用内外部实体 + `resolve-dtd-uris=false`，并以覆写 `resolveEntity` 抛异常做纵深兜底；DTD 既禁，Billion Laughs 一并被阻断。

**.NET Ticks 与日期歧义**（`KdbxXmlTimeHelper.kt:19-48`）：纪元差 62,135,596,800 秒、每秒 10^7 ticks、`Math.floorDiv/floorMod` 正确处理负数；ISO-8601 嗅探用 `^\d{4}-\d{2}-\d{2}`，标准 Base64 字母表不含连字符，因此含大写 `T` 的 Base64 时间值不会被误判 —— 这个坑被显式识别并封住了。

**流式化宣称为真**：全模块 `ByteArrayOutputStream` 使用点逐一核查（头部字节、探针单块、单个附件字段、VariantDictionary、CBOR），load/save 全链路无整库明文/密文物化；`HmacBlockStream.readAll/writeAll` 的"仅限测试"声明经验证成立；`NonClosingInputStream/OutputStream` 正确隔断级联 close。

**Passkey 签名与 COSE**：`ECDSASigner(HMacDSAKCalculator(SHA256Digest()))` 即 RFC 6979 确定性 k，结构上排除 nonce 复用导致的私钥泄露；`buildAuthenticatorData` 与 WebAuthn §6.1 一致；`CoseKey` 标签顺序 `1,3,-1,-2(,-3)` 符合 CTAP2 canonical CBOR 排序；`CborEncoder.writeTypeAndArgument` 严格最短形式，`Long.MIN_VALUE` 无溢出。

**同步引擎**：三哈希状态机六条主分支各有明确动作与事件；无 ETag 退化路径真实存在且有 3 个用例覆盖；`markResolvedAndUpload(expectedEtag)` + `pendingRemoteEtag` 确实用冲突时刻 ETag 做 `If-Match`，412 时清会话并引导重新同步；`cleanEtag` 结构级解析不误伤含 `W`、`/` 的不透明 ETag；`SyncCache` 三处写入均为 `.tmp → flush → fd.sync() → moveAtomically`；三方合并 base 取独立 `basecache`；"云端已上传但本地保存失败"如实报错。

**TLS 未被削弱**：全仓库 `TrustManager|HostnameVerifier|trustAllCerts|SSLContext|sslSocketFactory|checkServerTrusted|ALLOW_ALL` **零命中**。
