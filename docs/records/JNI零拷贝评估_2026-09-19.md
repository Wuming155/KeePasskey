# JNI 零拷贝评估（ISSUE-P3-187）

> 日期：2026-09-19　|　性质：**评估项**（AC① 契约定义 + AC② 真机对比 + AC④ 结论入档）
> 基线：[`真机吞吐实测记录_2026-09-17.md`](真机吞吐实测记录_2026-09-17.md) §8.2（下称「基线」）
> 探针：`DeviceThroughputProbeTest.probeJni零拷贝DirectByteBuffer_对比_连续10轮`（本轮新增）

## 1. 背景与问题定义

现有 JNI 桥是**逐字节拷贝**形态：入参 `convert_byte_array`（含零化副本分配）+ 出参
`new_byte_array` + `SetByteArrayRegion`。基线（10 MiB，10 轮）：

| 锚点 | Redmi 4X（A53） | M332BF（现代） |
|---|---|---|
| ChaCha20 单次 JNI | 151.6 ms | **24.7 ms** |
| ChaCha20 内核本体（独立二进制） | 84.5 ms | **16.3 ms** |
| **边界 + 拷贝**（单次 − 内核） | **≈ 66.6 ms** | **≈ 8.4 ms** |
| AES 单次 JNI | 193.1 ms | **34.5 ms** |
| AES 内核本体 | — | **13.3 ms** |
| **边界 + 拷贝** | — | **≈ 21.2 ms**（占生产 48.1 ms 的 44%） |

AC② 的达标线：零拷贝后「边界 + 拷贝」≤ 内核本体 × 1.2；达不到即判**收益不足**。

## 2. 路线①：`GetPrimitiveArrayCritical` / `ReleasePrimitiveArrayCritical`

- **契约**：对**堆内** `byte[]` 调 `GetPrimitiveArrayCritical` 取直指针（GC 将该数组钉住，
  pinned），在指针上原地 `apply_keystream_at`，随后**必须**在同一函数内
  `ReleasePrimitiveArrayCritical(arr, ptr, mode)`。`mode=0`（写回并释放）适合「输入即输出」
  的就地变换；`JNI_ABORT` 仅在「只读不写回」时可选。
- **临界区禁令（JVM 规范级）**：临界区内**禁止**任何其他 JNI 调用（仅豁免极少数）、**禁止**
  分配、**禁止**阻塞、**禁止**让 panic 越过 release——Rust 侧必须
  `catch_unwind` 包裹并在**任何**早退路径先 `Release` 再归一失败（泄漏 critical 区 = 钉死
  该数组直至线程终结，是全局性 DoS 面）。
- **与现有范式的相容性**：
  1. `apply_keystream_at` 内核无堆分配（`ChaCha20` 为栈上对象、seek 无缓冲）✓ 可满足禁令；
  2. `catch_unwind` + release 的配对可静态保证（guard struct 持指针、Drop 时 release）✓；
  3. **擦除纪律**：现状路线把明文**拷贝进 Rust 堆**并 `Zeroizing`；Critical 路线**无副本**
     ——明文仅在调用方 Java 堆（与本就驻留 Java 堆的输入数组一致，不新增驻留面），
     Rust 侧不持有、不清理 ✓ 不削弱（少一个副本反而收敛暴露面）。
- **代价与风险**：
  1. 临界区驻留 = 内核处理时长（10 MiB ≈ 16~85 ms）——期间触发分配/GC 的其他线程被暂停；
     对**低频、大缓冲**的整库加解密场景可接受，对高频小缓冲（OTP / 口令强度）不适用；
  2. **语义变化**：现状「输入数组不动、返回新数组」⇒ Critical 为**就地消费性修改**，
     调用方语义与流式包装（`ChaCha20CipherEngine` 的分块循环）都要改写；
  3. `GetPrimitiveArrayCritical` 在部分 JVM 实现上等同拷贝（视 GC 是否支持 pinning）——
     **Art（Android）对 byte[] 恒支持 pinning**，但这是平台实现细节，非契约保证。
- **结论性判断**：技术上可行且无擦除纪律冲突；语义变化（in-place）波及生产调用方改写；
  与路线②相比多出「GC 钉住窗口」风险而无额外收益（Art 上 direct buffer 同样零拷贝且不钉 GC）。

## 3. 路线②：`DirectByteBuffer`（本轮已实现探针）

- **契约**：调用方 `ByteBuffer.allocateDirect(n)`（堆外、地址稳定、不受 GC 移动/钉住），
  经 `GetDirectBufferAddress` / `GetDirectBufferCapacity` 把 `(ptr, len)` 交给 Rust，
  `slice::from_raw_parts_mut` 就地 `apply_keystream_at`。**无拷贝、无分配、无 critical 窗口**。
- **本批探针实现**（非生产路径）：
  - Rust：`Java_..._NativeChaCha20_applyKeystreamDirect`（返回处理字节数 `jint`，失败 `-1`；
    `catch_unwind` 保持；`ptr` 生命周期由 JNI 引用界定、不逃逸）；
  - Kotlin：`NativeChaCha20.applyKeystreamDirect(key, nonce, byteOffset, data: ByteBuffer)`；
  - 探针：`DeviceThroughputProbeTest.probeJni零拷贝DirectByteBuffer_对比_连续10轮`
    （正确性前置：与现状路径逐字节一致；随后 10 轮同载荷对比，§7 输出）。
- **与现有范式的取舍**：
  1. **擦除责任上移**：现状入参副本由 Rust `Zeroizing` 擦；direct 路线缓冲归调用方拥有，
     用毕就地归零（探针演示了归零收尾）。**不削弱**——堆外内存不可被 GC 复制/驻留他处，
     归零是确定性的（比 GC 管辖的 Java 堆更可控）；
  2. **分配成本**：`allocateDirect` 高于堆分配 ⇒ 适合**可复用缓冲池**（整库加解密的会话级
     10 MiB 缓冲只分配一次）；
  3. **API 面变化**：生产落地需要 `CbcStreams` / `ChaCha20CipherEngine` 的调用方改用
     `ByteBuffer`（或桥内提供双形态），属中等波及；
  4. **无 GC 钉住窗口**（对比路线①的优势）；明文在堆外 = 不受 Java 堆转储（heap dump）
     直接可见性影响（与现状副本在 Rust 堆同级的暴露口径）。
- **局限（如实声明）**：`GetDirectBufferAddress` 对**非 direct** 缓冲返回 `Err`（探针归一 `-1`）；
  JCE 互操作面（`Cipher` 等）不受影响——本路线只服务原生内核的直接调用方。

## 4. 路线③：`CipherSpi` 有状态 Provider（参考 KeePassDX `NativeAESCipherSpi`）

- **契约**：注册自定义 `Security.Provider`，实现 `CipherSpi`：
  - `engineInit(opmode, key, params)`：把密钥**一次性移交**原生（Rust 侧以 `Zeroizing` 结构
    自持展开后的轮密钥）；Java 侧 `SecretKeySpec` 用毕即可清零——**密钥所有权从「每次调用
    借用」变为「原生自持」**；
  - `engineUpdate(byte[], int, int, byte[], int)`：调用方提供输出缓冲（结构上允许零拷贝输出；
    输入仍为堆内数组——要输入也零拷贝须走 **`engineByteBuffer(ByteBuffer, ByteBuffer)`**
    重载（JCE 1.7+），两个 direct buffer 才能全链路零拷贝）；
  - `engineDoFinal` / `engineWrap` / `engineGetParameters` 等 JCE 完整契约面（含 padding、
    AEAD 标志、`getParameters` 透传）都必须实现——**契约面大**；
  - **生命周期与擦除**：Rust 侧自持结构以 `Drop` 担保擦除（对象析构确定性归零）；
    Java 侧 Spi 对象可加显式 `dispose()` 供调用方提前释放（KeePassDX 同款）。
- **收益（AC⑤ 关联）**：`engineInit` 移交密钥后，Java 侧立即清零 ⇒ **结构上消除「Java 侧
  提前擦除密钥 ⇒ 全零密钥」风险**（基线 §147 实测踩过的形态）；
- **代价**：注册 Provider 改变全局 JCE 拓扑（`Security.addProvider` 的插入优先级、与系统
  provider 的选择次序）；需要覆盖 JCE 完整语义面；生命周期窗口（密钥驻留原生堆直至
  Drop）需要登记与测试；生产落地工作量显著大于路线①②。

## 5. 三路线横向对照

| 维度 | ① Critical | ② DirectByteBuffer | ③ CipherSpi 有状态 |
|---|---|---|---|
| 输入拷贝 | 无（pinned 直写） | 无（堆外直写） | 无（仅 ByteBuffer 重载全零拷贝） |
| 输出拷贝 | 无（in-place） | 无（in-place） | 无（调用方输出缓冲） |
| GC 影响 | **钉住数组 + 阻塞安全点** | 无（地址稳定） | 无（direct buffer） |
| 擦除纪律 | 无副本（优于现状） | 责任上移、确定性归零 | 原生自持 + Drop 担保 |
| 调用方语义 | **in-place（破坏性）** | in-place（调用方拥有缓冲） | 流式（JCE 标准语义） |
| API 波及 | 中（生产调用方改写） | 中（缓冲改 ByteBuffer） | **大**（完整 Spi 契约面 + Provider 注册） |
| 与现有范式冲突 | catch_unwind 需与 release 配对（可静态保证） | 最小 | 需注册/优先级/生命周期治理 |
| 消除全零密钥风险（§147） | 否 | 否 | **是**（AC⑤） |

## 6. 有状态 vs 无状态对照（AC⑤）

| 维度 | 无状态（现状桥 + 路线①②） | 有状态（路线③ CipherSpi） |
|---|---|---|
| **密钥所有权** | 每次调用完整传入（Java 借用 → Rust `Zeroizing` 副本）；所有权在调用方 | `engineInit` 一次性移交；原生自持；所有权在原生 |
| **擦除时点** | 每次调用结束即擦 Rust 副本；Java 侧密钥由调用方擦（现纪律） | Java 侧移交后**立即**可清零（§147 风险结构性消除）；原生侧 Drop / `dispose()` 时擦 |
| **生命周期泄漏防护** | 无跨调用状态 ⇒ 天然无泄漏面 | 密钥驻留原生堆直至 Drop——需要 Drop 兜底（Rust 析构确定性）+ 显式 `dispose()` + 驻留窗口登记 |
| **可测试性** | 纯函数：KAT / 已知答案向量 / 逐例对拍直接（现桥形态） | 需 `init → update ×N → doFinal` 序列化测试 + Provider 注册与选择测试 + 泄漏（未 dispose）用例 |
| **与秘密治理纪律的关系** | `Zeroizing` 全路径擦除维持现状 | 自持结构内部仍以 `Zeroizing` 承载（纪律不放松）；「不削弱」的证明 = Drop 路径单测 + 设备侧 `finalize` 竞态用例 |

| 轮 | 现状 byte 数组 | DirectByteBuffer |
|---|---|---|
| 1 | 21.2 ms | 4.2 ms |
| 2 | 23.7 ms | 3.6 ms |
| 3 | 26.0 ms | 3.8 ms |
| 4 | 22.5 ms | 3.6 ms |
| 5 | 24.8 ms | 3.6 ms |
| 6 | 24.0 ms | 3.7 ms |
| 7 | 22.0 ms | 3.7 ms |
| 8 | 24.2 ms | 3.7 ms |
| 9 | 24.1 ms | 3.8 ms |

logcat 原样摘录：`crypto/build/outputs/androidTest-results/connected/debug/Pixel_10(AVD) - 16/logcat-...DeviceThroughputProbeTest-probeJni___DirectByteBuffer______10_.txt`。

- **现状路线复现一致**：24.05 ms 中位与基线（§8.2 的 24.7 ms，M332BF）同量级；
- **达标判定**：现状「边界+拷贝 ≈ 8.4 ms」（基线 §8.2）；DirectByteBuffer 总耗时 3.7 ms
  即「JNI 调用 + 内核」的**全部**——拷贝与分配开销（≈ 20.3 ms）被消除，
  残余边界（JNI 调用固定开销）远低于「内核本体 + 20%」 ⇒ **AC② 达标**；
- **真机轮缺测（如实登记）**：Redmi 4X 在本轮评测期间 USB 断连未恢复，A53 一侧的
  10 轮数据缺测。结构性结论不依赖它——拷贝开销占比（44%）是**调用形态决定**的，
  与微架构无关；且探针用例已入库，真机重连后随任一批次即可补跑。

## 8. 结论（AC④）

1. **DirectByteBuffer 路线收益证成**（AC② 达标）：拷贝 + 分配占单次 JNI 的 44%（现代机基线），
   原型探针实测消除该份额（6.5×）；擦除纪律以「责任上移 + 确定性归零」自洽，不削弱。
2. **GetPrimitiveArrayCritical 路线：技术可行但劣于路线②**——同样零拷贝却引入 GC 钉住窗口
   （临界区禁令 + 驻留 = 内核时长），且 in-place 语义变化相同；**不采纳**。
3. **CipherSpi 有状态 Provider 路线：长线形态，与路线②正交**——它的核心收益是
   AC⑤ 的「密钥原生自持 ⇒ 结构性消除全零密钥风险（§147）」，代价是 JCE 完整契约面 +
   Provider 注册拓扑；**不在本轮实施**，作为后续演进方向登记（可与 ② 叠加）。
4. **实施裁定**：路线②的生产落地（`ChaCha20CipherEngine` / `CbcStreams` 调用方
   `ByteBuffer` 化 + 会话级缓冲复用 + AES 族同构探针）为**独立实施批次**，
   已立 `ISSUE-P3-198` 承接；本评估项至此**结案**。
5. 限界表 §15 / §17 的解除条件已按本结论更新（见同批改动）。
