# 软件工程质量审查记录（2026-10-05）

## Rust 内核与 JNI

### QE-01 `crypto/src/main/rust/src/jni_bridge_ext.rs:201` — AES/Twofish 两个 JNI 入口约 45 行逐字重复（medium，维度①）

- **问题描述**：`twofish_cbc_jni`（124-168 行）与 `aes_cbc_jni`（201-245 行）函数体 diff 仅差 3 行（140 行 `BLOCK_LEN` ↔ 217 行 `aes_cbc::BLOCK_LEN`，两常量均为 16；145/147 行与 222/224 行的内核调用），判空、`catch_unwind`、三个入参转 `Zeroizing`、长度闸门、IV 回写、`new_byte_array`+`set_byte_array_region`、失败归一 null 其余约 45 行逐字一致；200 行文档注释原样承认「与 `twofish_cbc_jni` 同构，仅内核不同」。这是安全敏感的边界样板（擦除语义、panic 归一、有符号闸门全在其中），两份拷贝意味着任一侧修复必须记得同步另一处，否则两条 cipher 路径静默漂移。
- **改进建议**：合并为单个私有函数 `block_cbc_jni(env, key, iv, data, encrypt, kernel: fn(&[u8], &mut [u8], &[u8]) -> Option<Vec<u8>>)`，加密侧传 `aes_cbc::cbc_encrypt` / `twofish_cbc::cbc_encrypt`，解密侧同理；两个 `#[no_mangle]` 导出仅一行转发。两内核 `cbc_encrypt/decrypt` 签名完全一致（见 `aes_cbc.rs:64/95`、`twofish_cbc.rs:60/89`），函数指针方案不改 JNI 定长布局契约。
- **证据**：函数体逐行比对差异恰为上述 3 行；限界表未登记豁免（`grep twofish` 零命中）。

### QE-02 `crypto/src/main/rust/src/aes_cbc.rs:64` — CBC 加/解密「拷出形态」与「原地形态」双份手写实现（medium，维度①）

- **问题描述**：`cbc_encrypt`/`cbc_decrypt`（64-89 / 95-120 行）与 `cbc_encrypt_in_place`/`cbc_decrypt_in_place`（128-149 / 155-177 行）是同一套 CBC 链接逻辑的两份实现：相同的参数闸门（65/96/129/156 行）、相同的链值 `Zeroizing` 单缓冲（71/101/135/161 行）、相同的逐块 XOR-变换-推进循环。原地版 KDoc 自述「与 `cbc_encrypt` 语义逐字节一致（含 `iv` 出口契约）」（124 行），一致性目前仅靠人工对照 + 测试维持；两形态分别服务整块 JNI 路径（`jni_bridge_ext.rs:222/224`）与 direct ByteBuffer 零拷贝路径（`311/313`），任一侧漂移将导致两条生产管线密文不一致。
- **改进建议**：拷出形态改为薄委托：`pub fn cbc_encrypt(key, iv, data) -> Option<Vec<u8>> { let mut out = data.to_vec(); cbc_encrypt_in_place(key, iv, &mut out)?; Some(out) }`（解密同理），闸门与循环只留 in_place 一份；既有 NIST KAT 与等价用例（`aes_cbc_tests.rs:202-235`）足以锁定等价。
- **证据**：四个函数的全部失败路径均先于 `iv.copy_from_slice`（87/118/147/175 行）返回，空数据边界亦等价，委托不改可观测语义；模块头「与 twofish_cbc 完全同构」是跨文件有意设计，twofish 侧无原地形态。

### QE-03 `crypto/src/main/rust/src/twofish_cbc.rs:70` — twofish 仍用 aes_cbc 文件头明令禁止的旧循环形态（low，维度①）

- **问题描述**：`aes_cbc.rs:14-16` 立有「**性能纪律（§147 实测教训）**：逐块循环里**禁止**任何逐块分配 / 逐块 `Vec::push` / 逐块 `Zeroizing`」（原文载明早期版本每块构造 `Zeroizing<[u8;16]>` + `extend_from_slice` 单块开销显著高于 AES 本体，现版本改为预分配输出缓冲直接写切片、链值单缓冲承载）；而同 crate 的 `twofish_cbc.rs` 加/解密循环（70-79 / 98-108 行）仍是每块 `let mut block = Zeroizing::new(*as_block_ref(chunk))` + `out.extend_from_slice(&block[..])` 的旧形态（71/100 与 78/107 行）。且 `aes_cbc` 已有 in_place 零拷贝变体（`ISSUE-P3-198`）而 twofish 完全没有；`aes_cbc.rs:3` 自述两模块「完全同构」实际已不同构。Twofish 自述「作用于整库数据流，属数据面热点」（`twofish_cbc.rs:8-10`）。
- **改进建议**：twofish 改写为 aes_cbc 同款「预分配 out + 链值单缓冲 + 直接写切片」循环；若采纳 QE-02 的委托整改，可一并补 `*_in_place` 变体使两内核面完全对称。
- **证据**：`aes_cbc.rs:15-16` 禁令原文与 `twofish_cbc.rs:71/100`、`78/107` 代码逐字对应；`grep twofish` 于限界表无命中。

### QE-04 `crypto/src/main/rust/src/jni_bridge_ext.rs:301` — direct ByteBuffer 取址/容量校验 unsafe 样板两处逐字重复（low，维度①）

- **问题描述**：`aes_cbc_direct_jni`（301-309 行）与 `applyKeystreamDirect`（442-450 行）各自手写同一序列：`env.get_direct_buffer_address(&data).ok()?` → `env.get_direct_buffer_capacity(&data).ok()?` → `ptr.is_null() || len == 0` 判定 → `unsafe { std::slice::from_raw_parts_mut(ptr, len) }`，连 SAFETY 注释（「ptr 在 buffer 存活期内有效；len 取自 GetDirectBufferCapacity…本函数内不逃逸」）都逐字重复；grep 全文件仅此两组。unsafe 样板重复意味着任何一处修订（如容量上界校验）需人工双改。
- **改进建议**：抽 `unsafe fn direct_buffer_slice<'a>(env: &JNIEnv, data: &JByteBuffer) -> Option<&'a mut [u8]>`（含唯一一份 SAFETY 注释），两个 direct 入口共用。
- **证据**：两处上下文一致（均在 `catch_unwind` 闭包内、入参 `JByteBuffer`、失败映射 -1）；缓和性事实：`jni_bridge_ext.rs:425` KDoc 明言 ChaCha20 直扣为非生产路径的真机对比探针，故定级 low。

### QE-05 `crypto/src/main/rust/src/jni_bridge_ext.rs:67` — JNI `catch_unwind` 护栏样板跨 8 个导出路径重复（low，维度①）

- **问题描述**：每个 `#[no_mangle]` 导出函数都手写同一序列：`let outcome = catch_unwind(AssertUnwindSafe(|| -> Option<...> { ... }));`，随后按返回型收尾。该 `catch_unwind` 护栏在 **8 处**导出路径原文一致：`deriveKey`(67-90)、`twofish_cbc_jni`(135-167)、`aes_cbc_jni`(212-244)、`aes_cbc_direct_jni`(298-324)、`estimate`(346-359)、`applyKeystream`(384-406)、`applyKeystreamDirect`(439-464)、`passkey_sign_jni`(504-524)。任何一处 panic→失败归一语义的修订都需人工同步 8 处，存在静默漂移风险。
- **改进建议**：抽一个按返回型参数化的护栏（`jbyteArray` / `jintArray` / `jint` 三类各一薄包装，或返回 `Result<Option<T>, ()>` 的泛型护栏），各导出函数仅留业务闭包；不改 JNI 定长布局契约。**注意**：原设想「单一泛型 `jni_guard<F, R>() -> Option<R>` 内写 `null_mut()`」不可编译（`Option<R>` 与裸指针不同型），须按返回型分型。
- **证据**：8 处 `catch_unwind(AssertUnwindSafe(...))` 逐字一致；收尾 `match` 分两类——6 处 `Ok(Some(arr)) => arr, _ => null_mut()`（`deriveKey` 87-90、`twofish_cbc_jni` 164-167、`aes_cbc_jni` 241-244、`estimate` 356-359、`applyKeystream` 403-406、`passkey_sign_jni` 521-524），2 处 `Ok(Some(n)) => n, _ => -1`（`aes_cbc_direct_jni` 321-324、`applyKeystreamDirect` 461-464，二者返回 `jint`）。限界表无该样板豁免。

### QE-06 `crypto/src/main/rust/src/jni_bridge_ext.rs:80` — 输出字节数组发射样板跨 5 处重复（low，维度①）

- **问题描述**：把受管结果回写为 Java 数组的序列 `env.new_byte_array(len).ok()?` → `as_jbyte(&...)`（unsafe）→ `set_byte_array_region(...).ok()?` → `into_raw()` 在 `deriveKey`(80-84)、`twofish_cbc_jni`(157-161)、`aes_cbc_jni`(234-237)、`applyKeystream`(396-399)、`passkey_sign_jni`(514-517) 共 **5 处**逐字重复；`estimate` 的 `IntArray` 发射(351-352)为同构的 `new_int_array`+`set_int_array_region` 变体。SAFETY 注释（u8↔i8 同宽同布局）亦随之复制。
- **改进建议**：抽 `unsafe fn emit_byte_array(env: &JNIEnv, data: &[u8]) -> Option<jbyteArray>`（含唯一 SAFETY 注释）与 `fn emit_int_array(env: &JNIEnv, data: &[i32]) -> Option<jintArray>`，5 处 + `estimate` 共用。
- **证据**：5 处 `new_byte_array(... as jint).ok()?` + `as_jbyte` + `set_byte_array_region(...).ok()?` + `into_raw()` 序列逐项对齐；`as_jbyte` 定义(41-44)。

### QE-07 `crypto/src/main/rust/src/{aes_cbc,twofish_cbc}.rs:64,60` — 两内核 `cbc_encrypt/decrypt` 跨文件同构但已实质漂移（low，维度①）

- **问题描述**：`aes_cbc.rs:3` 自述与 `twofish_cbc`「完全同构」。两者 `cbc_encrypt`(aes 64-89 / twofish 60-83) 与 `cbc_decrypt`(aes 95-120 / twofish 89-112) 确为同一套「链值单缓冲 + 逐块循环 + `iv` 原地回写 + 参数闸门」结构，仅内层符号相反（加密先 XOR 链值再 transform、解密先 transform 再 XOR；解密侧链值取密文）。但 `aes_cbc` 已下沉 `cbc_encrypt_in_place`/`cbc_decrypt_in_place`(128-177) 而 `twofish_cbc` 完全没有；且 `twofish` 仍用 QE-03 点名的旧循环形态（逐块 `Zeroizing<Block>` + `extend_from_slice`）。两模块名义同构、实际已不对称，漂移风险随各自迭代上升。
- **改进建议**：采纳 QE-02 的委托整改后，为 `twofish_cbc` 补 `*_in_place` 变体，使两内核面完全对称；或抽 `fn cbc_loop(key, iv, data, encrypt, transform)` 让两内核共享循环体。
- **证据**：`aes_cbc.rs:3` 自述；两文件 `cbc_encrypt/decrypt` 结构逐项对齐；twofish 无 in_place、旧循环见 QE-03。

### QE-08 `crypto/src/main/rust/src/strength.rs:160` — 热路径每次调用全量分配 `Vec<char>`/`String`（low/medium，维度②）

- **问题描述**：`estimate`(158-279) 在文档明示的「全库审计对每条口令调用」热路径(23-29)上，每次都分配 `chars: Zeroizing<Vec<char>>`(160)、`lowered: Zeroizing<String>`(200)；此外同函数内经 `date_like_weight` 各次分配 `Zeroizing<String>`（499、520 两处）、经 `unique_char_count` 分配 `Vec<char> others`(548)、经 `minimal_period` 分配 `Vec<usize>`(582)。其中 `Vec<char>` 把口令以 UTF-32 物化（长度×4 字节），对长口令与超长恶意输入放大堆压力；该模块虽已把三条平方级路径线性化，但**逐调用全量分配**未解决。
- **改进建议**：复用调用方传入的 UTF-8 字节直接做字符类别/键盘/周期判定（避免 `Vec<char>` 物化）；`lowered` 用 `&[u8]` 小写视图替代 `String` 分配；`minimal_period` 改用固定上限滚动 KMP（见 QE-10）。
- **证据**：`strength.rs:160/200/582` 三处主分配 + `499/520/548` 三处次分配；模块头(23-29)自陈热路径；`MAX_ANALYZED_CHARS=256`(84) 仅约束模式识别前缀，全量分配不受其限。

### QE-09 `crypto/src/main/rust/src/jni_bridge_ext.rs:80` — 导出函数局部 JNI 引用未显式 `DeleteLocalRef`（low，维度③·防御性）

- **问题描述**：各导出函数在 `catch_unwind` 闭包内创建局部 JNI 引用 `java_out`（`deriveKey` 80、`twofish_cbc_jni` 157、`aes_cbc_jni` 234、`applyKeystream` 396、`passkey_sign_jni` 514）与 `estimate` 的 `java_out`(351)，依赖 JNI 在 native method 返回时统一释放，**未显式 `DeleteLocalRef`**。当前所有函数为单次调用（非长循环内累积），无实际泄漏；但作为内存纪律，长数据分段若将来在某函数内循环处理，默认 512 的 local ref 帧会被耗尽。属防御性、低优先。
- **改进建议**：对创建后即刻消费完的局部引用显式 `DeleteLocalRef`；或在模块级注释固化「导出函数不得在本帧内累积 local ref」纪律。
- **证据**：全文件 `grep DeleteLocalRef` **零命中**；上列 6 处 `new_byte_array`/`new_int_array` 后无对应释放调用。注：入参 `iv` 在各函数中以 `let java_iv = iv;` 别名后回写，属调用方引用，不产生新 local ref，不在本项范围。

### QE-10 `crypto/src/main/rust/src/strength.rs:221` — 超长口令 `minimal_period` 全量 `Vec<usize>` 分配放大（low，维度③）

- **问题描述**：`minimal_period`(576-601) 为 KMP 前缀函数分配 `vec![0usize; len]`(582)，调用点(221)传入的是**未经 `MAX_ANALYZED_CHARS` 截断的全量 `&chars`**（注释明言「截断会让 `abc×100` 漏判」）。恶意库可塞入超长口令，使该临时分配峰值随输入长度线性增长——虽非秘密泄漏（`usize` 索引无明文），但是热路径上的 **DoS 内存面**。
- **改进建议**：改用不需完整前缀数组的**滚动/双指针 KMP** 或固定上限缓冲（周期检测只需 `len % p == 0` 与逐字符相等，可在一次遍历中以 O(1) 额外空间判定整周期），消除随输入增长的分配。
- **证据**：`strength.rs:221 minimal_period(&chars)`（全量）+ 582 `vec![0usize; len]`；模块头(218-220)明言跑全量字符。

## Kotlin 面

### K-01 `sync/src/main/java/com/keepasskey/sync/engine/SyncCache.kt:284` — 缓存流以裸 `FileInputStream` 返回，关闭责任在调用方（low，维度③内存/资源）

- **问题描述**：`openCacheStream(remotePath)`（282-285 行）直接 `return if (...) FileInputStream(file) else null`，返回的 `InputStream` 无任何 `.use{}` 强制，调用方须自行关闭；**关闭责任跨两层上移**（`FileBinaryStore.openStream` → `InnerHeader.BinaryItem.openStream`），泄漏点在**链路末端的每个消费点**——新增任一消费点遗漏 `.use{}` 即泄漏文件描述符。属资源所有权移交模式，风险取决于末端调用点闭合覆盖率。
- **改进建议**：在**契约层**固化关闭责任——落点选 `SyncCache.openCacheStream`（改「接收消费 lambda」形态以内建 `use`）或 `BinaryStore.openStream` 接口（KDoc 固化「调用方必须 `use`」并说明多级透传链），须写明所选层级与理由。
