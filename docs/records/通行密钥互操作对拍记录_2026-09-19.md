## 4. 本批由对拍**首次暴露**的缺陷（`ISSUE-P2-211`）

### 4.1 现象

首次运行对拍脚本时，`cryptography` 无法解析 Ed25519 条目的 `KPEX_PASSKEY_PRIVATE_KEY_PEM`：

```
✗ 对拍失败（3/66 条判据不通过）：
  - [Passkey ES256 (passkey-interop.example)] PEM 内容与清单 SHA-256 不一致（产物被改写？）
  - [Passkey Ed25519 (passkey-interop.example)] PEM 内容与清单 SHA-256 不一致（产物被改写？）
  - [Passkey Ed25519 (passkey-interop.example)] cryptography 无法解析该 PKCS#8 PEM：
      ASN.1 parsing error: extra data
```

**如实标注**：三条里只有**第三条**是被验对象的真实缺陷；前两条是**对拍脚本自身**的口径问题
（清单按「PEM 文本字节」取摘要、脚本按「剥装甲后的 DER」取摘要，两边口径不一致），
已改为两侧统一按 **DER** 取摘要后消失。**不得**把「3 条不通过」直接读作「3 个产品缺陷」。

### 4.2 Ed25519 PKCS#8 的实际字节结构（修复前）

```
  0: 30 51 02 01 01 30 05 06 03 2b 65 70 04 22 04 20   -- SEQUENCE { INTEGER 1（version）, AlgId, OCTET STRING … }
 16: 19 8a 2d 05 b1 40 1d 39 9d 19 9b 1f 23 cf e1 da
 32: a9 4d be 81 2b 88 68 10 bc 80 3a b1 dc c0 a2 a9
 48: 81 21 00 67 dd b2 c6 83 4b 4f f8 d8 17 43 60 20   -- publicKey [1] IMPLICIT BIT STRING（可选字段）
 64: 72 ee 84 20 2c dc 00 4c 86 10 c3 95 dc 99 5a a6
 80: 81 41 10
```

即 BC `PrivateKeyInfoFactory` 产出的 RFC 5958 `OneAsymmetricKey`：**`version = 1`** + `publicKey [1]`。

### 4.3 隔离实验（判定「到底哪一处被拒」）

把三份手写 DER 逐个送 `cryptography.hazmat.primitives.serialization.load_der_private_key`：

| 形态 | 结果 |
|---|---|
| `version = 0` + 内层双包 `04 22 04 20 …` | **OK**（`Ed25519PrivateKey`） |
| `version = 1` + 内层双包（**即修复前的产物形态**，且**不含** publicKey 的可变体） | **FAIL** `Invalid key` |
| `version = 0` + 内层**单包** `04 20 …` | **FAIL**（`Could not deserialize key data`） |

⇒ **拒收由 `version = 1` 引起**；内层「OCTET STRING 套 OCTET STRING」的双包恰恰是规范要求
（RFC 8410 §7：`privateKey` 的 OCTET STRING 内承载 `CurvePrivateKey`，而后者本身也是 OCTET STRING）。

RFC 8410 §10.3 已就此警示：部分私钥导入函数尚不支持 RFC 5958 的 `OneAsymmetricKey` 结构，
**会拒绝含 `publicKey` 的私钥结构**，并给出 `version = 0` 的编码示例。
`KPEX_PASSKEY_PRIVATE_KEY_PEM` 的消费方正是 KeePassXC 这类 OpenSSL 系实现 ⇒ **可导入性优先**。

### 4.4 为何长期未被发现

本仓解码器刻意接受 v0/v1（`PKCS8_VERSIONS = setOf(0, 1)`，为兼容存量条目），
于是「自家 writer → 自家 reader」恒绿；ES256 / RS256 的 DER 形态本就正确，
**只有跨实现读取**才能显形 —— 这正是 `AGENTS.md` 规则 8 要防的那一类逃逸。

### 4.5 修复与复跑

- 编码侧改为手工构造 RFC 8410 `version = 0` 最小形态（`PasskeyPkcs8Codec.ed25519PrivateKeyInfoDer`）；
- 解码侧**保持接受 v0/v1**（存量库不回归，新增用例锁定该兼容面）；
- `cryptography` + `keepassxc-cli` 复跑：**114/114 判据通过**（见 §2）；
- 新增设备侧判据 `PasskeyCreationDeviceTest > 真机生成Ed25519与RS256通行密钥并校验PEM形态与签名能力`
  在 Redmi 4X 实跑通过。

## 5. 本记录的**证据边界**（不得读作超出以下范围成立）

1. **文件级、离库证据**：证明的是 `.kdbx` 里 `KPEX_PASSKEY_*` 字段的键名 / 保护位 / 值形态
   与私钥的可解析、可导出公钥；**不含**任何 CM（Credential Manager）通道交互。
2. **未做「用外部管理器登录真实 RP」**：本记录**不**证明 KeePassXC / KeePassDX 能拿这些条目
   完成一次真实网站登录（那需要真实 RP 与浏览器交互，见 §6 的未执行清单）。
3. **PRF 未与真实 RP 对拍**：只证明 `KPEX_PASSKEY_PRF` 的承载形态与保护位被外部实现原样读写。
   > **2026-09-23 补注（§269）**：该边界**已解除**——真机在 Corbado PRF Demo
   > （`webauthn-passkeys-prf-demo.explore.corbado.com`）完成一次带 PRF 扩展的注册 + 登录断言，
   > 页面回显 `Authentication successful (PRF)`、「PRF Support on Creation」「PRF Value on Creation
   > (CTAP 2.2+)」「PRF Support during Authentication」三项全绿。本节第 1 条「不含 CM 通道交互」
   > 同时被同一轮实证穿透（系统 CM 选择器弹出并完成交互）。详见 `ISSUE-P2-254` 结案批次 §269。
4. **v1 旧条目仍不自动迁移**（口径不变，见限界 §4.3）。
   > **2026-09-20 补注（§222）**：该边界已收窄——条目因断言而被原子修补签名计数器时，会在同一受控变换内
   > 就地迁移为 KPEX（旧键清除 + 私钥重包 PKCS#8 PEM）；**从未被断言触及**的 v1 条目仍保持旧形态。
   > 本记录其余结论不因该补注改变，以限界 §4.3 第 4 条为准。
