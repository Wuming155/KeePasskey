## 1. ISSUE-P3-155：AES-256-CBC 现状 512 B 流 vs 候选 64 KiB 分块（真机）

载荷 10 MiB；预热 1 次 + 采样 5 次取中位数（logcat `PERF-PROBE|` 原样摘录，2026-09-17 22:02）：

| 路径 | median | min | max | 吞吐 |
|---|---|---|---|---|
| **解密** · 现状（生产 `AesCipherEngine` 流 = `CipherInputStream` 内部 512 B） | **653.8 ms** | 648.9 | 899.3 | **15.3 MB/s** |
| **解密** · 候选（64 KiB 分块直投 `Cipher.update`） | **89.9 ms** | 89.2 | 99.0 | **111.2 MB/s** |
| **解密** 加速比 | **7.3×** | | | |
| **加密** · 现状（生产流 = `CipherOutputStream`） | 98.6 ms | 94.7 | 132.1 | 101.4 MB/s |
| **加密** · 候选（64 KiB 分块） | 97.4 ms | 95.8 | 101.8 | 102.6 MB/s |
| 加密 加速比 | 1.0×（无收益） | | | |
| 参照 · 一次性 `doFinal`（10 MiB 整块，加密侧） | 31.4 ms | 31.0 | 33.4 | 318.7 MB/s |

**正确性前置（设备侧已断言）**：现状流与候选路径密文逐字节一致；两条路径解密往返逐字节还原明文。

### 采纳后复测（同日 §144 批次落地后，2026-09-17 22:47 同机同探针）

生产 `AesCipherEngine.createDecryptingStream` 切换为 `CbcDecryptingInputStream`（64 KiB 分块 +
`AES/CBC/NoPadding` 变换）后，探针「现状-生产流」实测的即**新生产路径**：

| 路径 | median | 吞吐 | 对比采纳前 |
|---|---|---|---|
| 解密 · 生产流（**采纳后** = 64 KiB 分块骨架） | 180.1 ms | **55.5 MB/s** | 采纳前 15.3 MB/s ⇒ **3.6×** |
| 解密 · 裸 64 KiB 直投 `update`（理论上界参照） | 93.5 ms | 106.9 MB/s | — |

**残余差距的如实解释**：生产路径与裸 `update` 循环之间约 87 ms / 10 MiB 的差距来自分块骨架的
**明文零化纪律与缓冲拷贝**（`CbcDecryptingInputStream` 每块的明文缓冲清零、`bodyScratch` 复用、
out→调用方拷贝；属 ISSUE-P3-177 起确立的安全纪律）。消除它需在共享框架上引入 `(offset, len)`
原地契约——与 §138 拒绝同类 AC 同理，**判定不做**（触及 Twofish 共用路径，风险不对称）。

**正确性前置（设备侧已断言）**：现状流与候选路径密文逐字节一致；两条路径解密往返逐字节还原明文。

### 结论

1. **瓶颈在解密侧且量级确凿**：`CipherInputStream` 内部 512 B 缓冲把解密吞吐压到 15.3 MB/s，
   64 KiB 分块即恢复到 111.2 MB/s（7.3×）。ISSUE-P3-155 的前提与量级在真机上**成立**。
2. **加密侧无收益**（1.0×）：`CipherOutputStream` 对 ≥512 B 的写入已直通 `Cipher.update`，
   与条目「512 B 瓶颈」的表述相比，**整改范围应收窄为解密侧**（`createDecryptingStream` 一侧）。
3. **采纳建议**：值得采纳（复用 `CbcStreams` 分块骨架、仅解密侧），收益约 7× 且无新依赖；
   触及主数据面，按条目原 AC 走互操作与流语义对拍后另行开批实施。

## 2. ISSUE-P3-153：BC 现行 vs Rust 候选真机吞吐（同一设备）

### 2.1 ChaCha20 整库流（外层 cipher 候选，10 MiB，BC 用完整 `BouncyCastleProvider` 实例）

| 实现 | median | 吞吐 | 备注 |
|---|---|---|---|
| BC（完整 provider）一次性 `doFinal` | 3712.5 ms | 2.7 MB/s | min 3705.0 / max 3718.8 |
| BC（完整 provider）64 KiB 分块 `update` | 3779.4 ms | 2.6 MB/s | min 3754.1 / max 3788.3 |
| **Rust `chacha20` crate**（64 KiB `apply_keystream`） | **84.5 ms**（复跑 85.0 ms） | **117.6~118.4 MB/s** | min 84.0 / max 85.2 |

加速比 ≈ **44×**（保守取 BC 分块值 3779.4 / 85.0 = 44.5×；若取 BC 最优 bulk 值为 43.9×）。

### 2.2 Passkey 三算法（keygen 与「生产 `signAssertion` 路径」sign）

| 操作 | BC（真机，5 轮均摊中位） | Rust 候选（同法） | 加速比（BC/Rust） |
|---|---|---|---|
| ES256 keygen | 18.389 ms（16.9~21.8） | 0.900 ms（0.899~0.903） | **20.4×** |
| ES256 sign | 17.681 ms（16.1~27.3） | 1.066 ms（1.065~1.069） | **16.6×** |
| Ed25519 keygen | 5.099 ms（1.9~9.1） | 0.167 ms（0.166~0.168） | **30.5×** |
| Ed25519 sign | 3.816 ms（2.8~4.7） | 0.171 ms（0.169~0.172） | **22.3×** |
| RS256 keygen（2048, certainty=80） | **992.987 ms**（677.4~2451.7） | **2106.5 ms**（599.2~3813.2） | **0.47×（Rust 慢）** |
| RS256 sign | **10.869 ms**（10.5~11.0） | **17.804 ms**（17.797~17.808） | **0.61×（Rust 慢）** |

### 结论（评估定案）

1. **ChaCha20 下沉收益确凿**：BC 纯 Java 实现真机仅 2.6~2.7 MB/s（AES 硬件路径的 ~1/118），
   Rust 候选 44×；若产品保留 ChaCha20 外层 cipher 选项，下沉是唯一现实的性能出路。
2. **ES256 / Ed25519 下沉收益明确**（keygen 20~30×、sign 17~22×），属用户可见时延
   （每次通行密钥断言都要签名）。
3. **RS256 否定下沉**：`rsa` crate 在真机上 keygen 慢 2.1×、sign 慢 1.6×（纯软件大整数 vs BC
   的 CRT/Montgomery 优化），**不得**以「Rust 更快」为由下沉 RSA。
4. **是否立项待裁定**：三处候选均需**新增 Rust 依赖**，须先过 `crypto/src/main/rust/deny.toml`
   （`wildcards = "deny"`、依赖树无重复密码学实现）与供应链 CVSS ≥ 7.0 闸门；结合用户既有
   供应链口径（拒绝低 star / 单维护者加密库），立项决策**留给用户裁定**，数据已备齐。

## 3. ISSUE-P2-92（新发现）：平台剥离版 BC 抢占 provider 名，真机 ChaCha7539 不可用

> **闭环注记（同日 §143）**：整改中核对 `bouncyCastleProvider()` 全部调用点发现 **Twofish 路径
> 同样踩中且更隐蔽**——`NativeTwofish.available` 探活的 BC 对照抛异常被
> `catch (Throwable) { false }` 吞掉 ⇒ 真机上原生 Twofish 被静默弃用、JCE 兜底再挂。
> 修复与验证（宿主 `BcProviderCollisionTest` 1 例 + 真机 `BcProviderDeviceTest` 3 例全绿）见
> [`resolved/batches/143-真机BCProvider抢占解耦批次.md`](../resolved/batches/143-真机BCProvider抢占解耦批次.md)。

- **现象（真实失败，2026-09-17 22:04 真机 instrumented 首跑）**：
  `javax.crypto.Cipher.getInstance("ChaCha7539", <Security.getProvider("BC")>)` 抛
  `java.security.NoSuchAlgorithmException: Provider BC does not provide ChaCha7539`
  （logcat：`crypto/build/outputs/androidTest-results/connected/debug/Redmi 4X - 17/logcat-...probeChaCha20...txt`）。
- **根因**：Android 平台自带**剥离版** BC provider（注册名同为 `"BC"`，不含 `ChaCha7539` 等
  轻量算法）。`ChaCha20CipherEngine.ensureBouncyCastle()` 以
  `Security.getProvider("BC") == null` 判定是否注册完整 BouncyCastle——真机上该判定恒为
  「已注册」，完整版**永远不会被注册**；`bouncyCastleProvider()` 随后返回的正是剥离版平台
  provider。
- **影响面**：真机上**任何**经 `ChaCha20CipherEngine` 的加解密路径（选 ChaCha20 为外层 cipher
  的建库 / 保存 / 读取）必然 fail-fast；读取他人创建的 ChaCha20 KDBX 同样失败。
  宿主 JVM 无平台 `"BC"`，`ensureBouncyCastle` 会注册完整版，故宿主单测全绿——**经典「仅真机失败」**。
  旁证：`AesCipherEngine` 不指定 provider（走平台 AndroidOpenSSL）与 `PasskeyCryptoEngine`
  （直接用 BC 轻量 API 类，不经 JCE provider）均不受影响。
- **整改方向**：完整 BouncyCastleProvider 以**独立 provider 名**注册（如 `"BC/keepasskey"`——
  `new BouncyCastleProvider().getName()` 不可改时用 `BouncyCastleProvider` 子类化或
  `insertProviderAt` 新名），或引擎内**不查注册表、直接传实例**
  （`Cipher.getInstance("ChaCha7539", BouncyCastleProvider())`，本批探针已实证该形态在真机可用）。
  注意勿 `removeProvider("BC")`（平台组件可能依赖）。
- **核实时间点与方式**：2026-09-17 真机 instrumented 探针首跑的真实异常 + 复跑（传完整实例）
  通过；`grep app/src` 确认无任何 `removeProvider` / 完整版注册点。

`crypto/build/rust-probe/src/main.rs`（全文留档如下；§2 所有 Rust 数字即由此版本二进制产出）：

```rust
// ISSUE-P3-153 评估专用探针：Rust 候选算法真机吞吐（chacha20 / p256 / ed25519-dalek / rsa）。
// 方法学与 BC 侧 DeviceThroughputProbeTest 对齐：先预热、再多轮采样取中位数，输出前缀
// `PERF-PROBE-RUST|`。独立二进制直跑于设备 shell（无 JNI / 无 JVM）——方法学差异在记录文档声明。

use rand::rngs::OsRng;
use rand::RngCore;
use rsa::pkcs1v15;
use rsa::signature::{Signer, Verifier};
use sha2::Sha256;
use std::hint::black_box;
use std::time::Instant;

const PREFIX: &str = "PERF-PROBE-RUST|";
const PAYLOAD_BYTES: usize = 10 * 1024 * 1024;
const CHUNK_64K: usize = 64 * 1024;
const WARMUP: usize = 1;
const SAMPLES: usize = 5;
const OPS_PER_SAMPLE: usize = 50;
const RSA_SIGN_OPS_PER_SAMPLE: usize = 20;

fn median(v: &mut Vec<f64>) -> f64 {
    v.sort_by(|a, b| a.partial_cmp(b).unwrap());
    v[v.len() / 2]
}

fn fmt(v: f64) -> String {
    format!("{:.1}", v)
}

fn fmt3(v: f64) -> String {
    format!("{:.3}", v)
}

fn main() {
    println!(
        "{}环境|target=aarch64-linux-android,profile=release,opt-level=3,lto=true",
        PREFIX
    );
    probe_chacha20();
    probe_es256();
    probe_ed25519();
    probe_rs256();
}

fn probe_chacha20() {
    use chacha20::cipher::{KeyIvInit, StreamCipher};
    use chacha20::ChaCha20;

    let mut payload = vec![0u8; PAYLOAD_BYTES];
    OsRng.fill_bytes(&mut payload);
    let key = [0x42u8; 32];
    let nonce = [0x24u8; 12];

    // 与候选实现等价的投递粒度：64 KiB 分块（流式位置随块推进）
    fn run_once(key: &[u8; 32], nonce: &[u8; 12], payload: &[u8]) -> Vec<u8> {
        let mut buf = payload.to_vec();
        let mut cipher = ChaCha20::new(key.into(), nonce.into());
        for chunk in buf.chunks_mut(CHUNK_64K) {
            cipher.apply_keystream(chunk);
        }
        buf
    }

    // 正确性前置：往返一致
    let encrypted = run_once(&key, &nonce, &payload);
    let round_trip = run_once(&key, &nonce, &encrypted);
    assert_eq!(round_trip, payload, "ChaCha20 往返必须还原明文");

    for _ in 0..WARMUP {
        run_once(&key, &nonce, &payload);
    }
    let mut samples = Vec::new();
    for _ in 0..SAMPLES {
        let start = Instant::now();
        let out = run_once(&key, &nonce, &payload);
        samples.push(start.elapsed().as_secs_f64() * 1000.0);
        black_box(&out);
    }
    let m = median(&mut samples);
    println!(
        "{}ChaCha20(rust)加密|64KiB分块apply_keystream|payload=10MiB|median={}ms|min={}ms|max={}ms|throughput={}MB/s",
        PREFIX,
        fmt(m),
        fmt(samples.iter().cloned().fold(f64::MAX, f64::min)),
        fmt(samples.iter().cloned().fold(f64::MIN, f64::max)),
        fmt(PAYLOAD_BYTES as f64 / 1024.0 / 1024.0 / (m / 1000.0))
    );
}

fn probe_es256() {
    use p256::ecdsa::signature::Signer as _;
    use p256::ecdsa::{Signature, SigningKey, VerifyingKey};

    let sk = SigningKey::random(&mut OsRng);
    let data = vec![0x5Au8; 64];

    // 正确性前置：签名可验
    let sig: Signature = sk.sign(&data);
    let vk = VerifyingKey::from(&sk);
    vk.verify(&data, &sig).expect("ES256 签名必须可验");

    // keygen：随机标量 + 公钥点计算（与 BC ECKeyPairGenerator 口径对称）
    let mut keygen_per_op = Vec::new();
    for _ in 0..SAMPLES {
        let start = Instant::now();
        for _ in 0..OPS_PER_SAMPLE {
            let k = SigningKey::random(&mut OsRng);
            let _pub: VerifyingKey = VerifyingKey::from(&k);
            black_box(());
        }
        keygen_per_op.push(start.elapsed().as_secs_f64() * 1000.0 / OPS_PER_SAMPLE as f64);
    }
    let kg = median(&mut keygen_per_op);
    println!(
        "{}ES256(rust)|keygen(随机标量+公钥点)|n={}轮均摊|median={}ms|min={}ms|max={}ms",
        PREFIX,
        keygen_per_op.len(),
        fmt3(kg),
        fmt3(keygen_per_op.iter().cloned().fold(f64::MAX, f64::min)),
        fmt3(keygen_per_op.iter().cloned().fold(f64::MIN, f64::max))
    );

    for _ in 0..WARMUP {
        let s: Signature = sk.sign(&data);
        black_box(s);
    }
    let mut per_op = Vec::new();
    for _ in 0..SAMPLES {
        let start = Instant::now();
        for _ in 0..OPS_PER_SAMPLE {
            let s: Signature = sk.sign(&data);
            black_box(s);
        }
        per_op.push(start.elapsed().as_secs_f64() * 1000.0 / OPS_PER_SAMPLE as f64);
    }
    let m = median(&mut per_op);
    println!(

fn probe_rs256() {
```

## 7. 追问复核（2026-09-17 第二轮）：JNI 边界开销、RS256 口径界定与 Rust AES-CBC 实测

> **动因**：用户就 §1 / §2 的结论提出两处追问——
> ① AES-256-CBC 是否应「统一」实现（原记「无收益」）；
> ② RS256「Rust 慢 1.6~2.1×」是否把 **JNI 开销**算进去了。
> 本节只登记**本轮新实测**的数字；§1~§6 的历史数字**原样保留、未改写**。

### 7.1 JNI 边界单次开销（真机实测，`probeJni边界单次开销`）

以既有内核 `NativeChaCha20.applyKeystreamChecked` 实测「一次跨边界调用 + 入参/出参数组拷贝」：

| 载荷 | 单次调用耗时（5 轮均摊中位） | 说明 |
|---|---|---|
| **16 B** | **18.956 µs** | ≈ 纯边界固定开销（内核计算量可忽略） |
| **64 KiB** | **1001.002 µs** | 其中内核计算 ≈553 µs（按 §2.1 的 118.6 MB/s 折算）⇒ **边界+拷贝 ≈448 µs / 64 KiB** |

**结论**：跨 JNI 处理 **10 MiB** 数据、按 64 KiB 分块 = 160 次调用 ⇒ **固定开销约 3.0 ms**，
外加随字节线性增长的拷贝代价（≈448 µs/64 KiB ⇒ 约 71 ms/10 MiB，是**主项**）。
这正解释了 §2.1 中「生产路径 54~66 MB/s vs 裸内核 118 MB/s」的差距来源。

### 7.2 RS256 口径界定（回答「是否考虑 JNI 开销」）

| 形态 | 实测（5 轮均摊中位） | 与 Rust 的可比性 |
|---|---|---|
| Rust `rsa` crate 签名（**独立二进制，无 JVM / 无 JNI**） | **17.828 ms** | 基准（已享受「无边界」的最优条件） |
| BC 生产路径（`signAssertion`，**每次调用解析 DER**） | 11.807 ms | 与生产一致 |
| BC（**key 解析一次**、复用对象） | 10.230 ms | 与 Rust 同形（两者均为预置 key 复用） |

**三条判定**：
1. **JNI 不构成解释**：Rust 侧数字**根本不含 JNI**（§0 已声明），若上生产还要再加
   1 次调用的 **18.956 µs**（占 11.8 ms 的 **0.16%**）⇒ 只会更慢。keygen 同理（2 次调用 ≈38 µs vs 秒级耗时）。
2. **同形对照仍是 Rust 更慢**：同为「预置 key 复用」，BC **10.230 ms** vs Rust **17.828 ms** = **1.74×**。
   生产形态对照（BC 含每次解析 11.807 ms）则为 **1.51×**。
3. **一处对 Rust 有利、本轮已界定的不对称**：BC 侧含**每次调用的 DER 解析**（约 **1.58 ms/次**，
   由 11.807 vs 10.230 之差得出）；Rust 侧复用预置 key。**该不对称方向对 Rust 有利**，
   纠正它只会让差距更大。

**另一处（对 Rust 更不利、以字节码证据判定）**：BC 1.77 `RSADigestSigner` 的构造器在字节码中
实例化 **`org/bouncycastle/crypto/engines/RSABlindedEngine`**（`javap -c` 取证，
2026-09-17 于 `bcprov-jdk18on-1.77.jar`）⇒ **BC 的 RS256 签名默认带盲化**；
而 `rsa` crate 的 `Signer` 路径**不带盲化**（盲化需显式传 `Rng` 的 `new_blinded` 变体）。
即：**Rust 是在少做一层侧信道防护的前提下仍然更慢**；若按安全等价口径补上盲化，差距只会进一步扩大。

> 结论保持不变并**加强**：RS256 不下沉（见 [`已知工程限界.md`](../architecture/已知工程限界.md) §16）。

### 7.3 Rust AES-256-CBC 实测（回答「统一到 Rust 是否有收益」）

探针新增 `probe_aes_cbc()`（64 KiB 分块逐块 CBC + PKCS#7，与生产形态一致）；
**后端判定**：`aarch64_aes_intrinsics_detected=true`（`cpufeatures` 运行期检测）⇒
**Rust 侧确实使用 ARMv8 硬件 AES 指令**，非软件回退。

| 路径 | 实测（10 MiB，5 采样中位） | 相对「当前生产」 |
|---|---|---|
| **Rust** AES-CBC 加密（64 KiB 分块 + PKCS#7） | **63.0 ms / 158.7 MB/s** | 生产 100.2 MB/s ⇒ **1.58×** |
| **Rust** AES-CBC 解密（64 KiB 分块） | **40.1 ms / 249.2 MB/s** | 生产 55.5 MB/s ⇒ **4.49×** |
| 平台 JCE · 一次性 `doFinal`（加密，§1 参照） | 31.4 ms / **318.7 MB/s** | 仍是加密侧最快者 |
| 平台 JCE · 裸 64 KiB `update`（解密，§1 参照） | 93.5 ms / 106.9 MB/s | — |

**如实声明（含本轮发现的自有瑕疵）**：
1. **§2 与 §7.3 早期的 Rust 数字含计时区内 `clone()`**（每采样多算一次 **10 MiB 拷贝**），
   故那些数字均为**下界**；本轮已修正计时纪律（改为同缓冲原地重复变换）——§7.3 的 AES 数字是修正后的。
   早先的 ChaCha20 118 MB/s、ES256/Ed25519 等**未重测**（其结论为数量级差，不受该瑕疵影响）。
2. **上表是「内核级」实测，不含 JNI**：换算到生产形态还需叠加 §7.1 的边界代价
   （64 KiB 分块 ≈448 µs/次 ⇒ 160 次约 71 ms/10 MiB）。**粗算的生产形态预估**：
   加密 ≈76 MB/s（**低于**现状 100.2）、解密 ≈92 MB/s（**高于**现状 55.5，约 1.65×）。
   该预估为**算术投影，非实测**，且未计 Kotlin 流包装的额外拷贝 ⇒ 仅作决策参考。
3. 因此「AES 下沉 **零收益**」的原表述（§2 之前的推断，非实测）**已被推翻**：
   收益存在但**方向不一致**——解密侧明确受益，加密侧在计入边界代价后可能**不划算**；
   而加密侧真正的天花板在平台侧（318.7 MB/s），瓶颈是**流包装**而非算法实现。

**核实时间点与方式**：2026-09-17 第二轮，`crypto/build/rust-probe`（cargo 交叉编译 aarch64 直跑）
与 `:crypto:connectedDebugAndroidTest -P...class=...DeviceThroughputProbeTest`（logcat 前缀
`PERF-PROBE|` / `PERF-PROBE-RUST|`）原样摘录；`javap -c` 取证 BC 字节码。

| 算法本体（内核，暖缓冲） | 13.3 ms | 28% | 独立二进制实测 |
| JNI 边界（入/出参拷贝 + 入参零化） | **21.2 ms** | 44% | 单次 JNI 34.5 − 内核 13.3 |
| PKCS#7 整缓冲垫片 + 明文擦除 | **13.6 ms** | 28% | 生产 48.1 − 单次 JNI 34.5 |
| 对照：JCE `doFinal` **全程** | **9.2 ms** | — | 平台实现 |

### 8.3 结论（§7.3 口径的两处修正 + 本轮定案）

1. **§7.3 的「1.58× / 4.49×」加速比是基线选取不当，现予修正**：该表的对照物是**当时的 JCE 流式
   生产路径**（加密 `CipherOutputStream` 100.2 MB/s、解密 64 KiB 骨架 55.5 MB/s），**不是 JCE 最优路径**。
   以 JCE 一次 `doFinal`（**318.7 MB/s**）为基线，**内核级 Rust 加密即已慢 2.0×**
   （63.0 vs 31.4 ms）；解密侧 JCE `doFinal` 未测，故「Rust 解密更快」只在「对 JCE 分块投递」口径下成立。
   ⇒ **「AES 内核层占优」在加密侧不成立**，这一点 §7.3 表述有漏，此处更正。
2. **「落差全在边界」的机制在两台机上均成立**：内核 → 生产形态的放大为 Redmi 约 4~6.5×、
   现代机约 3~3.6×；现代机上**解密内核仅 2.0 ms 而生产路径 34.3 ms（17× 放大）**，
   放大项全部是边界与包装。
3. **实现上限（可证伪的否定结论）**：现代机上 Rust **内核本体**（13.3 ms）已慢于 JCE **全程**
   （9.2 ms，含 init/分配/拷贝），且 CBC 加密是串行依赖、逐块调用吃不到 ILP，追不上 OpenSSL 汇编
   ⇒ **无论怎样优化实现，AES 加密下沉都不可能超过 JCE**；「先修实现开销再复测」这条路径**至此排除**。
4. **但取向已裁定（2026-09-18，用户）**：minSdk 36 面向现代设备，主库体积普遍 <5 MB，
   额外 10~20 ms 属**无感区**；本项按**可靠性 / 稳定性 / 可维护性**（跨平台统一、审计一致性）保留，
   **不以性能为由**。代价与边界登记见 [`已知工程限界.md`](../architecture/已知工程限界.md) §17。
5. **必须并排看的反例**：同批下沉的 ChaCha20 在两个时代都是**绝对巨益**（现代 244.2 → 24.7 ms，
   省 **219.5 ms**，9.9×；A53 3712.5 → 85 ms，省 3627 ms，44×）
   ⇒ **不得把 ChaCha20 的收益口径外推到 AES**，两者方向相反。

### 9.1 数据（10 MiB，10 轮中位，同机同轮次两路径对照）

| 锚点（10 轮中位） | Pixel_10（x86_64 模拟器 / API 36.1） | Redmi 4X（A53 真机） |
|---|---|---|
| ChaCha20 现状 byte 数组（JNI 双拷贝） | 23.6 ms | 149.8 ms |
| ChaCha20 DirectByteBuffer 直扣 | **3.7 ms** | **66.3 ms** |
| ChaCha20 倍数 | **≈6.4×** | **≈2.26×** |
| AES 现状 byte 数组（JNI 双拷贝） | 43.9 ms | 178.9 ms |
| AES DirectByteBuffer 直扣（原地内核） | **14.7 ms** | **48.7 ms** |
| AES 倍数 | **≈3.0×** | **≈3.67×** |

- **现状路径复现一致**：模拟器 ChaCha20 23.6 ms（评估轮 24.05 / 基线 24.7，同量级）；Redmi 4X
  ChaCha20 149.8 ms（基线 151.6）、AES 178.9 ms（基线 193.1，漂移 −7%，属频率/热状态波动）。
- **直扣残余口径**：AES 模拟器直扣 14.7 ms ≈ 内核本体 13.3 ms × 1.1 ≤ ×1.2 ⇒ **AC② 判据成立**；
  ChaCha20 模拟器直扣 3.7 ms 即「JNI 固定边界 + 内核」全部（拷贝 = 0）。
- **跨形态口径警示（不得误读）**：Redmi 4X ChaCha20 直扣 66.3 ms **低于** §2.1 的「内核本体 84.5 ms」
  ——后者是**独立二进制**口径（进程调度 / 频率状态 / 预热均不同），两者**不可直接相减得出「负边界」**；
  正确读法是「直扣路径无拷贝，其总耗时即调用 + 内核的全部」，消除量以**现状 − 直扣**计：
  ChaCha20 83.5 ms（与基线「边界 + 拷贝 ≈ 66.6 ms」同量级，口径含入参零化与输出数组分配）、AES 130.2 ms
  （Redmi 4X 的 AES 内核本体基线缺测，此为消除量口径而非边界口径）。
- **AC③ 真机补测完成**：评估期 Redmi 4X USB 断连缺测的 10 轮对比，于本批实跑补齐
  （期间设备仍时断时续：单跑探针类一次成功，整层 connected 首跑因 `device not found` 中断）。

### 9.2 生产路径落地形态与本节数字的关系（如实声明）

1. **探针数字 ≠ 生产端到端数字**：探针对比的是「同载荷、单次 JNI 调用」两形态；生产流路径受
   `InputStream` / `OutputStream` 字节 API 限制，堆 ↔ 堆外各有一次不可消的边界拷贝（解密流：
   `source.read → 堆内` + `put` + 原地变换 + `get` 交付；旧形态为 4 次拷贝 + 每 chunk 2 个 64 KiB
   数组分配）。生产端到端收益 = 消除「JNI 双拷贝 + chunk 级 copyOf/新数组 + Rust 侧入参零化」份额，
   **比例低于上表倍数**，以本节与批次文档登记为准。
2. **落地范围**：ChaCha20 解密流（`NativeDecryptingInputStream`）与 AES 双流（`CbcStreams` direct
   形态）切换直扣；**整块 `byte[]` 路径与 ChaCha20 加密流维持拷贝桥**（边界理由见批次文档 §3.4）。

**核实时间点与方式**：2026-09-19，Pixel_10（AVD）与 Redmi 4X 各一次
`:crypto:connectedDebugAndroidTest`（真机轮限定 `-P...class=...DeviceThroughputProbeTest`），
logcat 前缀 `PERF-PROBE|`，10 轮；模拟器轮 37 例全绿（含两枚探针），真机探针类 8 例全绿。
