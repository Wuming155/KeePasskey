## 4. 用例设计与「为什么这么写」

设备侧用例：`app/src/androidTest/java/com/keepasskey/app/autofill/`

| 文件 | 职责 |
| --- | --- |
| `AutofillAuthChainDeviceTest.kt` | 全链路驱动与断言、证据落盘（logcat + 文件 + 截图） |
| `AutofillClientActivity.java` | **真实客户端**：独立包名的登录表单，自行 `requestAutofill` |
| `DeviceAutofillProbe.kt` | 无障碍树读取 + shell 身份执行（`UiAutomation`）与触摸/文本注入 |
| `AutofillTestVaultSeeder.kt` / `AutofillSeedContract.kt` | 用**生产写入管线**现场播种真实 KDBX v4 密码库（虚构凭据） |

关键设计点（后人复用必读）：

1. **客户端必须用 Java 写**：该 Activity 运行在**测试 APK 自己的进程**（`com.keepasskey.test`），
   而测试 APK **不打包 Kotlin 运行时**（instrumented 测试代码平时寄生在被测应用进程、借用其 classpath）。
   用 Kotlin 写本类会以 `ClassNotFoundException: kotlin.jvm.internal.Intrinsics` 崩溃。
   ⇒ **未修改 `app/build.gradle.kts`**（没有新增任何依赖），而是让该测试专用 Activity 保持零 Kotlin 依赖。
2. **客户端每个实例只主动请求一次**（首帧后 `requestAutofill`）：认证 Activity 进出会令客户端多次
   `resume`，若每次 resume 都请求，会把「框架自行重发」与「客户端又请求了一次」混为一谈。用例同时
   记录**客户端请求次数**（`requestAutofill(` 留痕计数）作为归因依据。
3. **播种时序**：库列表是 `RealVaultRepository` 首次构造时对 `filesDir` 的一次扫描结果，而该单例
   在 `MainApplication.onCreate` 中不被注入 ⇒ 用例**最前面**播种即可让该库成为活动库（无需测试专用注入通道）。
4. **两次认证交互各需一次「干净会话」**：选择器路径写入「包名 + 签名摘要」首次绑定后，**下一次**
   填充请求才会出现自动匹配候选（实测 `候选数据集数量=0` → 重启客户端后 `=1`）。
5. **设备侧命令一律「整份 logcat dump + Kotlin 侧过滤」**：`UiAutomation.executeShellCommand` 不保证经
   `sh -c`，`&&` / `|` / 重定向会被当作参数整体失败（实测 `cp a b && echo OK` 返回空输出）。

## 7. 新发现（4 条）

### 7.1 【产品级】解锁后框架**不会**自动重发 `onFillRequest`（与 KDoc 前提不符）

- **既有前提**：`AutofillUnlockActivity` KDoc 明写「解锁成功后立即 setResult(RESULT_OK) 并 finish()——
  自动填充框架收到成功结果后会自动重新发起 onFillRequest，此时密码库已解锁，服务端即可输出真实凭据候选」。
- **实测（归因干净）**：客户端**每个实例只主动请求一次**；解锁页结束后 25 s 窗口内
  - 服务侧：无新的 `onFillRequest` 留痕；
  - 框架侧：`AutofillSession` / `RemoteFillService` **事件新增 0 条**（第二条独立证据通道）；
  - 客户端：`requestAutofill(` 留痕计数 **1 → 1**（未自行请求）。
- **功能后果**：解锁完成后**不会自动出现凭据候选**；用户需再次聚焦输入框（或应用再次请求）才会看到候选。
  本用例后续阶段正是靠**显式再请求**才继续（用例证据中明确标注该步为「补救驱动，不代表产品行为」）。
- **建议**：登记为独立条目（自动填充解锁后无自动重发 / 需二次触发）。**未**在本次做代码改动：
  唯一可能真正闭合该路径的修法方向是让认证结果回传数据集/`FillResponse`（即 AC①「数据集回传」口径），
  而 AC① 已经 2026-09-16 用户裁决**本轮不实施**；且 §7.1.1 的归因实验表明「只回传数据集」在该构造下
  并未改变行为，故**不该**据此重启 AC①，需先查清真正的约束变量。
- **不排除的替代解释**：本结论的适用面是「原生应用客户端 + 本用例的字段聚焦时序」；
  若客户端在回到前台时重新触发 view-entered，框架侧仍可能重发——本用例未构造该场景。

#### 7.1.1 归因对照实验（实验态 vs 最终态）——**假设被本实验证伪**

- **归因现状（不夸大）**：确认页当前只回传「成功」而不回传数据集（`Bundle.EMPTY`）；但 §7.1.1 的实验表明

### 7.3 【工具链】系统 UiAutomation 是**每用户单槽位**，会被 Android CLI 交互辅助 APK 占住

- 现象：instrumented 进程取 `UiAutomation` 抛 `IllegalStateException: UiAutomationService … already registered!`，

## 11. 2026-09-17 修复与真机验证（`ISSUE-P2-86` 闭环）

> **本节取代 §7.1.1 / §7.1.2 / §8 的「真正约束变量尚未确定」结论。** §7 / §8 的原始测量**一律不改**（记录体例）。

### 11.1 定位：缺的不是「框架重发」，而是「交付路径」

§7.1.1 的实验只改了**载荷**（回传真实 `Dataset`），却**保留**了认证 `PendingIntent` 的 `FLAG_IMMUTABLE`
与基 Intent 的 `NEW_TASK|CLEAR_TOP`——即两个脚手架变量**根本没动**。后续对照取证
（[`docs/references/存量5项开放问题的参考项目对照.md`](../references/存量5项开放问题的参考项目对照.md)）给出关键事实：
**KeePassDX 与 keepass2android 都不依赖框架重发**，其认证 `PendingIntent` 在 API≥31 **一律 `FLAG_MUTABLE`**、
基 Intent **不带任何 activity flag**；而**本应用内唯一经真机验证可填充的选择器路径**恰好就是这一构造
（`FLAG_MUTABLE` + 无基 Intent flags + 回传真实 `Dataset`）。⇒ 缺的是**交付路径**，不是框架行为。

### 11.2 修法（三项）

1. `AutofillDatasetBuilders.buildLockedUnlockDataset`：认证 `PendingIntent` `FLAG_IMMUTABLE` → **`FLAG_MUTABLE`**；
   基 `unlockIntent` **去掉** `NEW_TASK|CLEAR_TOP`，并携带选择器所需的四个 extras（目标框 id / 调用方包名 / 表单自报域）。
2. `AutofillUnlockActivity`：解锁成功后**链入 `AutofillPickerActivity`**，并把选择器的认证结果
   （`resultCode` + `data`，其中 `data` 携带 `EXTRA_AUTHENTICATION_RESULT` 的真实 `Dataset`）**原样转发**给框架；
   用户取消 / 无结果时如实回传 `RESULT_CANCELED`（双参 + 非空 extras，不谎报成功）。
3. KDoc 与 `AndroidManifest` 注释：删除被证伪的「框架会自动重发 `onFillRequest`」前提。

### 11.5 阶段二（确认路径）——**反向结论**

## 12. 2026-09-17 确认路径修复与真机验证（`ISSUE-P2-88` 闭环，§111 批次）

> **本节取代 §11.5 的「`FLAG` 与基 Intent flags 不是确认路径的决定变量」结论。** §11 的原始测量**一律不改**（记录体例）。

### 12.1 定位依据：官方契约（不是试错）

`android.service.autofill.Dataset.Builder#setAuthentication`（**数据集级**认证，即确认路径所用形态）原文两条：

> "Once you complete your authentication flow you should set the activity result to `Activity.RESULT_OK` and
> **provide the fully populated dataset or a fully-populated response by setting it to the
> `AutofillManager.EXTRA_AUTHENTICATION_RESULT` extra**. **If you provide a dataset in the result, it will
> replace the authenticated dataset and will be immediately filled in.**"
>
> "Note: **Do not make the provided pending intent immutable by using `PendingIntent.FLAG_IMMUTABLE` as the
> platform needs to fill in the authentication arguments.**"

⇒ 确认路径**同时违反两条**（PI 不可变；结果未携带数据集）。§11.5 之所以「无效」，是**只补了前者**。
**`FLAG_MUTABLE` 是平台强制、必要但不充分。**

> **口径陷阱（本条缺陷的成因）**：官方那句「可以用 `Bundle.EMPTY` / null 以避免 Android 12 崩溃」出自
> **`FillResponse.Builder#setAuthentication`（响应级）**，原文是「set the extra with the fully populated response
> (**or null if the screen cannot be autofilled**)」。它是**崩溃规避**条款，**不是**「可以不回传数据集」的许可。

### 12.2 修法（两处一起改）

① 确认入口 PI 改 `FLAG_MUTABLE`、基 Intent 去掉 `NEW_TASK|CLEAR_TOP` 并**下发目标框 id**；
② 确认页在**显式确认成功后**按 `EXTRA_ENTRY_ID` 取回凭据、构造真实 `Dataset` 经 `EXTRA_AUTHENTICATION_RESULT` 回传
（交付载荷构造收敛为**单一实现** `AutofillAuthResultDelivery`，选择器与确认页共用）。
**候选数据集自带的真实值保留**——`ISSUE-P3-42` 会话宽限分支依赖它。

### 12.3 真机证据与**负向对照**

正向（设备 `1c859bcc7d24`，task `BUILD SUCCESSFUL`；确认窗口内 `requestAutofill` **5 → 5** 未重请求）：

```
09-17 10:34:52.653 24751 24751 I AutofillClientTest: 客户端状态 #1 AC3-STATUS username=[ac3-device-user] passwordLength=12 usernameFilled=true passwordFilled=true
```

负向（**只改 `FLAG`、不回传数据集**——`FLAG` 与目标框 id 保持已改）：

```
AutofillAuthChainDeviceTest > 设备侧实测自动填充认证填充链路[Redmi 4X - 17] FAILED
	java.lang.AssertionError: 确认页在真机上**未**把凭据写入客户端输入框（确认后未新增「passwordFilled=true」留痕）——ISSUE-P2-88 修复未生效
> Task :app:connectedDebugAndroidTest FAILED
```

⇒ 「`FLAG_MUTABLE` **必要但不充分**」在真机上被**钉成回归**。

### 12.4 **比推断更细的实测结论**：框架对回传数据集是 **replace 语义**

第一轮（契约已补但回传数据集**不完整**）的原始留痕：

```
09-17 10:19:50.165 21810 21810 I AutofillClientTest: 客户端状态 #1 AC3-STATUS username=[] passwordLength=12 usernameFilled=false passwordFilled=true
```

⇒ 框架**按回传内容原样填**（该轮数据集里只有口令字段 ⇒ 只填口令），
**不会**复用服务端候选数据集里已带的值。故**回传数据集必须完整**。

### 12.5 过程中暴露的第二个缺陷：**认证 Activity 不得假设异步缓存已就绪**

第一轮回传不完整的根因在取数：`AutofillPickerViewModel` 的条目缓存由 `init` **异步**填充，
而确认页是**按需创建**该 VM（`by viewModels()` 首次访问发生在用户点「确认」那一刻）⇒ 用户名取到空串。
修法：用户名改为「缓存命中即用，**未命中回退仓库快照**」（锁定态仍 fail-safe，`ISSUE-P2-52` 语义不变）。

### 12.6 边界（**勿过度解读**）

1. **未做「保留数据集回传、把 PI 改回 `FLAG_IMMUTABLE`」的单变量对照** ⇒ 本批只能断言
   「**数据集回传是必要的另一半**」，**不能**由实测断言「`FLAG_MUTABLE` 单独必要」——后者只有**官方明文**依据。
2. **未做** §11.1 所列的备选路线实验（把候选数据集改写成选择器同构造）——现结论已证明原形态可修复，无须再走。
3. **框架侧 `onAuthenticationResult` 留痕本轮抓不到**（两轮 dump 命中 **0 行**）⇒ 结论**只**建立在功能观测上；
   §11 里那句 `onAuthenticationResult(): empty intent` 本轮**未复现**，**不据它立论**。
4. 新登记 **`ISSUE-P3-148`**：确认页每次确认会装载整库条目投影（缓存未命中时再装一次），实际只需一条。

   > 并改由选择器页显式发起、`VaultEntrySecretReader` 按 id 读取改走 `findEntry`），
