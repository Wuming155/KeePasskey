### (f) 设备侧工具链约束（2026-09-16 实测，后续设备侧用例须遵循）

1. 系统 `UiAutomation` 是**每用户单槽位**——若 `com.android.cli.interact.instrumentation`（Android CLI 自带的交互辅助 APK）
   在跑，instrumented 进程再取 `uiAutomation` 会抛 `IllegalStateException: UiAutomationService … already registered!`，
   框架随后在「连接中」状态调用 `disconnect()` **直接崩溃进程**（连断言都执行不到）。规避：运行前确认该辅助 APK 未运行
   （`dumpsys accessibility` 中无 `Ui Automation[...]` 条目），并**在用例运行期**（而非构造期）经 `by lazy` + `runCatching`
   获取 `uiAutomation`。
2. **锁屏（Doze）下任何 Activity 都无法真正进入前台** ⇒ 认证类 Activity 始终不出现在无障碍树中；
   设备侧 UI 驱动类用例须先**唤醒并解锁屏幕**。
依据：[`docs/records/自动填充认证链路真机实测记录.md`](自动填充认证链路真机实测记录.md) §7.3 / §7.4。

## §7 目录枚举鬼影的派生残余与观测点原始记录

### (a) 派生残余（产品代码 · 第二处，2026-09-17 新增证据，**该处此前只有「偶发红」的现象、没有根因**）

`SyncCacheEvictor.evictAll()` 的**残留计数**同样受该鬼影影响——它以
`dir.list()?.count { !SyncCache.isRollbackStateFileName(it) }` 清点「应清理项」，鬼影会让该计数**多出 1**，于是：
① 返回 `false`（调用方据此认为清理未完成）；② 落一条**误报** WARN「同步缓存残留 N 项，锁定后密文可能仍可恢复」；
③ 使 `SyncCacheEvictorTest` 的 `F23 锁库清理缓存不得删除防回滚状态文件` **偶发红**——该项目**早已观测并留痕**
（用例注释记「观测 **3 次全量 / 1 次失败**，独立复跑 4 次全绿」），并**刻意**在断言消息里带上「销毁器日志 + 实际目录内容」以待定位。
**2026-09-17 一次全量跑的失败信息恰好完成了该定位**：断言消息给出
「目录索引条目 = 磁盘上真实存在的文件 = **仅** `<hash>.rollback`」，而销毁器日志为「同步缓存残留 **1** 项」——
由于 `isRollbackStateFileName` **确实**排除了该文件名，这个 `1` 只能来自 `dir.list()` 返回的**无实体条目**
⇒ 鬼影已从「**测试侧**目录索引」扩展到「**生产代码的清点**」。该次定位后单独复跑该类**绿**，与「偶发」一致。

## §22 凭据拒绝页：无自动化覆盖的具体缺口与理由（原始条目）

- **为什么不采用「跳转设置页」方案（已在方案演进中被否决）**：
  1. `MainActivity` 是唯一无权限保护的导出组件，`ExportedComponentHygieneTest` 锁定了
     「不得消费任何外部 intent 数据」这一安全不变式，跨 Activity 传递目标路由无法走标准 Intent；
  2. 凭据窗口具有「不提供本应用内导航」的加固取向（`CredentialUnlockPresenter` 等三处 no-op）；
  3. 用户命题明确要求「减少跳转和操作」——就地完成授权使操作步数由「跳去设置 → 找开关 → 找应用 → 切回浏览器」
     骤降为「点一次添加 → 回浏览器重试」。
- **无自动化覆盖的具体缺口（需真机核验的项）**：
  ① 真实系统拉起下，按钮点击后的 `CircularProgressIndicator` 转圈与状态刷新流程度；
  ② 写入偏好后回到浏览器再次发起 passkeys.io 注册，是否确实直接放行且不再弹拒绝页；
  ③ 读不到签名证书（例如特殊沙箱环境）时的 `STATUS_FAILED` 失败文案呈现。

### ## 10. 同步「内容是否变化」与合并「是否被修改」两处判定口径**刻意不同**（`ISSUE-P2-91`，§122 复核）

  `app/src/main/java/com/keepasskey/app/sync/KdbxContentComparator.kt`（原 `SyncContentChangeDetector` 的三个
  private 函数，§122 抽为可直测的纯对象）——回答「**是否需要重新序列化并上传**」，比较已覆盖的内容字段 + 历史**条数**，**刻意不比 `times`**；②
  `sync/src/main/java/com/keepasskey/sync/merge/KdbxEntryMerger.kt` 的 `isModified`——回答「条目相对 **base** 是否被修改」
  （冲突裁决用），**必须**把 `times.lastModificationTime` 计入。
- 若 ① 纳入 `times`：「触碰但内容等同」的操作会被判成内容变更 ⇒ 重新序列化 + 上传 + **前移远端 ETag**（KDBX4 随机 IV 使重序列化字节必然漂移——这正是该检测器存在的理由，F5）。
- 若 ② 不比 `lastModificationTime`：时间戳更新过的条目会**退出合并**。
- **前提复核（§122 已核实并据此撤销原 `P2-91` 判定）**：生产代码**无任何**只改 `times` 的编辑入口——`expires` / `expiryTime`
  在全仓生产代码**无写入者**（仅 XML 读取端与默认值构造）；`times` 的改写只经 `withField`（**同时**改 `fields`）与 passkey 计数器补丁（**同时**改
  `customFields`）⇒ 「仅 `times` 变化的本地编辑被静默丢弃」在**本应用可达面上不成立**。
- **外部客户端**（其它 KDBX 实现）若写入「只改 `times`」的条目，本应用同步时同样**不会**把该变化读作内容变更——两者是**不同命题**，该形态下的表现**未实测**。


### ## 11. 基线快照与缓存快照**各写一份**（`ISSUE-P3-167` 的「重复写盘」复核裁决，**刻意不改**）

- 两次写盘各自走「tmp → flush → `fd.sync()` → 原子 rename」。
- **裁决：不做「内容一致则跳过第二次写盘」**（§125 复核推翻原 `ISSUE-P3-167` 建议），两条独立理由：①
  **逐字节判定不是免费的**——判定须先读全量内容并哈希（长度预检只能排除尺寸不同的情形），而 `advanceBaseAndPersist` **总在内容刚变更之后**被调用（上传成功 / 接受远端内容）⇒
  在最常见路径上「先读一遍再决定不写」**净增**工作量，只在「内容恰好未变」时才有收益；② **廉价推断不安全**——以「`basecache` 存在且 `<hash>.baseversion` 已等于该摘要」
  为判据看似零成本，但本函数的写序是 `updateBase` → `writeBaseContent`，两步之间崩溃会留下「baseversion 已前移、basecache 仍是旧字节」；
  此时跳过写盘会把**陈旧基准永久固化**——而基准快照存在的意义正是避免「base 被本地修改版污染 ⇒ 三方合并退化为远端全胜」（见 `SyncCache.readBaseContent` 的 KDoc）。

### ## 16. RS256 保持 BouncyCastle 纯 Java（`ISSUE-P3-153` / §146 实测否定下沉）

- 原因是 BC 的 RSA 带 CRT / Montgomery 优化，`rsa` crate 在该规模下未占优。
- WebAuthn 实践中 RS256 凭据占比很低，故该代价面有限。
- **同形对照仍慢 1.74×**（同为预置 key 复用：BC **10.230 ms** vs Rust **17.828 ms**；生产形态含每次 DER 解析 11.807 ms 对照为
  **1.51×**）。
- **两处口径不对称方向都对 Rust 有利**：BC 侧含每次调用的 DER 解析（≈1.58 ms/次）；且经 `javap -c` 字节码取证，BC 1.77 `RSADigestSigner` 默认实例化
  **`RSABlindedEngine`**（**带盲化**），而 `rsa` crate 的 `Signer` 路径**不带盲化**——即 **Rust 是在少做一层侧信道防护的前提下仍然更慢**。
- 数据见 `docs/records/真机吞吐实测记录_2026-09-17.md` **§7.1 / §7.2**。


### ## 17. AES-256-CBC 统一到 Rust 内核后的**性能代价**与 JNI 边界秘密治理面（§147，**取向为可靠性/可维护性，非性能**）

### ## 21. 供应链扫描面 = **生产可运行面**：AGP 工具链配置族不入扫描（`ISSUE-P2-219`，§225）

  `*CompileClasspath` 面为 **0 条**：
- **处置口径（本条的**唯一**授权范围）**：在 `.github/dependency-check.init.gradle.kts` 的 `skipConfigurations`
  中**显式枚举**上述配置族（以及既有的 androidTest / lint 条目），使扫描面 = 生产可运行面。

- 实测收口效果：`1316 条实例 / 948 达阈` → **`5 条实例 / 0 达阈`**，断言退出码 `1` → **`0`**；报告仍覆盖 **317 个构件 / 57 个配置**。

### ## 22. 凭据拒绝页「就地授权特权浏览器」的残余边界（`ISSUE-P3-221`，§227）

- 由此带来的工程边界与残余：① **本次请求仍然失败**——创建流程拉起时系统凭据框架已将 origin 固定（非白名单浏览器退化为 `android:apk-key-hash:...`），无法在运行时原地变更为

### ## 24. 自选位置（SAF）密码库的写回是**非原子**的，且不参与同步（`ISSUE-P2-229`，§233）

- 这类库的后续保存走 `ContentResolver.openOutputStream(uri, "rwt")` 截断式写——`AtomicFileWriter` 的 `.tmp` + `renameTo` /
  `Files.move(ATOMIC_MOVE)` + `.bak` 滚动备份 + 目录 fsync 在 SAF 文档上**全部不可用**（无同目录临时件命名权、无原子重命名语义）。
- 同时 `SyncCycleRunner` 硬依赖 `currentFile`（本地 `File`）并以 `activeFile.name` 推 remotePath，故这类库**不支持 WebDAV / S3
  同步**。
- 本批取「cacheDir 造临时库 → 字节搬到目标文档 → 以 `openStream` 读回复核」的最小改造，既不改动原子写盘通道，也让内部存储路径**行为逐字不变**。
- 现改为：**仍容错继续**（本条第 ② 点不变，provider 不支持持久化授权时本次打开与保存必须正常）+ ① 失败落 `AppLog.w` 留痕；②
  解锁页一次性提示（`unlock_msg_no_persisted_permission`，含「重启后可能需要重新选择该文件」）；③ 列表卡片给出可辨识状态与**重新授权**入口（重选同一文件重取长期授权，
  复用既有导入路径登记）。
- 判定同源单点：`VaultUriPermission.lacksPersistedReadPermission`（纯函数）+ `persistedReadUriStrings`（唯一平台查询，查询失败按「未知」
  处理、**不误报**）。


### ## 25. IP 字面量主机名旁路 `Dns` 层：SSRF 守卫仅由连接期层覆盖（`ISSUE-P3-234`，`SUPPLY-06` 余项）

  下限（`isRegistrableDomain`）拒绝。
