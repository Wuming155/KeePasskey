## 一、假开关

### 表现特征

共同外观：**旗标/规则/环境变量/设置项「写在那里」，构建与 CI 照常 BUILD SUCCESSFUL、无任何显式报错，UI 可拨动可回显、测试全绿，实际却不生效**。宿主 `test` 全绿时尤其不可见——宿主 JVM 本来就走兜底分支。按排查面归纳为三族形态（均已在本仓实刻）：

**构建/CI 面**（build.gradle.kts、gradle.properties、proguard-rules.pro、AndroidManifest、.github/workflows/*.yml）四种典型形态：
1. R8 keep 规则指向依赖里已不存在的方法——规则恒不匹配成为 no-op，且 `proguard-rules.pro:22` 的 `-dontnote **` 把不匹配提示整个吞掉（同病先例：ISSUE-P3-98 的 AppLog 规则签名写错、永不匹配，后由 AppLogProguardRuleTest 锁定）；
2. workflow env 声明无人消费——改了 env 值 CI 行为不变（本例 `RUST_TOOLCHAIN`）；
3. 构建脚本传的属性与消费脚本口径不一致（`dependency-scan.yml` 仍传 `-Dorg.owasp.dependencycheck.nvd.api.key`，而 init 脚本明文不读该属性名）；
4. 同一依赖/开关多处定义、实际值取决于解析顺序而非显式声明（material3 的 BOM 行 + 显式 alpha 行并存，靠 Gradle「最高版本胜出」维持 pin）。注释/文档声称的状态与代码实际状态漂移是伴生症状（`proguard-rules.pro` 注释称「见第 13 节」而全文件只有 1–12 节；dependency-scan.yml 头注释自供过一次「声明漂移」）。

**设置域 UI 面**：开关在 UI 上一切正常——可拨动、落盘、重启后回显与上次一致——但拨动后任何可观察行为都不变化；或设置页/关于页呈现的值恒等于硬编码字面量、与真实构建或真实行为脱节；或 Compose 状态模型字段从不被投影赋值。本仓已裁决的同型案例：CM/Autofill 通道假开关（ISSUE-P2-228，限界表 §23）、云端同步三项（PD-39：useFileTransactions/preloadDatabaseEnabled/allowedWifiSsids 移除）、安全与外观两项（PD-40：rememberRecentFiles/iconSet 移除）、触感「开了没用」（2026-09-28 §350 用户命题「全面排查存量假开关」的起点）、AutoType 可编辑但零执行方（PD-42，以 supportingText 如实标注收口）。

**原生探活面**四种可辨识形态：
1. 探活结果被 `by lazy` 进程级缓存后永不刷新（`NativeCryptoLibrary.kt:29` `val loaded: Boolean by lazy`，七个 `Native*.kt` 的 `available` 同型）——首次触碰时一次瞬时失败（缺 ABI、KAT 不匹配、catch Throwable）即把「原生=关」钉死到进程结束，之后所有解锁/加解密静默走 JCE/BC 兜底，界面与日志毫无异常，只有性能劣化（Argon2 原生较 BC 快 2.2~5.4×，`Argon2KdfEngine.kt:14`）；
2. 探活判据过弱（历史上 `NativeArgon2.available` 曾「非空即通过」，`Argon2ProbeKatTest.kt:11` 记载），内核返回同长度垃圾值也判真——后来以 KAT 升级堵住（ISSUE-P3-204）；
3. 探活的对照依赖被环境抢占：ISSUE-P2-92 实测 Android 平台剥离版 BC 抢占注册名 `"BC"`，`NativeTwofish.available` 的 BC 对照抛异常被 `catch (Throwable){false}` 吞掉 ⇒ 探活恒假 ⇒ 原生 Twofish 被静默弃用（`BcProviderDeviceTest.kt:19`）；
4. 文档/守卫名与真实路径漂移：Rust 侧契约注释声称某 JNI 导出「非生产路径」而它已是生产热路径；KDoc 引用不存在的守卫类名。

### 常见成因

1. 依赖升级后 keep/-assumenosideeffects 规则未同步（方法改名/非静态化/删除 ⇒ 规则恒不匹配；规则 12 由此补了 AppLogProguardRuleTest，但同文件其余规则无守卫）。
2. GitHub Actions 的 `with:` 与 workflow 级 env 双写：`with:` 入参据信不能引用 workflow 级 env，被迫「env 声明 + 字面量」双写，env 声明退化为装饰点且 header 注释（`build.yml:18`「Rust…全部在 env 中写死，禁止漂移」）与实际不符。（F02 复核经 GitHub 官方 contexts 文档证实 `steps.with` 可用上下文含 env、该理由不成立——但「双写 + 无机检比对人工同步点」的成因结构仍在。）
3. 插件换 Property API / init 脚本重构后旧传参通道失效，新通道另起但旧通道未拆（OWASP 插件 13.0.0 的 `nvd{}` 改读环境变量，workflow 侧 `-D` 未撤）。
4. BOM + 显式版本双声明时 pin 的效力依赖冲突解析方向，无机检守卫。
5. 注释引用不存在的章节/状态（`proguard-rules.pro` 注释称「见第 13 节」，全文件只有 1–12 节）。
6. 功能重构移除了唯一消费方而保留开关与持久化——useOfflineCache 即此型：commit 2a0dd5d1（2026-09-30）为修「首传永不联网」拆掉 `syncCoordinator.setOfflineMode` 误接后，开关变成零消费方死开关（KDoc 与文案仍承诺行为，`SettingsExtendedPreferencesController.kt:21` 的 syncCoordinator 依赖也残留未用）。
7. 从参考项目（KP2A 形态）整卡移植的偏好项在本仓架构（minSdk 36、系统 Autofill/CM）下无对应实现——autoReturnFromQuery，PD-16 明写「该行为在本应用既无实现也无消费方……新增即 ISSUE-P2-228 同类的假开关」。
8. UI 状态模型字段从未接入投影链（debugLogRecordsCount；同文件 ISSUE-P3-126③ 删除 kdbxFormat 死字段是先例）。
9. 双存储冗余键无对账（ISSUE-P3-363：lockWhenScreenOff 曾「显示值≠熄屏行为」，已改 DataStore 单源）。
10. 镜像/种子断链——`check_launch_language_seed.py` 守护的五条（E1 install / E2 initialValue / E3 tracker 取种 / E5 慢路径补种 / E4 store 镜像）任一断即「切了语言重启又变回去」（§415）；其它镜像同型风险在只写不读或 publish/save 只做一半。
11. 「探活（懒加载一次）」设计只考虑了稳态，未考虑首次触碰瞬态失败后的永久钉死与重启之外的自愈路径。
12. 回落可观测性只做了 KDF 一层（`NativeKdfFallbackLog` KDoc 自述仅覆盖 `NativeArgon2`/`NativeAesKdf`；ISSUE-P3-392 的口径就是「探活失败静默回落不可观测」，但强度/AES/Twofish/ChaCha20/Passkey 签名五个内核未同批纳入）。

15. 「供诊断」的旗标（`nativeAvailable`）立了而没接线，形成无人读的死旗标。
16. 宿主与真机是两条验证路径，假开关只会在其中一条显形——AGENTS.md §5 明文「compileDebugAndroidTestKotlin 通过不构成验证证据」「宿主全绿不代表设备可用」。

### 表现特征

这类故障的共同特征：**功能完全正常、零报错、零崩溃、零 Error 终态——但实际读到的「源」是错的或被折算过的**。本仓「读取源错误」主要变现为四种读错形态：①把「探测失败/信号缺失」读成「无信号可用」的合法回退（Kotlin 空值链把两种语义合并到同一空值上）；②把多种真实失败读进同一「成功型/离线型」结果类，UI 映射粒度过粗，真实原因被吸收；③门禁/对拍脚本读不到某条判据腿时读成「通过」（退出码语义 fail-open）；④探活读到的对照基准被环境抢占（按注册名取 BC 被剥离版抢占）。具体表现：

**crypto 原生回落面**：本仓的兜底实现与主实现被逐字节对拍用例锁定等价（CipherFallbackParityTest / TwofishNativeParityTest / CbcStreamFramingTest，及强度面的跨语言契约用例——真实落点为 PasswordStrengthTest.kt:182；早期排查材料将该用例写作 PasswordStrengthNativeParityTest，该类名经 F06 核实全仓不存在、git 全史从未存在），因此测试面与用户可见功能面全绿；差异只落在两处不可见维度：性能（ChaCha20 原生 ≈118 MB/s vs BC 2.6~2.7 MB/s，ChaCha20CipherEngine.kt:23-24 KDoc 自记）与判定质量（强度评估兜底丢顺序段/键盘行走/周期重复/日期 4 类模式检测，PasswordStrength.kt:130-135）。用户/排障视角：解锁或保存莫名变慢、健康检查漏报弱口令，而 logcat 搜不到任何「回落/降级」字样——分派点形如 `val useNative get() = !force && NativeXxx.available`，回落分支不产生任何日志或状态位。本仓已有对照组：ISSUE-P3-392 修复前的 KDF 正是「性能骤降全程不可观测」这一形态（docs/resolved/batches/359 批次 §ISSUE-P3-392 原文），修复方式即接一次性 AppLog。

**sync 面（WebDAV/S3 客户端、缓存命中/降级路径、合并冲突、TLS/认证、防回滚旁路）**四类形态，共同点是不抛错、不崩、不产生 Error 终态，且 `SyncFailureSignal.shouldNotifyOutcome` 只认 `Error`（app/src/main/java/com/keepasskey/app/sync/SyncFailureNotifier.kt:42），凡被折叠进 Offline/成功语义的降级都不产生任何通知：① 同步终态与真实远端状态脱节——多种失败被折叠进同一「离线」态（`SyncOutcome.Offline` 承接 `RemoteUnreachableUsingCache`/`CacheHitOffline`/`RemoteUnreachable`/`NetworkError` 等来源：SyncCycleRunner.kt:320-333、SyncCycleCommitPaths.kt:52-64/:155；ISSUE-P2-402 曾实测 401/429/超时被一律标成 Offline，现仅首传路径修好）；② 条件写静默变无条件写——上游 `getOrNull()` 探测失败折算成空串，下游把空值当「无基线可校验」的合法回退，乐观锁被静默剥除；③ 旁路提示通道对「信号缺失」恒报正面结论——回前台探测通道对远端变更不可察觉（F16 实测整条空转）；④ 兜底重试的 KDoc 与实现漂移、数据类不变式（truncated⇒nextCursor 非空，RemoteListModels.kt:26）只写在 KDoc 无机检，破坏后 UI 按旧假设继续工作。反例（已核对非静默降级、勿重报）：`RemoteUnreachableUsingCache`→Offline 有 `SyncCacheEvent.CouldntOpenFromRemote` 事件兜底通知（SyncEngine.kt:222 + SyncFailureNotifier.kt:97-103）；`overwriteRemoteWithoutPrecondition`/KEEP_LOCAL 是用户显式偏好（SyncEngine.kt:432-459 KDoc 明示「不是静默降级」）；防回滚 fail-open 窗口（状态缺失/32 条窗口/sequence 不参与裁决）已登记于 docs/security/同步层记录级完整性威胁建模.md §3.3 与 docs/architecture/已知工程限界.md §5；TLS 面恒 RESTRICTED_TLS+MODERN_TLS 无降级（SyncHttpClientFactory.kt:36-39）。

**database 解析层 + tools/** 脚本面**可观察形态：①对拍/门禁脚本打印绿色结论但某条判据腿根本没跑——实测对照：同一份探针产物，keepassxc-cli 在场时 verify_interop.py 判「161 条判据全部成立」，剥 PATH 后同一文件变「133 条判据全部成立」（被跳过的官方 CLI 腿＝28 条判据），摘要行却仍写「（pykeepass + cryptography + keepassxc-cli）」且退出码同为 0；②畸形/损坏输入不报错而是产出空对象（如附件交付 0 字节）；③证据留存脚本对不可解析的证据静默 continue；④同一解析器内 fail-closed 口径不一致——UUID/受保护字段/时间戳 Base64 损坏一律抛 KdbxCorruptFileException，个别分支却静默默认；⑤文档串/README 声称的退出码语义与实现 return 分支不符。

### 常见成因

**crypto 侧**：
1. 探活与分派分离：七个 Native* 绑定各自以懒加载 KAT 探活（NativeCryptoLibrary.kt:29-36 对加载失败 catch Throwable 返 false，KDoc:17 明写「降级到纯 JVM 实现，不抛出、不阻断调用方」），引擎按布尔分派，探活失败在运行时零痕迹。
2. 兜底路径靠 internal 构造器强制进入常态回归（AesCipherEngine.kt:31-43 等），对拍全绿后语义差异只剩性能/覆盖面，更无人怀疑。
3. 整改只覆盖被点名的调用点——P3-392 批次 AC 的「涉及文件」明写 Argon2KdfEngine.kt 与 AesKdfEngine.kt（359 批次文档），同型分派点在三个 cipher 引擎、PasswordStrengthEvaluator、PasskeyAssertionSigner 处未同步。
4. 设备侧 .so 与宿主 .so 是 cargo-ndk 另编的两个二进制（§151 批次实测记录过「六个原生内核里 AES-KDF 与口令强度从未在真机执行」），「个别机型 so 加载失败 / KAT 不匹配」是 P3-392 背景自认的现实发生类。
5. database 解析面的吞异常点绝大多数是 fail-closed 收敛（类型化 KdbxCorruptFileException / KdbxResult.Failure），真正的静默降级集中在 crypto 的原生→JVM 分派层。

**sync 侧**（纯 Kotlin 引擎 + kp2a 决策树移植 + OkHttp + 双通道 ETag/内容哈希裁决）：
1. 决策树降级分支返回「成功型结果类」（`SyncOpenResult.RemoteUnreachableUsingCache`/`SyncCommitResult.RemoteUnreachable`），UI 映射粒度过粗（一律→Offline），真实原因被吸收——ISSUE-P2-402 的教训。
2. Kotlin 空值链（`getOrNull()`/`orEmpty()`/`ifEmpty{}`）把「探测失败」与「无信号」合并为同一空值，而下游判据（如 `conflictUploadExpectedEtag`：SyncConflictAutoMerge.kt:23-24）把空值解释为「无 ETag 服务器⇒无预条件」这一刻意留存的显式回退，两种语义在空值上合流。
3. 双通道裁决只在引擎主路径对齐（RemoteConsistencyProbe），旁路通道（回前台探测 ResumeSyncProbeCoordinator）只做了 ETag 单通道。
4. 修复型兜底（409/423 先 DELETE 目标再重试 MOVE，ISSUE-P2-381）先改远端再重试，重试参数与两处 KDoc 漂移后无机检拦截。
5. 数据类不变式只落在 KDoc（RemoteListModels.kt:26），实现可静默破坏（S3DirectoryList.kt:86）。
6. 已登记的刻意降级（无 ETag 服务器空值回退，SyncEngine.kt:480-486 KDoc「唯一显式回退情形」）为后续旁路开了同形先例，新代码照抄空值回退即复利。

**脚本侧**：
1. 环境缺失走「跳过+exit 0」而非显式失败（对照仓内正确先例 tools/template-group-interop/verify_template_group.py:15「2 = 环境缺失（不得当绿）」）。
2. 解析失败回落空集合/缺省值且无守卫测试反向锁定。
3. cmd 括号块内 %errorlevel% 在整条语句解析期展开（须 delayed expansion 才取运行期值），使 bat 回退分支成为死代码。
4. 聚合计数脚本对「空输入」无专属分支（同目录 preserve_test_failures.py:27 对同一输入状态显式退 2 并标注不得当绿，两口径并存）。
5. catch 块把「读不到」与「没问题」合并处理。
