## 3. 两份报告的口径冲突（**本文件存在的第二个理由**）

| 报告 | 反对的**失效模式** | **不是**反对 |
| :-- | :-- | :-- |
| A5 | 「**用异常做流程控制**」+「**静默**吞掉（无 `AppLog`）」 | 不反对「兜底」这个行为本身 |
| B1 | 「**删掉兜底、却留下会抛的替代品**」⇒ 崩溃可原路复发 | 不反对「据 `cleared` 降级」这条定则 |

**冲突的性质**：两条**同时成立**，且指向同一段代码的相反动作。**代理的字面执行是回归的流程根因**：上一批对「删掉 catch」**照字面执行**，正确做法是「**先删因、再判果**」——先消除「为什么需要这个 catch」（把读取本身变成不抛），再判断 catch 是否还需要。

**代理提出的裁决候选口径（待裁决，采纳后应入 `产品裁决登记.md`）**：
1. 按**消费面**分层：写盘 / 落库 / 凭据下发 = fail-fast（其防线在 `database/src/main/java/com/keepasskey/database/xml/KdbxXmlEntrySerializer.kt:211/223`，本批未触碰）；展示 / 检索 / 报告 / 解析面 = 读到不可读即降级；
2. 判据必须落在**读取自身**（单一判据点）；「先查 `cleared`、后裸读」的**两步式一律视为缺陷形态**（应加机检钉住）；
3. 兜底（catch）**只允许作第二层**且必须留痕；**不得**作为唯一机制（否则即回到 A5 反对的形态）；
4. 两份报告给出相反动作时**不取折中**：追问各自反对的失效模式，设计一个同时排除两者的实现——通常是**消除让两种坏结果都可能的前提**。

**关键事实（决定「非抛化不伤数据完整性」）**：
- 真正的写盘路径是 `KdbxXmlEntrySerializer.kt:211/223`（`value.readUtf8()` / `writer.text(value.readString())`），**另一模块、另一文件**；
- `PasskeyData.fromCustomFields` 的调用方（20 处，含测试）**本就按 fail-safe 契约使用它**：`?: return entry` / `?: continue` / `?: return false`；其唯一的迁移写路径 `PasskeyEntryCoordinator.migrateLegacySchemaIfNeeded:352` 的 KDoc 明写「**失败即放弃**：… 原样返回条目，只留痕不迁移」⇒ 该函数**现在会抛 ISE 才是对契约的违背**。
