## P1 高危与核心功能问题（1 项）

### ISSUE-P1-431：封印载荷含整个密钥文件字节（上限 1 MiB），StrongBox 处理达数十秒，快速解锁不可用

- **核实时间点**：2026-10-02；**核实方式**：用户真机走查 §400 装机反馈「没有卡死，但转圈转了半天（密码 + 选密钥文件解锁后弹生物识别验证，最终进去了但耗时过长）」；密钥文件 ~700 KB。§400 已消除 ANR（密算移 IO），但 StrongBox 分块处理 700 KB 载荷本身仍需数十秒，且每次指纹解封都重复。ANR 期取证单次 binder `update` 即 5.28s。
- **参考调研（2026-10-02，docs/references/）**：KeePassDX 不封印密钥文件（`MainCredentialActivity.kt:452-455` TODO，开库时重读 `LoadDatabaseRunnable.kt:56`）；keepass2android 只封主密码、解锁时从磁盘重读（`PasswordActivity.cs:981-989`）；Monica 只封 32B 数据密钥。**无一家把密钥文件字节放进 Keystore 载荷**（ISSUE-P2-23 引入的做法属三家皆无）。
- **方案裁决（用户 2026-10-02 二选一拍板）**：**方案一（KeePassDX/kp2a 口径）**——封印载荷只装主密码；指纹解封后经「记住的密钥文件位置」（ISSUE-P3-04 基建：SAF 持久化读授权 + 记忆开关）重读密钥文件组合复合密钥；重读失败（文件移动 / 删除 / 授权失效）清陈旧封印回落密码模式（恢复通道既有）。不采用双层 DEK 封装（协议改动大）。
- **验收标准**：
  ① 登记与重封印载荷不再含密钥文件字节（v1 帧不带 keyfile 标志）；
  ② 解封路径：会话已有密钥文件因子（冷启动记忆恢复）直接用；没有则经记忆 Uri 现读（IO 线程）；读不到清陈旧封印回落密码模式并如实提示；
  ③ 敏感字节清零链与失败语义零变化；强生物识别 / 降级确认闸门不动；
  ④ 单测覆盖「解封 + 记忆重读成功送达两因子」「重读失败回落」；全量 test 绿 + 门禁全 PASS；真机装包 ~700 KB 密钥文件指纹解锁秒级完成（用户走查）。

## P3 低危问题、特性接线与体验优化（3 项）

### ISSUE-P3-339：仿冒域能否唤醒通行密钥（本地 RP 实验室）——**浏览器半环搁置**

- **状态（2026-09-27 用户指示）**：**暂时搁置**。剩余部分需要外部资源（自有域名 + ACME DNS-01，或企业策略放行自建 CA，或换自带信任库的浏览器并相应重述判据），用户裁「先精简描述、暂不做」。
- **威胁模型（勿在后续复用时被悄悄替换）**：**真实攻击者只有公开 DNS 与公网可信证书，没有任何设备篡改能力**。⇒ 一切结论必须出自**攻击者可达的**配置。
- **已闭环半环（代码层，2026-09-27）**：见批次与历史条目；`CredentialProviderLookalikeMatchTest` 已锁定跨域泄露收紧与 `extractDomain` 去尾点。
- **红线（不变）**：**在破不通真实信任锚之前，本条目下不得出现任何「仿冒域不会唤醒」的结论**。今天能声称的只有「本应用对给定 rpId 的接受/拒绝判定」，**不是**「Chrome 不唤醒仿冒站」。

### ISSUE-P3-437：长操作缺过程可感知性——解锁（KDF 派生 / 密钥文件 / 封印解封）零进度指示，同步与导入导出均为「结果型反馈」

- **核实时间点**：2026-10-02；**核实方式**：① 本仓走查——`UnlockScreen.kt` 全文无任何 `CircularProgressIndicator` / `LinearProgressIndicator` / 过程文案节点，`strings.xml` `unlock_*` 段无「正在派生 / 正在解锁」类条目（grep 核实）；同步 / 导入导出的既有反馈均为终态 Snackbar 或下拉刷新指示器，无分阶段 / 进度形态；② 竞品对照——[UI与操作体验的竞品对比报告.md](references/UI与操作体验的竞品对比报告.md) §3.1/§3.4/§5-G1：KeePassDX `ProgressTaskUpdater` 进度对话框贯穿加解密全流程（其架构分析 §6.3/§8.2 第 10 条，并点名为「大库在低端机上的可感知性」）；keepass2android `IKp2aStatusLogger` 两级进度消息（可取消）+ 前台同步服务进度通知（其架构分析 §6.2/§7.6）。
- **背景**：KDF 派生秒级起步，弱机 + 大库 / StrongBox 场景可达数十秒（`ISSUE-P1-431` 实测：分块处理 ~700 KB 密钥文件载荷达数十秒、单次 binder `update` 5.28s）；期间解锁界面无任何变化（按钮态之外零反馈），用户只能猜「卡没卡」。同步 / 导入导出同理：只有起点（转圈）与终态（Snackbar），上传下载中途不可见。
- **验收标准**：
  ① 解锁页接入状态驱动的过程指示：至少含「正在派生密钥…」「正在读取密钥文件…」阶段文案（Argon2 原生侧回调进度百分比为进阶项，不强制）；派生期间主线程不阻塞感知（文案先行即可）；
  ② 云同步「立即同步」与导入导出长操作复用同一过程反馈通道（阶段型起步即可，前台服务进度通知为进阶项）；
  ③ 过程反馈不泄露敏感信息（不显示密钥文件名以外内容、不显示派生中间量）；`FLAG_SECURE` / 遮挡过滤语义不变；
  ④ 新增 UI 状态有 `@Preview` 覆盖；全量 test 绿 + 门禁全 PASS。
- **关联**：与 `ISSUE-P1-431`（封印载荷性能）叠加修复后，快速解锁等待全过程可解释；本条只管「可感知性」，不改任何密算路径。

### ISSUE-P3-438：进程被系统杀死后无「上次会话未正常关闭」提示，用户不解为何需重输主密码

- **核实时间点**：2026-10-02；**核实方式**：① 本仓走查——`strings.xml` 全文无「上次会话 / 异常退出 / 被系统杀死」类文案（仅有编辑面 `unlock_unsaved_edits_discarded`「上次未保存的改动已丢弃」，`strings.xml:399`，语义不同层）；解锁页无对应一次性提示节点；② 竞品对照——[UI与操作体验的竞品对比报告.md](references/UI与操作体验的竞品对比报告.md) §3.1/§5-G2：keepass2android `AppKilledInfo` 在下次启动提示「上次被系统杀死」（其架构分析 §8.4）。
- **背景**：自动锁定把进程杀掉（系统回收）与用户主动锁库在 UI 上不可区分——下次打开都落在解锁页，用户易误读为「应用丢了我的会话 / 出了故障」，反而削弱自动锁定本应传达的安全感。
- **验收标准**：
  ① 区分「上次为异常退出（进程被系统回收 / 崩溃）」与「用户主动锁库 / 超时锁定」，仅前者在解锁页展示一次性轻提示（文案如实，不渲染成错误告警）；
  ② 判定依据复用进程生命周期既有信号（如进程级 `AutoLockManager` 状态），不新增持久化敏感数据；
  ③ 提示文案走 `strings.xml` 双语；有 `@Preview` 覆盖；全量 test 绿 + 门禁全 PASS。
- **关联**：低优先；可与 `ISSUE-P3-437` 同批实施（同为解锁页过程说明面）。
