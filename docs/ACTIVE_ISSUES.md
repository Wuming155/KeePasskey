### ISSUE-P2-620：进程重建后旧 PendingIntent 可混用另一域的密码请求

- **核实**：2026-10-15，当前工作区静态调用链、独立复核及 [Android 官方 PendingIntent 契约](https://developer.android.com/reference/android/app/PendingIntent)；中危、置信度中，**需要进一步验证真实 Credential Manager 保留窗口**。
- **位置**：`CredentialPendingIntents.kt:89-96`、`CredentialResponseAssembler.kt:346-359`、`PasswordFillActivity.kt:129-139,191-206,237-243`。
- **触发与后果**：系统仍持有域 A 的旧候选，提供者普通进程死亡后，新进程从 1000 重发同码，为同浏览器域 B 创建同组件、仅 extras 不同的入口；`FLAG_UPDATE_CURRENT` 可更新旧 token。落地页只比较系统包名，随后用新版 entry/domain 自洽校验；用户点旧项并完成验证后，A 请求可能收到 B 口令。未证明无交互窃取；force-stop 不可替代普通死亡。
- **建议与验收**：为每条入口设置跨进程唯一且参与 `filterEquals` 的请求标识（如随机 `Intent.data`），交付前绑定最终系统 origin/package/条目，保持系统所需可变标志。用独立持有者和真实两域 CM 流程验证旧请求不能收到新域秘密，保留 PID、系统回执与非空设备测试 XML；Autofill 同形计数器与旧 `AutofillId` 接受条件另行验证，不据此认定同样泄露。
- **整改方案**：[凭据入口跨进程隔离与最终请求绑定方案](architecture/问题整改方案/P2/ISSUE-P2-620/凭据入口跨进程隔离与最终请求绑定方案.md)（部分实施，仍开放）。
- **已实现**：入口加入随机 `Intent.data` 身份及交付前进程内请求上下文复核；API 37 Redmi 4X 实体机 `PendingIntentMatchKeyDeviceTest` 6/6 通过。
- **尚未完成**：用真实 Credential Manager 保留旧候选，验证提供者普通进程死亡后两个域的旧请求不能收到新域口令；Autofill 旧 `AutofillId`/请求计数器接受边界另需验证。

### ISSUE-P2-621：回滚状态写失败后，后续同步可采纳旧版本

- **核实**：2026-10-15，当前同步采纳、缓存比较、错误返回及锁定/重开链静态追踪；中危、置信度中，**需要进一步验证本地故障注入**。
- **位置**：`SyncEngineAdoptionSettlement.kt:26-34`、`SyncEngineSupport.kt:75-84`、`SyncRollbackGuard.kt:134-162,193-211`、`SyncContentChangeDetector.kt:59-83`、`SyncCycleRemoteOutcomes.kt:145-165`。
- **触发与后果**：同进程成功同步 A 后锁库并重开未改过的 A，进程内文件 checkpoint 仍在而内存同步参考为空；采用远端 B 并保存、提交 B 缓存/基线后，rollback 写入或改名失败。周期返回 Error，但进程与缓存继续存在；下一轮本地 B 对缓存 B 判未变，远端重放 A 因守卫 `current=A` 判 Unchanged，可再次保存并丢失 B 更新。需本地持久化故障，未证明远端能诱发该故障。
- **反证边界**：普通进程重建会在开库前清同步缓存且没有进程内 checkpoint，基线缺失时保守走冲突；**不报告仅靠进程死亡即可静默回滚**。正常高水位提交后 A 会进入 recent 并被拒绝；已有状态缺失/不可解析及 32 项窗口限界不等于本次部分提交状态。
- **建议与验收**：为正式库、缓存基线和高水位建立可恢复的代际/事务状态，高水位失败后禁止继续自动采用旧远端。定点注入 B 基线提交后的 rollback 写/rename 失败，再重放 A，确认拒绝或显式恢复/冲突而非直接覆盖；普通进程重建另列对照。
- **整改方案**：[同步采纳代际事务与失败隔离方案](architecture/问题整改方案/P2/ISSUE-P2-621/同步采纳代际事务与失败隔离方案.md)（部分实施，仍开放）。
- **已实现**：增加待提交摘要 quarantine；写入、开库和冲突处理遇隔离时 fail closed；加入基线提交故障注入用例。
- **尚未完成**：覆盖各提交阶段的进程终止/重启和真实磁盘回放；实现冷启恢复 UI 与意图协调，并验证重放旧远端 A 不覆盖已提交 B。

### ISSUE-P2-625：同步网络等待可使安全锁定延期数分钟

- **核实**：2026-10-15，当前同步挂锁、自动锁定与请求超时/重试源码及独立基线复核；中危、置信度高，未做慢网设备复现。
- **位置**：`SyncCoordinator.kt:245-252`、`SyncCycleRunner.kt:126-135`、`AutoLockSessionGuard.kt:128-143`、`AutoLockHoldoff.kt:21-52`、`SyncNetworkOptions.kt:37-42`、`TransientHttpRetry.kt:52-68`。
- **触发与后果**：取得同步 mutex 前即增加长任务挂锁计数，直到整个网络周期结束才释放；熄屏/后台超时锁定只返回 Deferred。单 call 上限 300 秒、至多 3 次尝试，但没有周期总预算或挂锁 deadline；慢响应可使安全锁定延期数分钟，排队调用也可延长挂锁。明文暴露另需设备/应用仍可被人访问，云端不能直接读库；finally 和单请求超时构成反证，不称永久不锁。
- **建议与验收**：网络使用独立密文快照，挂锁缩至必要本地提交段；明确安全锁定最长延期，能取消/暂停后续明文工作并可靠清理主凭据，合并重复触发。以慢 HTTPS、熄屏、后台超时和同步排队验证锁定完成时间及文件保全。
- **整改方案**：[同步网络与安全锁定解耦方案](architecture/问题整改方案/P2/ISSUE-P2-625/同步网络与安全锁定解耦方案.md)（部分实施，仍开放）。
- **已实现**：同步 mutex 取得后才申请自动锁挂锁；限时取得本地密文快照后释放；冲突上传前释放，并在本地采纳时重取挂锁；barrier/JVM 用例通过。
- **尚未完成**：定义并强制整个同步周期的锁定延期上限；取消底层 HTTP 请求并覆盖 412 重入；在实体机用慢 HTTPS、熄屏和后台超时实测锁定时间及文件保全。

### ISSUE-P2-627：锁库或进程冷启时周期同步在联网前直接失败

- **核实**：2026-10-15，WorkManager 执行体、周期入口和设置文案静态追踪；中危、置信度高，未实跑锁定态周期任务。
- **位置**：`PeriodicSyncWorker.kt:32-47`、`SyncCycleRunner.kt:134-136`；设置文案 `strings.xml` 的 `sync_periodic_sub`。
- **触发与后果**：启用周期同步后，任务运行时若库已锁定或进程新建，`databaseFlow` 为空，直接返回未解锁错误，尚未构造 Provider 或探测远端；Worker 对所有结果返回 success。周期任务不能在常见锁定状态完成所述后台云端变更检查，解封云凭据无需用户认证也不能消除此依赖。
- **建议与验收**：将密文待传队列/元数据探测与需解锁的 KDBX 合并分离，按库持久化修订及条件写基线；锁定时仅执行无需明文的工作，合并留待解锁。未支持前明确限定文案，锁定跳过与真实鉴权失败分开表示；不得为后台同步长期保留主密钥。以锁库/冷启后真实请求和解锁后收敛验收。
- **整改方案**：[锁定态周期同步分层与持久化任务方案](architecture/问题整改方案/P2/ISSUE-P2-627/锁定态周期同步分层与持久化任务方案.md)（部分实施，仍开放）。
- **已实现**：锁定态只做元数据探测；按库保存非秘密目标身份摘要、ETag 和待解锁状态；锁定态不下载、解析或上传 KDBX，并区分鉴权、临时网络和远端缺失结果。
- **尚未完成**：实现加密待传队列；用真实 WorkManager 冷启和持久化生产配置验证联网探测，并证明解锁后安全收敛。

## P3 低危问题、特性接线与体验优化

### ISSUE-P3-623：CSV 导出的库字段可被电子表格当作公式

- **核实**：2026-10-15，当前导入到导出的静态追踪及 [LibreOffice 公式导入选项](https://help.libreoffice.org/latest/en-US/text/shared/00/00000208.html)核对；低危、置信度高；已实现文本型工作簿，尚未用目标电子表格验证公式解释行为。
- **位置**：`KdbxCsvExporter.kt:81-95,106-144` 的 String/CharArray 两种写入；`BrowserCsvImporter.kt:130-143` 仅告警而保留字段；`SettingsExportController.kt:139-152` 有效保护明文导出授权。
- **触发与后果**：不可信条目字段以公式前缀进入库，用户确认导出 CSV 后，在允许公式求值的表格软件中打开。原始 CSV 仅转义分隔符、引号和换行，不能保证单元格按文本解释；具体内容伪造、外联或泄露取决于下游策略，不能描述为自动泄露。
- **建议与验收**：按 PD-86 区分原值交换 CSV 和表格安全导出；后者强制单元格文本语义，并提示原样 CSV 使用者存在公式风险。用无外联公式验证目标软件按文本导入，同时对拍原值 CSV 往返保持秘密不变。
- **整改方案**：[CSV 导出用途分离与公式防护方案](architecture/问题整改方案/P3/ISSUE-P3-623/CSV导出用途分离与公式防护方案.md)（部分实施，仍开放）。
- **已实现**：按 PD-86 保留原值交换 CSV，并新增将单元格写为 `inlineStr` 的表格安全 XLSX 导出；单测覆盖公式前缀、Unicode、空值、前导零和原值往返。
- **尚未完成**：在 Excel、Sheets 或 LibreOffice 等目标软件实际导入 XLSX，确认公式样式字段保持文本；API 37 实体机未安装表格应用。
