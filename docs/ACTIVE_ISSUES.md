### ISSUE-P1-589：解绑密钥文件后缓存残留，下一次保存重新引入旧因子

- **来源 / 严重度**：全面软件审计 `AUD-01`，High，可信度高。
- **核实时间点 + 核实方式**：2026-10-13；直读 `SessionCredentialCache.rotateCredentials`、`SessionPersistence.changeCredentials/save` 与 `ChangeCredentialsKeyFileRebindTest`；用现有编译类和临时合成库复现第一次解绑可仅密码打开、再次保存后必须使用旧密钥文件。仅审计，未整改。
- **背景 / 位置**：`database/.../session/SessionCredentialCache.kt:106-113` 仅当新密钥文件非 null 时更新缓存；解绑当次产物由 `SessionPersistence.kt:194` 用 null 生成，但后续保存又读取旧缓存（`:92`）。
- **触发 / 后果**：密码 + 密钥文件库解绑后再保存条目或同步；库悄然重新依赖旧密钥文件，用户已删除文件时可能失去库访问能力。
- **建议 / 验收**：轮换缓存必须精确采用双参意图并擦除旧因子；补「解绑→再次保存→锁定→仅密码重开」及失败回滚覆盖，检查导出密钥文件为空。不得只验证解绑的第一份产物。
- **详细证据**：[全面软件审计](security/全面软件审计_2026-10-13.md)。

### ISSUE-P1-591：同步完成时采用活动树，未上传的新编辑被记为已同步

- **背景 / 位置**：`app/.../sync/SyncCycleCommitPaths.kt:114-115` 等分支使用 `databaseSession.databaseFlow.value` 更新 `lastSyncedDb`，不是实际上传的 `localDbSnapshot`。`SyncContentChangeDetector.kt:59-65` 优先使用该基线。
