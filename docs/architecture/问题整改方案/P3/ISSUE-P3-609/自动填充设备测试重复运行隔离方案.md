# ISSUE-P3-609：自动填充设备测试重复运行隔离方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：本项已实施并于[批次504](../../../../resolved/batches/504-首轮在途整改收口批次.md)验收闭环。 以下矩阵保留原实施验收要求，实际结果以批次为准。

## 1. 问题与依据

来源为 DYN-03。2026-10-13 对照动态审计及 `AutofillAuthChainDeviceTest.kt` 前后置：独立客户端未结束，NEW_TASK 可复用原 Activity，客户端 requestedOnce 随实例保留。冷停后恢复数据集只证明请求前提修复，不证明认证后半段已经通过。

## 2. 目标与边界

同一设备连续执行至少两次，每轮都有新请求且完成最终填充验证；每轮失败也能清理测试客户端。只操作专用合成测试包，不 force-stop/清数据用户实际应用。

## 3. 实施步骤

1. 在 setUp 验证外部客户端包确为本用例的测试安装身份，再明确结束旧客户端 Activity/进程；同时建立 provider 会话锁定和服务选择前提。
2. 启动前记录客户端 PID/实例或运行编号，启动后断言本轮实际发出 requestAutofill；窗口出现不能代替新请求证据。
3. 对可复用 Activity 的客户端，按新运行身份重置 requestedOnce 或直接保证新实例；不能每次 onResume 都无限重发请求，形成系统弹窗循环。
4. tearDown 无论成功/失败都结束客户端并撤销该轮未消费句柄，恢复原 autofill_service；清理失败写独立证据，不覆盖原测试失败。
5. 证据路径加入轮次标识，保留第一轮失败、第二轮失败和修复复跑；不要让下一轮 logcat 清理抹掉未保存证据。
6. 把启动/结束操作做成显式测试前后置契约，避免依赖 connected 任务最后卸载时才清理。

## 4. 验收矩阵

| 执行方式 | 必须观察的结果 |
|---|---|
| 同设备连续两轮 | 两次新请求，两次完整认证及填充成功 |
| 第一轮故意超时→第二轮正常 | 第一轮证据留存，第二轮不被旧状态阻塞 |
| 客户端已在后台/前台 | 前置成功建立新实例/运行身份 |
| NEW_TASK 复用场景 | requestedOnce 不阻断本轮请求 |
| 清理异常 | 原失败仍可诊断，不删除用户包数据 |

修改客户端仅位于测试资产；保留其作为独立 uid 的真实系统交互，不替换成 app 内假页面绕过框架。

## 5. 顺序与实施验收

与 ISSUE-P3-608 的语言定位及 ISSUE-P3-610 的活动库选择一起验证，每轮结果要独立核对，不并发运行设备测试。装机身份先经过修复后的 ISSUE-P3-607 读数；设备源集修改必须实跑，之后执行统一全量与门禁。
