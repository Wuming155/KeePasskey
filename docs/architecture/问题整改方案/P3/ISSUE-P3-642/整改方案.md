# ISSUE-P3-642 原生Passkey候选在请求RP不匹配时仍走包名回退

> 状态：**尚未实施**。核实：2026-10-16（Asia/Shanghai）；源码基线：`94172d1efca004692b68ea480a1516753087fd70`。
> 等级：P3；结论：静态确认协议错配；不认定新增跨RP权限；置信度：高。本轮只记录审查和方案，不修改业务代码。

## 1. 问题与依据

PD-77规定rpId缺失/空白才退回包名维度，但native候选始终domainMatch||packageMatch。最终上下文未保留请求rpId，已绑定app即使请求RP-B也能选到RP-A并生成A的响应。

- 审查维度：功能完整性、安全性与权限控制。
- 影响范围：错误候选、被正常RP拒绝的断言和不必要计数写入；同一已绑定app本来可直接请求A，因此不把它定成新跨RP登录漏洞。
- 核实方式：当前源码调用链、状态转换及相关测试源码核对；下列产品复现序列未实跑。

- [app/src/main/java/com/keepasskey/app/passkey/CredentialCandidateMatcher.kt](../../../../../app/src/main/java/com/keepasskey/app/passkey/CredentialCandidateMatcher.kt)：原始行 57–62。
- [app/src/main/java/com/keepasskey/app/passkey/PasskeyAssertionRequest.kt](../../../../../app/src/main/java/com/keepasskey/app/passkey/PasskeyAssertionRequest.kt)：原始行 104–123。

复现/验证路径：

1. 已绑定native app具RP-A条目，以非空RP-B和空allowCredentials发Get请求。
2. 观察RP-A仍入候选；用户选中并验证后追踪authData使用A的RP。
3. 正常B应拒绝，核对未发生跨RP成功登录。

反证和限制：包名签名绑定和验证窗口仍有效，窗口按条目A展示RP；域不匹配不等于已证明越权。

## 2. 修复目标与边界

非空请求RP明确收敛候选与最终断言；缺失RP兼容政策另行明确。

涉及模块：app CredentialCandidateMatcher/PasskeyAssertionRequest/Activity。

预期结果：候选和实际签发与请求RP一致，减少协议失败。

保持现有产品裁决和已接受边界；方案中的新接口、屏障与测试是拟议实现，不能记作已落地。未经独立实现端到端读取/对拍，不声称 KDBX 互操作已经通过。

## 3. 实施步骤与失败处理

1. 按PD-77纠正包名回退条件并在上下文保留系统请求RP。
2. 最终门控复核凭据RP与请求；不匹配回明确静态错误。
3. 对缺失rpId流程先确认规范/兼容需求再定拒绝或受控回退，不凭空放宽来源校验。

失败处理：出现目标库/修订不匹配、IO失败或取消时，不谎报成功；保全已确认的正式文件和用户仍持有的草稿/恢复材料，明确展示部分完成边界。秘密仅在确定所有权后擦除，禁止误擦活动库共享引用。对“需要进一步验证”的后果先完成正负对照；反证成立则调整或撤销该结论，不硬凑修复。
