# ISSUE-P1-593：凭据轮换取消事务方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：核心候选已接入，仍未完整验收，条目保持开放；范围与剩余工作见[批次504](../../../../resolved/batches/504-首轮在途整改收口批次.md)。 以下矩阵保留原实施验收要求，实际结果以批次为准。

## 1. 问题与依据

来源为 AUD-05。2026-10-13 直读 `SessionPersistence.changeCredentials`：先轮换缓存再挂起写盘，CancellationException 在回滚前重抛，旧副本擦除也不覆盖此路径。已登记的宿主补证只证明写入前取消窗口；真正写后及 ViewModel 销毁窗口仍需验证。

## 2. 目标与边界

提交前失败保持旧磁盘+旧缓存；提交后保持新磁盘+新缓存并完成必要收尾。不能通过把取消归为普通 Failure 来掩盖取消，也不能仅用一个 finally 无条件恢复旧缓存。

## 3. 实施步骤

1. 先明确文件/SAF writer 的提交契约，区分未提交、已提交和结果不确定；writer 返回之后才置一个布尔标记，无法覆盖「替换完成但返回取消」窗口。
2. 在受控应用作用域运行轮换事务，页面仅等待/展示。受理请求时先复制调用方的密码/因子数组并建立任务所有权，不能让页面清理借用输入后后台任务仍读取它。UI 取消可以取消等待，已进入关键提交阶段的写入及收尾由事务所有者完成。
3. 优先以候选新凭据序列化，暂不更换现行缓存；进入提交窗口重新检查会话身份/代次和漂移，提交确认后原子切换缓存及会话状态。
4. 将删除旧凭据备份、同步凭据代次失效、封印更新纳入提交后的收尾。不能依赖一个可能已销毁的 ViewModel 执行这些步骤；封印无法更新时清除陈旧封印并标识待重登记。
5. 普通文件按提交证据决定回滚；SAF 部分写入可能使文件不可判定时进入恢复/告警状态，不假定抛异常等于旧文件完好。
6. 事务 finally 擦除所有自有旧/新副本及序列化缓冲。恢复缓存采用克隆或显式所有权转移，与 ISSUE-P1-589 一致；取消最终仍向原调用方传播。

## 4. 验收矩阵

| 注入窗口 | 必须观察的结果 |
|---|---|
| 派生前、派生后、写盘前取消 | 旧组合仍有效，候选副本擦除 |
| 原子替换完成、writer 尚未返回时取消 | 新组合有效，不回滚成旧缓存 |
| 切回调用调度器前取消 | 已提交事务仍完成同步/封印收尾 |
| ViewModel 销毁、后台锁请求 | 状态一致，无无限挂锁 |
| SAF 写入结果不确定 | 显式恢复状态，不谎报成功或可靠回滚 |

用可控制调度器和 writer 屏障验证，每个窗口回读磁盘并检查缓存、封印及同步标记。不能用「Job 已取消」替代事务结果断言。

## 5. 顺序与实施验收
