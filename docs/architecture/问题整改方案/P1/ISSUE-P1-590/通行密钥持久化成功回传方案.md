# ISSUE-P1-590：通行密钥持久化成功回传方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-02。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/data/repository/PasskeyEntryCoordinator.kt`，创建、替换、解绑及计数器更新均存在「保存 Failure 后只告警仍返回成功值」的分支。现有内存原子计数不等于磁盘提交。本次未验证真实 RP 或系统回调。

## 2. 目标与边界

注册成功必须对应已持久化的私钥；断言响应中的计数必须已提交。持久化失败时不向 Credential Manager 回传成功，不写入调用方信任绑定。沿用 KPEX、算法和计数饱和规则。

## 3. 实施步骤

1. 梳理协调器各写接口及仓库、注册 Activity、断言 Activity、导入消费方；统一返回 `KdbxResult<T>`，把未命中与保存失败分开表达。
2. 创建/替换/解绑对保存结果显式分支；仅 Success 向上交付成功值，Failure 使用既有稳定错误码和资源文案。
3. 为「更新计数→持久化→交付已提交值」建立受控事务。并发断言串行提交，各响应使用自己的已提交值，不重新读全局最新计数；不得持有会话 Mutex 再调用会重复取同锁的 save。
4. 失败策略采用保留 DIRTY 并显式阻断本次交付；计数允许产生空洞但禁止成功响应后回退。重试必须重新获取已提交计数，不能复用失败任务的响应。
5. 页面销毁后的事务由受控应用作用域收尾；响应发送仍检查请求存活，完成落盘不强迫已取消请求接收成功。
6. 切换调用方信任登记、成功提示与结果 Intent 到持久化确认之后；新私钥及签名中间数组由所有者 finally 擦除。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 返回 Failure / 抛出写盘异常 / 漂移拒绝 | 注册、替换、解绑均无成功响应，显示可恢复失败 |
| 计数保存失败 | 无有效断言被回传；重试不交付旧响应 |
| 多路并发断言 | 成功响应计数与对应提交一致且不重复，保留既有饱和语义 |
| 注册成功后立即锁定/重启 | 私钥仍存在并能完成后续断言 |
| 提交后页面取消 | 磁盘状态正确，无迟到的成功回调 |

扩展 `PasskeyEntryCoordinatorSignCountTest`，补协调器失败注入及 Activity 结果测试；保存失败不能只通过日志断言判定。

## 5. 顺序与实施验收

依赖 ISSUE-P1-601 的写入保护，事务取消语义参照 ISSUE-P1-593。先跑 app 定向测试并核对 XML，再全量及门禁；系统回传在独立 AVD 真跑。若触及 Passkey schema / PKCS#8 / KPEX，额外执行既有互操作对拍，退出码 2 不能当通过。
