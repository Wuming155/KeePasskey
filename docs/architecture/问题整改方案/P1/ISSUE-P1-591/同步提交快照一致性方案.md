# ISSUE-P1-591：同步提交快照一致性方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：本项已实施并于[批次517](../../../../resolved/batches/517-同步提交快照一致性批次.md)验收闭环。 以下矩阵保留原实施验收要求，实际结果以批次为准。

## 1. 问题与依据

来源为 AUD-03。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/sync/SyncCycleCommitPaths.kt`：首传及快速提交成功分支读取完成时的活动树作为 `lastSyncedDb`；快速路径还保存此时的活动树。上传 A 时用户保存 B，上传字节与基线可错配。交错后果仍需受控运行验证。

## 2. 目标与边界

上传字节、基线树、凭据版本、远端 ETag 及本地文件检查点必须具有明确版本对应。远端接受 A 后，可以保留本地 B，但不得把 B 标为已上传；不用长时间禁用编辑作为唯一方案。

## 3. 实施步骤

1. 从周期起点建立版本化快照，记录库身份、内容修订号、凭据代次、树及对应序列化字节；树浅拷贝共享秘密时声明借用和生命周期，不能直接清整棵旧树。
2. 将快照贯穿首传、快速提交、常规上传、强制策略及合并提交路径。所有基线赋值来自实际发送版本，不再读取完成时 Flow。
3. 上传返回后校验会话身份与代次；同库仍为 A 时完成正常结算。活动内容已为 B 时，仅登记远端已接受 A，保留 B 的待同步状态和本地检查点。
4. 快速路径的本地补存如保存了 B，应明确记录「本地 B、远端 A」；不得把 `settlement.accept()` 当成 B 已同步。核对拒绝结算时远端已变更的处理。
5. 凭据轮换或换库期间完成的旧上传不能污染新会话基线；由受控状态机处理结果，必要时失效并重新同步。
6. 同步状态回显只有在当前版本等于远端已确认版本时才能显示已同步；上传失败不前移基线。

## 4. 验收矩阵

| 受控时序 | 必须观察的结果 |
|---|---|
| 暂停上传 A→保存 B→恢复上传 | 远端为 A，B 仍待同步，第二轮上传 B |
| 上述时序后另一端写 C | B 与 C 合并或进入冲突，B 不静默丢失 |
| 首传/快速/强制/常规路径 | 每条路径遵守同一版本对应 |
| 上传期间换库或换凭据 | 旧结果不成为新会话基线 |
| 远端成功、本地补存失败 | 明示两端不同步，重启后可对账，不谎报全部成功 |

使用可控挂起点/屏障调度，不用概率性 sleep 模拟竞态；分别核对实际远端产物、缓存、正式文件和内存基线。

## 5. 顺序与实施验收

与 ISSUE-P2-596 的变化检测配套，随后联测 ISSUE-P2-597 的合并分支。先宿主受控交错测试，再本机 HTTPS 服务+独立 AVD 验证上传/重启/再次同步；跨客户端产物走官方实现对拍。读取同步威胁建模，维持既有 ETag、防回滚及 PD-21 基线/缓存分存口径。
