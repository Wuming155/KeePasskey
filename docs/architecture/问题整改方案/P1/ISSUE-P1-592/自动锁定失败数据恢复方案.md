# ISSUE-P1-592：自动锁定失败数据恢复方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：本项已实施并于[批次518](../../../../resolved/batches/518-自动锁定失败数据保全批次.md)验收闭环。 以下矩阵保留原实施验收要求，实际结果以批次为准。

## 1. 问题与依据

来源为 AUD-04。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/security/AutoLockSessionGuard.kt`：DIRTY 补存 Failure 后仍调用 lock，唯一的新树被销毁。问题针对已进入会话的修改，不改变主动放弃编辑草稿的产品口径。

## 2. 目标与边界

锁定继续按安全事件生效；补存失败不静默销毁未提交版本。推荐独立加密恢复副本，而非永久保持解锁。任何存储都不可写时只能如实告知无法保全，不能承诺必然恢复。

## 3. 实施步骤

1. 为锁定路径加入明确结果：正常保存、恢复副本已提交、全部保全失败；告警尽力持久化供下次进入应用查看。若连告警都无法写入，当前受保护界面必须明确提示，不能承诺进程死亡后仍有告警记录。
2. 正常保存失败时，在应用私有非缓存目录写恢复版本，使用会话当前复合凭据生成标准 KDBX；主密码和密钥文件不得随副本落盘。
3. 恢复产物包含库身份、版本关联及完整性可核对的信息，采用临时写入、fsync、原子替换；保留上一份有效副本直到新副本确认。恢复明文语义从成功解密产物读取，非敏感旁路索引只用于发现。
4. 恢复副本完成或明确失败后锁定并擦除会话；序列化走 Default，写入走 IO，受控作用域负责有限收尾。两个通道均失败时，登记明确数据丢失告警。
5. 冷启动发现副本后，让用户以对应凭据解锁，预览差异并选择恢复或另存；不能直接覆盖可能已经外改的正式库。
6. 成功恢复并确认正式文件后才删除副本。凭据轮换要重加密或清理旧凭据副本，不能重新引入旧密码可读的历史密文。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 正式写失败、恢复目录可写 | 如期锁定；重启后恢复新条目和附件 |
| 磁盘满，两通道都失败 | 仍锁定，明确无法保全告警，不显示已保存 |
| 写恢复临时文件中断/损坏 | 上一有效副本保留；损坏副本不能自动采纳 |
| 正式库已外改 | 恢复走差异/另存流程，不无提示覆盖 |
| 换凭据后发现旧恢复副本 | 遵循旧密文清理策略，不绕过换密目的 |

扩展 `AutoLockSessionGuardTest`，对正常补存、失败补存及保全失败分别注入。设备测试确认熄屏、后台锁和进程重启后的真实行为。

## 5. 顺序与实施验收

在 ISSUE-P1-593、ISSUE-P1-601 的事务保护稳定后实现。恢复入口和保留数量/期限属于本项新行为，需要在实施批次明确产品口径并同步政策；本方案推荐保留一份最新有效恢复版本，清理前须确认已恢复或用户明确放弃。执行统一结案验收；新增设备测试必须实跑。
