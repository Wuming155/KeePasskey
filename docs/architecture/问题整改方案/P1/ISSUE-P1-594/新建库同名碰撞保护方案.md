# ISSUE-P1-594：新建库同名碰撞保护方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-06。2026-10-13 直读 `VaultLifecycleCoordinator.createInFilesDir` 和 `SessionOpener.create`：向导名称直接映射文件，下层使用覆盖写通道。登记已有宿主合成库同路径 create 成功补证，不能将滚动备份视作安全的新建语义。

## 2. 目标与边界

普通新建只能创建不存在的目标，碰撞不能覆盖库、替换备份或注册空库。推荐默认建议不冲突名称、底层仍拒绝碰撞；本项不新增「确认后覆盖旧库」功能。

## 3. 实施步骤

1. UI 初始化及名称修改时建议未占用名称，存在碰撞给明确错误；统一处理扩展名和路径规范化，名称不得通过分隔符逃离指定目录。
2. 在 database 创建入口实施不可覆盖语义，而不是只依赖 UI 的 exists 检查；检查应在释放当前会话之前发生。
3. 使用文件系统支持的排他创建/不可替换提交原语，并让同目录其他写操作遵守约定。Windows 与 Android 分别验证支持情况，不能默认普通 rename 是不覆盖保证。
4. 临时加密文件完成后提交到占用的目标；并发被抢占时拒绝，不破坏对方文件。失败只清理由当前任务拥有的临时文件/占位，不删既有路径。
5. 成功后才切换会话与登记库列表；失败保留原活动库。既有缺文件自动建库入口同样遵守排他契约。
6. SAF 以系统创建文档的实际 Uri 为准，验证返回结果和失败清理；不得把任意已存在 Uri 的截断写入当作安全新建。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 同名旧库，备份开启/关闭 | 旧库和 .bak 哈希均不变，新建失败 |
| 两个任务争同一名称 | 仅一个创建成功，成功产物不被另一任务覆盖 |
| 目标是目录/路径逃逸/仅大小写差异 | 按实际文件系统规则拒绝，不影响目录外资源 |
| 临时写入失败 | 原活动库可继续使用，无误注册条目 |
| 正常建议新名称 | 新库可重开，登记路径为实际成功路径 |

覆盖 UI 与直接 DatabaseSession.create；底层测试必须绕过向导，证明不存在保护旁路。失败清理的文件归属也应断言。

## 5. 顺序与实施验收

本项可优先独立修复。普通保存的替换语义继续保留，新建使用独立的明确原语。先 database/app 定向测试并回读 XML，再全量与门禁；Android 文件及 SAF 语义在独立 AVD 验证，KDBX 新建产物走既有官方对拍。
