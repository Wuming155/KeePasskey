# ISSUE-P1-589：解绑密钥文件缓存修复方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：本项已实施并于[批次504](../../../../resolved/batches/504-首轮在途整改收口批次.md)验收闭环。 以下矩阵保留原实施验收要求，实际结果以批次为准。

## 1. 问题与依据

来源为 AUD-01。2026-10-13 直读 `database/src/main/java/com/keepasskey/database/session/SessionCredentialCache.kt` 与 `SessionPersistence.kt`：双参换凭据的 null 表示解绑，但 `rotateCredentials` 只在非 null 时替换密钥文件缓存。登记中的宿主复现已证实「第一次解绑成功、第二次保存重新依赖旧因子」；本次仅核对源码，没有重跑复现。

## 2. 目标与边界

双参接口精确采用新密码和新密钥文件；单参换密码继续保留原因子。主密码为空且解绑后不剩因子的组合必须拒绝。修复限于缓存与轮换事务，不改变密钥文件格式或记忆文件产品语义。

## 3. 实施步骤

1. 扩展现有 `ChangeCredentialsKeyFileRebindTest`，先固定连续保存后的失败表现，而非只检查解绑当次文件。
2. 在缓存锁内先准备新因子的独立副本，再完整替换两个缓存，null 必须落实为 null；旧缓存由缓存所有者擦除。准备副本失败时不得先销毁现行凭据。
3. 保留单参重载显式获取旧密钥文件副本的行为；将 Keep / Remove / Use 映射与双参契约逐条核对。
4. 将失败恢复与 ISSUE-P1-593 的提交点处理合并设计；旧快照移交缓存后不得又被 finally 擦掉，采用「恢复时克隆，事务擦除快照」或明确转移，不能混用。
5. 成功后沿现有路径刷新凭据版本、封印及同步失效标记；导出因子应返回空结果，不返回旧文件内容。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 密码+文件→解绑→编辑保存两次→锁定重开 | 仅密码每次均可打开；内容完整 |
| 改密码且 Keep | 新密码+旧文件可打开；缺文件失败 |
| 文件 A→文件 B→再次保存 | 只接受目标组合；导出为 B |
| 写盘失败 | 磁盘与缓存仍采用旧组合，能继续保存 |
| 仅文件库请求解绑 | 操作失败，原文件字节与因子保持有效 |

通过引用观察旧缓存和事务副本的擦除；调用方借用数组保持不变。拓展 `ChangeCredentialsKeyFileWipeTest`，不得仅凭最终引用为 null 推断字节已清零。

## 5. 顺序与实施验收
