# ISSUE-P1-631 外部漂移合并伪造共同基线，可能丢失本地新增和编辑

> 状态：**尚未实施**。核实：2026-10-16（Asia/Shanghai）；源码基线：`94172d1efca004692b68ea480a1516753087fd70`。
> 等级：P1；结论：静态确认；置信度：高。本轮只记录审查和方案，不修改业务代码。

## 1. 问题与依据

mergeAndSave 把当前 localDb 同时传作 base 与 local。合并器因此认为本地从未修改：本地新增条目在磁盘缺失时被推断为远端删除，同 ID 本地编辑则让磁盘版本成为唯一修改。随后采用并保存该结果。分组也受相同基线错误影响。

- 审查维度：数据流转与一致性、功能完整性。
- 影响范围：用户选择“合并后保存”仍可能丢失未提交本地条目/分组或恢复磁盘旧值；影响本地文件和 SAF 外部漂移处置，不代表普通三方同步均有此缺陷。
- 核实方式：当前源码调用链、状态转换及相关测试源码核对；下列产品复现序列未实跑。

- [app/src/main/java/com/keepasskey/app/data/repository/VaultFileDriftResolve.kt](../../../../../app/src/main/java/com/keepasskey/app/data/repository/VaultFileDriftResolve.kt)：原始行 141–159。
- [sync/src/main/java/com/keepasskey/sync/merge/KdbxEntryMerger.kt](../../../../../sync/src/main/java/com/keepasskey/sync/merge/KdbxEntryMerger.kt)：原始行 49–93。

复现/验证路径：

1. 打开基线库，保留磁盘旧版本；在当前会话新增 E 或把条目字段 A 改为 B。
2. 在保存前让外部写入改变文件元数据，触发漂移提示；选择“合并后保存”。
3. 跟踪 base=local=B、remote=A 的合并分支；E 因 be存在/re不存在被删除，B 被 A 选中；重解析保存文件核对。

反证和限制：正常 sync 周期若提供真实 base 不受这个特定调用错误影响；文件备份可能保留旧数据。本轮未实跑产品复现，静态数据选择分支已闭合。

## 2. 修复目标与边界

共同基线必须来自打开/最后确认持久化的真实版本；没有可信基线时保守保留两侧并要求冲突裁决。

涉及模块：app 仓库/漂移处置；sync 合并器；database 会话落盘。

预期结果：合并不会把本地修改同化为基线；采用失败不前移基线。

保持现有产品裁决和已接受边界；方案中的新接口、屏障与测试是拟议实现，不能记作已落地。未经独立实现端到端读取/对拍，不声称 KDBX 互操作已经通过。

## 3. 实施步骤与失败处理

1. 为漂移处置保留绑定库身份和修订的真实基线，避免借用当前可变树充作基线。
2. 按真实 base/local/disk 合并，展示冲突并在同一库修订校验后提交；基线缺失时禁止静默做删除裁决。
3. 覆盖条目/分组新增、同字段双改及删除/修改组合；失败保全原正式文件、脏树和恢复副本。

失败处理：出现目标库/修订不匹配、IO失败或取消时，不谎报成功；保全已确认的正式文件和用户仍持有的草稿/恢复材料，明确展示部分完成边界。秘密仅在确定所有权后擦除，禁止误擦活动库共享引用。对“需要进一步验证”的后果先完成正负对照；反证成立则调整或撤销该结论，不硬凑修复。
