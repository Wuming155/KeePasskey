# ISSUE-P1-601：全部写入口文件漂移保护方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-13。2026-10-13 直读 `RealVaultRepository.persistSession` 的漂移检查，与 `SettingsPreferencesController`、`SettingsDatabaseMetaController` 的直接 save 及 `VaultLifecycleCoordinator` 的换凭据入口对照：保护仅覆盖部分入口。本次未动态构造外部修改。

## 2. 目标与边界

所有修改已有活动库的用户操作，在覆盖前采用同源漂移/版本检查。外部修改必须提示或进入现有重载/合并流程，不能把更改设置当成覆盖授权。本项不改变 SAF 元数据不可读时的限界 §39，也不承诺无协作外部写者的绝对原子 CAS。

## 3. 实施步骤

1. 列出普通编辑、设置、元数据、换密、改绑、Passkey、自动锁补存、同步采纳等写入口，标明现有保护与例外；补测试证明所有受保护入口确实经过统一出口。
2. 在 app 仓库建立单一写入协调边界，负责库身份、会话修订、漂移检查、挂锁和结果；设置控制器只提交意图，不直接调用 session.save。
3. 参数校验和候选变换准备后，在实际提交前重验文件检查点。保持清晰锁顺序，避免在协调锁下调用再取同锁的入口；提示用户期间不长期持有会话锁。
4. 检测到漂移时返回稳定冲突结果并保留尚未落盘的意图；用户选择重载/合并后重建候选，不能把陈旧候选套到新树。
5. 成功提交后更新同一库的文件检查点、列表和同步标记；失败不刷新基线。SAF 元数据异步刷新继续按限界 §38 处理。
6. database 保留文件提交基本能力，不反向调用 app 漂移守卫。同步自身 ETag 与会话 CAS 仍由原协议负责，统一入口不能额外递归触发同步。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| File 被外端修改→算法/KDF/名称保存 | 拒绝无提示覆盖，外部文件字节保持 |
| 外改→换密/解绑/改绑 | 操作失败或经显式冲突处置后重建，缓存不先变 |
| 提示期间再次外改或换库 | 二次检查生效，旧确认不能授权新版本 |
| 保存成功→再次普通保存 | 检查点正确，无错误漂移告警 |
| SAF 元数据可读/不可读/延迟刷新 | 符合已登记边界，不宣称新增强保证 |

复用 `VaultFileDriftMetadataTest` 等现有资产，添加各入口动态失败注入。入口接线静态检查只能辅助，不能替代真实文件外改测试。

## 5. 顺序与实施验收

先定义统一出口，再接 ISSUE-P1-593、ISSUE-P2-602、ISSUE-P1-590；自动锁和同步联测检查死锁/递归。完成宿主 File 外改、AVD SAF 写回和取消测试，再统一结案验收。后续若要解决外部写者最后检查后的竞争，需单独定义文件系统/提供方支持，不在本项伪造保证。
