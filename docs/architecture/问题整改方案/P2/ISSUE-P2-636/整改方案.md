# ISSUE-P2-636 同步缓存与版本标记分离提交可在重启后误判无修改

> 状态：**尚未实施**。核实：2026-10-16（Asia/Shanghai）；源码基线：`94172d1efca004692b68ea480a1516753087fd70`。
> 等级：P2；结论：静态确认，崩溃矩阵待实跑；置信度：高（false-clean分支）；后续覆盖后果待验证。本轮只记录审查和方案，不修改业务代码。

## 1. 问题与依据

writeCache先替换.cache，再独立更新.version。两步之间中断会留下新字节与旧/缺失version；hasLocalChanges仅比较version/baseversion，缺失version直接false。冷启内容比较以当前库对新cache，两者相同仍判UNCHANGED，无法修复旧标记。

- 审查维度：数据流转与一致性。
- 影响范围：已保存本地内容可能不上传，远端长期落后；远端后续变化时有覆盖本地新内容的风险。不能表述为崩溃立即损坏正式KDBX。
- 核实方式：当前源码调用链、状态转换及相关测试源码核对；下列产品复现序列未实跑。

- [sync/src/main/java/com/keepasskey/sync/engine/SyncCache.kt](../../../../../sync/src/main/java/com/keepasskey/sync/engine/SyncCache.kt)：原始行 126–158。
- [sync/src/main/java/com/keepasskey/sync/engine/SyncCacheMaintenance.kt](../../../../../sync/src/main/java/com/keepasskey/sync/engine/SyncCacheMaintenance.kt)：原始行 29–39。
- [app/src/main/java/com/keepasskey/app/sync/SyncContentChangeDetector.kt](../../../../../app/src/main/java/com/keepasskey/app/sync/SyncContentChangeDetector.kt)：原始行 69–91。

复现/验证路径：

1. 建立已同步基线A，使version与baseversion相等。
2. 本地正式库保存B，writeCache交付B后、写version前用定点故障或进程杀死中断。
3. 重启：currentDb与cache皆B，但version/baseversion仍A；跟踪hasLocalChanges=false和远端A未更新；再引入远端C验证后续行为。

反证和限制：正常写完version或本轮重新序列化会恢复；进程内lastSyncedDb也可能识别内容变化。关键前提为冷启且缓存新字节与正式库一致。

## 2. 修复目标与边界

缓存字节、摘要和同步基线有可恢复的一致提交/校验规则；异常状态不能按clean处理。

涉及模块：sync SyncCache/SyncCacheMaintenance/SyncEngine；app SyncCycleSetup/SyncContentChangeDetector。

预期结果：重启不会把尚未同步的B标作clean；损坏元数据可诊断恢复。

保持现有产品裁决和已接受边界；方案中的新接口、屏障与测试是拟议实现，不能记作已落地。未经独立实现端到端读取/对拍，不声称 KDBX 互操作已经通过。

## 3. 实施步骤与失败处理

1. 选择单一事务清单指向版本化payload，或启动时从实际cache摘要重建并校验元数据。
2. 缺失/损坏/不匹配version保守标为需核对，禁止自动以远端覆盖。
3. 把恢复裁决接入app冷启内容变化检测，区分当前缓存与已确认同步base。

失败处理：出现目标库/修订不匹配、IO失败或取消时，不谎报成功；保全已确认的正式文件和用户仍持有的草稿/恢复材料，明确展示部分完成边界。秘密仅在确定所有权后擦除，禁止误擦活动库共享引用。对“需要进一步验证”的后果先完成正负对照；反证成立则调整或撤销该结论，不硬凑修复。
