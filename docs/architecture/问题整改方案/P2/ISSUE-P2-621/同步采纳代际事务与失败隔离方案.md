# ISSUE-P2-621：同步采纳代际事务与失败隔离方案

> 编制日期：2026-10-15（Asia/Shanghai）；源码基线：`4cfedc840d8cec67d7ba9db594de3b14c9355d0d`。
> 状态：已闭环，见 §532。Redmi 4X API 37 上五阶段 OS 进程 SIGKILL/冷启动矩阵 5/5 通过；正式 KDBX B 保全、远端 A 重放被拒。独立 marker 无 P2-627 探测记录时在实际解锁 UI 显示；恢复路径在 412 并发后保留本地 B、远端 C，再以新 ETag 显式选择本地并完成条件上传。细节与 run IDs 见 [§532 验收批次](../../../../resolved/batches/532-同步采纳进程终止恢复与本地保留Redmi真机验收批次.md)。

## 1. 问题与依据

当前登记为 P2、置信度中，需要进一步验证本地故障序列。[SyncEngineAdoptionSettlement.kt](../../../../../sync/src/main/java/com/keepasskey/sync/engine/SyncEngineAdoptionSettlement.kt) 的 `DeferredBaselineSettlement.accept()` 先提交缓存回执，再 `advanceBaseAndPersist()`，最后 `recordAccepted()`；句柄在这些 IO 前即标为已结算。[SyncRollbackGuard.kt](../../../../../sync/src/main/java/com/keepasskey/sync/engine/SyncRollbackGuard.kt) 状态写/rename 失败时，没有跨文件补偿。

正式库与 B 基线已前移、高水位仍为 A 的部分提交状态下，同进程再次同步可能把重放 A 判为 Unchanged，并覆盖 B。需本地持久化故障，尚未证明远端能诱发。普通进程重建会清同步缓存且不保留进程内 checkpoint，不能用它代替本次序列；正常提交后 A 进入 recent 会被拒绝。

## 2. 目标与边界

正式库、缓存、同步基线和已见高水位必须能对账到同一次采纳；出现不确定提交时禁止后续自动采纳远端，直到恢复或用户明确解决冲突。保留已知的状态缺失/不可解析及 32 项历史窗口限界，不增加 PD-46 已否决的本地 MAC/HMAC。

推荐“持久化采纳意图 + 代际对账 + 安全失败”设计。单纯把高水位写到最前面，会造成远端尚未落库就被标为已采纳；只在内存加错误标志，又不能处理锁库/重启。因此需要同一状态机覆盖本地提交前后。

## 3. 实施步骤与失败处理

1. 在 app 编排层定义采纳事务身份：库身份、远端目标/配置代次、原/目标内容摘要、远端 ETag、阶段。sync 层只接收不透明修订/摘要与回执，不依赖 database 模块或持有解密树。
2. 正式库变更前，原子持久化待采纳记录并同步落盘；记录失败即不进入正式库采纳。缓存/basecache 保持 PD-21 的分存语义，不因事务化合并删掉任一份。
3. 在数据库共享提交边界提交 B，取得与库身份、修订及实际文件绑定的回执；随后提交缓存、基线和高水位。每个阶段可重入，持久化阶段记录失败时保留原待采纳意图，不能假装事务已完成。
4. 重构 settlement 的 Pending/Committing/Committed/RecoveryRequired/Rejected 状态；accept 中途异常不能被幂等标志掩盖，reject 也不能“撤销”已提交的正式文件。明确重复调用与并发调用的终态。
5. 周期发生部分提交后立即进入恢复隔离：不自动下载覆盖、不谎报已同步。下一次同步、锁库重开及冷启均先读取待采纳记录，对比正式库摘要和事务代次；能证明 B 已提交才补齐状态，无法证明时保留本地与候选密文并要求恢复/冲突。
6. 初次引入事务记录时，旧状态按明确迁移规则读取；不要把“发现未完成事务”当作普通缺失状态走 fail-open。完成记录最后清理，清理失败按已提交事务幂等对账，不反复写旧正式库。

## 4. 验收矩阵

| 注入点/时序 | 必须观察的结果 |
|---|---|
| 已同步 A → 锁库重开 A → 采纳 B | 成功对照：正式库、缓存/基线、高水位一致，A 被拒绝 |
| B 基线提交后 rollback 写失败或 rename 失败 → 重放 A | B 不被覆盖；返回恢复/冲突或拒绝，且隔离状态持续有效 |
| 意图写失败、正式库写失败、缓存/basecache 失败 | 无虚假成功；正式库与记录能解释实际已提交阶段 |
| 各持久化阶段后普通死亡并冷启 | 不丢 B，不依赖原进程 checkpoint；可恢复或显式阻止自动采纳 |
| accept/reject 重复、accept 中途失败再调用 | 无第二次错误发布/覆盖；恢复结果唯一且可观察 |
| 无故障普通重启、旧版状态、32 项窗口对照 | 保持既有限界，不能把原有窗口误报为本次新缺陷 |

扩展 `SyncEngineTest` 的 P2-308 settlement 用例及 `SyncRollbackGuardTest`；真实临时文件系统覆盖缓存交付、基线文件及高水位原子替换失败。Redmi 4X API 37 设备验收已完成正式 KDBX B 重解析、独立 OS 进程阶段矩阵、无探测记录恢复提示及本地 ETag 条件恢复，具体结果见 §532。用户恢复操作只选择保留本地并发布密文，不提供无条件覆盖远端的路径；412 时保持隔离并要求再次确认。

## 5. 顺序、交付与回退

先建立故障序列，再确定与 ISSUE-P2-624 共用的版本回执，接入引擎 settlement 与 app 采纳，最后做恢复和格式迁移。推荐与 624/626 作为同一同步一致性批次联测，但各项独立给出验收结果。

回退必须保留待恢复记录及自动采纳隔离。旧版本不能识别未完成事务时，不允许无检查降级继续写库；先恢复/导出安全副本。正式库保全和重放拒绝证据不足时，本条保持开放。
