# ISSUE-P2-620：凭据入口跨进程隔离与最终请求绑定方案

> 编制日期：2026-10-15（Asia/Shanghai）；源码基线：`4cfedc840d8cec67d7ba9db594de3b14c9355d0d`。
> 状态：部分实施，仍开放。随机入口身份与请求上下文复核已落地；API 37 Redmi 4X 实体机 6/6 通过。真实 Credential Manager 保留候选、进程死亡与跨域交付尚未端到端验收。

## 1. 问题与依据

当前登记为 P2、置信度中，真实 Credential Manager（CM）保留旧候选的窗口仍需验证。[CredentialPendingIntents.kt](../../../../../app/src/main/java/com/keepasskey/app/passkey/CredentialPendingIntents.kt) 的 `nextRequestCode()` 仅进程内递增，重建后回到 1000；注释中“PendingIntent 不跨进程存活”的前提不成立。[官方 PendingIntent 契约](https://developer.android.com/reference/android/app/PendingIntent)明确：创建进程被杀后，其他进程持有的 token 仍可使用；extras 不参与匹配。

[CredentialResponseAssembler.kt](../../../../../app/src/main/java/com/keepasskey/app/passkey/CredentialResponseAssembler.kt) 的 `buildPasswordEntries()` 仅通过 extras 区分条目/域。[PasswordFillActivity.kt](../../../../../app/src/main/java/com/keepasskey/app/passkey/PasswordFillActivity.kt) 只交叉核对最终系统包名，域匹配仍取 extras。普通进程死亡后，同浏览器另一域的新入口可能更新旧 token；用户点击旧候选并验证后可能收到另一域口令。尚未证明无交互窃取，也不能用 force-stop 代替普通进程死亡。

## 2. 目标与边界

每条凭据入口具有跨进程不复用、参与 Intent 匹配的身份；最终交付同时满足系统背书调用方、候选上下文、活动库和目标条目绑定。请求不能验证时返回取消并重新获取候选。保持先验证后取密、包名签名绑定、黑名单及浏览器白名单语义。

[PasswordCredentialEntry 官方契约](https://developer.android.com/reference/androidx/credentials/provider/PasswordCredentialEntry.Builder)要求入口使用唯一 requestCode、`FLAG_MUTABLE` 且不使用 `FLAG_ONE_SHOT`。整改继续满足这些要求，不能用不可变入口阻断系统最终请求注入。

## 3. 实施步骤与失败处理

1. 在共享工厂生成不可预测的随机入口 ID，将不含域名、库名或秘密的 ID 放入预置 `Intent.data`；显式组件及现有 requestCode 分配继续保留。即使计数器重置或回绕，不同逻辑入口也不能匹配同一 token。
2. 接入 `CredentialResponseAssembler` 的密码/断言入口、`CredentialCreateEntries` 的创建入口、`KeePasskeyCredentialProviderService` 的解锁 Action。仅审计这些共享工厂消费者；Autofill 同形计数器单独验证，不能从本条推定其同样泄露。
3. 为入口保存不可混用的非秘密上下文：请求 ID、库身份、条目 ID、候选时可信 origin/package 和请求类型。生命周期/失效规则由入口工厂统一管理；重建后无法恢复上下文的旧入口安全失败，不以新版 extras 补配。不要为此持久化密码或用户验证结果。
4. `PasswordFillActivity` 使用 `PendingIntentHandler` 取得最终请求，并复用 `CallingOriginResolver.resolveTrustedOrigin()` 及现行浏览器白名单。比较最终 origin/package 与候选上下文，再按最终可信身份检查目标条目。缺失系统请求、非法 origin、身份不符均取消；原有“缺失时兼容放行”须连同兼容性用例一起更新。
5. 用户验证通过后、读取密码之前再次检查会话/库/条目及请求有效性；换库、锁库、字段绑定变化或请求失效均不交付。避免沿用验证前捕获的陈旧条目引用。
6. 更新错误注释和现有接线测试。旧版本发出的无随机身份入口只允许失效重选，不迁移为另一新请求。异常和诊断只记结果类别，不记录 origin、条目内容或口令。

## 4. 验收矩阵

| 场景 | 必须观察的结果与证据 |
|---|---|
| 同 requestCode、同组件、不同随机身份 | 实际 token 不同；发送旧 token 不读出新 extras，保留同身份负对照 |
| 独立持有者保留 A → 提供者普通死亡 → B | 提供者 PID 确实改变，旧 token 仍由持有者保留；旧入口只处理 A 或取消，绝不交付 B |
| 真实浏览器 A/B 两域 CM 流程 | 记录系统请求身份与虚构密码接收端回执；A 不收到 B 的秘密，不能仅凭组件测试宣称完成 |
| 系统请求缺失、域不同但包相同、白名单失败 | 无成功响应；原生应用签名绑定正常路径仍通过 |
| 验证期间锁库/换库/改绑定；取消后再次点选 | 不交付陈旧凭据；合法重复选择仍可用 |
| 解锁、密码创建、Passkey 创建/断言 | 最终请求仍能注入，既有归属门控及用户验证保持有效 |

扩展 `CredentialPendingIntentsTest`、`CredentialRequestCodeWiringTest` 与 `PendingIntentMatchKeyDeviceTest`。新增的跨进程用例须由独立进程/测试宿主持有 token；instrumentation 重启自身不能充当独立持有者。保留 PID、脱敏回执、非空设备 XML，分开记录 token 机制与真实 CM 结果。

## 5. 顺序、交付与回退

先建立旧 token 负对照，再实现统一入口身份与密码交付复核，最后回归所有共享工厂消费者。独立于同步整改，可单独交付。若真实 CM 保留窗口无法复现，保留机制证据并标记该项仍需验证，不能扩大漏洞结论。

回退时仍保留请求身份隔离和最终身份拒绝门控；兼容性故障可引导重新选择，不恢复无最终身份校验的交付。实施、JVM、设备、真实 CM 四层证据齐备且覆盖原触发链后，才能评估关闭。
