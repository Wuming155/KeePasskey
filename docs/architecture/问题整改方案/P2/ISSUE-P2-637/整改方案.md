# ISSUE-P2-637 前台闲置锁定任务未保存句柄，关闭或重排无法取消旧定时器

> 状态：**已闭环**。核实：2026-10-16（Asia/Shanghai）；整改与验收：2026-10-18。
> 等级：P2；结论：静态确认；置信度：高；定向 JVM 与隔离 API 36 AVD 验收通过。

## 1. 问题与依据

scheduleForegroundIdleLock取消foregroundLockJob后启动scope.launch，却没有把返回Job赋给该字段。所有取消点实际拿不到已启动任务；延迟结束又使用捕获的旧settings，不重新检查开关/前后台状态。

- 审查维度：功能完整性、用户体验与易用性、安全性与权限控制。
- 影响范围：关闭前台锁定、调长超时或转后台后旧计时器仍可能锁库；连续触摸积累多个定时任务。此路径更可能提前锁定，不支持“绕过锁定泄露”的结论。
- 核实方式：当前源码调用链、状态转换及相关测试源码核对；下列产品复现序列未实跑。

- [app/src/main/java/com/keepasskey/app/security/AutoLockManager.kt](../../../../../app/src/main/java/com/keepasskey/app/security/AutoLockManager.kt)：原始行 115–153。

复现/验证路径：

1. 启用短前台超时并启动计时，捕获旧任务。
2. 关闭前台锁定或将超时调长，或转后台且关闭后台锁定。
3. 以虚拟时钟推进旧deadline：字段仍null无法取消，旧设置进入triggerLock；设备样本验证实际交互时序。

反证和限制：每个旧任务会复查最近交互时间，部分时序自然不锁；因此实际触发应以确定性调度测，不能用随机等待概括。

## 2. 修复目标与边界

任一时刻至多一个当前有效前台计时任务，旧任务不能执行锁定。

涉及模块：app AutoLockManager/设置观察。

预期结果：锁定发生时间跟随最新设置和生命周期，旧任务不产生副作用。

保持现有产品裁决和已接受边界；方案中的新接口、屏障与测试是拟议实现，不能记作已落地。未经独立实现端到端读取/对拍，不声称 KDBX 互操作已经通过。

## 3. 实施步骤与失败处理

1. 将scope.launch返回值赋foregroundLockJob并在关闭/转后台/锁定/重解锁成对取消。
2. 到期读取最新调度代次、开关、会话与前后台状态后再触发锁定。
3. 保持后台计时语义和现有长任务挂锁策略。

失败处理：出现目标库/修订不匹配、IO失败或取消时，不谎报成功；保全已确认的正式文件和用户仍持有的草稿/恢复材料，明确展示部分完成边界。秘密仅在确定所有权后擦除，禁止误擦活动库共享引用。对“需要进一步验证”的后果先完成正负对照；反证成立则调整或撤销该结论，不硬凑修复。
