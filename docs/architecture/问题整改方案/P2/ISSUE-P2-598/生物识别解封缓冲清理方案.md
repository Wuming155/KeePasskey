# ISSUE-P2-598：生物识别解封缓冲清理方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-10。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/ui/screens/unlock/BiometricUnlockCoordinator.kt`：decode 与第一次挂起恢复密钥文件都在 finally 之前；解密数组由 withContext 返回还存在取消交付窗口。本次确认生命周期缺口，没有进行内存提取或硬件认证实测。

## 2. 目标与边界

从解密结果产生到最终消费，每个自有字节/字符载体均有确定性清理所有者；不能擦除 KeyFileSessionCoordinator 借出的会话密钥文件，也不改变生物识别授权和旧封印迁移语义。

## 3. 实施步骤

1. 在外层建立一个自有解密结果持有者，分配发生于工作调度器时立即登记进去；取消导致结果未回到调用方，外层 finally 仍能擦除它。
2. 解封完成后的流程以 decryptedBytes 的 try/finally 开始，再 decode；decode 抛异常时原字节同样被擦除。
3. 解码后的 payload 从获得时进入嵌套 try/finally，密钥文件恢复、解锁、成功事件发送等全部挂起点位于保护范围内。
4. 清理顺序覆盖 payload 密码/旧载荷因子及 decryptedBytes；payload 自有因子与会话借用因子分别登记，不做不区分所有权的统一清零。
5. 核对 codec 的半解码失败：若内部已分配 passwordChars 再抛异常，codec 本身负责该未交付资源；调用方 finally 无法清理未返回对象。
6. 取消继续重抛，恢复失败使用稳定文案；不要把用户取消误当「封印已失效」并无条件删除有效封印。

## 4. 验收矩阵

| 注入路径 | 必须观察的结果 |
|---|---|
| 第一次恢复操作抛异常/取消 | decryptedBytes、payload 自有数组已擦除 |
| decode 中途失败 | 原字节与已分配但未交付的数组已擦除 |
| 工作线程完成、调用线程接收前取消 | 分配结果仍被清理 |
| 解锁失败、成功事件 emit 取消 | 清理义务均完成 |
| 借用会话密钥文件 | 借用数组保持有效，不被本协调器擦除 |

测试以引用观察字节内容，并用受控调度器制造交付窗口；不只验证回调执行次数。保留旧/新载荷 codec 用例。

## 5. 顺序与实施验收

可独立整改，与 ISSUE-P2-600/606 共用所有权审查方法，不新增通用杂物类。先 app codec/协调器定向测试及 XML，再独立 AVD 生物识别授权、取消、返回密码模式验证和统一结案门禁。官方依据：[withContext 返回资源的取消风险](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/with-context.html)。
