# ISSUE-P2-655 S3目录参数先拼原文再拆分，含&前缀导致签名不一致

> 状态：**已实施（2026-10-17，JVM 级验证；真实 S3 端到端待执行）**。核实：2026-10-16（Asia/Shanghai）；基线：`94172d1efca004692b68ea480a1516753087fd70`。静态确认，置信度：高。

## 1. 问题与依据

目录列举将原始queryPairs拼成signQuery，值内&被signer当成参数分隔；wire URL则先编码值。prefix=foo&bar/因此在线上是一个参数，签名里却被拆为两项，canonical request不一致。

影响：含&的合法S3目录前缀无法浏览；若服务返回此类续页token，翻页亦失败。普通参数不受影响，不是凭据泄漏。

- [sync/src/main/java/com/keepasskey/sync/s3/S3DirectoryList.kt](../../../../../sync/src/main/java/com/keepasskey/sync/s3/S3DirectoryList.kt)：原始行48–61。
- [sync/src/main/java/com/keepasskey/sync/s3/S3RequestSigner.kt](../../../../../sync/src/main/java/com/keepasskey/sync/s3/S3RequestSigner.kt)：原始行110–123。

AWS SigV4要求按键和值分别URI编码并构造canonical query；依据：[官方签名步骤](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html)。

1. 使用前缀foo&bar（或测试续页token含&）调用list。
2. 抓取构建的wire URL和传入signer的signQuery：线上prefix编码为foo%26bar%2F，签名却按&拆成额外项。
3. 对照官方SigV4规范和独立签名实现，验证请求被拒签；真实服务验收待执行。

反证与限制：=在当前首个等号解析下不一定单独触发；需用&作确定缺陷，不声称所有特殊字符均坏。 本轮没有运行产品、服务或新增运行测试。

## 2. 修复目标与边界

同一结构化参数表生成wire和canonical query，值中的分隔符只作为数据。

模块：sync S3DirectoryList/S3RequestSigner/S3KeyCodec；app远端浏览。预期结果：保留字符不改变参数结构，合法目录与分页可验证通过。

## 3. 实施步骤与失败处理

1. 将签名query接口改为键值列表或明确编码后表示，避免丢失结构再解析。
2. 分别对键和值按SigV4编码再排序，wire/签名共用一份规范输出，避免双重编码。
3. 保留现有无参数签名与普通上传下载契约。

失败必须如实返回，不伪装成功/空列表；不打印请求认证材料，工作副本按所有权在finally清理。接口调整同时检查所有调用方，不修改生产凭据或真实远端数据。

## 4. 验收矩阵

- prefix/cursor含&、=、%、+、空格、Unicode和重复键；比较wire与canonical。
- 独立AWS签名向量与隔离S3服务目录/分页回执；错误不伪装空目录。

验收用例是后续计划，不是已通过结果。实现、编译/JVM/设备、真实S3端到端尚未执行。设备用例若新增/修改必须在隔离AVD或可丢弃设备实际运行并确认非空XML。
