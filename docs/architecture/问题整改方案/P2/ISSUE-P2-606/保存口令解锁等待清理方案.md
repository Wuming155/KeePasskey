# ISSUE-P2-606：保存口令解锁等待清理方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-18。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/passkey/PasswordSaveActivity.kt`：在 requireUnlocked 之前创建 passwordChars，finally 仅在之后的 startSave 协程内。取消解锁或协程根本未启动时，现有清理不执行。问题是可变副本遗漏，不要求平台字符串可擦除。

## 2. 目标与边界

口令数组从构造时即有所有者；解锁等待、取消、销毁、保存失败及成功移交均闭环。不能在异步保存仍借用数组时提前 onDestroy.fill，导致写入全零口令。

## 3. 实施步骤

1. 将数组登记到专用请求载体，由 Activity 的等待阶段持有；构造之后任何早退均调用幂等 release，不只在保存函数 finally 清理。
2. requireUnlocked 明确取消/失败回调并撤销迟到成功回调；取消立即释放待处理载体，成功只允许一次进入保存。
3. 保存任务启动前明确复制或转移：推荐保存任务持独立数组、Activity 擦除等待副本。创建任务但未执行也必须有完成钩子清理，不依赖协程体 finally 必然进入。
4. 保存任务借用其自有数组直到仓库调用结束，再 finally 擦除；onDestroy 仅清 Activity 仍拥有的副本，不碰任务副本。
5. 配置重建不把秘密写 SavedState；旧实例清理并注销回调，新实例重新验证请求来源和消费状态。重复回调不能重复保存。
6. 成功只在实际落盘后回传，沿用现有 Failure 判断；任务取消清理后重抛，使用资源文案而非异常明文。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 取消解锁、返回键、Activity 销毁 | 等待数组已擦除，不触发保存 |
| 已取消后迟到 UnlockSuccess | 无再次消费，不保存全零数组 |
| launch 前/未进入协程体即取消 | 任务副本清理执行 |
| 解锁成功后销毁/旋转 | 自有副本各自清理，无双写和提前擦除 |
| 正常保存成功/Failure | 内容正确或明确失败，所有自有数组最终清理 |

用受控 presenter 和调度器保留引用检查擦除；设备端补取消解锁及重建路径，不只验证 onDestroy 被调用。

## 5. 顺序与实施验收

与 ISSUE-P2-603 的请求身份/单次消费共同设计，避免两个独立状态机相互矛盾。先 app 定向测试/XML，再 Credential Manager 与传统 Autofill 两来源的独立 AVD 实跑，最终全量与门禁。平台 Intent/String 残留边界仍按限界表声明，不把数组修复表述为零明文驻留。
