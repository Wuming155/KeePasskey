# ISSUE-P2-599：历史尺寸免读取附件方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：已实施，条目已关闭；实施结果与验收限制见[批次505](../../../../resolved/batches/505-凭据轮换与历史大小整改闭环批次.md)。以下矩阵保留原方案与验收范围。

## 1. 问题与依据

来源为 AUD-11。2026-10-13 直读 `database/src/main/java/com/keepasskey/database/history/HistoryManager.kt`：估算附件用 attachment.data.size；`core/.../model/KdbxAttachment.kt` 已提供不读取来源的 Long size。落盘来源的 data 会重新加载独立明文。本次未测 ANR/OOM 或设备性能阈值。

## 2. 目标与边界

历史预算计数只读取尺寸元数据，不加载附件明文；保留现行数量优先、体积次之、最旧端裁剪的语义。此次不改变历史大小估算与真实序列化大小之间的既有差异。

## 3. 实施步骤

1. 将 attachment.data.size 改为 attachment.size，尺寸累加全程使用 Long；字段长度及其他 Int 相加先转 Long，避免提前溢出。
2. 对异常负尺寸/超大尺寸设计稳定拒绝或饱和策略，不能溢出成负数后绕过预算；与 BinarySource 的尺寸契约对齐。
3. 一次计算各历史项估算值并按结果裁剪，避免求和后又反复估算被删除项；只在收益明确时加入该局部优化。
4. 核对编辑及保存调用链的调度，确有大量遍历的 CPU 段放 Default；尺寸 getter 不包含 IO，不因本修复引入额外读取。
5. 保持条目与附件共享生命周期：求尺寸过程不擦数据，不清 BinaryStore；历史下线后的擦除仍交给现有身份判定路径。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| load/openStream 调用即失败的 BinarySource | 正常完成计数和裁剪，读取次数为 0 |
| size 超 Int.MAX_VALUE 的虚拟来源 | 按 Long 正确执行预算，不截断 |
| 多份大附件历史、数量/尺寸双约束 | 按原规则保留最新项 |
| maxItems/maxSize 负值或零值 | 保持既有禁用/清空语义 |
| 正常编辑与保存 | 存活附件完整，下线资源按所有权清理 |

扩展 `HistoryManagerTest`，用虚拟尺寸而非分配数 GB 数组验证边界。性能测试另用设备合成大附件库记录主线程耗时、分配量与读取次数。

## 5. 顺序与实施验收

可独立先做，并与 ISSUE-P2-600 的附件交接联测。迭代跑 database 定向测试并回读 XML，结案全量与门禁；性能结论只引用实际设备读数，宿主「0 次 load」只证明算法没有读取附件。
