# ISSUE-P2-627：锁定态周期同步分层与持久化任务方案

> 编制日期：2026-10-15（Asia/Shanghai）；源码基线：`4cfedc840d8cec67d7ba9db594de3b14c9355d0d`。
> 状态：已完成，见 §531。锁定态元数据探测、filesDir KDBX 密文队列、ETag 条件上传、网络恢复重试和 Android 系统重启恢复均已验收。Redmi 4X API 37 冷启损坏队列流程通过 1/1：恢复提示在 MainActivity 解锁界面真实显示，用户显式手动同步后提示清除，正式库及 HTTPS 服务端均保留 revision B。P2-621 独立采纳阶段进程终止、正式 KDBX 文件事务对账和无探测记录意图处置仍由 ISSUE-P2-621 跟踪，不纳入本条关闭结论。

## 1. 问题与依据

当前登记为 P2、置信度高。[PeriodicSyncWorker.kt](../../../../../app/src/main/java/com/keepasskey/app/sync/PeriodicSyncWorker.kt) 调用普通周期入口；[SyncCycleRunner.kt](../../../../../app/src/main/java/com/keepasskey/app/sync/SyncCycleRunner.kt) 在 `databaseFlow` 为空时、构造 Provider 之前返回未解锁错误。Worker 将非取消结果都映射成 success，该次不会因此重试；app 的 `lastOutcome`/失败通知仍可能反映错误，不能称完全无反馈。

解封云凭据不依赖用户认证，并不能消除 KDBX 会话依赖。`SyncCacheEvictor` 锁库即清现有 sync 缓存；它不能直接当作跨锁/冷启的待传队列。现状未实测真实锁定态请求。

## 2. 目标与边界

拆成无需解锁的密文/元数据工作与必须解锁的 KDBX 校验、解密和合并。锁定时只探测远端或条件上传已证明对应的密文快照；远端变化先登记待合并，解锁后验证再收敛。不为后台周期长期保留主密钥，不自动解锁，不将已下载密文直接采用为正式库。

分阶段交付：先如实限定设置文案和结果，再支持锁定态元数据探测，最后接入持久化密文待传队列。仅完成前一阶段时不得宣称完整后台同步已可用。

## 3. 实施步骤与失败处理

1. 将周期入口分派到“已解锁完整同步”或“锁定态探测/密文传输”，定义未配置、需要解锁、远端变化待合并、暂时网络失败、鉴权失效等有类型结果。Worker 调度结果与用户同步状态分开，不把锁定跳过标成已同步。
2. 引入按库身份和配置代次持久化的非秘密任务描述：目标、已确认 ETag/条件写基线、密文修订摘要、回滚库命名空间及待传/待合并阶段。待传密文本体独立于锁库会清的 sync 缓存，保存在应用私有 `filesDir/periodic_sync_pending`，通过 `AtomicFileWriter` 原子写入并限制为 128 MiB；载荷是原样 KDBX 密文，不持有主密钥或解密树。
3. 锁态 Worker 从当前正式 KDBX 文件/有持久授权的 SAF URI 读取已加密字节，先形成摘要并持久化密文快照，再与目标、库身份、回滚作用域和基线 ETag 一致性复核。仅当本地快照摘要仍匹配且远端 ETag 未变时才条件上传；队列不确定、配置代次不符或旧版缺回滚作用域时停止自动写入。
4. 复用 P3-628 的生产 `useProvider` 作用域。锁定态执行元数据请求；远端 ETag 改变或不存在时记待处理状态，不将 ETag 当可信内容版本，也不在锁定时解析 KDBX 明文。
5. 上传采用现有条件写契约，412/目标变化变为待解锁冲突。提交前写 rollback quarantine；远端成功后才前移回滚高水位与探测 ETag。进程在远端提交后、本地记录前死亡时，下一次锁态任务下载并校验候选密文摘要，匹配则幂等收尾，不匹配则保留队列和 quarantine 并要求解锁。该事务仍依赖 P2-621 冷启恢复 UI 收口。
6. 解锁后校验库/配置代次与正式库修订，验证候选完整性并按既有合并/防回滚流程采纳；本地已有新保存时保留双方版本。删除库、解绑云端、改账号/路径后废止旧队列，避免向旧目标继续上传。
7. 为暂时网络错误使用有上限的 retry/backoff，锁定待合并不做重试风暴，鉴权失效要求用户处理。修改 `sync_periodic_sub` 及状态文案，说明系统调度非精确计时和锁定态能力范围。[WorkManager 官方契约](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)说明周期执行受约束及系统优化影响。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 锁库后执行真实周期任务 | 持久化生产配置生成真实元数据请求，无主密钥/解密树驻留 |
| 普通进程死亡 → 冷启 Worker | 不打开 UI 即能恢复允许的任务，不能用注入 Provider 代替生产配置 |
| 有待传密文且远端基线未变 | 条件上传对应修订；本地更新版本不误记已上传 |
| 远端变化/412、队列缺失或元数据损坏 | 不覆盖远端/正式库，记录需要解锁或恢复 |
| 解锁、再次编辑、完整同步 | 待合并状态真实收敛，所有本地更新保留，正式文件可重解析 |
| 网络暂错、鉴权失败、任务停止、换库/换目标 | 正确分类、有限重试、清理凭据，不上传旧目标 |

JVM 已覆盖密文队列原子持久化/摘要校验、锁态条件上传、412 后按原 ETag 重试、回滚高水位更新、服务端提交后冷启动对象重建与摘要对账，以及解锁后正式库 B 保全。新增 debug-only raw trust anchor 后，`run_p2_627_locked_queue.py` 可在不改系统 trust store、不重启实体机的情况下运行受控 HTTPS。Redmi 4X API 37 非空 prepare/resume XML 覆盖普通 app 进程死亡；受控 MOVE race 的 HTTP 412 与原子上传队列保留；载荷摘要篡改导致 `needs_unlock/PROBE_STATE_CORRUPT` 且远端不变；暂停本地 HTTPS 服务导致 `temporary_network_failure`，服务恢复后新 Worker 重试上传 B 并清队列。系统重启分支仍在隔离 API 36 AVD 上通过，新 PID 执行任务并在解锁后保全 B。普通进程死亡、force-stop 和系统重启分别记录，不混用结论。剩余 UI/意图协调依赖 P2-621。

## 5. 顺序、交付与回退

建议顺序：文案/结果分类 → 生产 Provider 作用域 → 持久化元数据探测 → 密文队列 → 解锁收敛。完整队列依赖 P2-621/624 的事务和修订回执，锁定安全依赖 P2-625。持久化探测基线供 P3-628 复用。

回退时停止有不确定状态的后台上传，保留待传快照与待合并信息供解锁恢复；仍可提供安全的元数据探测。不得通过保留主密码、关掉锁库缓存清理或无条件上传实现“可用”。
