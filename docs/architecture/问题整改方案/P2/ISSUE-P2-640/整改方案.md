## 1. 问题与依据

导入generation只防止旧进度覆盖UI；persist开头只检查一次isLocked，后续各条saveEntry/saveGroup面向当前活动单例，没有捕获目标path/session ticket。锁库/换库/重新解锁交错下，剩余条目可能写入另一个库。

- 审查维度：数据流转与一致性、安全性与权限控制。
- 影响范围：可能产生跨库错投或部分导入；目前只有缺少目标绑定的静态证据，实际UI/锁定交错需确定性验证，不宣称已发生数据泄露。
- 核实方式：当前源码调用链、状态转换及相关测试源码核对；下列产品复现序列未实跑。

- [app/src/main/java/com/keepasskey/app/data/importer/VaultImporter.kt](../../../../../app/src/main/java/com/keepasskey/app/data/importer/VaultImporter.kt)：原始行 81–95。

复现/验证路径：

1. 在库A启动含多个条目的导入。
2. 首条持久化后暂停，通过正常锁定/解锁流程转到B（记录实际可达入口）。
3. 恢复导入，检查后续写入是否被拒绝及A/B正式文件；若生产流程已阻止交错，记录反证并调整定性。

反证和限制：进度对话框限制部分本地导航，单次底层写入也有锁；这不能静态证明整个导入批次绑定，但会降低交错可达性。

## 2. 修复目标与边界

批次目标和每次写入均绑定启动时库身份及有效会话代次。

涉及模块：app VaultImportController/VaultImporter/ImportPersistRun/仓库写入。

预期结果：余下导入不会跟随全局活动库漂移，部分完成可解释。

保持现有产品裁决和已接受边界；方案中的新接口、屏障与测试是拟议实现，不能记作已落地。未经独立实现端到端读取/对拍，不声称 KDBX 互操作已经通过。

## 3. 实施步骤与失败处理

1. 先加barrier复现和生产入口走查，确认是否可达；若不可达保留约束证据后重评。
2. 引入显式导入target ticket并让组/条目提交在同一原子校验边界核对，变更会话立即中止。
3. 返回已提交/未提交分段报告，取消不谎报回滚整个批次；失败清理待提交秘密。

失败处理：出现目标库/修订不匹配、IO失败或取消时，不谎报成功；保全已确认的正式文件和用户仍持有的草稿/恢复材料，明确展示部分完成边界。秘密仅在确定所有权后擦除，禁止误擦活动库共享引用。对“需要进一步验证”的后果先完成正负对照；反证成立则调整或撤销该结论，不硬凑修复。

### 2026-10-20 实施与证据

实现采用 `SessionCredentialRequest` 协程上下文传播；`SessionContentMutations` 的既有 mutex 与 `SessionPersistence.saveLocked` 在实际改树/写盘前复核身份，避免外层持同一非重入锁造成死锁。`VaultImportController` 在解析前捕获请求，`ImportPersistRun` 遇会话变化立即停止；报告单列 `unprocessed` 和 `recycleBinIncomplete`，此前已确认写入保留在原库。

2026-10-21 续办核对：JVM `ImportSessionStopTest` 3 例覆盖首条提交后停止、分组失效不得回退以及回收站部分完成报告；`SessionBoundMutationTest` 2 例在同一 mutex 上排队后替换库/同路径会话，覆盖七类变更与保存；原有导入进度/取消、会话与仓库回归一并运行。隔离 `KeePasskey_Remediation_20261020`（Android 16 / API 36）实跑 `ImportSessionBindingDeviceTest` 1/1：真实 CSV 控制器和生产仓库在首条 A 正式写入后以屏障切 B，A 重解析仅有首条，B 正式文件逐字节未变，报告 `imported=1/unprocessed=1/sessionChanged=true`。不将该设备样本外推为进程终止、取消再启动或完整锁定重开矩阵已完成。
