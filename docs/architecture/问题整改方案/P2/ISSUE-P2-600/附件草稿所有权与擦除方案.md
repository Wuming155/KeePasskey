# ISSUE-P2-600：附件草稿所有权与擦除方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-12。2026-10-13 直读 `EntryEditPasswordGenerator.kt` 的 EntryEditAttachmentDraft 与 `AttachmentMergePolicy.kt`：同名替换/移除直接丢引用，新附件入库直接共享 UI 数组；登记指出 ViewModel 锁定/销毁清理遗漏附件。KdbxAttachment 的内存 data 是借用视图，不能直接填零补洞。

## 2. 目标与边界

未交付草稿由编辑页独占并在移除、替换、放弃、锁定和销毁时擦除；已进入会话的附件由会话负责，草稿清理不得损坏库。保持 refIndex 优先的同名附件身份匹配与既有落盘附件策略。

## 3. 实施步骤

1. 在导入→UI草稿→提交候选→会话/历史的链路标明 O/B/S 所有权；区分新导入自有数组与已有附件投影，不能仅按 filename 判谁拥有。
2. 推荐复制交接：提交时为会话建立独立副本，草稿仍持原副本直到提交状态明确，再擦草稿；不修改 KdbxAttachment 全局零拷贝契约。
3. 同名替换/移除前只清理该草稿独占的旧数组；UI 状态更新可能重试，不把清零副作用放入会重复执行的 StateFlow.update 闭包。
4. 保存失败区分「未入会话」与「已入会话但落盘失败」：后者由会话保留 DIRTY，新会话副本不能随错误界面销毁；未采纳候选由候选所有者擦除。
5. 给锁定、换库、离开编辑页、onCleared 建立幂等清理入口；如使用转移备选，必须在成功交接后从草稿注销，不能仍双持同一数组。
6. 历史及附件池共享资源继续使用身份集合判定，不对已有投影调用 data.fill；敏感草稿不得写 SavedState、日志或可打印 data class。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| 新导入→移除/同名替换/放弃/锁定 | 被淘汰的自有数组擦除 |
| 保存成功→编辑页销毁→锁定重开 | 库附件字节完整，不全零 |
| 候选失败/落盘失败→重试 | 责任归属明确，DIRTY 数据可补存 |
| 已有同名不同 refIndex 附件 | 不误删、不擦借用资源 |
| 重复锁定及 onCleared | 幂等，无提前擦除或遗漏 |

扩展 `AttachmentDataOwnershipTest`、`AttachmentSameNameEditSaveTest`；用引用和内容分别断言草稿擦除与存活副本不受损。

## 5. 顺序与实施验收

先定所有权再补清理，不能反过来直接填零。与 ISSUE-P1-592 的锁定恢复联测，恢复产物要包含已入会话附件。app/database 定向测试回读 XML，再独立 AVD 导入/保存/锁定/重开及统一结案验收。
