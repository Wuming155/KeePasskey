# ISSUE-P2-603：锁定态自动填充保存请求隔离方案

> 编制日期：2026-10-13（Asia/Shanghai）；源码核对基线：`65cc39f8`。
> 状态：方案已编制，尚未实施；登记条目继续开放。以下测试均为实施时的验收要求，不是本次实测结果。

## 1. 问题与依据

来源为 AUD-15。2026-10-13 直读 `app/src/main/java/com/keepasskey/app/autofill/KeePasskeyAutofillService.kt` 的 dispatchLockedSave：固定 requestCode，身份相同的 Intent 只变 extras，配合 UPDATE_CURRENT 会更新旧入口数据。官方 PendingIntent 契约确认 extras 不足以建立独立身份。

## 2. 目标与边界

每个保存请求对应唯一系统入口；两个请求并存、乱序点击、进程重建均不串凭据。保持显式非导出 Activity 和 FLAG_IMMUTABLE；不通过恢复可变性解决串单。

## 3. 实施步骤

1. 每次请求生成不可预测且不含凭据的请求标识，写入 Intent.data 或其他参与 filterEquals 的身份字段；仅递增 Int 可能在重启后重用，不作为唯一长期身份。
2. 保留显式组件及 immutable 标志；审查 UPDATE_CURRENT 的必要性，同一请求身份更新不能影响另一请求。
3. 推荐单次消费与过期回收：本请求成功、取消、超时后使句柄失效；系统未点击的请求不能因 Service.onDestroy 被过早取消。
4. 进程死亡后若系统仍保有含本请求 extras 的 PendingIntent，按相同请求身份继续；重复消费通过已消费/过期元数据拒绝。元数据不得包含明文口令，也不能依赖仅内存的标记完成跨进程判定。
5. 如改为应用请求仓库，只在加密载体内保留敏感请求并定义解封/清理期限；不能为了恢复把口令写普通文件或 SavedState。
6. Activity 检查绑定包名、域及当前请求身份；数组生命周期另由 ISSUE-P2-606 负责。

## 4. 验收矩阵

| 场景 | 必须观察的结果 |
|---|---|
| A、B 同时等待，先 A 后 B / 先 B 后 A | 各自保存正确用户名、包/域、口令 |
| A 已获得入口后创建 B | A 的 extras 不被更新成 B |
| 杀死服务进程后点击 A | 正确恢复 A，或明确拒绝；绝不打开 B |
| 重复点击、取消、过期 | 单次消费/失效生效，敏感状态清理 |
| 试图 fillIn 修改目标或凭据 | immutable 与显式组件继续有效 |

宿主可检查 Intent 身份构造；PendingIntent 等价及系统留存必须在独立 AVD 验证，不以 requestCode 数值不同的断言代替真实点击。

## 5. 顺序与实施验收

与 ISSUE-P2-606 及 ISSUE-P3-608~610 的可重复设备环境配套。官方依据：[PendingIntent 身份与更新规则](https://developer.android.com/reference/android/app/PendingIntent)。先 app 定向测试/XML，再设备双请求实跑和统一结案验收；请求仓库为备选，优先减少额外持久秘密。
