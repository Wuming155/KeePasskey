## 1. 问题陈述

`RC-02` 的症状是「同一个文件里，三处清了、第四处漏清」，且**反复出现**（`P3-96` / `P3-140` /
`P3-198` 三批各自都是「又发现一处漏清」）。逐处补丁之所以必然再漏，是因为：

1. **擦除义务没有归属主体**：`Arrays.fill(x, 0)` 写在函数体里，语义只表达「我擦了一个数组」，
   不表达「这个数组归我所有、我擦它是本分」。下一个读代码的人无法判断「某处没擦」是**遗漏**
   还是**有意留手**（借用视图确实不能擦）。
2. **交付边界没有名字**：同一份字节在传递过程中会换手（本类持有 → 传给流 → 传给原生变换），
   而 Kotlin 没有 `Drop` / RAII，`copyOf()` 与直接赋值在**调用点看起来一样**
   （`ownedSecrets` 的 §147 缺陷正是这类误判：调用方按 JCE 假设以为「已克隆」而提前擦除，
   致原生惰性读路径拿到全零密钥）。
3. **豁免没有下界**：既然没定义「什么算秘密」，那么「这里不用擦」就永远只是一句口头理由。

**本契约要固定的就是这三件事**：类别（谁负责）、边界（怎么交）、下界（什么可以不管）。

**不在本契约范围内**（避免范围漂移，各有归口）：
- **生命周期事件的覆盖面**（锁定 / 换库 / 退出三事件是否通知到每个持有者）→ `RC-05`，
  见 `ACTIVE_ISSUES.md` `ISSUE-P2-232` 与 `已知工程限界.md` §13 / §14。
- **秘密以不可擦 `String` 表示的边界**（Compose 主密码、HBF 前缀等）→ `RC-01`，
  见 `已知工程限界.md` §2.4 / §8。
- **函数内是否该用 `ByteArray` 而非 `String`** → 见 `.codebuddy/rules/engineering-rules.md`
  §「敏感数据处理」。

## 2. 四类所有权（唯一分类法）

任何承载**明文或密钥材料**的数组 / 缓冲，在任一时刻**恰好**属于下列四类之一。

### 2.1 类别定义

| 类别 | 名称 | 定义 | 就地 `fill(0)` | 交出后 |
|:--:|---|---|:--:|---|
| **O** | **Owner（独占所有权）** | 本持有者是该缓冲的**唯一**引用者，且其可达性由本持有者独自决定 | ✅ **允许且必为** | 必须**转移**（交出后本方不再持有）或**复制**（各自负责） |
| **B** | **Borrow（借用视图）** | 本持有者可读该缓冲，但**唯一所有者是别人**（本方不决定其生命周期） | ❌ **禁止** | 原样归还 / 只读消费，不得驻留 |
| **S** | **Shared（别名共享）** | 同一实例被**两个及以上逻辑所有者**同时可达（copy-on-write、浅拷贝、列表复用） | ❌ **禁止**（会误伤存活方） | 只能「丢引用」；擦除须经身份集合判定 |
| **P** | **Process-lifetime（进程级）** | 该秘密的生命周期**等于进程**，设计上**不擦、不轮换** | ❌ **禁止** | 不适用 |

### 2.2 判定树（依次问，命中即停）

```
Q1 该秘密是否由进程级密钥派生、且设计上要求「随进程存活」？
     └─ 是 → P（必须登记到 §4 的 P 类清单；禁止新增）
Q2 是否存在第二个持有者，能在本持有者释放之后**继续读取**该缓冲？
     └─ 是 → S（典型：data class 浅拷贝共享数组、copy-on-write 共享 ProtectedString、
              `KdbxDatabase.copy()` 复用同一 `binaries` 列表）
Q3 交出者是否**保留引用**并期望自己仍可继续使用（读或写）？
     └─ 是 → B（典型：KdbxAttachment 内存附件的 data 借用视图、
              InnerRandomStreamCipher 对 streamKey 的只读消费）
Q4 否则 → O
```

> **判定优先序的理由**：`S` 必须在 `B` 之前问。若先问 Q3，会把「双方都以为自己是所有者」
> 的浅拷贝误判成借用，从而**放弃擦除义务**；反过来若把 `B` 误判为 `O`，则会产生 §9.6 #2/#3
> 一类「擦掉别人正在用的字节」的事故。

### 2.3 P 类（进程级）的既有实例与边界

**唯一**既有实例及理由：`InMemoryCipher` 的进程密钥——`ProtectedString` 的驻留加密密钥
「读入即常驻、永不擦除、永不轮换」（`已知工程限界.md` §2.2）。其**必然性**在于：
`ProtectedString` 实例被多棵树共享（copy-on-write），换钥即静默数据破坏。

⇒ **不得**为「看起来更干净」而给进程密钥加擦除入口；**不得**把「持有进程密钥者可在读取瞬间
截获明文」当作未处理的缺陷重提（同一节已声明该边界）。

## 3. 规范性规则（R1 ~ R6）

> 本节是**可判定的**条款：每条都给出「违例形态」，供 §8 的机检面与代码评审引用。

### R1 — 就地擦除只对 O 类合法
**唯 O 类**允许 `fill(0)`。对 B 类的返回值、对 S 类的实例做就地清零**一律为违例**。

- 违例形态：`attachment.data.fill(0)`（B；内存附件的 `data` 是借用视图，
  `KdbxAttachment.kt:38-48`）；`oldRoot.clearSensitiveData()`（S；新树共享未修改子树引用，
  `KdbxGroup.kt:96-97` 明令禁止）。
- 正例：`KdbxAttachment.clear()`（`KdbxAttachment.kt:83-85`）只擦**本实例持有的** `inlineData`。

### R2 — 跨边界交付必须显式声明三种方式之一
交出缓冲时，必须（在 KDoc 与该方法的签名/命名上）声明为 **转移（transfer）/ 借用（borrow）/
复制（copy）** 之一；**默认是不转移**。

- **转移**：交出后本方**不得**再读、再擦（擦除责任随之转移）。落地形态：交出 `ownedSecrets`。
- **借用**：接收方只读且不驻留，**不得**擦除；KDoc 必须写「严禁修改或清零」。
- **复制**：接收方持独立副本、自负擦除责任；交出方保留自己的副本与责任。
- 违例形态：`return combined` 后又在 `finally` 中 `fill(combined)`（擦掉了返回值本身）——
  见 `SECURITY_RECHECK_2026-09.md` §9.6 #2 与 `CredentialIntermediateWipeTest` 的形状锁；
  正确形态是先 `copyOf()` 再擦原数组。

### R3 — O 类的擦除必须挂在**确定性钩子**上
允许的钩子只有四种：`Closeable.close()` / `use { }` / 会话终止三事件（锁定 / 换库 / 退出）/
函数 `finally`。**禁止**以「等 GC」作为擦除手段。

- 落地形态：流实例自持副本由 `close()` 擦（`CbcStreams.kt:184-195`；
  `CbcDecryptingInputStream.kt:49-58` 的契约说明）；会话级由 `DatabaseSession.lock()` /
  `close()` / 换库前置释放统一触发（`KdbxDatabase.kt:62-74`）。
- 违例形态：把缓冲存进字段、却没有任何一个钩子会遍历到它。

### R4 — 函数内局部 O 缓冲：`finally` 擦除 + 不得外泄
函数内创建的 O 缓冲必须在 `finally` 中擦除，且**不得** `return`、不得写入字段、
不得传给非「转移」接收者。

- 正例：`HmacBlockStream.kt:363-382`（末块明文切片写出后清零，满块则留给 `close()` 收口）；
  `ProtectedString.useChars` / `useUtf8`（`ProtectedString.kt:129-151`）——把「借出 + 擦回」
  封成一个作用域，调用方无法忘记。
- 违例形态：`val copy = x.copyOf(); use(copy); return`（无 `finally`）。

### R5 — 会话级 O 缓冲的擦除必须经**统一收口点**
会话级秘密（凭据、派生密钥、整树、附件字节）只能由**已登记的收口点**擦除，
不得由各组件各自 `fill`（否则必然出现「补一处、漏一处」）。

- 收口点清单见 §4；新增会话级秘密必须**同时**登记其收口点，否则视为未完成。
- 反面形态（已登记为限界，非本条违例）：散落在各解析/序列化路径的**函数内局部** O 缓冲，
  由 R4 约束，不经 R5。

### R6 — 豁免必须落在 §5 清单内
未被 §5 清单收录的数据**一律推定为秘密**，必须指定所有权类别与擦除责任。
新增豁免须在 §5 追加一行并给出「为何不由密文 / 公开信息推导」的理由。

## 6. `已知工程限界.md` §1.6「池内擦除解除条件」评估

**原解除条件**：`KdbxDatabase.copy()` 会共享同一 `binaries` 列表，池项擦除须先为
`InnerHeader.BinaryItem` 定义「谁拥有该数组」的所有权规则（对齐 `R-CLEAR-2` 所有权约定）。

### 6.1 按本契约对池的所有权判定

| 对象 | 类别 | 依据 |
|---|:--:|---|
| `BinaryItem.inlineData`（内存条目） | **O**（归 `BinaryItem` 实例） | 构造后不再外泄可变视图（`InnerHeader.kt:61-66` 的 `load()`/`data` 返回 `inlineData` 本身——但它是**同一实例的成员**，无第二个持有者） |
| 同一 `BinaryItem` 实例被多处可达时（`KdbxDatabase.copy()`、去重器交付、同步树复用） | **S** | 浅拷贝 / 列表复用使实例被多个逻辑所有者共享（§9.6 #19 同型） |
| `KdbxAttachment` 内存附件的 `data`（持 `inlineData` 者） | **B** | 借用视图，`KdbxAttachment.kt:38-48` 已就地声明 |
| 去重器交付的 `pooled.data.copyOf()` | **O**（归接收方） | 独立副本，别名隔离契约的代价（`已知工程限界.md` §1.7） |

### 6.2 评估结论

1. **规则文本前提已满足**：本契约给出了 `BinaryItem` 的类别判定（§6.1）与擦除责任归属，
   §1.6 所说的「先补齐所有权规则」**已可判定为完成**。
2. **但实施前提**（≠ 规则前提）**尚未满足**，故**本设计交付时不得实施池内擦除**：
   - 池的天然收口点是 `KdbxDatabase.clearSensitiveData()`，但该点被调用时**仍可能存在存活的
     别名持有者**——`SyncSessionState.lastSyncedDb`（`SyncSessionState.kt:38, 53-56`）与
     `SyncConflictController.clearPendingConflictSession()`（`SyncConflictController.kt:221-230`）
     当前**只置 null、不擦树**（§6/G2）。若此时就地擦 `inlineData`，会使仍在使用的树**静默拿到
     全零附件**——正是 §9.6 #3 的形态。
   - 即：**S 类实例的擦除必须以「确认再无存活别名」为前提**；本仓现有的正确做法是
     **身份集合判定**（`KdbxGroup.eraseSupersededSensitiveData`，`KdbxGroup.kt:102-140`），
     而非「随手 `clearSensitiveData()`」。
3. **⇒ 池内擦除的准入条件（两步，缺一不可）**：
   - **准入①**：G2 的别名持有者全部纳入会话终止三事件（属 `RC-05` 归口，须先闭环）；
   - **准入②**：池内擦除的实现必须走身份集合判定（「该 `BinaryItem` 实例在本会话是否仍可达」
     的判据），**不得**写成 `binaries.forEach { it.clear() }`。
4. **本条对 §1.6 的处置**：§1.6 的「解除条件」**文字层面已解除**，但「可实施」仍需准入①②；
   ⇒ 建议在 `已知工程限界.md` §1.6 就地补一句指针（指向本文件 §6.2），
   **使后续读者不再以「规则未定义」为由重复论证**。（该文档改动随迁移批次一并做，见 §7 Step 4。）

1. **覆盖矩阵**：§4 每个 O 类收口点必须至少有一条契约用例；不得再出现「有实现无契约」的收口点。
