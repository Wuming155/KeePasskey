## PD-01 建库 KDF 默认强度维持既定值，不接入设备自适应建议值

- **对应历史条目**：`ISSUE-P2-79` AC②（AC① / AC③ 的处置见文末「分流去向」）。
- **口径**：建库默认维持 **`Argon2id m=64 MiB / t=2 / p=2`**
  （`database/src/main/java/com/keepasskey/database/file/KdbxHeader.kt:166-170`），
  **不**在建库路径消费 `KdfBenchmark` 的设备自适应建议值。读取路径对既有库的工作因子照收、
  保存时逐字保留（仅刷新盐 / 种子，`KdbxFile.kt:332,337`）。
- **理由（降强面）**：`KdfBenchmark` 的建议值是**设备自适应**的，直接接入会出现**降强**，
  且**三项都可能弱于现默认**——内存下界 `MIN_ARGON2_MEMORY_BYTES = 8 MiB < 64 MiB`（`KdfBenchmark.kt:44`）、
  迭代可低至 `1 < 默认 2`（`:97`）、并行度为 `cores.coerceIn(1,4)` 故可为 `1 / 3 / 4 ≠ 默认 2`（`:91`）。
  ⇒ 须**逐参数**取 `max(建议值, 现默认)` 才不降强；而「逐参数 max」后已不再是设备自适应，
  且该做法**超出全部参考项目**，实施须自证与官方客户端的互操作。
- **参考对照（可作维持现状的反证）**：官方 C# / KeePassDX / KeePassXC **都有 1 秒级 benchmark**，
  DX 与 KXC 在**建库路径自动消费**。但 DX 的 `KdfEngine.kt:79-83,96-105` 把 memory / parallelism
  **覆盖后当结果返回**，是一条**主动降强**路径 ⇒ 参考项目的自动校准**确有降强缺陷**，不构成必须照抄的理由。
  另：官方**建库默认是 AES-KDF 600k 轮**（不是 Argon2），所谓「强度基线」在三家之间**不在同一坐标系**。
  弱参数**导入告警**只有官方 C# 做了（默认开启，判定后由用户 Yes/No），**且其判据只比 `I×M`、忽略并行度 P**，
  照抄会漏维度——该能力已转登为 `ISSUE-P2-87`。
- **前提核实**：2026-09-16 对 HEAD `2e5ce38` 复核，本条所依赖的默认值、消费方唯一性、削弱陷阱**全部成立**
  （见 [`records/存量条目前提复核记录.md`](../records/存量条目前提复核记录.md) ②）。
- **重开条件**：产品确认「目标强度口径」（如「设备实测约 1 秒」），并同时定义**逐参数** max 规则，
  且以官方客户端互操作对拍自证不降强（`AGENTS.md` §3.8 互操作证据纪律）。
- **依据**：`RESOLVED_LOG.md` §76 / §78；`docs/records/存量条目前提复核记录.md` ②。

## PD-02 同步端点默认拒绝内网 / 自建，且不提供终端用户可配置入口

- **对应历史条目**：`ISSUE-P3-121` AC①（AC③ 的处置见文末「分流去向」）。
- **口径**：`SyncNetworkOptions.ssrfAllowedHosts` **维持默认空集**
  （`sync/src/main/java/com/keepasskey/sync/network/SyncNetworkOptions.kt:25`），
  RFC1918 / 链路本地 / ULA / `localhost` / `.localhost` / `.local` / `.internal` 等主机
  **一律被 `SyncEndpointGuard` 拒绝**；**不给出厂可用口径，也不提供终端用户可配置入口**。
- **理由**：SSRF 纵深防御的**默认收紧**——放开等于给「同步端点被指向内网」留口子。
- **⚠️ 登记语义更正（2026-09-16 复核，本表以更正后语义登记）**：原裁决理由称
  「需要内网同步的用户**可经既有显式白名单机制自行配置**」——**不成立**。
  `ssrfAllowedHosts` 仅是 `sync` 模块的**库级构造参数**：**无 UI 入口、无持久化键
  （`SyncCredentialsStore.kt:299-318` 键枚举中无此项）、无 DI 装配点**，全仓**无任何生产写入点**，
  唯一非默认赋值在单测（`SyncEndpointGuardTest.kt:179`）；归档文档
  `docs/resolved/batches/86-DAL出口纵深防御批次.md:17` 亦自述该通道为「**预留**」。
  ⇒ 本条的真实语义是「**内网 / 自建同步对终端用户彻底不可用**」，**不是**「默认收紧但高级用户可自配」。
  两者在产品定位与 README 文案上导向不同结论，故必须按更正后语义引用。
- **参考对照（无口径可援引）**：5 家参考项目**无一家做 SSRF 防护**——keepass2android / Monica /
  官方 C# **地址一律放开**（kp2a 的 SMB / SFTP 输入提示直接写 `192.168.1.10`），安全靠「明文 http 开关 /
  证书三态 / 逐 host SHA-256 指纹 TOFU 弹窗」；KeePassXC 把端点**外包给用户自定义命令**。
  ⇒ 本仓默认收紧是**全场最严、属有意偏离主流**，**不得**以「参考项目都放开」为由要求放宽；
  反之，也**没有**外部口径可援引为「必须收紧」的依据——这是本仓自己的选择。
- **重开条件**：产品要求支持自建 / 内网同步时，须新增「**用户显式声明内网主机 + 风险二次确认**」
  设置入口（默认仍为拒绝），并把 `ssrfAllowedHosts` 从预留参数接成真实可配置项；
  Monica 的证书 TOFU 弹窗（`WebDavCertificateDialog.kt:26-40`）是最接近的现成形态。
  实施时须同时给出默认拒绝与审计留痕证据。
- **依据**：`docs/records/存量条目前提复核记录.md` ①；`docs/references/存量5项开放问题的参考项目对照.md`；
  `docs/resolved/batches/86-DAL出口纵深防御批次.md:17`。

## PD-03 封印（快速解锁）凭据不绑定库 header 摘要

- **对应历史条目**：`ISSUE-P2-47` AC②（AC① / AC③ 的处置见文末「分流去向」）。
- **口径**：封印载荷**不**绑定「库 header 摘要 / 封印序号」。快速解锁的失效判定维持现状，
  **不**按原 AC② 原文实施。
- **理由（原 AC② 按原文不可实施，代码取证非推测）**：`KdbxFile.kt:337` 保存时
  `p.copy(salt = freshSalt)`、`:342` `masterSeed = freshMasterSeed`——**KDF 盐与主种子每次保存都重新生成**，
  故任何形式的「库 header 摘要」**每次保存都会变**；照 AC② 原文绑定 header 摘要，结果是
  **每次保存后快速解锁立即失效**（核心功能回归）。另：封印载荷持有的是**主密码**，
  「回滚到旧主密码版本」的旧口令本就解不开当前库（原条文亦自认「价值有限」）；
  而「库与封印被**一致**回滚」属**同步防回滚链**的职责，封印侧无参照可比。
- **参考对照（属自有加固，不是照抄）**：5 家参考项目**全无文件级防回滚**——keepass2android 只有
  单个 `baseversion` 摘要，「远端变 + 本地未变」直接静默 `LoadDb` 重载；官方 C# 只有会话内哈希 +
  保存前三选一；KeePassDX 用**单向** `mtime + 10s`（回退根本不触发）；KeePassXC 零远端版本概念；
  Monica 是唯一有单调序号 + 上一步摘要的（`conflicting digest for segment N` → 持久化 `blockedReason`），
  但依赖自有段协议、只回看一步。
  ⇒ 本仓「已见摘要链」**强于全部参考项目**。**不得**把本条读作「参考项目都没做所以不必做」，
  也不得读作「照抄某家做法」——它是**自有加固的取舍**。
- **同步防回滚的边界与现状**（5 处引擎裁决点、`sequence` 不参与裁决、状态缺失 / MAC 失效 fail-open）
  **登记在 [`已知工程限界.md`](已知工程限界.md) §5**，不在本表重复。
- **重开条件**：若确认必须抗「封印与库被**一致**回滚」，应在**同步防回滚链**层解决；
  若确要保留封印侧绑定，须改设计为绑定「**库文件内容摘要**」并在每次保存后刷新，
  代价是刷新窗口内需回退主密码解锁——属架构决策，须先取得裁决再实施。
- **依据**：`docs/resolved/batches/83-内层XML-DTD拦截设备侧前置断言批次.md`；
  `docs/resolved/batches/90-防回滚引擎级回归补齐批次.md`；`docs/records/存量条目前提复核记录.md` ③。

## PD-04 不启用「分支保护必需状态检查」——供应链闸门取**「检测」**而非「阻断」

- **对应历史条目**：`ISSUE-P3-146`（承 `P2-54` 的 AC②「把 `OWASP Dependency-Check` 设为分支保护必需状态检查」）。
- **口径**：`main` **不设**分支保护规则，因而**不**把任何检查设为必需状态检查。供应链闸门维持**「检测」**语义——
  工作流照常在 `push{main}` 与 `pull_request` 上运行、CVSS ≥ 7.0 硬断言 **fail-closed**、SARIF 进 Code Scanning，
  但**不阻断**推送与合并。**`P2-54` 的 AC② 据此判为「有意不实施」**（而非「未闭环」）。
- **一手核实（2026-09-17，仓库所有者于 GitHub 设置页）**：`main` **无任何分支保护规则**（既无经典保护规则、
  亦无 rulesets）。**仓库为公开仓库** ⇒ 分支保护在**计划层是可用**的，故本口径**不是**受计划限制，
  而是**主动做出的取舍**（勿读作「做不到」）。
- **理由（按重要性排列）**：
  1. **单人仓库下，保护规则对唯一行为者几乎不起约束**：官方文档明写
     「By default, the restrictions of a branch protection rule **don't apply to people with admin permissions**」
     ——不勾「Do not allow bypassing the above settings」时，管理员（即唯一提交者）**不受约束**；
     勾上则连自己的紧急直推也会被挡。
  2. **要真「阻断」就必须引入 PR 流程，与本仓工作流冲突**：官方文档对「必需检查是否也约束**直推**」的措辞**含糊**
     （同一段里既有 "before collaborators can make changes to a protected branch"，也有 "After all required
     status checks pass, any commits must either be pushed to another branch and then merged **or pushed directly
     to the protected branch**"）；**唯一不含糊**的阻断机制是「Require a pull request before merging」——
     而它会使 `AGENTS.md` 规则 6.4 的「整改后**立即** `git commit & push` 到 main」**不再可行**，
     属**流程改造**而非加一个勾。
  3. **闸门的实质价值已由工作流本身获得**：「检测」层（fail-closed 扫描 + CVSS 硬断言 + SARIF 上传）
     已在位且**同时在 push 与 PR 上运行**；分支保护额外买到的仅是「阻断」，而在单人仓库上（见理由 1）这层额外收益经不起理由 2 的代价。
- **不得**据此断言「仓库未受保护即无供应链闸门」（闸门是工作流，不是保护规则）；
  也**不得**据此断言「已受保护」。
- **重开条件（任一成立即重新裁决）**：① 出现**第二个提交者**（保护规则开始真正约束他人）；
  ② 引入**发布流程 / 版本 tag** 的保护需求；③ 发生一次「坏提交直推 `main` 且造成实际损失」的事故；
  ④ 需要把 `build` 工作流变成**编译硬门禁**（而不仅是安全扫描）。
  **重开时的完整清单**（须**四项同批**处理，且**必须实测一次「PR 被挡下」**，否则只能写「已启用、未实测阻断」）：
  ① 勾「Require a pull request before merging」；② 勾「Do not allow bypassing the above settings」；
  ③ 勾「Require status checks」并选中 `OWASP Dependency-Check`（其 job 名在**全仓唯一**，
  不触发官方提醒的「同名检查导致结果歧义并卡住 PR」）；④ **同批修改 `AGENTS.md` §6.4** 的「立即直推 `main`」口径。
- **依据**：官方文档 [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
  （管理员默认可绕过；「Require status checks before merging」与「Require a pull request before merging」的差别；
  必需检查的 job 名唯一性要求；分支保护在公开仓库的可用性）；
  `RESOLVED_LOG.md` §112；`ISSUE-P3-146`；
  [`docs/security/退役审计承接-43-安全整改方案与附录.md`](../security/退役审计承接-43-安全整改方案与附录.md) 的 `C-10`
  （本条同时给出该行的答案：分支保护不存在 ⇒ `build` 未被要求通过，`F-05` 的爆炸半径**不因分支保护而收窄**）。

## PD-05 库锁定填充：解锁成功后**无条件**链入选择器——「唯一强匹配候选不直达」属待裁决取舍

- **对应发现**：2026-09-17「坏交互排查」（用户命题「本该一次点击就完成，却要点很多次，尤其密码填充」）。
  锁库状态下经 Autofill 通道填充：解锁成功后 `AutofillUnlockActivity.chainToPicker`
  （`app/.../autofill/AutofillUnlockActivity.kt:108-133`）**不看候选数量**，一律链入手动选择器
  `AutofillPickerActivity`（搜索 / 点选条目 → 有认证器时再过一次生物识别 → 回传真实 Dataset）。
- **交互成本**：站点 / 应用恰有 1 个严格匹配条目时，用户须完成「解锁（主密码或生物识别）→ 点条目 → 生物识别」；
  解锁页本身已是一次强认证，对刚输完主密码的用户，选择器内的生物识别是同一次填充意图里的**第二次认证**。
- **为什么是取舍而非缺陷**：选择器跳承担着数据集路径没有的安全职责——强制展示请求方归属
  （`ISSUE-P2-70`）+ 写入 `android://` 维度首次绑定（`ISSUE-P2-46`，未绑定调用方**唯一**的补救路径）+
  选中即显式授权（P2-24 语义）。若「唯一强匹配 + 调用方已完成首次绑定」时跳过选择器直达回传，
  等于把这三件事并入解锁页，安全面收窄须显式裁决，故**不登记为 ISSUE**。
- **候选方向（供裁决，均未实施）**：
  - **A. 维持现状**（每次解锁后进选择器）——最大安全面，交互成本最高；
  - **B. 直达回传**：「唯一强匹配 + 调用方已绑定授权」时解锁成功直接构造真实 Dataset 回传
    （解锁动作即确认）——一次认证，但归属展示与显式授权语义缺失；
  - **C. 链入确认页**：解锁成功后若存在唯一强匹配则改链 `AutofillConfirmActivity`
    （保留归属展示 + 单次生物识别 / 手动确认）——两次交互，安全职责基本保留。
- **裁决前口径**：**维持现状 A**；在取得裁决前不得改动 `chainToPicker` 的无条件链入语义，
  也不得在解锁页内自建数据集回传。
- **依据**：`AutofillUnlockActivity` / `AutofillPickerActivity` 源码通读（2026-09-17）；
  `resolved/batches/` 中 P2-86（解锁后链入选择器的真机结论）与 P2-70 / P2-46（选择器安全职责）相关批次。

## PD-06 密码学实现收敛到 Rust 一份内核库，**不引入** Botan 等第二套密码学栈

- **裁决**：对称密码与 KDF 全部由 `crypto/src/main/rust/`（RustCrypto 官方 crate）提供；
  **不引入** Botan / OpenSSL / libsodium 等第二套密码学实现。
- **理由**：
  1. **效率无收益**：Android 平台已提供硬件加速对称密码（Conscrypt/OpenSSL → ARMv8 `aese`）；
     Botan 在 Android 上用的是**同一批指令**，既不会更快，也不会比现有 Rust 内核（同走硬件后端）快。
  2. **可维护性净负**：会形成**两套密码学栈** + 第二条原生构建链（CMake/NDK × 4 ABI）+ 第二套 JNI 桥；
     KAT / 对拍 / 真机记录 / 契约用例等验证资产大部分需重做（Rust 侧资产无法迁移到 Botan）。
  3. **供应链纪律冲突**：项目已入库闸门要求依赖树**无重复密码学实现**（§145/§146 `cargo deny` 四项全 ok）；
     Botan 是**一整个密码学栈**（含 TLS / 证书 / PKCS#11 等本项目不需要的面），引入即冲突。
- **参考对照**：KeePassXC 用 Botan 的前提是「**桌面 C++/Qt 多平台**，需要一份库覆盖
  Windows/macOS/Linux」；本项目是**单平台 Android**，该前提不成立。KeePassDX / 官方 /
  keepass2android 均为**混合形态**（AES 走平台或自家原生，Twofish / ChaCha20 走 BC 纯 Java 或托管），
  其代价是真机可测的性能与语义漂移（BC ChaCha20 实测 **2.7~40.9 MB/s**，对比 Rust 生产路径 404 MB/s）。
- **如实说明（不构成反对理由）**：Botan 为 2-clause BSD，与主工程 GPL-3.0 单向兼容，**许可证不构成障碍**。
- **重开条件**：出现 **iOS / 桌面等非 Android 分发目标**，且要求「一份密码学实现跨全部平台」。
  **即便届时**，也应先评估把现有 Rust 内核交叉编译过去（KAT 与契约资产可整体带走），而非引入 Botan。

## PD-07 流式语义保留**两套**（原生自研骨架 + 兜底 JCA 流），以对拍用例锁定等价

- **裁决**：原生路径用自研 `CbcStreams`（`CbcEncryptingOutputStream` / `CbcDecryptingInputStream`，
  64 KiB 分块 + `Pkcs7`）；兜底路径用 JCA 的 `CipherInputStream` / `CipherOutputStream`。
  **两者并存、不互相改写**——这一点与 KeePassDX「全部塞进 JCA、流语义只有一套」**有意不同**。
- **理由（为什么值得留两套）**：
  1. **性能**：JCA `CipherInputStream` 内部固定 **512 B** 缓冲，真机把解密压到 **15.3 MB/s**；
     自研骨架 64 KiB 分块达 **55.5 MB/s**（3.6×，§144 实测）。若为「只有一套」而全走 JCA，
     等于**主动放弃**该收益。
  2. **安全**：自研骨架承担明文零化纪律与 `ownedSecrets` 契约（§147），能表达 JCA 流表达不了的擦除时点。
- **代价（如实）**：两套流语义必须保持可观测等价。本项目以**刻意对齐 + 逐例锁定**承担该成本：
  `CbcDecryptingInputStream` 的 KDoc 明确「错误语义以实测的 `javax.crypto.CipherInputStream` 基线为准」，
  并由 `CbcStreamFramingTest`（与真实 JCE 逐例对照）与 `CipherFallbackParityTest`
  （强制兜底 ↔ 原生产物逐字节一致）**双重锁定**。
- **不该读作**：不得据此认为「两套流语义是免费的」——它是**用维护成本换性能与擦除时点**的取舍；
  新增流式路径必须同时补两套的等价用例。
- **重开条件**：若将来把两套合一（统一到 JCA + 自持缓冲，或统一到自研骨架），须先证明
  **不损失**上述性能与擦除时点两条，并完整保留等价性用例。
- **依据**：§144 批次（`ISSUE-P3-155` 解密侧分块流）、§147 批次；
  `crypto/src/main/java/com/keepasskey/crypto/cipher/CbcStreams.kt` KDoc；`CbcStreamFramingTest` /
  `CipherFallbackParityTest`。

## PD-08 通行密钥二维码导入：载荷采用 **FIDO CXF v1.0 单凭据 Passkey JSON**，入口为「相机扫码 + 相册识码」

- **裁决**（2026-09-18，用户命题「扫码添加通行密钥（添加照片的方式）」）：
  1. **二维码载荷** = FIDO Alliance **Credential Exchange Format (CXF) v1.0**（Proposed Standard
     2025-08-14，errata 2026-03-09）的单凭据 `Passkey` 字典 JSON：`credentialId` / `userHandle` /
     `key` 为 Base64URL，`key` 为 **PKCS#8 ASN.1 DER** 的 Base64URL 编码。解析器兼容三级形态：
     裸 Passkey 对象 → CXF 凭据数组 → CXF 完整文档（`collections[].items[].credentials[]`），取首个有效凭据；
     并**兼容 KeePassXC `.passkey` 单对象 JSON**（`relyingParty` / `privateKey`（PEM 包裹 PKCS#8）等
     6 必需字段，`src/gui/passkeys/PasskeyImporter.cpp` 口径）——KeePassXC 是本项目 Passkey schema 裁决者。
  2. **入口** = 条目编辑页通行密钥区块的**双入口**：相机扫码（复用 `SecureCaptureActivity` 受保护取景）+
     相册照片识码（Photo Picker + zxing 本地解码，无需相机权限）。
  3. **落库口径**（**2026-09-18 §149 批次更正**）：解析结果写入条目 **`KPEX_PASSKEY_*`** 自定义字段
     （KeePassXC / KeePassDX 口径，细则见下文 **PD-09**；原表述为「写入 `Passkey.*`」，
     与本仓同日确立的互操作 schema 相冲突，故按 PD-09 更正），私钥走受保护字段
     CharArray 链路、逐算法还原为**与生成侧完全一致的驻留格式**（原为 hex / Base64 标量口径，
     现统一为 **PKCS#8 PEM**），复用既有保存路径；URL / 用户名留白时以 rpId / userName 补齐；
     条目已有通行密钥时整体替换（KDBX 历史快照可回滚）。**导出二维码不在本期范围**（另行裁决）。
- **理由**：
  1. WebAuthn 场景的二维码（hybrid transport / caBLE）是**临时会话握手**，业界**不存在**「扫码导入
     通行密钥」的传送标准——二维码只是个容器，载荷格式才是裁决点；
  2. CXF 是 FIDO 唯一 sanctioned 的凭据交换格式，Chrome / 1Password / Bitwarden / Dashlane 已采用，
     KeePassXC 2.7.7+ 的 passkey 导入导出同源（`gui/passkeys/PasskeyImporter`）；
  3. CXF `key` = PKCS#8 DER 与本项目 `PasskeyData`（PKCS#8 语义私钥文本 + `ProtectedString`）**天然对齐**，
     无需第二套密钥编解码。
- **重开条件**：FIDO 演进出二维码专用 CXF profile，或业界形成事实上的 QR 传送标准时重评载荷包装。
- **后续演进路线（2026-09-18 补记）**：Google 已发布 Credential Manager **凭据传输 API**
  （`androidx.credentials:providerevents`，API 26+，1.0.0-alpha06），官方明确以**同一 CXF 标准**
  支持 `ExportEntry`（导出器）/ `ImportCredentialsRequest`（导入器）的同设备对等传输——
  本裁决的 CXF 载荷与其同源；后续可另立裁决接入官方传输 API（届时扫码导入仍覆盖
  跨设备 / 照片来源场景，二者互补）。
- **依据**：[FIDO CXF v1.0 PS](https://fidoalliance.org/specs/cx/cxf-v1.0-ps-20250814.html)（§3.3.12
  Passkey Dictionary、errata 版 §3.3.12 `key` = PKCS#8）；[Android 凭据传输指南](https://developer.android.google.cn/identity/sign-in/credential-transfer)；
  KeePassXC `PasskeyImporter.cpp` / `PasskeyExporter.cpp` 源码定点核实（2026-09-18）；
  [`references/KeePassDX-架构分析.md`](../references/KeePassDX-架构分析.md) §3（`privateKeyPem`）/本项目 `crypto`/`PasskeyKeyCodec` 驻留格式与
  `PasskeyAssertionActivity.decodePrivateKeyBytes` 的消费口径（2026-09-18 源码通读）。

## PD-09 通行密钥落库 schema 采用 **KeePassXC / KeePassDX 的 `KPEX_PASSKEY_*` + PKCS#8 PEM**（写入口径）

- **口径**（2026-09-18，§149 批次）：
  1. 写入键名一律 `KPEX_PASSKEY_RELYING_PARTY` / `_USERNAME` / `_USER_HANDLE` / `_CREDENTIAL_ID` /
     `_PRIVATE_KEY_PEM` / `_FLAG_BE` / `_FLAG_BS`（`1` / `0`）/ `_PRF`；`CREDENTIAL_ID` / `USER_HANDLE` /
     私钥 / PRF 秘密为**受保护字段**（与 KeePassXC `EntryAttributes`、KeePassDX `PasskeyEntryFields` 逐项一致）；

     ——64 字符 hex → ES256、32 字节种子 → Ed25519，`ISSUE-P3-214`）。
- **更正（2026-09-21）**：本节边界原写「**未**用 `keepassxc-cli` / `pykeepass` / 真实 KeePassDX 端到端对拍」，

- **理由**：KeePassXC 是本项目 Passkey schema 裁决者（`AGENTS.md` §3）；KeePassDX 源码注释明写
  "field names from KeypassXC are used" ⇒ 三者共用同一 schema 才有**库文件级**互通；

- **重开条件**：KeePassXC / KeePassDX 变更 schema，或 FIDO 推出统一凭据存储规范。
- **边界（不得读作「互操作已验证」）**：本仓只提供**格式面**证据（编码 ↔ 解码往返、命名曲线 OID 断言），

## PD-10 通行密钥特权浏览器白名单：内置**仅已取证浏览器**，其余由用户**逐项显式启用**

- **口径**（2026-09-18，§149 批次）：
  1. 内置白名单**由已取证指纹表派生**（`BrowserSigningFingerprints.TRUSTED`：每条注明来源与核实方式），
     不再手抄字面量；
  2. 其它浏览器（Firefox 之外的 Brave / Edge / Samsung / Vivaldi…）由用户在「特权浏览器白名单」设置页**逐项启用**，
     指纹**现场读取该包自身签名证书的 SHA-256**（与系统校验同源，不臆写常量）；
  3. 列表仅呈现能处理 `https` VIEW 意图的应用（`queryIntentActivities`，**不需要** `QUERY_ALL_PACKAGES`）；
  4. 默认**空集**（除内置已取证项）。
- **安全语义（如实声明）**：启用某个应用等于允许它**以任意 web origin 发起凭据请求**——这正是浏览器委派的固有语义
  （CM 通道只在调用方的应用/签名命中白名单时才返回系统背书的 origin）。因此默认关闭、逐项授权、
  换签名或同包名顶替立即失效（fail-closed）；该能力**不得**被描述为「零风险」。
- **理由**：不做用户可配置则非 Chrome 浏览器上通行密钥**完全不出候选**（origin 退化为 `apk-key-hash`，
  与 `https://<rpId>` 绑定条目不匹配）——这是功能可用性与授权面之间的取舍，故交由用户显式决定。
- **重开条件**：CM 通道出现**不依赖白名单**的系统级中立 origin 授权面（如系统统一维护的浏览器清单）时，
  改为消费该系统面并收窄本口径。
- **依据**：§149 批次；`app/.../passkey/CallingOriginResolver.kt`、
  `app/.../data/repository/PasskeyPrivilegedBrowserStore.kt`、设置页 `PrivilegedBrowserSettingsScreen`。

## PD-12 凭据拒绝页至多提供一条**就地授权**的补救动作，唯一目标为加入特权浏览器白名单

- **口径**（2026-09-20，§227 批次，**由用户裁决**）：
  1. 凭据拒绝页（`CredentialRejectionScreen`）在拒绝原因**确有用户可执行的解法**时，在页面内呈现说明句
     与两个选择：主动作**「添加到特权名单」**、次动作**「退出」**；无从下手的原因（`CREDENTIAL_ALREADY_EXISTS`
     这类正常结果、`MISSING_REQUEST` / `INTERNAL_ERROR` 这类系统或内部异常）**维持原布局**（仅退出），不得硬凑入口；
  2. 唯一受支持的补救动作是**将调用方浏览器加入特权名单**。**不得**提供「跳过通行密钥站点归属校验」
     （`skipDalVerification`，即设置页该开关；`ISSUE-P2-240` 前的界面文案误写为「跳过浏览器兼容层」，
     已更正）一类使本次请求通过、或削弱 DAL 核心防线的直达路径——
     把关闭防线做成一步操作，等于给出绕过「任意应用冒充任意域名注册 Passkey」防线的捷径；
  3. 动作**全程在当前受保护窗口内就地完成，不跳转任何其它界面**，彻底消除跨 Activity 路由传递带来的
     DoS 面与未解锁绕过风险；
  4. **严格的资格守卫（fail-closed）**：调用方必须是系统背书的包名、且必须是已安装的浏览器候选
     （能处理 https VIEW 且现场可读签名证书）——**原生 App 一律不呈现该动作**（原生 App 无论加不加白名单
     都无法通过 DAL，给它这个入口就是误导用户）；已在名单里的浏览器亦不呈现；
  5. **本次请求仍然必然失败**：即使用户点了「添加到特权名单」且授权成功，本次创建的 origin
     在拉起时早已被系统解析为 `apk-key-hash`，无法中途变更为 web origin。授权成功后页面就地提示
     「已添加，请回到浏览器重新发起创建」，收尾仍回传 `RESULT_CANCELED`。它改变的是**下一次**发起。
- **理由（为什么这与既有纪律完全自洽）**：
  1. 完全遵守「凭据窗口不提供本应用内导航」的既有取向（`CredentialUnlockPresenter` 等三处 no-op）——
     **没有跳转任何应用内界面**，窗口级 `FLAG_SECURE` 与反悬浮窗加固全程闭环覆盖；
  2. 它也不构成 §226 所否定的「让本次请求通过的第二条出路」：本次被拒请求**仍然必然失败**，
     对系统契约依然是 `RESULT_CANCELED`，授权只作用于下一次发起；
  3. 相比「跳转设置页」方案，就地授权免去了用户跳去设置、找入口、找应用、再切换回浏览器的多步操作，
     直接减少了跳转与操作成本（用户命题原文「减少跳转和操作」）。
- **边界（不得据本条外推）**：
  1. 仅覆盖**调用方确为浏览器**的 DAL 门禁拒绝；不得据此为原生 App 提供任何绕过 DAL 校验的入口；
  2. 不得据本条把「用户授权」做成「让本次请求通过」——任何影响**本次**请求结果的入口
     （重试、跳过校验、降级）都不在本条授权范围内；
  3. 「至多一条」是硬上限：出现第二种补救动作时须重裁（见重开条件），不得直接追加按钮。
- **重开条件**：系统 Credential Manager 提供运行时动态刷新 origin 的中立能力（使本次请求可原地生效）时，
  重新裁决是否允许就地重试。
- **依据**：§227 批次；`app/.../passkey/CredentialRejectionAction.kt`、

## PD-13 完整性风险升级**不**触发活动会话熔断：以「提示 + 后续通道门控」为准（**2026-09-20 已裁决 · 方向 A**）

  生物识别快速解锁门控、自动填充 / CM 通道门控），**不**新增 `COMPROMISED → triggerLock` /
  `clearSensitiveData` 接线。
- **裁决理由（含一处对原「误伤形态」登记的关键补正）**：
  1. **`COMPROMISED` 的构成不支持「熔断」这一处置粒度**。`RuntimeIntegrityPolicy.evaluate` 的分档依据

     Superuser 路径）、`magiskDetected`（6 条 Magisk 痕迹路径）、`hookFrameworkDetected` 的**落点层**

     但未运行**的设备，会在解锁后 **≤30 s**（`LIVE_RESCAN_INTERVAL_MS`）被强制锁库；本仓**无草稿自动保存**，
     未保存的条目编辑即丢失，且每次解锁都复发 ⇒ 本应用对这类设备**实质不可用**。
     原登记只写出了 frida 落点这一面，**遗漏了 root / Magisk 这一更广的同性质面**——

     （2026-09-20，核实方式：直读两函数全文 + `IntegritySignals` 字段构成）。

     「**持续附着**」型对手，对首次 dump 无覆盖；它缩短的是暴露窗口，不是阻止已发生的读取。
  3. **既有门控已覆盖「后续通道」**。四条消费点均 fail-closed：攻击者被探测到后拿不到新解封的主密码、

     已按残余风险登记于 [`已知工程限界.md`](已知工程限界.md) §26。

  2. `beingTraced` 进入**周期重扫快照**（当前 `detectSignals()` 不采该信号，仅非 suspend 门控经
     `escalateForLiveSignals` 实时求值）——否则被动熔断看不到「持续附着」；

  [`246-移除密码库确认文案与真实行为一致批次.md`](../resolved/batches/246-移除密码库确认文案与真实行为一致批次.md)）。
- **口径**：
  1. **应用私有目录（`filesDir`）内的库**：移除动作 = **永久删除该文件**，删除后不可恢复；
     确认弹窗按此**照实**表述（红色危险按钮 + 正文指名被删文件 + 明示不可恢复），
     **不改**成「只移除关联」；
  2. **外部来源的库**（`content://` / 应用外路径）：维持「仅摘除本机登记、不动物理文件」，
     文案与按钮与上面那套**三处措辞全不相同**；
  3. 两类的判定为纯函数 `VaultRemovalKind.of(条目 path, filesDir)`（无 I/O），
     文案与动作由同一枚判据投影，且**同一枚判据**下行给数据层决定是否真删文件。
- **理由（技术事实，非偏好）**：
  1. **私有库不存在「只移除关联」这个状态**：列表由 `VaultDatabaseCatalog.buildDatabaseList`
     **按目录扫描** `filesDir/*.kdbx` 构建，判定只认文件本身、登记表里没有内部库的条目 ⇒
     若「移除」不删文件，该卡片在**下一次刷新必然原样回来**——那不是「移除」，而是「按了没反应」；
  2. 走「不删文件」就必须新增一层「已忽略文件」持久化与扫描差集逻辑，且默认动作变成**静默无效**
     （用户以为移除了、实际只是被隐藏）；破坏性动作并未消失，只是被挪到第二层入口，
     却新增了一条「看起来成功其实没动」的默认路径；
  3. 本条目的根因是**「界面说的和实际做的不一样」**，不是「删了文件」——对私有库而言删除是让它
     从列表消失的唯一动作，故正确处置是照实说，而不是把动作改成不生效。
- **不得外推的边界**：
  1. 本条**不**授权对私有库以外的对象做任何删除（外部库的移除一行文件操作都不做）；
  2. 本条**不**改变删除动作的**判定方向**：`kind` 与 `id` 不一致时最坏结果是「该删的没删」，
     **绝不允许**出现「不该删的删了」；
  3. 本条**不**把 `<库>.kdbx.bak`（`AtomicFileWriter` 滚动备份、属用户数据）纳入删除或保护承诺——
     它**不随删除移除**且应用内无入口读回，故**不得**在界面文案里把它写成恢复路径。
- **重开条件**：产品要求「私有库也必须可无痕下架」（即提供一层「已忽略库」持久化使其从列表隐藏、
  文件保留）时，须**先落地该层状态与其差集语义**，并把默认动作明确为「不删文件」，
  再另行裁决「删除文件」入口的位置与二次确认强度；届时须同批更新本条与批次 §4 的结论。
