## PD-01 建库 KDF 默认强度维持既定值，不接入设备自适应建议值

- **对应历史条目**：`ISSUE-P2-79` AC②（AC① / AC③ 的处置见文末「分流去向」）。
- **口径**：建库默认维持 **`Argon2id m=64 MiB / t=2 / p=2`**
  （`database/src/main/java/com/keepasskey/database/file/KdbxHeader.kt:166-170`），
  **不**在建库路径消费 `KdfBenchmark` 的设备自适应建议值。读取路径对既有库的工作因子照收、
  保存时逐字保留（仅刷新盐 / 种子，`KdbxFile.kt:332,337`）。
- **理由（降强面）**：`KdfBenchmark` 的建议值是**设备自适应**的，直接接入会出现**降强**，
  且**三项都可能弱于现默认**——内存下界 `MIN_ARGON2_MEMORY_BYTES = 8 MiB < 64 MiB`（`KdfBenchmark.kt:44`）、
  迭代可低至 `1 < 默认 2`（`:97`）、并行度为 `cores.coerceIn(1,4)` 故可为 `1 / 3 / 4 ≠ 默认 2`（`:91`）。
  ⇒ 须**逐参数**取 `max(建议值, 现默认)` 才不降强；而「逐参数 max」后已不再是设备自适应，
  且该做法**超出全部参考项目**，实施须自证与官方客户端的互操作。
- **参考对照（可作维持现状的反证）**：官方 C# / KeePassDX / KeePassXC **都有 1 秒级 benchmark**，
  DX 与 KXC 在**建库路径自动消费**。但 DX 的 `KdfEngine.kt:79-83,96-105` 把 memory / parallelism
  **覆盖后当结果返回**，是一条**主动降强**路径 ⇒ 参考项目的自动校准**确有降强缺陷**，不构成必须照抄的理由。
  另：官方**建库默认是 AES-KDF 600k 轮**（不是 Argon2），所谓「强度基线」在三家之间**不在同一坐标系**。
  弱参数**导入告警**只有官方 C# 做了（默认开启，判定后由用户 Yes/No），**且其判据只比 `I×M`、忽略并行度 P**，
  照抄会漏维度——该能力已转登为 `ISSUE-P2-87`。
- **前提核实**：2026-09-16 对 HEAD `2e5ce38` 复核，本条所依赖的默认值、消费方唯一性、削弱陷阱**全部成立**
  （见 [`records/存量条目前提复核记录.md`](../records/存量条目前提复核记录.md) ②）。
- **重开条件**：产品确认「目标强度口径」（如「设备实测约 1 秒」），并同时定义**逐参数** max 规则，
  且以官方客户端互操作对拍自证不降强（遵守根目录 AGENTS.md 的 KDBX 互操作证据纪律）。
- **依据**：`RESOLVED_LOG.md` §76 / §78；`docs/records/存量条目前提复核记录.md` ②。

## PD-02 同步端点仅 HTTPS（明文全拒）；自建内网 HTTPS 端点默认可用，连接期守卫拦非预期内网到达

- **对应历史条目**：`ISSUE-P3-121` AC①（AC③ 的处置见文末「分流去向」）；
  **2026-10-01 `ISSUE-P2-425` 推翻 2026-09-16 的「默认拒绝内网」旧口径**（用户裁决：
  「只要是加密协议的就可以，明文传输的全部拒绝」），本条按新口径登记。
- **口径**：
  - **明文全拒**：同步端点仅接受 HTTPS——明文 `http://` 在构造期即抛
    `SyncException.InvalidEndpointError`，且 `SyncHttpClientFactory` 恒 TLS-only +
    平台 Network Security Config 双层强制；
  - **自建内网 HTTPS 端点默认可用**：用户**显式配置**的 RFC1918 / ULA / 链路本地（非元数据）/
    `localhost` / `.local` / `.internal` 端点不再被构造期拒绝（自托管 NAS / MinIO / Nextcloud
    开箱即用）；其连接期可达性由 `SyncHttpClientFactory` 把已配置端点主机登记进豁免
    （主机名经 Dns 豁免、IP 字面量经预登记——OkHttp 对字面量短路不经 Dns）；
  - **云元数据红线**：`169.254.0.0/16`（含 `169.254.169.254`）任何形态、任何路径
    （配置端点 / 豁免主机解析结果 / 重定向目标）一律不放行；
  - **连接期守卫不变**：重定向 / DNS 重绑定跳到的**非预期**内网地址仍被
    `SsrfGuardDns` / `SsrfGuardSocketFactory` 在 TCP 建立前拦截；
  - `SyncNetworkOptions.ssrfAllowedHosts` 维持默认空集，降格为**高级逃生通道**
    （合法重定向落到自建内网等边缘情形）；
  - **信任锚恒为系统 CA（2026-10-01 用户重申定版）**：**不引入**用户 CA 信任、自签证书
    TOFU 指纹放行或参考项目那类「证书三态」开关——自建端点持受信 CA 证书（如 ACME
    DNS-01 签发）是用户侧的部署义务，产品侧不给任何放行面（一旦信任用户证书，受信
    证书下载的恶意 App / 中间人面即失守，代价远大于省一次证书签发）。
- **理由**：SSRF 真正的纵深防御在**连接期**（拦「非用户意图」的内网到达），与「用户显式配置
  哪个端点」是两件事；把合法的加密自建目标与恶意内网重定向同等待遇，只会伤害自托管用户而
  不增益安全（DNS 重绑定本就由连接期解析地址复核兜底）。
- **历史登记存照（2026-09-16 旧口径，已被推翻，仅留档防复用）**：旧口径为「默认拒绝内网 / 自建，
  不提供终端用户可配置入口」——当时复核确认 `ssrfAllowedHosts` 无 UI / 无持久化键 / 无 DI 装配点
  （全仓零生产写入点），真实语义是「内网 / 自建同步对终端用户彻底不可用」。推翻依据与实施见
  `ISSUE-P2-425` 批次文档。
- **参考对照（无口径可援引）**：5 家参考项目**无一家做 SSRF 防护**——keepass2android / Monica /
  官方 C# **地址一律放开**（kp2a 的 SMB / SFTP 输入提示直接写 `192.168.1.10`），安全靠「明文 http 开关 /
  证书三态 / 逐 host SHA-256 指纹 TOFU 弹窗」；KeePassXC 把端点**外包给用户自定义命令**。
  ⇒ 新口径（加密即可 + 连接期纵深）与参考项目的差异收敛为「全站强制 TLS + 连接期守卫」两点。
- **重开条件**：若产品要求重新收紧，只可走「用户显式声明内网主机 + 风险二次确认」的设置入口形态
  （Monica 的证书 TOFU 弹窗 `WebDavCertificateDialog.kt:26-40` 是最接近的现成形态），
  不得静默回退构造期拦截。
- **依据**：`docs/records/存量条目前提复核记录.md` ①；`docs/references/存量5项开放问题的参考项目对照.md`；
  `docs/resolved/batches/86-DAL出口纵深防御批次.md:17`；`ISSUE-P2-425` 批次文档。

## PD-03 封印（快速解锁）凭据不绑定库 header 摘要

- **对应历史条目**：`ISSUE-P2-47` AC②（AC① / AC③ 的处置见文末「分流去向」）。
- **口径**：封印载荷**不**绑定「库 header 摘要 / 封印序号」。快速解锁的失效判定维持现状，
  **不**按原 AC② 原文实施。
- **理由（原 AC② 按原文不可实施，代码取证非推测）**：`KdbxFile.kt:337` 保存时
  `p.copy(salt = freshSalt)`、`:342` `masterSeed = freshMasterSeed`——**KDF 盐与主种子每次保存都重新生成**，
  故任何形式的「库 header 摘要」**每次保存都会变**；照 AC② 原文绑定 header 摘要，结果是
  **每次保存后快速解锁立即失效**（核心功能回归）。另：封印载荷持有的是**主密码**，
  「回滚到旧主密码版本」的旧口令本就解不开当前库（原条文亦自认「价值有限」）；
  而「库与封印被**一致**回滚」属**同步防回滚链**的职责，封印侧无参照可比。
- **参考对照（属自有加固，不是照抄）**：5 家参考项目**全无文件级防回滚**——keepass2android 只有
  单个 `baseversion` 摘要，「远端变 + 本地未变」直接静默 `LoadDb` 重载；官方 C# 只有会话内哈希 +
  保存前三选一；KeePassDX 用**单向** `mtime + 10s`（回退根本不触发）；KeePassXC 零远端版本概念；
  Monica 是唯一有单调序号 + 上一步摘要的（`conflicting digest for segment N` → 持久化 `blockedReason`），
  但依赖自有段协议、只回看一步。
  ⇒ 本仓「已见摘要链」**强于全部参考项目**。**不得**把本条读作「参考项目都没做所以不必做」，
  也不得读作「照抄某家做法」——它是**自有加固的取舍**。
- **同步防回滚的边界与现状**（5 处引擎裁决点、`sequence` 不参与裁决、状态缺失 / MAC 失效 fail-open）
  **登记在 [`已知工程限界.md`](已知工程限界.md) §5**，不在本表重复。
- **重开条件**：若确认必须抗「封印与库被**一致**回滚」，应在**同步防回滚链**层解决；
  若确要保留封印侧绑定，须改设计为绑定「**库文件内容摘要**」并在每次保存后刷新，
  代价是刷新窗口内需回退主密码解锁——属架构决策，须先取得裁决再实施。
- **依据**：`docs/resolved/batches/83-内层XML-DTD拦截设备侧前置断言批次.md`；
  `docs/resolved/batches/90-防回滚引擎级回归补齐批次.md`；`docs/records/存量条目前提复核记录.md` ③。

## PD-04 不启用「分支保护必需状态检查」——供应链闸门取**「检测」**而非「阻断」

- **对应历史条目**：`ISSUE-P3-146`（承 `P2-54` 的 AC②「把 `OWASP Dependency-Check` 设为分支保护必需状态检查」）。
- **口径**：`main` **不设**分支保护规则，因而**不**把任何检查设为必需状态检查。供应链闸门维持**「检测」**语义——
  工作流以 `schedule` + `workflow_dispatch` 运行（`ISSUE-P3-316` 起为现状，见下方**补记**；
  原文「照常在 `push{main}` 与 `pull_request` 上运行」自 2026-09-25 起已失真并已更正）、
  CVSS ≥ 7.0 硬断言 **fail-closed**、SARIF 进 Code Scanning，但**不阻断**推送与合并。
  **`P2-54` 的 AC② 据此判为「有意不实施」**（而非「未闭环」）。
- **一手核实（2026-09-17，仓库所有者于 GitHub 设置页）**：`main` **无任何分支保护规则**（既无经典保护规则、
  亦无 rulesets）。**仓库为公开仓库** ⇒ 分支保护在**计划层是可用**的，故本口径**不是**受计划限制，
  而是**主动做出的取舍**（勿读作「做不到」）。
- **理由（按重要性排列）**：
  1. **单人仓库下，保护规则对唯一行为者几乎不起约束**：官方文档明写
     「By default, the restrictions of a branch protection rule **don't apply to people with admin permissions**」
     ——不勾「Do not allow bypassing the above settings」时，管理员（即唯一提交者）**不受约束**；
     勾上则连自己的紧急直推也会被挡。
  2. **要真「阻断」就必须引入 PR 流程，与本仓工作流冲突**：官方文档对「必需检查是否也约束**直推**」的措辞**含糊**
     （同一段里既有 "before collaborators can make changes to a protected branch"，也有 "After all required
     status checks pass, any commits must either be pushed to another branch and then merged **or pushed directly
     to the protected branch**"）；**唯一不含糊**的阻断机制是「Require a pull request before merging」——
     而它会使 `AGENTS.md` 规则 6.4 的「整改后**立即** `git commit & push` 到 main」**不再可行**，
     属**流程改造**而非加一个勾。
  3. **闸门的实质价值已由工作流本身获得**：「检测」层（fail-closed 扫描 + CVSS 硬断言 + SARIF 上传）已在位；
     分支保护额外买到的仅是「阻断」，而在单人仓库上（见理由 1）这层额外收益经不起理由 2 的代价。
     **注意（`ISSUE-P3-316` 后）**：「检测」**已不再是 push / PR 即时运行**——三个 workflow 现为**定时 / 手动**触发
     （原文「已在位且同时在 push 与 PR 上运行」已失真并已更正），理由 3 原以「闸门即时运行」为前提，
     该前提自 2026-09-25 起**已不成立**；随之产生的残余风险见下方**补记**。
- **补记（2026-10-11，`ISSUE-P3-586`）**：
  - **触发面现状**：本条登记于 2026-09-17，**8 天后**（2026-09-25）的 `ISSUE-P3-316`（触发频率治理：
    原 `push{main}` + `pull_request` 全量触发在 5 天产生 126 次 run）把三个 workflow **全部改为
    `schedule` + `workflow_dispatch`**——[`build.yml`](../../.github/workflows/build.yml):36-43（每日 UTC 21:00 全量巡检）、
    [`codeql.yml`](../../.github/workflows/codeql.yml):31-36（每周一次兜底巡检）、
    [`dependency-scan.yml`](../../.github/workflows/dependency-scan.yml):27-31（每周一全量扫描）。
    故本条原两处「照常在 `push{main}` 与 `pull_request` 上运行」（`口径`）与「已在位且同时在 push 与 PR 上运行」（理由 3）
    **与本状态不符**，已按上述现状逐处更正（**实质结论未变**：供应链闸门取「检测」而非「阻断」、不启用分支保护、
    `P2-54` 的 AC② 判为「有意不实施」）。
  - **随之产生的残余风险（本条显式登记）**：合并进 `main` 的内容**在合并前无任何 GitHub Actions 自动检测**
    （唯一检测是人工 review）；合并后为**延迟巡检**——`build` 最长约 **24h**（每日一次）才可能揭出坏提交，
    `dependency-scan` 与 `CodeQL` 最长约 **7 天**（每周一次）。⇒ 本条的「检测」语义只保证「**最终会被巡检**」，
    **不再保证**「合并前 / 合并后即时的自动检测」；「闸门即时运行」不再是本条的支撑面。
    在「所有者只审 diff 即合并外部 PR」的场景下，本地门禁（`gradlew test` + `gate_readings.py`）**无自动强制力**。
  - **不重复登记**：该残余的**检测面**（含「合并前零 CI 自动检测」与「三个 workflow yml 自身及触发面未纳入门禁脚本基线」）
    已由 [`已知工程限界.md`](已知工程限界.md) **§42** 承载（`ISSUE-P2-574`，§489）——本表只登记**登记漂移**这一根因，
    残余指向该 §，不在两表重复。**两 fix 汇合于同一动作**（恢复合并前检测 / 承载残余），但**根因不同，不合并**。
  - **重开条件补充**：除原重开条件④「需要把 `build` 工作流变成编译硬门禁」外，若**恢复无 secrets 轻量 job 的
    `pull_request` 触发**（`ISSUE-P3-316` 属**产品级取舍**，须另行裁决并登记），本条即按新的触发面重新评估。
- **不得**据此断言「仓库未受保护即无供应链闸门」（闸门是工作流，不是保护规则）；
  也**不得**据此断言「已受保护」。
- **重开条件（任一成立即重新裁决）**：① 出现**第二个提交者**（保护规则开始真正约束他人）；
  ② 引入**发布流程 / 版本 tag** 的保护需求；③ 发生一次「坏提交直推 `main` 且造成实际损失」的事故；
  ④ 需要把 `build` 工作流变成**编译硬门禁**（而不仅是安全扫描）。
  **重开时的完整清单**（须**四项同批**处理，且**必须实测一次「PR 被挡下」**，否则只能写「已启用、未实测阻断」）：
  ① 勾「Require a pull request before merging」；② 勾「Do not allow bypassing the above settings」；
  ③ 勾「Require status checks」并选中 `OWASP Dependency-Check`（其 job 名在**全仓唯一**，
  不触发官方提醒的「同名检查导致结果歧义并卡住 PR」）；④ **同批修改 `AGENTS.md` §6.4** 的「立即直推 `main`」口径。
- **依据**：官方文档 [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
  （管理员默认可绕过；「Require status checks before merging」与「Require a pull request before merging」的差别；
  必需检查的 job 名唯一性要求；分支保护在公开仓库的可用性）；
  `RESOLVED_LOG.md` §112；`ISSUE-P3-146`；
  [`docs/security/退役审计承接-43-安全整改方案与附录.md`](../security/退役审计承接-43-安全整改方案与附录.md) 的 `C-10`

  `AutofillCandidateRanker.MatchReason` 既有 exact 语义）；`AutofillUnlockActivity.chainToPicker`
  按其结论路由，`PICKER` 分支逐字保持旧构造，`CONFIRM` 分支携带确认页既有 extras 启动
  `AutofillConfirmActivity`，两条链的结果均经解锁页既有 launcher **原样转发**（`RESULT_OK + data`
  转发、取消 `RESULT_CANCELED + Bundle.EMPTY`）。解锁页**不自建 Dataset**（对候选 B 的禁令精神延续：
  数据集构造与回传只在落地页）。**本条已于 §261 批次闭环。**
- **跟踪沿革**：裁决作出前，本条的待裁决状态曾登记为 [`../ACTIVE_ISSUES.md`](../ACTIVE_ISSUES.md)
  `ISSUE-P3-256`（§260 补登；彼时本表只承载候选与裁决前口径）；裁决作出后随 §261 批次闭环归档，
  跟踪入口收口于本表。
- **对应发现**：2026-09-17「坏交互排查」（用户命题「本该一次点击就完成，却要点很多次，尤其密码填充」）。
  锁库状态下经 Autofill 通道填充：解锁成功后 `AutofillUnlockActivity.chainToPicker`
  （`app/.../autofill/AutofillUnlockActivity.kt`）**不看候选数量**，一律链入手动选择器
  `AutofillPickerActivity`（搜索 / 点选条目 → 有认证器时再过一次生物识别 → 回传真实 Dataset）。
- **交互成本**：站点 / 应用恰有 1 个严格匹配条目时，用户须完成「解锁（主密码或生物识别）→ 点条目 → 生物识别」；
  解锁页本身已是一次强认证，对刚输完主密码的用户，选择器内的生物识别是同一次填充意图里的**第二次认证**。
- **为什么是取舍而非缺陷**：选择器跳承担着数据集路径没有的安全职责——强制展示请求方归属
  （`ISSUE-P2-70`）+ 写入 `android://` 维度首次绑定（`ISSUE-P2-46`，未绑定调用方**唯一**的补救路径）+
  选中即显式授权（P2-24 语义）。若「唯一强匹配 + 调用方已完成首次绑定」时跳过选择器直达回传，
  等于把这三件事并入解锁页，安全面收窄须显式裁决，故**不登记为 ISSUE**。
- **原三候选（沿革，裁决日 2026-09-22 前的登记原文，均未实施）**：
  - **A. 维持现状**（每次解锁后进选择器）——最大安全面，交互成本最高；
  - **B. 直达回传**：「唯一强匹配 + 调用方已绑定授权」时解锁成功直接构造真实 Dataset 回传
    （解锁动作即确认）——一次认证，但归属展示与显式授权语义缺失；
  - **C. 链入确认页**：解锁成功后若存在唯一强匹配则改链 `AutofillConfirmActivity`
    （保留归属展示 + 单次生物识别 / 手动确认）——两次交互，安全职责基本保留。**← 本裁决所取**
- **历史沿革（原「裁决前口径」，已随 2026-09-22 裁决失效）**：裁决前维持现状 A，`chainToPicker`
  冻结不得改动、也不得在解锁页内自建数据集回传；裁决作出后该冻结解除，按候选 C 实施
  （「解锁页不自建数据集回传」的精神作为 C 的实施约束保留）。
- **重开条件**：
  - 用户改判要求「单次交互直达」（解锁即回传、免确认页）⇒ 重评候选 B 及其安全面收窄
    （归属展示、`android://` 首次绑定补救、选中显式授权三项职责的去向须逐项显式处置）；
  - 系统填充协议变化（认证结果回传 / 链式启动契约变更，例如框架不再接受经解锁页跨 Activity
    转发的 `EXTRA_AUTHENTICATION_RESULT`）⇒ 重评本路由与两条交付链。
- **依据**：`AutofillUnlockActivity` / `AutofillPickerActivity` 源码通读（2026-09-17）；

## PD-06 密码学实现收敛到 Rust 一份内核库，**不引入** Botan 等第二套密码学栈

- **裁决**：对称密码与 KDF 全部由 `crypto/src/main/rust/`（RustCrypto 官方 crate）提供；
  **不引入** Botan / OpenSSL / libsodium 等第二套密码学实现。
- **理由**：
  1. **效率无收益**：Android 平台已提供硬件加速对称密码（Conscrypt/OpenSSL → ARMv8 `aese`）；
     Botan 在 Android 上用的是**同一批指令**，既不会更快，也不会比现有 Rust 内核（同走硬件后端）快。
  2. **可维护性净负**：会形成**两套密码学栈** + 第二条原生构建链（CMake/NDK × 4 ABI）+ 第二套 JNI 桥；
     KAT / 对拍 / 真机记录 / 契约用例等验证资产大部分需重做（Rust 侧资产无法迁移到 Botan）。
  3. **供应链纪律冲突**：项目已入库闸门要求依赖树**无重复密码学实现**（§145/§146 `cargo deny` 四项全 ok）；
     Botan 是**一整个密码学栈**（含 TLS / 证书 / PKCS#11 等本项目不需要的面），引入即冲突。
- **参考对照**：KeePassXC 用 Botan 的前提是「**桌面 C++/Qt 多平台**，需要一份库覆盖
  Windows/macOS/Linux」；本项目是**单平台 Android**，该前提不成立。KeePassDX / 官方 /
  keepass2android 均为**混合形态**（AES 走平台或自家原生，Twofish / ChaCha20 走 BC 纯 Java 或托管），
  其代价是真机可测的性能与语义漂移（BC ChaCha20 实测 **2.7~40.9 MB/s**，对比 Rust 生产路径 404 MB/s）。
- **如实说明（不构成反对理由）**：Botan 为 2-clause BSD，与主工程 GPL-3.0 单向兼容，**许可证不构成障碍**。
- **重开条件**：出现 **iOS / 桌面等非 Android 分发目标**，且要求「一份密码学实现跨全部平台」。
  **即便届时**，也应先评估把现有 Rust 内核交叉编译过去（KAT 与契约资产可整体带走），而非引入 Botan。
- **依据**：参考对照 [`references/KeePassXC-架构分析.md`](../references/KeePassXC-架构分析.md) /
  [`KeePassDX-架构分析.md`](../references/KeePassDX-架构分析.md) §4.2 /
  [`KeePass-2.61.1-架构分析.md`](../references/KeePass-2.61.1-架构分析.md)；
  实测 [`records/真机吞吐实测记录_2026-09-17.md`](../records/真机吞吐实测记录_2026-09-17.md) §8。

## PD-07 流式语义保留**两套**（原生自研骨架 + 兜底 JCA 流），以对拍用例锁定等价

- **裁决**：原生路径用自研 `CbcStreams`（`CbcEncryptingOutputStream` / `CbcDecryptingInputStream`，
  64 KiB 分块 + `Pkcs7`）；兜底路径用 JCA 的 `CipherInputStream` / `CipherOutputStream`。
  **两者并存、不互相改写**——这一点与 KeePassDX「全部塞进 JCA、流语义只有一套」**有意不同**。
- **理由（为什么值得留两套）**：
  1. **性能**：JCA `CipherInputStream` 内部固定 **512 B** 缓冲，真机把解密压到 **15.3 MB/s**；
     自研骨架 64 KiB 分块达 **55.5 MB/s**（3.6×，§144 实测）。若为「只有一套」而全走 JCA，
     等于**主动放弃**该收益。
  2. **安全**：自研骨架承担明文零化纪律与 `ownedSecrets` 契约（§147），能表达 JCA 流表达不了的擦除时点。
- **代价（如实）**：两套流语义必须保持可观测等价。本项目以**刻意对齐 + 逐例锁定**承担该成本：
  `CbcDecryptingInputStream` 的 KDoc 明确「错误语义以实测的 `javax.crypto.CipherInputStream` 基线为准」，
  并由 `CbcStreamFramingTest`（与真实 JCE 逐例对照）与 `CipherFallbackParityTest`
  （强制兜底 ↔ 原生产物逐字节一致）**双重锁定**。
- **不该读作**：不得据此认为「两套流语义是免费的」——它是**用维护成本换性能与擦除时点**的取舍；
  新增流式路径必须同时补两套的等价用例。
- **重开条件**：若将来把两套合一（统一到 JCA + 自持缓冲，或统一到自研骨架），须先证明
  **不损失**上述性能与擦除时点两条，并完整保留等价性用例。
- **依据**：§144 批次（`ISSUE-P3-155` 解密侧分块流）、§147 批次；
  `crypto/src/main/java/com/keepasskey/crypto/cipher/CbcStreams.kt` KDoc；`CbcStreamFramingTest` /
  `CipherFallbackParityTest`。

## PD-08 通行密钥二维码导入：载荷采用 **FIDO CXF v1.0 单凭据 Passkey JSON**，入口为「相机扫码 + 相册识码」

- **裁决**（2026-09-18，用户命题「扫码添加通行密钥（添加照片的方式）」）：
  1. **二维码载荷** = FIDO Alliance **Credential Exchange Format (CXF) v1.0**（Proposed Standard
     2025-08-14，errata 2026-03-09）的单凭据 `Passkey` 字典 JSON：`credentialId` / `userHandle` /
     `key` 为 Base64URL，`key` 为 **PKCS#8 ASN.1 DER** 的 Base64URL 编码。解析器兼容三级形态：
     裸 Passkey 对象 → CXF 凭据数组 → CXF 完整文档（**`accounts[].items[].credentials[]`**；
     原表述为 `collections[].items[].credentials[]`，`2026-09-26` 依 CXF v1.0 PS §3.2.1~3.2.3 原文勘误：
     `Collection.items` 是 `LinkedItem{item, ?account}` **仅引用、不含凭据**，凭据挂在 `Account.items` 的
     `Item.credentials` 下），取首个有效凭据；
     并**兼容 KeePassXC `.passkey` 单对象 JSON**（`relyingParty` / `privateKey`（PEM 包裹 PKCS#8）等
     6 必需字段，`src/gui/passkeys/PasskeyImporter.cpp` 口径）——KeePassXC 是本项目 Passkey schema 裁决者。
  2. **入口**（**2026-09-26 按 `ISSUE-P3-337` 用户决定改写并登记理由**）= **顶栏「扫码」分流为主入口**
     （载荷分类后 TOTP / 通行密钥各走各路；通行密钥分支须**先经用户确认再落库**，不得静默建条目）+
     **条目编辑页通行密钥区块保留附加入口**（挂到当前条目、整体替换）。两入口的取景与相册识码均
     **复用现件 `TotpScanDialog`**（相机 + Photo Picker 合一，§340/§341；原表述所引
     `SecureCaptureActivity` 已随 `ISSUE-P3-319` 退役，此处一并勘误），相册通路无需相机权限。
  3. **落库口径**（**2026-09-18 §149 批次更正**）：解析结果写入条目 **`KPEX_PASSKEY_*`** 自定义字段
     （KeePassXC / KeePassDX 口径，细则见下文 **PD-09**；原表述为「写入 `Passkey.*`」，
     与本仓同日确立的互操作 schema 相冲突，故按 PD-09 更正），私钥走受保护字段
     CharArray 链路、逐算法还原为**与生成侧完全一致的驻留格式**（原为 hex / Base64 标量口径，
     现统一为 **PKCS#8 PEM**），复用既有保存路径；URL / 用户名留白时以 rpId / userName 补齐；
     条目已有通行密钥时整体替换（KDBX 历史快照可回滚）。**导出二维码不在本期范围**（另行裁决）。
  4. **规范符合性补记（2026-09-26，依 CXF v1.0 PS §3.3.12 原文逐字核对）**：`Passkey` 字典成员为
     `type` / `credentialId` / `rpId` / `username` / `userDisplayName` / `userHandle` / `key` 七个必填 +
     可选 `fido2Extensions` —— **规范不含 `alg` 成员**（算法须由 PKCS#8 DER 的 OID 判定，不得依赖载荷自述）；
     `key` 原文为「The value MUST be PKCS#8 ASN.1 DER formatted byte string which is then Base64url encoded」
     （与本裁决第 1 项一致）；`username` / `userDisplayName` 亦为**必填**，与本裁决第 3 项「用户名留白补齐」
     相冲突；`fido2Extensions.hmacCredentials` **承载 PRF 双值**（`credWithUV` / `credWithoutUV`，
     §3.3.12.3 并规定导入方「MUST store and use these credential as-is during the HMAC operation.
     There MUST NOT be any additional derivation or domain separators」），
     与本库 `KPEX_PASSKEY_PRF` 单秘密字段存在 schema 落差。**须连带记入 WebAuthn L3 §10.1.4 原文**：
     「This extension only exposes a single PRF per credential and, when implementing on top of
     `hmac-secret`, that PRF **MUST be the one used for when user verification is performed**.
     This overrides the `UserVerificationRequirement` if necessary.」⇒ `prf` 语义下**只有 withUV 一枚有消费方**，
     `credWithoutUV` 仅关 CXF 的存储保真度；本库 `crypto/.../passkey/PasskeyPrf.kt:70-96` 把种子**原样**
     作 HMAC 密钥、客户端 `SHA-256("WebAuthn PRF" ‖ 0x00 ‖ input)` 属规范规定的 salt 构造，
     **不构成**该句所禁的「额外派生或域分隔」。
     后两点的处置口径**已于 2026-09-26 由 `PD-48` 定稿**（必填边界取 (b)、PRF 双值取 (c′)，
     另连同确认对话框 `FLAG_SECURE` 归类一并登记）；跟踪条目 `ACTIVE_ISSUES.md` `ISSUE-P3-337`。
     **第 3 片（落库接线）自 `PD-48` 落档后方准开工**。
  5. **编辑页只读口径（2026-09-26 第 4 片（下）代理裁决，依 §3.3.12.1 原文）**：规范对 `Passkey` 字典
     成员的约束是「除 `username` / `userDisplayName` 外的成员 MUST NOT be user editable」⇒ 本仓在条目
     编辑页把**全部 passkey schema 键（含 `Passkey.*` v1 旧键）锁为只读**，仅按规范明文豁免两个展示字段
     （`KPEX_PASSKEY_USERNAME` / `Passkey.UserName` / `Passkey.UserDisplayName`）。被锁字段同时**不再
     按需解密进编辑态**（改不动就没有把私钥物化进内存的理由），保存时由仓库既有的「受保护字段未提交即回填原值」
     分支写回，不依赖编辑态副本。
     取舍：「按规范精锁」与「顺手全锁」的差别只在那两个展示字段，而用户事后修正显示名是正当需求
     （规范也正是为此把它们排除在约束之外）⇒ 取精锁。
     **可逆性**：要放开某个键，改 `EDITABLE_PASSKEY_DISPLAY_KEYS` 一处即可；但须同步撤销该键在
     `EntryEditViewModel.loadEntry` 里的「不解密」待遇，否则放开的是一栏空值。
- **理由**：
  1. WebAuthn 场景的二维码（hybrid transport / caBLE）是**临时会话握手**，业界**不存在**「扫码导入
     通行密钥」的传送标准——二维码只是个容器，载荷格式才是裁决点；
  2. CXF 是 FIDO 唯一 sanctioned 的凭据交换格式，Chrome / 1Password / Bitwarden / Dashlane 已采用，
     KeePassXC 2.7.7+ 的 passkey 导入导出同源（`gui/passkeys/PasskeyImporter`）；
  3. CXF `key` = PKCS#8 DER 与本项目 `PasskeyData`（PKCS#8 语义私钥文本 + `ProtectedString`）**天然对齐**，
     无需第二套密钥编解码。
- **重开条件**：FIDO 演进出二维码专用 CXF profile，或业界形成事实上的 QR 传送标准时重评载荷包装。
- **后续演进路线（2026-09-18 补记）**：Google 已发布 Credential Manager **凭据传输 API**
  （`androidx.credentials:providerevents`，API 26+，1.0.0-alpha06），官方明确以**同一 CXF 标准**
  支持 `ExportEntry`（导出器）/ `ImportCredentialsRequest`（导入器）的同设备对等传输——
  本裁决的 CXF 载荷与其同源；后续可另立裁决接入官方传输 API（届时扫码导入仍覆盖
  跨设备 / 照片来源场景，二者互补）。
- **依据**：[FIDO CXF v1.0 PS](https://fidoalliance.org/specs/cx/cxf-v1.0-ps-20250814.html)（§3.3.12
  Passkey Dictionary、errata 版 §3.3.12 `key` = PKCS#8）；[Android 凭据传输指南](https://developer.android.google.cn/identity/sign-in/credential-transfer)；
  KeePassXC `PasskeyImporter.cpp` / `PasskeyExporter.cpp` 源码定点核实（2026-09-18）；
  [`references/KeePassDX-架构分析.md`](../references/KeePassDX-架构分析.md) §3（`privateKeyPem`）/本项目 `crypto`/`PasskeyKeyCodec` 驻留格式与
  `PasskeyAssertionActivity.decodePrivateKeyBytes` 的消费口径（2026-09-18 源码通读）。

## PD-09 通行密钥的 KDBX 存储遵循 KPEX 与 PKCS#8

- **裁决**：数据库内通行密钥采用 KeePassXC / KeePassDX 兼容的 KPEX 字段方案；私钥使用 PKCS#8 PEM 表示。KPEX 未定义的导入数据可用本仓扩展字段保真存储。旧版 v1 `Passkey.*` 字段保留只读兼容；断言导致签名计数需写回时，写路径将该条目整体迁移为 KPEX，不做全库批量改写。
- **理由**：沿用 KeePass 生态已有 schema 和标准私钥格式，避免自造字段或编码造成跨实现无法读取。具体键名、保护位和兼容解析由数据模型及互操作测试维护。
- **重开条件**：KeePassXC / KeePassDX 改变 schema，或 FIDO 提供统一且广泛支持的凭据存储规范。

## PD-10 通行密钥调用方授权仅内置已取证浏览器，其余由用户逐项启用

- **裁决**：内置信任范围限于已取证的浏览器；其他浏览器须由用户逐项授权。授权表示允许该应用通过系统通道发起请求，并不替代系统的 origin 归属校验，也不证明该应用报告的每个 origin 都可信。
- **理由**：系统未提供可由本应用代替用户维护的中立浏览器授权列表；将未取证应用默认纳入信任范围会扩大凭据调用面。
- **重开条件**：Android 提供不依赖应用包名或签名列表的系统级 origin 授权能力。

## PD-12 凭据拒绝页至多提供一条**就地授权**的补救动作，唯一目标为加入特权浏览器白名单

- **口径**（2026-09-20，§227 批次，**由用户裁决**）：
  1. 凭据拒绝页（`CredentialRejectionScreen`）在拒绝原因**确有用户可执行的解法**时，在页面内呈现说明句
     与两个选择：主动作**「添加到特权名单」**、次动作**「退出」**；无从下手的原因（`CREDENTIAL_ALREADY_EXISTS`
     这类正常结果、`MISSING_REQUEST` / `INTERNAL_ERROR` 这类系统或内部异常）**维持原布局**（仅退出），不得硬凑入口；
  2. 唯一受支持的补救动作是**将调用方浏览器加入特权名单**。**不得**提供「跳过通行密钥站点归属校验」
     （`skipDalVerification`，即设置页该开关；`ISSUE-P2-240` 前的界面文案误写为「跳过浏览器兼容层」，
     已更正）一类使本次请求通过、或削弱 DAL 核心防线的直达路径——
     把关闭防线做成一步操作，等于给出绕过「任意应用冒充任意域名注册 Passkey」防线的捷径；
  3. 动作**全程在当前受保护窗口内就地完成，不跳转任何其它界面**，彻底消除跨 Activity 路由传递带来的
     DoS 面与未解锁绕过风险；
  4. **严格的资格守卫（fail-closed）**：调用方必须是系统背书的包名、且必须是已安装的浏览器候选
     （能处理 https VIEW 且现场可读签名证书）——**原生 App 一律不呈现该动作**（原生 App 无论加不加白名单
     都无法通过 DAL，给它这个入口就是误导用户）；已在名单里的浏览器亦不呈现；
  5. **本次请求仍然必然失败**：即使用户点了「添加到特权名单」且授权成功，本次创建的 origin
     在拉起时早已被系统解析为 `apk-key-hash`，无法中途变更为 web origin。授权成功后页面就地提示
     「已添加，请回到浏览器重新发起创建」，收尾仍回传 `RESULT_CANCELED`。它改变的是**下一次**发起。
- **理由（为什么这与既有纪律完全自洽）**：
  1. 完全遵守「凭据窗口不提供本应用内导航」的既有取向（`CredentialUnlockPresenter` 等三处 no-op）——
     **没有跳转任何应用内界面**，窗口级 `FLAG_SECURE` 与反悬浮窗加固全程闭环覆盖；
  2. 它也不构成 §226 所否定的「让本次请求通过的第二条出路」：本次被拒请求**仍然必然失败**，
     对系统契约依然是 `RESULT_CANCELED`，授权只作用于下一次发起；
  3. 相比「跳转设置页」方案，就地授权免去了用户跳去设置、找入口、找应用、再切换回浏览器的多步操作，
     直接减少了跳转与操作成本（用户命题原文「减少跳转和操作」）。
- **边界（不得据本条外推）**：
  1. 仅覆盖**调用方确为浏览器**的 DAL 门禁拒绝；不得据此为原生 App 提供任何绕过 DAL 校验的入口；
  2. 不得据本条把「用户授权」做成「让本次请求通过」——任何影响**本次**请求结果的入口
     （重试、跳过校验、降级）都不在本条授权范围内；
  3. 「至多一条」是硬上限：出现第二种补救动作时须重裁（见重开条件），不得直接追加按钮。
  > **补注（2026-10-07，`ISSUE-P2-530`）**：本条的**适用链路**由「创建」扩至**断言（使用）**——同一处
  > 补救动作、同一套资格守卫（`BrowserRemedyBuilder`），只是宿主改为 `PasskeyAssertionActivity`，
  > 新增原因 `CALLER_BROWSER_NOT_TRUSTED`（成因同族：非白名单浏览器无 web origin）。
  > 三点口径**一字未变**：仍是「至多一条」动作、仍只对**确属浏览器**的调用方呈现、仍是
  > 「本次必然失败、授权只影响下一次」。断言链路的归属复校（`passesOriginBinding`）**未放宽**。
- **重开条件**：系统 Credential Manager 提供运行时动态刷新 origin 的中立能力（使本次请求可原地生效）时，
  重新裁决是否允许就地重试。
- **依据**：§227 批次；`app/.../passkey/CredentialRejectionAction.kt`、
  `app/.../passkey/BrowserRemedyBuilder.kt`、`app/.../passkey/BaseCredentialActivity.kt`、
  `app/.../passkey/PasskeyCreateActivity.kt`；`ISSUE-P3-221` **已于 §227 结案**（[`../RESOLVED_LOG.md`](../RESOLVED_LOG.md) §227；

## PD-17 「移除密码库」对**应用私有库**维持「移除即永久删除」，以**照实声明**消除误导（**2026-09-21 裁决**）

- **对应条目**：`ISSUE-P1-241` AC③ 的二选一（同轮闭环；批次正文
  [`246-移除密码库确认文案与真实行为一致批次.md`](../resolved/batches/246-移除密码库确认文案与真实行为一致批次.md)）。
- **口径**：
  1. **应用私有目录（`filesDir`）内的库**：移除动作 = **永久删除该文件**，删除后不可恢复；
     确认弹窗按此**照实**表述（红色危险按钮 + 正文指名被删文件 + 明示不可恢复），
     **不改**成「只移除关联」；
  2. **外部来源的库**（`content://` / 应用外路径）：维持「仅摘除本机登记、不动物理文件」，
     文案与按钮与上面那套**三处措辞全不相同**；
  3. 两类的判定为纯函数 `VaultRemovalKind.of(条目 path, filesDir)`（无 I/O），
     文案与动作由同一枚判据投影，且**同一枚判据**下行给数据层决定是否真删文件。
- **理由（技术事实，非偏好）**：
  1. **私有库不存在「只移除关联」这个状态**：列表由 `VaultDatabaseCatalog.buildDatabaseList`
     **按目录扫描** `filesDir/*.kdbx` 构建，判定只认文件本身、登记表里没有内部库的条目 ⇒
     若「移除」不删文件，该卡片在**下一次刷新必然原样回来**——那不是「移除」，而是「按了没反应」；
  2. 走「不删文件」就必须新增一层「已忽略文件」持久化与扫描差集逻辑，且默认动作变成**静默无效**
     （用户以为移除了、实际只是被隐藏）；破坏性动作并未消失，只是被挪到第二层入口，
     却新增了一条「看起来成功其实没动」的默认路径；
  3. 本条目的根因是**「界面说的和实际做的不一样」**，不是「删了文件」——对私有库而言删除是让它
     从列表消失的唯一动作，故正确处置是照实说，而不是把动作改成不生效。
- **不得外推的边界**：
  1. 本条**不**授权对私有库以外的对象做任何删除（外部库的移除一行文件操作都不做）；

## PD-26 转场动效按「**空间段对齐 MotionScheme / 效果段对齐设计规范时间轴**」双栏定标

> **2026-09-25 括注（`ISSUE-P3-323`）**：本条目两处口径经 `PD-44` 降档复定标——空间段档位改为
> slow / default 档、**顶层 Tab** 淡化改双向同时交叉淡化；共享轴（下钻 / 返回）的顺序淡化时间轴、
> 缩放与插值器取值、预测性返回口径**均维持不变**。

- **对应条目**：`ISSUE-P3-261` AC① / AC③ / AC⑤。
- **口径**：一次转场拆成**两类量**分别定标——
  - **空间段（位移 / 缩放）**：走 `MaterialTheme.motionScheme`（主题已声明 `MotionScheme.expressive()`）的
    `defaultSpatialSpec` / `fastSpatialSpec`（spring，damping 0.8 / stiffness 380 与 0.6 / 800）。
    **不采用** AndroidX `material-components-android` 实现的 `motionDurationLong1`（450ms）与
    `motionEasingEmphasizedInterpolator`（`EasingEmphasizedCubicBezier`）——那是**实现值**，
    而设计规范给 shared axis 的滑动是 300ms + `cubic-bezier(0.4, 0, 0.2, 1)`。
    选 spring 的理由取官方一句：**spring 在被手势打断时保证速度连续**，`tween` 从零重启；
    且底栏 `NavigationBarItem` 指示器本就走 MotionScheme 的 spring，同屏两套语言即「傻快傻快」的来源。
  - **效果段（透明度）**：走官方 shared axis 淡化对——出向 90ms、入向 210ms 且延迟 90ms
    （`AppNavigationMotion.FADE_OUT_MS` / `FADE_IN_MS` / `FADE_IN_DELAY_MS`），**顺序**而非并发。
    顺序淡化必须由**确定时长**表达，故此处刻意**不用** spring。
  - **阈值**：官方原文「At the 35% mark, neither screen is showing」是**约束**而非毫秒数，
    故以两条不变式落地（`FADE_OUT_MS ≤ 300ms × 35%`、`FADE_IN_DELAY_MS ≥ FADE_OUT_MS`）并由
    `AppNavigationMotionTest` 锁定；**注意**：AC② 原文写出的 90 / 210+90 是官方 shared axis 表的
    取值（90/300 = 30%），本裁决按**阈值约束**统一解释，不把它读成「35% 正好等于 90ms」。
  - **AC③ 缩放起点二选一的落地**：两值**分属两种官方表面**，按槽位分工，不再存在无出处的 `0.96f`——
    fade through 的入口取 `0.92f`（AndroidX `MaterialFadeThrough.DEFAULT_START_SCALE`，由小涨上来），
    全屏表面的预测性返回入口取 `110% → 100%`（`PREDICTIVE_ENTER_SCALE = 1.1f`，由大收进来）。
- **不得外推的边界（如实声明）**：① 本裁决**不**主张 spring 的观感与 300ms `tween` 等价——两者时长
  不同（expressive spatial 约 250ms 量级落定），这是**有意**的取舍；② 本裁决**不**授权把
  `AppNavigationMotion` 里的顺序淡化时长改成 spring（顺序语义会随之丢失）；
  ③ `AppNavigationMotionTest` 的「全仓 `app/src/main` 不得再出现裸 `tween(`」豁免清单当前**只有**
  `AppNavigationMotion.kt` 一项，**不得**为让守卫变绿而扩名单。
- **重开条件**：① 主题的 `MotionScheme` 改为 `standard()` 或自定义（届时空间段参数随主题变化，
  须复核底栏指示器是否仍同族）；② 上游 `material-components-android` / Material 3 规范给出
  shared axis 的新淡化对（届时阈值不变式按新表重算）；③ 出现「必须在无手势场景下保证确定时长」的
  无障碍诉求（如系统开启「移除动画」外的减弱动效偏好）——届时改判空间段。
- **依据**：[`../resolved/batches/262-导航转场定标与顶层Tab返回栈整改批次.md`](../resolved/batches/262-导航转场定标与顶层Tab返回栈整改批次.md)；

  `app/src/main/java/com/keepasskey/app/ui/theme/Theme.kt`（`MotionScheme.expressive()`）。

## PD-27 同级 / 层级的转场**选型分配维持现状**（同级 Fade Through、层级共享轴 X），有意偏离 Android Auto 口径

- **对应条目**：`ISSUE-P3-261` AC⑦（偏差表第 14 / 15 项）。
- **事实**：本应用现行为「同级 Tab 用淡入淡出、层级下钻用横向滑动」；而 corpus 内 Google 文档
  （**Android Auto 设计系统 Motion 页**）的口径相反——同级 peer views 用**横向**「side-to-side movement
  reflects the state of staying at the same level」，层级下钻用 **Z-depth**（缩放 + 顺序淡化）。
- **口径：维持现状**（同级 = Fade Through；层级 = 共享轴 X），**不**按 Android Auto 口径对调。两条理由：
  1. **来源层级不同**：Android Auto 的 peer 指引面向**车机 app bar 标签**，其「横向移动」指的是标签指示器
     在标签之间平移，**不是整页横滑**；把它外推到手机整页导航，是把一个更弱、语境不同的来源
     凌驾于 M3 / Navigation Compose 的平台实现口径之上。
  2. **与本仓返回栈语义冲突**：整页横滑在「同级不改变空间层级」上会自相矛盾——同级切换若产生横向位移，
     返回键方向的语义就会被读成「下钻返回」（这正是 `ISSUE-P2-260` 影响④描述的旧观感），
     而 `ISSUE-P3-261` AC② 已把 fade through 定为**最高优先**。
- **偏差表第 15 项（解锁 / 锁库宜用 Z-depth）的落地**：**维持 Fade Through**。解锁 ↔ 库列表是
  「会话门」而非空间层级——锁库的语义是「库门关上」，缩放会把『门』读成『更深一层』；
  且 `Unlock` 与顶层 Tab 共用同一族转场，才能让「闪一下切走 = 会话结束」形成稳定预期。
- **不得外推的边界**：① 本裁决**不**声称 Android Auto 口径有错，只声明它**不适用于**本应用的整页导航；
  ② 本裁决**不**授权新增第三种转场语言（如给某个 Tab 单独一套横滑）——顶层 Tab 必须同族
  （`AppNavigationMotionTest` 按 `BottomNavItem.routes` 逐条锁定）。
- **重开条件**：① M3 / Navigation Compose 官方文档给出「顶层目的地用整页横向、层级用 Z-depth」的
  手机端明文口径（届时按规范对调并同批回写本条）；② 产品明确要求「同级切换也要有方向感」。
- **依据**：`ISSUE-P3-261` 偏差表第 14 / 15 项与 AC②；
  `docs/references/Monica-架构分析.md:184-186`（参考项目中唯一有成文动效设计者）；
  `app/src/main/java/com/keepasskey/app/ui/KeePasskeyNavGraph.kt`（四个顶层 Tab 同族接线）。

## PD-28 预测性返回**保留 90% 屏幕缩放**（全屏表面规格），有意偏离「与 Navigation Compose 同用时应避免缩到 90%」的告诫

- **对应条目**：`ISSUE-P3-261` AC④。
- **事实**：官方移动端 predictive back 设计指引同时给出两句话——① 全屏表面规格表：
  Exit Scale `100% → 90%`、Enter Scale `110% → 100%`、以 35% 进度阈值为界、插值器 `(.1, .1, 0, 1)`；
  ② 「（共享元素过渡）does not work with FragmentManager, the Navigation Component, or Navigation Compose.
  **In these cases, avoid scaling the screen by 90%**. Instead, run the shared element transition as the
  user navigates back.」
- **口径**：**保留 90% 缩放**，且只挂在 `predictivePopExitTransition` / `predictivePopEnterTransition`
  两个**手势专属槽位**上；同批**移除**与缩放并发的满屏滑动（原实现为 slide + scale + fade 三效并发），
  并补齐插值器 `(.1, .1, 0, 1)` 与 35% 顺序淡化阈值。
- **理由**：第 ② 句的**替代方案是共享元素过渡**——它说的是「要么做共享元素、要么别缩」，
  而本应用已按 `PD-29` 裁决**不做**共享元素（Navigation Compose 与该能力不兼容），
  故第 ② 句的适用前提在本仓不成立；反过来，若既不做共享元素、又去掉缩放，
  则「返回」只剩一次淡出，层级感反而比整改前更弱。
- **不得外推的边界**：① 本裁决**只**授权手势槽位的缩放，**不**授权把 90% 缩放加回普通返回
  （`popExitTransition` 现为共享轴视差，前进 / 返回镜像）；② 本裁决**未**证明「手势缩放不与系统
  Back-to-home 窗口缩放叠加」——该叠加关系只有真机手势实录可证，见批次正文的**如实声明**段；
  ③ 不得据本条把 `enableOnBackInvokedCallback` 关掉。
- **重开条件**：① 本仓将来引入共享元素过渡（`SharedTransitionLayout` 等）——届时必须回退本条的缩放；
  ② 真机实录证成「本槽位的缩放与系统窗口缩放叠加成 0.81 倍」——届时按第 ② 句去掉缩放。
- **依据**：`ISSUE-P3-261` AC④；`app/src/main/java/com/keepasskey/app/ui/navigation/AppNavigationMotion.kt`
  （`predictivePopEnterTransition` / `predictivePopExitTransition` / `PREDICTIVE_EXIT_SCALE` /
  `PREDICTIVE_ENTER_SCALE` / `SYSTEM_UI_EASING`）。

## PD-29 「列表项 → 详情页」共享元素过渡**不做**

## PD-31 HMAC 块流**读侧块长上限移除**——仅拒绝负数，对齐三家参考实现（**2026-09-23 用户裁决**）

- **对应条目**：`ISSUE-P3-268` AC⓪（裁决项；评估阶段曾提「设置页自定义 / 固定放宽 16 MiB」两候选，
  用户指示核实参考项目后明示「**既然别家都没有上限，那么咱们也不要设置上限，只检查负数**」）。
- **事实**：旧读侧上限 `MAX_READ_BLOCK_SIZE = 1 MiB` 对「块长 > 1 MiB」一律判损坏文件，
  而规格对块长仅定 Int32、1 MiB 只是官方写侧惯例；三家参考实现读侧**均无上限、均无设置项**
  （官方 KeePass 2.61.1 `HmacBlockStream.cs:231-237` 与 keepass2android 同源仅查
  `nBlockSize < 0`；KeePassXC `HmacBlockStream.cpp:142-149` 同，其 1 MiB 仅是写侧默认分块）——
  本仓旧上限是比三家都严格的自加护栏，构成对合法第三方文件的误拒面。
- **口径**：读侧仅拒绝负数块长（与三家对齐）；「声明超大块而流不满足」由块数据读取的
  EOF 路径兜底为 `KdbxCorruptFileException`（类型化，不裸漏 `EOFException`）；
  恶意分配由 `LittleEndianUtil.readBytes` 既有通用护栏（`DEFAULT_MAX_READ_BYTES = 16 MiB`，P0-5）
  兜底——该护栏属工具层通用语义，**不属于**本裁决可支配面，不得以「读侧无上限」为由放宽或绕过。
- **不采纳「设置页自定义上限」的理由**：三家参考实现均无此设置项先例；该上限属格式解析层
  内部护栏，普通用户无从判断取值，且「自定义调大」即用户自行放弃防护——伪需求。
- **不得外推的边界**：① 写侧契约**不变**——本仓恒以 1 MiB（`DEFAULT_BLOCK_SIZE`）分块写出；
  ② 本裁决只支配 HMAC 块流层的块长校验，不构成对其它长度校验（外层头字段 1 MiB /
  内层头 64 MiB / 变体字典 value 1 MiB / `readBytes` 16 MiB 通用护栏）的放宽依据。
- **重开条件**：实测出现「> 16 MiB 单块且合法」的真实客户端文件（届时须先评估
  `readBytes` 护栏与低内存设备的分配上限，再裁决是否收窄护栏例外）。

## PD-41 剪贴板冷启动对账**维持 fail-safe 清空**、不持久化派生摘要；误清面以文案如实声明（2026-09-24，`ISSUE-P3-293` AC② 登记）

- **对应条目**：`ISSUE-P3-293` AC②——`ClipboardSecurityManager.reconcileOnColdStart` 在读到一个**布尔**跨进程标记后
  直接 `clearClipboard()`，**无摘要比对**，故可能清除**其它应用**写入的剪贴板内容。
- **裁定**：**维持现状（fail-safe 清空）**，不引入跨进程摘要比对；把误清面写进**用户可见文案**
  （`sec_clipboard_risk_notice` 中英成对），**不**登记为缺陷。
- **理由**：
  1. **改法要求把派生秘密落地**：冷启动时进程内无 `lastSensitiveHash`（进程已死），要「先比对摘要」就必须把
     口令 / 验证码的 **SHA-256 摘要持久化**到 `SharedPreferences`。而该文件的现有设计明文写着
     「跨进程仅留存一处**布尔**待清标记（**无明文、无摘要**）」——这是**刻意**的最小驻留选择。
     摘要虽是派生值，但对手里能读应用私有目录的攻击者而言，加盐与不加盐等价（盐与其同文件共存），
     故持久化摘要**换不来实质安全收益**，只增加一处「口令派生值落地」的面。
  2. **方向为安全侧**：误清他应用剪贴板内容的最坏后果是「用户少一次粘贴」，而漏清的后果是
     「口令在剪贴板里长期驻留」；两者不对称，fail-safe 是正确的一侧。
  3. **触发窗口极窄且已被限缩**：默认 30 秒定时器会在正常路径先清；跨进程标记**仅在**
     进程于该窗口内被 kill / force-stop 时才残留到下次启动。
- **不得外推的边界**：① 本条**不**授权在任何其它路径（定时清除 / 切后台 / 熄屏 / 锁库）放宽为
  「不比对摘要即清空」——那四条路径的比对语义与 `clipboardSuperseded` 标志不得改动；
  ② 本条**不**授权把摘要 / 明文写入偏好或日志（铁律 2 不变）；③ 文案必须与实现保持同向：
  若未来改回「只清本应用内容」，须同批撤下本条并改写文案。
- **重开条件**：① Android 提供「仅清本应用写入项」的可靠系统能力（如携带归属标记的剪贴板 API）；
  ② 用户反馈误清造成实际损失且频次可证。
- **依据**：`app/src/main/java/com/keepasskey/app/security/ClipboardSecurityManager.kt`（`reconcileOnColdStart`）、
  `app/src/main/res/values/strings.xml` / `values-en/strings.xml`（`sec_clipboard_risk_notice`）；
  [resolved/batches/305-剪贴板文案与冷启动对账批次.md](../resolved/batches/305-剪贴板文案与冷启动对账批次.md)。

## PD-44 转场动效**节奏降档复定标**：导航滑动取 slow 档、视差与列表取 default 档、顶层 Tab 改双向同时交叉淡化（2026-09-25 用户裁决，`ISSUE-P3-323` AC① / AC② / AC③ 登记）

## PD-46 不维护本地文件级 MAC、断言和签名加固层

- **裁决**：不为节流状态、防回滚状态、快速解锁断言或字段屏蔽记录增加本地 Keystore MAC / HMAC。基础失败节流、已见内容摘要防回滚和字段屏蔽功能仍按各自当前实现工作。
- **理由**：能任意改写应用私有文件的攻击者已超出这些文件级校验可形成可靠边界的范围；加密认证会增加密钥生命周期与恢复复杂度，却不能抵御同 UID 或 root 级攻击者。
- **风险边界**：具备应用私有目录写能力的攻击者可能重置节流/防回滚状态或读取字段屏蔽目标；不将这些文件状态描述为防御同 UID/root 的信任根。
- **重开条件**：攻击者能力边界或 Android 平台提供的文件保护原语发生实质变化。

## PD-47 TOTP 扫码取景窗口遵循防截屏设置

扫码取景窗口的 FLAG_SECURE 随用户的「禁止截屏与录屏」设置启用或解除。设置关闭时，取景画面（可能包含 TOTP 秘密）可被截屏或录屏；已保存到相册或其他位置的副本无法由应用收回。

此裁决只涉及截屏保护。遮挡触摸和覆盖层防护继续按各自安全策略执行；设置开启时仍无条件保护的凭据对话框不因本裁决改变。若关闭设置导致实际凭据泄露，应重新评估该窗口是否继续跟随设置。

## PD-48 通行密钥扫码导入的字段、PRF 与截屏取舍

- **仪式字段**（type、credentialId、rpId、userHandle、key）无效或缺失时拒绝导入；仅展示用的用户名或显示名缺失时允许补齐，并明确标注来源未提供。补齐值不得参与认证或归属判定。
- **PRF 数据**：KPEX_PASSKEY_PRF 保留 credWithUV；credWithoutUV 存入 KeePasskey 扩展字段，避免一次性导入后丢失不可恢复的数据。没有第二枚输入值时不得伪造第二枚值。
- **确认对话框**的 FLAG_SECURE 跟随防截屏设置；遮挡触摸和覆盖层防护不随该设置改变。
- **理由与边界**：展示字段不参与 WebAuthn 仪式，容错可避免丢弃有效私钥；安全字段仍严格拒绝。扩展字段用于保留导入数据，不声称其他管理器可识别它。若补齐展示值被用于认证或归属判断，或标准改变 PRF 值的选用语义，应重新裁决。

## PD-49 通行密钥扫码导入四项工程裁决（**代理裁决**，2026-09-26 用户授权）：导入凭据计数起点 / PRF 长度与别名单值 / 文档内多把凭据 / 共享取景器分辨率例外

- **授权来源**：用户 2026-09-26 明示「**我不懂这些，要我拿意见不合适，请你策划给出最佳决策**」
  ⇒ 本条四项由**代理裁决**，用户保留事后否决权。四项**均可逆**（各自的「重开条件」就地写明），
  且不涉及密码学强度取舍——属于「实现取向 + 成本」类决策，故不占用用户裁决原话栏。
- **对应条目**：`ISSUE-P3-337` 的「未决 6 / 未决 7 / 未决 8」与 **AC⑤′**；口径落点见该条目 口径 11 / 2′ / 10。

### 裁决一：导入凭据的 `signCount` 采 **(γ′) 随机高位起点**

- **内容**：第 3 片落库时，对**导入**所得凭据写入本仓扩展键 `Passkey.SignCount`，
  取值 = 在 `[2^20, 2^24)` 区间**均匀随机**一枚（`SecureRandom`）；此后由既有断言链
  `PasskeyData.nextSignCount` 单调 +1 ⇒ **断言链与 `PasskeyAssertionActivity` 零改动**。
- **为何排除另两项**（决定性证据是 RP 侧**实测行为**，不是规范措辞）：
  - **(α) 恒发 0**：`stored > 0` 时**每一次**断言都满足 §6.1.1 的「either is non-zero 且 new ≤ stored」
    ⇒ 永久落在克隆嫌疑区且**永不恢复**。反例已到手：open-passkey 的 RP 侧在这种情形**直接判失败**
    （`packages/core-ts/src/authentication.ts:246`），故「恒 0 是生态常态、RP 必然容忍」这一说法
    **不成立**——**代理上一轮曾如此推荐，本轮收回**。
  - **(β) 不写键、从 1 递增**：同样落 `≤` 区间，且若 RP 存的既有计数为 N（重度使用的硬件密钥可达数千），
    需 N 次**成功**断言才爬出 ⇒ 实践中**等价于永不恢复**。
  - **(γ′)**：一步跨过不可见的既有计数，此后单调性由我们自己**真实**维护。
- **残余风险（第 3 片必须同批登记进 [`已知工程限界.md`](已知工程限界.md)，登记前不得声称已闭环）**：
  一把被导出过的私钥，其计数器**本就不含**导出前的真实使用次数；交出高位起点后
  **该凭据的克隆检测语义归零**（若他处存有同一私钥副本，其较低计数会被我方高位值掩盖）。
  须如实认识：这是 CXF「导出即复制」的**固有后果**，不采 (γ′) 并不会恢复检测能力，
  只会把「能用」变成「被拒」。**若产品坚持保留克隆检测语义，唯一正解是拒绝导入通行密钥**
  ——那与 `PD-08` 已裁决的兼容目标直接冲突，须重开 `PD-08`。
- **重开条件**：AC⑧③ 真机对真实 RP 实测若显示「计数大幅跳变」被 RP 视为异常（风控告警 / 拒绝注册态更新），
  立即回退到「不写键」默认行为，并在本条就地登记更正与实测读数。

### 裁决二：PRF 值**长度不校验**；别名形只带一枚时**不生成第二枚**

- **内容**：① 对 `credWithUV` / `credWithoutUV` / 别名 `secret` 一律**不判长度、不裁剪、不拒收**
  ——规范 §3.3.12.3 的用词是「**SHOULD** be 32 bytes」而非 MUST ⇒ 长度异常时**原样保真存**，
  且**不进**确认清单（用户对此无法采取任何行动，写进 UI 只是噪声；与 AC⑪② 的「不承载项必须点名」
  不冲突，那是"丢弃"才需要披露）；② 载荷只带**一枚**值（规范附录 A 的 `hmacSecret{secret}` 形）
  ⇒ 按 WebAuthn L3 §10.1.4 的单 PRF 语义存 `KPEX_PASSKEY_PRF`，`Passkey.PrfNoUv` **留空**；
  **禁止**复制同一枚充当 `credWithoutUV`——那是伪造种子，违反 §3.3.12.3「MUST store … as-is」。
- **依据**：`PD-48` 裁决二 (c′) 的保真取向 + 本轮规范取证（`ISSUE-P3-337` 核实 10 的 SHOULD 用词与示例单值形）。
- **重开条件**：若出现以 PRF 值直接当对称密钥消费的下游（长度成为硬约束），须前置校验并回改本口径。

### 裁决三：文档内多把通行密钥——**导第一把 + 点名其余**，不做选择列表

- **内容**：CXF 文档含 ≥2 把 `type == "passkey"` 时，导入**首个有效**凭据，并在确认对话框如实显示
  「文档内另有 N 把通行密钥未导入」；**不**实现逐把选择列表。
- **理由**：选择列表要把**多枚私钥同时**驻留内存，直接放大[敏感缓冲所有权契约](敏感缓冲所有权契约.md)的擦除义务面
  （每枚都需独立的用毕即擦路径与失败路径断言）；而「另有 N 把未导入」的提示本身**已满足**
  AC⑪②「禁止静默丢弃」，不选择列表不等同于隐瞒。
- **重开条件**：AC⑧ 实拍取样若显示主流导出器**默认**一次给多把 ⇒ 「单凭据为主」的前提不成立，
  须改逐把导入（届时按 P2 另立条目重评擦除义务面与 UI）。

### 裁决四：**准予**越界改动共享取景器分辨率（AC⑤′ 的例外成立）

- **内容**：允许把 `TotpScanDialog` 的 `ImageAnalysis` 增设为
  `setResolutionSelector(ResolutionSelector.Builder().setResolutionStrategy(ResolutionStrategy(Size(1280, 960), FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER)).build())`；
  这是「TOTP 分支一字不改」的**唯一**豁免，改动**仅限**分辨率构造一行，不得顺带触碰裁剪 / 朝向 / hints / 线程模型。
- **为何值得越界**：解码**之前**无从知道载荷类型 ⇒ 无法只对通行密钥提分辨率；而 900 B 文档级载荷
  在默认 640×480 下只有 2.4–3.8 px/模块，贴 `ISSUE-P3-337` 核实 11 实测的乐观 floor（2–3）
  ⇒ 不提分辨率则相机通路对通行密钥**近乎不可用**，只能把声称范围缩到「仅相册导入」。
- **代价与硬边界**：每帧像素 ×4 的解码 CPU，由既有 `STRATEGY_KEEP_ONLY_LATEST` + 单线程解码器吸收；
  真机**必须回读 `ImageProxy.width/height` 实际值**进批次文档（设备硬件等级会限制可达上限，
  **严禁**以「已设 1280×960」推定「已拿到」）；TOTP 侧既有用例（含 `VaultListScanEntryPointTest`）仍须全绿。
- **重开条件**：若真机读数或用户反馈显示掉帧 / 发热可感知 ⇒ 改「渐进式提分辨率」
  （先默认分辨率试解，连续 N 帧失败后提升）——该方案仍**不解载荷内容**，与 口径 1
  「禁止回退式猜测」不冲突（那条禁的是**载荷类型**的回退猜测，不是帧率策略）。

## PD-51 凭据请求「无匹配 → 就地新建」的边界：**只做口令、强制新建、按钮文案零插值**；通行密钥维度**永不**提供「新建通行密钥」（**代理裁决**，2026-09-27，`ISSUE-P3-345` 登记）

- **授权来源**：`ISSUE-P3-345` 实施授权由用户 2026-09-27 明示（「方案可行，完成任务，过程中遇到问题自行决定」）；
  本条属该授权下的技术取舍，用户保留事后否决权。同类项目对照证据（KeePassDX / keepass2android 已逐行核实）
  见条目正文，此处不重复。
- **对应条目**：`ISSUE-P3-345`。

### 裁决内容

1. **新建动作只服务口令维度**。`androidx.credentials.provider.Action` 只在「请求含
   `BeginGetPasswordOption` 且密码候选为 0」时产出；公钥（通行密钥）请求零候选**不产出任何
   新建条目**——本应用无法凭空造出一把对某 rpId 有效的凭据，用户在登录页看到「新建通行密钥」
   按钮、点完却产不出能通过 RP 验证的凭据，就是 **PD-50 同型的「控件骗人」**。公钥零候选的
   正确出路只有站点自己的注册仪式（create 流的 `CreateEntry` 已具备）。
2. **新建 = 强制新建，不沿用 `saveAutofillCredential` 的静默「命中则原地更新」语义**。
   该入口的存在前提就是「候选装配判定无匹配」，此时再静默改写同域旧条目名不副实且不可感知；
   落库走 create-only 路径（`entryId` 为空的 `saveEntry`），命中重复由用户在既有编辑/删除面处理。
3. **按钮文案零插值**（沿用 `ISSUE-P1-10` / `PD-12` 纪律）：按钮标题不得携带域名 / 包名 /
   rpId；站点标识只允许出现在说明句与表单内的**只读绑定展示**（数据源仅限系统背书请求，
   绝不读调用方可控的 `candidateQueryData`）。
4. **入口呈现门控**：库锁定（两条通道各自已有解锁链）/ 只读会话 / 通道总开关关闭 / 调用方
   黑名单命中——四条路径**一律不呈现**新建入口（与 §232 通道开关、`PD-50` 只读拒绝同口径）。

### 为什么不采另两条路

- **对通行密钥也挂「新建」按钮再在落地页报错**：把不可满足的请求延后到用户输入之后才拒绝，
  比一开始不呈现更差（浪费用户输入，且拒绝文案无法解释「为什么按钮给了却做不了」）。
- **把 Action 常驻挂出（无论有无候选）**：系统选择器的 Actions 类目每次请求都多一行，
  而有候选时用户点它的概率趋近于零；只挂「真正无匹配」这一语境，噪声最小。
  （keepass2android 的占位数据集常驻是在**数据集层**、语义是「去 KP2A 里搜」，与本条语境不同。）

### 重开条件

若将来本应用获得「为任意 rpId 生成可用凭据」的能力（例如经通行密钥导入通道对接外部认证器、
或 WebAuthn 规范演进允许离线注册预填），第 1 项可重开为「公钥请求也呈现引导动作」；
若用户裁决「有候选时也想常驻新建入口」，第 2 段「只挂无匹配语境」作废——两种改动都只动
`CredentialResponseAssembler` 的挂出条件，不推翻本条其余口径。

## PD-69 解锁常驻通知复制快捷动作的**字段子集与存活口径**（安全复核，2026-10-03，`ISSUE-P3-440` 前置硬门）

- **对应条目**：`ISSUE-P3-440`（前台通知补「复制用户名 / 密码 / TOTP」快捷动作——条目正文明确
  「前置安全复核为硬门，未过复核**不得**开工」；本条目即该复核的裁决结论，落裁决登记而非另立文档）。
- **口径**（逐项对齐 AC 要求裁决的三问）：
  1. **字段子集**：通知上**只允许两个动作**——「复制用户名」与「复制验证码 (TOTP)」。
     用户名是公开登录标识（低敏）；TOTP 是 30 秒级一次性码，过期即失效，且用户开启常驻通知本身
     即已同意动态码可见（与 `TotpNotificationPublisher` 同判据）。**密码、受保护自定义字段、
     TOTP 种子、库文件名一律不得**出现在通知面（含动作文案与通知正文）——通知动作是「零二次确认」
     的一键路径，最高敏项必须留在「须进入应用」的一侧。
  2. **存活口径**：复制动作**只在存在「最近查看条目」时挂出**（`UnlockedNotificationEntryTracker`，
     **仅进程内存**、不落盘、不进 `SavedStateHandle`）。作用对象变化即重发通知，动作与对象不脱节；
     库锁定 / 关闭 / 偏好关闭 / 权限回收 → 通知整体撤销并**同时清除登记**。自动锁倒计时窗口内
     （即库仍处于解锁态时）动作仍可用——这与「立即锁定」动作同一面，属用户离开设备前的主动操作；
     倒计时归零系统锁库后动作与通知一起消失。进程重启后登记为空 ⇒ 不会复制「上个会话的条目」。
  3. **暴露面**：通知维持 `VISIBILITY_SECRET`（锁屏不展示内容，动作随之不展示）；动作文案为
     **固定通用文案**（不含条目名 / 用户名值 / 域名）；跨 `PendingIntent` 的载荷**只有字段名**
     （不含条目 id 或任何用户数据），作用对象在点击时现读；点击**不展开任何明文 UI**
     （走广播接收器 + 后台复制），明文只进剪贴板，复用既有 `ClipboardSecurityManager` 链
     （`EXTRA_IS_SENSITIVE` 标记 + 用户设置的定时擦除 + 熄屏 / 后台 / 锁库清除）；
     反馈仅 Snackbar（主界面可达时）或 Toast 兜底。**受信设备（无锁屏）**上通知栏可展开看到
     两个按钮，判为**可接受**：按钮文案零用户数据、点击后的明文受既有擦除约束，
     攻击者至多得知「本应用解锁中且存在一个最近查看条目」。
- **理由**：竞品 keepass2android `CopyToClipboardService.cs:111-156` 的前台通知带
  username / password / TOTP **三个**动作；本仓只取其中低敏两项，把最高敏项主动放弃——
  「竞品有」不构成让密码上通知面的理由。其余两问的答案（存活口径 / 锁屏暴露面）见上。
- **重开条件**：需要把密码或受保护字段也搬上通知面时，**必须重新做安全复核**并覆盖本条目；

## PD-75 云同步页「离线缓存」假开关**移除**：离线缓存为引擎无条件内置语义（2026-10-06，`ISSUE-P2-497` 登记）

- **对应条目**：`ISSUE-P2-497`（云同步页「离线缓存」开关为零行为消费方死开关）。
- **裁定**：**整链移除**。`ExtendedSettings` 的离线缓存字段、偏好键 `use_offline_cache` 的读写、
  `SettingsUiState` 字段与投影、`CloudSyncSections` 的开关行、controller setter 与
  `SettingsViewModel` 透传、`sync_offline_cache_title` / `sync_offline_cache_sub` 双语文案 **同批清除**；
  并顺带清理 `SettingsExtendedPreferencesController` 中同批失去消费方的 `syncCoordinator` 残留依赖。
- **理由**：离线缓存（缓存先行 + 失败保底重试）是 `SyncEngine` 的**无条件内置语义**，全路径无绕过分支；
  该开关**两向均 no-op**——ON 无增量、OFF 关不掉。它自 `2a0dd5d1`（2026-09-30，为修「首传永不联网」
  拆掉开关 → `setOfflineMode` 误接）后即变成零消费方死开关，而 KDoc 与副标题文案
  （「断网时继续读写本地缓存，联网后自动同步」）仍以**可用开关**口吻书写、UI 仍可拨动并回显，
  属 PD-39 `useFileTransactions` 行同型的**「关了也没变化」假开关**；且比一般假开关更重——
  它位于常显设置页（默认开启），每次拨动必经「落盘 + 回显」闭环，**虚假可供性被持续产出**。
- **不得外推的边界**：① 本条**不**授权移除或改写 `SyncEngine` 的离线缓存语义本身——缓存先行 +
  失败保底重试仍是无条件内置不变量，任何**新增**同步读取路径必须继续遵循；② 本条**不**触及
  `SyncCoordinator.setOfflineMode` / `SyncSessionState.isOfflineMode` 这套**引擎离线模式**管线
  （它由同步周期读取、设备侧用例消费，与本开关语义正交，误接它才会造成首传永不联网）；

## PD-79 敏感字段读取的**分层口径**：写路径 fail-fast、展示 / 解析面降级——并禁止「先查 `cleared` 再裸读」的两步式（2026-10-08 **代理裁决，用户授权**，`ISSUE-P2-540` 登记）

## PD-80 标准五字段按内容比较，非标准字段保留逐值语义

## PD-82 口令强度估算器**不**替换为 zxcvbn：维持自研模式惩罚模型，并把兜底实现补齐为原生内核的直译（2026-10-09 **用户裁决**）

- **裁定（用户裁决）**：**不**把 `crypto` 的强度估算能力替换为第三方 zxcvbn——`zxcvbn` crate 3.1.1（Rust 侧）与
  `com.nulab-inc:zxcvbn` 1.9.0（JVM 侧）**均不引入**；维持既有「自研模式惩罚型模型 + 原生优先 / 兜底降级」形态。

  1. **消费面粗，精度不承重**：强度输出全库仅 2 处生产消费——健康审计的 `isWeak` 布尔

     ⇒ 换成更精细的估算器，下游消费不到那份精度。
  2. **换不掉主要成本，反而放大它**：`strength.rs` 共 710 行的成本在**自建的热路径 DoS 加固**

     长度截断（提交 `65a1d1b0`）⇒ 换模型会**放大**该面，且仍须自建截断。
  3. **无 oracle，收益只能表述为「同源可比」**：`WEAK` 没有客观真值可比（本仓有裁判的是 `.kdbx` 互操作，
     见 `AGENTS.md` 规则 8），换估算器换不到「更准」，只能换到「与 KeePassXC 同源」；

- **边界（不得据本条外推）**：
  1. 本条**不**主张「自研模型优于 zxcvbn」，也**不**禁止将来重开——重开条件见下；选型调研（`B3-R`）作为

  3. 「只取 zxcvbn 词典数据、模型维持轻量基线」的**中间选项不采纳**：它省掉了依赖面，却没省掉 `PD-38`
     的重新标定，治理收益为零；

- **重开条件**：① 出现明确产品需求「健康面板数字须与 KeePassXC **同源一致**」；② 自研模型出现**真实误判事故**

## PD-85 字段冲突选择支持“保留本地 / 采用云端值 / 采用云端删除”（2026-10-15 用户裁决，ISSUE-P3-629）

逐字段解决冲突时使用三态决策：保留本地值、采用云端存在的值、采用云端字段删除。云端字段缺失与字段存在但值为空必须保持可区分；默认仍保留本地，删除必须由用户在明确显示“云端已删除”的字段行中选择。

标准字段与自定义字段均按精确键应用显式删除，删除仅作用于本次冲突快照中的已知差异键；自动合并、未选择字段、未知/伪造决策及整条目/历史/附件策略均不因本裁决改变。字段移除与普通修改沿用现有修改时间和历史快照流程，旧树或历史仍引用的 `ProtectedString` 不提前清零。用户裁决后本地会话或远端 ETag 变化时，旧决策失效并重新冲突。

依据：KeePass KDBX 4.1 XML Schema 允许条目 `String` 元素缺省；KeePass `KPScript GetEntryString` 亦单独提供 `FailIfNotExists`，说明缺失不同于空值。[KDBX XML Schema](https://keepass.info/help/download/KDBX_XML.xsd) · [KeePass GetEntryString](https://keepass.info/help/v2_dev/scr_sc_index.html)。外部互操作结论仍须独立 KeePass 实现端到端对拍。

  ① **归属绑定**：用户对漂移提示作出的选择（三选或合并裁决）只对**最近一次被提示的那个库**有效。
     若选择在「换库之后」才被执行（点击与执行之间存在挂起窗口），一律 fail-closed 拒绝并清除残留
     提示，绝不对用户从未裁决过的新库套用「以磁盘为准」之类的决策
     （`VaultFileDriftCoordinator.lastPromptedPathIdentifier` + `staleChoiceOwner`）。
  ② **差异字段范围**：`KEEP_LOCAL` / `KEEP_DISK` / `KEEP_BOTH` 只重裁冲突条目的**差异字段**
     （`modifiedFields`），条目的非差异字段保持三方合并产物——不得整条目替换（那会静默丢掉
     对侧对其它字段的就近修改）。「双方保留」= 以合并产物为底版、各自带自己一侧差异字段版本
     的两条条目（副本换新 UUID、标题加「磁盘冲突副本」后缀）。
  ③ **提交不可被取消切断**：采纳 + 落盘合成同一 `NonCancellable` 提交段；取消只丢弃本次回执
     展示，不留下「内存已合并、磁盘未写」的半步状态。
- **理由**：①静默把旧库决策套到新库＝对用户没见过的数据做取舍（数据丢失面）；②整条目替换会
  丢弃对侧非差异字段修改，且这些字段用户从未被询问过；③半步状态会让「重开即见旧内容」与
  「内存显示新内容」长期分叉，且无提示。
- **粒度边界**：仍为**整批策略**（不是逐字段 UI），分组级差异不进冲突清单——见
  [已知工程限界.md](已知工程限界.md) §46；库级 Meta 不参与合并——同文件 §47。
- **重开条件**：引入逐字段裁决 UI、或裁决持久化跨进程（当前提示为内存态：进程重建后
  由下一次保存重新检出漂移并重建提示，见 `PD-87`）时，须同步更新本条与 §46。

## PD-89 分组同字段双侧异值在漂移面**与同步面**都必须裁决（不得静默 LWW）；读取版本以**内容摘要**钉扎；采纳与落盘合成同一临界区（2026-10-16 ISSUE-P1-631 第三轮登记；2026-10-17 同步面接入后修订）

- **裁定**：
  ① **分组冲突面**：库文件漂移后的「合并后保存」若发现**同一分组**的**同一字段**（组名 / 备注 /
     图标 / 自定义图标 / 父组 / 组级自定义数据键）在本地与磁盘上**都被修改且取值不同**，一律
     **阻断待裁决、不落盘**，与条目冲突同口径；三选（以本地为准 / 以磁盘为准 / 双方保留）驱动
     **同一合并实现**只重裁差异字段后提交。
     - 「双方保留」对分组＝**复制整棵子树**为同父兄弟（分组 / 条目 / history 的 UUID 全部重生成、
       子树内引用重映射、根节点名带「磁盘冲突副本」后缀）——不复制则磁盘一侧的组名会挂在一个
       没有内容的空组上，等于把内容搬走，用户仍会认为数据丢了。
     - **删除 vs 修改**保持既有确定裁决（比较墓碑时刻与修改时刻；无墓碑时修改方胜），不进冲突面。
     - **单侧修改**（含两侧改成同值）照旧直接合并，不进冲突面——避免把正常合并误报成冲突。
  ② **读取版本以内容摘要钉扎**：漂移合并的「读取版本复核」以**所读取整份密文的 SHA-256** 为主判据
     （按同通道重读比对），元数据（size / mtime）仅在读取时点内容不可得时作为唯一判据。
     理由：SAF 提供方常不暴露 mtime，纯元数据判据可被「同尺寸改内容」与「ABA 复原」骗过。
  ③ **采纳与落盘不可分割**：采纳合并产物与写盘在同一会话临界区内完成（一次取锁），
     取消只影响回执展示，不产生「内存已合并 / 磁盘未写」的半步状态。
- **理由**：①「同字段双侧修改不静默取一侧」是本项为**条目**定下的合并安全口径；分组此前缺冲突模型
  而由 LWW 静默定案，属**同类**数据丢弃面，不能因实现能力不足而豁免。②与③是同一目标的两处
  加固：本次合并必须**基于且只基于**那次读取到的版本，且它的结果必须**完整**落到磁盘或被明确拒绝。
- **粒度边界**（2026-10-17 修订）：漂移面仍为**整批策略**（不是逐字段 UI）；**同步（云端）路径**的
  分组差异**也已接入冲突面**——`SyncConflictDecision` 携带 `groupConflicts`，冲突页逐组裁决
  （整组本地 / 整组云端 / 双方保留），与漂移面共用同一落树原语，见 §46 与 `ISSUE-P2-660`（已闭环，归档 §536）。
  库级 Meta **已参与三方合并**（漂移 / 同步自动合并 / 同步用户裁决三路径），身份字段恒取本地，
  见同文件 §47 与 `ISSUE-P2-659`（JVM 级验证，设备端产品路径待跑，条目仍开）。
- **重开条件**：引入逐字段裁决 UI、或同步面接入分组冲突面、或通道提供内容级 compare-and-swap 时，
  须同步更新本条与之对应的限界条目。
