## 1. 内存与落盘

### 1.1 KDBX 对象树整体驻留内存（附件除外）

- **事实**：解析已流式化，但 KDBX 对象树仍**整体驻留内存**。附件字节**除外**——超过阈值
  （`BinaryStorePolicy.DEFAULT_THRESHOLD_BYTES` = **1 MiB**，可配）的附件经 `BinaryStore` 落盘
  （`cacheDir/attachments`，0600/0700），池中只留引用。
- **清理为两层**：① 应用冷启动（`MainApplication.onCreate`，任何会话打开之前）；② 会话锁定 / 关闭事件。
- **边界（F-13 / `ISSUE-P1-19`，如实声明）**：进程被 kill / force-stop 而未经过上述任一路径时，
  已解密附件快照会**留存至下次冷启动**。⇒ **不得**再单独使用「锁定即闭环」这类措辞。
- `KdbxAttachment.clear()`（`inlineData.fill(0)`）对**落盘项**的字节不动作——其 KDoc 明写
  「字节在 store 中由多个引用者共享，**不在此处清零**（清零会连带损坏其它引用者）」，
  生命周期由 `BinaryStore.clear`（会话锁定 / 关闭；冷启动另有一层）统一收口。
- **依据**：`core/src/main/java/com/keepasskey/core/security/BinaryStore.kt`；
  `RESOLVED_LOG.md` §35 / §38 / §68。

### 1.2 用户显式「彻底退出应用」的清理面与边界（`ISSUE-P3-116`，§68）

- **事实**：该入口（`showKillAppOption` 开启时呈现）的执行顺序固定为
  「退栈 → **清理易失缓存** → `exitProcess(0)`」——清理**必须早于**退出，否则进程终止后无任何代码可执行。
  清理动作收敛在 `MainApplication.purgeVolatileCachesBeforeExit()`，覆盖
  `cacheDir/attachments`（附件解密明文）与 `cacheDir/sync`（KDBX 密文快照）**两个面**。
- **不覆盖（如实声明）**：`<库文件>.kdbx.bak`（滚动备份，属用户数据非缓存，口径见 §1.4）与
  `filesDir/rollback`（防回滚安全状态，**不得**随退出销毁，否则云侧可重放旧库）。
- **清理为同步 best-effort**：任一实现失败只落脱敏日志、**不阻断退出**；与反取证无关
  （落盘清理仍是 unlink-only，见 §1.5），**不得**据此断言「退出即不可恢复」。
- **依据**：`app/src/main/java/com/keepasskey/app/MainApplication.kt`；
  `docs/resolved/batches/68-退出前清理易失缓存批次.md`。

### 1.3 条件写依赖服务端（S3 兼容存储的分级语义）

- **事实**：S3 首传用 `If-None-Match: *` 原子创建，覆盖用 `If-Match: "<etag>"` 条件写；
  HEAD 预检只是**快速失败优化**，正确性由服务端条件写校验保证。
- **边界**：AWS S3 原子生效；**少数未实现条件写的兼容存储会忽略 `If-Match`**，语义退化为
  「HEAD 预检 + 无条件 PUT」（与旧版行为一致，不会更差）。⇒ 并发正确性在自建兼容存储上
  **不作强承诺**。
- **依据**：`sync/src/main/java/com/keepasskey/sync/s3/S3SyncProvider.kt`（类 KDoc「并发安全与条件写策略」）；
  `sync/src/main/java/com/keepasskey/sync/provider/SyncProvider.kt`。

### 1.4 `.kdbx.bak` 滚动备份的语义与保留期（`ISSUE-P3-107`，§62）

- **事实**：`createBackupBeforeSave`（默认 **true**）开启时，每次**成功写入**都会把写入前的稳定版本
  另存为**同目录**的 `<库文件名>.kdbx.bak`——滚动保留**恰好一份**（上一次成功写入的版本），逐次覆盖，
  **不**多代累积、**不**迁往其它目录。该文件是用**写入当时生效的凭据**加密的**完整库副本**，因此：
  ① 成功换密（`DatabaseSession.changeCredentials`，含换密钥文件）后**一律删除**——否则旧口令仍可解开；
  ② 关闭开关时不生成并清理历史遗留 `.bak`。
- **残余（如实声明）**：若用户在**本应用之外**（其它 KDBX 客户端）更换口令，本应用无从知晓，
  该 `.bak` 会一直可用**旧口令**解开，直至下次在本应用内写入（滚动覆盖或被换密路径删除）。
- **依据**：`database/src/main/java/com/keepasskey/database/session/DatabaseSession.kt`
  （`createBackupBeforeSave` KDoc）；`docs/resolved/batches/62-导出确认令牌下沉与文案一致性批次.md`。

### 1.5 落盘清理为 unlink-only（`ISSUE-P2-66`，已接受边界）

- **事实**：`SyncCache` / 附件缓存的清理走 `File.delete` / `deleteRecursively`，已 unlink 的扇区
  在介质 TRIM 前仍可能被恢复（取证级威胁，需**物理介质访问能力**）。
- **已接受原因**：本仓**不**实施应用层覆写擦除——对现代闪存无确定语义且显著拖慢锁定路径；
  该层面的收窄由平台全盘加密 / FBE 承担。⇒ **不得**据此断言「锁定即不可恢复」。
- **依据**：`docs/resolved/batches/51-自动填充默认值与内存保护口径批次.md`。

### 1.6 KDBX 内存池的擦除边界与树外可达性（`ISSUE-P3-119`，§52）

- **事实**：`KdbxDatabase.clearSensitiveData()` 擦除**条目树**（受保护字段 / 自定义字段 / 附件 / 历史）
  与头部 KDF secret，但**不擦内层二进制池**（`InnerHeader.binaries`）——≤ 落盘阈值的附件明文在池中
  仅随引用丢弃、等待 GC。
- **树外可达性（已逐点核实并收口）**：整树引用者只有 `SyncSessionState.lastSyncedDb`（锁库经 `clear()` 释放）
  与 `SyncConflictController` 的 `pendingLocalDb` / `pendingRemoteDb` / `pendingMergedRoot`
  （随 `clearPendingConflictSession()` 释放）；同步路径上**仅服务单次内容判定 / 一次性合并**的解析产物
  已显式擦除（`SyncContentChangeDetector` 的缓存快照树、`SyncConflictController.wipeDiscarded` 的三处丢弃点）。
  **`ISSUE-P3-168` ① 起的一处口径更新**：三方合并的本地侧改为**直取会话内存树快照**
  （`handleConflictMerge(..., localDbOverride = …)`，省去一次「解析 localBytes 回树」），于是
  `pendingLocalDb` 与 `pendingMergedRoot` 在**冲突待决**期间可能**别名引用会话树节点**（`KdbxMerger`
  对单侧独有对象按原实例复用），而不再总是独立的解密副本——它们的「释放」随 `clearPendingConflictSession()`
  变为**只丢引用**（语义更轻，明文副本数变少）；同时 `wipeDiscarded(localDb)` 必须由
  `localDbOwned` 判据把关（裸调用会静默清空活动库，已有用例与接线守卫双锁）。
- **未实施池内擦除的原因与解除条件**：`KdbxDatabase.copy()` 会**共享同一 `binaries` 列表**
  （合并路径常态发生），池项擦除须先为 `InnerHeader.BinaryItem` 定义「谁拥有该数组」的所有权规则
  （对齐 R-CLEAR-2 所有权约定），否则会误伤存活树仍在引用的同一数组。
  ⇒ **解除条件**：补齐 `BinaryItem` 所有权规则后即可实施池内擦除。
- **依据**：`docs/resolved/batches/52-同步解析落盘与内存池擦除边界批次.md`。

### 1.7 保存路径的整树重建与附件字节副本是**别名隔离契约的代价**（§115 复核，**刻意不改**）

- **事实**：`KdbxBinaryDeduplicator` 在每次保存时**无条件重建整棵树**（逐组 `group.copy`、逐条 `entry.copy`），
  并对每个**内存**附件交付独立副本（`pooled.data.copyOf()`）。这两件事都**不是**可随手省掉的开销，
  而是 ISSUE-P3-07 / P1-9 确立的**别名隔离契约**：池为唯一权威源，外部按 `Closeable` 契约
  `attachment.clear()` **不得**波及二进制池。
- **边界（⇒ **不得**据此判定「这是可随手删掉的浪费」）**：`ISSUE-P3-150`（§115）曾以「纯浪费」为由要求删掉这两处，
  复核后**推翻**——省下的只是若干对象分配（内存附件亦 ≤ 落盘阈值 1 MiB），代价是放宽一条**被用例守护的
  所有权保证**（`KdbxBinaryDeduplicatorTest.testAttachmentClearDoesNotZeroBinaryPool`）。该用例是硬护栏：
  任何「复用原附件实例以省分配」的改法都会使它变红。
- **同批确认的真实成本面（已修）**：落盘附件的 `contentHash` 是**实例级** `lazy` 缓存，
  而 `candidateItem` 原恒以 `withFlags(...)` 新建实例 ⇒ 缓存每次保存作废 ⇒ 每次保存重新读盘全部落盘附件。
  已改为 `flags` 未变时复用来源实例（读回次数恒为 1）。**该修复不涉及任何所有权语义**。
- **依据**：`docs/resolved/batches/115-IO缓冲与写出批量化及落盘附件重复读盘批次.md`；
  `KdbxBinaryDeduplicator.kt`（`deduplicateEntry` / `candidateItem` 就地 KDoc）。

## 2. 密码学与密钥派生

### 2.1 KDF 工作量上界为「按实测速率锚定的有界值」（`ISSUE-P2-49` AC②，§78）

- **事实**：Argon2 的 `I×M` 联合预算为 **`2^33` 字节·轮**（原 `2^40`），依据是 §76 的 arm64 真机实测吞吐
  ≈2.1×10⁸ 字节·轮/秒 ⇒ **最坏合法配置的墙钟 ≈40 s**（原约 1.4 小时）；AES-KDF 的 `R ≤ 2^28` 封顶
  对应实测 ≈35 s（默认 `R = 6×10⁶` ≈0.79 s）。
- **残余（如实声明）**：**不支持派生中途取消**——RustCrypto 的 `hash_password_into_with_memory`
  不暴露逐 pass 回调，协程 `withTimeout` 对阻塞式原生派生**无效**（第四轮复核定版已确认），
  故本仓以「有界工作量」而非「墙钟超时」控制最坏耗时。
- **解除条件**：若需秒级上界或取消能力，须在原生内核引入可取消派生（pass 之间检查取消标志）。
- **依据**：`database/src/main/java/com/keepasskey/database/file/KdbxKdfParameterCodec.kt`
  （`ARGON2_MAX_TOTAL_WORK` / `AES_KDF_MAX_ROUNDS` KDoc）；`docs/records/原生Argon2真机验证记录.md` §9；
  `RESOLVED_LOG.md` §76 / §78。

### 2.2 `ProtectedString` 内存加密为纵深防御层

- **事实**：`ProtectedString` 驻留加密（`InMemoryCipher` 进程密钥）是**纵深防御层**，
  进程密钥**永不擦除、永不轮换**（读入即常驻，属该原语选择的必然结果，非可「补开关」修复）。
- **边界**：持有进程密钥或**任意代码执行**者仍可在读取瞬间截获明文；⇒ 不得据此宣称
  「内存中无明文」或把它计入对同 UID 攻击者的防护。
- **依据**：`core/src/main/java/com/keepasskey/core/model/MemoryProtectionConfig.kt`；
  `docs/security/退役审计承接-42-威胁建模与架构评估.md`。

### 2.3 原生内核为 Rust，秘密缓冲由 `Zeroizing` RAII 全路径擦除

- **事实**：选择 Rust 的代价是体积，收益是**秘密确定性擦除**与 Argon2 优于纯 Java 路径。
  **arm64 真机已验证**（原生内核 JNI 通路 / 与 BouncyCastle 逐字节一致 / R1 性能闸门 +
  真实语料端到端解锁）。
- **仍未覆盖（如实声明）**：官方客户端（`keepassxc-cli` / `pykeepass`）对**本仓产物**的
  端到端互操作对拍以 `AGENTS.md` §3.8 互操作证据纪律为准（`OwnProductInteropProbeTest` + `PROBE.md`）。
- **依据**：`RESOLVED_LOG.md` §47。

### 2.4 主密码在 Compose 文本状态中为不可擦 `String`（已接受残余）

- **事实**：主密码输入经 Compose `TextField` 承载时，文本状态是**不可擦的 `String`**
  （`KeyboardType.Password` 已阻挡候选词外泄通道；输入法个性化学习见 §3.4），
  因而会作为不可控副本存活至 GC。
- **已接受原因**：可擦形态需要自行实现文本编辑栈（`AndroidView(EditText)` 或自绘输入），
  属「以稳定性换纸面加固」；且进程内取证者本已在信任边界之外（见 §2.2）。
  ⇒ 该副本**不得**被读作「会话中始终无主密码明文」。
- **依据**：`docs/security/SECURITY_RECHECK_2026-09.md`（第一轮敏感数据流审计 `M2` 分流结论，
  见 `docs/resolved/batches/41-敏感数据流审计-退役与分流.md`）。

## 3. 平台行为与窗口加固

### 3.1 原生库懒加载顺序契约

- **事实**：`System.loadLibrary` 经 `NativeCryptoLibrary.loaded` 统一懒加载；
  各绑定类的 `available` **必须**先求值该属性再发起原生调用，否则库未加载时调用 `external fun`
  会抛异常（顺序依赖，属已登记的同类限界）。
- **依据**：`crypto/src/main/java/com/keepasskey/crypto/NativeCryptoLibrary.kt`。

### 3.2 `CipherInputStream` 的异常语义

- **事实**：`CipherInputStream` 对填充非法 / 长度非整数倍抛 `IOException`（**非**静默 EOF）。
  新增 CBC 流式实现须遵守同一基线。
- **依据**：`RESOLVED_LOG.md` §38；`crypto` 模块 CBC 流式用例。

### 3.3 遮挡触摸过滤 / 悬浮窗屏蔽的接线面（无盲区）

- **事实**：窗口级遮挡触摸过滤（`setFilterTouchesWhenObscured`）在 `MainActivity` 经 `FlagSecureGuard`
  施加于 `decorView`；独立窗口按各自威胁面分别接线：
  自动填充窗口（`AutofillConfirmActivity` / `AutofillPickerActivity` / `AutofillUnlockActivity`）与
  通行密钥窗口（`CredentialUnlockActivity` / `CredentialVerificationLauncher`）调用遮挡触摸过滤；
  `BaseCredentialActivity` 体系（`PasswordSaveActivity` / `PasswordFillActivity` /
  `PasskeyAssertionActivity` / `PasskeyCreateActivity`）直接 `setHideOverlayWindows(true)`
  屏蔽悬浮窗覆盖（API 31+ 强于触摸过滤，覆盖被完全阻断故无需再叠触摸过滤）。
- **依据**：`docs/resolved/batches/73-CI原生门禁与清单导出面硬化批次.md`；
  `app/src/test/java/com/keepasskey/app/security/ObscuredTouchWiringTest.kt`、
  `SensitiveWindowHardeningTest.kt`（后者含接线守卫）。

### 3.4 IME 个性化学习（`ISSUE-P3-76`，已接受残余，不实施）

- **事实**：Compose **1.11.4** 无公开 API 可下发 `IME_FLAG_NO_PERSONALIZED_LEARNING`（逐条源码核实在案）；
  当前依赖 `KeyboardType.Password` 的部分缓解。
- **已接受原因**：把 `SecurePasswordField` 改写成 `AndroidView(EditText)` 属「以稳定性换纸面加固」。
- **解除条件**：Compose 暴露该位域即接线（结论原样收录于 `RESOLVED_LOG.md` §89）。

### 3.5 完整性重扫的 30 s 检测窗口（`ISSUE-P3-152` 复核结论，**不得为省电放宽**）

- **事实**：`RuntimeIntegrityDetector` 以 **30 s** 周期在 IO 线程重扫（root / Magisk 路径、
  `/proc/self/maps`、安装来源、`TracerPid`），并由 **120 s** 快照陈旧窗口保证
  「连丢 4 次重扫 ⇒ 非 suspend 门控（生物识别快速解锁等）转 fail-closed 保守策略」。
- **边界（⇒ **不得**据此判定「这是可省的常态开销」）**：该 30 s 既是**注入框架被捕获的上界**，
  也是高价值通道判定新鲜度的来源；省下的只是每 30 s 一次的文件探测（IO 线程），
  与「判定新鲜度」不成比例。**不得**为省电调大重扫周期或陈旧窗口——
  `RuntimeIntegrityRescanContractTest` 已把该结论钉成**可执行契约**（放宽即红，收紧不受限）。
  `ISSUE-P3-152` 复核时的另一处同类成本（`UnlockedNotificationController` 的 **2 s** 偏好轮询）
  属**真浪费**（无安全语义，且进程级快照早已存在）⇒ 已改为订阅内存快照、零 IO，见 §116。
- **解除条件**：引入**事件驱动**的等价信号源（例：由系统 / 内核侧回调替代轮询式探测），
  使同等检测时效不再依赖周期扫描。
- **依据**：`app/.../security/RuntimeIntegrityDetector.kt`（两个常量就地 KDoc）；
  `app/src/test/java/com/keepasskey/app/security/RuntimeIntegrityRescanContractTest.kt`；
  `docs/resolved/batches/116-常驻轮询收敛与完整性重扫参数守卫批次.md`。

## 4. 验证覆盖的边界（**不得**把「未覆盖」读作「已验证」）

### 4.1 设备侧（instrumented）覆盖现状

- **事实**：`app` / `database` / `sync` / `crypto` / `core` 五模块均建有 `androidTest` 源集

### 4.3 通行密钥 KPEX schema 互操作：**文件级对拍已达成**（§149 → §220，§222 补写路径自动迁移与 v1 形态嗅探），交互链路仍未覆盖

- **事实（2026-09-20 §222 更新）**：§149 批次把通行密钥落库 schema 由自造 `Passkey.*` + hex/Base64 私钥改为
  **KeePassXC / KeePassDX 口径**的 `KPEX_PASSKEY_*` + **PKCS#8 PEM**（EC 用命名曲线 `secp256r1`），
  读侧三形态兼容（KPEX / v1 旧键 / 外部条目按 `AlgorithmIdentifier` 的 OID 字节嗅探；§222 起 v1 文本形态
  也被精确嗅探——64 字符 hex → ES256、32 字节种子 → Ed25519，不再静默回落 ES256）。
  `ISSUE-P2-210` 已按 `AGENTS.md` 规则 8 补齐**官方实现端到端对拍**：
  - **写入方向**：`PasskeyInteropProbeTest` 经生产写入路径产出含 ES256 / Ed25519 / RS256 三条 KPEX 条目的
    `.kdbx`；`keepassxc-cli 2.7.12` 与 `pykeepass 4.2.0` **各自独立**读出全部 KPEX 键与保护位，
    且 `cryptography`（OpenSSL 后端）**独立解析**私钥 PEM 并**由私钥重导出公钥与产物公开公钥逐字节相等**
    （114 条判据全绿，退出码 0）；
  - **读取方向**：由 `pykeepass` + `cryptography` 产出、**不含**任何 `Passkey.*` 扩展键的 fixture，
    经生产 `KdbxFile.load` + `PasskeyData.fromCustomFields` 还原，算法由 OID 字节嗅探得出，
    且该私钥可真实签名并被外部实现生成的公钥验签通过。
  证据留痕（命令 + 原文输出 + 判据构成）：[`records/通行密钥互操作对拍记录_2026-09-19.md`](../records/通行密钥互操作对拍记录_2026-09-19.md)。
- **该对拍当次即暴露并闭环一个真实缺陷（`ISSUE-P2-211`）**：Ed25519 私钥曾被写成 RFC 5958
  `OneAsymmetricKey`（`version = 1` + `publicKey [1]`）——本仓解码器接受，**OpenSSL 系实现（含 KeePassXC）拒收**
  ⇒ 已改为 RFC 8410 `version = 0` 最小形态；解码侧**继续接受 v0/v1** 以兼容存量库。
  ⇒ **不得**再以「格式面按源码口径对齐 + 自家往返」替代外部对拍。
- **边界（不得读作「互操作已全面验证」）**：
  1. 证据是**文件级 / 离库**的：**不含** CM 通道交互，也**不含**「用外部管理器完成一次真实 RP 登录」；
  2. 系统 **CM 选择器 UI 全链路 + 通知渲染**仍未覆盖（口径见 §4.1）；端到端手工冒烟清单见
     `records/通行密钥互操作对拍记录_2026-09-19.md` §6，**2026-09-19 尚未执行**；
  3. **PRF 仍未与真实 RP 对拍**：只证 `KPEX_PASSKEY_PRF` 的承载形态与保护位被外部实现原样读写；
  4. **v1 旧条目只在「被用到时」迁移**（`ISSUE-P3-213`，§222 起）：条目因断言而被原子修补签名计数器时，
     在**同一受控变换内**整条换新为 KPEX（全部 `Passkey.*` 旧键清除，私钥重包为 PKCS#8 PEM 写入
     `KPEX_PASSKEY_PRIVATE_KEY_PEM`）；但**从未被断言触及**的 v1 条目仍是旧形态
     （读侧永久兼容、断言功能不受影响）⇒ 老库与 KeePassXC / KeePassDX 的互通**不因升级自动成立**，
     只在「该凭据被实际使用过」之后才成立。另有两条边界：私钥无法重包（形态非法 / 算法不匹配 /
     标量越界）时**放弃迁移并保持原文**（fail-safe，只留日志），以及迁移**不阻断计数器写入**。

## 7. 目录枚举噪声与其派生残余（`ISSUE-P3-142`）

- **事实**：本机（Windows/NTFS）`File.listFiles()` / `File.list()` **偶发返回「大写拼写、磁盘上并不存在」的目录条目**
  （本仓实测命中率约 **3%–6.5%**；四路交叉取证一致否认其存在：`exists`/`isFile`/`canRead`/`length` 全为 false/0、
  NIO `readAttributes` 与 `DirectoryStream` 读不到、原生 `cmd dir /b` 看不到）。该形态**既非本仓写入者、
  亦非外部进程写入者**所致，判为**平台枚举鬼影**；其具体内部路径**未证实**
  （纯文件系统 churn 20 000 轮 0 命中 ⇒ 与「写」无关，与「删后的目录索引」有关）。
- **边界**：
  1. **不得**以 `File.listFiles()` 的**原始返回值**作为「目录已清空 / 无残留」的判据——须先以**实体**复核
     （`File(dir, name).isFile` 或 NIO）；本仓 `SyncCacheTest` 与 `SyncCacheEvictorTest` 已按此口径更正；
  2. 该口径**不是放宽断言**：`isFile == true` 的**真残留仍必红**，被排除的只是「索引说有、磁盘上没有」的鬼影；
  3. 即便按上述口径，仍有约 **3%** 的**假阳性残余**（`isFile` 非百分百可靠）。更强判别式为
     **同路径短时有界重枚举**（15 ms × 4 次，实测在 380 例假阳性上 **0 命中**）——**刻意未采纳**
     （避免引入时序依赖断言），可按需启用。
- **解除条件**：平台 / 文件系统不再出现无实体枚举条目（无法主动解除）；或采纳上列更强判别式，把假阳性降到可忽略。
- **派生残余（产品代码）**：`SyncCache.deleteOrphanTmpFiles` 的匹配**大小写敏感**
  （`file.name.startsWith(key) && file.name.endsWith(SUFFIX_TMP)`，`SyncCache.kt:381`），对**大写拼写**的孤立 tmp
  不匹配。当前所有写入者均为小写，**不构成缺陷根因**；**刻意未改**（无根因依据不动产品代码）。
  解除条件：引入大写命名写入者或外部工具落临时文件时再改（改法：小写归一化后比较）。
- **派生残余（产品代码 · 第二处，2026-09-17 新增证据，**该处此前只有「偶发红」的现象、没有根因**）**：
  `SyncCacheEvictor.evictAll()` 的**残留计数**同样受该鬼影影响——它以
  `dir.list()?.count { !SyncCache.isRollbackStateFileName(it) }` 清点「应清理项」，鬼影会让该计数**多出 1**，于是：
  ① 返回 `false`（调用方据此认为清理未完成）；② 落一条**误报** WARN「同步缓存残留 N 项，锁定后密文可能仍可恢复」；
  ③ 使 `SyncCacheEvictorTest` 的 `F23 锁库清理缓存不得删除防回滚状态文件` **偶发红**——该项目**早已观测并留痕**
  （用例注释记「观测 **3 次全量 / 1 次失败**，独立复跑 4 次全绿」），并**刻意**在断言消息里带上「销毁器日志 + 实际目录内容」以待定位。
  **2026-09-17 一次全量跑的失败信息恰好完成了该定位**：断言消息给出
  「目录索引条目 = 磁盘上真实存在的文件 = **仅** `<hash>.rollback`」，而销毁器日志为「同步缓存残留 **1** 项」——
  由于 `isRollbackStateFileName` **确实**排除了该文件名，这个 `1` 只能来自 `dir.list()` 返回的**无实体条目**
  ⇒ 鬼影已从「**测试侧**目录索引」扩展到「**生产代码的清点**」。该次定位后单独复跑该类**绿**，与「偶发」一致。
- **第三处观测点（§152 第 3 轮实测命中，2026-09-18）**：`SyncCacheEvictorTest > 同步凭据清空时连带销毁同步缓存`
  ——该断言**早已按本条的实体口径**写（`syncDir.walkTopDown().filter { it.isFile }` 与 `emptyList<File>()` 比对），
  本次鬼影条目 `<64位大写HEX>.META.tmp` 的 `isFile` **返回 true** ⇒ 落进的正是上面「边界 3」自陈的约 **3% 假阳性残余**，
  而非「用了原始目录返回值」那一类。**处置：不改测试、不改产品代码**（更强的「短时有界重枚举」判别式仍按本条
  「刻意未采纳 / 可按需启用」的口径保留），仅在此登记观测点，使下一次同形红**不再被读作新缺陷**。
  命中后隔离复跑该类 **3/3 绿**，与「偶发」一致。
- **影响范围（如实界定，勿夸大）**：该鬼影是**本机 Windows/NTFS** 现象，Android 生产环境（EXT4/F2FS）**未观测到**
  ⇒ 它是**宿主侧测试可靠性**问题（附带在 Windows 上开发时可能出现一次误报 WARN），**不是终端用户可见缺陷**。
- **刻意不改（第二处同样适用）**：为迁就宿主鬼影而在产品代码里改用「实体复核后计数」，
  等于把**测试侧口径**下沉进产品代码；且 §7 已自陈按实体口径仍有约 **3% 假阳性残余**（`isFile` 非百分百可靠）
  ⇒ 换不来确定性，只换来「看起来修好了」。**解除条件**：平台 / 文件系统不再出现无实体枚举条目时自动消失。

## 8. 弱工作因子告警的**覆盖面**（`ISSUE-P2-87` 的已知残余）

- **事实**：`ISSUE-P2-87`（§110 批次）为「导入 / 打开工作因子过低的库」加了**非阻断**告警，判据由
  `KdbxKdfStrengthAssessor`（`database` 模块）给出，基线取 `KdbxHeader.createDefault`（低于基线即告警）。
  但告警的实际**呈现面只覆盖两个导入入口中的一个**：
  - ① **已覆盖**：解锁页空态的「打开已有密码库（.kdbx）」入口 ⇒ 经 `UnlockViewModel.importExternalDatabase`
    置 `UnlockUiState.infoMessage`（用户导入后停留在该页，提示可见）；
  - ② **未覆盖（本项登记的理由）**：库选择器页（`DatabasePickerScreen`）的「从来源打开」导入路径**不给提示**——
    该页在 `DatabaseSelected` 后**立即** `popBackStack()`（`KeePasskeyNavGraph.kt:57-59`），
    且其**退栈落点不固定**（可能回解锁页、也可能回库列表页），故无法用「交给落点显示」的方式可靠覆盖。
    选择器页的导入方法旁已留 KDoc 说明该责任转移，并注明**不要**在本页另加提示通道。
- **边界（如实声明）**：
  1. **不得**据本项断言「任何导入路径都会提示」——走「选择器 → 从来源打开（**本地文件**）」的用户**看不到**弱因子提示。
  2. **远端来源刻意不评估**：WebDAV / S3 的非本地路径在导入时只登记来源、**不放下载内容**，
     评估需要额外的下载预览通道；静默降级是有意的（提示不得反过来影响已成功的导入）。
  3. 评估读的是 KDBX **外层明文头部**（按规范位于认证之前），任何失败一律降级为「未评估」并**不提示**——
     即「读不到」**不等于**「达标」，**不得**把未评估读作已通过。
  4. `UnlockUiState.infoMessage` 的渲染点只在 `UnlockMode.STANDARD` 分支（`UnlockContentSections.kt:278`）：
     若导入的来源**此前已在本机封印过快速解锁凭据**（`QUICK_UNLOCK`），该信息位不渲染。
     这是**既有**的对称缺口（`infoMessage` 与 `errorMessage` 皆然），**非本项引入**，仅在此如实登记。

  ① `VaultRepository` 加一次性 `pendingKdfStrengthNotice` + `consume`，由退栈落点消费；
  ② **更优**：在设置页的 KDF 展示处（`SettingsPreferencesController.kt:41-57` 已读 `header.kdfParameters` 同源数据）
  追加「低于本应用建库默认强度」标注——它与导入路径**无关**，可一次覆盖全部来源。
  实施时须一并注意上述第 4 条的 `QUICK_UNLOCK` 渲染缺口。

## 9. OTP 取码的 `Mac` 实例复用**刻意不实施**（`ISSUE-P3-172` ④，§121 复核裁决）

- **事实**：`OtpEngine.calculateHotp` 每次取码都 `Mac.getInstance(...)` + `init(...)`。
  `ISSUE-P3-172` ④ 原 AC 要求「按算法持有 `Mac` 并 `reset()` 复用」；该条在 §121 批次
  **判定不实施**（同批 ①②③ 已整改并归档）。
- **理由（不是「做不到」，是取舍）**：复用 `Mac` 意味着该实例**长期持有** `init` 传入的

  ⇒ **以扩大密钥副本驻留面换微优化，不值得**。
- **⇒ 不得**据本表重提「把 `Mac` 缓存复用」；若日后确需优化该路径，须走**不扩大密钥 / 明文驻留面**

- **解除条件**：出现「无需实例持有密钥态」的等价原语（可在不保留密钥态的前提下复用 provider 句柄），

## 10. 同步「内容是否变化」与合并「是否被修改」两处判定口径**刻意不同**（`ISSUE-P2-91`，§122 复核）

- **事实**：本仓有**两处**条目变化判定，口径不同且**各有其正确性理由**：
  - ① `app/src/main/java/com/keepasskey/app/sync/KdbxContentComparator.kt`（原
    `SyncContentChangeDetector` 的三个 private 函数，§122 抽为可直测的纯对象）——
    回答「**是否需要重新序列化并上传**」，比较全部内容字段 + 历史**条数**，**刻意不比 `times`**；
  - ② `sync/src/main/java/com/keepasskey/sync/merge/KdbxEntryMerger.kt` 的 `isModified` ——
    回答「条目相对 **base** 是否被修改」（冲突裁决用），**必须**把 `times.lastModificationTime` 计入。
- **理由**：`KdbxTimes` **混装**内容语义（`expires` / `expiryTime`）与使用性字段
  （`lastAccessTime` / `usageCount`）及 `lastModificationTime`，而 `KdbxEntry.withField` 经
  `withModified()` **一次性改写三者**。
  - 若 ① 纳入 `times`：「触碰但内容等同」的操作会被判成内容变更 ⇒ 重新序列化 + 上传 +
    **前移远端 ETag**（KDBX4 随机 IV 使重序列化字节必然漂移——这正是该检测器存在的理由，F5）。
  - 若 ② 不比 `lastModificationTime`：时间戳更新过的条目会**退出合并**。
- **前提复核（§122 已核实并据此撤销原 `P2-91` 判定）**：生产代码**无任何**只改 `times` 的编辑入口——
  `expires` / `expiryTime` 在全仓生产代码**无写入者**（仅 XML 读取端与默认值构造）；
  `times` 的改写只经 `withField`（**同时**改 `fields`）与 passkey 计数器补丁（**同时**改 `customFields`）。
  ⇒ 「仅 `times` 变化的本地编辑被静默丢弃」在**本应用可达面上不成立**。
- **边界（如实声明，勿外推）**：以上结论针对**本仓生产代码的写入面**。**外部客户端**（其它 KDBX 实现）
  若写入「只改 `times`」的条目，本应用同步时同样**不会**把该变化读作内容变更——两者是**不同命题**，
  该形态下的表现**未实测**。
- **⇒ 不得**据本表以「口径漂移」为由在**任一侧**「顺手对齐」（两侧 KDoc 均已就地声明差异与理由）。
- **解除条件**：① 出现**只改 `times`** 的生产写入路径（如新增「编辑到期时间」功能，或
  `expires` / `expiryTime` 获得产品入口）——届时该判定须纳入 `expires` / `expiryTime`
  （**仍不得**纳入使用性字段与 `lastModificationTime`）；② 或引入「等条数原地改写历史」的路径——
  届时历史须改内容级比较。
- **依据**：`docs/resolved/batches/122-同步变化判定口径声明与语义锁定批次.md`；

## 11. 基线快照与缓存快照**各写一份**（`ISSUE-P3-167` 的「重复写盘」复核裁决，**刻意不改**）

- **事实**：`advanceBaseAndPersist`（`sync/src/main/java/com/keepasskey/sync/engine/SyncEngineSupport.kt`）
  在每次基线前移时写**两份**完整内容——缓存快照 `<hash>.cache`（`SyncCache.writeCache`）与
  基准快照 `<hash>.basecache`（`SyncCache.writeBaseContent`），各自走
  「tmp → flush → `fd.sync()` → 原子 rename」。原 `ISSUE-P3-167` 曾建议「内容一致则跳过第二次写盘」。
- **裁决：不做该跳过**（§125 复核推翻），两条独立理由：
  1. **逐字节判定不是免费的**：判定须先读全量内容并哈希（长度预检只能排除尺寸不同的情形），
     而 `advanceBaseAndPersist` **总在内容刚变更之后**被调用（上传成功 / 接受远端内容）
     ⇒ 在最常见路径上「先读一遍再决定不写」**净增**工作量，只在「内容恰好未变」时才有收益。
  2. **廉价推断不安全**：以「`basecache` 存在且 `<hash>.baseversion` 已等于该摘要」为判据看似零成本，
     但本函数的写序是 `updateBase` → `writeBaseContent`，两步之间崩溃会留下
     「baseversion 已前移、basecache 仍是旧字节」；此时跳过写盘会把**陈旧基准永久固化**——
     而基准快照存在的意义正是避免「base 被本地修改版污染 ⇒ 三方合并退化为远端全胜」
     （见 `SyncCache.readBaseContent` 的 KDoc）。
- **⇒ 不得**以「纯浪费」为由删除任一份写盘，也不得改为「按 `baseversion` 推断跳过」（理由 2）。
- **解除条件**：出现**廉价且字节级可靠**的同等性信号（例如平台提供可持久化的内容校验和，
  且该信号的写入与内容写入**原子绑定**），可在不改语义的前提下跳过重复写盘。
- **依据**：`docs/resolved/batches/125-同步接受路径摘要一次化批次.md`；
  `sync/src/main/java/com/keepasskey/sync/engine/SyncEngineSupport.kt`（`advanceBaseAndPersist` KDoc）。

## 12. 宿主侧 Windows 原子 rename 偶发 `AccessDeniedException`（**平台现象，非产品缺陷**）

- **事实**：`SyncRollbackGuard.persist` 走「写 `<hash>.rollback.<uuid>.tmp` → 原子 move 覆盖
  `<hash>.rollback`」的安全写盘序列；在**本机 Windows/NTFS** 上，该 move **在全量单测负载下偶发**
  抛 `java.nio.file.AccessDeniedException`（2026-09-17 §133 批次观测 1 次：`SyncRollbackGuardTest`
  的 `摘要重载与字节重载的裁决逐项一致`；**定向复跑 8/8 绿**、随后全量复跑绿）。
  机制：Windows 对「覆盖已存在目标」的 rename 在**目标句柄未完全释放**（索引器 / 杀软实时扫描）
  时会拒绝；POSIX / Android（EXT4 / F2FS）的 `rename(2)` **无此语义**（原子替换恒成功）。
- **边界（如实声明，勿外推）**：
  1. 这是**宿主侧测试可靠性**现象，**不是终端用户可见缺陷**——Android 侧不存在该拒绝语义；
  2. **不得**据此在产品代码里加「rename 重试」以为修复：那会把宿主侧口径下沉进产品，
     且 Android 上该重试永不触发（**无靶加固**）；同理**不得**据此放宽任何断言；
  3. 触发条件：**全量并发 / 高文件 churn 下偶发，隔离运行 8/8 绿**——与 §7 记录的
     「文件系统 churn 放大」同类环境依赖。
- **解除条件**：宿主侧不再复现（换 Linux/macOS 宿主，或 Windows 侧消除句柄竞争来源）。
  **维持现状**：不改产品代码、不改断言，复现时按「定向复跑确认 + 全量复跑」处置并留痕。
- **依据**：`docs/resolved/batches/133-WebDAV首传重复探测收敛批次.md` §5.2（含异常原文与复跑计数）。

## 13. 实时验证码窄通道在会话锁定后的驻留（`ISSUE-P3-182`；两页共用同一对象）

- **事实**：`ui/model/TotpCountdownTracker.liveCodes`（`entryId → 本周期实时验证码`）是一份内存
  `StateFlow<Map<String, String>>`，按 `ISSUE-P2-65` 的口径属「明文（验证码）驻留点」，**它未注册
  `SessionLockObserver`**：锁库 / 关库后节拍上游随 `WhileSubscribed(5000)` 停表、无人再订阅，
  故 `Map` 里的上一次取码结果会**留在内存**，直到承载它的 ViewModel 被销毁（`onCleared` →
  `viewModelScope` 取消）、或下一次周期边界刷新写空表覆盖它。
- **为什么维持现状（本批不修）**：
  1. 该通道自 §114 起由**列表页**持有（§139 只是让验证器页**复用同一实现**，未新增驻留点类型），
     §120 / §132 两轮复核均未把它判为缺陷；
  2. 驻留对象是**按周期失效**的验证码（`≤ period` 秒后即无效），不是主密码 / 种子 / 库明文那类长期秘密；
     库锁定后该页也已被移出返回栈，ViewModel 的存活期即该值的实际驻留上界；
  3. 若要「锁库即擦除」，需给两个 ViewModel 各注入 `SessionLockObserver` 并给该通道加清除 API——
     属**独立改动**（`ISSUE-P3-182` 的 AC 不含此项）。
- **解除条件**：若后续安全复核要求「锁库即擦除**全部**明文驻留点」一律成立，则应：给
  `TotpCountdownTracker` 加 `clearLiveCodes()`（写 `emptyMap()`），由列表页与验证器页各自在
  `SessionLockObserver` 回调中调用，并补「锁库 → 通道为空」的断言用例（机制对齐 §48 的四处观察者）。
- **依据**：`docs/resolved/batches/139-验证器页倒计时解耦批次.md` §5.6；列表页实现见
  §114 / §120 批次文档。

## 14. 会话级「内容摘要 → 已解析树」缓存刻意不实施（`ISSUE-P3-168` ②）

- **条目原文**：为 `SyncDatabaseCodec` 加会话级「内容摘要 → 已解析树」缓存（锁内使用，锁库 / 超限即
  `clearSensitiveData` 淘汰）。条目自身的风险提示已写明：树级缓存**扩大解密明文的驻留面**，
  必须按 §1.6 同口径登记所有权与擦除责任，**否则不得实施**。
- **裁决：不实施**（§140 批次），四条理由：
  1. **收益已被 ① 吃掉**：① 之后「本地侧重新解析」这一处**唯一可省**的解析已改为直取会话内存树；
     ② 的剩余收益只剩「后续周期重复解析**同一份**远端 / base 快照字节」，而 base 快照字节恰恰会跨周期
     复用 ⇒ 要拿到这份收益就必须**跨整个会话**持有解密树。
  2. **驻留面**：缓存项是**整棵解密树**（含 ≤ 落盘阈值的附件内联明文与受保护字段），生命周期不是
     「单次判定 / 单次合并」而是「直到锁库或淘汰」；这会同时打破 §1.6「树外可达性」清单的**穷举性**，
     而该清单正是 §52 / `ISSUE-P3-119` 擦除边界的成立依据。
  3. **没有擦除钩子，也没有淘汰口径**：`SyncDatabaseCodec` 是无接口的 `final class`，不持有会话锁观察者
     （`SessionLockObserver` 由 `SyncCoordinator` 实现）。实施需新增三项政策决定：谁在锁库时清缓存、
     「超限」是条数还是字节数、并发访问是否需要额外锁——都属**安全面新增决定**。
  4. **风险不对称**：一次漏清（锁库后仍留一棵解密树）＝**明文长期驻留**；换来的只是特定路径上
     数百毫秒级的重复 KDF。与本仓「敏感数据铁律」的取向相反。
- **替代方案（已实施）**：`ISSUE-P3-168` ①——本地侧直取会话树，**零新增明文副本**（反而少一份解密副本）。
  若日后确需缓存，正确形态是**周期内**的有界复用（同一同步周期内把已解析的 base / 远端树交给合并，
  周期结束即擦除），而非跨会话的摘要缓存。
- **解除条件**：愿意为「跨会话解密树缓存」写定所有权、淘汰口径与锁库擦除路径，并重新穷举 §1.6 的
  「整树引用者」清单——**先补该登记，再实施**。
- **依据**：`docs/resolved/batches/140-冲突合并本地侧直取内存树批次.md` §2 / §5。

## 15. ChaCha20 原生路径的 JNI 拷贝与「写粒度敏感」（§145，§215 起**解密流已直扣、其余面维持**）

- **事实**：ChaCha20 的原生优先路径（`ISSUE-P3-153` / §145）经 JNI 边界有**两次数组拷贝**
  （`convert_byte_array` 入参 + `SetByteArrayRegion` 出参），且流包装按调用方 `write` 粒度
  **逐次调用 JNI**（不像 JCE 的 `CipherOutputStream` 自带内部缓冲）。真机实测（10 MiB）：
  整块路径 **66.4 MB/s**、流路径 **54.1 MB/s**，而评估期**裸 Rust 二进制**（无 JNI）为 **118 MB/s**
  ⇒ 差距约 **1.8~2.2×**，全部来自 FFI 拷贝与 Kotlin 流中转。
- **边界（**不得**据此断言）**：
  1. **不得**读作「Rust 下沉未达预期」——相对 BC 基线（2.7 MB/s）仍为 **20~24×**；
  2. **不得**把 10 MiB 单次写入的数字外推到小粒度写入场景：写粒度越碎，单次 JNI 调用开销与
     双拷贝的**固定占比越高**（每次调用的开销摊在更少字节上）。KDBX 主流程经 GZip 写出，
     块粒度并非 64 KiB 级，故生产吞吐可能低于上述实测值。
- **残余面现状（§215 更新，按 `ISSUE-P3-198` 解除）**：`ISSUE-P3-187` 评估定案（2026-09-19，见
  [`records/JNI零拷贝评估_2026-09-19.md`](../records/JNI零拷贝评估_2026-09-19.md)）后，
  `ISSUE-P3-198` 已实施并真机验证（2026-09-19，见
  [`records/真机吞吐实测记录_2026-09-17.md`](../records/真机吞吐实测记录_2026-09-17.md) §9）——
  **解密流**（`NativeDecryptingInputStream`）已切 direct `ByteBuffer` 直扣（探针 66.3 / 3.7 ms，
  消除现状 149.8 / 23.6 ms 的拷贝份额）；**残余面缩至两处且均为有意保留**：
  ① **加密流**（`NativeEncryptingOutputStream`）——写粒度由调用方决定且可任意大，固定 direct
  缓冲需分段循环反而引入每段 JNI 固定开销，拷贝次数不变（字节 API 两侧各留一次），仅省输出
  数组分配，收益不入；② **整块 `byte[]` 路径**——契约要求返回新数组且输入不动，直扣后仍需
  put/get 两次堆内↔堆外拷贝，与现状 JNI 双拷贝等量，无收益。
- **解除条件**（§215 更新）：本条主体已解除。若未来要消除上述两处残余面，须先改变其 API 契约
  （加密流提供 `ByteBuffer` 写入口、整块路径允许就地语义）——届时按评估文档 §6 四维对照先行。
- **依据**：`docs/resolved/batches/145-ChaCha20Rust内核下沉批次.md` §4 / §5；
  实测数据 `docs/records/真机吞吐实测记录_2026-09-17.md` §2.1 / §9；
  评估与探针 `docs/records/JNI零拷贝评估_2026-09-19.md`（`ISSUE-P3-187` / §212）。

## 16. RS256 保持 BouncyCastle 纯 Java（`ISSUE-P3-153` / §146 实测否定下沉）

- **事实**：真机实测（Redmi 4X / arm64-v8a，预热 + 多轮中位数，见实测记录 §2.2）Rust `rsa` crate
  对 BC **更慢**：keygen 2106.5 ms vs **993.0 ms**（慢 2.1×）、sign 17.8 ms vs **10.9 ms**（慢 1.6×）。
  原因是 BC 的 RSA 带 CRT / Montgomery 优化，`rsa` crate 在该规模下未占优。
- **边界（**不得**据此断言）**：
  1. **不得**以「Rust 更快」为由重提 RS256 下沉；
  2. **不得**把 ES256 / Ed25519 的 16~22× 加速比外推到 RSA——三者算法不同、实现成熟度不同，
     结论**只对测过的那对实现成立**（与 `ISSUE-P3-153` 原文「量化前提不得外推」同口径）。
- **现状代价（如实）**：RS256 passkey 的每次断言签名仍走 BC 纯 Java（真机 sign 10.9 ms 量级）。
  WebAuthn 实践中 RS256 凭据占比很低，故该代价面有限。
- **解除条件**：Rust RSA 生态出现经**同法实测**（同机 / 同语料 / 预热 + 多轮中位数）显著快于 BC 的
  实现；或 BC 退出维护 / 许可面发生变化——届时须重跑对比再决定。
- **追问复核（2026-09-17 第二轮，回答「是否把 JNI 开销算进去了」）**：
  1. **JNI 不构成解释**：Rust 侧数字取自**独立 aarch64 二进制**（无 JVM / 无 JNI），
     是「无边界」的最优条件；真机实测 JNI 单次固定开销 **18.956 µs**（16 B 载荷），
     占一次 RS256 签名（11.8 ms）的 **0.16%** ⇒ 上生产只会更慢。
  2. **同形对照仍慢 1.74×**：同为「预置 key 复用」，BC **10.230 ms** vs Rust **17.828 ms**；
     生产形态（BC 含每次 DER 解析 11.807 ms）对照为 **1.51×**。
  3. **两处口径不对称，方向都对 Rust 有利**：① BC 侧含每次调用的 DER 解析（≈1.58 ms/次）；
     ② 经 `javap -c` 字节码取证，BC 1.77 `RSADigestSigner` 默认实例化
     **`RSABlindedEngine`**（**带盲化**），而 `rsa` crate 的 `Signer` 路径**不带盲化**——
     即 **Rust 是在少做一层侧信道防护的前提下仍然更慢**。
- **依据**：`docs/resolved/batches/146-Passkey签名内核下沉批次.md` §4；
  实测数据 `docs/records/真机吞吐实测记录_2026-09-17.md` §2.2 与 **§7.1 / §7.2**。

## 17. AES-256-CBC 统一到 Rust 内核后的**性能代价**与 JNI 边界秘密治理面（§147，**取向为可靠性/可维护性，非性能**）

- **事实（双机 10 轮实测，10 MiB，每轮 5 采样中位；见实测记录 §8）**：

  | 路径 | Redmi 4X（A53） | M332BF（现代） |
  |---|---|---|
  | 生产·整块加密（原生 JNI） | 250.9 ms | **48.1 ms** |
  | 生产·流式加密 | 291.2 ms | **54.9 ms** |
  | 生产·整块解密 | 259.6 ms | **34.3 ms** |
  | 生产·流式解密 | 315.3 ms | **49.1 ms** |
  | 对照·JCE 最优（`doFinal` / 64 KiB 分块） | 34.4 / 101.3 / 93.5 ms | **9.2 / 19.5 / 14.3 ms** |
  | **额外开销（绝对差）** | **+166~222 ms** | **+20~39 ms** |
  | 对照·倍数 | 2.8~7.3× | 2.4~5.2× |

- **成本构成（现代机 48.1 ms，同一份 10 MiB）**：算法本体 **13.3 ms（28%）** + JNI 边界
  **21.2 ms（44%）** + PKCS#7 整缓冲垫片与明文擦除 **13.6 ms（28%）**；
  对照 JCE `doFinal` **全程仅 9.2 ms**。
- **边界（**不得**据此断言）**：
  1. **不得**以「下沉更快」描述本项：内核层与现代设备上**均不占优**——现代机 Rust**内核本体**
     （13.3 ms）已慢于 JCE **全程**（9.2 ms）；CBC 加密是串行依赖、逐块调用吃不到 ILP，追不上
     OpenSSL 汇编 ⇒ **优化实现不可能翻盘**，「先修实现开销再复测」这条路径已排除。
  2. **不得**把「无感」外推到「老设备 × 大库」：A53 级设备 5 MB 库约 **+83~111 ms**（非十几毫秒）；
     20 MB 级库在现代机也到 **+40~78 ms**。
  3. **不得**把 ChaCha20 的收益外推到 AES：同批下沉的 ChaCha20 是**绝对巨益**
     （现代 244.2 → 24.7 ms，省 219.5 ms；A53 3712.5 → 85 ms），两者方向相反。
  4. **不得**用单一机型的内核数字外推全部机型：同一份 Rust 代码的 CBC 解密在 A53 为 249 MB/s、
     现代机为 **5072 MB/s**（现代 OoO 核可把硬件 AES 延迟流水化），差异 20×。
- **已接受的判据（2026-09-18，用户裁定，本节存在的前提）**：`minSdk 36` 面向**现代设备**，
  主库体积普遍 **<5 MB** ⇒ 额外 **10~20 ms** 落在无感区；本项按**可靠性 / 稳定性 / 可维护性**
  （跨平台统一、审计一致性、单一填充实现）保留，**性能不作为理由**。
- **本项新增的残余风险面（非性能，须持续警惕）**：JNI 边界的**秘密治理**。§147 实施中实测踩中
  一次契约漏洞——原生变换**惰性**读取密钥，而调用方（`KdbxFile` / `KdbxCipherKeyResolver`）
  依据「`SecretKeySpec` 已克隆密钥」的 **JCE 假设**在建流后立即擦除自己的密钥数组，
  导致以全零密钥解密（表现为末块 PKCS#7 校验失败）。该缺陷**只在真机回归暴露**（宿主单测全绿）。
  现由 `CbcEncryptingOutputStream` / `CbcDecryptingInputStream` 的 `ownedSecrets` 契约
  （流自持副本并负责擦除）+ `StreamKeyOwnershipContractTest` 锁定；**新增任何原生流式变换必须
  一并核对该契约**。
- **解除条件**（§215 更新，已按 `ISSUE-P3-198` 重估）：`ISSUE-P3-187` 评估定案后，`ISSUE-P3-198`
  已实施并真机验证（2026-09-19，实测见
  [`records/真机吞吐实测记录_2026-09-17.md`](../records/真机吞吐实测记录_2026-09-17.md) §9）。
  **流式生产路径**（整库加解密的实际形态）的「边界 + 拷贝」份额已消除（直扣后 AES 单次
  178.9 → 48.7 ms @ Redmi 4X、43.9 → 14.7 ms @ 模拟器，直扣 14.7 ≈ 内核 13.3 × 1.1）；
  **整块 `byte[]` 路径**（探针/整库一次性形态）维持拷贝桥——其契约要求返回新数组且输入不动，
  直扣后 put/get 拷贝量与 JNI 双拷贝等量、无收益，属**已接受残余面**（上表 44% 占比对整块
  口径仍然成立，**不得**据此断言流式路径同比例存在）。另一解除路径不变：RustCrypto 侧出现
  能吃到 ILP 的 CBC 批处理实现（仅影响加密侧，且仍不足以追平 JCE）。
- **依据**：`docs/resolved/batches/147-AES内核下沉批次.md`；实测数据
  `docs/records/真机吞吐实测记录_2026-09-17.md` **§8**（含 §8.3 对 §7.3 基线口径的修正）。

- **事实（2026-09-18 全量 `wc -l` 复核）**：巨型类专项整改后仍超 500 行的**逻辑**（非 Compose）文件两个：

## 19. 测试侧 `Dispatchers.Main` 采「只装不卸」口径：换取偶发红消失，代价是失去「忘装 Main 立刻抛错」的检测（`ISSUE-P3-189`，§153）

- **事实（2026-09-18 实测）**：`withContext(Dispatchers.Default)` 的块**正常跑完**后，把结果回送给父协程时
  仍要对父作用域的 `Dispatchers.Main` 问一次 `isDispatchNeeded`（栈：`DispatchedCoroutine.afterResume` →
  `DispatchedContinuationKt.safeIsDispatchNeeded` → `TestMainDispatcher.isDispatchNeeded`，
  异常 `Dispatchers.Main was accessed when the platform dispatcher was absent`，抛点
  `TestMainDispatcherJvm.kt:45`）。故「先 `viewModelScope.cancel()` 再 `Dispatchers.resetMain()`」
  **只保证续体不被执行，不保证不再访问 Main**——取消本身反而**制造**一次回跳访问；
  而该访问落在真实线程上，被协程测试记给**下一个**用例 ⇒ 偶发红且位置漂移（§152 实测命中率 **1/4**）。
- **裁决（路线①）**：`app/src/test` 全源集**不再**调用 `resetMain()`，改由各用例 `@Before` 各自
  `setMain(新实例)` 覆盖；迟到回跳因此永远有「已装的」派发器可落，落进的是**当时那个**用例自己的调度器，
  其父作用域已取消 ⇒ 续体被丢弃、不执行。由 `quality/MainDispatcherPollutionGuardTest` 钉死
  「守卫之外不得出现 `resetMain()`」「构造 ViewModel 必须 `track(`」「登记守卫者必须自行 `setMain(`」。
- **接受的代价（不得当作已解决）**：一旦某用例**忘装** Main，将静默继承上一个用例的派发器而不再立刻抛错。
  之所以**不**强制「凡构造 ViewModel 者必须装 Main」：现不装 Main 的仓库面确实不触达 `Main`，
  而为其装 `StandardTestDispatcher` 会一并改掉 `Dispatchers.Main.immediate` 的**就地执行**语义（属行为改动）。
  忘装的后果仍会以「工作从未被推进 ⇒ 用例自身断言失败」的形态暴露，只是不再是干净的报错。
- **边界（不得据本条外推）**：
  1. 本条**只**约束单元测试的 Main 生命周期，**不**是产品缺陷——生产环境 `Dispatchers.Main` 恒存在；
  2. **不**等于「跨用例污染已根治」：在途工作仍需 `MainDispatcherGuard.track` 显式取消，
     本条只是取消之后**收尾顺序**不再引发假异常；漏 `track` 的用例照样会回写别人；
  3. **不**适用于 `:crypto:` / `:database:` / `:sync:` 四件套与设备侧用例（它们不装测试 Main）。
- **解除条件**：`kotlinx-coroutines-test` 改为「`resetMain()` 后访问 Main 不抛（回落平台实现或空实现）」、
  或本仓为 ViewModel 侧 CPU 段提供可 await 的生命周期句柄（§152 登记的路线③）使「取消」不再需要——
  届时可恢复 per-test 的 `resetMain()` 并删除本条。
- **依据**：批次 [`../resolved/batches/152-污染防护全覆盖与归档文档精简批次.md`](../resolved/batches/152-污染防护全覆盖与归档文档精简批次.md) §1.7（反证）与
  [`../resolved/batches/153-Main派发器只装不卸批次.md`](../resolved/batches/153-Main派发器只装不卸批次.md)（落地与 8 轮验证）。

## 22. 凭据拒绝页「就地授权特权浏览器」的残余边界（`ISSUE-P3-221`，§227）

- **事实**：凭据拒绝页的就地补救动作（将发起请求的浏览器添加到特权浏览器白名单）**不跳转任何界面**，
  在当前受保护窗口内直接调用 `PasskeyPrivilegedBrowserStore.setEnabled(pkg, true)` 完成授权。
  由此带来的工程边界与残余：

  1. **本次请求仍然失败**：创建流程拉起时，系统凭据框架已将 origin 固定（非白名单浏览器退化为
     `android:apk-key-hash:...`），无法在运行时原地变更为 web origin。故即便用户在拒绝页上点击了
     「添加到特权名单」并成功写入，当前这次创建仍以 `RESULT_CANCELED` 收尾。授权生效于**下一次发起**——
     用户回到浏览器重新点击创建时，该浏览器才能经系统 `getOrigin` 取得 web origin 从而豁免 DAL；
  2. **原生 App 严格 fail-closed 不提供入口**：DAL 门禁被拒的调用方若非浏览器（`installedBrowsers`
     未命中，即不能处理 https VIEW 意图），`BrowserRemedyBuilder` **恒返回 null**——不提供添加按钮。
     因为将原生 App 加入特权浏览器白名单对它的 DAL 校验毫无帮助，给入口只会欺骗用户；
  3. **该界面的动态交互无自动化用例覆盖**：仓库 `app/src/androidTest` **无 Compose UI 测试基建**
     （无 `createAndroidComposeRule`），故「点击后转圈 → 成功文案呈现 → 确认后退出」的完整 UI 交互
     只能靠真机手工核验。宿主单测覆盖的是**纯逻辑与静态接线**：`BrowserRemedyBuilder` 的三个 fail-closed
     前提、`forReason` 穷举映射、写入下沉 Default 协程、无插值与占位符规范、不拉起外部 Activity。

- **为什么不采用「跳转设置页」方案（已在方案演进中被否决）**：
  1. `MainActivity` 是唯一无权限保护的导出组件，`ExportedComponentHygieneTest` 锁定了
     「不得消费任何外部 intent 数据」这一安全不变式，跨 Activity 传递目标路由无法走标准 Intent；
  2. 凭据窗口具有「不提供本应用内导航」的加固取向（`CredentialUnlockPresenter` 等三处 no-op）；
  3. 用户命题明确要求「减少跳转和操作」——就地完成授权使操作步数由「跳去设置 → 找开关 → 找应用 → 切回浏览器」
     骤降为「点一次添加 → 回浏览器重试」。
- **无自动化覆盖的具体缺口（需真机核验的项）**：
  ① 真实系统拉起下，按钮点击后的 `CircularProgressIndicator` 转圈与状态刷新流程度；
  ② 写入偏好后回到浏览器再次发起 passkeys.io 注册，是否确实直接放行且不再弹拒绝页；
  ③ 读不到签名证书（例如特殊沙箱环境）时的 `STATUS_FAILED` 失败文案呈现。
- **边界（不得据本条外推）**：
  1. 本条**不**授权「让本次请求通过」——任何原地重试或中途修改 origin 的企图均属严重安全降级；
  2. 本条**不**代表对原生 App 放宽 DAL 校验；
  3. 本条**不**构成「无需真机验证」的理由——真机冒烟是本项交付的必要环节。
- **解除条件**：① 系统 Credential Manager 引入支持在回调内动态重新协商 origin 的机制时，可评估是否支持原地重试；
  ② 引入 Compose UI 自动化测试基建后，将交互状态机纳入自动化回归。
- **依据**：批次 [`227-Passkey拒绝页就地补救授权批次.md`](../resolved/batches/227-Passkey拒绝页就地补救授权批次.md)；
  `app/.../passkey/CredentialRejectionAction.kt`、`app/.../passkey/BrowserRemedyBuilder.kt`、
  `app/.../passkey/CredentialRejectionScreen.kt`、`app/.../passkey/BaseCredentialActivity.kt`；
  `app/src/test/.../passkey/CredentialRejectionFeedbackTest.kt`。

  凭据提供方——用户看到的是「列表里还在，点了没内容」。
- **为何不接受为缺陷**：组件注册由 `AndroidManifest.xml` 声明 + 系统设置选取决定。理论上可用
  `PackageManager.setComponentEnabledSetting(...DISABLED)` 动态摘除，本批**刻意不做**：
  1. 已被系统**选中**的扩展组件被就地禁用，会把系统留在「已选中但无响应」的异常态，
     恢复路径只有用户自己去系统设置改选——比「返回空响应」更不可预期；
  2. 「不再交付任何凭据」已覆盖用户关闭通道的**安全意图**（该通道不再流出凭据），
     而「从列表消失」属可见性诉求，代价与本收益不成比例；
  3. 动态组件开关与本仓 Manifest / 权限卫生的静态守卫口径相冲（组件声明面须保持可审计的静态形态）。
- **文案已按此表述**：`autofill_service_sub` / `autofill_cm_sub` 明确写出「系统设置仍会列出本应用，
  可在其中改选」，不得改写成「已从系统移除」这类做不到的承诺。
- **解除条件**：若系统后续提供官方的「应用内自助停用扩展组件」通道（不产生「选中但无响应」异常态），
  可在三条开关上叠加该动作；届时须同步改文案并更新本条。

  `app/.../data/repository/ExtendedSettingsStore.kt`（三个 `is*Enabled()` 的 KDoc）、
  `app/.../passkey/KeePasskeyCredentialProviderService.kt`、`app/.../autofill/KeePasskeyAutofillService.kt`、
  `app/src/test/.../ui/AutofillChannelSwitchWiringTest.kt`。
