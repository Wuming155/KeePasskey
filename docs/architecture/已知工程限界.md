## 1. 内存与落盘

### 1.1 KDBX 对象树整体驻留内存（附件除外）

- **事实**：解析已流式化，但 KDBX 对象树仍**整体驻留内存**；附件字节**除外**——超过阈值（`BinaryStorePolicy.DEFAULT_THRESHOLD_BYTES` = **1
  MiB**，可配）的附件经 `BinaryStore` 落盘（`cacheDir/attachments`，0600/0700），池中只留引用。
- **清理由三条路径驱动**：① 应用冷启动（`MainApplication.onCreate`，任何会话打开之前）；② 会话锁定 / 关闭事件；③「彻底退出应用」（见 §1.2）。
- **边界（F-13 / `ISSUE-P1-19`，如实声明）**：进程被 kill / force-stop 而未经过上述任一路径时，已解密附件快照会**留存至下次冷启动**。⇒
  **不得**再单独使用「锁定即闭环」这类措辞。
- **落盘项的清零责任**：`KdbxAttachment.clear()`（`inlineData.fill(0)`）对**落盘项**的字节不动作——其 KDoc 明写「字节在 store 中由多个引用者共享，
  **不在此处清零**（清零会连带损坏其它引用者）」；生命周期由 `BinaryStore.clear`（会话锁定 / 关闭；冷启动另有一层）统一收口。
- **依据**：`core/src/main/java/com/keepasskey/core/security/BinaryStore.kt`；`RESOLVED_LOG.md` §35 / §38 / §68。

### 1.2 用户显式「彻底退出应用」的清理面与边界（`ISSUE-P3-116`，§68）

- **事实**：该入口（`showKillAppOption` 开启时呈现）的执行顺序固定为「退栈 → **清理易失缓存** → `exitProcess(0)`」——清理**必须早于**退出，
  否则进程终止后无任何代码可执行；清理动作收敛在 `MainApplication.purgeVolatileCachesBeforeExit()`，覆盖
  `cacheDir/attachments`（附件解密明文）与 `cacheDir/sync`（KDBX 密文快照）**两个面**。
- **不覆盖（如实声明）**：`<库文件>.kdbx.bak`（滚动备份，属用户数据非缓存，口径见 §1.4）与 `filesDir/rollback`（防回滚安全状态，**不得**随退出销毁，否则云侧可重放旧库）。
- **清理为同步 best-effort**：任一实现失败只落脱敏日志、**不阻断退出**；与反取证无关（落盘清理仍是 unlink-only，见 §1.5），**不得**据此断言「退出即不可恢复」。
- **依据**：`app/src/main/java/com/keepasskey/app/MainApplication.kt`；
  `docs/resolved/batches/68-退出前清理易失缓存批次.md`。

### 1.3 条件写依赖服务端（S3 兼容存储的分级语义）

- **事实**：S3 首传用 `If-None-Match: *` 原子创建，覆盖用 `If-Match: "<etag>"` 条件写；HEAD 预检只是**快速失败优化**，正确性由服务端条件写校验保证。
- **边界**：AWS S3 原子生效；**少数未实现条件写的兼容存储会忽略 `If-Match`**，语义退化为「HEAD 预检 + 无条件 PUT」（与旧版行为一致，不会更差）⇒
  并发正确性在自建兼容存储上**不作强承诺**。
- **当前口径（`ISSUE-P2-244`，2026-09-21 补 / §249 闭环）**：原缺「`expectedEtag` 为空且 HEAD 成功但**未返回 ETag** 时一个条件头都不发」
  这一比「兼容存储忽略 `If-Match`」**更弱**的形态；现该分支为 **fail-closed**——HEAD 成功但缺 `ETag` 时**上抛**
  `SyncException.ProtocolError` 且**不发任何 PUT**（`takeIf { isNotBlank }` 可选放行已移除）。
- **依据**：`sync/src/main/java/com/keepasskey/sync/s3/S3SyncProvider.kt`（`upload` 方法 KDoc「并发安全与条件写策略」，
  `S3SyncProvider.kt:225`）；`sync/src/main/java/com/keepasskey/sync/provider/SyncProvider.kt`。

### 1.4 `.kdbx.bak` 滚动备份的语义与保留期（`ISSUE-P3-107`，§62）

- **事实**：`createBackupBeforeSave`（默认 **true**）开启时，每次**成功写入**都会把写入前的稳定版本另存为**同目录**的
  `<库文件名>.kdbx.bak`——滚动保留**恰好一份**（上一次成功写入的版本），逐次覆盖，**不**多代累积、**不**迁往其它目录。
- **残余（如实声明）**：若用户在**本应用之外**（其它 KDBX 客户端）更换口令，本应用无从知晓，该 `.bak` 会一直可用**旧口令**解开，直至下次在本应用内写入（滚动覆盖或被换密路径删除）。
- **依据**：`database/src/main/java/com/keepasskey/database/session/DatabaseSession.kt`（
  `createBackupBeforeSave` KDoc）；`docs/resolved/batches/62-导出确认令牌下沉与文案一致性批次.md`。

### 1.5 落盘清理为 unlink-only（`ISSUE-P2-66`，已接受边界）

- **事实**：`SyncCache` / 附件缓存的清理走 `File.delete` / `deleteRecursively`，已 unlink 的扇区在介质 TRIM 前仍可能被恢复（取证级威胁，
  需**物理介质访问能力**）。
- **已接受原因**：本仓**不**实施应用层覆写擦除——对现代闪存无确定语义且显著拖慢锁定路径；该层面的收窄由平台全盘加密 / FBE 承担。⇒ **不得**据此断言「锁定即不可恢复」。
- **依据**：`docs/resolved/batches/51-自动填充默认值与内存保护口径批次.md`。

### 1.6 KDBX 内存池的擦除边界与树外可达性（`ISSUE-P3-119`，§52）

- **事实**：`KdbxDatabase.clearSensitiveData()` 擦除**条目树**（受保护字段 / 自定义字段 / 附件 / 历史）与头部 KDF secret，
  但**不擦内层二进制池**（`InnerHeader.binaries`）——≤ 落盘阈值的附件明文在池中仅随引用丢弃、等待 GC。
- **树外可达性（已逐点核实并收口）**：整树引用者只有 `SyncSessionState.lastSyncedDb`（锁库经 `clear()` 释放）与 `SyncConflictController` 的
  `pendingLocalDb` / `pendingRemoteDb` / `pendingMergedRoot`（随 `clearPendingConflictSession()` 释放）；
  同步路径上**仅服务单次内容判定 / 一次性合并**的解析产物已显式擦除（`SyncContentChangeDetector` 的缓存快照树、
  `SyncConflictController.wipeDiscarded` 的三处丢弃点）。
- **未实施池内擦除的原因与解除条件**：`KdbxDatabase.copy()` 会**共享同一 `binaries` 列表**（合并路径常态发生），池项擦除须先为
  `InnerHeader.BinaryItem` 定义「谁拥有该数组」的所有权规则（对齐 R-CLEAR-2 所有权约定），否则会误伤存活树仍在引用的同一数组。⇒ **解除条件**：补齐
  `BinaryItem` 所有权规则后即可实施池内擦除。
- **依据**：`docs/resolved/batches/52-同步解析落盘与内存池擦除边界批次.md`；再收口见 `docs/resolved/batches/238-待决冲突解析树身份判定擦除批次.md`。

### 1.7 保存路径的整树重建与附件字节副本是**别名隔离契约的代价**（§115 复核，**刻意不改**）

- **事实**：`KdbxBinaryDeduplicator` 在每次保存时**无条件重建整棵树**（逐组 `group.copy`、逐条 `entry.copy`），
  并对每个**内存**附件交付独立副本（`pooled.data.copyOf()`）。这两件事都**不是**可随手省掉的开销，而是 ISSUE-P3-07 / P1-9 确立的**别名隔离契约**：
  池为唯一权威源，外部按 `Closeable` 契约 `attachment.clear()` **不得**波及二进制池。
- **边界（⇒ **不得**据此判定「这是可随手删掉的浪费」）**：`ISSUE-P3-150`（§115）曾以「纯浪费」为由要求删掉这两处，复核后**推翻**——省下的只是若干对象分配（内存附件亦 ≤ 落盘阈值
  1 MiB），代价是放宽一条**被用例守护的所有权保证**（`KdbxBinaryDeduplicatorTest.testAttachmentClearDoesNotZeroBinaryPool`）。
  该用例是硬护栏：任何「复用原附件实例以省分配」的改法都会使它变红。
- **同批确认的真实成本面（已修）**：落盘附件的 `contentHash` 是**实例级** `lazy` 缓存，而 `candidateItem` 原恒以 `withFlags(...)` 新建实例 ⇒
  缓存每次保存作废 ⇒ 每次保存重新读盘全部落盘附件；已改为 `flags` 未变时复用来源实例（读回次数恒为 1）。
- **依据**：`docs/resolved/batches/115-IO缓冲与写出批量化及落盘附件重复读盘批次.md`；
  `KdbxBinaryDeduplicator.kt`（`deduplicateEntry` / `candidateItem` 就地 KDoc）。

## 2. 密码学与密钥派生

### 2.1 KDF 工作量上界为「按实测速率锚定的有界值」（`ISSUE-P2-49` AC②，§78）

- **事实**：Argon2 的 `I×M` 联合预算为 **`2^33` 字节·轮**（原 `2^40`），依据是 §76 的 arm64 真机实测吞吐 ≈2.1×10⁸ 字节·轮/秒 ⇒
  **最坏合法配置的墙钟 ≈40 s**（原约 1.4 小时）；AES-KDF 的 `R ≤ 2^28` 封顶对应实测 ≈35 s（默认 `R = 6×10⁶` ≈0.79 s）。
- **残余（如实声明）**：**不支持派生中途取消**——RustCrypto 的 `hash_password_into_with_memory` 不暴露逐 pass 回调，协程 `withTimeout`
  对阻塞式原生派生**无效**（第四轮复核定版已确认），故本仓以「有界工作量」而非「墙钟超时」控制最坏耗时。
- **解除条件**：若需秒级上界或取消能力，须在原生内核引入可取消派生（pass 之间检查取消标志）。
- **依据**：`database/src/main/java/com/keepasskey/database/file/KdbxKdfParameterCodec.kt`（
  `ARGON2_MAX_TOTAL_WORK` / `AES_KDF_MAX_ROUNDS` KDoc）；`docs/records/原生Argon2真机验证记录.md` §9；
  `RESOLVED_LOG.md` §76 / §78。

### 2.2 `ProtectedString` 内存加密为纵深防御层

- **事实**：`ProtectedString` 驻留加密（`InMemoryCipher` 进程密钥）是**纵深防御层**，进程密钥**永不擦除、永不轮换**（读入即常驻，属该原语选择的必然结果，非可「补开关」
  修复）。
- **边界**：持有进程密钥或**任意代码执行**者仍可在读取瞬间截获明文；⇒ 不得据此宣称「内存中无明文」或把它计入对同 UID 攻击者的防护。
- **依据**：`core/src/main/java/com/keepasskey/core/model/MemoryProtectionConfig.kt`；
  `docs/security/退役审计承接-42-威胁建模与架构评估.md`。

### 2.3 原生内核为 Rust，秘密缓冲由 `Zeroizing` RAII 全路径擦除

- **事实**：选择 Rust 的代价是体积，收益是**秘密确定性擦除**与 Argon2 优于纯 Java 路径。
- **互操作证据（2026-09-21 更正后的口径：**文件级对拍已完成**）**：官方客户端对本仓产物的**文件级**端到端对拍**已完成**——`keepassxc-cli 2.7.12` 与
  `pykeepass 4.2.0` 各自独立读出 KPEX 条目（114 条判据全绿、退出码 0；2026-09-21 复跑通过），细则见 §4.3 与
  [`records/通行密钥互操作对拍记录_2026-09-19.md`](../records/通行密钥互操作对拍记录_2026-09-19.md)。
- **依据**：`RESOLVED_LOG.md` §47。

### 2.4 主密码在 Compose 文本状态中为不可擦 `String`（已接受残余）

- **事实**：主密码输入经 Compose `TextField` 承载时，文本状态是**不可擦的 `String`**（`KeyboardType.Password` 已阻挡候选词外泄通道；输入法个性化学习见
  §3.4），因而会作为不可控副本存活至 GC。
- **已接受原因**：可擦形态需要自行实现文本编辑栈（`AndroidView(EditText)` 或自绘输入），属「以稳定性换纸面加固」；且进程内取证者本已在信任边界之外（见 §2.2）。⇒
  该副本**不得**被读作「会话中始终无主密码明文」。
- **依据**：`docs/resolved/batches/41-敏感数据流审计-退役与分流.md:89`（第一轮敏感数据流审计 `M2` 的分流结论；引用更正见[附二](#附二更正留痕按日期) §2.4）。

## 3. 平台行为与窗口加固

### 3.1 原生库懒加载顺序契约

- **事实**：`System.loadLibrary` 经 `NativeCryptoLibrary.loaded` 统一懒加载；各绑定类的 `available` **必须**先求值该属性再发起原生调用，
  否则库未加载时调用 `external fun` 会抛异常（顺序依赖，属已登记的同类限界）。
- **依据**：`crypto/src/main/java/com/keepasskey/crypto/NativeCryptoLibrary.kt`。

### 3.2 `CipherInputStream` 的异常语义

- **事实**：`CipherInputStream` 对填充非法 / 长度非整数倍抛 `IOException`（**非**静默 EOF）。
- **依据**：`RESOLVED_LOG.md` §38；`crypto` 模块 CBC 流式用例。

### 3.4 IME 个性化学习（`ISSUE-P3-76`，已接受残余，不实施）

- **事实**：Compose **1.12.0**（BOM 2026.08.00 钉版；2026-09-21 直读 `~/.gradle` 缓存中的 `compose-bom-2026.08.00.pom`

### 3.5 完整性重扫的 30 s 检测窗口（`ISSUE-P3-152` 复核结论，**不得为省电放宽**）

- **事实**：`RuntimeIntegrityDetector` 以 **30 s** 周期在 IO 线程重扫（root / Magisk 路径、`/proc/self/maps`），并由 **120 s**
  快照陈旧窗口保证「连丢 4 次重扫 ⇒ 非 suspend 门控（生物识别快速解锁等）转 fail-closed 保守策略」。
- **边界（⇒ **不得**据此判定「这是可省的常态开销」）**：该 30 s 既是**注入框架被捕获的上界**，也是高价值通道判定新鲜度的来源；省下的只是每 30 s 一次的文件探测（IO 线程），
  与「判定新鲜度」不成比例。**不得**为省电调大重扫周期或陈旧窗口——`RuntimeIntegrityRescanContractTest` 已把该结论钉成**可执行契约**（放宽即红；该用例另以
  `assertEquals(间隔 × 4, 陈旧窗口)` 锁定两者**精确比例**，故**单独收紧间隔而不等比调整窗口同样会红**）。`ISSUE-P3-152`
  复核时的另一处同类成本（`UnlockedNotificationController` 的 **2 s** 偏好轮询）属**真浪费**（无安全语义，且进程级快照早已存在）⇒ 已改为订阅内存快照、零 IO，见

- **与用户开关的关系（`ISSUE-P3-236` / `PD-15` 补注，2026-09-21）**：本检测改为用户可配置开关、出厂默认关闭，但**关闭只解除通道降级，不停探测**——30 s

### 4.3 通行密钥 KPEX schema 互操作：**文件级对拍已达成**（§149 → §220，§222 补写路径自动迁移与 v1 形态嗅探），交互链路仍未覆盖

- **事实**：§149 批次把通行密钥落库 schema 由自造 `Passkey.*` + hex/Base64 私钥改为 **KeePassXC / KeePassDX 口径**的
  `KPEX_PASSKEY_*` + **PKCS#8 PEM**（EC 用命名曲线 `secp256r1`），读侧三形态兼容（KPEX / v1 旧键 / 外部条目按
  `AlgorithmIdentifier` 的 OID 字节嗅探；§222 起 v1 文本形态也被精确嗅探——64 字符 hex → ES256、32 字节种子 → Ed25519，不再静默回落 ES256）。
- **该对拍当次即暴露并闭环一个真实缺陷（`ISSUE-P2-211`）**：Ed25519 私钥曾被写成 RFC 5958 `OneAsymmetricKey`（`version = 1` +
  `publicKey [1]`）——本仓解码器接受，**OpenSSL 系实现（含 KeePassXC）拒收** ⇒ 已改为 RFC 8410 `version = 0` 最小形态；解码侧**继续接受
  v0/v1** 以兼容存量库。⇒ **不得**再以「格式面按源码口径对齐 + 自家往返」替代外部对拍。
- **边界（不得读作「互操作已全面验证」）**：① 证据是**文件级 / 离库**的：**不含** CM 通道交互，也**不含**「用外部管理器完成一次真实 RP 登录」；② 系统 **CM 选择器 UI 全链路
  + 通知渲染**仍未覆盖（口径见 §4.1），端到端手工冒烟清单见 `records/通行密钥互操作对拍记录_2026-09-19.md` §6，**2026-09-19 尚未执行**；③ **PRF
  仍未与真实 RP 对拍**：只证 `KPEX_PASSKEY_PRF` 的承载形态与保护位被外部实现原样读写；④ **v1 旧条目只在「被用到时」迁移**（`ISSUE-P3-213`，§222 起）：
  条目因断言而被原子修补签名计数器时，在**同一受控变换内**整条换新为 KPEX（全部 `Passkey.*` 旧键清除，私钥重包为 PKCS#8 PEM 写入
  `KPEX_PASSKEY_PRIVATE_KEY_PEM`）；但**从未被断言触及**的 v1 条目仍是旧形态（读侧永久兼容、断言功能不受影响）⇒ 老库与 KeePassXC / KeePassDX
  的互通**不因升级自动成立**，只在「该凭据被实际使用过」之后才成立。另有两条边界：私钥无法重包（形态非法 / 算法不匹配 / 标量越界）时**放弃迁移并保持原文**（fail-safe，只留日志），
  以及迁移**不阻断计数器写入**。
- **依据**：`tools/passkey-interop/`（探针产物 + 对拍脚本 + fixture 生成器）；

## 7. 目录枚举噪声与其派生残余（`ISSUE-P3-142`）

## 8. 弱工作因子告警的**覆盖面**（`ISSUE-P2-87` 的已知残余）

- **事实**：`ISSUE-P2-87`（§110 批次）为「导入 / 打开工作因子过低的库」加了**非阻断**告警，判据由 `KdbxKdfStrengthAssessor`（`database` 模块）给出，

## 16. RS256 保持 BouncyCastle 纯 Java（`ISSUE-P3-153` / §146 实测否定下沉）

- **事实**：真机实测（Redmi 4X / arm64-v8a，预热 + 多轮中位数，见实测记录 §2.2）Rust `rsa` crate 对 BC **更慢**：keygen **2106.5 ms**
  vs **993.0 ms**（慢 2.1×）、sign **17.8 ms** vs **10.9 ms**（慢 1.6×）。
- **边界（**不得**据此断言）**：① **不得**以「Rust 更快」为由重提 RS256 下沉；② **不得**把 ES256 / Ed25519 的 **16~22×** 加速比外推到
  RSA——三者算法不同、实现成熟度不同，结论**只对测过的那对实现成立**（与 `ISSUE-P3-153` 原文「量化前提不得外推」同口径）。
- **现状代价（如实）**：RS256 passkey 的每次断言签名仍走 BC 纯 Java（真机 sign 10.9 ms 量级）。
- **JNI 不构成解释（2026-09-17 第二轮复核）**：Rust 侧数字取自**独立 aarch64 二进制**（无 JVM / 无 JNI），是「无边界」的最优条件；真机实测 JNI 单次固定开销
  **18.956 µs**（16 B 载荷），占一次 RS256 签名（11.8 ms）的 **0.16%** ⇒ 上生产只会更慢。
- **解除条件**：Rust RSA 生态出现经**同法实测**（同机 / 同语料 / 预热 + 多轮中位数）显著快于 BC 的实现；或 BC 退出维护 / 许可面发生变化——届时须重跑对比再决定。
- **依据**：`docs/resolved/batches/146-Passkey签名内核下沉批次.md` §4。

## 17. AES-256-CBC 统一到 Rust 内核后的**性能代价**与 JNI 边界秘密治理面（§147，**取向为可靠性/可维护性，非性能**）

- **事实（双机 10 轮实测，10 MiB，每轮 5 采样中位）**：**10 MiB 中位——现代机（M332BF）加密 48.1 ms / 解密 34.3 ms，A53（Redmi 4X）加密 250.9
  ms / 解密 259.6 ms**；对照 JCE 最优路径为现代 **9.2 / 14.3 ms**、A53 **34.4 / 93.5 ms** ⇒ **额外开销（绝对差）现代机 +20~39 ms、A53
  +166~222 ms（2.4~7.3×）**。
- **成本构成（现代机 48.1 ms，同一份 10 MiB）**：算法本体 **13.3 ms（28%）** + JNI 边界 **21.2 ms（44%）** + PKCS#7 整缓冲垫片与明文擦除
  **13.6 ms（28%）**；对照 JCE `doFinal` **全程仅 9.2 ms**（分解见同记录 §8.2）。
- **边界（**不得**据此断言）**：① **不得**以「下沉更快」描述本项：内核层与现代设备上**均不占优**——现代机 Rust**内核本体**（13.3 ms）已慢于 JCE **全程**（9.2 ms）；
  CBC 加密是串行依赖、逐块调用吃不到 ILP，追不上 OpenSSL 汇编 ⇒ **优化实现不可能翻盘**，「先修实现开销再复测」这条路径已排除；② **不得**把「无感」外推到「老设备 × 大库」：A53
  级设备 5 MB 库约 **+83~111 ms**（非十几毫秒）；20 MB 级库在现代机也到 **+40~78 ms**；③ **不得**把 ChaCha20 的收益外推到 AES：同批下沉的
  ChaCha20 是**绝对巨益**（现代 244.2 → 24.7 ms，省 219.5 ms；A53 3712.5 → 85 ms），两者方向相反；④ **不得**用单一机型的内核数字外推全部机型：同一份
  Rust 代码的 CBC 解密在 A53 为 249 MB/s、现代机为 **5072 MB/s**（现代 OoO 核可把硬件 AES 延迟流水化），差异 20×。
- **已接受的判据（2026-09-18，用户裁定，本节存在的前提）**：`minSdk 36` 面向**现代设备**，主库体积普遍 **<5 MB** ⇒ 额外 **10~20 ms** 落在无感区；
  本项按**可靠性 / 稳定性 / 可维护性**（跨平台统一、审计一致性、单一填充实现）保留，**性能不作为理由**。
- **本项新增的残余风险面（非性能，须持续警惕）**：JNI 边界的**秘密治理**。
- **解除条件**（§215 更新，已按 `ISSUE-P3-198` 重估）：`ISSUE-P3-187` 评估定案后，`ISSUE-P3-198` 已实施并真机验证（2026-09-19，实测见
  [`records/真机吞吐实测记录_2026-09-17.md`](../records/真机吞吐实测记录_2026-09-17.md) §9）。**流式生产路径**（整库加解密的实际形态）的「边界 + 拷贝」
  份额已消除（直扣后 AES 单次 178.9 → 48.7 ms @ Redmi 4X、43.9 → 14.7 ms @ 模拟器，直扣 14.7 ≈ 内核 13.3 × 1.1）；**整块 `byte[]`
  路径**（探针/整库一次性形态）维持拷贝桥——其契约要求返回新数组且输入不动，直扣后 put/get 拷贝量与 JNI 双拷贝等量、无收益，属**已接受残余面**（上表 44% 占比对整块口径仍然成立，
  **不得**据此断言流式路径同比例存在）。另一解除路径不变：RustCrypto 侧出现能吃到 ILP 的 CBC 批处理实现（仅影响加密侧，且仍不足以追平 JCE）。

## 22. 凭据拒绝页「就地授权特权浏览器」的残余边界（`ISSUE-P3-221`，§227）

- **无自动化覆盖的具体缺口（需真机核验的项）**：① 真实系统拉起下，按钮点击后的 `CircularProgressIndicator` 转圈与状态刷新流程度；② 写入偏好后回到浏览器再次发起

## 23. 通道开关的语义上限是「不交付凭据」，而非「从系统服务列表消失」（`ISSUE-P2-228`，§232）

- **边界**：设置页三条通道开关（凭据管理器 / 通行密钥 / 系统自动填充）关闭后，
  本应用对相应通道**一律返回空响应、不产出候选、不接受保存**；
  但本应用**仍会被系统列出**为可用的自动填充服务 /
  凭据提供方——用户看到的是「列表里还在，点了没内容」。
- **语义限定（2026-09-21 更正）**：三条开关**并非同一后果**——通行密钥开关只拦**公钥类**创建请求（
  `app/.../passkey/KeePasskeyCredentialProviderService.kt:248-262`），**密码类**候选与保存**不受其影响**。
- **为何不接受为缺陷**：组件注册由 `AndroidManifest.xml` 声明 + 系统设置选取决定。理论上可用
  `PackageManager.setComponentEnabledSetting(...DISABLED)` 动态摘除，本批**刻意不做**：① 已被系统**选中**的扩展组件被就地禁用，
  会把系统留在「已选中但无响应」的异常态，恢复路径只有用户自己去系统设置改选——比「返回空响应」
  更不可预期；② 「不再交付任何凭据」已覆盖用户关闭通道的**安全意图**（该通道不再流出凭据），
  而「从列表消失」
  属可见性诉求，代价与本收益不成比例；③ 动态组件开关与本仓 Manifest / 权限卫生的静态守卫口径相冲（组件声明面须保持可审计的静态形态）。
- **文案已按此表述**：`autofill_service_sub` / `autofill_cm_sub` 明确写出「系统设置仍会列出本应用，可在其中改选」，不得改写成「已从系统移除」这类做不到的承诺。
- **解除条件**：若系统后续提供官方的「应用内自助停用扩展组件」通道（不产生「选中但无响应」异常态），可在三条开关上叠加该动作；届时须同步改文案并更新本条。

- **事实**：`RuntimeIntegrityDetector` 以 30 s 周期重扫（`LIVE_RESCAN_INTERVAL_MS`；`P3-120` 已真机三形态 **3/3** 命中），但
  `RuntimeIntegrityReport` 在**已解锁的活动会话**期间只驱动四点——设置页风险提示卡、生物识别快速解锁门控、自动填充 / CM 通道门控；**不**调用
  `AutoLockSessionGuard.triggerLock` / `clearSensitiveData`，故已驻留内存的整棵解密对象树不被主动擦除、会话不被锁定。
- **为什么接受**（完整裁决理由见 [`产品裁决登记.md`](产品裁决登记.md) `PD-13`）：`COMPROMISED` 的五项构成中有**三项是纯文件存在性检查**（root 痕迹 / Magisk
  痕迹 / Frida 落点），按「`COMPROMISED` → 熔断」实施会让所有 root / Magisk 设备与「装过 frida 未运行」的设备在解锁后 ≤30 s
  被强制锁库并反复复发（本仓**无草稿自动保存** ⇒ 编辑内容丢失）⇒ 实质不可用；而熔断增益受 30 s
  探测上界限制（缩短暴露窗口，而非阻止已发生的读取），既有四条门控已保证「后续通道不给新秘密」。
- **边界（不得据本条外推）**：① 本条**不**授权放宽 `LIVE_RESCAN_INTERVAL_MS` / `SNAPSHOT_STALE_AFTER_MS`（§3.5 口径不变）；②
  本条**不**授权移除或削弱任何一条既有消费点门控（不得以「反正不熔断」为由放松通道降级）；③
  本条**不**是「完整性检测无效」的声明——检测有效（真机 3/3），本条只界定**探测结果的处置粒度**。
- §3.5 已就地补注；本节的裁决理由与解除条件（`PD-13`）不因此改变，但**不得**把本节读作「防护默认已生效」。
- **解除条件**：`PD-13` 的三条重开条件同时满足后（等级语义细分出「确证即时附着」、`beingTraced` 进入周期重扫快照、具备真机验收条件），可评估按「确证注入」单独熔断。

## 27. 系统设置页一键直达入口的可用性取决于 ROM（缺 activity 时**如实降级为纯文案**）（`ISSUE-P2-239`，§247）

- **为什么不整改**：`SystemSettingsNavigation` 的三条硬约束（可解析才给入口 / 启动失败不崩 / **不做反射 hack**，只用公开 `Settings.ACTION_*`）
  是本仓既有立规——为「让按钮一定出现」而改走厂商私有页面或强制 `startActivity`，等于把排障入口变成新的崩溃点与不可移植路径。
- **边界（不得据本条外推）**：① 本条**不**是「这些入口无用」——在提供对应 activity 的 ROM（含 AOSP / Pixel 系）上照常渲染，故 `ISSUE-P3-41` /
  `ISSUE-P3-215` 的接线与守卫（`OneTapInteractionWiringTest`）**一行不得放宽**；② 本条**不**授权删除纯文案指引，也**不**授权把文案改成「已开启 / 已启用」
  一类断言；③ 本条**不**覆盖「action 可解析但启动被 ROM 拦截」的情形（那条由 `launchSafely` 静默降级承接）。
- **解除条件**：目标 ROM 补齐这两个 Settings 落点，或官方提供可解析的等价入口（届时可直接复测 `resolve-activity` 由无命中转为有命中，无需改代码）。
- **依据**：批次正文 §247；`app/.../ui/components/SystemSettingsNavigation.kt`（三条硬约束 KDoc）、

  `cmd package resolve-activity` 三条 action 对照读数见批次正文 `docs/resolved/batches/247-凭据提供者通道健康检查批次.md` §4。
